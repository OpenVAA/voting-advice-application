# Analytics

This page is for the developer or deployer who wants usage analytics from an OpenVAA instance. It describes the relay through which the frontend sends its events, the catalogue of events it sends, how to add an analytics provider, the mechanism that keeps a voter's answers and identity out of the events, and the checklist a deployer works through before turning analytics on. The variables the relay reads are listed on [Environment variables](/developers-guide/configuration/environmental-variables).

## Event catalogue

The table lists every event the browser may send, one row per event of the closed vocabulary in [`events.schema.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/analytics/events.schema.ts). A unit test, `apps/frontend/src/lib/analytics/eventCatalogue.test.ts`, fails when a row is missing for an event of the schema or names an event the schema does not have.

Every event shares one envelope, which the Fields column leaves out: its name, the time the relay stamps on it (its receive time less the event's age in the batch), the app it belongs to (`voter`, `contestant` or `admin`, taken from the route of the view) and, on every event but the pageview, the visit id when the modes allow it (see [Privacy mechanism](#privacy-mechanism)). An event is put in a buffer when it happens and sent with the next batch: at the next client navigation, when the tab is hidden, or when the page is left.

The last column is for the default consent mode, `gated`. **Sensitive** marks the events in `SENSITIVE_EVENTS`, which say how a visitor answered or which entity they looked at: in `gated` mode they carry the visit id once consent is given, so they can be linked to the visit's other events, and in `free` mode they never carry it.
