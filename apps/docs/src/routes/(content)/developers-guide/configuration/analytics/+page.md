# Analytics

This page is for the developer or deployer who wants usage analytics from an OpenVAA instance. It describes the relay through which the frontend sends its events, the catalogue of events it sends, how to add an analytics provider, the mechanism that keeps a voter's answers and identity out of the events, and the checklist a deployer works through before turning analytics on. The variables the relay reads are listed on [Environment variables](/developers-guide/configuration/environmental-variables).

## How it works

The browser never talks to an analytics service. It sends its events in batches to the frontend's own address, `/api/usage`, with one same-origin request at a time. The frontend server's relay ([`relay.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/relay.ts)) checks each request, validates every event against the schema, rebuilds the events it keeps, and puts them in a bounded in-memory queue. It answers as soon as the events are queued. The queue hands them to the configured provider on its own timer, every `ANALYTICS_FLUSH_INTERVAL_MS` milliseconds (2000 by default), and once more when the server shuts down. While a provider is slow or down, events beyond the queue's cap of 1000 are dropped and only their number is logged. A content blocker may still block `/api/usage`, and nothing works around that, so every count is a lower bound.

Five settings decide what is collected. All but the last are server environment variables, read when the server starts and listed under [Analytics on the environment-variable page](/developers-guide/configuration/environmental-variables#analytics):

- **The provider**, `ANALYTICS_PROVIDER`: one of the names in `PROVIDERS`, `none`, `log` or `posthog`. `none`, the default, keeps nothing: the relay reads nothing of the request and answers 204. `log` writes each event as one JSON line to the server's output stream, for the container's log store to keep. `posthog` forwards the events to PostHog, at `ANALYTICS_POSTHOG_HOST` (the EU cloud by default) with the project key `ANALYTICS_POSTHOG_KEY`. A production server refuses to start when any analytics variable has a problem, such as an unknown provider or `posthog` without its key, and names the variable; in development the same problem resolves the provider to `none`, so a misconfigured server sends nothing.
- **The consent mode**, `ANALYTICS_CONSENT_MODE`: `gated` by default. In `gated` mode no event but the pageview is sent until the visitor consents: the voter through the consent prompt, a candidate or a party by accepting the terms of use without ticking the box that opts out. In `free` mode events are sent without asking, and the sensitive events never carry the visit id.
- **The visit-id mode**, `ANALYTICS_VISIT_ID_MODE`: `memory` by default. In `memory` mode the events of one page life share one visit id, held in memory only. In `none` mode no event carries a visit id.
- **The server pageview.** A pageview is sent for every view whenever a provider is configured and the browser does not send Global Privacy Control, whatever `trackEvents` and the consent choice are. The server builds its record from the route, the locale, the route parameters the route's allowlist admits and a coarsened duration, and never gives it a visit id. So with any provider but `none`, the server pageview is recorded in any case.
- **`analytics.trackEvents`**, a dynamic setting of each project's [app settings](/developers-guide/configuration/app-settings), `false` by default. It is respected: while it is `false` no event but the pageview is sent, whatever the consent mode, and the consent prompt is not shown. It is changed in the project's stored settings, not in the environment.

A browser that sends Global Privacy Control sends nothing, the pageview included, and a request that carries `Sec-GPC` is dropped by the relay and answered exactly as an accepted one.

## Event catalogue

The table lists every event the browser may send, one row per event of the closed vocabulary in [`events.schema.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/analytics/events.schema.ts). A unit test, `apps/frontend/src/lib/analytics/eventCatalogue.test.ts`, fails when a row is missing for an event of the schema or names an event the schema does not have.

Every event shares one envelope, which the Fields column leaves out: its name, the time the relay stamps on it (its receive time less the event's age in the batch), the app it belongs to (`voter`, `contestant` or `admin`, taken from the route of the view) and, on every event but the pageview, the visit id when the modes allow it (see [Privacy mechanism](#privacy-mechanism)). An event is put in a buffer when it happens and sent with the next batch: at the next client navigation, when the tab is hidden, or when the page is left.

The last column is for the default consent mode, `gated`. **Sensitive** marks the events in `SENSITIVE_EVENTS`, which say how a visitor answered or which entity they looked at: in `gated` mode they carry the visit id once consent is given, so they can be linked to the visit's other events, and in `free` mode they never carry it.

## Adding a provider

A provider is one file under [`apps/frontend/src/lib/server/analytics/providers/`](https://github.com/OpenVAA/voting-advice-application/tree/main/apps/frontend/src/lib/server/analytics/providers). Each implements `AnalyticsProvider` from [`provider.type.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/providers/provider.type.ts): a `name` and a `capture(events)` that hands one batch on and always resolves, logging a failure without any event content. A provider receives the events only, never the request that carried them, and takes its `fetch`, its output stream and its random-id function from `ProviderDeps`, so a test can pass stand-ins. [`posthog.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/providers/posthog.ts) is the example that forwards over the network, [`log.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/providers/log.ts) the one that writes locally.

To add one, follow these steps.

1. Write the provider's file under `providers/`, with a unit test beside it.
2. Add its name to `PROVIDERS` in [`config.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/config.ts).
3. Add its case to the switch of `createProvider` in [`providers/index.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/analytics/providers/index.ts), the only code that names a provider. A provider that needs settings resolves them in `resolveAnalyticsConfig`, and a missing setting is a problem that refuses start, as `posthog` without its key is.
4. Add each variable it reads to `ANALYTICS_ENV` in `config.ts`, and to the frontend task's environment list, [`task-environment.json`](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/modules/frontend-service/task-environment.json): a secret, whose name ends in `KEY`, `SECRET`, `PASSWORD` or `TOKEN`, is a `parameter` read from the parameter store, and any other variable a `value`.

The guards then require the rest. The unit test of the task environment, `taskEnvironment.test.ts`, fails until the list holds every name of `ANALYTICS_ENV`, each name appears in the root `.env.example` and in the environment section of the staging AWS runbook, and every AWS root's `terraform.tfvars` sets each new `value`. The test of the environment-variable reference, `environmentReference.test.ts`, fails until each name is listed on [Environment variables](/developers-guide/configuration/environmental-variables). The scan in `noAddressOrAgent.test.ts` covers the new file too, and fails if it reads a client address or a user agent or computes a hash.

## Privacy mechanism

What the relay reads and keeps is fixed in code, whatever the provider:

- **No address, no software, no cookie.** The relay reads five request headers by name, `sec-gpc`, `sec-fetch-site`, `origin`, `content-type` and `content-length`, and the body. It reads no client address, no user agent and no cookie, and computes no hash of anything. A standing unit test, `noAddressOrAgent.test.ts`, fails when analytics code reads a client address, a user agent or a forwarded-address header, or calls a hashing function.
- **Only what the schema admits.** Each event is parsed against the closed vocabulary, strict at every level, so an unknown field anywhere drops the event. No field admits text a visitor typed: content is named by an id, an index or a count, except the localised title of an information section, which is published content. The kept event is rebuilt from the admitted fields, a video's media URL loses its query string and fragment, and the relay refuses a request that is not same-origin (403), not JSON (415) or larger than 32 KiB (413).
- **The pageview has no id.** The server builds the pageview from the batch's route, its locale, the parameters the route's allowlist in [`pageviewRoutes.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/analytics/pageviewRoutes.ts) admits (never one that identifies an entity or a nomination) and a duration rounded down to 100 ms and capped at six hours. The PostHog provider gives each pageview a fresh random id, so a pageview is never linked to other events.
- **The visit id joins one page life at most.** In `memory` mode the id is a UUIDv7 held in a module variable for the life of the document. It is never written to a cookie or a browser store, so a reload starts a new one and nothing on the device links two visits. In `none` mode there is no id, and in `free` mode the sensitive events never carry it. The relay applies the same rules again on arrival, and also removes an id that is not a UUIDv7 or whose time stamp lies more than a day from its clock.
- **What an event can be linked to.** With a visit id, an event can be linked to the other events of the same page life: in `gated` mode after consent, the answers, the results viewed and the filters used in that visit. Without one it stands alone. No event carries anything that identifies the visitor's device or person, and nothing is kept in the browser for analytics but the consent choice.
- **What a provider sees.** The PostHog provider sends each batch from the frontend server, so PostHog receives the server's address, never the visitor's, and the only request header it sets is the content type. Each item asks PostHog to keep no person profile (`$process_person_profile: false`) and to derive no location (`$geoip_disable: true`). The log provider's line holds the event and nothing of the request; where it is kept, and for how long, is the log store's retention.

On the staging PostHog project, in PostHog's EU cloud, the project's setting that discards client IP data read back through PostHog's API as `anonymize_ips` true on 2026-11-19, and the operator found that the project offers no GeoIP transformation to turn off (phase 188 record). The same day, the events of one consenting browser journey carried no `$ip`, no `$geoip_` property, no user agent, URL, referrer or host, and no person profile, as recorded in the [staging AWS runbook's observations](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/envs/staging/aws/README.md#observations).

## The deployer's checklist

Whether a deployment may collect usage data, and whether it must ask for consent first, is the deployer's determination to make for their own jurisdiction, and so is every item below. The repository makes no such determination: each item says what it does by default and where to change it, and leaves the answer to the deployer.

- **Consent mode.** Do you ask visitors before collecting their events? The default, `ANALYTICS_CONSENT_MODE=gated`, sends no event but the pageview until the visitor consents; `free` sends them without asking and keeps the sensitive events unlinked. You choose the value in the task environment, as described in [How it works](#how-it-works).
- **`trackEvents`.** Do you collect the detailed events at all? `analytics.trackEvents` is `false` by default, so a deployment with a provider counts only pageviews until you turn it on in the project's [app settings](/developers-guide/configuration/app-settings).
- **Visit-id mode.** Do you link the events of one page life to each other? `ANALYTICS_VISIT_ID_MODE=memory`, the default, does, within one document only; `none` links nothing.
- **The server pageview.** Do you accept that, with any provider but `none`, every view is counted whatever `trackEvents` and the consent choice are? Its record holds the route, the locale, the allowlisted route parameters and a coarsened duration, and no id. The only switch is the provider itself, and a browser that sends Global Privacy Control sends none.
- **The provider's region and terms.** Where does the provider keep the events, and under which data-processing terms? The default PostHog host is PostHog's EU cloud, `https://eu.i.posthog.com`, set by `ANALYTICS_POSTHOG_HOST`; with `log`, the events are kept where the container's logs are, in the region of your log store. Reading and accepting the provider's terms is yours to do; the repository signs nothing.
- **PostHog's IP capture and `$geoip_disable`.** Does your PostHog project discard client IP data? The relay sends from the frontend server, so PostHog sees the server's address and never the visitor's, and every event asks PostHog to derive no location (`$geoip_disable: true`) and keep no person profile. The project's own IP setting is set in PostHog, not by the repository; on staging it read as discarding client IP data on 2026-11-19, as [Privacy mechanism](#privacy-mechanism) records.
- **The billing limit.** What may the provider charge, and what happens to events past the limit? The repository sets no limit; you set it in the provider's billing settings. On staging the PostHog Product analytics limit was set to 20 USD on 2026-11-18 (phase 188 record), and the operator found no sentence on the billing page saying what happens at the limit.
- **Retention.** How long are events and logs kept? The PostHog project keeps events for as long as its plan and settings say. The frontend's log group keeps the server's log lines, and with `log` the events, for `log_retention_days`, 90 days in the example and staging roots, and the module accepts only a retention CloudWatch Logs offers, never forever.
- **The terms of use.** Do the terms tell candidates and parties how their use is measured? When a provider is configured and `trackEvents` is on, the Contestant App's terms of use show a paragraph on usage data, `privacy.usageData.content`, with a box to opt out; the voter's privacy page shows `privacy.analytics.content.gated` or `privacy.analytics.content.free` by consent mode, and `privacy.analytics.pageviews`. The texts are in `apps/frontend/messages/<locale>/privacy.json`; whether they say enough is yours to judge.
- **The address `account-access` keeps.** Do you accept that the caller's address is stored to limit three operations of the `account-access` function? Behind Cloudflare, with `behind_cloudflare` true, the function keys its per-caller limit on `cf-connecting-ip`, which Cloudflare sets to the connecting client, and stores that address in clear as part of a key of `private.invitation_throttle` for the 10-minute window, after which a later request deletes it. With the setting `false` there is no per-caller limit and no address is stored. See [The per-caller limit of account-access](/developers-guide/deployment#the-per-caller-limit-of-account-access).
- **The address the feedback limit keeps.** Do you accept that each feedback sender's client address is stored? The feedback limit keeps it in clear as the key of its row in `private.feedback_rate_limits` (`cf-connecting-ip` behind Cloudflare, otherwise the last `x-forwarded-for` hop) with a count and the start of its window, and nothing deletes the row: the address stays with no expiry until you purge the table yourself. See [Feedback rate limit and Cloudflare](/developers-guide/deployment#feedback-rate-limit-and-cloudflare).
