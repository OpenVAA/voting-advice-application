# Login and password reset

Candidates sign in to Supabase Auth with an email address and a password. The session is kept in cookies that the SvelteKit server sets, so the server-side loaders of the Contestant App see the same session as the browser (see [Sessions](/developers-guide/backend/authentication#sessions)).

## Login

The login screen, `/contestant/login`, holds no form: "Sign in with email" leads to the sign-in screen, `/contestant/login/email`, and "Register" to the registration screen (see [Registration](/developers-guide/contestant-app/registration)).

A notice under the login screen's title says why a visitor was sent there, for the reasons `$contestant/utils/loginError` knows. The `errorMessage` search parameter names `loginFailed`, `authError` or `emailTaken`, as the sections below describe, and two reasons for a session that ended without the user pressing Log out in that tab (see [Logout](#logout)): `loggedOutAutomatically` after the end of a logout count in the tab that counted, and `loggedOutElsewhere` after a sign-out the tab follows from another tab or window. That second reason is given only when, at the client's `SIGNED_OUT`, the tab had heard the other tab's Log out announce its `start` on the `BroadcastChannel` named `openvaa-logout` with no `end` since, no more than 30 seconds before, or its `end` no more than about 5 seconds before; any other sign-out the tab did not start, such as one the auth client makes by itself when it finds its session gone, leads to the login page with no reason. The candidate context's `logout` puts the first on the login page's address when it is given it as its reason, and the context builds the second itself. The reason `loggedOutAutomatically` also comes from the page's server load: after the server's sign-out at the end of a logout count, the load finds the settled value the request hook wrote into `COOKIE.logoutPending` (see [Logout](#logout)). The address bar's reason is shown first. Any other value shows nothing, and no text from the address bar is rendered. While the notice is shown, the heading the page focuses on arrival names it as its description. The sign-in screen posts its form to its own server action, [`login/email/+page.server.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/routes/contestant/login/email/+page.server.ts). The action calls the shared `passwordLogin` helper with the request's own Supabase client, so that the session cookies are set on this response:

1. It signs in with `signInWithPassword`. Wrong credentials give `400`, and nothing else runs.
2. It claims the user's invitations: the data writer's `claimInvitations()`, on the request's own client, calls `claim_invitations` as the user just signed in.
3. When the claim wrote a grant, it refreshes the session with `refreshSession()`, so that the access token lists the grant.
4. It reads the session back. A missing session gives `500`.
5. It checks the grants in that session's access token against `CONTESTANT_GRANTS`, which admits an `editor` grant on a `candidate` or an `organization` entity. Any other user, the editor of a faction or an alliance included, is signed out again and gets `403`. This is an entry gate only: whether the project serves the editor's entity type is decided after sign-in, and the database's policies decide what the user may read or write.
6. It redirects to the `redirectTo` path from the form, if that is a safe relative app path, or to the Contestant App home page.

The screen shows one sentence for a refusal, chosen by its status alone: `400`, which a wrong address, a wrong password and an account with no password all answer, shares one sentence; `403` says the user has nothing to edit; anything else is the unknown error. A press with a field empty posts nothing, and the empty field says what to enter. The form works before the page's script has loaded; a refusal posted without the script shows the same sentence, with the address field empty.

Under the password field the form holds two links to the forgot-password page: "Forgot Password?" and, for a user who has no password yet, "I have not set a password yet". The second is rendered when the `email` or the `identity_provider` registration mode is allowed for a served entity type (`signInLinkOffered`), whatever the answers lock says. Both are `PasswordSignIn`'s, and both carry the address typed so far in the page's `email` search parameter, so that the forgot-password page's field holds it; neither needs one, and the screen asks for no mail itself. The forgot-password page's request serves both users (see [Password reset](#password-reset)). A user who signs in on the screen leaves the entry flow empty.

Steps 2 to 5 are the shared `admitSession` helper ([`$lib/auth/sessionAdmission.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/auth/sessionAdmission.ts)). The claim comes before the gate because the gate reads the token: an invited person who signs in with a password for the first time holds no grant until the claim writes it and the refresh puts it into the token. A claim that fails is logged, no refresh is made, and the gate reads the token as the sign-in issued it. The Admin App's login action runs the same steps and gates on `ADMIN_GRANTS`. See [The order every entry point follows](/developers-guide/contestant-app/pre-registration-and-invitation#the-order-every-entry-point-follows).

`invitationCodeLogin`, in the same directory, is the same sequence for a sign-in with an invitation code and a password: it calls the data writer's `signInWithInvitationCode` in place of step 1 and then `admitSession`. The code sign-in screen's server action, [`register/sign-in/+page.server.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/routes/contestant/register/sign-in/+page.server.ts), calls it after asking whether the code mode is offered.

The pages under `/contestant` that need a candidate live in the `(protected)` route group. Its server loader redirects to the login page when there is no session, and then reads the user-level data and the list of the entities the user edits. The pages that show an entity live below it, under the two route params `[entityType]/[entityId]`, so the URL names the entity: `/contestant/candidate/<id>/profile`. Their own server loader checks that entity against the list and then reads it. A URL that names an entity the user does not edit is redirected to the app root, `/contestant`. The root redirects a user who edits exactly one entity to that entity's home, lets a user who edits several choose one, and shows a signed-in user with nothing to edit a screen that says so, with the email address they are signed in with, the support block and a logout button, instead of signing them out. A protected path that names no entity, such as `/contestant/profile`, is redirected to the same page under the user's one entity, and to the root otherwise. When the user-level data cannot be read, the protected loader signs the user out and redirects to the login page with the `errorMessage` search parameter `loginFailed`, which the login page shows. When that sign-out fails it is logged and the request's client is asked whether a session is left. When none is left, as after a failed call to the auth service, which removes the session before it answers, the redirect follows as after a sign-out that worked. When one is left, or the client answers an error, the error page is shown, because the gate would send a live session straight back from the login page. An entity with no nomination is not signed out: it reaches its home, and its profile, questions and preview stay closed until it has one (see [The home, the tasks and the nominations view](/developers-guide/contestant-app/home-and-tasks)). No loader looks at the kind of grant the user signed in with: the list of the entities the user edits decides.

## Password reset

A forgotten password is reset through a recovery link that the [`account-access`](/developers-guide/backend/edge-functions#account-access) Edge Function mails. The frontend sets the new password on the session the link creates.

1. **Request.** On `/contestant/forgot-password` the user types their email address, or finds it already in the field when a sign-in screen's link carried it in the `email` search parameter; the page reads the parameter once, when it is created, and asks for nothing until its button is pressed. The page asks for a recovery link through the contestant context's `sendEntryLink`, which calls the data writer's `requestPasswordRecovery`: the `request-recovery` operation, with the address and the reader's locale. The function answers `{ "accepted": true }` before any work, so the page shows the same "email sent" screen to every visitor, whether or not the address has an account. The page is open to a signed-in user too: one who asks for a link here sees the "email sent" screen like anyone else, with the mail sent, because that screen is not one of the gate's entry routes. With no link held, as after a reload or a visit by its address, the screen leads to the login screen, which sends a signed-in user to the app's home.
2. **Mail.** After its answer the function asks the database which mail the address earns. An account with a confirmed address that holds a grant reaching the project is sent the recovery mail: a project grant on the project, an entity grant on one of its entities, any global grant, or an account grant on the project's account, whatever its role; an address that has an open invitation and no account yet is sent the sign-in mail instead, because it has no password to recover; anyone else is sent nothing. The recovery request and the sign-in request share one mail slot per address (see [Email](/developers-guide/backend/email#the-recovery-link)).
3. **Confirm page.** The recovery link is `<SITE_URL>/<locale>/auth/confirm?token_hash=…&type=recovery`. It opens the confirm page, whose Continue verifies it, claims the user's invitations and redirects to `/contestant/password-reset`.
4. **New password.** The reset page's server load decides by the session alone: a visitor with no session is redirected to the login screen before any of the page is rendered, and every signed-in user is shown the page, however they arrived. It returns the verified user's address, which the page shows and hands to the password form. Saving calls the contestant context's `setPassword` and leads to the app root with the loads rerun. The page asks for no current password.

A link's `type` is a landing hint and nothing more. The auth service accepts a sign-in token presented as `recovery`, so whoever holds a link can change the type it names; the confirm page lands by the type, and the reset page therefore does not read "arrived with `type=recovery`" as "asked for a recovery".

The local auth server redirects only to `site_url` and the URLs in `additional_redirect_urls`, both in the `[auth]` section of [`config.toml`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/supabase/supabase/config.toml). The list admits the confirm page's path, `/auth/confirm`, with and without one locale segment in front of it. A hosted project needs the same entries in its Auth URL configuration.

The forgot-password, "email sent" and password-reset screens are shared components, `ForgotPasswordScreen`, `EmailSentScreen` and `PasswordResetScreen` in `$lib/dynamic-components/accountScreens`, which each app's page renders over its own context. The entry flow behind "email sent" is one `EntryFlowHolder` (`$lib/auth/entryFlow`), which each app's context holds.

### Recovery in the Admin App

The Admin App's login, `/admin/login`, has the same two links under its form, "Forgot Password?" and "I have not set a password yet", with the same labels, the ones the recovery mail quotes. Both lead to `/admin/forgot-password`, carrying the address typed so far. That page asks through the admin context's `sendEntryLink`, which calls `requestPasswordRecovery` with `app: 'admin'`, and leads to `/admin/email-sent`. The `account-access` function then writes `next=/admin` into the link it mails, the recovery link or the sign-in link alike, so the link lands in the Admin App: a recovery link on `/admin/password-reset`, a sign-in link on the Admin home, where the Admin App's set-password gate asks a user with no password to choose one. The Admin App's password-reset page's server load redirects a visitor with no session to the Admin login. A request the Contestant App makes names no app, and its links are as they always were.

A signed-in candidate changes their password on the settings page, which also calls `setPassword`. [Password validation](/developers-guide/contestant-app/password-validation) describes the checks the set-password gate, the reset page and the settings page run.

## The confirm page

Every mailed link opens the confirm page, `/<locale>/auth/confirm` ([`+page.server.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/routes/auth/confirm/+page.server.ts)): the recovery link, the sign-in link of an invitation or of a returning user, and the link that confirms the address an account the identity provider made gave. The page's load verifies nothing, so fetching a link spends no token; [Sessions](/developers-guide/backend/authentication#sessions) describes the page. The token is spent when the person presses Continue: for a link of a type it accepts, the page's action signs out any session the browser holds, then hands the link to `verifyMailedLink` ([`$lib/server/auth/mailedLink.ts`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/frontend/src/lib/server/auth/mailedLink.ts)), which runs four steps in order: it verifies the token with `verifyOtp`, claims the user's invitations with the data writer's `claimInvitations()`, refreshes the session when the claim wrote a grant, and only then chooses where the user lands, by the link's `type` and, for the app, by its `next`:

| `type`                      | Lands on                                                                                |
| --------------------------- | --------------------------------------------------------------------------------------- |
| `recovery`                  | the app's password reset page                                                           |
| `magiclink`                 | the app's home; the app's login page with `errorMessage=authError` after a failed claim |
| `email_change`              | the Contestant App root, whatever `next` says; after a failure, see below               |
| any other type, or no token | the app's login page with `errorMessage=authError`; the token is not verified           |

The app is the one the link's `next` names, read through one allow-list, `MAILED_LINK_LANDINGS` in `$lib/server/auth/mailedLink.ts`: the exact value `/admin`, which the `account-access` function writes for a request made in the Admin App, names the Admin App's home, password-reset page and login; every other value, and none, names the Contestant App's. `next` is looked up as a key of the table and never used as a path, so no link can lead anywhere the table does not name. The confirm page's load and action, and the server route `/api/auth/callback`, read `next` through the same table before they refuse a link, so a refused or failed link the Admin App asked for lands on the Admin login, which says the link could not be used (`adminApp.login.errors.linkFailed`).

A link with no `next`, which every request the Contestant App makes earns, lands in the Contestant App, for an admin too. The Contestant App's protected load then sends a session whose grants open the Admin App and not the Contestant App (`isAdminOnly` in `$lib/auth`: an admin grant at global, account or project scope and no editor grant on a candidate or an organization) to the Admin home, after the session check and before it reads anything else. So an admin who asked for a link on the Contestant App's pages meets the Admin App's set-password gate, never the Contestant App's gates or its empty entity list. A user who also edits a candidate or an organization stays in the Contestant App.

The sign-in link is of the type `magiclink` for a first-time and for a returning user alike, and the page does not tell the two apart: a user with no password meets the set-password gate on the first protected page (see [The set-password gate](/developers-guide/contestant-app/registration#the-set-password-gate)). When the claim fails on the `magiclink` arm, `verifyMailedLink` signs the session out and redirects to the app's login page with `errorMessage=authError`; on the other arms a failed claim is logged and the landing goes ahead. Nothing issues a link of the types `invite`, `signup` or `email`, and verifying one for an invited account would store a password nobody chose, so the page refuses them, and every type it does not mail, before verifying.

A link that confirms a new address, of the type `email_change`, makes that address the account's sign-in address and answers with a session. A verification that answers no session confirmed nothing, because the auth service still waits for the account's current address, so it is taken for a failure, as an error is, and nothing is claimed. A failure lands on the login page, because Continue has signed out any session the browser held before the link was verified: with `errorMessage=emailTaken` when the verification failed as a taken address does (status 500 with no error code), and with `errorMessage=authError` otherwise. Any other server error with status 500 and no code is read the same way.

The page applies no grant gate. When an account whose address another account has taken signs in again, the protected layout reads the account's own pending address and shows the identity provider's view asking for another address, with a notice that says so. The server route `/api/auth/callback` verifies nothing: it redirects a link that names it to the confirm page with the same parameters. A user who lands on the Contestant App root with nothing to edit there, such as the holder of a project grant only, sees the screen that says so.

## Logout

The logout button opens a modal over a page holding an unsaved change, which it reads through `hasActiveNavigationGuard` in `$lib/components/preventNavigation/navigationGuards`, where `PreventNavigation` registers its guard. The modal says the change will be lost. Continue, its close button, Escape and a close the platform makes, such as a phone's back gesture, keep the change, because nothing is done to it: the user stays signed in, on the page, with the change and its draft, and the count stops. A navigation closes the modal before the new page is written, so a page's guard is not read across the route change, and a guard's `isActive` must not throw. The modal's Log out and the end of its count call the candidate context's `logout`. The end of its count passes the reason `loggedOutAutomatically`, which `logout` puts on the login page's address as `errorMessage`, so the login screen says the user was logged out automatically; the modal's Log out and a press that logs out at once pass none. Of overlapping calls, which are one logout, the first call's reason is carried.

The count ends by the clock. `TimedModal` keeps its end as a time on the wall clock from the moment it opens, and checks it every second and whenever the tab is shown, restored from the back-forward cache, focused or resumed, so a count whose tab was asleep, frozen or in the background ends as soon as the tab comes back rather than after the rest of it, and ends once. A tab closed during the count does not keep the session. While the modal is open the button keeps two cookies: `COOKIE.logoutPending`, an opaque id of the count, kept as long as the session cookie, and `COOKIE.logoutDeadline`, the same id, which the browser drops at the count's end plus ten seconds by its own clock. A request that carries the first without the second is signed out by `logoutDeadlineHandle` in `hooks.server.ts`, before the gate reads the session, so a protected page goes to the login page, and the hook marks the first settled in the same response, so a sign-in after it keeps its session. The login page that request lands on says why: its load reads the settled value and shows the notice `loggedOutAutomatically`, and the heading it focuses names the sentence as its description. A tab that reaches the login page only after another tab has met the server's sign-out finds the value already removed and shows no reason. No clock is compared across the network: a device whose clock is off neither ends the session early nor keeps it late. The tab's next navigation or the next document then removes the Contestant App's drafts, as the count's own sign-out does, and both cookies. Both go too when the modal closes in any way; when the button's sign-out starts, before its request, so a sign-out that fails at the count's end is not made again later by the server; at the start of any Log out of either app, before its request, whoever wrote them, and on the server, at every sign-in and every sign-out it makes, so a count a closed tab left cannot end a session signed in after that Log out; and when the tab that held the modal is reloaded. A page of another tab leaves them, and so does a page restored from the back-forward cache whose modal still counts. Log out is browser-wide: a count whose tab is closed ends the session in every tab of that browser at its next request, with their drafts, as a count left running in an open tab does.

While that sign-out runs, the modal stays: its close button and Escape do nothing, and a close the platform forces opens it again, through the modal's `holdOpen`, which the button holds up while it is leaving. At the end of its count the modal waits for the sign-out to settle before it closes. A link pressed while any sign-out the button started runs asks nothing and waits: the button runs `logout` inside `holdNavigationWhile`, and its `beforeNavigate` callback, a function of each button's own that calls `holdNavigation`, both in `navigationGuards`, cancels the navigation and remembers where it led. After a sign-out that worked the user is on the login page and the link is dropped; after one that failed the link is followed, and the page's guard asks as it does for any link. A Back or Forward held the same way is followed as the same move in the history, with `history.go`, so it leaves no extra entry. `PreventNavigation` asks nothing while `isNavigationHeld()`, and does not stop the tab from closing during a sign-out.

The context's `logout` asks nothing. It runs the Supabase data writer's `_logout`:

1. In the browser, it posts to the server route `/api/auth/logout`, which signs out on the server with `signOut({ scope: 'local' })` and so clears the session cookies on its response.
2. It then signs out the browser's own client the same way.

The order after those two steps is the guard's `discardGuardedEdits`, the navigation to the login page with the guards stood down, and then the reset, which clears the candidate's data from memory and their drafts from `localStorage`. Once the sign-out has succeeded the browser always leaves: a navigation that did not move it, or that rejected, is followed by the reset and `leaveByFullLoad`, a full load of the login page whose promise never settles, so the guards stay stood down until the document has gone. Overlapping calls are one logout.

A sign-out that fails rejects. The page stays, nothing is reset, the edits stay, and the message `common.logoutFailed` is shown, from the contestant layout. The message goes when the user closes it, when the next logout starts, when the session reads as gone, and on any of the app's entry routes, as `isEntryRoute` in `$lib/routes` reads them. Every entry route has a server load, so a client-side navigation to one is a request the gate answers, in dev and in production alike: a live session is sent to the app's home, with the message still there, whenever a request reaches the gate. A page that makes no request can still stand on an entry route: one restored from the back-forward cache, a form left open while the user signed in in another tab, and the stale tab the [authentication page](/developers-guide/backend/authentication#known-residuals) describes. So a request that reaches one found no session. Every way to a sign-in passes an entry route or a new document, so the message does not follow into the next sign-in, which a test shows by signing in again. A Back the gate redirects writes no history entry: the page is the home, the address bar keeps the entry route's address until the next navigation, and a further Back moves on as usual. The "email sent" screen is not one of the gate's entry routes, by decision. With a live session the message stays there and is true. After a failure that cleared the cookies, Back to that screen still shows the message, though the session has gone, until the next entry route. After a failure that cleared the cookies, the message also stays on the other pages with no server load, Help, Privacy and the forgot-password page, until the next entry route. One row is accepted: during an auth outage with the cookies kept, the session read finds no session, the gate lets the request through, and the message goes on the entry route though it is still true. A user is told only while the document stays and until a link reaches the gate, and a press of the header's Log out on that screen says nothing. The cookies read as signed in once the service is back, until the next Log out. The session read does not tell the two apart, by decision.

The Admin App's Log out goes through the admin context's `logout`. A failure sets `logoutFailed`, and the admin layout shows the same message under the same rule. Once the sign-out has succeeded the browser always leaves: a navigation that did not move it, or that rejected, is followed by `leaveByFullLoad`. Overlapping presses are one sign-out. The Admin App's login page says why, as the Contestant App's does: after a sign-out followed from another tab whose Log out it heard announce its `start` or its `end`, under the rule the next paragraph states, the admin context opens it with `errorMessage` `loggedOutElsewhere`, after any other sign-out the tab did not start it opens it with no reason, and after the server's sign-out at a count's end its load reads the settled value and answers `loggedOutAutomatically`, which the page shows before the `loginFailed` the gate puts on the address bar; its heading takes the focus on arrival and names the sentence as its description.

A sign-out the browser makes in one tab sends the app's other open tabs, in either app, to its login page at once, through the data writer's `onSignOut`, and a tab's stored drafts follow another tab's removal of them, so its next edit does not store a removed draft again. The login page names another tab as the cause only when that tab announced it. A Log out of either app, and the Admin App's sign-out of a user who is no administrator, posts `start` on the `BroadcastChannel` named `openvaa-logout` (`$lib/auth/logoutAnnouncement`) before its sign-out request and `end` once that request has settled, worked or failed, and each app's context listens on that channel while it is mounted; a document never hears its own announcement. A tab that, at its client's `SIGNED_OUT`, heard a `start` with no `end` since no more than 30 seconds (`LOGOUT_IN_FLIGHT_CAP_MS`) before, or an `end` no more than about 5 seconds (`LOGOUT_ANNOUNCEMENT_WINDOW_MS`) before, goes to the login page with `errorMessage` `loggedOutElsewhere`, and the login screen says the user was logged out in another tab or window. Any other sign-out the tab did not start goes to the login page with no reason, because the auth client also signs out by itself: after a refresh the auth service refused, when `getUser()` finds the session gone, and for an invalid stored session. Its drafts are discarded either way. A browser without `BroadcastChannel`, or one where it throws, announces nothing and names no such cause, and a Log out whose requests take longer than 30 seconds, or whose tab is closed before they end and whose sign-out reaches the other tabs more than 30 seconds after its `start`, leaves those tabs at the login page with no reason.

Every sign-out the browser makes removes the Contestant App's drafts from `localStorage`, in either app, through `discardContestantDrafts` in `$lib/contexts/contestant/contestantDrafts`, which the reset also calls: the Log out of either app once its sign-out has worked, the Admin App's protected load when it signs out a user who is no administrator and the session has ended, and a sign-out made in another tab, which both apps follow. A session that lapses keeps them, because a load that merely finds no session removes nothing; so does a sign-out made by the server alone, which cannot reach the browser's storage, and a sign-out that fails with the session left.

An ordinary link on a page holding an unsaved change keeps the native question `PreventNavigation` raises.
