# Hosted Supabase settings

This page is for the deployer who runs OpenVAA against a hosted Supabase project. It lists every setting the repository writes to that project, says where each one is set (in Terraform, in the Supabase configuration file or by hand in the dashboard) and how to verify that the project holds it. The path from an empty account to a running instance is on the [Deployment](/developers-guide/deployment) page, and the variables the frontend and the Edge Functions read are on [Environment variables](/developers-guide/configuration/environmental-variables).

## The settings

Each row is one setting the Supabase module in `infra/modules/supabase/` sends, except the anon role's statement timeout, which the migrations set on the role. Where a value comes from a Supabase root rather than from the module, the row names the root's variable. A secret is listed by its name and its source only.

## Parity classes

The parity class is the one `yarn assert:hosted-settings-parity` gives the setting. That guard, [`scripts/assert-hosted-settings-parity.mjs`](https://github.com/OpenVAA/voting-advice-application/blob/main/scripts/assert-hosted-settings-parity.mjs), runs in `yarn lint:check` and compares `hosted-settings.json` with the local stack's [`apps/supabase/supabase/config.toml`](https://github.com/OpenVAA/voting-advice-application/blob/main/apps/supabase/supabase/config.toml), the configuration the test suite runs with:

- `must agree`: the hosted value equals the local one. Some are inverted, such as `disable_signup` against the local `enable_signup`, and `max_rows` must also equal the frontend's page size.
- `hosted may be stricter`: the hosted value may be stricter than the local one, never weaker.
- `differs by design`: the hosted value is different on purpose and is held to a rule. The site address is the root's `public_origin`, an https origin with no path, and the redirect list is that origin followed by each callback path, with no wildcard in the host.
- `not compared`: the guard compares neither the SMTP settings, the rate limits nor the function secrets. Each depends on the environment, and the local rate limits are sized for a test suite on one address. Nor does it compare the anon role's `statement_timeout`: the migrations set it on the role, so the local stack and a hosted project hold the same value once the migrations are applied, and a project whose migrations are not applied keeps the platform's default.

## What the module writes

The module is [`infra/modules/supabase/`](https://github.com/OpenVAA/voting-advice-application/tree/main/infra/modules/supabase), called by each Supabase root under `infra/envs/<env>/supabase`. It writes through three resources:

- `supabase_settings.this` sends the API settings and the auth settings. It is the only writer of them: no workflow or script pushes the local configuration to a hosted project, and the parity guard fails if one appears. It sends only the keys the table lists; every other setting keeps the value the project holds. The provider drops a key it does not know without an error, so take key names only from [`hosted-settings.json`](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/modules/supabase/hosted-settings.json) and read the served settings back after every apply.
- `supabase_settings.smtp_secret` sends `smtp_user` and `smtp_pass`, in a resource of their own so that no plan diff of the main settings shows them. It exists only while the root sets `smtp`.
- `supabase_edge_function_secrets.this` sets the function secrets. It is their only writer: on apply it deletes a secret that is in its state but no longer listed, and leaves alone a secret it never managed. The values are stored in Terraform state in plain text, so a persistent root keeps its state in an encrypted bucket.

Each hook has a switch in every root's `terraform.tfvars`, `enable_access_token_hook` and `enable_send_email_hook`. Both are `true` in each root, and the parity guard fails on a `false` that carries no `# hook off until <reason>` comment. While the send-email hook is on, the auth service sends no mail of its own: the Edge Functions send the application's mail with the `SMTP_` function secrets. The auth SMTP settings and `rate_limit_email_sent` then govern no mail the auth service sends.

## What the repository does not set

- **The project.** It is created by hand in the Supabase dashboard and imported into the root; the module never creates it. Its organisation, name and region are the values the import shows. The instance size is not declared. The database password is required by the provider and never sent.
- **`IDENTITY_CALLBACK_SERVER_SECRET`.** It is set outside Terraform, with the same value in two places: as a secret of the `identity-callback` function and as a private environment variable of the frontend server. The AWS task environment does not carry it: [`task-environment.json`](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/modules/frontend-service/task-environment.json) holds no such name. No identity-provider setting of `identity-callback` is set by Terraform either, so the function refuses every call until a deployment sets them. See [Bank authentication](/developers-guide/contestant-app/bank-authentication).
- **The platform's own secrets.** The function secrets whose names begin with `SUPABASE_` are set by the platform.
- **Anything changed in the dashboard.** A setting the module does not send keeps whatever value the dashboard gave it, and no guard sees it.

## How to verify

The conformance probe compares what the project serves with what the repository declares for it, through the Management API, the project's public API with the anon key, and the catalog over `psql`. It writes nothing to the project and never takes the service-role key. Run it as [Step 23 of the Supabase runbook](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/envs/staging/supabase/README.md#step-23-the-conformance-probe) describes:

```bash
node infra/scripts/probe-hosted.mjs \
  --root "infra/envs/<env>/supabase"
```

It needs `SUPABASE_ACCESS_TOKEN`, `SUPABASE_ANON_KEY` and a catalog connection in the shell. Each line it prints is `PASS <check>` or `FAIL <check>: <finding>`, and its status is 0 when every check passed, 1 when one failed and 2 when it could not run. The check names in the table are the names those lines print.

Where the probe does not reach, the table names one of two other reads. A plan of the Supabase root that reads `No changes` shows that the values in state are the ones the root and the shell give. The read-back of [Step 18](https://github.com/OpenVAA/voting-advice-application/blob/main/infra/envs/staging/supabase/README.md#step-18-the-settings-and-the-function-secrets) prints the served auth and API settings and lists the function secrets by name, never with a value.
