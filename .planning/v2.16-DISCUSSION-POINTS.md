## Cross-phase picture

### Where the tree contradicts the roadmap or the requirements

Each is a numbered fact in the named phase's baseline table. They are gathered here because they change how
the roadmap reads.

- **ENT-03's named blocker is not one (173).** `idx_grants_one_candidate_editor` is unique on `target_id`: one
  editor per candidate, not one candidate per user. What stops a multi-entity user is the user-data RPC raising
  `ERR_ENTITY_IDENTITY_AMBIGUOUS`, and the frontend. An organization editor cannot sign in at all today.
- **Anon cannot read a closed project's settings (171).** `anon_select_app_settings` requires
  `project_open_for_voters`, which is false while contestants register. Without 171-B1 the login screen sees
  shipped defaults only, so neither the app name nor the Register entry can follow the project.
- **Removing the terms-of-use conjunct publishes entities nobody has registered for (172).** Two seeded E2E
  candidates are hidden only by it, and with INV-05 an invited, never-signed-in entity with a confirmed
  nomination becomes public (172-D2).
- **GEN-03's lock is not what the database enforces (175).** An organization's `name` freezes when the row is
  confirmed, whatever the nominations lock says, and `short_name` never freezes. An organization confirmed at
  seeding (INV-05) or at the callback (REG-07) could not be named by its own user. 175-B2 ★ resolves it, and
  179-C1 ★ creates self-registered organizations unconfirmed.
- **NOM-04 contradicts the schema (177).** `election_symbol` is refused for anyone without
  `project.edit_nominations`. Most of the rest of the nomination write path exists from Phase 162, but there is
  no entity DELETE policy, and a candidate cannot read the party list before the project opens.
- **The identity-provider write does not happen at the callback today (179).** The callback route sets a
  cookie; the Edge Function runs three screens later, is publicly callable, and creates candidates only. The
  bank-auth specs are opt-in and have not run since Phase 158.
- **`invite-candidate` has no caller (174)**, and its redirect target `/candidate/complete-registration` has
  no page (170).
- **REG-04's "without confirming" meets a security limit (179-B1, 174).** An unverified typed address that
  works as a sign-in identifier is a recovery route into a bank-verified account, and Phase 174's claim trusts
  only a confirmed address. 179-B1 ★ records the address as pending and never blocks editing.

#### X1 ⚠ DECIDE — Which entity types the E2E base dataset serves

171-E1 ★ keeps the suite's base at `['candidate']` with `candidate: ['email', 'code']`, so today's login screen
and app name are unchanged in every existing spec. 173-E1 ★ puts a multi-grant user holding a candidate and an
organization on that same base dataset, which needs both types served.

- [ ] **(a) The base stays candidate-only in 171; Phase 173 widens it to both types, with `organization: []`,
      and re-baselines whatever the "Candidate and party app" name changes** — ★ RECOMMENDED — each phase
      changes the base only for what it delivers, and the name change lands with the first spec that needs an
      organization. Two phases touch the base settings.
- [ ] **(b) 171 declares both types in the base from the start** — one change. Every existing candidate spec
      then runs under the "Candidate and party app" name two phases before any organization page exists.
- [ ] **(c) The base stays candidate-only throughout; 173's multi-grant spec and 175's organization spec run
      in their own project** — the base never changes. 173-E1 loses its ★ and takes its (c)-style dedicated
      dataset, and 175-F1 ★ already assumes a separate project.

#### X2 ⚠ DECIDE — A person seeded by an admin who registers through the identity provider

The identity-provider path always creates a new entity (179 fact table). A candidate an admin seeded with an
email or a code (Phase 174) who identifies with the bank instead gets a second, duplicate candidate. Neither
phase section decides it.

- [ ] **(a) Accept it for v2.16 and file a todo: identity-provider registration never claims an invitation;
      the admin resolves a duplicate by hand** — ★ RECOMMENDED — the provider's claims give no email to match
      an invitation on, and matching on name or birth date is the account-collision defect the OIDC review
      already found. A project that seeds entities would not also allow `identity_provider` for that type.
- [ ] **(b) After CI1's address is confirmed, claim any invitation for that address** — falls out of 174-D1 ★
      for free once 179-B1 ★ confirms the address. The user then holds the self-created entity and the seeded
      one, and meets H; the duplicate still exists.
- [ ] **(c) Refuse the `identity_provider` cell for a type while the project holds unclaimed invitations for
      it** — no duplicate can arise. A settings rule that depends on data, enforced nowhere today.

#### 171-A2 — How the matrix is represented

- [ ] **(a) A map from entity type to a list of modes: `{ candidate: ['email', 'code'], organization: [] }`** — ★ RECOMMENDED — an empty cell, an empty row and an empty matrix are each a distinct, storable value. ### 173-B. Selected-entity encoding (ENT-01, ENT-02)

#### 173-B1 ⚠ DECIDE — Where the selection lives (the roadmap's "Discussion must settle")

| | Route param `contestant/(protected)/[entityType]/[entityId]/…` | Cookie | localStorage / context state |
|---|---|---|---|
| Server load knows the entity | Yes, from `params` | Yes | **No** — the protected load runs on the server |
| Deep links, reload, back button | Natural | Reload yes; back does not undo a switch | Reload yes; back no |
| Two tabs, two entities | Independent | **Shared — the second tab's switch redirects the first tab's saves** | Shared |
| Stale selection after a grant is revoked | The load refuses that URL | Stale value must be detected and cleared | Same |
| E2E addressing | By URL | Needs cookie setup | Needs storage setup |
| Cost | Every protected route constant gains two params right after Phase 170 moved them; links without an entity (emails, `redirectTo`) need a resolver; entity uuids appear in URLs | New cookie, its lifetime and clearing on logout | Server load cannot stay as it is |

- [ ] **(a) Route parameter** — ★ RECOMMENDED — the only encoding in which "every page shows and saves the newly

- [ ] **(b) Cookie** — routes stay as 170 leaves them. Two tabs silently share one selection, which is exactly the
      wrong-entity save criterion 3 forbids.
- [ ] **(c) localStorage or context state** — least route churn. The server load cannot read it, so the entity data
      load moves to the client or needs a second mechanism anyway.

### 174-A. Mechanism and scope

#### 174-A1 ⚠ DECIDE — The invitation mechanism

The recommendation on record (`REQUIREMENTS.md` § Open design questions). The alternatives are the two shapes earlier planning named.

- [ ] **(a) Accept: a `public.invitations` table holding the pre-defined grant plus an email or a code hash, claimed by one `SECURITY DEFINER` function after a GoTrue emailed-link sign-in. No auth user and no grant exists until the claim** — ★ RECOMMENDED — one model serves the email and the code mode, an unclaimed invitation confers nothing (fact 6), and duplicates are refused by table constraints rather than by GoTrue's "already registered" error. Sections B–D settle its detail.
- [ ] **(b) `email` and `registration_code` columns on the entity tables** (the Phase 162 brief's fact 16 shape) — no new table. One entity then carries at most one invitation, a used code has nowhere to record who used it, and an anon-readable table gains two secret-bearing columns that every policy and column grant must hide.
- [ ] **(c) Keep pre-creating the user with `inviteUserByEmail` and writing the grant at invite time; add a code table beside it** — least change for the email mode. Two mechanisms, and an invited address is an existing account, so GoTrue itself confirms which addresses were invited.

#### 174-A2 ⚠ DECIDE — How far into the frontend this phase reaches

The roadmap gives 174 "the model and both of its ends, seeding and claiming" and 178 "the screens that drive a claim". SC6 requires the existing invitation and registration specs to run on the new model, and no claim can happen without something calling it (fact 18).

- [ ] **(a) 174 builds the database model, the seeding path, the claim, the code check, the link-request endpoint (174-D2), and wires the claim plus a session refresh into the existing auth callback and login action. No new screen** — ★ RECOMMENDED — `candidate-journey.spec.ts` then registers through a seeded invitation at 174's close, and 178 adds screens over endpoints that already pass their own tests. The set-password page stays `register/password` until 178.
- [ ] **(b) Database only: table, seeding, claim and pgTAP. The callback and the E2E helpers keep writing grants directly until 178** — smallest phase. SC6's "re-pointed at the new model" is then met by nothing, and 178 inherits an untested claim path together with seven new screens.
- [ ] **(c) 174 also builds the code-entry and email-sent screens** — the model is exercised end to end at once. It duplicates 178's scope before the registration-mode selector and the shared components exist.

#### 174-A3 — What one invitation can grant

An invitation is a stored promise to write a grant, and its writer needs only `project.edit_entities` (fact 1). `grants` admits four scopes and two roles.

- [ ] **(a) One row promises one `(entity, <type>, <id>, editor)` grant, for any of the four entity types. The target is `(target_type, target_id)` with a cleanup trigger, as in `grants`. Several grants for one person are several rows: every open row carrying the proven email is claimed in one call, and a code names exactly one row** — ★ RECOMMENDED — an invitation can never mint project or account authority, so a project editor cannot seed their own promotion, and a person invited to a candidate and an organization gets both grants at first sign-in (INV-03's plural). Admitting all four types costs nothing and matches the 162 note that seeding should cover every entity type; the Contestant app still serves two.
- [ ] **(b) The same, restricted by a CHECK to `candidate` and `organization`** — mirrors `contestant_app_entities` exactly. A faction or alliance invitation later needs a schema change.
- [x] **(c) A general grant spec `(scope, target_type, target_id, role)`, or a child table of grants per invitation** — admin invitations and multi-grant codes become possible later. The seeding path must then re-implement "who may grant what", which the matrix reserves to `project.manage_editors` and `account.manage_admins`.

### 174-B. The table

#### 174-B1 ⚠ DECIDE — How a code is stored

`CAND-APP-PLAN.md`: "I'd like to save the code for users who have used it." The record says "a code hash". A deterministic value is needed either way, because the code is looked up by itself and must be unique (fact 20).

- [ ] **(a) `sha256` of the normalised code, hex, in `code_hash`. The plaintext is never stored and is returned once, by the seeding call** — ★ RECOMMENDED — a database leak yields no usable code, and lookup and uniqueness are one indexed equality. An admin who loses a code cannot read it back and must revoke and reissue.
- [ ] **(b) Store the plaintext code** — an admin can re-read and re-send it. Anyone with read access to the table, a backup or a log holds every unused registration credential in the project.
- [ ] **(c) HMAC with a server-side secret** — protects short codes even if the table leaks. It needs a secret available inside PostgreSQL, which the schema has no mechanism for today.

#### 174-B2 — Who makes the code, and what it looks like

- [ ] **(a) The server generates it: 12 characters from a 32-symbol alphabet without look-alikes (`0/O`, `1/I/L`), shown as `XXXX-XXXX-XXXX`, compared case-insensitively with separators and spaces stripped** — ★ RECOMMENDED — 60 bits, so guessing is infeasible even without a rate limit, and a code printed in a letter survives being typed by hand.
- [ ] **(b) The admin supplies the code, minimum length enforced** — an existing code list (a party's member numbers) can be reused. The entropy is whatever the admin chose, so 174-D5's rate limit becomes the only defence.
- [ ] **(c) Both: generated unless supplied** — flexible. Two paths to test, and (b)'s weakness for every supplied code.

#### 174-B3 — What counts as a duplicate

INV-02 refuses "the same email or the same code for the same target". A code is looked up without a target, so "per target" cannot be its whole rule. Emails are compared trimmed and lower-cased in every option.

- [ ] **(a) Email: unique per `(target_type, target_id, email)`; the same email on different targets is allowed and yields one user with several grants. Code: unique per project. A claimed or revoked row still counts** — ★ RECOMMENDED — it is the narrowest rule under which a code resolves to one row, and it keeps a used code from being reissued to someone else (INV-04).
- [ ] **(b) As (a), but code unique across the whole instance** — a code can never be ambiguous if a deployment serves several projects. One project's seeding can then fail because of another project's rows, which leaks their existence.
- [ ] **(c) As (a), and at most one open invitation per target** — a target cannot be promised to two people. It also forbids inviting two editors to one organization, which the grant model allows.

#### 174-B4 — Expiry and revocation

- [ ] **(a) Nullable `expires_at`, no default. An unclaimed invitation is revoked by deleting it; a claimed one is kept and cannot be deleted through the admin path. `created_by`, `claimed_by` and `claimed_at` are recorded** — ★ RECOMMENDED — INV-04 needs claimed rows to stay, and an unclaimed row has no history worth a `revoked_at`. Projects that want a deadline set one.
- [ ] **(b) Add `revoked_at` and never delete** — a full audit trail. Every lookup and uniqueness rule gains a third state, and a revoked code can never be reissued.
- [ ] **(c) A mandatory default expiry (for example 30 days)** — stale invitations close by themselves. Seed data and E2E fixtures then age out, and a long campaign needs re-seeding.

### 174-C. Seeding

#### 174-C1 ⚠ DECIDE — The admin-callable write path

"No Admin-app screen is in scope" (SC1). The path must refuse a caller without authority over the project and must return generated codes once (174-B2).

- [ ] **(a) A SQL RPC, `create_invitations(p_project_id, p_invitations jsonb)`, `SECURITY INVOKER` over RLS policies on `invitations` that ask `user_can('project', project_id, 'project.edit_entities')`; a batch is one transaction** — ★ RECOMMENDED — authority is decided where every other admin write is decided, the E2E client, dev-seed and a later Admin app call the same function, and it needs no service role. "Admin authority" is read as the permission `invite-candidate` already uses, held by project admins and editors.
- [ ] **(b) An Edge Function (`invite-candidate` renamed and generalised)** — it can also send mail and create auth users. It runs on the service role, so its own check is the only gate, and nothing in this design needs either ability at seed time (174-A1, 174-C4).
- [ ] **(c) An `invitations` collection in `bulk_import`** — entities and their invitations arrive in one payload. `bulk_import` requires an `external_id` per row and returns only counts (fact 10), so generated codes could not be handed back.
- [ ] **(d) As (a), but restricted to project admins** — the literal reading of "admin authority". No single permission separates admin from editor for entity work, so it needs a new permission or a role test outside the matrix.

#### 174-C2 — Does the seeding call create the entity?

`invite-candidate` creates the candidate and the invitation together (fact 1). INV-01 says "seed an entity with an email or a code".

- [ ] **(a) No. An invitation targets an existing entity, named by id or by `external_id`; entities are created by the existing paths (`bulk_import`, admin insert)** — ★ RECOMMENDED — one responsibility per function, and a real election imports its candidate list first. Seeding a new entity with an invitation is two calls.
- [ ] **(b) Yes, optionally: an item may carry the entity's name, and the entity is created in the same transaction** — one call does what `invite-candidate` did. The function then needs each entity type's column set and repeats what `bulk_import` already does.

#### 174-C3 — INV-05: when and how an entity becomes confirmed

Fact 9: confirming freezes the name for the entity's own user. Fact 8: it does not publish the entity.

- [ ] **(a) Creating an invitation sets `confirmed = true` on its target when the target has a name (candidate: first and last name; others: a non-empty localized `name`), in the same transaction, and requires the caller to hold `entity.confirm`. An invitation for a nameless entity is accepted and leaves it unconfirmed. Deleting the invitation does not unconfirm** — ★ RECOMMENDED — it is INV-05 as written, the admin vouches by the act of inviting, and the invited user cannot rename what was vouched for.
- [ ] **(b) Confirm at claim time instead** — an entity nobody registered for stays unconfirmed. Contradicts "confirmed from the moment it is seeded" (SC5), and the claim function would exercise `entity.confirm` on behalf of a user who does not hold it.
- [ ] **(c) Refuse an invitation for a nameless entity** — no confirmed-but-nameless state can arise. Phase 179's identity-provider organizations are created before they are named, and an admin could not invite a co-editor to one.

#### 174-C4 — Does seeding an email invitation send a mail?

`invite-candidate` mails at once. REG-10 has the user ask for the link. An emailed link lives one hour (fact 12), and `send-email` cannot address a person without an account (fact 11).

- [ ] **(a) Seeding sends nothing. The invitee opens the app and asks for a sign-in link (REG-10, REG-02). Announcing invitations by mail is filed as a todo beside the Admin-app screens** — ★ RECOMMENDED — a link mailed at seed time would be dead before most recipients read it, and the announcement belongs with the admin tooling that is out of scope. Until then admins announce out of band.
- [ ] **(b) Seeding can send an announcement that links to the app's registration screen and carries no token** — invitees hear about it from the system. It adds a mail template in seven locales and a send path for non-users to a phase with no UI.
- [ ] **(c) Seeding sends the sign-in link itself** — today's behaviour. The link expires in an hour, and the invitee still has to ask for a new one.

#### 174-C5 — The fate of `invite-candidate` and `send-email`

Fact 3: nothing calls `invite-candidate`. Its docs pages and `flowConformance.test.ts` go with it.

- [ ] **(a) Delete `invite-candidate` with its tests, the `_preregister` / `preregisterWithApiToken` contract and its docs. Leave `send-email` unchanged. The anon-facing operations of 174-D live in one new Edge Function** — ★ RECOMMENDED — the function's two jobs move to `create_invitations` and to the claim, and a dead function that pre-creates users would contradict the model.
- [ ] **(b) Rename it and make it the seeding path** — keeps the authority tests. Same cost as 174-C1(b).
- [ ] **(c) Leave it until Phase 179 removes the legacy trees** — nothing breaks now. Two invitation mechanisms coexist for five phases, one of them still redirecting to a missing route (fact 2).

### 174-D. Claiming

#### 174-D1 ⚠ DECIDE — What triggers a claim

The claim must write grants as the proven user and must finish before any grant gate runs (facts 5, 6, 7). In every option an email counts as proven only when `auth.users.email_confirmed_at` is set.

- [ ] **(a) An explicit call. `claim_invitations(p_project_id)` is `SECURITY DEFINER`, executable by `authenticated`, takes no email or user argument, and reads both from `auth.uid()`. The auth callback and the password sign-in action call it and then refresh the session. It is idempotent, and all matching rows are claimed in one transaction** — ★ RECOMMENDED — the function cannot be pointed at another account, a failure surfaces in the request that caused it, and a returning user picks up a new invitation at their next sign-in without re-registering. The census grows by one name (fact 15).
- [ ] **(b) A trigger on `auth.users`, firing when an email becomes confirmed** — no client call to forget. A failing trigger on the auth schema blocks sign-in for everyone, and an invitation seeded for an existing user is claimed only by a second trigger on `invitations`.
- [ ] **(c) Claim inside `custom_access_token_hook`** — the token is right the first time. The hook is `STABLE` and read-only by design (fact 6), and a write on every token issue is paid by every user for ever.

#### 174-D2 ⚠ DECIDE — Who may be sent a sign-in link (REG-10 against REG-F01)

REG-10 lets a user "register by email"; REG-F01 defers sign-up without an invitation. `enable_signup = true` means GoTrue mails and creates an account for any address asked of it (fact 12). SC2 of Phase 178 wants one response for every address.

- [ ] **(a) A gate. One anon-callable Edge Function takes an address and always answers the same. It issues a sign-in link only when the address has an open invitation in the project or belongs to a user who already holds a grant in it; otherwise it does nothing. The auth user is created at that moment, not before** — ★ RECOMMENDED — "register by email" means "claim an invitation by email", strangers get no mail and no account, and nothing distinguishes an invited address from any other. It is one more Edge Function, and it needs its own resend throttle (178-C3).
- [ ] **(b) No gate. The browser calls GoTrue's `signInWithOtp` directly; every address gets a link and an account. A user with nothing to claim is told so after signing in** — least code, and GoTrue's rate limits apply. The deployment mails any address a visitor types, grant-less accounts accumulate, and an uninvited person sets a password before learning there is nothing for them.
- [ ] **(c) Pre-create the auth user at seed time and call `signInWithOtp` with `shouldCreateUser: false`** — GoTrue refuses uninvited addresses by itself. Its refusal is visible in the response, so invited addresses can be enumerated, and it restores the pre-creation the recommendation replaces.

#### 174-D3 ⚠ DECIDE — How a code is tied to the email the user enters (D1 → E → the click)

The code is proven at C and the email at the click, possibly on another device.

- [ ] **(a) On D1 the server writes the entered address onto the code's row as a pending address and issues the link (through 174-D2's gate, which treats a valid code as its third ground). The claim consumes a code row whose pending address equals the caller's confirmed email. Until then the code stays unused and a later D1 entry replaces the pending address** — ★ RECOMMENDED — nothing secret travels in the link, the click works on any device, and a mistyped address does not burn the code. A second person who knows the code can redirect it until someone confirms.
- [ ] **(b) Carry the code in the emailed link and present it at the callback** — no pending state. The credential sits in a URL, in mail and in server logs.
- [ ] **(c) Keep the code in a cookie between D1 and the callback** — nothing is stored server-side. Opening the mail in another browser loses the code and the claim silently writes nothing.
- [ ] **(d) Consume the code at D1, before the email is confirmed** — simplest state. A typing mistake in the address burns the code and hands the invitation to whoever owns the mistyped address.

#### 174-D4 ⚠ DECIDE — A used code: what the server says, and how D2 signs the user in

REG-09 needs three answers at C: valid, used, anything else. D2 shows only a password field, so the server must find the account. The frontend cannot (fact 13), and returning the address would recreate fact 14's disclosure.

- [ ] **(a) The code check returns one of `valid`, `used`, `unknown` and nothing else. D2 posts code and password to the Edge Function, which resolves the user, signs in with GoTrue server-side and hands the session to the SvelteKit action; every failure is the one "wrong password" answer. "Used" means claimed. A user who claimed but never set a password asks, from D2, for a sign-in link to the account's address, which is never shown** — ★ RECOMMENDED — it is the flow in `CAND-APP-PLAN.md` with no address leaving the server; holding the code proves nothing beyond what the letter already gave its holder.
- [ ] **(b) D2 asks for the email as well and is an ordinary sign-in; the server only says "used"** — no server-side resolution and no new sign-in path. It amends the operator's D2, and a user who forgot which address they registered is stuck.
- [ ] **(c) The check returns a masked address (`k•••@e•••.fi`) for D2 to display** — the user sees which account it is. A partial disclosure to anyone holding a used code.

#### 174-D5 — Throttling code attempts

- [ ] **(a) Rely on 174-B2's 60-bit codes and add a per-client attempt limit in the code check, built like the feedback limit (fact 16)** — ★ RECOMMENDED — entropy is the real defence and the limit caps the noise; the header-trust logic already exists.
- [ ] **(b) Entropy only** — nothing to build. Unlimited guessing against admin-supplied or future shorter codes.
- [ ] **(c) A per-code lockout after N failures** — precise. An unknown code has no row to count against, so it cannot limit guessing at all.

#### 174-D6 — A claim that meets a grant constraint

Phase 173 decides whether a candidate keeps a single editor (fact 5). If it does, a second invitation for the same candidate collides when claimed.

- [ ] **(a) Each row is claimed or skipped by itself: a row whose grant would violate a constraint stays unclaimed, the others are claimed, and the function returns what it claimed and what it skipped** — ★ RECOMMENDED — one bad row cannot lock a user out of their other entities, and the skipped row stays visible to an admin.
- [ ] **(b) All or nothing** — simplest to reason about. One stale invitation blocks every claim for that address.
- [ ] **(c) Refuse at seed time any invitation whose claim could collide** — nothing fails later. The check races with claims and with direct grant writes, so the claim needs (a) or (b) anyway.

#### 174-D7 ⚠ DECIDE — How the sign-in link is issued, and what it points at

GoTrue's default mail links to its own `/verify` endpoint. Requested from a server, that endpoint returns the session in the URL fragment, which the server-side callback cannot read (fact 18); requested from the browser it returns a PKCE `code` that only the requesting browser can exchange (178-F1). A link that carries a `token_hash` straight to the app's callback is what the callback verifies today.

- [ ] **(a) The Edge Function obtains the token with `auth.admin.generateLink`, builds a link to the app's auth callback carrying `token_hash` and `type`, and sends the mail itself over SMTP as `send-email` does** — ★ RECOMMENDED — the link works on any device, the existing callback handles it unchanged, the mail text is ours to localise (178-E1), and no GoTrue mail limit throttles a registration peak. The function must throttle resends itself (178-C3) and the SMTP settings become load-bearing for sign-in.
- [ ] **(b) The Edge Function asks GoTrue to send (`signInWithOtp`), with a custom `[auth.email.template.*]` whose link is the callback plus `{{ .TokenHash }}`** — GoTrue keeps throttling per address and owns delivery. One template per mail type for all seven locales, and GoTrue's per-IP limits see the function as a single client (fact 12).
- [ ] **(c) GoTrue's default mail and `/verify` redirect, requested from the browser with PKCE** — nothing to configure. The link fails when opened in another browser or device, which is the normal case for mail on a phone, and it bypasses 174-D2's gate.

### 176-A. The task state (TASK-01)

#### 176-A1 ⚠ DECIDE — The shape of the one derived state

- [ ] **(a) An ordered `tasks` list — each `{ id, status: 'complete' | 'incomplete' | 'blocked', route, count? }` — plus a `nextStep` naming the task and the route to go to** — ★ RECOMMENDED — the home screen renders the list and every Continue reads `nextStep`, so the two cannot disagree (SC4). `blocked` expresses "not reachable yet" (NOM-07, required info) in the same place.

#### 176-A2 ⚠ DECIDE — Which tasks exist, and whether they differ by entity type

Today's three buttons are profile, questions and preview (fact 4). NOM-01 adds "Define nomination" first.

- [ ] **(a) Three tasks for both types — nomination, profile, opinion questions — in that order. Preview is a destination shown on home, never a task with a status. #### 176-A3 — When "Define nomination" counts as complete

- [ ] **(a) Complete when the entity has at least one nomination, confirmed or not** — ★ RECOMMENDED — NOM-01's wording ("incomplete while the entity has no nomination"), and the only rule under which a self-registered user can go on to the profile and questions before an admin acts.
- [ ] **(b) Complete only when at least one nomination is confirmed** — the task tracks public visibility. A freshly registered user is then locked out of everything until an admin confirms, which defeats the flow Phases 177-179 build.

#### 176-A4 — Where the state lives and what it is called

- [ ] **(a) Two accessors on the contestant context, `tasks` and `nextStep`, computed by a pure helper module that replaces `candidateHome.helpers.ts` and keeps a colocated unit test** — ★ RECOMMENDED — TASK-01 says "in the contestant context", the pure helper keeps the table-driven test the current helpers have, and both are reactive accessors read as `ctx.tasks` / `ctx.nextStep`, never destructured.
- [ ] **(b) A separate state class composed into the context, as `userData` is** — isolates the logic. It is derived data with no methods and no persistence, so the class adds only a constructor.
- [ ] **(c) Exported from the home page's helper and imported by the other pages** — least change. It is then not in the context, and each page must gather the inputs itself.

#### 176-A5 ⚠ DECIDE — What Continue means

SC4 says "the entity's next incomplete task". Three cases need a ruling: everything is complete; the user is inside the questions task; and the user saves the page of a task that is still incomplete (profile saved with required info missing — allowed today).

- [ ] **(a) `nextStep` is the first incomplete task. When that task is the questions, its route is the first unanswered question, keeping today's resume-at-first-unanswered behaviour (fact 6). When the task just saved is still incomplete, or when everything is complete, Continue goes home; on home, with everything complete, the primary action is Preview** — ★ RECOMMENDED — it reproduces what each of the five sites does today (fact 5) from one rule, so the candidate journey spec needs no behavioural change.
- [ ] **(b) Strict sequence: Continue always goes to the next task in order, complete or not** — predictable. A returning user with everything done is walked through every page again.
- [ ] **(c) `nextStep` is task-level only; after each saved answer the user returns to the questions list** — the simplest state. It removes question-to-question flow, which the journey spec asserts and the View Transition work was built for.

### 179-A. The round trip

#### 179-A1 ⚠ DECIDE — How the chosen entity type travels through the provider's flow

Whatever carries it, the value starts in the user's browser. What matters is that it is checked against the matrix where the entity is created (179-A2). Signicat has no `state` parameter (fact 7).

- [ ] **(a) A short-lived httpOnly cookie set by the authorize endpoint, after that endpoint has checked the type against the matrix; read and deleted by the callback** — ★ RECOMMENDED — the same mechanism as `oidc_state`, one more entry in `$lib/cookies`, and it works for both providers. No signature is needed: any value that passes the matrix is one the user was free to choose, and one that does not is refused at 179-A2.
- [ ] **(b) An HMAC-signed payload inside `state`** — nothing extra in the cookie jar and the value is tamper-evident. It needs a new server secret, and works for Idura only; Signicat would need `state` added to its flow first.
- [ ] **(c) One callback path per type (`/api/oidc/callback/candidate`, `…/organization`)** — the type is in the URL the provider returns to. Every redirect URI must be registered with the provider per type, and the choice is visible and editable in the address bar.

#### 179-A2 ⚠ DECIDE — Where the registration-mode matrix is enforced (facts 8, 9)

- [ ] **(a) In three places, with the Edge Function authoritative** — ★ RECOMMENDED — the function reads the project's settings with its service-role client and refuses a type for which `identity_provider` is not allowed, whatever the caller sent; the authorize endpoint refuses early so nobody is sent to the bank for a closed mode; the callback re-checks before invoking. An absent type is accepted only when exactly one type is allowed.
- [ ] **(b) In the frontend routes only (authorize and callback)** — no settings read in Deno. The function stays callable directly with the anon key, so anyone holding a valid ID token could create an organization in a project that allows candidates only.
- [ ] **(c) In the Edge Function only** — one check. A user in a project with the mode closed completes the bank's flow before being refused.

#### 179-A3 ⚠ DECIDE — Where the user and the entity are created (fact 1)

- [ ] **(a) The callback route invokes `identity-callback`, establishes the session and redirects to CI1; the `id_token` cookie, `/api/oidc/token` and `/api/candidate/preregister` are deleted** — ★ RECOMMENDED — "created when the provider's flow completes", read literally. The ID token never rests in the browser, and the two failure channels of fact 10 become one.
- [ ] **(b) Keep the `id_token` cookie; CI1 posts to create the user** — smaller change to the callback. The user sits on CI1 identified but not created, the token cookie and its expiry screen survive, and it is the deferred write the 2026-10-04 ruling rejected.

#### 179-A4 — One identity, more than one entity

A returning identity may choose a type it has no entity of.

- [ ] **(a) At most one entity per type per project for one identity; choosing the other type creates it and adds the grant, and the user then picks between them on H** — ★ RECOMMENDED — a person can be a candidate and also their party's contact. Repeating a type lands on the existing entity with CI1's "already registered" text.
- [ ] **(b) One entity per identity per project; a returning identity always lands on the existing one, whatever type was chosen** — simplest. A candidate who also runs the party's page must be invited by email for the second.
- [ ] **(c) A new organization each time the organization type is chosen** — a person can register several parties. One identity can then create unlimited organization rows.

### 179-B. The email address (CI1)

#### 179-B1 ⚠ DECIDE — What the typed address is trusted for, and when

REG-04 says the user goes straight to editing without confirming the address. It does not say the address may be used to sign in before anyone has proved control of it. CAND-APP-PLAN CI1 says "We'll send an email there." Phase 178 lets anyone ask for a sign-in link for an address ("I have not set a password yet"), after which gate F sets a password.

**The risk if the address is accepted unverified:** it becomes a recovery route into a bank-verified account at once. A typo hands the account to whoever owns the mistyped mailbox. And a registrant can enter another person's address before that person arrives; a later invitation to that address (Phase 174) would then be claimed into an account the first registrant can still enter through the bank.

- [ ] **(a) Pending until proved: CI1 records the address as a pending change and sends a confirmation link; the user goes straight on to G and editing; the address becomes the sign-in identifier when the link is clicked. Until then the user returns through the identity provider** — ★ RECOMMENDED — REG-04's "without confirming it" stays true (confirmation never blocks editing), the plan's "we'll send an email there" becomes true, and neither risk above exists. Cost: `double_confirm_changes` must not mail the placeholder (set it false, or issue the link with the admin `generateLink` and send it through `send-email`), and a user who never clicks is, for REG-05, a user without an email.
- [ ] **(b) Immediate and unverified: the server sets the address with `email_confirm: true`** — the literal reading of REG-04 and the least code. Both risks above are accepted; state so in the phase's security notes.
- [ ] **(c) Immediate, plus a notification mail to the address ("this address was added to an account; if this was not you…")** — the owner of a mistyped mailbox can object. It only detects; the stranger's mailbox can still take the account first.

#### 179-B2 — The typed address already belongs to another account

- [ ] **(a) Refuse with a specific message — "this address is already in use; enter another, or sign in with it" — and stay on CI1** — ★ RECOMMENDED — the user can act. It tells a bank-identified person that the address has an account, which is a narrow disclosure to an identified caller.
- [ ] **(b) Answer as screen E does: the same response whether or not the address is free** — no disclosure. The user proceeds believing the address is theirs and never receives a link.
- [ ] **(c) Merge: after the link is clicked, attach the provider identity to the existing account and move the grants** — the best outcome for a person who was invited by email and then used the bank. It is an account-linking feature with its own failure cases; file it as a todo.

#### 179-B3 ⚠ DECIDE — How an identity-provider user signs in with email "next time"

No password is set in the provider flow (REG-11 exempts it). REG-02 shows "I have not set a password yet" only **when the email mode is allowed**. In a project that allows the identity provider alone, an identity-provider user has an address and no way to use it, and CI1's "use your email next time" is untrue.

- [ ] **(a) The emailed sign-in link is offered whenever the email mode *or* the identity-provider mode is allowed for any served type; the first use leads to F, which sets the password** — ★ RECOMMENDED — one path for every passwordless account. It widens REG-02's condition, which Phase 178 builds.
- [ ] **(b) CI1 gets an optional "set a password now" field** — the user can sign in by email at once. A second place where passwords are set, inside the flow REG-11 exempts.
- [ ] **(c) In identity-provider-only projects the user always returns through the provider; CI1's text says so** — nothing changes in 178. The address is then collected for contact only, and CI1 needs two variants of its text.

#### 179-B4 — Where the "no email yet" gate sits (REG-05)

- [ ] **(a) A layout gate ahead of G: a user whose address is still the placeholder and who has no pending address is sent to CI1's email form; a user with a pending address passes, and sees a reminder with resend and "use a different address" on home** — ★ RECOMMENDED — closing the tab on CI1 cannot skip the step, and a mistyped pending address can be corrected. Gate order becomes F (exempt here) → email → G → H.
- [ ] **(b) Only on return from the provider** — no new gate. A user who abandons CI1 and later opens a protected URL directly reaches home without an address.
- [ ] **(c) Gate until the address is proved** — strongest. It is the email confirmation REG-04 rules out.

### 179-C. The created entity

#### 179-C1 ⚠ DECIDE — Is a self-registered organization created confirmed? (facts 3, 16)

The identity provider proves who the person is. It does not prove they speak for the party. INV-05 keeps an entity nobody vouched for unconfirmed.

- [ ] **(a) Unconfirmed, with an empty name; an admin confirms it** — ★ RECOMMENDED — consistent with INV-05. The user can name and rename it while it is unconfirmed (fact 16), which is what REG-07's "can be edited later" needs, and it is invisible to voters until an admin has looked. Candidates stay as today: confirmed, name from the claims, frozen.
- [ ] **(b) Confirmed, like a candidate** — the party is one nomination confirmation away from public. A confirmed name is frozen for its user, so REG-07's later edit would need an `entity.edit_immutable` exception, and anyone with a bank ID can create a vouched-for "party".
- [ ] **(c) Unconfirmed, and created only when CI1 is submitted with a name** — no unnamed rows. It is the deferred write the 2026-10-04 ruling rejected.

#### 179-C2 ⚠ DECIDE — What CI1 requires for an organization, and what an abandoned one becomes

- [ ] **(a) The name is required in the project's default locale, the abbreviation and other locales optional; a user whose organization has no name is sent back to CI1's form by the same gate as 179-B4; an abandoned unnamed organization stays unconfirmed and invisible, and is reused when the identity returns** — ★ RECOMMENDED — no entity without a name reaches home or the nomination parent list, and no cleanup job is needed because 179-A4(a) bounds the rows to one per identity.
- [ ] **(b) Name and abbreviation required in every supported locale** — complete data from the start. Seven locales × two fields before the user can do anything.
- [ ] **(c) Nothing required; the home screen lists "name your organization" as a task** — CI1 is never a wall. Unnamed organizations then appear in admin lists and the app has to render a nameless entity everywhere.

#### 179-C3 — CI1's texts for a returning user

- [ ] **(a) Three variants: new user (email form, plus the organization fields for an organization); returning with an address ("you have already registered — use your email to sign in next time", Continue); returning without one (the "already registered" line plus the email form)** — ★ RECOMMENDED — REG-05's two cases and REG-04's, each with its own message keys in seven locales. Under 179-B1(a) "with an address" includes a pending one, shown with a resend.
- [ ] **(b) Two variants: the returning user without an address sees the new-user screen** — fewer strings. A returning user is greeted as new.

### 179-D. The screens and the errors

#### 179-D1 — Where CI1 and CI2 live

- [ ] **(a) CI1 is a signed-in page of its own that the layout gates route to (ahead of G); CI2 is a public page beside the mode selector C** — ★ RECOMMENDED — CI1 needs the session and takes part in the gate order; CI2 has no session and its "Try again" returns to C with the identity-provider option open. Final paths follow Phase 178's route names.
- [ ] **(b) Both as states of the selector page C, switched by a query parameter** — no new routes. C then renders three unrelated screens, and CI1 sits outside the protected layout that runs the gates.

#### 179-D2 — The error classes (REG-08)

The todo's taxonomy has five causes, and "try again" is honest for only some.

- [ ] **(a) Three user-facing classes: *cancelled* (the provider's `access_denied` and known cancel values) — calm text, no apology; *may work on retry* (`token_exchange_failed`, `missing_code`, `invalid_state`, a 5xx from the function) — apology and "try again"; *will not work on retry* (`invalid_token`, mode not allowed, configuration) — "this is a problem on our side; contact support". All three show the support block and the Try again action** — ★ RECOMMENDED — three texts × seven locales, and none promises what cannot happen. Unknown provider values fall into the second class.
- [ ] **(b) One text per code** — most precise. Six or more texts per locale, and the page reveals which stage failed.
- [ ] **(c) Two classes: cancelled, and everything else with the retry text** — fewer strings. It tells a user to retry a misconfiguration, which the todo calls a regression in honesty.

#### 179-D3 — How the failure reaches CI2

- [ ] **(a) A query parameter carrying a code from a closed set; the callback maps the provider's raw value to a class before redirecting, so no provider-chosen string reaches the URL or the DOM; the four existing codes keep their spellings and two are added (`mode_not_allowed`, `registration_failed`)** — ★ RECOMMENDED — reload-safe, addressable by E2E, and the operator runbook's codes stay valid. CI2 announces the message through the existing route announcer.
- [ ] **(b) A one-shot flash cookie** — nothing in the URL. A reload loses the message, and it adds a cookie to declare and clear.
