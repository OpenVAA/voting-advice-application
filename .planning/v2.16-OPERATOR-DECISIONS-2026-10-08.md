(measured, from the policy and its own comment). So after the move, as captured, a project editor
can close and reopen the nomination period, and entity users can write again once it is reopened.
Settles the first half of 175 J5 and of 177 J2.

### B3 — What a project with no settings row means for the lock

Second half of 175 J5 and 177 J2. As captured: a project that does not exist is locked; a project

## E. Phase 177 — define nominations

### E1 — How the database enforces "a parent is required" — blocks the design of the write

You ruled that the database refuses a nomination the election's type forbids, for every writer, and
that "Other" satisfies a required parent. Two facts collide (measured in the schema). "Other" is
stored as no parent plus a text key. And a candidate may create a missing party nomination only
after its own row exists at that contest — so the write order is own row without a parent, then the
party's row, then the link; the first of those is exactly the row a list election now forbids (177
J4).

- [ ] **(a) Refuse a parentless candidate row unless it carries the "Other" text, and check
      "has a parent or the text" at the end of the transaction** — ★ RECOMMENDED — the three-step
      write passes and a lone parentless insert does not. Whether PostgreSQL's deferred triggers and
      the SQL linter accept this is a research item, not yet measured.
- [ ] **(b) The write inserts the own row with a placeholder "Other" text and removes it when it
      links the parent** — no deferred check. For one statement the row claims a party request it
      never made.
- [ ] **(c) Let the party's row be created first** — rewrites the guard that ties a placeholder
      party nomination to a real nominee at that contest.
- [ ] **(d) The database enforces only "this entity type may stand in this election"; "required" is
      left to the write function and the screens** — simplest. A direct API call can still write a
      parentless candidate into a list election, which is less than criterion 2 says.

### E2 — How far the election-type rule reaches

Your matrix names candidates and organizations. The database rule also sees factions, alliances,
updates, and admin and service writes (177 J5).

- [ ] **(a) Inserts and updates, every role; a faction is admitted where a candidate may have a

- [ ] **(b) Bind signed-in users only; the service role stays free** — seeds can hold unusual
      shapes. It is no longer "whoever writes it".
- [ ] **(c) As (a), but faction and alliance rows are never refused by this rule** — less to test.
      Those two types can be written into elections of any type.
- [ ] **(d) As (a), plus a rule that refuses an election-type change which would leave existing
      nominations invalid** — closes the gap (a) leaves. One more trigger, and an admin must remove
      nominations before changing a type.
