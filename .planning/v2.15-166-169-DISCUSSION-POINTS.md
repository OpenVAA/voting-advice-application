### 166-C. How many users per entity (SC4)

#### 166-C1 ⚠ DECIDE — One user per candidate?

- [x] **(a) A partial unique index: `CREATE UNIQUE INDEX … ON public.grants (target_id) WHERE scope = 'entity'
      AND target_type = 'candidate' AND role = 'editor'`** — ★ RECOMMENDED — matches the 162 user-rights model,
      where Candidate is the only candidate-scope user type (D-07). A second editor would otherwise be
      indistinguishable from the candidate. Research must confirm no pgTAP fixture (notably 12-user-can's
      13-row set) or E2E setup grants two users the same candidate. `writeEntityGrant`'s
      `UNIQUE_VIOLATION` → success mapping must then name the constraint, or a second user's grant would
      read as success.
- [ ] **(b) No index** — leaves room for a future delegated editor. Two users editing one candidate become
      indistinguishable, and nothing in the schema says so.
- [ ] **(c) Index for candidates and organizations alike** — symmetric, but it removes the multi-editor
      support for organizations that the column could not represent and SC4 expects to gain.

#### 166-C2 — One candidate per user per project (the source of 166-B2's ambiguity)

- [ ] **(a) No write-time constraint; 166-B2's read-time error is the guard** — ★ RECOMMENDED — `grants` has
      no project column, so a write-time rule needs a trigger that joins the entity table on every grant
      insert.
- [ ] **(b) A constraint trigger on `grants` that refuses a second candidate-editor grant in the same project** —
      the failure moves to write time. It is a new trigger on the authority table, with its own pgTAP pair.

### 169-B. What "safe" means

#### 169-B1 ⚠ DECIDE — Minimum release age

- [ ] **(a) Any version we take must be at least 7 days old at bump time. A new major line must also have
      its `x.0.0` release at least 30 days old; otherwise that package stays on the latest release of its
      current major, and the reason is recorded. Exception: a patch that fixes an open high+ advisory can be
      taken once it is 2 days old** — ★ RECOMMENDED. Today this rule holds back Kit 3, adapter-node 6 and
      adapter-static 4 (0 days old), and nothing else that matters.
- [ ] **(b) 7 days flat, with no separate rule for majors** — Kit 3 could then land only a week or two after
      release, before `svelte-check`, `eslint-plugin-svelte` and paraglide are confirmed against it.
- [ ] **(c) No age gate; take the `latest` tag** — leaves the window for a compromised publish fully open
      (the 2025 npm worm and hijack incidents spread within hours of publishing).
- [ ] **(d) 14 days for everything** — safer, but it would hold back recent security patches. The
      `devalue` fixes, for one, would not have qualified when the advisories landed.

#### 169-B2 — How the age rule is enforced

- [ ] **(a) Set `npmMinimalAgeGate` in `.yarnrc.yml` permanently, at the B1 value (7 days)** — ★ RECOMMENDED.
      Yarn then enforces the rule on every future `yarn up`, not just in this phase. The cost: an urgent
      security patch younger than the gate needs a per-package exception (`npmPreapprovedPackages`). Also
      confirm the key is not in `FORBIDDEN_YARNRC_KEYS` (`auditBaselineShape.test.ts:106`). The guard
      forbids the advisory-ignore keys, so it should not be.
- [ ] **(b) Apply the rule by hand in this phase and only document it** — no config change, but nothing
      enforces it the next time.
- [ ] **(c) Set the key only while this phase runs, then remove it** — enforced now, gone afterwards.

#### 169-B3 — The "no open advisory" clause

- [ ] **(a) A chosen version must have no open high+ advisory (the gate threshold). Moderate and low
      advisories on chosen versions are listed in the phase summary** — ★ RECOMMENDED.
- [ ] **(b) No open advisory at any severity** — stricter, but it may block the latest release of packages
      with minor findings, and it goes beyond what the gate enforces.
- [ ] **(c) Only whatever `yarn audit:deps` enforces** — nothing is checked or recorded below high.

#### 169-B4 — Majors blocked by a peer that hasn't caught up (TS 7, ESLint 10, frontend Vite 8)

- [ ] **(a) Use a supported replacement where one exists. Otherwise hold the major and record the blocking
      peer in a todo with a re-check trigger** — ★ RECOMMENDED. The per-case decisions are **D2**, **D3** and
      **D4**.
- [ ] **(b) Force the major through with `packageExtensions` or peer overrides** — the result is a
      combination nobody upstream supports, and any failure is ours to debug.
