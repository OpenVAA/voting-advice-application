<objective>
Stop `authenticated` from writing the columns it has no business writing, on **both** entity tables,
and observe each denial rather than infer it.

This is roadmap criterion 5 / REVIEW-DB-05. `303-column-grants.sql` grants `authenticated` UPDATE on
`sort_order`, `created_at` and `updated_at` for `public.candidates` and again for
`public.organizations`. `created_at` and `updated_at` are audit fields — a record's own owner being
able to rewrite when it was created or last touched is a repudiation vector — and `sort_order`
controls presentation order, which is a tampering vector against how entities are ranked to voters.

The criterion names the columns but not the tables. **The answer is both**, per D-E3: the vector is
identical on each, and a denial proof run against a half-fixed surface proves nothing about the half
that is still open. That makes six assertions, not three.

**Two measured facts remove the only reasonable objection.** First, revoking `updated_at` cannot break
candidate self-edit: column privileges are checked against the columns *named in the statement*, not
against what a `BEFORE UPDATE` trigger assigns, and this was proven live — with `updated_at` absent
from the grant, an authenticated update of a permitted column succeeded and the timestamp still moved.
Second, no application code writes any of the three as `authenticated`: the only authenticated write
path in the Supabase adapter builds its update from exactly two columns, neither of them these.

Purpose: this is the phase's one substantive security control, and its evidence must be an observed
failure. `yarn db:reset-with-data` seeds as `service_role`, which bypasses column grants entirely, so
the seed says nothing here. pgTAP's `set_test_user` sets the role AND the full JWT claims payload
exactly as PostgREST does per request, and a denied column update raises SQLSTATE 42501 — the same
error PostgREST surfaces as HTTP 403. That is the proof; the E2E suite in plan 10 is the corroboration.

Output: two narrowed GRANT lists, two corrected comment mirrors, six observed denials, and a
privilege-catalogue check that the remaining column sets are exactly what was intended.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated PostgREST client → Postgres column privileges | The enforcement point. PostgREST is a pass-through; there is no application-tier check and none is wanted, because a client that can reach the database directly would bypass it. |
| record owner → their own audit fields | The specific vector: a principal legitimately allowed to edit its own row must not be able to rewrite when that row was created or last modified. |
| `BEFORE UPDATE` trigger → columns the caller may not name | The trigger writes `updated_at` with the definer's authority, independent of the caller's column privileges. |
