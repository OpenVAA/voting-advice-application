<objective>
Make role identity in the auth layer a type rather than a convention.

This is roadmap criterion 2 / REVIEW-DB-02. Today `public.user_roles.role` is already the enum
`user_role_type`, but its sibling `scope_type` is `text NOT NULL` with a trailing comment listing the
five legal values — and `301-auth-functions.sql` compares both against string literals pulled out of a
JSONB claim. A comment is not a constraint: an illegal scope inserts cleanly and then silently fails
every predicate that looks for it.

Two changes: `user_roles.scope_type` becomes a new enum `public.role_scope_type` with members
`'candidate', 'organization', 'project', 'account', 'global'` — the column comment's own vocabulary,
with the renamed role term — and `has_role` / `can_access_project` compare enum values instead of text.

**Rewrite-in-place makes this cheap, and that is worth stating.** Changing `has_role`'s parameter
types would normally require `DROP FUNCTION ... CASCADE`, which takes the nine RLS policies that call
it with it, and then recreating all nine. Under D-E2 there is no `DROP`: `00001` creates the function
before the policies, so editing its signature in place means `supabase db reset` simply builds the new
signature first and the policies bind to it. Any task that reasons about a live `ALTER` is solving a
problem this phase does not have.

Purpose: criterion 2 is an access-control strengthening. After it, an unknown role or scope label is a
type error at the point of insert and can never match a predicate — where today it is a value that
compares false and looks like a legitimate denial.

Output: a new enum, a retyped column with its now-redundant comment removed, two rewritten predicate
functions with their security properties intact, three new pgTAP assertions, and a recorded decision
about what happens to a stale claim.
</objective>

Retype the two predicate functions' comparisons, in both SQL copies.

**`has_role` signature.** Change `p_check_role text` to `p_check_role public.user_role_type` and `p_check_scope_type text DEFAULT NULL` to `p_check_scope_type public.role_scope_type DEFAULT NULL`. `p_check_scope_id uuid DEFAULT NULL` is unchanged. **Write both type names schema-qualified.** The function carries `SECURITY DEFINER` and `SET search_path = ''`; with an empty search path an unqualified type name does not resolve. Do not relax the search path to make an unqualified name work — that setting exists to close a search-path hijack.

**The comparison trap, and it is the one thing most likely to go wrong here.** `role_entry->>'role'` yields `text`. Comparing `text` to an enum parameter is an operator that does not exist, so the function will fail to create. There are two ways out and they are not equivalent:
- casting the PARAMETER down to text — which keeps the comparison a string comparison and does not satisfy this criterion;
- casting the CLAIM VALUE up to the enum — which is what "uses enums in place of string comparison" means, and is what to do.

So `IF role_entry->>'role' = p_check_role THEN` becomes `IF (role_entry->>'role')::public.user_role_type = p_check_role THEN`, and `IF role_entry->>'scope_type' = p_check_scope_type` becomes `IF (role_entry->>'scope_type')::public.role_scope_type = p_check_scope_type`. Follow the schema's existing fully-qualified `::public.<enum>` cast style.

The three structural branches are unchanged and must stay unchanged:
- the `super_admin` short-circuit still compares the parameter to a bare literal, which now coerces to the enum;
- **the no-scope-filter branch — `IF p_check_scope_type IS NULL THEN RETURN true; END IF;` — stays exactly as it is.** It is what lets a one-argument call mean "any matching role", and nine policies depend on it;
- the `scope_id` comparison stays a text comparison against `p_check_scope_id::text`.

**`can_access_project`** compares claim values against bare literals rather than against parameters: the super-admin check, the project-admin role-and-scope pair, and the account-admin role-and-scope pair. Cast each claim value to its enum in the same way, so the comparisons are enum equality rather than string equality. Its signature takes only a uuid and does not change.

**Record the consequence, do not bury it.** Casting the claim value up means a JWT carrying a label the enum does not have RAISES `22P02` (invalid_text_representation) rather than quietly comparing false. In a predicate that is a fail-closed outcome — the query errors instead of returning rows — but it is a different failure shape from today's silent false, and it can only happen with a session minted before the rename. `db:reset` invalidates every local session and there is no deployed database, so the exposure is a developer's own stale tab. Add an entry to `156-DISPOSITIONS.md` stating the choice and its consequence, so no later reader has to rediscover it.

Do not change any RLS policy. Every call site passes bare quoted literals, which coerce to the new parameter types; confirm that by reading them rather than by assuming it.
