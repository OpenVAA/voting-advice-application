<objective>
Two RPC corrections that pull in opposite directions, and the asymmetry is the point.

This is roadmap criterion 6 / REVIEW-DB-06.

**`upsert_answers` generalises.** It is the answer-write path for entities, but both of its branches
write `public.candidates` unconditionally, so an organization cannot save its own answers through it.
Measured: exactly two tables carry an `answers` column — candidates and organizations; factions and
alliances do not. So "all entities carrying answers" is a two-table widening, not a four-table one.
Its signature, its three parameters and its `SECURITY INVOKER` security are unchanged, so the adapter
call site is source-compatible.

**`merge_custom_data` does not generalise — it gets the name it always deserved.** The criterion
offers rename or generalise and requires the choice recorded; the choice was recorded in
`156-DISPOSITIONS.md` by plan 01, before Phase 157 could be planned against a guess, and it is
**rename**. Everything about the function except its name is already question-specific: the parameter
is a question id, the target table is hard-coded, the returning clause names that table's column, the
error message says a question was not found, and the security rationale names the one RLS policy that
gates questions. Generalising would need a table discriminator, therefore dynamic SQL inside an
invoker-security function, therefore a table allow-list — and it would ship with no consumer.

Purpose: one of these is a real capability gap and the other is a naming lie. Treating them the same
way — generalising both, or renaming both — would get one of them wrong.

Output: an entity-generic answer writer, a correctly-named question custom-data merge, and the rename
carried through all eleven of its naming sites across SQL, the adapter, the unit tests and pgTAP.
</objective>

<assumption_delta_decision>
This plan implements the generalisation outcomes recorded in `156-DISPOSITIONS.md` by plan 01.

**`upsert_answers` — singular→plural generalization.**
- Primary noun: **an entity carrying answers** (measured: `public.candidates` and `public.organizations`).
- Decision: **promote**. The entity-generic writer becomes the primary representation and the candidate
  case becomes one variant inside it. The candidate-specific writer is not kept alongside — there is one
  function, with one fall-through, and the signature does not change.
- Rationale: a second real consumer exists, and `SECURITY INVOKER` keeps per-table RLS as the authority,
  so promotion costs no new privilege surface.

**`merge_custom_data` — rename vs. generalise.**
- Primary noun: **a question's custom data** — unchanged. Nothing generalised here.
- Decision: **no-change to the shape; rename the symbol** to `merge_question_custom_data`.
- Rationale: everything but the name was already question-specific, and generalising would require
  dynamic SQL inside an invoker-security function plus a per-table RLS rationale, for a capability with
  no consumer. Not accepted debt: no second representation is left standing, so nothing would later
  force a promote.
</assumption_delta_decision>
