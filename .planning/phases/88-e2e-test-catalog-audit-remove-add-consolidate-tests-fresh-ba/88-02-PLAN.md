## Objective

Refactor the voter-app results route from the current 3-segment shape
`results/[[entityTypePlural=entityTypePlural]]/[[entityTypeSingular=entityTypeSingular]]/[[id]]`
to the new 4-segment shape
`results/[[electionTab]]/[[entityTab=etPl]]/[[entity=etSg]]/[[id]]`. The change
(a) introduces an OPTIONAL front route param `electionTab` that identifies the
SINGULAR selected election whose results are being rendered, (b) renames the
two matcher-gated segments to short-form (`etPl` / `etSg`) so the directory
listing is readable, and (c) achieves NAME-DISJOINT dissociation between
the route-side `params.electionTab` (selected election; one) and the
search-side `?electionId=…` / `?electionId[0]=…&electionId[1]=…` persistent
search-param surface (available elections; zero-or-more, set at `/elections`,
drives nomination / question filtering via `voterContext.selectedElections`).
The two surfaces share NO key name — `electionTab` (route) and `electionId`
(search) are different identifiers throughout the codebase. This is sharper
than a same-name semantic dissociation: a contributor can't accidentally
conflate the two because `params.electionTab` and `searchParams.get('electionId')`
are literally different reads.

This refactor is operator-motivated by the Phase 88 mega-journey: the
deferred-88-nn placeholders in `voter-mega-journey.spec.ts` (refactor-doc:294,
:311 + cluster) currently can't run deterministically because election
selection is in-page UI that races with cold-start hydration cascades. A
deterministic URL like `/results/test-el-reg/candidates` (route segment ⇒
unambiguous selection) makes those steps wirable in the immediate follow-on
plan (88-03+). This plan delivers the route surface; 88-03 wires the
placeholders. The mega-journey spec itself remains UNTOUCHED in 88-02.

## In Scope

2. **Directory migration** of the entire `(voters)/(located)/results/` tree to the new shape, including `+layout.svelte`, `+layout.ts`, the leaf `[[id]]/+page.svelte` + `+page.ts`, and the `statistics/+page.svelte` leaf.
3. **`apps/frontend/src/lib/utils/route/route.ts`** updates: `Results`, `ResultCandidate`, `ResultEntity`, `ResultParty`, `Statistics` template strings + `DEFAULT_PARAMS` key rename (`entityTypePlural`→`entityTab`, `entityTypeSingular`→`entity`).
4. **`params.ts`**: rename in `ROUTE_PARAMS` (`entityTypePlural`→`entityTab`, `entityTypeSingular`→`entity`) AND add `'electionTab'` as a new ROUTE_PARAMS entry. `PERSISTENT_SEARCH_PARAMS` keeps `'electionId'` UNCHANGED. The two arrays are now NAME-DISJOINT — no entry appears in both. `ARRAY_PARAMS` keeps `'electionId'` (search-side still accepts arrays); `electionTab` does NOT join ARRAY_PARAMS (route segment is always singular).
5. **`parseParams.ts` + `filterPersistent.ts` + `buildRoute.ts`**: the dissociation rule lands structurally — no special-case logic needed. `parseParams(current)` continues to merge route + search params into one `Partial<Params>` object via existing `Object.assign`-style precedence, BUT because the route side emits `electionTab` and the search side emits `electionId`, the two surfaces coexist on the merged object without overwriting each other. No slash-guard needed. `buildRoute({ electionTab: 'X' })` routes `X` to the ROUTE segment via `isRouteParam('electionTab') === true`; `buildRoute({ electionId: 'X' })` routes `X` to the search side via `isPersistentSearchParam('electionId') === true`. A caller wanting BOTH (set the selected election AND keep the available array in scope) passes BOTH keys.
6. **voterContext getter** `currentResultsElection` — reactive accessor returning the election matching `page.params.electionTab` (with default-pick fallback to first-available when route param absent). Per CLAUDE.md destructure rule, consumers read via `ctx.currentResultsElection`.
7. **Server-side guards** on the new tree (`+layout.server.ts` OR `+page.server.ts`, planner-chosen): invalid `params.electionTab` → redirect to `/results` with stripped segment + preserved search; absent + 1-available → auto-redirect to `/results/{thatId}`; absent + 2+available → render existing election-picker shape.
8. **URL-string updates** in voter specs (`voter-results.spec.ts` is the primary; grep audit surfaces other consumers) — use `buildRoute({ route: 'Results', electionTab: 'test-el-reg', entityTab: 'candidates' })` shape (route-side singleton), or pass both `electionTab` (route) AND `electionId` (search) when both surfaces matter; do NOT hand-roll URL strings.
9. **134 `$getRoute(opts)` / `buildRoute(...)` consumer site audit** for any call passing `entityTypePlural` / `entityTypeSingular` keys — mechanical rename to `entityTab` / `entity`.

## Approach

Order of operations is interface-first (zero-dependency matcher files land
ahead of everything else, giving a fast green-checkpoint) then directory
migration (atomic move + ROUTE-constants update together because SvelteKit's
route table is type-checked at compile time and a half-moved tree would fail
`tsc --noEmit`) then the route-utility plumbing (`params.ts` /
`parseParams.ts` / `filterPersistent.ts` / `buildRoute.ts` — small surgical
edits) then the voterContext accessor + server-side guards (the
behavior-defining tier) then spec URL-string updates + a full-suite
regression smoke at the end.

The matcher files land first because they're independent (no route consumes
them until Task 2's directory tree references them), they're 25-line files,
their unit tests are 30-line files, and getting them green gives a
fast-feedback win before the bigger surface comes online. Decision in Task 1:
whether to delete the old `entityTypePlural.ts` / `entityTypeSingular.ts`
matchers — grep first; if their only consumers are inside the soon-to-be-moved
`results/` tree, delete in Task 2 as part of the tree migration. The grep
audit already conducted by the planner shows the matchers are ALSO referenced
in `voterContext.svelte.ts` (line 385 comment), `filterContext.svelte.ts`,
`filterContext.type.ts`, and the EntityCard / EntityInfo consumers — but those
are STRING references inside comments / `params.entityTypePlural` reads, NOT
imports of the matcher modules. So the matcher files are only directly
imported by the `results/[[entityTypePlural=entityTypePlural]]/...` route
folder bracket-syntax (which SvelteKit resolves at build time) plus the
`.test.ts` siblings. They can be safely deleted in Task 2 once the tree moves.

The dissociation rule is enforced **structurally** via name-disjoint key
allowlists. `ROUTE_PARAMS` gains a new entry `'electionTab'`;
`PERSISTENT_SEARCH_PARAMS` keeps `'electionId'` unchanged; the two arrays
never overlap. SvelteKit surfaces the route segment value via
`page.params.electionTab`; the search-side AVAILABLE-array is read via
`url.searchParams.getAll('electionId')` (or the `qs.parse` array form for
`?electionId[]=…`). No same-name semantic gymnastics — the two surfaces
are literally different identifiers in code. `buildRoute({ electionTab: 'X' })`
routes via the route-side branch; `buildRoute({ electionId: 'X' })` routes
via the search-side branch; a caller wanting both passes both keys.
Verification: grep audit confirms `params.electionTab` (route reads) and
`searchParams.electionId` (search reads) live in DISJOINT file sets, with
the only intersection being `parseParams.ts`'s documented merge point
(which now simply concatenates the two surfaces' outputs into one
`Partial<Params>` object without any special-case logic).

## Risks & Mitigations

### Risk 1 — Contributors may still conceptually conflate `electionTab` and `electionId` even though they're name-disjoint

The two surfaces have DIFFERENT names (`electionTab` route key; `electionId`
search key), so the code-level confusion that would exist under a same-name
scheme is structurally impossible — `grep`-equivalence is impossible because
they're literally different identifiers. The residual risk is CONCEPTUAL: a
contributor may not realize both keys are about elections and may, e.g.,
update `electionTab` semantics without considering whether the AVAILABLE-array
surface needs a parallel update. This is a smaller risk than the same-name
version but not zero.

**Mitigation:**
- Task 4 adds a block-comment at `params.ts` (above the two arrays) documenting that `electionTab` and `electionId` are intentionally name-disjoint and what each surface means.
- Task 5 adds a TypeDoc comment on `currentResultsElection` cross-referencing `selectedElections` (the available-array surface) — calls out that they're related but read different keys.
- Task 6's server-guard adds a top-of-file block-comment documenting the dissociation and the redirect chain that ties the two keys together at the route entry point.
- Task 8 grep-audits both keys and records the disjoint file sets in the commit message body — a future contributor running `grep -rn "electionTab" apps/frontend/src` gets the route-side surface; `grep -rn "searchParams.*electionId\|qs.parse.*electionId" apps/frontend/src` gets the search-side surface; no overlap.

### Risk 2 — Consumer sites that pass `{ electionId }` expecting search-side landing keep working; sites that intended route-side landing must explicitly opt-in via `{ electionTab }`

`buildRoute({ electionId: 'X' })` continues to land `electionId` on the
search side because `isPersistentSearchParam('electionId') === true` and
`electionId` is NOT in `ROUTE_PARAMS` — no behavioral change for existing
search-side callers. The only callers that change shape are the spec /
component sites that pass results-route URLs and want the SELECTED election
on the path segment; they migrate from `{ electionId: 'X' }` (which used to
land on search) to `{ electionTab: 'X' }` (which now lands on route). Task
7's grep audit drives this migration.

**Mitigation:**
- Task 7's grep audit explicitly enumerates all 134 consumer sites (using `grep -E "getRoute|buildRoute"` with the Result-route pattern); each call is reviewed against the new dual-key surface and migrated to `electionTab` when the caller's intent is route-side, kept as `electionId` when the intent is the available-array.
- Task 4 documents the disjoint default behaviors in the `buildRoute` docstring with a clear example pair (`electionTab` → route, `electionId` → search).
- Callers wanting BOTH surfaces populated (the canonical case in voter-results specs after this refactor) pass both keys: `buildRoute({ route: 'Results', electionTab: 'test-el-reg', electionId: ['test-el-reg'] })` — route segment lands `test-el-reg`, search side keeps the available-array under `?electionId=test-el-reg`.

### Risk 3 — Param-matcher rename is a SvelteKit compile-time concern; missing a reference inside a moved file = silent 404

SvelteKit resolves bracket-segment matcher names at build time. A moved file
that still references `params.entityTypePlural` (the OLD name) inside
`page.params.X` will simply read `undefined` at runtime — no compile error,
no 404, just silently broken UI.

**Mitigation:**
- Task 2's verify step is explicit: `grep -rn "entityTypePlural\|entityTypeSingular" apps/frontend/src/routes/(voters)/(located)/results` returns 0 matches.
- Task 2's verify also includes `dev-server start without route-collision errors` (manual smoke).
- Task 7's grep audit catches any residual `params.entityTypePlural` reads outside the route folder.
- Task 8's full-suite e2e run is the last line of defense — voter-results URL-shape assertions fail loudly if a `params.X` read returns undefined.

### Risk 4 — Auto-redirect for "1 available election" subtly changes existing behavior

Today's results page renders a picker even when there's only one election
(the `if (elections.length > 1)` branch at +layout.svelte:344). The
operator's stated motive is to KILL this spurious-picker behavior to give
voter-journey:292-294 a deterministic URL. But other specs (and the
e2e dataset shapes that have only one election by default) may be
asserting the picker's absence in a way that the new auto-redirect breaks
(e.g. asserting `page.url() === '/results/candidates?electionId=X'` —
which now becomes `'/results/X/candidates?electionId=X'` after Task 6's
auto-redirect).

**Mitigation:**
- Task 6's verify step is explicit about the redirect target; spec assertions in Task 7 update to the new behavior.
- Task 7's grep audit specifically looks for `expect(page).toHaveURL` / `waitForURL` calls with results URL patterns; each is reviewed against the new shape.
- Task 8's full-suite run catches any remaining spec breakage at the integration level. If a spec breaks specifically because of the auto-redirect behavior, the executor records the failure mode and the planner decides whether to (a) update the spec, (b) make the auto-redirect opt-in via a query param, or (c) defer the auto-redirect to a follow-on plan.

`filterContext.svelte.ts` derives the active `FilterGroup` from the `(electionId, entityTypePlural)` URL scope tuple (D-14).
