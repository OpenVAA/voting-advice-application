# Phase 175 — UI Design Contract

> Visual and interaction contract for the surfaces Phase 175 adds or reshapes in the Contestant app: the
> profile page's name fields (an organization's multilingual name and short name, and a candidate's first
> and last name on the same lock rule), the logo, the colour field, the save path including the refused
> save, the state of an entity with no opinion questions, the organization's preview, and the copy that
> differs by entity type. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase adds no design language.** SvelteKit 2 + Svelte 5 runes, Tailwind 4 + DaisyUI 5, Inter,
> theme colours in `packages/app-shared/src/settings/staticSettings.ts`. The token sections below
> **document the established contract** the surfaces obey; they introduce **no new token, font, spacing
> step, colour, icon or component library**. The load-bearing content is in *Surface Contracts*,
> *Copywriting Contract*, *Locator Contract*, *Axe Scan Entries* and *UI Considerations*.
>
> **How to read the evidence marks.** `[tree]` = read on this worktree at HEAD `d76a595e8` on 2026-10-08.
> `[CONTEXT D-nn]` = a locked decision of `175-CONTEXT.md`; `[OD08-xx]` = the operator decision of
> 2026-10-08 it cites. `[RESEARCH T-n / P-n / RQ-n / A-n]` = a finding, pitfall, answered question or
> logged assumption of `175-RESEARCH.md`. `[computed]` = calculated from the theme tokens for this
> document. `[U-nn]` = a rule proposed in this document — **PROPOSED — operator to confirm** — all listed
> together at the end. Code is cited by path and a content anchor (a symbol or a quoted line), never by
> line number. Names of symbols this phase introduces are suggestions unless a `[CONTEXT]` mark fixes
> them; what they must do is the contract. Frontend paths are relative to `apps/frontend/src/` unless they
> start with `apps/`; `ENTITY/` abbreviates
> `routes/contestant/(protected)/[entityType=servedEntityType]/[entityId=uuid]/`.
>
> **This run was non-interactive.** Nothing the context records as settled is reopened. Every place where
> the context and the research leave a UI question open carries a `[U-nn]` mark. Three proposals **depart
> from a locked decision as it is written** — `[U-05]` from `[CONTEXT D-14]`, `[U-12]` from
> `[CONTEXT D-05]`, `[U-30]` from `[CONTEXT D-18]` — and say so where they are made.
>
> **Revised in place on 2026-10-08 after the check** (no BLOCK, nine flags). `U-01` to `U-26` keep their

Rules that follow from the table:

- **This phase puts nothing new on the preview's `base-300` background.** The tag line is inside the
  `base-100` card (S6). The only text on `base-300` stays the existing tip, whose `text-secondary` passes
  with no margin (4.6:1 light / 4.7:1 dark) today and is reworded per type, not restyled.
- **The colour a party chooses is never a text or background colour on the profile page.** It is a 24px
  swatch with a `secondary` outline, so a white, black or page-coloured choice is still a visible control.
- **The last two rows hold only because the read goes through `ensureColors`** (`lib/utils/color/ensureColors.ts`,

  white initials is about 1.3:1. This is why `[CONTEXT D-04]` routes the preview's read through the util,
  and why the preview scan uses a colour that fails unadjusted (*Axe Scan Entries*).

## Surface Contracts

### Shared premises

- **One page per route, one descriptor per type** `[CONTEXT D-02]`. Each page reads the descriptor of the
  selected entity's type. *The per-type descriptor* below enumerates **every** difference the surfaces
  S1–S7 use; a difference that is not in that table is not built. **It carries no lock rule** — that is
  one rule for every type. No `{#if type === 'organization'}`, and no ternary on the type, appears in a
  page, a layout or the menu.
- **The descriptor is chosen from page data, so it is right on the server and on first paint**
  `[RESEARCH, Pattern 5]`: by `contestantCtx.selectedEntity?.type`, not by the store-derived
  `const isOrganization = $derived(userData.current?.entity.type === 'organization');` that
  `ENTITY/profile/+page.svelte` has today. Phase 173's first-paint rule is kept: a candidate's two name
  inputs are in the server-rendered markup. If no selected entity is known, the candidate descriptor is
  used and every name field is locked.
- **The name rule, said once** `[CONTEXT D-05, D-07, D-09]`. A name field — first name, last name, name,
  short name — is editable exactly when the selected entity is known, is unconfirmed, and
  `contestantCtx.answersLocked` is off. One pure function decides it for every field and both types. It
  yields the three **name states** used below:

  | Name state | Condition | `data-name-state` |
  |------------|-----------|-------------------|
  | editable | entity known, `confirmed === false`, answers not locked | `editable` |
  | locked by confirmation | `confirmed === true` (whatever the answers lock says) | `locked-confirmed` |
  | locked by answers | `confirmed === false` and answers locked; also an unknown entity | `locked-answers` |

  The nominations lock plays no part `[CONTEXT D-05]`. The page's lock is presentation; the database
  trigger is the control (S4).
- **Reactive reads.** `selectedEntity`, `answersLocked`, `appSettings`, `opinionQuestions`,
  `profileComplete`, `unansweredRequiredInfoQuestions`, `unansweredOpinionQuestions`, the new
  `nominationsLocked` and the new "question data is loaded" fact are reactive accessors: read
  `contestantCtx.X`, never destructure; `dataRoot` is never bound to a read alias (`CLAUDE.md` § Context
  Destructuring Rule; `.claude/skills/components/context-reactivity.md`).
- **Values reach an `Input` through `userData.current`, as plain objects** `[RESEARCH RQ-7, P-8]`. A
  `$state` proxy handed in as `value` throws at mount; a value emitted by `onChange` is staged as a
  snapshot, normalised (trimmed, blank locales dropped, `null` when nothing is left `[RESEARCH P-4]`), and
  staged **only if it differs from the saved value**.
- **Vocabulary** `[U-25]`. The UI never says "entity" or "organization". An organization is a **party**,
  as `common.organization.singular` already has it in all seven catalogues (`parti`, `party`, `erakond`,
  `puolue`, `parti`, `Partei`, `parti` — read 2026-10-08); the thing a user edits is a **profile**
  (Phase 173, U-01). `short_name` is labelled **Abbreviation**. `179-CONTEXT.md` D-12 and R16 record the
  CI1 sentence as ending "until an administrator has confirmed your organization": that is the decision
  in planning vocabulary, written before any catalogue string. The two phases show **one** word to the
  user. This contract's English is "…has confirmed your party", and Phase 179's CI1 string takes the same
  noun; if `[U-25]` is overruled to "organization", both change together.
- **RTL is out of scope on this branch.** Nothing here is designed or verified right-to-left. The one
  cheap rule: markup written for this phase uses logical utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`,
  `text-start`, `text-end`) where it sets a side, as `Input` already does (`me-8`, `text-end`), so the
  RTL branch's port stays mechanical.

- The required field carries `aria-required="true"`.

- **Which locale** `[U-04]`: `defaultLocale` exported by `lib/i18n/init.ts`, as `[RESEARCH RQ-5]`
  recommends. In the shipped configuration it is `en`.

**Language of parts** `[U-23]`. Each locale's `<input>` / `<textarea>` and its language label carry

### S4 — Profile: saving, the unsaved-changes guard, and a refused save

**One Save, one guard, one failure surface** `[CONTEXT D-09, D-12]`. The names, the colour and the logo are
staged in the store and saved by the same `userData.save()` and the same `profile-submit` button as the
info answers. The name fields have no save button and no guard of their own.

**What is staged.** `image`, `name`, `shortName`, `color` for an organization; `image`, `firstName`,
`lastName` for a candidate `[CONTEXT D-12]`. Staged names and the staged colour are **held in memory, like
the image** `[U-07]` — not in the per-entity `localStorage` draft that answers use. Each is staged only
while its normalised value differs from the saved one, so typing a name and restoring the saved text
leaves nothing unsaved.

**The guard with staged properties.**

| Action with a staged name, colour or logo | What happens |
|-------------------------------------------|--------------|
| Any link or menu item out of the page | The existing native confirm, `components.preventNavigation.unsavedChanges`. Cancel → the user stays, edits intact. Confirm → `userData.resetUnsaved()` discards **every** staged property and the answer draft, and the navigation continues. |
| Cancel (`profile-cancel`) | Enabled while anything is unsaved; discards every staged property and the answer draft and returns to the entity home without a prompt (existing behaviour, widened). |
| Reload or closing the tab | The browser's own `beforeunload` prompt. Staged names, colour and logo do not survive the reload; the answer draft does, as today. No "draft restored" notice. |
| Switching to another entity | As any link out of the page (Phase 173, S2). |
| `answersLocked` turns on | The store discards the staged properties with the answer draft, without a prompt `[CONTEXT D-12]`; the page shows the locked-by-answers state and no Save. |
| Expanding translations, or focusing and leaving a field unchanged | Nothing is staged; no prompt. |

The Save button's label is the existing four-way choice (`common.saveAndContinue` / `common.continue` /
`common.saveAndReturn` / `common.return`), now counting staged properties as unsaved.

**While a save is in flight.** The Save button shows its spinner and `common.saving` and is disabled
(`const isDisabled = $derived(disabled || loading);` in `Button.svelte`). Fields are not disabled and do
not flash. A second submit is impossible.

**Outcomes of a save.** A save is two requests — answers, then properties `[RESEARCH P-3]` — so three
outcomes exist, and the page tells them apart.

| Outcome | What is stored | What the page does | Message | Focus and announcement |
|---------|----------------|--------------------|---------|------------------------|
| **Saved** | Everything staged. | Clears the staged properties and the draft. If a listed property changed — name, short name, logo or colour — the entity list is re-read, so the menu's group title and the selection card show the saved values without a reload `[U-14; RESEARCH P-7]`. Then navigates to `submitRouting.submitRoute`. | none | The next page's `<h1>` receives focus (root `afterNavigate`); `#route-announcer` speaks its title. |
| **Name refused** — an admin confirmed the entity during the session, and the trigger refuses the changed name `[CONTEXT D-05; OD08-C7]` | The answers, and the logo and colour changed in the same save: **a refused name never costs the other edits** `[U-12]` — a departure from `[CONTEXT D-05]` as written, see below. | **Failed** — any other failure of either request | Whatever the requests before the failing one stored. | Stays on the page; keeps every staged property and the draft, so pressing Save again retries. | `contestantApp.error.saveFailed` (existing) | As above. |

**Where `[U-12]` departs from the context.** `[CONTEXT D-05]`'s planner constraint reads: "The property
update is one `UPDATE` statement … a statement that carries a *changed* name for a confirmed row fails
whole — image and colour with it." Built to that sentence, a refused name also refuses the logo and the
colour, and the page would have to say so. This contract asks for the other outcome — the name columns in
a statement of their own, after the others, as `[RESEARCH P-3]` describes — because a user who is told
"your name is locked" should not also lose a logo they uploaded in the same save. **It is a change to a
locked decision's constraint, not an interpretation of it, and it is the operator's to confirm.** If it
is overruled, the middle row above reads: stored — the answers only; the logo and the colour stay staged
and are saved by a second press of Save; and `nameLocked.<type>` says "your answers were saved" in place
of "your other changes were saved".

**When the re-read of the entity list is slow, or fails.** The re-read follows a save that has already
been stored; it is never the save.

- While it is in flight the Save button stays in its saving state, as `TermsOfUseGate.svelte` keeps its
  Continue loading across `await invalidateAll();`. No loading view replaces the page.
- If it fails, the save is **not** reported as failed: no `saveFailed` message, no staged edit restored.
  What happens next is the user-level load's own failure path, unchanged by this phase — the sign-out
  with `loginFailed` (Phase 173, D-11). The saved values are stored and are what the next sign-in shows.
- After a refused name, the fields must not stay editable on a failed re-read: the staged names are
  already discarded, and the message has been shown before the re-read starts.

**The message region** `[U-13]`. One container in `primaryActions`, in the place of today's
`{#if status === 'error'}` block, **always in the DOM** so that a message inserted into it is announced:

```
<div role="alert" class="mb-lg mt-md" data-testid="profile-save-message"

  {#if message}<ErrorMessage inline {message} />{/if}
</div>
```

- It holds at most one message; a new save clears it when it starts.
- A name-refused message stays until the user leaves the page or saves again; it survives the re-read of
  the list that follows it.
- **After a save that does not navigate, focus is on the Save button**, whichever browser removed it while
  the button was disabled. The page restores it; it does not move focus to the message, which `role="alert"`
  already announces.
- Both messages are Body size, `text-error` on `base-200` (6.4:1 / 5.4:1), wrapped, full column width.
- **What the region speaks.** `ErrorMessage`'s inline variant renders
  `<span class="text-error text-center">{emoji} {effectiveMessage}</span>` `[tree]`, where the emoji is
  `dynamic.error.heroEmoji` (🙊 as shipped). Left as it is, the alert would begin with the emoji's name —
  "speak-no-evil monkey" — before the sentence. With `[U-28]` the emoji is wrapped in
  `aria-hidden="true"` and the region speaks **the translated sentence and nothing else**; the pixels and
  the element's text content are unchanged.
- **`saveFailed` says "saving your answers"** and is shown here for a failed name, colour or logo too. It
  is kept as it is, as a named acceptance `[U-29]`: the same string already covers the logo on this page
  and the terms-of-use acceptance on the gate (`TermsOfUseGate.svelte`), and on the question page, which
  shares the key, "answers" is exact.

**Not built:** a success toast (a successful save navigates), a modal, a per-field "saved" mark, or a
notice when an admin confirms the entity while the user is not saving.
