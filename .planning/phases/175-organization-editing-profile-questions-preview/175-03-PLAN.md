## Rulings and deviations carried by this plan

1. **Orchestrator ruling 3, the database half.** The stored shape of `color` is checked where every writer is bound. The reader that no longer passes an unparsable value through is plan 175-08's; the writer's own hex check is plan 175-07's. The three together are the mitigation of the stored-CSS-injection path, and this plan's threat model carries it.
2. **Which tables (planner's judgement under ruling 3).** "The tables this phase lets users write" is read as the four entity tables: the column grant admits `color` to an entity's editor on each, whatever the app's own screens offer. `nominations.color` is guarded by `project.edit_nominations`, and the election, constituency and question tables are admin-written; they are left alone, and the reader's fix covers them on read.
3. **A trigger, not a CHECK constraint**, for both validations: it binds every writer as a constraint does, and it can name the offending member, which is the house style of the validation functions beside it.
4. **Name and short name get no database shape check in this phase** (the orchestrator left it to the planner). The values are not interpolated into markup, `getLocalized` degrades a malformed value to nothing, and a check added here would bind seeds and imports whose stored names nobody has surveyed. Plan 175-07 validates what the app sends; plan 175-13 files the todo.
5. **Pattern map item 5: a pgTAP file of its own.** No file is dedicated to `bulk_import`, so the type list's cells and the import's cells go in a new numbered file, `40-entity-type-list.test.sql`; the colour's go in `41-entity-color.test.sql`.
6. **D-21's "one migration regeneration"** is one per schema commit, as plan 175-02 records.
7. **The unquoted item key in `_bulk_upsert_record`** (research, *Security Domain*) is outside this phase and is not changed here; plan 175-13 files it.

8. **Every commit of this plan that changes the schema, the migration or a pgTAP file carries the `[db]` tag in its subject**, as `.agents/code-review-checklist.md` requires and as Phase 174's commits do. The two dev-seed commits of Task 2 change no database object and carry none.
9. **Trigger names follow the checklist's convention**: each new trigger is named for what it validates, in the `validate_{thing}` form.
