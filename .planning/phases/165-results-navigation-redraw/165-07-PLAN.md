<objective>
The phase gate. Run every instrument this repository has, at one head, on the finished tree, and let a
human judge the one result that cannot be judged automatically.

Purpose: the project's cardinal rule is explicit - no task proceeds, completes or is marked done while
any E2E test is failing, there are no known-flaky exemptions, and a test that did not run counts as a
failure. This plan is where that rule is discharged for the phase as a whole rather than per plan.

D-19 adds the one judgement call: run the visual project first, and re-capture a baseline **only** when
the diff is explained by an intended change. An unexplained diff is a defect to investigate. The
phase has two plausible sources of intended visual change - the layout split moved markup nesting, and
the drawer host replaced the per-route drawer - and one recorded hazard that would void the run rather
than redden it: a no-space condition inside the container runtime.

Output: a recorded gate section in the phase's evidence document carrying every command, its exit code
and its counts, plus the operator's disposition on each visual difference.

**On the visual judgement and how it reaches the operator.** `.planning/config.json` sets no
`workflow.human_verify_mode`, so the project default applies and human verification is harvested at the
end of the phase rather than halted on mid-flight. The visual-baseline judgement is therefore carried in
task 3's `<verify><human-check>` block rather than as a mid-flight checkpoint task: the executor runs the
visual project and prepares the per-baseline explanation, and the verifier collects the judgement into
the phase's user-acceptance pass. **No baseline is re-captured before that judgement is given.**
</objective>

forced off wherever a cached replay is possible. This is the shape the previous phase used and it is
reused verbatim rather than re-derived: the unit suite, the lint gate, the format check, the build, the
frontend type-check and the workspace typecheck, chained so the first failure stops the chain.

Two rules bind every command here.

First, **force the cache**. This repository has a recorded defect where an unforced gate is a replay of
a cache entry taken before the edits under test, so it reports green without measuring anything. Prefix
the turbo-backed gates accordingly.

Second, **read each exit status directly from the command**. Never pipe a gate into a pager, a grep or a
counter to read its result: a pipeline reports the last stage's status, and the project memory records
two commits of hidden lint violations produced by exactly that mistake. If output must be captured, tee
it to a file and read the status separately.

Before running, record the head the gates are taken at, and after running, confirm the head has not
moved - a gate run that straddles a commit proves nothing about either state.

Record the results in `165-NEGATIVE-CONTROL.md` under a `## Gates` section: for each command, the
command verbatim, its exit code, and its counts where it reports them - the number of test files and
tests for the unit suite, the error and warning counts for the type-check, and the package count for
the build. A gate recorded as "green" with no counts beside it is not a record; counts are what make a
later reader able to tell a real run from a no-op.

If a gate is red, fix the cause rather than the gate, and re-run the whole chain from the top at the new
head. A partially re-run chain is not a gate.
