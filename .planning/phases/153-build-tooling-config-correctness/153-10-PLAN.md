<objective>
Close the cross-runtime environment-variable drift surface with a derived registry guard and a
value-agreement checker — and keep the two honestly distinct, because only one of them can run in CI.

## Why this plan exists

Phase 155 hardened three Edge Functions and, in doing so, made the cross-runtime configuration
surface visible. **Four variables exist twice**, once for the Deno Edge Function runtime and once
for the SvelteKit frontend:

| Deno Edge Function | Frontend | Read where |
|---|---|---|
| `SUPABASE_URL` | `PUBLIC_SUPABASE_URL` | platform-injected / client bundle |
| `SUPABASE_ANON_KEY` | `PUBLIC_SUPABASE_ANON_KEY` | platform-injected / client bundle |
| `IDENTITY_PROVIDER_CLIENT_ID` | `PUBLIC_IDENTITY_PROVIDER_CLIENT_ID` | function / client bundle |
| `IDENTITY_PROVIDER_TYPE` | `PUBLIC_IDENTITY_PROVIDER_TYPE` | function / client bundle |

Three further identity variables (`IDENTITY_PROVIDER_ISSUER`, `IDENTITY_PROVIDER_JWKS_URI`,
`IDENTITY_PROVIDER_DECRYPTION_JWKS`) are already **single-source** — the same name is read by both
runtimes. They are not pairs and need nothing.

**This is not a hypothetical class.** The frontend and Deno copies of the identity provider config
have drifted apart **twice**, both times undetected, and were caught only by a code review and then
by a plan that happened to re-measure. Phase 155's verifier recorded the missing drift guard as the
residual risk that survives that phase.

## What this plan does NOT do, and why

It does not unify the pairs. Two reasons, one per class:

- **`SUPABASE_URL` / `SUPABASE_ANON_KEY` are injected automatically by the Supabase Edge runtime.**
  Deployed functions receive them without configuration. Switching the Deno side to read
  `PUBLIC_SUPABASE_URL` would mean configuring, in every environment, something the platform
  already provides — a downgrade, not a simplification.
- **`PUBLIC_` is a bundling contract, not a naming convention.** In SvelteKit/Vite it means *this
  value is embedded in client JavaScript*. It is the one signal that tells a reviewer whether a
  value is browser-safe. Reusing it in a server-only Deno runtime, where it means nothing, erodes
  that signal and invites a later author to prefix a secret because "that is what we do for shared
  vars".

So the pairs stay, and the drift gets a detector instead.

## The distinction this plan must not blur

**A build-time check cannot compare values.** CI has no secrets, and nothing guarantees both members
are set at build time. So this plan ships two scripts that check genuinely different things:

1. **`assert-env-pair-registry.mjs` — static, runs in `lint:check`, needs no secrets.** Proves the
   *pairing contract*: every cross-runtime twin discoverable in source is documented as a pair in
   the co-located `.env.example` block. Catches "someone added `PUBLIC_FOO` and a `Deno.env.get('FOO')`
   and told nobody."
2. **`assert-env-pairs-agree.mjs` — runtime, invoked with an env file.** Proves the *values* match.
   Catches actual drift.

**Shipping only the first while calling it a drift guard would be the exact failure this milestone
kept finding: a gate that examines nothing and reports green.** Each script's docblock must say
which of the two it is and what it cannot see.

Purpose: make cross-runtime config drift detectable instead of discoverable-by-accident.
Output: two guards, a co-located `.env.example` block, and a record naming what each cannot catch.
</objective>

<why_not_unify>
Recorded here so a later reader does not "simplify" this away:

Unifying onto `PUBLIC_*` loses the Supabase platform injection for two pairs, and overloads a
browser-exposure marker for the other two. Unifying onto the unprefixed names would require the
frontend to read values Vite will not expose to the browser bundle, breaking the client.

If unification is ever revisited, it is a **decision for the operator with a threat model**, not a
refactor — the same standing that phase 155 gave to collapsing the Deno/frontend identity copies.
</why_not_unify>
