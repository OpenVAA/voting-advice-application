<open_decision id="OQ-2">
**Question (153-RESEARCH.md § OQ-2):** D-B5 requires *"(ii) a `.yarnrc.yml` setting that makes a
mismatch an **error**"*. Measured three ways against the pinned `.yarn/releases/yarn-4.13.0.cjs`,
that setting does not exist: zero occurrences of `enableEngineChecks`, `engineStrict`,
`engine-strict` or `checkEngines`; Yarn's own bundled string reads *"The --ignore-engines option is
deprecated; engine checking isn't a core feature anymore"*; `yarn config --json` lists 101 settings
with no engine-related one; and a scratch project declaring `engines: { node: ">=99" }` **installs
cleanly under Node v24.14.1 with no warning**. D-B5 rejected option (c) on the premise that *"the
package manager already has one"*. **It does not.**

**Planned here (provisional default):** option **(a) — CI-consumption binding.** Rename at both
sites (locked, uncontested), then replace the four hard-coded `node-version: 22.22.1` inputs in
`main.yaml` with `node-version-file: package.json`, so `actions/setup-node` resolves the range from
`engines.node` itself and a re-misspelling breaks every job that uses it. No bespoke code, no new
dependency. *Does not reject an out-of-range Node locally.* The `main.yaml` half is implemented by
153-03; this plan does the rename and the measurement.

**Alternatives, verbatim from RESEARCH:**
- **(b) Install-time binding via a repo script.** *"A `preinstall` (or a `scripts/assert-node-engine.mjs` chained into `lint:check`) comparing `process.version` against `engines.node`. This is the only option that literally rejects an out-of-range Node, locally and in CI — and it is precisely what D-B5(c) rejected on a now-falsified premise. **Does this reversal have your approval?**"*
- **(c) Third-party Yarn plugin** (`devoto13/yarn-plugin-engines`): *"native install-time rejection, but 64★, last pushed 2024-04-07, **not published to npm**, and it would be **committed into `.yarn/plugins/`** and executed on every install by everyone. Flagged **SUS**; not recommended."* **This plan records (c) as REJECTED on supply-chain grounds. It must not be adopted.** If it ever is, a blocking `checkpoint:human-verify` package-legitimacy gate becomes mandatory first (see `COVERAGE.md` § Package legitimacy).
- **(d) Rename only**, restating criterion 2 as *"the field is spelled correctly and is consumed by CI"* — i.e. (a) without the negative-control job.
- **Sub-question, verbatim:** *"should the out-of-range-Node job be a **permanent** gate or a **one-off** observation? A permanently-red-by-design job is unusual CI shape, and under option (a) it would be *skipped entirely*."* Planned default: a **permanent, self-asserting** job (it runs a deliberately out-of-range Node and asserts the repo's gate rejects it, so it is green when the constraint binds) — see 153-03.

**If the operator rules differently:** for (b), add `scripts/assert-node-engine.mjs` beside the other
guards, append `yarn assert:node-engine` to the `lint:check` chain (append-only, per 153-01's
discipline), and drop 153-03's `node-version-file` edit to `main.yaml`. For (d), drop 153-03 Task 2
entirely and record criterion 2's evidence as the rename plus the CI-consumption observation only.
For (c), stop and open a package-legitimacy checkpoint.
</open_decision>
