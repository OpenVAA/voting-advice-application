<objective>
Extract the `VideoController` currently EMBEDDED inside `layout/layoutContext.svelte.ts` as the `video` const-ref
(`show`/`hasContent`/`mode`/`player` `$state` mutated in place + the inline `load()`) into a standalone Svelte 5

all 34 `getLayoutContext()` consumers (reading `video.show`, `video.load(...)`, etc.) stay byte-identical (A4).

decision on the `initLayoutContext()` orchestrator (see `<deferred_coverage>`).

Purpose: VideoController is the last of the four Group F helpers (CLASS-01). Unlike the other three it is
extracted from a host context, so this plan also de-embeds it cleanly while keeping the layout subsystem coherent.
Output: `class VideoController` in its own file with a new headless test; `layoutContext` constructs it; consumers
byte-identical; the orchestrator-deferral recorded.
</objective>

<deferred_coverage>
## DEFERRED COVERAGE — for the plan-checker to weigh (CONTEXT.md boundary note)

The CONTEXT.md boundary note asks the planner to either (a) fold the `initLayoutContext()` orchestrator's OWN
class conversion into this phase, or (b) keep it a factory and FLAG it as deferred.

**Decision: option (b) — `initLayoutContext()` stays a factory this phase; the orchestrator class conversion is
DEFERRED.** Rationale (anchored to LOCKED decisions, not difficulty):
- Locked decision **A1** explicitly lists `initLayoutContext()` among the factory wrappers to KEEP (`return new …`),
  i.e. the factory shape is sanctioned for the orchestrator this phase.
- Locked decision **A10** enumerates the class names this phase produces — `PopupStore`, `SettingsOverlay`,
  `VideoController`, and a persistedState class — and does NOT include a layout-orchestrator class.
- ROADMAP Phase 106 Success Criteria #1 enumerates exactly those four classes; a layout orchestrator class is not
  in scope.
- The orchestrator's remaining members (`progress`, `routeTitle`, `navigation`, `setRouteTitle`,
  `useTopBar`/`usePageStyles`/`useNavigation`) are Group A/D/G context members; converting the orchestrator is the
  Phase-107+ orchestrator-class pattern (the leaf/orchestrator tiers), and folding it here would widen blast radius
  across the 34 `getLayoutContext()` consumers without a locked decision authorizing it.

This is NOT a capability/difficulty judgment (the planner has no such authority) — it is a scope decision driven by
the locked A1/A10 decisions and the ROADMAP success criteria. After this phase, `initLayoutContext()` is a factory
that holds the new `VideoController` class instance plus 3 `SettingsOverlay` class instances; its OWN conversion to
a `class LayoutContextProvider` is the natural Phase-107 follow-on (or a dedicated item the checker may promote).

**Recommendation to the milestone:** track "`initLayoutContext()` orchestrator → class" as a Phase-107 (leaf/
orchestrator tier) coverage item so the layout subsystem reaches full class-shape coherence. CLASS-01 (the four
helper classes) is fully satisfied by this phase regardless.
</deferred_coverage>
