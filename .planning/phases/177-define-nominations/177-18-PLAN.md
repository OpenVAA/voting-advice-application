## Rulings and deviations carried by this plan

1. **The label is one pure function and no context accessor is built** (item P-15): `nominationsSaveAction` is given the draft's three facts and `contestantCtx.taskState`, read in the page's own derived scope. The todo's item 2 stays open for the profile and the question page.
2. **Flagged assumption — the label while the task state is not known.** The UI contract's table has no row for an entity that has a nomination and whose question lists are not loaded yet. The function answers the continuing label of the draft's row there (the last row of `<the_label>`), as the contract already does for an entity with no nomination, where the label is a prediction. It is one branch with its unit case.
3. **Flagged assumption — UI: research · What the database tells the page.** The UI contract marks this row unresolved because it was written before the research. It is built on the research as it now stands: a refusal reaches the page as the writer's result or a rejection (RQ-3; plan 177-09), the entity-level load is rerun with `invalidateAll()` (RQ-6), and the limit of ten stays as ruled (RQ-8; item P-03). What stays unconfirmed until it is run: the refusals through the real API, which plan 177-09's integration cases assert, and assumptions A3 and A4, which Task 2's component test pins. Where that test shows one tick is not enough, the handler waits for the state to be known by the means the test shows sufficient — never by a timer — and the finding is recorded.
4. **The two lock tests are written after the control.** What the tracer's handler does when a lock is found is read from RQ-6 and was not run, and a control whose named set rests on an unrun reading is no control. Both tests are held green by the pre-commit run; whether either would have been red on the tree before this plan is not established and the summary says so.
5. **`tooManyPending` and `failed` are shown in no browser.** Reaching the limit needs ten unconfirmed rows originated by one signed-in user, and a failure the page cannot name needs a broken request; neither is a state the dataset's steps write. Both outcomes are component cases with the context's write as a spy, and the two refusals' codes are asserted through the real API by plan 177-09. Plan 177-21 records them among the states held by a component case alone.
6. **A stored save under a fresh answers lock ends on the nominations view** (item P-17, new): the handler's check that the page is still shown is made after every outcome, the stored one included. The other option — the user goes on to the next task — is that check made on the refused path alone.
7. **The store's guard rides this plan** (operator decision F6 (a)): this phase's rerun of the entity-level load calls the store's `init` again under the same effect. It changes nothing a browser shows, and no spec depends on it.
8. **The pre-commit run is a full default run**, since the store is read by every page of the Contestant app and by specs outside the permutation chain.
9. **The page reads nothing again before it writes** (item P-18, new): the re-read of U-21 follows a refusal, as the UI contract has it. What that leaves, accepted and filed by plan 177-21: a nomination an administrator adds to the entity while the editor is open is left out of the desired set and is deleted by the save, with no refusal — the function's rule for a row the set leaves out (U-03); and a value an administrator changes meanwhile is written over by the card's value as the user last saw it when the user saves a change elsewhere. A row an administrator removed is caught: the function raises on a statement that touches no row, and the page shows `changed`. The other option — one re-read and one comparison before the write — is a located change in this plan's handler; it would also turn a lock away before the database is asked, which the UI contract's stale-browser row does not want.
