## Per-Cell Root-Cause Analyses

### Cell #1 — `candidate-settings.spec.ts:469-499` (SETTINGS-01 wave A `header.showFeedback=false`)

**Root cause (HIGH confidence — verified by trace; documented in v2.11+ todo + spec inline rationale):**
At `apps/frontend/src/routes/(voters)/+layout.svelte:65-70`, `topBarSettings.push({ actions: { feedback: $appSettings.header.showFeedback ? 'show' : 'hide', ... } })` runs in script body **once at mount**. At that moment, `appContext.svelte.ts:74` has initialized `appSettingsValue` to `mergeAppSettings(staticSettings, dynamicSettings)` — pure defaults. The `$effect` at `appContext.svelte.ts:94-100` that merges `page.data.appSettingsData` fires AFTER mount, so the runtime override (`header.showFeedback: false`) lands too late — `topBarSettings` already has the static-default-shaped layer pushed onto the stack.

**Verification path:** `topBarSettings` is a `StackedState` (`StackedState.svelte.ts:21-76`). Its `current` is `$derived(this.#stack[this.#stack.length - 1])`. `push()` mutates `#stack` via `#updater` (which uses `mergeSettings`). The stack is reactive AT THE VALUE LEVEL — but the layer added at script-body time is a static merge of `{ actions: { feedback: 'show', help: 'show' } }` with no re-evaluation when `$appSettings` later changes.

**Fix shape (test-only-fix NOT VIABLE — production-code REQUIRED per D-10):**

```svelte
<script lang="ts">
  // ... existing imports / context init
  const { appSettings, popupQueue, ... } = initVoterContext();
  const { navigation, topBarSettings } = getLayoutContext(onDestroy);

  // OPTION A: $effect-driven push (re-evaluates when $appSettings updates).
  // Caveat: $effect doesn't "replace" a stack layer — it pushes a new one each time.
  // Without state-tracking, this creates an infinite stack growth on every $appSettings change.
  // Resolution: capture initial push index and revert + push on each $effect run.

  // OPTION B (cleaner): use a $derived reactive read directly inside push at mount,
  // OR plumb the `feedback`/`help` attributes through Banner via a reactive prop
  // (sidesteps topBarSettings.push entirely for these two attributes).

  // RECOMMENDED OPTION (per v2.11+ todo recommendation #1, adapted):
  // Wrap the push in $effect with a manual revert-then-push pattern. ~30-60 LOC.
  let topBarSettingsIdx = $state(-1);
  $effect(() => {
    // Read $appSettings reactively
    const next = {
      actions: {
        feedback: $appSettings.header.showFeedback ? 'show' : 'hide',
        help: $appSettings.header.showHelp ? 'show' : 'hide'
      }
    };
    if (topBarSettingsIdx >= 0) topBarSettings.revert(topBarSettingsIdx);
    topBarSettingsIdx = topBarSettings.getLength() - 1; // index BEFORE push
    topBarSettings.push(next);
  });
</script>
```

**LOC estimate:** 25-45 LOC (replace the existing 5-line push with a 10-15-line $effect block + handle initial-revert + onDestroy revert).

**1h-cap fit risk:** LOW. The fix shape is well-understood; the Svelte 5 reactivity pattern is documented in v2.11+ todo. Smoke verifies via the existing parameterized cell loop at `candidate-settings.spec.ts:754-792` — once `skipReason` is removed for cells 2/3 (header.showFeedback / header.showHelp), the loop runs the assertion.

**Side-effect surface (D-10 risk gate):** `topBarSettings.push` is called at 9 other sites across the codebase (candidate/+layout.svelte:61, etc.). The fix to `(voters)/+layout.svelte` is LOCAL — no other layout is touched. **Verify**: per-spec smoke covers candidate-settings.spec.ts CAND-09/10/11 (which exercise the same Banner UI from candidate side). If those regress, the fix is unsound.

**Disposition guess:** FIX-PASS.

### Cell #5 — `voter-feedback-persistence.spec.ts:42-150` (E2E-03 / DETERM-13)

**Root cause (MEDIUM-HIGH confidence — H1+H4 empirically disproved):**

The test asserts the FeedbackModal closes after cancel and after send via `expect(page.getByTestId('feedback-form')).toHaveCount(0)`. Two prior fix-attempts:

**True close signal (per ModalContainer.svelte:92-122 inspection):**

```svelte
function handleClose(noCallbacks?: boolean) {
  modalContainer?.close();    // HTMLDialogElement.close() removes `open` attribute
  inTransition = true;
  isOpen = false;
  if (!noCallbacks) onClose?.();
}
```

The `<dialog>` element STAYS in the DOM (line 132 — `bind:this={modalContainer}` is unconditional). The `class:hidden={!isOpen && !inTransition}` CSS-hides it after the transition completes. **The authoritative close signal is `<dialog>.open` attribute switching from `true` → absent**.

**Two viable fix shapes:**

1. **Test-only fix:** Assert on `getByRole('dialog')` count (HTML5 accessibility tree only includes `<dialog open>` in the dialog role). The current spec already uses `feedbackDialog = page.getByRole('dialog').filter({ has: page.getByTestId('feedback-form') })` at line 87. The H1 attempt with this locator AND `toHaveCount(0)` STILL failed in the trace-restored baseline — but that was BEFORE the trace artifact was inspected. **Trace capture is recommended next action #1 per v2.11+ todo.**

### Cell #6 — `voter-popup-hydration.spec.ts:152-224` (LAYOUT-03 / DETERM-12)

**Root cause (MEDIUM confidence — 86.1-03 cell 1 PASS-WITH-DEFERRAL inheritance):**

## Common Pitfalls

### Pitfall 1: `$effect` infinite stack growth on `topBarSettings.push` (cells #1/#2)

**What goes wrong:** Naive `$effect(() => topBarSettings.push(...))` pushes a NEW layer on every `$appSettings` change, growing the stack indefinitely.

**Why it happens:** `StackedState.push` mutates `#stack` reactively; `$effect` re-runs when `$stack` changes; cycle.

**How to avoid:** Capture the initial stack length before the first push, then `topBarSettings.revert(initialIdx)` BEFORE each subsequent push. OR move the reactive read out of push and into Banner directly via a reactive prop.

**Warning signs:** `topBarSettings.getLength()` grows beyond expected bounds; layout's `onDestroy → revert(indexTopBar)` (layoutContext.svelte.ts:177) reverts to a stale layer.

### Pitfall 2: Cell #3 fire-once guard interacts with `access.voterApp=false` early-return

**What goes wrong:** `$effect(() => { if (!$appSettings.access.voterApp) return; ... })` doesn't fire the notification push when `access.voterApp` transitions false→true mid-session.

**Why it happens:** Svelte 5 `$effect` re-runs on EVERY $appSettings dependency change; the `notificationQueued` guard is purely client-state, not re-evaluated against new appSettings.

**How to avoid:** Track the last appSettings reference that was checked + only suppress on identity match.

**Warning signs:** Cell #3 smoke passes but the corresponding `access.voterApp` cell (#1 in `settings01WaveACells`) regresses.

### Pitfall 3: Phase 86 RESEARCH §3.10 `--likert-only` regression

**What goes wrong:** Any attempt to flip the `voter-app` project's seed to `--likert-only` regresses 60+ PASS_LOCKED cells that depend on non-Likert opinion questions (boolean sort-18, categorical sort-17, number sort-?).

**Why it happens:** The default `e2e` template ships heterogeneous opinion-question types; many existing voter-app specs assert on those specific question types.

**How to avoid:** Cells #7/#8 MUST NOT use a project-wide `--likert-only` flip. The walkToQuestion helper-resilience fix (cell #7+#8 Option B) is the correct fix path.

**Warning signs:** Any plan proposal that re-shapes the data-setup project's seed flags.

### Pitfall 4: Cell #6 fixture pre-hook breaks the test's "FULL page load" contract

**What goes wrong:** The spec docstring (lines 6-39) explicitly says "page.goto('/results?electionId=X&constituencyId=Y') — the URL carries both selectors, so the (voters)/(located)/+layout.ts loader does not need to imply (avoids the 2-election e2e-template election selector page). This exercises the FULL page load (SSR + hydration) path on /results directly." A fixture pre-hook that pre-creates a browser context with localStorage seeded might violate this contract if it also caches additional state.

**Why it happens:** `storageState` in a fixture pre-hook carries cookies, localStorage, and sessionStorage forward — not just the answer-store seed.

**How to avoid:** Use a SCOPED storageState that ONLY seeds `VoterContext-answerStore` localStorage; verify zero cookies + zero sessionStorage in the fixture setup.

**Warning signs:** Cell #6 smoke passes but the test no longer exercises the cold-start SSR path (test loses LAYOUT-03 regression-gate value).

### Pitfall 5: Modal `<dialog open>` attribute switching is rendered-via-`showModal()`/`close()` calls — NOT a bind:

**What goes wrong:** Assertion `await expect(dialog).toHaveAttribute('open', null)` may resolve correctly BUT only if the `dialog.close()` call has completed inside the `handleClose` function AND the DOM has reflected the change.

**Why it happens:** `HTMLDialogElement.close()` is synchronous but the attribute removal hits the DOM in the same tick — Playwright's auto-wait handles this. But if the close transition (`inTransition` state at ModalContainer.svelte:84 + ontransitionend handler at line 134) runs CSS animations, the dialog may stay visible for hundreds of ms even after `open` is removed.

**How to avoid:** Don't conflate "dialog closed" with "dialog removed from layout." For cell #5, the test contract is "user can dismiss and the form text persists" — assert on (1) `open` attribute absence + (2) form input bound state preservation. These are independent contracts.

**Warning signs:** Smoke shows the dialog's `open` attribute is gone but visual debug shows the dialog is still on-screen mid-transition.
