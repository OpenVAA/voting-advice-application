<objective>
Amplify rather than weaken, test whether the mechanism needs contention, and write the named root
cause.

Plan 02 ran the cheap levers. This plan runs the expensive one — CDP CPU throttling at the
PRODUCTION element budget, which is the strong form of criterion 1: a failure forced without
shrinking the oracle proves the race exists at the budget the suite actually runs at. It then tests
D-04's stated risk head-on: the isolated spec may not carry the full suite's contention conditions,
and the suite runs six concurrent Chromium workers locally, which is the environment the 1-in-8 was
observed in. Finally it converts the evidence into the artefact criterion 1 actually requires: a
written root cause that names a mechanism.

Purpose: criterion 1 is not satisfied by a reproduction alone. It requires a *named* mechanism —
file:line, ordering, or contended resource. This plan is where the evidence becomes a diagnosis.

Output: `138-FORCED-REPRO.md` extended with the amplification and contention experiments, and
`138-DIAGNOSIS.md` § Named root cause filled in — or, if all three hypotheses fall, the disproof
ledger and the next hypothesis with its discriminator.
</objective>

Determine whether the mechanism requires the contention the full suite creates, or is present in
isolation.

The suite runs six concurrent Chromium workers locally. That is the environment in which the 1-in-8
was observed, and it is the most plausible amplifier of a rendering-frame cost. The hunt spec run
alone has none of it. These are two different experiments and must be recorded as such.

Method, appended under `## Contention — isolated vs. under worker pressure`:
  1. **Arm ISOLATED** — the best forcing configuration from task 1 (or plan 02, if task 1 did not
     improve on it), hunt project alone, 10 consecutive runs. If a forcing configuration exists this
     is a re-statement of an earlier block; cite it rather than re-running, and say so.
  2. **Arm PRESSURED** — the identical forcing configuration, but with the suite's worker pressure
     present. Two acceptable constructions, pick one and state which and why:
       a. run the hunt project concurrently with a load generator of five further Chromium workers
          driving an existing read-only voter project, or
       b. run the full gate suite with the forcing prefix applied, and read the hunt spec's result out
          of that run's `results.json`.
     Construction (b) is closer to the real environment; construction (a) is faster and isolates the
     variable more cleanly. If (b) is used, note that this is a forced-configuration run and is
     therefore NOT a gate run — the cardinal rule is not violated by a deliberate, scoped,
     recorded negative control, and the run must be excluded from any determinism count. State that
     exclusion explicitly at the point of recording.
