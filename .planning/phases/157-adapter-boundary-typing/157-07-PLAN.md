<objective>
Install the zod parse gate at the Supabase adapter edge, so data crossing the boundary is **validated
into** its type rather than cast into it (D-F2, REVIEW-ADP-01; the reviewer's comments at
`supabaseDataProvider.ts:60`, `:92` and `:511`, "Make sure we need these smelly typecasts nowhere").

The two-step shape this implements, per `157-RESEARCH.md` Pattern 1: the JSONB columns do NOT hold the
application type, they hold a localised, storage-relative variant of it. So "validate into its type"
is really "validate the stored shape, then derive the application type" — parse with the `Stored*`
schemas from `157-02`, then run the existing localisation and URL-ification to produce the application
value.

Also closes decision **E(ii)**: the `Array<unknown>` at `supabaseAdminWriter.ts:80` is criterion 1's
problem in another method, and it gets the same treatment.

Output: parse calls at every typed-JSONB read, a degrade-not-throw failure branch that logs through
the new structured logger, and zero `as Json as unknown as` triple casts in the adapter.
</objective>
