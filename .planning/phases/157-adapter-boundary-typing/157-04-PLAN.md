<objective>
Prove the new SQL against a live Postgres, and regenerate the types the adapter is typed from.

This plan carries the phase's `[BLOCKING]` schema push. Build and type checks pass WITHOUT it,
because TypeScript types come from `packages/supabase-types` (generated from config) rather than from
the live database — so a `.rpc('get_questions', ...)` against a database that never ran the migration
returns `PGRST202` at runtime while `yarn build` stays green. That false-positive verification state
is exactly what this plan closes.

It also closes a measured coverage gap: `grep -rn 'get_nominations' apps/supabase/supabase/tests/`
returns ZERO hits today. The existing `get_nominations` RPC has no pgTAP coverage at all, so this file
carries the first-ever result-shape coverage for it as well as the new `get_questions` coverage.

Output: `apps/supabase/supabase/tests/database/11-question-rpcs.test.sql`, a reset-and-applied local
database, and regenerated `packages/supabase-types`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migrations -> the live database | The only applied path. A schema-only change never crosses it. |
| the live database -> `packages/supabase-types` | Generated types are the adapter's compile-time truth; they can be right while the database is wrong, and vice versa. |
| anon caller -> `get_questions` | Newly granted; the pgTAP security assertions are what prove the grant is what was intended. |
