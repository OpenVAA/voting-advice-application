<objective>
Shrink the adapter-boundary allowlist from ten entries to nine, by taking the one route file that
genuinely belongs to this phase (decision A; `157-RESEARCH.md` section F.7's concrete recommendation).

`routes/candidate/preregister/+layout.server.ts` reads `app_settings` directly through
`locals.supabase.from('app_settings').select('settings')`. That is a plain data read the provider
ALREADY implements as `_getAppSettings`, it needs no new adapter method, and the exact configuration
pattern is used two directories away in the protected candidate layout.

Why only this one: of the eight leaking files, three are HARD and are the heart of Phase 158's login
collapse, three hand the cookie-capable client to the adapter and arguably should never be removed at
all, and two more need adapter methods that do not exist. Driving to zero inside 157 means doing Phase
158's work inside a phase whose six criteria are about typing and validation — and the migration is
already filed as a todo whose Problem section records a live production incident.

Taking one entry makes the allowlist demonstrably a shrinking target rather than a permanent amnesty,
which is what criterion 6's "routes are clean" can honestly mean at the end of this phase.

Output: one route file moved behind the adapter, one allowlist entry removed, and one self-test case
proving the guard now covers it.
</objective>

    the wrong initialisation pattern is how that class of defect spreads, and the correct pattern is two
    directories away.

    reaches the same consumers by a different route. Quote the before and after return statements in the
    SUMMARY as evidence.

    degrades on a malformed row. This route previously read the column raw. Moving it behind the adapter
    inherits that validation for free, which is a small piece of criterion 1 landing through criterion 6.
