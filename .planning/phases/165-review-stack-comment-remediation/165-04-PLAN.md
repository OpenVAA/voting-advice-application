<rewrite_rules>
- A file header states what the file asserts and what fixture it depends on. A section comment states what the next assertions prove and, where it is not obvious, why that property matters. Keep references to other test files and to schema objects by name.
- Assertion descriptions (the last text argument of each pgTAP call) keep their meaning and lose only their planning references and narrative, for example `'resolve_email_variables is NOT executable by anon (CR-01)'` becomes `'resolve_email_variables is NOT executable by anon'`. Single quotes inside a description stay doubled (`''`).
- Never change an assertion's SQL, its expected value, the `plan (N)` count, or the order of assertions. Some suites identify recorded failures by assertion number, so an inserted or moved assertion is a behaviour change.
- One to three sentences per comment block; lists as `-- - item`; no measurement anecdotes that do not constrain the test.
</rewrite_rules>
