<objective>
The three F19 sites, and the single highest-consequence recording decision in the phase.

`URLSearchParams.get()` and `FormData.get()` return `string | null`, never `undefined`, so
`expect(null).toBeDefined()` **passes** — the assertion nominally guarding "the JAR request parameter
is present" is structurally incapable of detecting its absence. That is the finding. But the line
three below each assertion (`requestParam!.split('.')`, `assertion.split('.')`) throws a `TypeError`
on `null`, so the test file still goes red. Vitest reports per-test outcomes, not per-assertion
outcomes, so the passing `toBeDefined()` is invisible in the summary line.

If the record carries one "observed" column it will read FAIL, ROADMAP criterion 2's "reads blind but
fails correctly is withdrawn" will fire, and three valid findings will be withdrawn by accident —
shrinking ASSERT-03 and Phase 140 as well as ASSERT-07/Phase 142. D-02 forecloses exactly this: a
vacuous-but-red assertion is `confirmed` with the mitigation recorded on the verdict, because the cost
is diagnosis time rather than coverage. Criterion 2's withdrawal clause reaches only findings whose
OWN assertion catches the regression, not findings rescued by an incidental downstream throw.

So every observation in this plan is recorded twice — assertion outcome and file outcome — with the
verbatim runner failure block showing the failing line, and each verdict cites the assertion column.

**This plan ships zero product code.** `apps/frontend/src/lib/api/utils/auth/providers/idura.ts` is
injected and reverted inside the task that injects it. These injections strip authentication material
from a live OIDC flow, so the hygiene loop is not bookkeeping here — it is the security control.

Purpose: ASSERT-01 — confirm or withdraw each single-source finding against the live code (D-01).

Output: `139-VERDICTS.md` §§ 5.7, 5.8 and 5.9 filled, § 4 rows 7-9 updated, four placeholders left.
</objective>
