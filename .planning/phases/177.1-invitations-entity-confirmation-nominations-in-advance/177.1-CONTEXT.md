## Phase Boundary

An admin who seeds an invitation says, in the same call, whether the invited entity is confirmed and
which nominations it holds, so that inviting an entity never changes what voters see by side effect.
**Requirements:** none new — extends **INV-01** and **INV-05**; **E2E-03** as closing criterion.
**Depends on:** Phase 174 (`create_invitations`, the invitation E2E fixtures) and Phase 177 (the
election-type rules, the parent pairing and the create-the-parent's-nomination step). **UI hint:** no —
a schema, RPC and test-fixture phase.

It delivers:

- **`create_invitations` with a required `p_confirm_entity`** that replaces the two-argument form, and
  with nominations stated per entity-scope invitation under a `nominations` key (D-02–D-05);
- **the nomination write inside the invitation call**: create or update, never delete, with `confirmed`
  stated on every object, in the caller's transaction and under the caller's policies (D-06–D-11);
- **one `private` resolve-or-create-the-parent's-nomination function**, extracted from
  `set_entity_nominations` and called by both writers (D-12, D-13);
- **every caller moved to the new signature** — dev-seed, the E2E admin client and fixture, every spec
  and setup that seeds through them, the frontend integration test, pgTAP, the docs (D-16, J1);
- **the journey re-pointed** at the extended call, `invitationFlow.whileHiddenFromVoters` removed, and
  `invitation-contract.spec.ts` showing that `false` confirms no one (D-14, D-15, D-17);
- **INV-05 reworded** (D-18), **the witness assertion of pgTAP file 39 scoped** (D-21), and **a todo
  filed** for invitations in dev-seed templates (D-19).

**Not in this phase:** invitations in dev-seed templates (D-19, todo filed); nominations of factions and
alliances through an invitation (D-10 — they stay with `bulk_import`); confirming a parent's nomination
as a by-product (D-13); any change to the registration-mode matrix, `claim_invitations`, the
`account-access` function or any other Edge Function (none calls `create_invitations`; Phase 180's
counts do not move); any page of the application.

### Roadmap success criteria (ROADMAP.md § Phase 177.1, as amended 2026-10-08)

1. `create_invitations` takes a required `p_confirm_entity`. The invited entity is confirmed only when the
   caller says so; no call confirms an entity implicitly, and a call that omits the parameter is refused.
2. `create_invitations` takes an optional `p_nominations`, a JSONB array of objects, one per nomination,
   with the same keys as Phase 177's `set_entity_nominations` takes: for each nomination an election id,
   a constituency id, an optional parent entity id, an optional election symbol, `confirmed`, the
   election round, and the nomination's other writable columns. The nominations are written in the same
   transaction as the invitation, pass the same validation as any other nomination write, and a caller
   without the authority to write them is refused with nothing written. **— reworded by D-05 (a
   `nominations` key on each invitation), D-08 (the round optional) and fact 12 (the parent is 177's
   `parent` object, not a bare id); the rewording is D-20's last plan's.**
3. A parent entity id is resolved to the parent's existing nomination in that election and
   constituency, and one is created when none exists. That resolve-or-create step is one utility
   function, and the self-nomination path of Phase 177 calls the same one; no second copy of the rule
   exists.
4. The E2E journey invites its candidate through the extended call, with the entity's confirmed state
   and its nomination stated outright, and runs as the invitation model leaves an invited user.
   `invitationFlow.whileHiddenFromVoters` is removed, and no spec hides an entity by unconfirming rows
   around a seeding step.
5. Every caller of `create_invitations` — the dev-seed writer, the E2E admin client, pgTAP, the docs —
   passes the new parameter; the seed writer and the docs pass "confirmed" for a named entity unless
   told otherwise; and the full E2E suite is green at close (E2E-03). **— "the dev-seed writer" is read
   as `SupabaseAdminClient.createInvitations` (D-19); the caller population is larger than listed
   (fact 3).**

### A — `p_confirm_entity`

- **D-02 (177.1-A1 (a) ★):** `true` confirms every **named** entity of the batch; a nameless one stays
  unconfirmed, by the name test `create_invitations` applies today (a candidate's two names non-blank;
  `private.localized_has_text(name)` for the other three types). Each returned item says whether its
  entity is now confirmed (D-11). A batch may mix named and nameless entities.
  **If wrong** (confirm whatever the name): an empty name is frozen on confirmation, and the user meant to
  fill it in cannot.
- **D-03 (177.1-A2 (a) ★):** `false` means "this call confirms no one", **never** "unconfirm". An entity
  that is already confirmed stays confirmed; an admin unconfirms by editing the entity.
  **If wrong** (`false` unconfirms): inviting a second user to a party voters already see would take it
  out of the voter app — the mirror image of the defect this phase removes.
- **D-04 (177.1-A3 (a) ★):** One value per call; **no item key** overrides it. A batch that wants both
  states is two calls.

### B — The nominations

- **D-05 (177.1-B1 (a) ★) ⚠ DECIDE:** **A `nominations` key on each entity-scope invitation, holding the
  array.** The objects keep 177's keys, because the invitation already names the entity. Refused with
  `22023`: the key on a project-scope item; nominations stated for the same entity on two items of one
  batch. Criterion 2's "takes an optional `p_nominations`" is reworded (D-20).
- **D-06 (177.1-B2 (a) ★) ⚠ DECIDE:** **Create or update, never delete.** An object with an `id`
  describes that nomination of the invited entity and changes it where it differs; an object without one
  is a new row; a new row at a contest where the entity already stands under the same parent is refused
  by the existing uniqueness key. A missing key and an empty array both write nothing. Inviting someone
  can never remove a nomination. *See J2: 177's hand-over reads the invitation as insert-only.*
  **If wrong** (the whole set, as in 177): an invitation sent with an empty array or with only the new
  nomination deletes the entity's other nominations in reach.
- **D-07 (177.1-B3 (a) ★):** **`confirmed` is required on every nomination object**; a missing key is
  refused with `22023`. A project editor stating `confirmed: true` is refused (fact 10) and the whole
  batch with it; that rule is not this phase's to change.
  **If wrong** (a default): either a nomination is published by omission, or a confirmed entity stays
  invisible with no message saying why.
- **D-08 (177.1-B4 (a) ★):** An **optional `election_round`**; absent means the election's
  `current_round`, read in the function. The other writable columns (`name`, `short_name`, `info`,
  `color`, `image`, `sort_order`, `subtype`, `external_id`) are accepted under their column names.
  `custom_data` is merged, so the `requestedParentOrganization` key that `parent.kind = other` sets is
  not overwritten. Criterion 2 is reworded from a key the object has to a key it may have.
- **D-09 (177.1-B5 (a) ★):** **Uuids only**, as in 177: `election_id`, `constituency_id` and the
  parent's `entity_id`. A caller that works from external ids resolves them first, as the E2E admin
  client already does for the entity (`entityIdForGrantTarget`).
- **D-10 (177.1-B6 (a) ★):** As in 177: **candidate and organization only**; a candidate's parent an
  organization, an organization's an alliance; `parent.kind` `none`, `entity` and `other` as there,
  `keep` only with an `id`. `nominations` on an invitation for a faction or an alliance is refused with
  `22023`; those rows stay with `bulk_import`.
- **D-11 (177.1-B7 (a) ★):** Each returned item gains **`entity_confirmed`** (the entity's state after
  the call; `null` on a project-scope item) and, when it stated nominations, **`nominations`** with
  177's counts `inserted`, `updated`, `unchanged`, `parents_created` (no `deleted`, by D-06).
