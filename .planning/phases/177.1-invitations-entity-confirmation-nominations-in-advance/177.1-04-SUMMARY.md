# Phase 177.1 Plan 04: create_invitations states the confirmation and the nominations Summary

**`public.create_invitations (p_project_id, p_invitations, p_confirm_entity)` replaces the two-argument form. The third parameter has no default, and `NULL` is refused. `true` confirms each named invited entity; `false` confirms none and never unconfirms. An entity-scope candidate or organization item may carry a `nominations` array. Each object is validated by the shared private functions. The nominations are created or updated as the caller, never deleted, and their confirmation is read back. All 47 pgTAP files pass on a freshly reset database (2602 tests). File 39 also passes on a database that holds a foreign witness record.**

## The function (Task 1)

**Signature and privileges:**
- `CREATE OR REPLACE FUNCTION public.create_invitations (p_project_id uuid, p_invitations jsonb, p_confirm_entity boolean) RETURNS jsonb LANGUAGE plpgsql SECURITY INVOKER SET search_path = ''`, with no `DEFAULT`.
- `REVOKE … FROM PUBLIC, anon` and `GRANT … TO authenticated, service_role` on `(uuid, jsonb, boolean)`.
- No `DROP FUNCTION` and no overload.

**The body is one loop, in the order ruling 1 gives. For each item:**
1. Today's checks, with today's messages.
2. When the item has the key:
   - the project-scope refusal;
   - the faction/alliance refusal, with the article per type;
   - `private.nomination_list_checked`;
   - the same entity on two items (`<type>:<id>` keys);
   - `private.entity_project_id` against `p_project_id`.
3. Then, per object:
   - `private.nomination_object_checked`;
   - `confirmed` a JSON boolean;
   - `election_round` an integer (`pg_input_is_valid`);
   - the election read as the caller within the project;
   - the eight presentation columns by JSON type;
   - `custom_data` an object without `requestedParentOrganization`;
   - with an `id`: not repeated, the stored row of the invited entity in the project, and election, constituency and stated round equal to the stored row's;
   - without an `id`: `keep` refused.
4. The invitation INSERT, then the code read and cleared.
5. `IF p_confirm_entity AND v_scope = 'entity'`: today's four confirming UPDATEs, unchanged.
6. The nominations (ruling 2):
   - **New object:** the `entity` parent goes through `private.parent_nomination_resolved`. Then one INSERT with `parent_nomination_id` set and every stated column except `confirmed`, taking the id from `RETURNING`. When `confirmed: true` is stated, `UPDATE … SET confirmed = true … RETURNING confirmed` follows.
   - **`id` object:** the target is the stored row, overlaid with the stated columns, the computed parent and custom data, and the stated `confirmed`. If it equals the stored row, the object counts as `unchanged`. Otherwise one UPDATE writes every writable column at its target, `RETURNING confirmed`.
   - **Read-back:** `NOT FOUND`, or a confirmation that differs from the stated one, raises 42501 `… could not be written as stated`.
7. `entity_confirmed`, read as the caller.
8. The answer: today's eight keys, `entity_confirmed`, and `nominations` only when the item stated the key.

After the loop, when a nomination was written, `SET CONSTRAINTS public.nominations_parent_required IMMEDIATE;` then `… DEFERRED;`.

- **Result:** the reset ran again and exited 0 (`177.1-04-reset-t1-r2.*`). This happened before the commit, in Task 1's commit.
