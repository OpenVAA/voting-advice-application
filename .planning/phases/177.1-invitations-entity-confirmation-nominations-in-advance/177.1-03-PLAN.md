## Rulings and deviations carried by this plan

1. **The messages are the execution rules'** § *Messages*: the tests assert them whole, and plan 04 writes them.
2. **`true` at every existing call** keeps every assertion of file 39 meaning what it meant (research A7); `false`, `NULL` and the omission are file 47's.
3. **The research's open assumptions, decided here and pinned by a test each**: a contest change on an `id` object is refused, not performed (A4: it would be a delete, which D-06 forbids); the "only object of its election" rule of `set_entity_nominations` does not apply to an invitation — an organization may be nominated in two constituencies of one election in one item (A5); `custom_data` carrying `requestedParentOrganization` is refused (A6); an empty array answers four zeros and a JSON `null` is refused (A9).
4. **The update path is the admin's (J2).** A project admin or editor holds `project.edit_nominations` on every row and the service role bypasses the policies, so the invitation needs neither `set_entity_nominations`' reach nor its seven UPDATE forms; an `id` that names no nomination of the invited entity is refused.
5. **The read-back (research Pitfall 2).** A project editor's `confirmed: true` on a row already confirmed, with another column changed, is silently unconfirmed by rule 2 of `enforce_nomination_confirmation`; the function must refuse it, and file 47 asserts the refusal.
6. **The pass-through refusals are asserted by SQLSTATE and their message's beginning** (`Setting nomination `, `Nomination parent required: `), never re-worded.
