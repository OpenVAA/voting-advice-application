### WR-01: `create_invitations` checks the invited entity's project with a SECURITY DEFINER read before the authority check

**Files modified:** `apps/supabase/supabase/tests/database/47-invitation-nominations.test.sql`, `apps/supabase/supabase/schema/506-invitation-rpcs.sql`, `apps/supabase/supabase/migrations/00001_initial_schema.sql` (regenerated)
**Commits:** `6c4f6e28f` (the red assertion, alone), `e358b4fe6` (the schema fix and the regenerated migration)
**Status:** fixed: requires human verification (a logic change in an authority-adjacent check)
**Applied fix:**
- In `create_invitations`, `private.entity_project_id(...) IS DISTINCT FROM p_project_id` is replaced by a read under the caller's row-level security: `PERFORM 1 FROM public.candidates` (or `public.organizations`) `WHERE e.id = v_target_id AND e.project_id = p_project_id`, then `IF NOT FOUND` raises the same 22023 message. The check stays where it was, so the order of messages in files 39, 46 and 47 is unchanged.
- A caller with authority loses nothing. The entity-scope arm of `admin_insert_invitations` asks `project.edit_entities`. Every role that holds it (global, account and project admin, and project editor) also holds `project.read_entities`, which `authenticated_select_candidates` / `_organizations` read. The service role bypasses RLS, so a candidate of another project is still refused by `project_id = p_project_id`; the 46-XPROJ service-role assertion stays green.
- The function header's "Refused besides the shapes" sentence now reads "...no entity of p_project_id the caller can read".
- New pgTAP assertion in 47 (WHO block, plan 103 → 104, plus `eid('no_entity')`): admin_a holds no authority over project B. Its call to `create_invitations(project_b, ...)` with nominations gets `22023 ... no entity of the project` both for candidate_b, which exists but is unreadable to admin_a, and for an id that names no entity.
- **Red evidence:** `tests/e2e-runs/177.1-unit/177.1-fix-pgtap-red.{log,exit,head}` (exit 1, head `6c4f6e28f`). The one failure is that assertion. Before the fix the existing candidate passed the check and was refused further on, at the election check (`...names an election_id that is no election of the project the caller can read`), while the absent id got the cross-project refusal. That difference is the oracle.
- **Green:** full pgTAP suite on a fresh reset, `Files=47, Tests=2603` PASS. `database.ts` shows no diff after `yarn db:types` on a freshly reset database, as expected since no signature changed.
- **Reviewer to confirm:** a caller without authority still gets 42501 from the invitation policy for an entity they *can* read (a published candidate of an open project). That reveals nothing, because the row is public.

## Skipped Issues

### IN-01: `set_entity_nominations` now reports shape faults before row-reading faults

**File:** `apps/supabase/supabase/schema/503-entity-rpcs.sql:924-968`
**Reason:** skipped. Restoring the old order is not clean, and the new order is intended and documented.

- Restoring the old order means interleaving the row checks inside the shape checks. Those row checks are the duplicate id, the id outside the reach, the election mismatch and the readable-election read. The shape checks live in `private.nomination_object_checked`.
- That would mean splitting the function in two, or giving it a mode. Either way its binding name and signature (fixed in `177.1-EXECUTION-RULES.md`) and file 46, which pins it, would change. `create_invitations`, which asks the same function, would be reworked as well. That is the churn the orchestrator ruled out.
- The new order is the one the phase meant to build. The function header of `set_entity_nominations` states it: "the checks that read rows follow each object's shape check". Every message stays byte-identical, and 43 does not assert combined faults.
- The review's optional mitigation was not added: a pgTAP assertion in 46 pinning the order for a two-fault object. The operator can add it if the order is to be guarded.

**Original issue:** An object with two faults now gets a different 22023 message than before. For example, an `id` outside the reach combined with a 51-character symbol now reports the symbol. API clients can observe this, and no test pins it.
