## Warnings

### WR-01: `create_invitations` checks the invited entity's project with a SECURITY DEFINER read before the authority check

**File:** `apps/supabase/supabase/schema/506-invitation-rpcs.sql:230-233`

**Issue:** `create_invitations` is documented as holding "no authority rule of its own": the INSERT policy `admin_insert_invitations` decides, at line 394. For an item that states `nominations`, the function first runs the following check, and runs it before that INSERT:

```sql
IF private.entity_project_id(v_target_type, v_target_id) IS DISTINCT FROM p_project_id THEN
  RAISE EXCEPTION 'create_invitations: p_invitations[%] states nominations for an entity that is no entity of the project', v_index
```

`private.entity_project_id` is `SECURITY DEFINER` (`301-auth-functions.sql:265-277`), so this read ignores the caller's row-level security.

Any `authenticated` user can therefore call `create_invitations(X, '[{"target_type":"candidate","target_id":"<U>","nominations":[]}]', false)` for a project X where they hold no authority. The answer is a yes/no oracle:

- 22023 "no entity of the project" means uuid U is not a candidate of X.
- 42501 from the invitations RLS means U is a candidate of X, including an unpublished, unconfirmed one the caller cannot read.

Before this phase, every `target_id` item from a caller without authority failed the same way, with 42501. The caller does need to know the uuid already, which limits the impact, but the function now answers a question about rows the caller cannot see before it has checked the caller's authority.

**Fix:** Ask the question as the caller rather than as the owner, or ask it only after the invitation INSERT has passed the policy. The batch is one transaction, so the later INSERT is rolled back on refusal anyway. For example, keep the check where it is but read under the caller's RLS:

```sql
-- as the caller: an entity the caller cannot read is "no entity of the project"
CASE v_target_type
  WHEN 'candidate' THEN
    PERFORM 1 FROM public.candidates e WHERE e.id = v_target_id AND e.project_id = p_project_id;
  WHEN 'organization' THEN
    PERFORM 1 FROM public.organizations e WHERE e.id = v_target_id AND e.project_id = p_project_id;
END CASE;
IF NOT FOUND THEN
  RAISE EXCEPTION 'create_invitations: p_invitations[%] states nominations for an entity that is no entity of the project', v_index
    USING ERRCODE = '22023';
END IF;
```

The other option is to move lines 230-233 into the write phase, after the `INSERT INTO public.invitations`. Keep the 46-XPROJ service-role assertion green either way: the service role bypasses RLS, so the caller-scoped read still refuses a candidate of another project.

### WR-02: The dev-seed nomination seed types accept values `create_invitations` always refuses

**File:** `packages/dev-seed/src/supabaseAdminClient.ts:142-150, 161`

**Issue:** `InvitationNominationSeed` and `EntityInvitationSeedItem` are the typed contract of the SQL function, but several members are wider than what the function accepts. A value that typechecks can still be a guaranteed 22023 at run time:

| Member | Type allows | `create_invitations` (506) |
|---|---|---|
| `custom_data` (line 150) | `Record<string, unknown> \| null` | Refuses JSON `null` at lines 310-314 (`jsonb_typeof(...) <> 'object'`). The `\| null` arm is always refused. |
| `name`, `short_name`, `info`, `color`, `image` (lines 142-146) | `Json \| null` from `TablesInsert<'nominations'>`, so strings, numbers and arrays too | Accepts only a JSON object or null (lines 285-289, 298-303). |
| `sort_order` (line 147) | `number \| null`, including non-integers | Refuses a non-integer (`pg_input_is_valid(..., 'integer')`, line 300). |
| `nominations` (line 161) | Present for every `target_type: InvitationTargetType`, which includes `faction` and `alliance` | Refuses both (lines 214-218). The TSDoc states the restriction, but the type does not enforce it. |

The phase's own rule is "TypeScript strictly", so make the types match the function.

**Fix:**

```ts
type LocalizedObject = Record<string, unknown>;
export interface InvitationNominationSeed {
  // ...
  name?: LocalizedObject | null;
  short_name?: LocalizedObject | null;
  info?: LocalizedObject | null;
  color?: LocalizedObject | null;
  image?: LocalizedObject | null;
  sort_order?: number | null; // document: an integer
  custom_data?: Record<string, unknown>; // no `| null`: the function refuses it
}
```

Split `EntityInvitationSeedItem` so that `nominations` appears only on the arm where `target_type: 'candidate' | 'organization'`, and set `nominations?: never` on the `'faction' | 'alliance'` arm.

## Info

### IN-01: `set_entity_nominations` now reports shape faults before row-reading faults

**File:** `apps/supabase/supabase/schema/503-entity-rpcs.sql:924-968`

**Issue:** The old order was:

1. object, `election_id`, `constituency_id`
2. `id`, then the id's row checks (duplicate id, id outside the reach, election mismatch)
3. the readable-election check
4. symbol, parent, `keep`

The new order runs every shape check in `private.nomination_object_checked`, including symbol and parent, before the id's row checks and the election read. An object with two faults now gets a different 22023 message. For example, an `id` outside the reach combined with a 51-character symbol now reports the symbol, where it used to report the id.

Each message is still byte-identical, as the rules require. The new header text documents the order, and 43 does not assert combined faults. This is observable to API clients and is not pinned by any test.

**Fix:** None is required if the new order is intended. Otherwise add one pgTAP assertion in 46 that pins the order for a two-fault object, so a later edit cannot change it unnoticed.

### IN-02: `rowIdByExternalId` duplicates `entityIdForGrantTarget`'s query

**File:** `tests/tests/utils/supabaseAdminClient.ts:683-700, 710-723`

**Issue:** Both methods run the same chain: `.from(table).select('id').eq('external_id', …).eq('project_id', this.projectId).single()`, with the same error format. `organizations` appears in both lookups. The code-review checklist asks for no repeated code.

**Fix:** After it resolves the table, have `entityIdForGrantTarget` call `this.rowIdByExternalId(table, target.externalId, caller)`. To do that, widen `rowIdByExternalId`'s `table` parameter to include `candidates`.

### IN-03: The journey comment describes the removed mechanism

**File:** `tests/tests/specs/contestant/contestant-journey.spec.ts:352`

**Issue:** The comment reads "...so voters never see the candidate and no row is toggled". "No row is toggled" only makes sense against the wrapper this phase removed, which toggled confirmations around the seeding. Under Comment Hygiene a comment describes the code as it is, to someone reading it cold.

**Fix:** Drop the clause: "The one call confirms the candidate and states its only nomination unconfirmed, so voters never see the candidate: voter specs read this dataset's public rows while this walk runs."
