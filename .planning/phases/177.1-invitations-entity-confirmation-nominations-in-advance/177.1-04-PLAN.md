## Rulings and deviations carried by this plan

1. **One loop, the existing order kept** (the research drew two passes; this is the planner's choice, within the context's discretion on the function's body). Each item runs, in order: today's checks with today's messages; then, when it has a `nominations` key, every check of that key and of each object — so an item's nominations are validated whole before anything of that item is written; then the invitation INSERT and the code read; then the confirming UPDATE under `IF p_confirm_entity`; then the item's nominations; then `entity_confirmed`. An item without the key meets exactly the refusals, in exactly the order, it meets today, so file 39's assertions change by their third argument alone. The batch is one transaction, so a refusal at a later item stores nothing of an earlier one.
2. **The write as the caller.** A new object: parent kind `entity` asks `private.parent_nomination_resolved` first (admin callers are not held by the pairing guard; the service role passes no policy), then one INSERT of the entity's own row with `parent_nomination_id` set and every stated column except `confirmed` (absent from the `authenticated` INSERT grant), then, when the object states `confirmed: true`, `UPDATE … SET confirmed = true WHERE id = <new id> RETURNING confirmed`. An `id` object: the stored row read (as the caller) during validation; the target of each writable column computed — stated, or stored when not stated; `custom_data` merged over the stored object, then the parent's kind applied last (`other` sets the requested name, `entity` and `none` remove it, `keep` leaves it); if nothing differs, `unchanged`; otherwise one UPDATE of `election_symbol`, `parent_nomination_id`, `custom_data`, `confirmed` and the presentation columns at their targets, `RETURNING confirmed`. Every UPDATE that affects no row, and every `confirmed` read back that is not the stated one, raises the 42501 of the rules (research Pitfall 2).
3. **Force the parent rule only when a nomination was written**: `SET CONSTRAINTS public.nominations_parent_required IMMEDIATE;` then `… DEFERRED;`, so a call without nominations does not judge rows an earlier statement of the caller's transaction left pending.
4. **No `DROP FUNCTION`.** The declarative schema is applied to a fresh database; the two-argument form exists after this plan only on a database that was not reset, and every gate resets first (research § *Runtime State Inventory*).
5. **The red window opens with Task 1's commit** and is closed by plan 05's: `yarn typecheck` (dev-seed, the integration test) and every E2E spec that seeds an invitation are red in between. This plan's gate rows are therefore the database rows only. The operator accepted the window as planned on 2026-10-18 (execution rules § *When this phase runs*).
6. **[BLOCKING] schema push** is `yarn db:reset` applying the regenerated migration (no remote project exists); Task 2's rows are that push.
