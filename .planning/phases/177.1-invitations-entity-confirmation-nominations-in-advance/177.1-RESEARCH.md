**Researched:** 2026-10-17

## Summary

Everything this phase changes is already on the tree in a form that can be read: `create_invitations` is a 120-line plpgsql loop in `schema/506-invitation-rpcs.sql` whose only side effect beyond the invitation row is a confirming `UPDATE … SET confirmed = true` per entity-scope item; `set_entity_nominations` in `schema/503-entity-rpcs.sql` holds, inline, both pieces D-12 and J4 extract — the per-object validation loop and the "parent holds no nomination at the contest: create it" step. The work is (1) a third, `DEFAULT`-less parameter and an `IF p_confirm_entity` around the existing confirming `UPDATE`s, (2) a `nominations` key per entity-scope item written as the caller, (3) two new `private` SECURITY INVOKER functions that `set_entity_nominations` is re-pointed at with byte-identical messages, and (4) a mechanical sweep of ~40 call sites across pgTAP, dev-seed, the E2E admin client, the fixture and eight spec/setup files.

Three measurements settle the CONTEXT's *inferred* items. On PostgreSQL 17 (the local stack's major version), a call that omits a no-`DEFAULT` parameter fails at parse time with `42883 … does not exist`, by name and by position; through PostgREST the same call is `PGRST202` (HTTP 404). A new function in a non-`public` schema gets `EXECUTE` for `PUBLIC` by default, so each new `private` function must `REVOKE … FROM PUBLIC, anon` and `GRANT … TO authenticated, service_role` explicitly (the `301` blanket grant does not reach it). `CREATE OR REPLACE` with an added parameter creates a second overload rather than replacing the first — harmless on the declarative schema (applied to a fresh database by `db reset`), but a database that is not reset after the change keeps the two-argument form callable.

The research found three things the CONTEXT does not name that the planner must carry: an authenticated **project editor** stating `confirmed: true` on an *update* of an already-confirmed nomination is silently unconfirmed by rule 2 of `enforce_nomination_confirmation` (it raises only on a false→true transition), so the function must read the row's confirmation back and refuse a mismatch; the **admin** INSERT path on `nominations` has no entity-project check (`admin_insert_nominations` asks only `project.edit_nominations`, and `validate_nomination` checks only the election's and constituency's project), so the invitation path must refuse a parent — and an invited entity with nominations — that is not of `p_project_id`; and `set_entity_nominations`' "a new nomination must be the only object of its election" rule is a whole-set editing rule, not a row validation, and should not be applied to invitations.

**Primary recommendation:** Build two `private` SECURITY INVOKER functions in `503` (an object validator taking prefix and label, and a resolve-or-create-parent function returning the id and whether it created), re-point `set_entity_nominations` at both without touching file 43, then rebuild `create_invitations (p_project_id uuid, p_invitations jsonb, p_confirm_entity boolean)` as a validate-everything-then-write function; append `true` to every existing call, exercise `false`, `NULL` and omission in new tests, and put the nominations behaviour in a new pgTAP file `46-invitation-nominations.test.sql`.

#### A — `p_confirm_entity`

- **D-02 (177.1-A1 (a) ★):** `true` confirms every **named** entity of the batch; a nameless one stays

  entity is now confirmed (D-11). A batch may mix named and nameless entities.
  **If wrong** (confirm whatever the name): an empty name is frozen on confirmation, and the user meant to
  fill it in cannot.
- **D-03 (177.1-A2 (a) ★):** `false` means "this call confirms no one", **never** "unconfirm". An entity
  that is already confirmed stays confirmed; an admin unconfirms by editing the entity.
  **If wrong** (`false` unconfirms): inviting a second user to a party voters already see would take it
  out of the voter app — the mirror image of the defect this phase removes.
- **D-04 (177.1-A3 (a) ★):** One value per call; **no item key** overrides it. A batch that wants both

#### B — The nominations

- **D-05 (177.1-B1 (a) ★) ⚠ DECIDE:** **A `nominations` key on each entity-scope invitation, holding the
  array.** The objects keep 177's keys, because the invitation already names the entity. Refused with
  `22023`: the key on a project-scope item; nominations stated for the same entity on two items of one
  batch. Criterion 2's "takes an optional `p_nominations`" is reworded (D-20).
- **D-06 (177.1-B2 (a) ★) ⚠ DECIDE:** **Create or update, never delete.** An object with an `id`
  describes that nomination of the invited entity and changes it where it differs; an object without one
  is a new row; a new row at a contest where the entity already stands under the same parent is refused
  by the existing uniqueness key. A missing key and an empty array both write nothing. Inviting someone
  can never remove a nomination. *See J2: 177's hand-over reads the invitation as insert-only.*
  **If wrong** (the whole set, as in 177): an invitation sent with an empty array or with only the new
  nomination deletes the entity's other nominations in reach.
- **D-07 (177.1-B3 (a) ★):** **`confirmed` is required on every nomination object**; a missing key is

### Pattern 1: The J4 validator — one object, prefix and label as arguments

**What:** A `private` plpgsql function that performs the pure shape checks of one nomination object, raises with `<prefix>: <label> …`, and returns the normalised values. Context checks (duplicate `id`, reach, election match, move, election readable, `keep` vs. new) stay in each caller **after** the validator call.

### Pattern 4: The nomination write inside the invitation call

- **New object (no `id`):** for `parent.kind = entity`, call the resolve-or-create function first (admin callers are not subject to the pairing guard of `entity_insert_parent_nominations`, so order is free), then `INSERT` the entity's row with `parent_nomination_id` set, `election_round` = the stated round or the election's `current_round`, `election_symbol` trimmed, the presentation columns stated, `custom_data` = stated object (if any) with the requested-name key applied for `other`. **Never name `confirmed` in the INSERT**: it is absent from the `authenticated` INSERT grant — `GRANT INSERT ( project_id, candidate_id, organization_id, faction_id, alliance_id, election_id, constituency_id, election_round, parent_nomination_id, custom_data, name, short_name, info, color, image, sort_order, subtype, election_symbol, external_id ) ON public.nominations TO authenticated;` [VERIFIED: 303-column-grants.sql:178-198]. When the object states `confirmed: true`, follow with `UPDATE … SET confirmed = true WHERE id = <new id>`; for a project editor rule 2 refuses it by name ("Setting nomination % confirmed requires the nomination.confirm permission on project %; …") and the whole batch fails (fact 10) [VERIFIED: 011-validation-functions.sql:513-519].
- **Object with `id` (J2):** the row must be a nomination of the invited entity (`candidate_id`/`organization_id` = target) that the caller can read, else `22023`; the stated `election_id`, `constituency_id` and (if stated) `election_round` must equal the stored row's (a contest change would be 177's delete-and-insert "move", which D-06 forbids). Update only the columns that differ, with `confirmed` in the same statement, and `RETURNING confirmed` compared with the stated value.
- **Why the read-back:** rule 2 of `enforce_nomination_confirmation` reads, verbatim, `IF NEW.confirmed AND NOT OLD.confirmed THEN RAISE …; END IF; NEW.confirmed := false;` for an `authenticated` caller without `nomination.confirm` [VERIFIED: 011-validation-functions.sql:513-519]. A project editor who states `confirmed: true` on a row that is **already** confirmed and changes anything else gets no error and an unconfirmed row. The function must raise (`42501`, its own message) when the row's confirmation after the UPDATE differs from what the object stated.
- **RLS shortfall:** an UPDATE that RLS hides affects zero rows silently; raise `42501` on `NOT FOUND`, as `set_entity_nominations` does (`IF NOT FOUND THEN RAISE EXCEPTION USING MESSAGE = c_unwritten, ERRCODE = '42501';`) [VERIFIED: 503-entity-rpcs.sql:967-969].
- **`custom_data`:** merge the stated object over the stored one, then apply the parent rule last (`other` sets `requestedParentOrganization`, `entity`/`none` remove it, `keep` leaves it). Refuse (`22023`) a stated `custom_data` that is not an object or that itself carries `requestedParentOrganization`: otherwise `keep` would let an untrimmed, uncapped requested name in past the validator.
- **Presentation columns** (`name`, `short_name`, `info`, `color`, `image` objects or null; `sort_order` integer or null; `subtype`, `external_id` string or null): check JSON types and refuse with `22023`, so a wrong type is not a `22P02` cast error. `external_id` is immutable once set (`enforce_external_id_immutability`) — a different value on an `id` object raises from the trigger; that is acceptable pass-through.

### Anti-Patterns to Avoid

- **Copying the four validation rules into `create_invitations`.** J4 rules them shared; the copy is only the fallback.
- **A SECURITY DEFINER shared function.** D-12 "If wrong": the caller's policies and the cap of ten stop deciding.
- **Naming `confirmed` in an `INSERT` run by `authenticated`.** A column-privilege error (`42501`), not a confirmation.
- **Trusting an UPDATE's success.** RLS hides rows silently; rule 2 rewrites `confirmed` silently. Check `FOUND` and read `confirmed` back.
- **Applying "a new nomination must be the only object of its election" to invitations.** It is `set_entity_nominations`' whole-set editing rule [VERIFIED: 503-entity-rpcs.sql:549, 810-826], not a row validation; an organization is legitimately nominated in several constituencies of one election.
- **`SET CONSTRAINTS … IMMEDIATE` without the matching `DEFERRED`.** The skill: "The second statement is not optional" [VERIFIED: .claude/skills/database/SKILL.md § 7].
- **A `DROP FUNCTION` shim or a two-argument overload.** "Nothing is deployed" (CONTEXT standing rules).

## Common Pitfalls

### Pitfall 1: The stack is shared, and stopped
**What goes wrong:** a reset or E2E run here wipes the `-infra` worktree's data, or the reverse mid-run.
**Why it happens:** same project id and ports [MEMORY: project_infra_and_gsd_share_local_supabase_stack.md].
**How to avoid:** every gate set that resets, and every E2E run, starts only after the operator confirms the other session idle; the drivers' refusals (port held, `started` marker younger than ten minutes) are kept. At research time no Supabase container was running.
**Warning signs:** `db:status` finds nothing; a run red with missing-content assertions.

### Pitfall 2: A project editor's `confirmed: true` silently lost on an update
**What goes wrong:** the call reports `updated: 1`; the nomination is unconfirmed.
**Why:** rule 2 forces `NEW.confirmed := false` for any edit by an `authenticated` caller without `nomination.confirm`, raising only on false→true [VERIFIED: 011-validation-functions.sql:513-519].
**How to avoid:** `RETURNING confirmed` and refuse a mismatch; pgTAP case with the project editor fixture user.

### Pitfall 3: Cross-project rows through the admin path
**What goes wrong:** a project editor of A, or the service role, names a parent (or an invited `target_id`) of project B; a bare parent nomination with `project_id = A` and B's `organization_id` is written.
**Why:** `admin_insert_nominations` asks only `user_can ('project', project_id, 'project.edit_nominations')` [VERIFIED: 302-rls.sql:1107-1115]; `validate_nomination` checks the election's and constituency's project, and states that "The entity's own project is checked by the entity write policies in 302-rls.sql, not here" [VERIFIED: 011-validation-functions.sql `validate_nomination`]. The project-agreement guard exists only on `entity_insert_parent_nominations` [VERIFIED: 302-rls.sql:1160-1220].
**How to avoid:** in pass 1, refuse with `22023` a parent `entity_id` whose `private.entity_project_id` is not `p_project_id`, and an item with nominations whose entity is not of `p_project_id`. Assert both in file 46. (The same gap exists on `set_entity_nominations` for a project admin, who holds `nomination.edit` on every entity — see Open Question 2.)

### Pitfall 4: File 43 must stay byte-identical and green
**What goes wrong:** a message text drifts (`'s` vs `''s`, the `%` of the parent type), or the order of checks moves for an object 43 tests.
**How to avoid:** the validator formats `<prefix>: <label> <tail>` with `p_label` = `format('p_nominations[%s]', v_index)`; run file 43 alone (`supabase test db supabase/tests/database/00-helpers.test.sql supabase/tests/database/43-set-entity-nominations.test.sql`) before and after; `git diff --exit-code` on the file in the plan's verify.

### Pitfall 5: The `entity_type` of the parent check message
`set_entity_nominations` raises `names a parent whose entity_type is not %` with `v_parent_type` (`organization` for a candidate, `alliance` for an organization) [VERIFIED: 503-entity-rpcs.sql:645-648, 767]. The validator must take the parent type as an argument, not derive it from the label.

### Pitfall 6: New private functions are executable by `anon` by default
PostgreSQL gives `EXECUTE` to `PUBLIC` on a new function; a function in `private` created after `301`'s `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA private TO anon, authenticated, service_role;` ("The statement reaches only the functions defined before it") [VERIFIED: 301-auth-functions.sql:808-812] is then reachable by `anon` through that default, and has no explicit grant at all [VERIFIED: PG 17.6 probe — `anon_exec t` before the REVOKE, `f` after]. Add `REVOKE … FROM PUBLIC, anon; GRANT … TO authenticated, service_role;` for each, as `private.localized_has_text` does [VERIFIED: 506-invitation-rpcs.sql:40-48].

### Pitfall 7: `yarn db:lint:sql` lints only `public`
`"lint:sql": "supabase db lint --schema public --fail-on warning"` [VERIFIED: apps/supabase/package.json]. `create_invitations` and `set_entity_nominations` are checked by plpgsql_check at `warning` level (an unused variable left behind by the extraction fails the gate); the new `private` functions are not linted at all, so review them by reading.

### Pitfall 8: The journey candidate is confirmed for the first time
Today `whileHiddenFromVoters` leaves it unconfirmed for steps 4–22. After D-14 it is confirmed from step 3: the profile's name fields render locked (`nameState` answers `locked-confirmed`) [VERIFIED: apps/frontend/src/lib/contestant/utils/nameRule.ts:27-28]; `enforce_entity_immutability` refuses only a *changed* protected column (`IF (v_old_row ->> v_col) IS DISTINCT FROM (v_new_row ->> v_col) AND NOT …`) [VERIFIED: 011-validation-functions.sql `enforce_entity_immutability`], and steps 13–14 change answers and the portrait, not names [VERIFIED: contestant-journey.spec.ts:563-657]. Step 12's `expectCard` takes `confirmed: false`, already exercised by `perm/contestant-nominations.spec.ts` [VERIFIED: grep]. Still *inferred* until the journey runs: nothing else on the contestant pages keys on the entity's confirmation.

### Pitfall 9: Counts and comments that name the journey's nomination
`base.test.ts` `expect(fixedOf('nominations')).toHaveLength(61 + 3);` and its title [VERIFIED: base.test.ts:168-169]; `voter-journey.spec.ts` comments "Party AA has 7 nominal members; 2 are unconfirmed and so hidden … (test-e2e-base-ca-aa-hidden and test-e2e-base-ca-aa-unregistered)" and "CO-Reg-N has 17 candidate nominations; 4 of those candidates are unconfirmed" [VERIFIED: voter-journey.spec.ts:941, 1016].
