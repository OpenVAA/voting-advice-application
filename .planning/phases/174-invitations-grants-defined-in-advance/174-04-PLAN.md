## Rulings and deviations carried by this plan

1. **OQ-5.** `claim_invitations` returns a third key, `password_set`, read through a private definer helper
   that Phase 178 can reuse. It is the caller's own fact and adds no name to either census.
2. **Not as written: D-15's "cap per caller" and D-18's "coarse per-caller limit for unknown codes".** No
   function here takes or derives a caller identity, because none is observable that the caller cannot
   influence (RQ-6), and a project-wide cap would let any visitor deny the answer to everyone. Built: one
   mail per address per 60 seconds; one rebinding per code per 60 seconds; ten look-ups per used code per
   fifteen minutes. Unknown codes are defended by their 60 bits.
3. **`invitation_link_request` returns the address to mail, or null**, where the research's prototype
   returned a boolean. D-17 requires that a used code with no address asks for a link to its claimant's
   address; only the database knows that address, and it is handed to the service role and nobody else.
4. **A refused request changes no row**: the rebinding interval and the address slot are checked before the
   pending address is written.
5. **Deleting an invitation deletes its throttle keys.** Without it an admin who revokes and re-seeds, and
   an E2E run that follows another within a minute, would be answered with a stale wait.
6. **`claim_invitations` is revoked from `service_role` as well as from `anon`**: it answers for
   `auth.uid()`, which the service role does not have.
7. **Task 2 holds the census edit in the same commit as `claim_invitations`**, because a commit with the
   function and without the edit leaves pgTAP red.
8. **The slot is given back when no mail went out.** `invitation_link_release` exists so that a failure
   after the slot was taken — user creation, token issue, SMTP — does not hold the address for 60 seconds.
   The function of 174-05 calls it on every such path.
9. **A completion witness.** Two service-only functions over one `private` table let a test wait for the end
   of one request's background work before it asserts that no mail was sent. A witness is opened by the
   service role only; the function completes it by `UPDATE` and never inserts, so an anonymous caller cannot
   fill the table.
10. **The seeder's authority is not asked again at the claim** (residual R-e of 174-01), and pgTAP pins both
    halves: a demoted seeder's promise is honoured; a deleted promise grants nothing.
11. **The schema lands in two tasks**, the service-only helpers first and the claim with its census edit
    second, each with its own regenerate, apply and verify; the pgTAP sections are two tasks after them.
12. **This plan closes on ten gate rows and no E2E run.** It adds SQL nothing calls yet; its boundary proof is
   the full run that closes 174-06.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a signed-in user → `claim_invitations` | any authenticated caller, with any token, asks for grants |
| the Edge Function (service role) → the three helpers | values typed by an anonymous visitor arrive as arguments |
| the definer functions → `auth.users` and `public.grants` | the only code that reads the first and writes the second on a user's behalf |
