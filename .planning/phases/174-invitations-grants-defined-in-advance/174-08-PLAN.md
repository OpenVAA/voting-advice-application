<objective>
Stage 4 (wiring and close), part 1 of 3: put the claim and the session refresh into every entry point that
can sign an invitee in, and give the server contract its place in the adapter pattern (D-03, D-14, D-17,
D-20; obligation O-1).

Purpose: a grant written after the token was issued is neither listed nor admitted by row-level security
until the token is reissued. Without the order "session, claim, refresh, gate", a first-time invitee is
signed out with 403 straight after a successful claim.

Output: four writer methods, one shared admission sequence used by both login actions and by a new
code-login helper, the callback's `magiclink` arm, their unit tests, one gated integration measurement, and
the closing runs. No screen, no route, no message key.
</objective>

## Where each piece of the server contract lives

| Operation | Writer method (interface `DataWriter`) | Adapter | Called from, in this phase |
|---|---|---|---|
| `check code` | `checkInvitationCode({ code })` | `functions.invoke('account-access', …)` with `operation: 'check-code'` | its unit and integration tests; Phase 178's screen C |
| `request link` | `requestSignInLink({ email?, code?, locale })` | the same function, `operation: 'request-link'` | its tests; Phase 178's screens B, D1 and E |
| `code sign-in` | `signInWithInvitationCode({ code, password })` | the same function, `operation: 'code-sign-in'`, then `auth.setSession` on this writer's client | `invitationCodeLogin` in `$lib/auth`, which Phase 178's screen D2 calls from a form action |
| `claim_invitations` | `claimInvitations()` | `rpc('claim_invitations', { p_project_id })` | the auth callback and both login actions, through `admitSession` |

the invitation leg of the set-password page stays exempt from the registration-code guard.

## Rulings and deviations carried by this plan

1. **O-1 (hard).** Session, claim, refresh, gate — in the callback, in both login actions and in the
   code-login helper.
2. **OQ-5.** The callback lands by `passwordSet` from the claim's result, not by the link type.
3. **Claude's discretion (D-14).** One module, `sessionAdmission.ts`, holds the sequence; the refresh is
   skipped when nothing was claimed, because the token was issued a moment earlier by the same request and
   already projects every existing grant.
4. **The Admin App's login action is wired** (CONTEXT R6): a claimed `(project, admin)` promise opens it.
   A claimed `(project, editor)` promise opens neither app, because `ADMIN_GRANTS` lists admin shapes only;
   that is recorded and not changed here (ruling 18 of the phase).
5. **`invitationCodeLogin` has no caller in the application until Phase 178**; it is exercised by its unit
   test and by the integration measurement of A5. It is built here so that the claim and the refresh are not
   left for the screen's author to remember.
6. **A claim that fails**: a password login proceeds on the token's own grants; the callback's `magiclink`
   arm drops the session and reports the auth error, because where that arm lands depends on the claim's
   answer.
7. **The callback's `invite` arm stays in this plan**: the E2E helper still issues such links until 174-09
   replaces it and removes the arm.
8. **Twenty paths**: each of the four pure or structural modules has its test beside it.
9. **This plan's closing run is also 174-07's boundary proof.** 174-07 closed on gate rows; Task 4 says
   which failures of this run point back to it.
