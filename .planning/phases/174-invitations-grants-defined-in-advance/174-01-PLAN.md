## Rulings and deviations for operator review

This is the consolidated list for the whole phase, ordered by how much each item matters. Each later plan
repeats the items it carries.

**1. OQ-1 — the auth configuration changes: `[auth] enable_signup = false` and `[auth.email]
enable_confirmations = true` (174-03).** Measured by the research on a private GoTrue `v2.197.0` configured
as the local stack is: a public `POST /signup` with any address and a password of the caller's choosing
returned a session and a user whose `email_confirmed_at` was set, with no mail sent. That caller holds
exactly what `claim_invitations` trusts, so under the committed configuration a stranger claims another
person's invitation by typing their address. Confirmations alone do not close it: an attacker who signs up
first with the victim's address leaves an unconfirmed account carrying the attacker's password, the victim's
later click on the mailed link confirms that same account, and the attacker's password then signs in.
Disabling public sign-up closes both; confirmations stay on as the second lock. Nothing in the product calls
`auth.signUp` or `auth.signInWithOtp`. The plan carries a stack restart, a live probe before and after, a
repository gate, an E2E assertion, a fail-closed check in the new Edge Function, the full default suite and
both bank-auth projects. **A hosted project's dashboard must have "Allow new users to sign up" off and
"Confirm email" on; the repository cannot enforce that, and `claim_invitations` has no in-database guard on
it.** The function refuses to issue links when the served `/auth/v1/settings` says otherwise, which stops
the legitimate flow and makes the misconfiguration loud; it does not stop an attacker who signs up directly
on such a project and calls the claim (residual R-f below). No plan makes `claim_invitations` executable
before 174-03 closes.

**2. J3 and OQ-9 — the full authority map, and two ratified security lists edited (174-02).** The map of
D-09 is implemented whole, inline in one policy per command: entity editor promises ask
`project.edit_entities`, project editor promises ask `project.manage_editors`, project admin promises ask
`account.manage_admins`; account, global and empty-permission shapes are refused for every caller by CHECK
constraints. Because two formerly unenforced permissions are now read by policies, `SAME_PERMISSION_ALLOW`
in `apps/supabase/scripts/lint-schema.mjs` gains two entries and `m17_unenforced_ratified` in pgTAP
`25-matrix-conformance` loses two members, each with its written reason. Both edits are made only if the
linter and the test report exactly those entries on the applied schema; any other finding stops the task.

**3. J1 — the shape (174-02).** One invitation row promises one grant; the child table is not built.

**4. J2 — the duplicate rule (174-02).** A target is `(scope, target_type, target_id)`; an email is unique
per target within the project, with the role outside the key; a code hash is unique per project. The
replacement wording for INV-02 and roadmap criterion 2 is given to the orchestrator in the planner's reply;
no plan edits either file.

**5. Two CONTEXT.md sentences that are not planned as written — D-15's "a cap per caller" and D-18's "a
coarse per-caller limit for unknown codes" (174-04, 174-05).** No caller identity is observable behind the
Edge Function without trusting a header the caller can influence, which D-18's own "If wrong" forbids. That
is measured on the local stack only (174-05); the research could not measure the hosted topology (RQ-6). A
project-wide cap in their place would be a switch any anonymous visitor can use to deny the answer to
everyone. What is built: one link mail per address per 60 seconds, released again when no mail was handed to
SMTP; one rebinding per code per 60 seconds; ten look-ups per used code per fifteen minutes; 60-bit codes.
What is not built is accepted, each by its mechanism (residuals R-a to R-d below), and 174-10 files the todo
for a gateway-level limit.

**Residuals this phase accepts, each by its mechanism.**

- **R-a — unlimited anonymous `check-code` calls.** Each is one indexed database look-up; nothing in this
  phase bounds their rate. The exposure is load on the database, not disclosure: a guess meets 60 bits.
- **R-b — one mail per minute to any eligible address, indefinitely.** Anyone who knows an address that has
  an open invitation, or that belongs to a user holding a grant in the project, can make the deployment mail
  that address a sign-in link once every 60 seconds for as long as they like.
- **R-c — a new link invalidates the unopened one before it.** The research measured that issuing a second
  token of the same kind replaces the first; 174-05 measures it for the function's own links. If it holds, a
  third party who knows the address can, once a minute, make the link the user has not yet clicked stop
  working. Recorded as a fact for Phase 178's "email sent" screen.
- **R-d — the hosted caller topology is unmeasured (RQ-6).** "No caller identity observable" is a statement
  about the local stack; on a hosted deployment a gateway may offer one, and none of this phase's limits
  uses it.
- **R-e — a claim honours a promise whose seeder has since lost authority.** The promise was an authorised
  act when it was written, as a grant is; the authority map is asked when the row is written and not again.
  An admin revokes a promise by deleting the unclaimed invitation. Pinned in pgTAP (174-04): the seeder is
  demoted after seeding and the claim still writes exactly the promised grant; the invitation is deleted and
  the claim writes nothing. Re-validation at claim time stays deferred, as `174-CONTEXT.md` has it.
- **R-f — no in-database guard on the auth service's sign-up setting.** `claim_invitations` trusts a
  confirmed address and cannot ask how it was confirmed. On a hosted project whose dashboard still allows
  public sign-up the claim is forgeable, regardless of the function's fail-closed check.
- **R-g — the auth service's own `POST /otp`** still tells a registered address from an unregistered one
  (item 14).

**6. J4 — scope moved here from Phase 178 (174-04, 174-05).** The server-side 60-second resend interval and
the sign-in mail in seven locales. The six non-English texts are constructed, and a native-speaker review is
filed as a todo.

**7. OQ-5 — `claim_invitations` also returns `password_set` (174-04, 174-08).** Every mailed link is of type
`magiclink`, so the callback tells a first-time user from a returning one by the account's own password
state. Correction to CONTEXT fact 19: users created by `identity-callback` carry a generated password hash,
so that column is not a "password set" signal for them; filed as an input to Phases 178 and 179.

**8. OQ-4 — the mailed link's origin (174-03, 174-05, 174-06).** The origin is the function's `SITE_URL`
and nothing from the request. Before it issues a link the function asks the auth service whether
`<SITE_URL>/<locale>/api/auth/callback` is admitted by its redirect allowlist and refuses to issue links when
it is not; a positive answer is believed for at most ten minutes. The two env templates change `SITE_URL` to `http://localhost:5173`. The E2E helper replaces only
scheme, host and port of the received link with the run's own origin (`http://localhost:<FRONTEND_PORT>`),
which is the normalisation the existing mail helper already performs; path, locale segment, parameter names,
token and type stay byte-identical and are asserted as received.

**9. OQ-10 — the SMTP port, not planned as ruled, and an operator checkpoint (174-03).** The ruling asks
for the correction in the tracked function environment. The tracked templates already say `1025`; the stale
`2500` is in the functions' untracked environment file, which **no executor reads, writes or processes with
a script, anywhere in the phase**. 174-03 asserts the tracked values, reads three named variables
(`SITE_URL`, `SMTP_HOST`, `SMTP_PORT`) from the running edge container, one `docker exec … printenv <NAME>`
call each, and compares them with the tracked template. If one differs the plan stops at a
`checkpoint:human-action` task that names the three lines the operator sets and the restart that follows;
after the operator confirms, the next task restarts, reads the three variables again and proves delivery with
one mail sent by `send-email`. When the three are already equal the checkpoint is passed without a pause.
174-03 is `autonomous: false` for this reason.

**10. OQ-7 — `[edge_runtime] policy = "per_worker"` (174-03, measured in 174-05).** Set in the same restart
as the auth keys; its effect on the three existing functions is measured by the bank-auth runs and the mail
probe, and that a background send completes after the response is measured when the new function exists. If
it does not complete, 174-05 stops with a checkpoint.

**11. OQ-8 — the function takes its project from the request** and validates it as a uuid; it reads no
default project from its environment.

**12. OQ-2 — a deviation from D-06's wording.** "32 symbols after removing five" is arithmetically
impossible (31 remain). Codes use Crockford's base-32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, with `O`
read as `0` and `I`, `L` read as `1` on input: exactly 60 bits.

**13. OQ-3 — `toCallbackUrl` is not deleted** (the journey's password-reset step needs it until Phase 178
moves the recovery mail), so D-24's zero-hit search for it is dropped and handed to Phase 178.

**14. OQ-6 — GoTrue's own `POST /otp` still tells a registered address from an unregistered one.** Accepted
in this phase and filed as a todo for Phase 178, where a send-email hook can switch GoTrue's own mail off.

**15. Additions to the researched SQL contract (174-04).** `invitation_link_request` returns the address to
mail (or null) in place of a boolean, so that a used code with no address can ask for a link to its
claimant's address, which D-17 requires and the research did not prototype; a code row is rebound at most
once per 60 seconds (D-16's planner constraint); `invitation_link_release` gives the address's slot back
when no mail was handed to SMTP, so a failed send does not lock the real user out for a minute; deleting an
invitation clears its throttle keys, so a re-seeded invitation is not answered with a stale wait; and a
completion witness (`invitation_link_witness_open`, `invitation_link_witness`) lets the service role — in
practice a test — learn that the background work of one link request has finished and whether a mail was
handed over. A witness can be opened by the service role only; an anonymous caller who names one that was
never opened causes no write.

**16. The callback's `invite` arm is removed and the `invite` type refused (174-09).** Its two sources leave

**17. `CLAUDE.md` is not edited**, although `174-CONTEXT.md` says its sentences on the three Edge Functions
