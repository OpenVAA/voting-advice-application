## What "the link as received" means here

The function mails `<SITE_URL>/<locale>/api/auth/callback?token_hash=…&type=magiclink`. `SITE_URL` is the
function's configuration (`http://localhost:5173` on a local stack); the wrapper serves this checkout on
`http://localhost:<FRONTEND_PORT>`, port 5273 by default. A test therefore replaces **scheme, host and
port** of the received link with the run's `baseURL`, and nothing else. This is the normalisation the existing
helper `toCallbackUrl` already performs on its result (`http://localhost:<FRONTEND_PORT>`). It is not building
the callback, because everything that makes the link a sign-in link is taken from the mail and asserted
first: the path is exactly `/<locale>/api/auth/callback` with the locale that was requested; the query holds
exactly `token_hash` and `type`; `type` is `magiclink`; the token is non-empty. `toCallbackUrl`, by contrast,
reads a token out of the auth service's own verify link and writes the path, the parameter names and a
default type itself.

## Rulings and deviations carried by this plan

1. **OQ-4, second half.** As stated above; the helper refuses a link that does not have the callback's shape
   and never repairs one.
2. **Ruling 22 of the phase.** Two dedicated rows in `e2e/base`: one candidate and one organization, each
   with a name, `confirmed: false`, and no nomination, so that seeding an invitation for them can be seen to
   confirm them and neither can ever be public.
3. **D-22 (Claude's discretion).** The seeding helper calls the function through the service role, as every
   other fixture write does; the authority map is asserted in pgTAP, not here.
4. **The throttle and determinism.** Every address this spec mails is fresh for the run, so no test depends
   on the time since another run; the one case that needs a taken slot takes it itself.
5. **The spec is API-level.** It drives no page. The browser path through the callback is 174-09's.
6. **Negatives wait on the witness.** The function's background jobs do not finish in request order, so
   "a later mail arrived" proves nothing about an earlier request. The admin client opens a completion
   witness (174-04), the request carries it, and the negative is asserted only after it reads `not-sent`.
7. **Five tasks**: the utilities and the admin client's edits are two tasks.
