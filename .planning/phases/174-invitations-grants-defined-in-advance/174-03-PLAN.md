## The decision this plan carries, for operator review

**Ruling OQ-1: both `[auth] enable_signup = false` and `[auth.email] enable_confirmations = true`.**

What was measured, on a private GoTrue `v2.197.0` mirrored from the local container, with the anon key
(`174-RESEARCH.md` § RQ-1):

| Request | As committed | Confirmations on only | Sign-up off only | Both |
|---|---|---|---|---|
| `POST /signup`, unknown address and a password | **200, a session, address confirmed, no mail** | 200, unconfirmed, one mail | 422 `signup_disabled` | 422 `signup_disabled` |
| `POST /otp` with `create_user: true`, unknown address | user created, **confirmed at once** | user created, unconfirmed | 422 `signup_disabled` | 422 `signup_disabled` |
| signed-in change of one's own address | pending until the new address clicks | pending | pending | pending |
| the attacker signs up first with the victim's address, the victim later opens a mailed link, the attacker then signs in with the password | **signed in** | **signed in** | not possible | not possible |

So: confirmations alone leave the pre-registration attack open; sign-up off closes both; confirmations stay
on as the second lock, because if sign-up were ever re-enabled, auto-confirmation is what turns that mistake
into an immediate forgery. The measured fallout is none: no product or test code calls `auth.signUp` or
`auth.signInWithOtp`, and every service-side `createUser` in the tree passes `email_confirm: true`.

**What the repository cannot do, and what the database does not do.** A hosted project's two switches live in
its dashboard. `claim_invitations` reads `auth.users.email_confirmed_at` and has no way to ask the auth
service how that flag came to be set: **on a hosted project whose dashboard still allows public sign-up the
claim is forgeable**, whatever the Edge Function of 174-05 does. That function refuses to issue links when
the served settings disagree, which stops the legitimate flow on such a deployment and makes the
misconfiguration loud; it does not stop an attacker who signs up directly and calls the claim. The docs say
both.
