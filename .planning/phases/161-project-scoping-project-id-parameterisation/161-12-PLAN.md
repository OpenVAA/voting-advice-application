## Decision record for this plan

### DR-34 — Two different instruments, because the two blind spots are different kinds of thing

The schema hop and the invocation look alike — both are call shapes the receiver-anchored matcher misses
— but they need opposite treatments, and collapsing them into one rule would get one of them wrong.

**A schema hop is a PROHIBITION.** `this.supabase.schema('public').from('elections')` reaches a
project-scoped table. There is no legitimate use of it in a guarded adapter source, because the
sanctioned route to a table is the scoped helper. It joins the three shapes check 6 already forbids, for
the reason check 6's own docblock gives: a prohibition is decidable by inspection and has no next case,
whereas widening the receiver invites the fourth spelling. Measured before choosing: a repository-wide
grep for the schema call returns nothing, so the prohibition costs zero live sites.

The prohibition is also COMPLETE for this client rather than merely convenient. Of the client's own
members, only the schema call returns an object carrying `from` and `rpc`; `storage` and `functions` are
property reads and are handled separately; `auth` reaches no table. So forbidding the one call that can
put a table behind a mid-chain call closes the shape rather than sampling it.

**An invocation is a DISPOSITION.** An Edge Function invocation is not a table access and cannot be
forbidden — three of them are load-bearing. A static source guard cannot see inside a function body any
more than it can see inside an rpc body, which is exactly the situation `PROJECT_SCOPED_RPCS` already
answers: every function the repository invokes carries a written disposition, and the check enforces the
disposition's own promise at the call site. The new map is that mechanism, one surface over.

### DR-35 — The invocation matcher is anchored on the FUNCTION NAME, not on the receiver

Every other check in this guard anchors on `this.supabase`. The invocation check deliberately does not:
it matches `.functions.invoke(` on any receiver and reads the function-name literal.

Two reasons, both measured. The disposition lives with the function, not with the caller — the same
function invoked from two files needs the same answer. And the third live invocation in this repository
is `locals.supabase.functions.invoke('identity-callback', …)` in a route file, whose receiver is not
`this.supabase` at all. A receiver-anchored invocation check would be blind to it, which is the same
mistake in a new place. Anchoring on the name means the check works unchanged over whatever corpus it is
handed, which is what makes 161-13's widened enumeration a corpus change rather than a second matcher.

### DR-36 — The dispositions, and why each is true

| function | disposition | why it is true |
|---|---|---|
| `invite-candidate` | requires a project term | Its handler destructures `projectId` from the body, rejects the request when it is missing, and writes `project_id: projectId` on the candidate row it inserts. |
| `identity-callback` | scoped by deployment configuration | It resolves its project with `requireEnv('PUBLIC_PROJECT_ID', …)` and treats a body `project_id` as a claim it refuses unless it names that same project. The payload carries no project term BY DESIGN, so requiring one at the call site would be a false demand. |
| `send-email` | requires a project term | True as of 161-11, and not before it: that plan makes the function require the term, refuse a mismatch, and forward it to a `resolve_email_variables` that now requires `p_project_id`. This plan depends on 161-11 for exactly this reason — writing the disposition first would have made the map a claim rather than a statement. |

### DR-37 — Both new rules COUNT their sites, not just report them

`checkEscapeHatches` returns its find count and `checkSource` adds it to the total, and the reason is in
the fixture's own comment: the escape-hatch shapes were UNCOUNTED before check 6, so the non-vacuity
floor could not fire for a file that contained nothing else. The same applies here. Both new checks
return a count and both counts feed the total, so a corpus consisting only of schema hops and
invocations is a corpus the floor still sees.
