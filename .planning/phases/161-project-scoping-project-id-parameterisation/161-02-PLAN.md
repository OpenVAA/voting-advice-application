## Decision record for this plan

### DR-6 — `get_nominations` gains a required `p_project_id` via an **additive migration**

Measured this session:

- `apps/supabase/supabase/schema/503-entity-rpcs.sql` declares
  `get_nominations(p_election_id uuid DEFAULT NULL, p_constituency_id uuid DEFAULT NULL,
  p_include_unconfirmed boolean DEFAULT false)`; its `WHERE` joins only on entity ids and carries no
  project term, so with both id parameters NULL it returns every project's nominations. The
  `NULL, NULL` case is the adapter's default call shape.
- `nominations.project_id` already exists as `NOT NULL REFERENCES public.projects(id) ON DELETE
  CASCADE`, so the fix is a predicate, not a schema addition.
- **The repo's established mechanism for changing an existing function is an additive migration.**
  `apps/supabase/supabase/migrations/00002_anon_select_terms_of_use_and_get_nominations_rls_guard.sql`
  does exactly this for this exact function: a header block stating the background and an
  "Applies to schema files:" list, `BEGIN;`, the redefinition, and a re-issued
  `GRANT EXECUTE ON FUNCTION public.get_nominations(uuid, uuid, boolean) TO anon, authenticated;`.
  `161-PATTERNS.md` records "No Analog Found" for this file; that is superseded — `00002` is the
  analog and it is exact.
- **Therefore 161 adds `00004_get_nominations_project_scope.sql` and does not rewrite
  `00001_initial_schema.sql`.** This avoids pre-empting Phase 156's unresolved
  rewrite-in-place-versus-add-a-migration decision, and it keeps the change picked up by both
  `supabase migration up` and `yarn db:reset`.
- **Arity changes, so `CREATE OR REPLACE` is not enough.** Three parameters become four, which creates
  an overload rather than replacing the function. The migration must `DROP FUNCTION` the
  three-argument signature first. `p_project_id` must be the **first** parameter because a required
  parameter cannot follow a defaulted one in PostgreSQL. PostgREST calls RPCs by named argument, so
  the reordering is invisible to the client.

**Reversibility: one-way.** The change drops a granted, `anon`-executable function signature. Any
caller not passing `p_project_id` breaks; a local database that has already applied `00004` cannot be
returned to the old signature without another migration. Guarded by a `checkpoint:decision`.

### DR-8 — The `[BLOCKING]` schema application, and why it does not weaken criterion 3

This phase's schema-gate obligation is discharged by a **one-time** `yarn db:reset` during execution,
after the migration file is written and before any verification that depends on the new signature.
`supabase db push` is not this project's idiom (it targets cloud); `yarn db:reset` (`yarn db:start &&
supabase db reset`) is what applies migrations plus `seed.sql` to the live local database.

The distinction that must not be blurred: criterion 3 says `yarn test:e2e` must no longer **require**
`yarn db:reset` **as a precondition of a run**. A one-time schema application during development is
not a per-run precondition. The twice-in-a-row proof in plan `161-07` is taken *after* this reset has
long since happened, and its Run B carries `--no-db-reset` precisely to prove the per-run requirement
is gone. Nothing in this plan may add a reset to the E2E run path.
