## Phase decision record (canonical — every later plan in this phase cites this section)

These are the planner's decisions in the areas `161-CONTEXT.md` left to Claude's Discretion or left
open. They are binding for the whole phase.

### DR-1 — The canonical variable name is `PUBLIC_PROJECT_ID` (one physical name, two runtimes)

Resolves `161-CONTEXT.md` O-2, which records the name as contested three ways
(`PROJECT_ID` / `PUBLIC_PROJECT_ID` / `DEFAULT_PROJECT_ID`).

- **The frontend forces the `PUBLIC_` prefix.** SvelteKit's `kit.env.publicPrefix` defaults to
  `PUBLIC_` and `apps/frontend/svelte.config.js` declares no `kit.env` block, so an unprefixed name is
  classified private and can only be reached through `$env/dynamic/private` on the server. The
  Supabase adapter constructs a **browser** client (`supabaseAdapter.ts` `createBrowserClient` branch)
  and is re-`init()`ed from universal `+layout.ts` load functions that run on both sides. Setting
  `publicPrefix` to the empty string would publish every private root-`.env` key (identity-provider
  client secret, signing JWKS, LLM keys) and is rejected.
- **Deno imposes no prefix rule.** `Deno.env.get('<any name>')` is legal, so the Edge Function can
  read the same physical name. One name means one grep, one `.env.example` line, one thing to
  configure — which is literally what D-D3 assigns to this phase ("161 owns the rename/converge half").
- **`PUBLIC_` is semantically honest here.** The project id appears in every client query and in every
  storage path; it is not a secret.

**Recorded deviation from roadmap criterion 1.** Criterion 1 names "a `PROJECT_ID` environment
variable". As measured that literal name is **unsatisfiable for the frontend**. Criterion 1 is
therefore delivered in the form that is actually deliverable, restated:

> A single canonical project-id environment variable named **`PUBLIC_PROJECT_ID`** exists, defaults —
> as its documented value in the repo-root `.env.example` — to the default project id
> `00000000-0000-0000-0000-000000000001`, is read by both the SvelteKit frontend and the Deno
> `identity-callback` function, and replaces the hardcoded constant at
> `apps/supabase/supabase/functions/identity-callback/index.ts:31`, which stops supplying a silent
> fallback.

A verifier must read a `PUBLIC_`-prefixed name as satisfying criterion 1, not as a missed criterion.

**Reversibility: one-way.** The name is a published contract: it lands in `.env.example`, in operators'
untracked `.env` files, in Supabase Edge-Function secrets, and Phase 162 will be planned against it.
Guarded by a `checkpoint:decision` below.

### DR-2 — `E2E_PROJECT_ID` is a separate, test-harness-only variable

Value: **`00000000-0000-0000-0000-0000000000e2`** — a fixed, well-known uuid, deliberately distinct
from the default/seed project id `00000000-0000-0000-0000-000000000001` (reusing that id would leave
E2E sharing the default project and would deliver nothing). It is never read by application code; the
E2E run delivers it to the application by setting `PUBLIC_PROJECT_ID` to it on the dev-server spawn.

**It is a committed constant, not a required environment variable.** The `E2E_PROJECT_ID` line in
`.env.example` is **commented out**, and the harness falls back to the committed constant. Reason,
measured: `packages/dev-seed/src/cli/seed.ts` auto-loads the repo-root `.env` via `process.loadEnvFile`
and `tests/playwright.config.ts` calls `dotenv.config()`, so a **live** line in the root `.env` would
silently re-point `yarn db:seed:default` — and therefore `yarn db:reset-with-data` — at the E2E
project, leaving a plain local dev session showing an empty app. See plan `161-05` DR-15 for the full
resolution table.

### DR-3 — Teardown posture: create-if-absent, **never delete the project row**

D-J2 requires this choice be stated. It is stated here: the E2E project row and its `app_settings` row
are created idempotently by Playwright `globalSetup` and are **left in place** between runs. Only the
run's **content** is torn down, by the existing prefix-scoped `runTeardown` / `teardown:` projects.
`DELETE FROM public.projects` never runs in this phase.

### DR-4 — The `app_settings` FK cascade gap is **mooted by DR-3**, and Phase 156 has since claimed the fix

Verified in the tree: `apps/supabase/supabase/schema/106-app-settings.sql:8` is the only one of 13
`project_id` FKs to `public.projects` without `ON DELETE CASCADE`, and the same defect exists a second
time at `apps/supabase/supabase/migrations/00001_initial_schema.sql:916`.

**Status of Phase 156 changed during this planning run and is recorded honestly.** At the start of the
run 156's directory held no PLAN.md and none of its criteria named the cascade — which is what the
research measured. A concurrent planning run has since produced `156-06-PLAN.md`, whose task 3 is
titled "Give app_settings the cascade every other project foreign key has" and whose must-haves
include "Deleting a project cascades to `public.app_settings` instead of raising a foreign-key
violation". So the fix now has an owner, adopted deliberately as an item 156's criteria do not name.

**161's disposition is unchanged by that, and deliberately does not depend on it.** Under DR-3 the
project row is never deleted, so the gap is never exercised whether or not 156 lands first. 161 makes
no schema change for it and takes no blocking dependency on 156's plan. Plan `161-05` task 3 files a
`.planning/todos/pending/` entry per D-N2 **only if** 156's cascade has not landed by execution time —
the task carries the check and both branches, so the register neither loses the item nor duplicates a
fix that already shipped.

### DR-5 — The guard mechanism (D-J1)

A committed `scripts/assert-project-scoped-queries.mjs` in the house `assert-*.mjs` idiom, **not** a
custom ESLint rule (`packages/shared-config/` has no plugin module to host one) and **not** an AST
guard. The predicate is **inverted** from D-J1's literal wording into a forbidden call shape:

> No bare `this.supabase.from(<declared project-scoped table>)` and no bare
> `this.supabase.rpc(<declared project-scoped rpc>)` in a guarded adapter source — the declared scoped
> helper is used instead.

The inversion satisfies every binding D-J1 imposes: it is **static**; it fails **at the call site**
naming `file:line`; it reads from an **explicitly declared list of project-scoped tables**; it runs
inside **`yarn lint:check`**; and it covers the **read path by construction** — a brand-new unscoped
`.from('elections')` in `dataProvider/` is a violation whether or not `project_id` already appears in
the file, which is exactly the property D-J1's scope note demands and which the literal predicate
would fail to deliver against a provider that has zero `project_id` references today. The inversion is
also the only tractable form: five `let`-bound builders reassigned across `if` statements, one
union-typed dynamic table argument and two `storage.from('public-assets')` bucket accesses defeat the
literal "chain contains `.eq('project_id', …)`" predicate.

RLS is **not** the guard (D-J1 rejected option b) and is not to be re-proposed. It stays as defence in
depth only.

The guard is **not** added to `test:e2e`, matching Phase 152's explicit decision for its sibling
guard; `lint:check` membership is what criterion 2 requires.

<assumption_delta_decision>
**Trigger:** this phase fires two of the three assumption-delta families at once —
`chosen` (a hardcoded constant becomes a configuration parameter) and `pluralization` (the database
goes from holding one project to holding the deployment's project plus a second, E2E-owned project).

**The noun that is now primary:** *the project this deployment serves*, named once as a resolved value
(`PUBLIC_PROJECT_ID` in configuration; `#projectId` / `get projectId()` on `supabaseAdapterMixin`), and
carried explicitly by every project-scoped query.

**Decision: `promote`.** The general representation — "whichever project this deployment is configured
for" — becomes primary at every layer (config, adapter, RPC parameter, test harness). The old specific
representation — the hardcoded default-project uuid — is **demoted to a documented default value of
that parameter** in `.env.example`, and is deleted from application code
(`apps/supabase/supabase/functions/identity-callback/index.ts:31`,
`apps/frontend/.../supabaseFeedbackWriter.ts`'s `app_settings` derivation, and the two writers' four
further derivations). This is deliberately **not** add-alongside: no code path retains a
"the one project" assumption alongside the parameter.

**Boundary that bounds the promotion:** multi-project *serving* stays out of scope per
`161-CONTEXT.md` — each deployed instance still resolves exactly **one** project id at
`supabaseAdapterMixin.init()`. The promotion is of the *identity model*, not of the serving model.
Phase 162's `user_can(scope, uuid, verb)` work will be planned against the resolved-single-project
shape and against the name recorded in DR-1.

**Companion invariant test (suggested, delivered):** `scripts/assert-project-scoped-queries.mjs` plus
`packages/dev-seed/tests/projectScopingGate.test.ts` together encode the generalized intent — they go
red the instant a future phase reintroduces a bare, unscoped table access, i.e. the singular
assumption.
