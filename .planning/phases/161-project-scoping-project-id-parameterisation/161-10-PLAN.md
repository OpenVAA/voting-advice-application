## Decision record for this plan

### DR-28 — The lookup is EXTRACTED, not patched in place

Patching the chain inside `index.ts` closes the defect and proves nothing: `index.ts` imports
`https://esm.sh/@supabase/supabase-js@2` and reads `Deno.env`, so vitest cannot import it and the
strongest assertion available would be a string search over the file.

`scripts/assert-edge-env-defaults.mjs` check 3 already states the house contract for this exact
situation, in its own violation message: *"Pass the value in as a parameter instead and let the caller
read the environment — the shape `requireEnv(name, value)` exists for exactly this reason."* Three
modules in this directory already follow it (`envConfig.ts`, `claimConfig.ts`, `verifyConfig.ts`), each
with a test beside it. This plan adds a fourth rather than inventing a weaker verification story.

The extracted module takes the client as a parameter and the project id as a parameter. It therefore
has no Deno global and no remote import, which is what makes the behaviour — both filters applied, an
error thrown rather than swallowed — assertable by a running test rather than by a grep.

### DR-29 — `maybeSingle()` is kept, and the error check is what makes it safe

`maybeSingle()` answers `{ data: null, error: null }` for zero rows and populates `error` for two or
more. Before this change both of those, plus every transport failure, arrived at the call site as
`existingCandidate === null` and took the insert branch.

The parameter is not `maybeSingle` versus `single`. `single` would turn the legitimate zero-row case
(a first-time bank-auth registrant, the common path) into an error. The parameter is whether `error`
is read. Once it is, `maybeSingle()` is the correct call: zero rows means "create one", and anything
else — including the two-rows-in-one-project case that would signal a data-integrity defect — becomes
a throw naming a lookup failure instead of a second row.

### DR-30 — Reversion is pinned by a test, not by a comment

Adding `.eq('project_id', projectId)` is one line, and one line is one line away from being lost in a
future edit of a 400-line Edge Function. The pin is a second spec that reads `index.ts` as TEXT and
asserts the existing-candidate path goes through the helper, in the same shape
`packages/dev-seed/tests/projectScopingGate.test.ts` uses to assert over a script it cannot import.
Text assertion is the weaker instrument and it is deliberately the SECOND one here: the behavioural
tests in task 1 are what prove the helper is correct, and this only proves the helper is still the
route.
