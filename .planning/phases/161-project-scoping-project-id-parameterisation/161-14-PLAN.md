<objective>
Close the seventh, and last-named, blind spot in the project-scoped query guard: every matcher family
hard-codes a literal `.` as the access operator between the Supabase receiver and the next member, so
`this.supabase?.from('elections')` — idiomatic, unremarkable TypeScript — is invisible to all of them.

Purpose: `161-VERIFICATION.md` grades criterion 2 PARTIALLY ACHIEVED and blocking on exactly this. The
site is UNCOUNTED rather than merely unchecked, so the per-family non-vacuity floor 161-12 introduced
cannot see the family go silent either — the precise failure mode that floor exists to prevent,
reproduced in a spelling nobody enumerated. D-J1 binds the guard to be static, to fail at the call site
and to read from an explicitly declared list; it does not permit the guard to be blind to one of the two
member-access operators the language has.

Output: six matcher declarations whose access operator is optional, a narrowed binding lookahead that
tells an optional-chained ACCESS apart from an aliased CLIENT, twelve new committed fixture shapes across
all four fixture files, four raised exact self-test counts, four new exact per-shape message counts, and
an independent behavioural derivation of the whole closure in the gate spec.
</objective>

**The CLIENT_BINDING_RE question, answered by measurement rather than assumed.** It is currently
MIS-CLASSIFYING: `const b = this.supabase?.from('candidates')` and `const u = this.supabase?.restUrl`
both match it today and are both reported as `aliases the raw client`, which is a false statement about
each and puts an access into the escape-hatch tally. The naive repair — adding `?` to the trailing
lookahead's character class — fixes that AND silently stops reporting `const db = this.supabase ?? other`,
a genuine alias. Only an alternation that excludes the two-character punctuator specifically holds all
three cases at once. Measured, all three candidates against all five inputs:
