a true statement rather than a laundered one.

Purpose: `161-VERIFICATION.md` records that `supabaseAdminWriter.ts`'s `send-email` invocation "carries

## Decision record for this plan

### DR-31 — `send-email` is FIXED, not allow-listed

`161-VERIFICATION.md`'s `missing:` entry for the guard asks for "a prohibition or disposition
mechanism", and an allow-list entry with a written reason would satisfy that sentence literally. It
would not satisfy criterion 2, which reads "every query that is project-scoped is parameterised by it".

The guard's own `PROJECT_SCOPED_RPCS` docblock already rules on the shape of the alternative:
*"a disposition that overstates a function's scoping is worse than none — it launders the leak past
the next reader"*, and it records that **there is no `UNSCOPED` entry left**. Writing
`send-email: 'UNSCOPED: …'` would reopen a category the phase closed and would hand the next verifier a
written admission that a project-scoped query is unparameterised. The only disposition that is both
honest and green is `requires a project term`, and that disposition is only true once the function
consumes the term. So the function consumes it.

**Reversibility: costly, not one-way.** Reverting means a further migration restoring the three-argument
signature plus its two grants, and a matching revert of the schema mirror and the pgTAP call. Nothing is
destroyed and no data is lost. What makes it costly rather than free is that a signature change to a
granted function is visible to every applied database. What would force a revert: a caller outside this
repository that invokes `send-email` with the current body shape. None exists in this tree — the only
production reference is the adapter method changed here, and the E2E suite's own `sendEmail` helper in
`tests/tests/utils/supabaseAdminClient.ts` does not touch this Edge Function at all, it uses
`auth.admin.inviteUserByEmail`.

### DR-32 — The project term BOUNDS the data; it does not become the authorization check

`send-email` verifies the caller holds `super_admin`, `account_admin` or `project_admin` and does not
compare the role's `scope_id` with anything. That is a genuine gap and it is **not** this plan's. It is
an authorization-model question, and Phase 162's criteria 1 and 2 own the grants matrix and the
`can_access_project` / `can_edit_project` split that answer it.

What this plan does is narrower and squarely inside criterion 2: the DATA the function can reach is
bounded by the project it was asked for, so even the over-permissive admin check cannot render another
project's candidate names into an email. The register below carries the residual as an accepted threat
with that assignment written down, rather than leaving it unstated.

### DR-33 — The disposition keyword accepts both spellings of the project term

The two Edge Function payloads in this repository use different conventions: `invite-candidate` receives
`projectId` (camelCase, alongside `firstName` and `lastName`), and `send-email` receives snake_case keys
(`recipient_user_ids`, `dry_run`). Forcing either to change its convention to satisfy a guard would be
the guard dictating style rather than checking scoping.

The disposition 161-12 writes is therefore `requires a project term`, and its check accepts either
spelling. This plan keeps `send-email` snake_case and leaves `invite-candidate` camelCase, both
unchanged in convention and both carrying the term.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated admin caller → `send-email` | The caller is authenticated and admin-checked, but the recipient list is a caller-supplied array of arbitrary user ids |
| `send-email` → Postgres via the service-role client | The admin client bypasses RLS, and `resolve_email_variables` is `SECURITY DEFINER`, so the function's own predicates are the only scoping there is |
| deployment configuration → `send-email` | `PUBLIC_PROJECT_ID` names the one project this deployment may resolve variables for |
