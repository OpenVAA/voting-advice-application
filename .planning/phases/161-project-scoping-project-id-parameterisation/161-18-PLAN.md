<objective>
Close CR-02, the RECEIVER-DEPTH axis. `CLIENT_BINDING_RE`'s trailing lookahead excludes any directly-following
member access, which silences a genuine alias one link along: `const fns = this.supabase.functions;` then
`fns.invoke(…)`. `INVOKE_RE` then misses the call, because it requires the literal member name `functions`
immediately before `invoke`. Two undispositioned Edge Function invocations inside the adapter directory — the
guard's strictest corpus — currently move nothing.

The matrix could not surface it either: `CLIENT_BINDING_RE`'s call shape has exactly one link, so no
chain-link cell is generated and the bridge assertion is satisfied trivially, because the links themselves
are the hand-written list the matrix exists to eliminate everywhere else.

Purpose: a binding that reaches the client's tables past every receiver anchor must be reported whether it
binds the client or a member of it, and the matrix must be structurally able to see the difference.
Output: a promoted binding rule, three new violating shapes with a live-derived false-positive control, a
derived lookahead-span classification that un-trivialises the bridge, and one honestly stated residual.

Implements D-J1 ("What guard catches an unparameterised query?", roadmap criterion 2): this plan closes the
receiver-depth axis, where a binding one link along the client chain reached every table while the guard
reported the file clean.
</objective>

<assumption_delta_decision>
The deterministic detector fired on this phase, and this is the genuine architectural transition it points at.

- **Noun that is now primary:** *a binding of any node on the client's member chain*. The old noun — *a
  binding of the client itself* — becomes a variant of it (the zero-length-chain case).
- **Decision: `promote`.** `CLIENT_BINDING_RE` is widened in place so the general representation is the
  primary one, and the specific old case survives as the chain-of-length-zero reading of the same rule. The
  code review's suggested `CLIENT_MEMBER_BINDING_RE` — a second matcher parallel to a still-primary
  `CLIENT_BINDING_RE` — is REJECTED as accepted debt this plan has no reason to take on: two matchers reading
  overlapping shapes would need two message texts, two count families, and a written rule about which one
  reports a shape both match, and every future widening of one would be a decision about whether to mirror it
  in the other. The single rule has one trailing lookahead, and the self-test's alias count is already a
  three-way discriminator on that lookahead's content — which is the strongest assertion in the guard and
  which a second matcher would split in half.
- **What would force a later re-promote:** if the guard ever has to tell a bound client SUB-OBJECT apart from
  a bound SCALAR member (see the residual this plan states), the noun becomes *a binding of a node that can
  reach a table*, which no source-level regex can decide. That would be an AST-parse decision, not a second
  regex, and it is the trigger to revisit `WHY A REGEX READ RATHER THAN AN AST PARSE` in the module docblock.
- **Invariant test encoding the generalized intent (included in Task 2):** the matrix's chain link, disposed
  `admitted-by-exclusion` with `excludedBy` set to a method call on the client. It goes red the instant a
  future edit reintroduces the singular assumption by re-excluding any following member access, because the
  link's plain and optional renderings would stop matching.
</assumption_delta_decision>
