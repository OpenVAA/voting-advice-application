## Decision record for this plan

### DR-13 — Scope uniformly, including the authenticated paths

The pending todo `.planning/todos/pending/frontend-project-id-scoping.md` bounds itself to
*"voter (anon) paths only … candidate/admin paths authenticate and already have project context via
`can_access_project()`"*. That is an accurate description of where the **risk** is — the `anon_select_*`
RLS policies are `published = true` with no project term, while the `authenticated_*` policies route
through `can_access_project(project_id)`.

161's criterion 2 is nevertheless **wider**: *every* project-scoped query. The predicate is added
uniformly because (a) a static guard cannot distinguish an anon call site from an authenticated one,
(b) for an authenticated path the added `.eq()` narrows an already-narrow set and is a no-op at the
database, and (c) a uniform rule is the only one the guard can express without a per-site exception
list that would itself become the thing nobody audits.

### DR-14 — `get_candidate_user_data`'s returned project id is cross-checked

That RPC is dispositioned `scoped-by-identity: auth.uid()` in plan `161-02` DR-9 and needs no
parameter. It already **returns** `project_id` among its result columns. The adapter compares the
returned value with the configured one and throws on mismatch. This costs one comparison and catches
the mis-provisioned-deployment case that identity scoping alone cannot: an authenticated candidate
belonging to a different project than the one this deployment serves.
