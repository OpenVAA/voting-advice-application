# Phase 161 Plan 02.1: get_questions Project Scoping and the State-Dependent Partition Assertion — Summary

`public.get_questions` now takes a required `p_project_id` and can no longer return another
project's questions, closing the last `UNSCOPED` disposition in the adapter guard; and
`07-rpc-security` test 14, which 161-02 authored as an unrestricted row count, is scoped to its own
fixture so it survives the seeded database that plan 161-07 will run against.

## Task A — get_questions gets the get_nominations treatment

### The defect, re-measured rather than inherited

The live signature was re-derived from `pg_proc` before anything was written, because 161-02's plan
was stale by one parameter and it cost a correction there:

```
get_questions(uuid,uuid,integer) | p_election_id uuid, p_constituency_id uuid, p_election_round integer
```

That matched the schema mirror — the recipe was accurate this time — but the check was the point.
All three filters default NULL and NULL means "applies to all", so the call the voter app issues
before an election is chosen returned every project's categories and questions. Both source tables
carry `project_id uuid NOT NULL`, so the fix is a predicate, not a schema addition.

### Where the recipe WAS stale: positional callers

`.planning/todos/pending/2026-09-04-…md` step 5 asserted that the `get_questions` call sites in
`tests/database/11-question-rpcs.test.sql` are *"all named-argument or no-argument today, so none is
positionally sensitive"*. **That is false.** Every one of the 30 call sites in that file is
positional — `get_questions ()`, `get_questions (test_id ('election_a'))`,
`get_questions (NULL, test_id ('constituency_a'))`, `get_questions (NULL, NULL, 2)`, and two more
inside dollar-quoted `throws_ok` / `lives_ok` strings. Had the recipe been trusted, the parameter
would have landed and 30 assertions would have silently changed meaning: `test_id ('election_a')`
would have been read as a project id, matching nothing, and every membership assertion would have
gone red at once.

All 30 were rewritten to pass `test_id ('project_a')` first. Every synthetic and fixture row that
file reads belongs to project A, so no assertion changed meaning. The adapter calls by name, as
PostgREST requires, so it was unaffected by placement.

### What landed

| Piece | Where |
| --- | --- |
| Additive migration: `DROP FUNCTION (uuid,uuid,integer)`, re-create 4-arg, re-`GRANT` to `anon, authenticated` | `migrations/00006_get_questions_project_scope.sql` |
| `WHERE qc.project_id = p_project_id` and `WHERE q.project_id = p_project_id` on the two independent subqueries | migration + `schema/505-question-rpcs.sql` |
| Parity fixture re-baselined (32 hunks, 125 signature lines) | `apps/supabase/scripts/schema-migration-parity.expected.txt` |
| `p_project_id: this.projectId` on every call of the question fan-out | `supabaseDataProvider.ts` `_getQuestionData` |
| Generated type `p_project_id: string` — required, not optional | `packages/supabase-types/src/database.ts` |
| Disposition `UNSCOPED: …` → `requires p_project_id`, and its doc paragraph rewritten | `scripts/assert-project-scoped-queries.mjs` |
| Two new adapter unit tests mirroring the `get_nominations` pair (unfiltered call; all four calls of a 2×2 fan-out) | `supabaseDataProvider.test.ts` (77 → 79) |

The project predicate is stated FIRST in both subqueries, before the three defaulted filters, so a
reader checking the leak is closed does not have to read past them to find it. Both halves are
predicated separately on purpose: a project term present on categories and missing from questions is
a real and silent failure mode, and §9's assertions test the two halves independently for that
reason.

`PROJECT_SCOPED_RPCS` now has no `UNSCOPED` entry at all. The `UNSCOPED:` vocabulary is deliberately
left documented in the guard — it is the honest disposition for a future rpc whose body has no
project term, and removing the vocabulary would push the next such case toward an overstated
disposition instead.

### The cross-project proof, and its positive controls

Seven assertions in `07-rpc-security.test.sql` §9, built the way 161-02 built §8. **Project B's
category and question are published FIRST** — the fixture ships both `published = false`, so
asserting a zero for them in that state would have been a zero from an empty instrument that held
identically with and without a project predicate. Both projects are asserted to return rows BEFORE
either is asserted not to return the other's:

1. control: project A returns ≥1 category **and** ≥1 question
2. control: project B returns ≥1 category **and** ≥1 question — this is what makes A's zeros a measurement rather than an RLS artefact
3. project A returns neither `question_category_b` nor `question_b`
4. project B returns neither `question_category_a` nor `question_a`
5. partition: the four payload lengths sum to the anon-visible categories + questions **of these two projects**
6. adjacency: an `external_id` shared across projects yields exactly one category for A, not both
7. `get_questions()` with no argument raises `42883`, so `p_project_id` carries no DEFAULT

### Red/green proof, with a byte-identical restore

Baseline `md5(pg_get_functiondef(...))` = **`fac236ef4756d0fa98ecc41bd4f85e8b`**.

Both project conjuncts were then stripped from the **live** definition (signature unchanged) and the
suite re-run:

```
# Failed test 19: "get_questions for project A returns neither the category nor the question belonging to project B"
# Failed test 20: "get_questions for project B returns neither the category nor the question belonging to project A"
# Failed test 21: "the two project-scoped payloads partition this fixture's anon-visible categories and questions ..."
# Failed test 22: "an external_id shared by two projects yields exactly one category for project A, ..."
# Looks like you failed 4 tests of 23        Result: FAIL   (exit 1)
```

Assertions 17 and 18 — the two positive controls — stayed **green** throughout, which is what proves
the four failures are the predicate's absence rather than an instrument returning nothing.
Assertion 23 also stayed green, correctly: the probe changed the body, not the arity.

Restoring by re-running the migration file reproduced the definition byte-identically —
`md5 fac236ef4756d0fa98ecc41bd4f85e8b`, unchanged — with both grants intact and exactly one overload.

## Task B — the state-dependent partition assertion

### What was wrong

161-02 wrote test 14's right-hand side as an unrestricted count:

```sql
(SELECT count(*) FROM nominations n WHERE NOT COALESCE(n.unconfirmed, false))::integer
```

`create_test_data()` runs inside the file's transaction and contributes a fixed 4 rows, but rows
committed **outside** it were counted too. On the operator's database — 377 previously seeded
nominations, verified by direct count before any change — the assertion read `have: 4, want: 381`.
The clean-database precondition was never stated anywhere, so it presented as an intermittent
mystery rather than as the test-authoring bug it is. Plan **161-07 must prove `yarn test:e2e` green
twice in a row with no intervening `yarn db:reset`**, which an assertion coupled to pristine state
cannot survive.

### The fix

The right-hand side is restricted to the fixture's own two projects — the same discipline as the
project scoping this phase delivers:

```sql
WHERE n.project_id IN (test_id ('project_a'), test_id ('project_b'))
  AND NOT COALESCE(n.unconfirmed, false)
```

Not by resetting the database, and not by weakening the equality into an inequality or a `>= 1`.

### Probed in both directions

**Direction 1 — the old form really is state-dependent here.** The unrestricted right-hand side was
put back and the suite run against the 377-row database:

```
# Failed test 14: "the two project-scoped counts partition ..."
#         have: 4
#         want: 381
```

161-03's measurement reproduced exactly, on this database, as a controlled experiment rather than as
an inherited report.

**Direction 2 — the scoped form still fails on a real regression.** With the fix restored, the
project predicate was removed from the **live** `get_nominations` (signature unchanged):

```
# Failed test 12: "get_nominations for project A returns no nomination belonging to project B"   have: 2   want: 0
# Failed test 13: "get_nominations for project B returns no nomination belonging to project A"   have: 2   want: 0
# Failed test 14: "the two project-scoped counts partition ..."                                  have: 762 want: 4
# Failed test 15: "an external_id shared by two projects yields exactly one row for project A"    have: 2   want: 1
```

`have: 762, want: 4` — the assertion is loud, not vacuous. Every way the partition claim can break
still fails it: dropping the project predicate overshoots, dropping a row undershoots, double
counting overshoots. `get_nominations` was then restored from `00005` and confirmed byte-identical
(`md5 c2e9e0e1ad0d9866fe6af8f7f1cf611b`, before and after).

Attribution is recorded in the test file itself, naming 161-02 as the author and 161-03 as the
measurement, and naming 161-07 as the plan the coupling would have broken.

## Deviations from Plan

**1. [Rule 1 — Bug] The todo's step 5 was wrong about positional callers.**
Recorded above and in the close note on the todo. Found before acting, by grepping the call sites
rather than trusting the recipe. All 30 sites updated.

**2. [Rule 3 — Blocking] `yarn db:types` leaked pgTAP helper functions into the generated types.**
The first regeneration added `create_test_data`, `reset_role`, `set_test_user`, `test_id`,
`test_user_id` and `test_user_roles` alongside the intended `p_project_id` line.
`00-helpers.test.sql` creates its helpers OUTSIDE its transaction, so a preceding `supabase test db`
leaves them committed in `public` and the generator picks them up. The generated file was reverted,
the six helpers dropped, and the regeneration re-run — producing a clean **one-line** diff
(`p_project_id: string`, required). The suite recreates the helpers on its next run, and the final
`supabase test db` above confirms it did.

**3. [Rule 2 — Missing coverage] Two adapter unit tests added.**
`get_nominations` has dedicated tests asserting the project key is present on the unfiltered call
and on all four calls of a 2×2 fan-out. `get_questions` had none; without them a fan-out that passed
the key on only the first call would not have been caught by any unit test. Added as exact mirrors.
