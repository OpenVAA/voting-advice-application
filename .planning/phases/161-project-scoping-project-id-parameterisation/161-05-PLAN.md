## Decision record for this plan

### DR-3 (restated) — Teardown posture: create-if-absent, **never delete the project row**

D-J2 requires the choice be stated. The E2E project row and its `app_settings` row are created
idempotently and **left in place** between runs; only the run's content is torn down by the existing
prefix-scoped teardowns. Run *N+1* therefore finds the project already there and takes the reuse
branch — the same code path as steady state, which is what makes the twice-in-a-row proof cheap.

Cost: two rows persist in the local database between runs, invisible to the default project's data.
Benefit: `DELETE FROM public.projects` never runs, so the one `project_id` foreign key that lacks
`ON DELETE CASCADE` never fires and this phase does not cross into Phase 156's schema domain.

### DR-4 (restated) — The `app_settings` cascade gap is mooted here; Phase 156 has since claimed the fix

Verified in **both** trees (`apps/supabase/supabase/schema/106-app-settings.sql:8` and
`apps/supabase/supabase/migrations/00001_initial_schema.sql:916` — twelve of thirteen foreign keys
carry the cascade, this one does not).

**Ownership changed during the planning run and the plan says so rather than hiding it.** At the start
of the run Phase 156 had no PLAN.md and named the cascade in none of its criteria. A concurrent
planning run has since produced `156-06-PLAN.md`, whose task 3 adopts the fix deliberately as an item
outside 156's stated criteria, with a must-have that deleting a project cascades to `app_settings`
instead of raising a foreign-key violation.

161 takes **no dependency** on that either way: under DR-3 the project row is never deleted, so the gap
is never exercised. Task 3 therefore **checks the tree and branches** — filing the register entry only
if the cascade has not landed, so the item is neither lost nor duplicated. 161 makes no schema change
for it in either branch.

### DR-15 — Where the E2E project id is resolved, and where it deliberately is **not**

Measured constraint the research did not have: `packages/dev-seed/src/cli/seed.ts` **auto-loads the
repo-root `.env`** via `process.loadEnvFile`, and `tests/playwright.config.ts` does `dotenv.config()`.
So a live `E2E_PROJECT_ID=` line in the repo-root `.env` would re-point **`yarn db:seed:default`** and
therefore `yarn db:reset-with-data` at the E2E project, leaving a plain local dev session showing an
empty app. That is the rejected route.

The resolution is therefore:

| Site | Behaviour |
|---|---|
| `packages/dev-seed/src/supabaseAdminClient.ts` | Exports a new constant `E2E_PROJECT_ID = '00000000-0000-0000-0000-0000000000e2'` and a resolver `resolveE2eProjectId()`. **The base constructor's `?? TEST_PROJECT_ID` default is unchanged.** |
| `packages/dev-seed/src/ctx.ts` | **Unchanged.** |
| `tests/tests/utils/supabaseAdminClient.ts` | Constructor override: `projectId` defaults to `resolveE2eProjectId()`. This one edit re-points every argument-less `new SupabaseAdminClient()` inside `tests/`. |
| `tests/tests/setup/shared/setupFromTemplate.ts` | Passes the resolved id into both `runPipeline` (via a spread override of the template's `projectId`) and `new Writer({ projectId })`, so generated rows carry it too. No template file is edited. |
| repo-root `.env.example` | The `E2E_PROJECT_ID` line is **commented out**, documented as an override the harness does not need. `resolveE2eProjectId()` falls back to the committed constant. |

`resolveE2eProjectId()` reads `process.env.E2E_PROJECT_ID`, trims and lower-cases it, and: returns the
committed constant when it is absent or empty; **throws** naming the collision when it equals
`TEST_PROJECT_ID`; **throws** when it is not a canonical 8-4-4-4-12 lower-case hexadecimal uuid.

Note the `.env.example` line added by plan `161-01` must be **commented out** if it was written live;
task 1 corrects it if so and records the correction.

### DR-7 (restated) — The freshness probe is re-aimed now, its polarity is not promoted here

`probeFreshDatabasePrecondition` already queries through `client.query(...)`, which is
`.eq('project_id', this.projectId)`-scoped, so re-pointing the client re-aims the probe for free.
`BASELINE_SEED_PREFIX` existed only to hide `seed_`-prefixed rows sitting in the default project; once
the client is scoped elsewhere those rows are invisible and the exclusion is a stale guard — exactly
the class this milestone exists to close — so it is deleted.

The polarity is **not** promoted in this phase. The residual benign-noise source is *cross-family*
residue **inside** the E2E project: all families still share one project, and the base setup's
foreign-namespace pre-wipes exist precisely because an aborted run leaves recoverable state. A
hard-fail probe would convert that recoverable state into a run that refuses to start. Promotion is
filed in task 3 with the two green runs from plan `161-07` named as its evidence prerequisite.

The base setup's `extraTeardownPrefix` pre-wipes stay **unchanged**: same project, same need.
