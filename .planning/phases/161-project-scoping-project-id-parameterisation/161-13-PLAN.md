## Decision record for this plan

### DR-38 — Widening AND a statement, split by what each rule can honestly claim

The two halves of the answer are not alternatives here; they cover different surfaces.

**The invocation check is WIDENED outright.** It was already anchored on the function name rather than on
a receiver (161-12, DR-35), so running it over more files is a corpus change and nothing else. There is a
live site waiting for it: `apps/frontend/src/routes/api/candidate/preregister/+server.ts` invokes
`identity-callback` through `locals.supabase`, outside the adapter directory and through a receiver the
adapter's own checks would never have matched.

**The table and rpc checks get a STATEMENT instead of a widening.** Checks 1 to 4 depend on the adapter's
scoped helper being available, and a route file has no such helper — reporting "use `this.scopedFrom(…)`"
in a SvelteKit endpoint would be advice the file cannot take. So the rule outside the adapter directory is
not "use the helper", it is "do not reach a table here at all": the boundary is that all project-scoped
table and rpc access lives under the adapter directory, and the check fails when an access appears outside
it. Measured before choosing: a search of the frontend source tree outside the adapter directory for a
table or rpc access on a Supabase receiver returns nothing today, so the statement is true when it is
written and the check is a tripwire rather than a backlog.

### DR-39 — The outside corpus gets a floor on its ENUMERATION, not on its call sites

The adapter corpus has two floors already: an empty enumeration fails, and zero examined call sites fails.
Only the first transfers.

A floor on outside call sites would say "there must always be at least one Supabase call outside the
adapter directory", which is the opposite of what the boundary asserts — the correct long-run number of
table accesses out there is zero, and today the only outside site at all is one Edge Function invocation
whose removal would be a perfectly good change. A floor on the ENUMERATION says something different and
true: the walker must find files. That is the failure the adapter floor exists for — a matcher or a walker
that has quietly stopped looking while still printing a clean bill — and it is the one worth reproducing.

### DR-40 — The fixture pair is separate from the adapter fixtures, because the corpus semantics differ

The two existing fixtures model a guarded adapter source, and the clean one deliberately contains a
dispositioned rpc call — legitimate inside the adapter, a boundary violation outside it. Exercising the
boundary rule over that same file would force one of the two meanings to give way.

So the boundary rule gets its own committed pair under the same fixture directory, and the self-test runs
the boundary check over them exactly as it runs the source checks over the existing pair. Same shape, same
naming, same one-method-per-shape convention, four fixtures instead of two.

### DR-41 — The closing full-suite run resets the database, because this phase added a migration

`CLAUDE.md` records that a reset is not a precondition of a run and is worth doing only after a genuine
schema change. 161-11 is a genuine schema change: migration `00008` alters a granted function's signature.
The closing run therefore goes through the wrapper WITHOUT `--no-db-reset`, so the suite exercises a
database built from the migration set rather than one carrying a hand-applied state.
