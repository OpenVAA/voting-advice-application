<design_choice>
**Design A of three, per `140-RESEARCH.md` § F9 and the pattern map's cross-transplant finding.**

The two templates are each other's analog: `perm-hide-election-tags.ts` already carries `elections: 2`,
and `perm-hide-category-tags.ts` already carries a `questions.showCategoryTags` overlay. Design A is a
literal cross-transplant of one property each way, after which each spec can assert the presence of the
tag its sibling suppresses.

Design A was chosen over design B (positive assertions in `voter-journey.spec.ts`) and design C (a new
`perm-show-tags` project) because it is the only design under which ROADMAP criterion 3's sentence —
"`perm-hide-category-tags` / `perm-hide-election-tags` FAIL when the tag element stops rendering
anywhere" — is LITERALLY true. B and C both leave the named pair green. B additionally parks the control
inside a 1869-line serial walk where a failure is least legible, which is the exact legibility problem
F10 is about.
</design_choice>

`140-RESEARCH.md` § Validation Architecture specifies the F9 positive assertion as
`.not.toHaveCount(0)`. The pattern map found the house form is different: `perm-answers-locked.spec.ts:54`

`.not.toHaveCount(0)` appears **nowhere** in `tests/tests/specs/perm/`. There is no concrete reason to
introduce a second idiom for one assertion, and the house form carries the explanatory message this
phase wants on every new assertion. **Plan 04 lands the house form and updates `140-VALIDATION.md`'s
ASSERT-05 rows so the validation contract and the plans agree** — a validation document that contradicts
the plan is exactly the drift class this phase exists to close.
