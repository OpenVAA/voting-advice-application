<conflict_resolutions>
**F9 assertion form — research vs. pattern map.** `140-RESEARCH.md` § Validation Architecture specifies
the F9 positive assertion as `.not.toHaveCount(0)`. The pattern map found the house form is different:
`perm-answers-locked.spec.ts:54` uses `const count = await locator.count()` followed by
`expect(count, '<why>').toBeGreaterThan(0)`, and `.not.toHaveCount(0)` appears **nowhere** in
`tests/tests/specs/perm/`. **Resolved in favour of house style** — there is no concrete reason to
introduce a second idiom for one assertion, and the house form carries the explanatory message this
phase wants everywhere. Plan 04 lands the house form and updates `140-VALIDATION.md`'s ASSERT-05 rows
so the validation contract and the plans agree. (A validation document that contradicts the plan is
exactly the drift class this phase exists to close.)

**F19 message register — cross-register borrowing, deliberate.** The `expect(value, 'message').toX()`
*syntax* is precedented in the frontend suite (`apps/frontend/src/lib/i18n/tests/utils.test.ts:25-58`),
but every frontend instance uses a terse label ("Wildcard match from list"). The explanatory,
failure-naming register lives only in `tests/` (`perm-answers-locked.spec.ts:54`, the 27 teardown
sites). This plan borrows **syntax from the frontend precedent and phrasing register from `tests/`**.
Stated here so a reviewer does not read it as inconsistency.
</conflict_resolutions>
