<conflict_resolutions>
**F9 assertion form — research vs. pattern map. RESOLVED IN FAVOUR OF HOUSE STYLE, and this plan is
where the resolution is executed and written back.**

`140-RESEARCH.md` § Validation Architecture and its § F9 code example both specify the positive
assertion as `await expect(locator).not.toHaveCount(0)`. The pattern map established that the house form
is different: `tests/tests/specs/perm/perm-answers-locked.spec.ts:53-54` uses
`const count = await inputs.count();` then
`expect(count, 'profile page must render at least one visible input').toBeGreaterThan(0);`, with the
same shape at `:84` and at `perm-localisation-positive.spec.ts:193,205,244`. `.not.toHaveCount(0)`
appears **nowhere** in `tests/tests/specs/perm/`.

Resolved in favour of the house form. There is no concrete reason to introduce a second idiom for one
assertion; the house form carries the explanatory second-argument message this phase wants on every new
assertion; and `.not.toHaveCount(0)` is an auto-retrying web-first matcher whose negation semantics
differ subtly from a one-shot count comparison — a difference not worth introducing casually into a
suite that currently has none of it. Task 3 updates `140-VALIDATION.md`'s ASSERT-05 rows so the
validation contract states the form actually shipped.
</conflict_resolutions>
