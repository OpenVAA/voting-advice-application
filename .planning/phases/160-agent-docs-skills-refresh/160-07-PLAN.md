<task type="checkpoint:decision" gate="blocking">
  <decision>Whether to delete the generated spike-findings skill directory in full, delete only its
  source copies, or keep it.</decision>
  <context>
This is a one-way door in this repository, and that is why it is a gate rather than a plan decision.

The operator's binding note asked for the removal if the skill is not useful to maintain, on the
stated basis that the content would remain available from git history. **That basis is measurably
false here** and the record corrects it: the skills directory has never existed on the default branch,
the skill's add commit is not an ancestor of it, and the repository squash-merges — so a
delete-then-squash removes the content from the default branch's history entirely. The recovery path
would be a pre-squash branch reference, which is not a durable artifact.

The delete is nonetheless defensible, for a different reason. The majority of the skill's bytes are
formatter-reformatted copies of the spike write-ups under `.planning/spikes/`, which stays in the
working tree, is the superset, and holds the spike that is the source of the reactivity carve-out this
very phase relocated. But a real cost exists: the synthesised cross-spike digests — the skill file and
its reference files — are not in `.planning/spikes/` and would be genuinely lost from the working
tree. `.claude/skills/README.md` carries the full argument, the re-derived measurements, and the
recorded runner-up; read it before deciding.

Both spike domains have landed in production, and the skill is the repository's only skill whose
routing chain violates the one-level rule this phase asserts.
  </context>
