<objective>
Sweep the Supabase backend and the documentation site, and protect the one comment in this partition that is a
**live security invariant** rather than narrative.

**Scale note, so a later reader does not think this drifted.** CONTEXT.md fact 7 puts `apps` at 219
planning-reference comment lines; `152-RESEARCH.md` § 4 re-measured at HEAD `22c2542e3` and found **290**,
inside a repo-wide **888 citation lines / 942 union / 946 occurrences / 642 spans across 278 files** against
CONTEXT.md's 817. The measured figures govern per CONTEXT.md § 0.1. The register's `152-12` partition list is
authoritative for this plan's share.

**The security invariant, named so it cannot be swept by momentum.** The identity-callback Edge Function
carries a comment stating that a particular error is **logged and never returned**, because the
claim-extraction message enumerates which configured claim names were present or missing and would disclose
the provider's claim mapping to an unauthenticated caller. That is an ASVS V7 error-handling and logging
control expressed as a comment guarding the log call on the very next line — it is the reason the code is
shaped the way it is. It is also one of the 19 reviewed sites, where the reviewer asked only for the line
breaks to be removed. **Keep every word of its meaning.** The line-break half is plan `152-14`'s under an
operator decision; this plan's obligation is that if any citation is stripped from it, the disclosure rationale
survives complete.

**The stage-marker trap.** This partition contains comments and shell echo lines that name numbered stages —
a smoke-test section header in a pgTAP helper, a benchmark script's stage banner. They **look** like phase
citations to a naive pattern and are not: they are algorithm and benchmark stage markers. The retargeted
codemod already classifies them under its ambiguous-reference exclusion and never rewrites them, and the
judgement pass must not "finish the job" by hand.

**SQL migrations are effectively immutable.** A migration that has been applied cannot be meaningfully edited;
comment-only edits are safe and are all this plan makes, but every non-comment byte must be identical, and the
SQL comment marker is itself a double hyphen — which is one more reason this phase has no dash rule of any
kind.

**No schema push task is injected, and here is why — stated rather than skipped.** The schema-detection gate
fires on this plan because its file set encompasses the Supabase migration directory. It fires on the *paths*,
not on the change. This plan changes **comment bytes only**: no `CREATE`, `ALTER`, `DROP`, `GRANT`, `REVOKE`
or DML line may differ, the behaviour-neutrality prover asserts the non-comment byte stream of every touched
file is identical, and an acceptance criterion greps the diff for exactly those keywords and requires zero.
The failure mode the schema gate exists to prevent — build and types passing green because the types come from
config while the live database was never updated — cannot arise, because no schema statement changed and
nothing needs pushing. Running a push here would be a no-op at best. Recorded so a reviewer sees the gate was
considered and reasoned about, not bypassed.

Purpose: leave the backend and docs explained by their comments, with the disclosure control intact and every
migration byte-stable.
Output: a swept Supabase and docs surface, proven comment-only.
</objective>
