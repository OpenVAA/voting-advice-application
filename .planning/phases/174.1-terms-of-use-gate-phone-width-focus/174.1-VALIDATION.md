# Phase 174.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution. Two plans, two serial waves, six
> tasks, all automated; no checkpoint. Every task has a verify command with a stated failing direction. The
> phase is a defect fix on one screen: each of its two fixes sits behind a check that is written first and
> observed red, and the closing gate compares the suite, project by project, with the last full run before
> the phase.

`P4` is `.planning/phases/174-invitations-grants-defined-in-advance` and `P` is
`.planning/phases/174.1-terms-of-use-gate-phone-width-focus`.

**Drivers.** `174-gates.sh`, `174-e2e.sh` and `174-verdict.mjs` are Phase 174's, reused as they are; this
phase's runs take labels that begin `174.1-` and land in those drivers' own directories. `174.1-verdict.mjs`
is created by 174.1-01 Task 1 and `174.1-read.mjs` by 174.1-02 Task 1. Neither exists before its task.

**How a run is compared with another.** `--same-projects-as 174-10-final-r3` is the per-project comparison
with the last full default run before the phase, whose head is tree-equal to the phase's starting commit
outside `.planning/` (174.1-01 Task 1 asserts it before any edit). Every project has exactly its total
there, except the new project, named in `--except` with the number of tests the listing holds for it at run
time. No total is typed into a plan.

**How a later attempt is named.** Every later attempt at a run or a read session keeps its label and takes
the next `-rN` suffix. `resolveRun` in `174-verdict.mjs` follows a label to its newest `-rN` that holds a
`head` file and to nothing else; `174.1-verdict.mjs` and `174.1-read.mjs judge` resolve the same way.

**Which verdicts compare a recorded head with HEAD, and when each is taken.** `174-verdict.mjs gates` and
`e2e` — with `--allow-slice` too — and `174.1-read.mjs judge` refuse a run made on a tree that differs from
HEAD outside `.planning/`. Each is taken before the next commit outside `.planning/`. One of them is
time-bound by design: the `e2e` verdict of the one-project run `174.1-01-phone-fixed` holds at the end of
174.1-01 Task 2 and not after Task 3's first commit, so it is in Task 2's verify and in no later command;
its output is recorded in the plan's summary. `174.1-verdict.mjs control` reads a run's own head and holds
whatever was committed since. The verdicts of 174.1-02 hold to the end of the phase: that plan commits under
`.planning/` only, unless it fixes something, and then every read and run is made again.

**What makes a run void.** For an E2E run, the wrapper's marker `VOID-host-suspend.txt` and its status 8,
and nothing else. For the read session, which does not go through the wrapper, a Sleep entry of the host
inside the session's window, recorded by the session itself: the one place a later attempt is licensed
without the wrapper's marker. A red run with no marker is diagnosed and fixed at its cause.

**What no command of the phase does.** Read an untracked environment file; print a container's environment;
open a `db-start.log`; restart the stack. The Phase 174 hygiene verdict does not scan this phase's scripts,
so a negative search over `174.1-verdict.mjs` (174.1-01 Task 1) and over both scripts (174.1-02 Task 1) is
part of those tasks' verify commands.

## Sampling Rate

- **After every task commit:** the task's own `<automated>` command — static gates, a targeted Vitest
  filter, a one-project E2E verdict, or the read session's verdict.
- **After plan 174.1-01:** the red control and the green one-project run of the phone-width spec, the red
  and the green report of the focus cases, the whole frontend unit suite, `svelte-check`, and the scope of
  the phase's diff. No full E2E run: its boundary proof is the full run of 174.1-02.
- **After plan 174.1-02, and before `/gsd-verify-work`:** the closing gate of 174.1-02 Task 2 on one tree —
  the six gate rows, the full default E2E run compared project by project with `174-10-final-r3`, the
  schedule of the new project in that run, the read session's verdict, and the scope of the phase's diff.
- **Max feedback latency:** about 300 seconds per task for everything but the two closing runs; about 15
  minutes for the closing gate.
- **Never:** a retry until green, a skipped test, a status read through a pipe, a foreground command over
  about eight minutes, a deletion under `tests/e2e-runs/`, a stack restart, a read of an untracked
  environment file, a listing of a container's environment, a relation or a tolerance edited to pass.
