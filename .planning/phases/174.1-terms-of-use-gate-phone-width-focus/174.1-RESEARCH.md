## Summary

The expander does not force the width. The element that does is the consent `<label class="label …">` in `TermsOfUseForm.svelte`, and the rule is DaisyUI 5's `.label { white-space: nowrap }`. The label's text cannot wrap, so its minimum width is the checkbox (24 px) plus the gap (8 px) plus the whole sentence on one line (544.109 px in English) = 576.109 px. That it comes to 576 — the pixel value of `max-w-xl` — is a coincidence of the English string: the same label is 512.94 px in Finnish and 771.23 px in Luxembourgish `[MEASURED: M3]`. Every other 576 px box the todo listed (the form's `section`, its `div.mb-lg`, the expander, the expander's input) is that wide only because it fills the section, and the section is as wide as its widest unshrinkable child. Hiding the label alone removes the overflow; hiding or resizing the expander, its input or its title leaves all of it `[MEASURED: M2]`. The checkbox ends at a negative x because the section is a centred flex item (`items-center`) in a 350 px column: a 576.109 px box centred on a 350 px one sticks out 113 px on each side, and the column starts at x = 20, so the left edge is at −93.05 `[MEASURED: M1]`.

The fix is one class on that label: `whitespace-normal`. With the equivalent rule applied in the page the document stops overflowing and the checkbox sits at x = 20 at 320 and at 390 px, under both phone descriptors the suite uses, and the box can be ticked `[MEASURED: M2, M13]`. **It is not free at 1280 px in English:** the English label is 0.109 px wider than its 576 px column, so once it may wrap it does, onto a second line ("…the terms of / use."), and the hero, heading, ingress and expander move up 8.25 px. The Continue button, the checkbox's position and the document height do not change, and in Finnish nothing changes at all `[MEASURED: M11]`. The alternative that leaves 1280 px untouched by construction (wrap below 640 px only) was measured and leaves the checkbox off-screen at 640–740 px in Swedish, Danish, French and Luxembourgish `[MEASURED: M3]`. This is the one place where the roadmap's criterion 4 and criterion 1 pull apart, and it is the first open question.

Focus is lost to `<body>` in all three outcomes after the gate, measured: the selection screen, the "nothing to edit" view and an entity page reached through an entity URL (profile page, candidate home, organization home). The control — a single-entity user at the root, who is redirected — lands on the new page's `<h1>` `[MEASURED: M4]`. On each of those pages `focusNavigationTarget()` focuses the page's `<h1 tabindex="-1">`; none carries `[data-focus-on-nav]` `[MEASURED: M4]`. Requesting focus at the moment the gate view leaves the DOM puts focus on that `<h1>` and keeps it there in every outcome, and does no harm in the control `[MEASURED: M5, M6]`.

**Primary recommendation:** add `whitespace-normal` to the consent label in `TermsOfUseForm.svelte`; move focus from the protected layout whenever the view it renders changes without a navigation (one effect, covering this gate and Phase 178's); add one spec, `contestant-terms-gate-phone.spec.ts`, in its own leaf project, asserting at 320 and 390 px that `scrollWidth − clientWidth ≤ 0`, that the checkbox is wholly in the viewport, and that it can be ticked.

## Architecture Patterns

### System Architecture Diagram

```
 user presses Continue on the gate view
        │
        ▼
 TermsOfUseGate.handleSubmit ── acceptTermsOfUse() ──► database (acceptance row)
        │
        ▼
 invalidateAll()  ── reruns ──► (protected)/+layout.server.ts
        │                              │ firstNeededGate(user)
        │                              ▼
        │                 ┌── a gate still applies ──► data.gate = '<id>'  (Phase 178: the next gate)
        │                 └── none applies ─────────► data.gate = null, entities
        ▼
 (protected)/+layout.svelte re-renders
        │   {#if data.gate != null} <GateView/> {:else} children {/if}
        │
        ├── view unchanged ─────────────────────────────► nothing to do
        │
        └── view changed, and no navigation happened ───► focusNavigationTarget()      ◄── the fix
                                                             │  [data-focus-on-nav] ?? h1
                                                             ▼
                                                    <h1 tabindex="-1"> of the new view

 (a single-entity user at the root is then redirected: a real navigation,
  and the root layout's afterNavigate requests the same focus move — as today)
```

### Pattern 1: fix the unshrinkable box where it is declared

**What:** a flex item cannot be narrower than its `min-content` width. When a box overflows its column on both sides, look for a descendant whose `min-content` equals its `max-content` — text that cannot wrap — before suspecting the widest-looking widget.
**When to use:** any "N elements are all the same too-wide width" report. All but one of them are followers.
**How it was found here:** override one property at a time and read `scrollWidth`; ask the browser for the matched rule (CDP `CSS.getMatchedStylesForNode`); read `min-content` and `max-content` by setting `width` to each keyword.

### Pattern 2: focus follows a view swap that is not a navigation

**What:** `invalidateAll()` reruns loads and replaces the rendered view without a navigation, so `afterNavigate` does not run. Whatever swaps the view requests the focus move itself, through the same `focusNavigationTarget()` the root layout uses.
**Where:** the protected layout, which renders `GATE_VIEWS[data.gate]` or the page `[READ: apps/frontend/src/routes/contestant/(protected)/+layout.svelte]`: `{#if data.gate != null}` `{@const GateView = GATE_VIEWS[data.gate]}` `<GateView />` `{:else}` `{@render children?.()}` `{/if}`.

### Pattern 3: a stored session is read-only

`[READ: tests/README.md § Common pitfalls]`: "**A stored session is read-only.** `STORAGE_STATE`, `TERMS_PENDING_STORAGE_STATE`, `MULTI_ENTITY_STORAGE_STATE` and `NO_ENTITY_STORAGE_STATE` are each one file loaded by every test that names it". The phone-width check ticks the box, which is page state, and **must not press Continue**: that would record the acceptance and the `contestant-terms-gate` axe scans would no longer meet a gate.

### Anti-Patterns to Avoid

- **Clipping an ancestor** (`overflow-x: hidden` / `clip` on the page or the column). It hides the scrollbar and leaves the checkbox at −93. Forbidden by D-03 and refuted by M2: no ancestor property contains the label.
- **Fixing the expander.** Measured to change nothing (M2). `Expander.svelte` is used by six surfaces and has no defect here.
- **`max-sm:` or any breakpoint-gated wrap.** Leaves the checkbox off-screen at 640–740 px in four locales (M3).
- **Comparing against `window.innerWidth`.** Under `isMobile` it equals `scrollWidth` on the unfixed tree (484 = 484, M1), so such a check is green on the defect.
- **Asserting only with axe.** Green on the defect (M10).

## Common Pitfalls

### Pitfall 1: trusting the widest-looking widget
**What goes wrong:** the todo named the expander and its input; both are followers. A fix aimed at them changes nothing (M2).
**How to avoid:** the plan edits `TermsOfUseForm.svelte`'s label and does not touch `Expander.svelte`.

### Pitfall 2: reading criterion 4 as pixel identity
**What goes wrong:** with the label free to wrap, English wraps at 1280 px on this host by a margin of 0.109 px (M11). A verifier who diffs the view will see it.
**How to avoid:** settle Open Question 1 before the plan locks, and write the 1280 px verification as what must not move (Continue, the checkbox's x, the column width, no overflow, the Finnish view), naming the one thing that does.
**Warning sign:** a plan that promises "no change at 1280" without saying how that is checked.

### Pitfall 3: a check that is green on the defect
**What goes wrong:** `scrollWidth <= window.innerWidth` passes under `isMobile` on the unfixed tree (484 ≤ 484); an axe scan passes (0 violations); a `toBeVisible()` on the checkbox passes (it is rendered, just off-screen).
**How to avoid:** compare against `document.documentElement.clientWidth`; assert `toBeInViewport({ ratio: 1 })`; tick the box. Run the D-04 control and keep its run directory.

### Pitfall 4: accepting the terms under the shared session
**What goes wrong:** pressing Continue as the `TERMS_PENDING_STORAGE_STATE` user records the acceptance; the two `contestant-terms-gate` scans, in another project at the same time, then find no gate and fail their reach proof.
**How to avoid:** the spec ticks and asserts Continue is enabled. It never clicks Continue and never signs out.

### Pitfall 5: the layout effect firing on its first run, or cancelling itself
**What goes wrong:** an effect that reads `data.gate` runs once on mount, when the navigation that mounted the layout has already moved focus; and SvelteKit replaces `data` on every rerun load, so the effect may rerun with the same gate. Returning the cancel function as the effect's cleanup would then cancel a pending wait.
**How to avoid:** remember the last rendered view in a plain variable, act only when it differs, and cancel a pending wait explicitly (on the next request and on destroy), as the root layout does with `cancelPendingFocus` `[READ: apps/frontend/src/routes/+layout.svelte › afterNavigate]`.

### Pitfall 6: forgetting the new leaf in the suite's bookkeeping
**What goes wrong:** a spec file that matches no project runs from no command; a project the perm chain may overtake reads replaced settings.
**How to avoid:** an explicit `testMatch`; decide the anchor edge deliberately (see Code Examples); add the project to `tests/README.md`'s inventory. `perm-closed-project` derives its dependencies from every leaf (`CLOSED_PROJECT_DEPENDENCIES`), so that one needs no edit `[READ: playwright.config.ts]`.

### The focus fix

```svelte
<!-- apps/frontend/src/routes/contestant/(protected)/+layout.svelte — shape only -->
<script lang="ts">
  import { onDestroy, untrack } from 'svelte';
  import { GATE_VIEWS } from '$contestant/gates/gateViews';
  import { focusNavigationTarget } from '$lib/utils/focusNavigationTarget';
  import type { Snippet } from 'svelte';
  import type { LayoutData } from './$types';

  let { data, children }: { data: LayoutData; children: Snippet } = $props();

  // The view this layout last rendered: a gate's id, or null for the page.
  let renderedView = untrack(() => data.gate ?? null);
  let cancelPendingFocus: (() => void) | undefined;

  // A rerun load swaps the view without a navigation, so the root layout's focus reset does not run.
  $effect(() => {
    const view = data.gate ?? null;
    if (view === renderedView) return;
    renderedView = view;
    cancelPendingFocus?.();
    cancelPendingFocus = focusNavigationTarget();
  });
  onDestroy(() => cancelPendingFocus?.());
</script>
```
