# Phase 174.1: Code Review Report

**Reviewed:** 2026-10-22T19:56:33Z
**Depth:** standard
**Files Reviewed:** 9

## Summary

This is a retroactive review of the code at HEAD, concentrating on what phase 174.1 introduced (commits `(174.1-01)` since `91899da6f`):

- the focus move in the protected layout when its view is replaced without a navigation;
- the `whitespace-normal` fix on the consent label;
- the shared `$app/state` stub's `navigating` shape;
- the component cases in `gateFocus.svelte.test.ts`;
- the phone-width E2E spec, its fixture steps and its Playwright project.

Later-phase changes to `playwright.config.ts` and `testCredentials.ts` were read only where they touch this phase's project and session.

**The layout's focus logic is correct against the SvelteKit version in use.** I traced it against `@sveltejs/kit` 2.70.3 `client.js`:
- `_invalidate` (line 417 onward) calls `root.$set` without setting `navigating`, so an `invalidateAll` view swap reaches the focus request.
- `navigate()` sets `navigating` (line 1758) before `root.$set` and clears it only after `afterNavigate` runs (line 2050), so a swap during a navigation is correctly left to the root layout's reset.
- First render is skipped, a rerun that returns the same view is a no-op, and pending waits are cancelled on replacement and on destroy, but deliberately not by the effect's cleanup.

No blocker was found. The defects are in coverage and robustness:
- No real-browser test guards the focus fix.
- A viewport assertion depends on how much content sits above the checkbox.
- The label-wrap fix is a per-site patch of a DaisyUI default that still breaks other labels.

None of these overlaps the findings already recorded in 177.1-REVIEW.md or 179-REVIEW.md.

## Warnings

### WR-01: The phase's central a11y fix (focus after passing the terms gate) has no real-browser regression guard; the only tests mock the SvelteKit behaviour the fix depends on

**File:** `apps/frontend/src/routes/contestant/(protected)/+layout.svelte:31-39`, `apps/frontend/src/routes/contestant/(protected)/gateFocus.svelte.test.ts:28-53`, `tests/tests/specs/contestant/contestant-terms-gate-phone.spec.ts:28-34`

**Issue:** The layout moves focus only when `navigating.to === null` at effect time. That relies on a SvelteKit-internal fact: `invalidateAll()` (`_invalidate`) swaps the props without ever setting `navigating`. The component cases replace `$app/state` with a hand-built `navigating` object and replace the rerun load with a direct `props.data = …` assignment, so they **assume** that fact rather than test it. They also run in jsdom, where `requestAnimationFrame` and `MutationObserver` timing differs from Chromium.

No E2E spec asserts focus after the terms-of-use view is accepted:
- `contestant-journey.spec.ts:390-396`, `contestant-email-registration.spec.ts:121-125`, `contestant-identity-provider.spec.ts:159-160` and `contestant-terms-tracking.spec.ts:239-240` all call `acceptAndAdvance()` and then check the destination's content only.
- The set-password view to terms-of-use view replacement (journey line 390) asserts no focus either.
- The phase's own E2E spec covers only layout.

Two things would therefore pass the whole suite:
- A SvelteKit upgrade that marks invalidations as navigations, or that clears `navigating` before effects flush, would silently stop the focus move.
- A refactor that drops the effect would also pass, except for these jsdom cases.

The phase verified this behaviour by manual browser reads, which do not re-run.

**Fix:** Add a heading-focus step to the terms fixture and call it after acceptance, and after the set-password to terms replacement, in a spec that already performs them. For example:

```ts
// contestantTermsOfUsePage.fixture.ts
async expectHeadingFocused(): Promise<void> {
  await expect(page.getByRole('heading', { level: 1 })).toBeFocused({ timeout: TIMEOUTS.slowPage });
},
```

Then, in `contestant-journey.spec.ts`:

```ts
await contestantTermsOfUsePage.expectShown();
await contestantTermsOfUsePage.expectHeadingFocused();
// ...
await contestantTermsOfUsePage.acceptAndAdvance();
await contestantEntityHomePage.expectHeadingFocused(); // heading of the view that replaced the gate
```

`contestantEntityPages.fixture.ts:179` already has the equivalent step for the entity home.

### WR-02: `expectCheckboxInsideViewport` asserts the checkbox is above the fold, which ties the spec to how much content precedes it rather than to reflow

**File:** `tests/tests/fixtures/contestant/contestantTermsOfUsePage.fixture.ts:100-105` (used at `tests/tests/specs/contestant/contestant-terms-gate-phone.spec.ts:31`)

**Issue:** `toBeInViewport({ ratio: 1 })` does not scroll, so at 320x568 the step passes only while the following all fit in the first 568 px, under the header:
- the hero emoji;
- the `<h1>`;
- the `dynamic.contestantAppPrivacy.consent.ingress` HTML;
- the collapsed expander.

That text is dynamic and translatable, and deployments can override it. A longer ingress, a taller hero or a longer translation pushes the box below the fold, and the spec fails on a page that reflows perfectly. Below the fold is not a WCAG 1.4.10 failure.

The step's TSDoc says the step is meant to catch a box "beside the viewport", that is, horizontally unreachable. Its sibling `expectTrackingOptOutInsideViewport` (lines 168-175) was written for the same intent and scrolls the box into view first. The two steps therefore assert different things under similar names, and the phone spec's "on screen" claim depends on content.

**Fix:** Scroll first, as the opt-out step does, so that only the horizontal placement is asserted:

```ts
async expectCheckboxInsideViewport(): Promise<void> {
  const box = page.getByTestId(testIds.contestant.terms.checkbox);
  await box.scrollIntoViewIfNeeded({ timeout: TIMEOUTS.page });
  await expect(box).toBeInViewport({ ratio: 1 });
},
```

An alternative is `createPageGeometry(page).expectWithinViewportWidth(box)`.

### WR-03: The consent-label wrap fix patches DaisyUI's `.label { white-space: nowrap }` at one call site; other `.label`s with long content still overflow at phone width

**File:** `apps/frontend/src/lib/contestant/components/termsOfUse/TermsOfUseForm.svelte:49-50`

**Issue:** DaisyUI 5.7.46's `.label` sets `white-space: nowrap` (`node_modules/daisyui/components/label.css`). This phase fixed it by adding `whitespace-normal` to one label. The same per-site patch now exists in five places:
- `TermsOfUseForm.svelte:50`
- `TrackingOptOut.svelte:41`
- `ElectionSelector.svelte:53`
- `input/shared.ts:18`
- `Input.labelWrap.svelte.test.ts` (asserts it for `Input`)

Labels with variable-length content that never received the patch still do not wrap. The voter-facing filter options in `EnumeratedEntityFilter.svelte:176` sit in a `minmax(9rem, 1fr)` grid; their text is a party or candidate name plus a count, and it inherits `nowrap`. A long name therefore overflows its cell sideways at 320 px, which is the WCAG 1.4.10 Reflow defect this phase fixed for the consent sentence.

`app.css:466-475` already holds a project-wide `.label` override, which cancels DaisyUI's colour mute for an AA reason. The wrap default belongs in that same rule.

**Fix:** Move the wrap into the existing global override, then drop the per-site `whitespace-normal` classes and the comment at `TermsOfUseForm.svelte:49`:

```css
/* app.css, inside the existing utilities-layer block */
.label {
  color: inherit;
  white-space: normal;
}
```

Keep `nowrap` explicitly only where a single-line label is intended, such as `.label` inside `.input`/`.select`, which DaisyUI styles through a separate `:is(.input>*,.select>*)` rule that is unaffected. Add `EnumeratedEntityFilter` to a phone-width overflow check.

## Info

### IN-01: The in-flight check can be fooled by a stale `navigating` left by an aborted navigation

**File:** `apps/frontend/src/routes/contestant/(protected)/+layout.svelte:36`

**Issue:** SvelteKit 2.70.3 sets `navigating.current` when a navigation starts (`client.js:1758`). When a later navigation or an invalidation overwrites the global `token`, `navigate()` returns early with "navigation aborted" (`client.js:1809`, `1988`) and does not reset `navigating`. If an `invalidateAll` (for example, Continue on a gate) races a navigation that it aborts, the layout sees `navigating.to !== null` and requests nothing. The aborted navigation never reaches `afterNavigate`, so nothing moves focus, and the focused Continue button has already left the DOM. The race is narrow, and the root cause is in SvelteKit.

**Fix:** No change is needed now. If it is ever observed, combine the check with a flag that a `beforeNavigate`/`afterNavigate` pair maintains (set on start, cleared on `afterNavigate` and on `navigation.complete` rejection) instead of reading `navigating.to` alone.

### IN-02: The phone viewports and descriptor introduced here are now copied into seven specs, and the "suite's phone descriptor" the spec cites does not exist as a shared definition

**File:** `tests/tests/specs/contestant/contestant-terms-gate-phone.spec.ts:14,19-26`; `tests/playwright.config.ts:562-568`

**Issue:** `PHONE_VIEWPORTS = [{ width: 320, height: 568 }, { width: 390, height: 844 }]` and `test.use({ viewport, isMobile: true, hasTouch: true })` are repeated verbatim in `contestant-entry-phone`, `contestant-identity-provider`, `contestant-nominations`, `perm-no-nomination`, `perm-closed-project`, `perm-organization-editing` and `contestant-terms-tracking` (inline). The doc comment's "the suite's phone descriptor" implies one shared source. The project also starts from `devices['Desktop Chrome']`, so the user agent and `deviceScaleFactor` remain desktop values, and `check()` drives a mouse click, not a tap. "Phone descriptor" therefore overstates what is emulated.

**Fix:** Export `PHONE_VIEWPORTS` and a `phoneUse(viewport)` helper from one module under `tests/tests/utils/`, and import it in every phone spec. Optionally base it on a Playwright phone device descriptor.

### IN-03: The shared `$app/state` stub's `navigating` is a mutable module singleton whose doc invites mutation without a reset

**File:** `apps/frontend/src/lib/i18n/tests/__mocks__/app-state.ts:17-27`

**Issue:** The TSDoc says "A test that needs a navigation in flight sets `to`". Any file that follows that advice and forgets to reset it leaves every later case in that file seeing a navigation in flight, and the protected layout then silently requests no focus. `gateFocus.svelte.test.ts` sidesteps this by injecting its own object and resetting it in `afterEach`, but the stub's guidance points the other way.

**Fix:** Recommend `vi.mock` injection only, as the stub already does for reactive `page` needs, or export a `resetNavigating()` helper and name it in the doc.
