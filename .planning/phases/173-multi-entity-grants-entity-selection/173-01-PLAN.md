**Two CONTEXT.md sentences these plans knowingly contradict — the operator's acknowledgement is asked for
here, in one place.**

- **"The list answers from the table."** D-03 says the list answers H, the single-grant skip and "is this
  selection still mine" *from the table*, and D-10 says the check "is the list from D-03, read from the
  table". As built, the list is the table *and* what the caller's token may read. D-03 itself locks both
  functions as `SECURITY INVOKER`, so every row they return passes the caller's row-level security, and that
  reads the token's claim. The revocation half of D-10 holds exactly as written: a removed grant leaves the
  list at once. The other half does not: a grant the token does not carry yet is not listed.
- **"Selectable without a token refresh."** Obligation O-5 says "a grant written by a claim is selectable
  without a token refresh", and the *Integration Points* note says such a grant "is listed at once but its
  entity row is readable only after the session refreshes". As built, it is neither listed nor readable
  until the token refreshes.

Why the plans do this and do not build what the two sentences describe: listing from the table alone needs
either a definer function, which D-03 rules out and which would move the definer census, or a join outward
from the helper's ids, which yields a card with no name and a redirect target the one-entity read then
refuses. That is a redirect loop between the root and the entity for a single-entity user. With the list
and the read both "table and token", an entity is listed exactly when it can be read; the research measured
this in both stale-token directions and 173-02's pgTAP file pins it. The consequence for Phase 174 is one
step it already plans: refresh the session after a claim, before sending the user to the app root. It is
filed as a todo in 173-13.
