## Rulings and deviations carried by this plan

1. **More files than the phase's aim of about fifteen.** Thirteen are a directory rename committed on
   its own at full similarity. The rest is one unit by nature: the suite cannot be green with the pages
   moved and the root, the resolver or the entity check missing.
2. **The resolver is a matcher-guarded rest route inside the protected group** (D-07's discretion). An
   unauthenticated request for an entity-less protected path is still bounced to login by the request hook,
   and after sign-in the resolver finishes the job. An unknown path still answers 404.
3. **The resolver does not carry a query string.** Reading it would be a tracked URL read. If a spec or a
   link is found to rely on one, the query is read inside the load's `untrack` and that is named in the
   summary.
4. **Between this plan and 173-10 a user with several entities who opens an entity URL directly is served
   that entity**, while the root still signs such a user out. No such user exists before 173-12.
5. **The interim outcome for zero or several entities at the root is not pinned by any test.**
6. **Five tasks.** The root and the resolver are separate tasks, each with its load, its tests and its
   read-recording guard; between them an entity-less protected path answers 404, on a tree that typechecks.
7. **Research finding kept, not fought:** a grant written after the token was issued is not in the list
   until the token refreshes, so such an entity's URL redirects to the root until then (obligation to
   Phase 174).

| Boundary | Description |
|----------|-------------|
| URL → entity-level load | the browser names an entity type and an entity id |
| URL → resolver | the browser names a sub-path the server turns into a redirect target |
| login `redirectTo` → post-login redirect | a path carried through sign-in |
| token claim ↔ `public.grants` | the list is read through both; either can lag the other |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-173-28 | Elevation of privilege | insecure direct object reference through `[entityId]` | high | mitigate | the entity-level load refuses any `(type, id)` the caller's own served-filtered list does not hold, before reading; the read returns no row for an entity that is not the caller's; row-level security refuses the write whatever the UI does; five refusal cases, PROH-173-01 |
| T-173-29 | Information disclosure | an existence oracle on entity ids or types | medium | mitigate | not listed, unserved type, wrong type for the id, revoked and no row all give the same 307 to the app root, asserted equal; a malformed segment is a 404 before any load; no message is shown at the root |
| T-173-30 | Spoofing | an open redirect through the resolver or `redirectTo` | medium | mitigate | the resolver's target is built by `buildRoute` from a matcher-validated sub-path mapped to a route key and an entity of the caller's own list, never by joining strings; `redirectTo` still passes `safeRedirectTarget`, with two added cases |
| T-173-31 | Denial of service | a redirect loop between the root and an entity after a grant disappears | medium | mitigate | the user-level load tracks the two entity params, so both decisions use one freshly read list; the list function lists only what the read returns (173-02); one loop case |
