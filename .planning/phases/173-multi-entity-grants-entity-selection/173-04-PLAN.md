<objective>
Stage 2 (writer, types and store), part 2 of 2. Key the persisted draft by entity, reset the in-memory image
edit when the entity changes, give the store a way to let go of an entity without discarding its draft, make
logout clear every entity's draft, and close the stage (D-16; ruling O-Q5).

Purpose: today one fixed key holds the unsaved answers of whichever entity is loaded. The moment a user can
open a second entity, entity A's draft would overlay entity B and be saved to it. This plan removes that
before any route lets a user reach a second entity.

Output: one function added to the persisted-state module, the store re-keyed, new unit cases, and one run
of four gate rows (typecheck, lint, unit, svelte-check). No E2E run: 173-05's full run is the boundary
proof. The app still serves one entity through the old URLs.

## Rulings and deviations carried by this plan

1. **Ruling O-Q5.** The profile and question editors already ask "unsaved changes?" on any navigation and
   discard the draft on confirm. That prompt is left exactly as it is. D-16's "switching loses nothing" is
   delivered for the store: a draft survives a reload, a closed tab and a switch made from any page that
   raises no prompt. The E2E spec of 173-12 proves it through a reload.
2. **The key's stem changes** from the old fixed key to `contestantContext-userData-editedAnswers`, in the
   lower-case form of the context's three other keys, so the closing search for the old key can be empty
   (research P-17). A developer's browser keeps one orphaned key; nothing is deployed.
3. **No full E2E run closes this plan.** It closes on typecheck, lint, unit and svelte-check; the full run
   that closes 173-05 is its boundary proof, and that plan says which failures would point back here.
4. **`leaveEntity` is added here and first called in 173-07**, by the entity-level layout's teardown. Until
   then the store behaves as today between pages.
