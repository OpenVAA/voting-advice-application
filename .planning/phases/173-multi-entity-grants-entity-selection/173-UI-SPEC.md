# Phase 173 — UI Design Contract

> Visual and interaction contract for the five new or changed surfaces of Phase 173: screen H (entity
> selection), the entity switcher, the signed-in "nothing to edit" screen, current-entity indication, and
> the navigation split between user-level and entity-level pages. Generated by gsd-ui-researcher, verified
> by gsd-ui-checker.
>
> **This phase extends an existing, mature design system** — SvelteKit 2 + Svelte 5 runes, Tailwind 4 +
> DaisyUI 5, Inter, theme colours in `packages/app-shared/src/settings/staticSettings.ts`. The token
> sections below **document the established contract** the new surfaces obey; they introduce **no new
> token, font, spacing step, colour or component library**. The load-bearing content is in *Surface
> Contracts*, *Copywriting Contract*, *Locator Contract* and *UI Considerations*.
>
> **How to read the evidence marks.** `[tree]` = read on this worktree on 2026-10-06 (HEAD moved from
> `6449d46fd` to `1f58e6f46` while this was written; Phase 171 is executing). `[CONTEXT D-nn]` = a locked
> decision of `173-CONTEXT.md`. `[RESEARCH R-n]` = a finding of `173-RESEARCH.md`. `[172 plan]` = something
> Phase 172 is planned to leave and has not yet left — re-read the tree. `[U-nn]` = a decision taken in this
> document, listed for the operator at the end. Names of symbols this phase introduces are suggestions
> unless a `[CONTEXT]` mark fixes them; what they must do is the contract.

## Surface Contracts

### Shared premises

- **Three outcomes at the app root** `[CONTEXT D-08, D-11]`: zero served-filtered entities → the "nothing
  to edit" view; exactly one → a server redirect to that entity's home, H never painted; several → H. Both
  views are **views of the root page** (`contestant/(protected)/+page.svelte`), chosen from the root load's
  result; neither has a route of its own `[RESEARCH R-3.2]`. While a user-level gate is pending the layout
  renders the gate view instead and the root page renders nothing `[172 plan]`.
- **User-level versus entity-level.** A page is *entity-level* when its URL carries
  `[entityType]/[entityId]` (home, profile, questions, question, preview, settings). Every other contestant
  page is *user-level* (the root, Help, Privacy, and the signed-in password pages). This is decided from
  the URL, never from a list of page names.
- **Context accessors** `[CONTEXT D-17]` (names suggested by `[RESEARCH R-2.7, R-4.4]`): `contestantCtx.user`,
  `contestantCtx.entities`, `contestantCtx.selectedEntity` (the entry of `entities` matching the URL's two
  params, else `undefined`) and `contestantCtx.homeRoute` (the entity home when an entity is selected, else
  the root). All four are **reactive accessors: read as `contestantCtx.X`, never destructured**
  (`CLAUDE.md` § Context Destructuring Rule). They derive from page data, so they are correct on first
  paint and do not wait for the entity store.
- **Display name.** One string per entity, used by the card title, the sort order, the nav group title and
  the organization greeting: a candidate's formatted name as `@openvaa/data` formats it (`Candidate.name`),
  an organization's localized `name`. The nav title and the card title of the same entity must be the same
  string.
- **Vocabulary** `[U-01]`. The UI never says "entity". The user-facing noun for "the thing you edit" is
  **profile** — a word the app already uses for exactly that ("Your Profile", "Preview your profile") in
  all seven catalogues. A card's type is named with the existing `common.candidate.singular` /
  `common.organization.singular` ("candidate" / "party").

### S1 — Screen H: entity selection

**Route and layout.** `contestant/(protected)/+page.svelte`, view `select`. Frame: `MainContent` with
`title={t('contestantApp.entitySelection.title')}`. No `hero`, no `note`, no `primaryActions`, no
`heading` snippet (the default `<h1 tabindex="-1">` is the focus target) `[U-02]`.

**Background.** `base-300` for as long as the H view is shown, so the `base-100` cards have a surface to
stand on — the same pairing as the voter results list. Applied with the layout context's page-style overlay
scoped to the view: `$effect(() => { if (view is select) return pageStyles.push({ drawer: { background: 'bg-base-300' } }); })`
— `push` returns its own revert, so the background reverts when the root page shows the other view or is
left. It must **not** be applied with a page-level `pageStyles.use(...)`: that would also shade the
"nothing to edit" view, where a `prominent` (`base-300`) control would vanish `[U-02]`.

**Structure** (page-local markup; the grouping and sorting live in a pure, co-located helper with its own
test, in the mould of `contestantHome.helpers.ts`):

```
<MainContent title>
  <p class="text-center">                      ingress
  <div class="mt-lg gap-lg flex flex-col self-stretch"
       data-testid="contestant-entity-selection-list">
    loading  → <Loading />
    error    → <ErrorMessage inline />
    resolved → for each type group, candidates first:
      <section class="gap-md flex flex-col"
               data-testid="contestant-entity-selection-group"
               data-entity-type="candidate|organization"
               aria-labelledby={heading id, only when the heading is rendered}>
        <h2 class="mx-md text-lg" data-testid="contestant-entity-selection-group-heading">   only when BOTH types are present
        <EntityList cards={group.cards} />
      </section>
```

`self-stretch` is required: `MainContent`'s content column is `items-center`, so an unstretched list
shrinks to its content.

**Card.** `EntityCard` through `EntityList`, one card per entity the user may edit `[CONTEXT D-13, D-14]`:

| Card prop | Value | Why |
|-----------|-------|-----|
| `entity` | the `@openvaa/data` object from `ctx.dataRoot.getEntity(type, id)` | `EntityCard` takes a data object; H provides its own entities to the `DataRoot` `[RESEARCH R-4.3]` |
| `variant` | `'list'` | locked `[CONTEXT D-13]`; `'details'` is not clickable |
| `action` | the entity home URL (`getRoute.current({ route: <entity home key>, entityType, entityId })`) | a link: keyboard, screen reader, open-in-new-tab for free |
| `headerOnly` | `true` | see below |
| `showType` | `true` | see below |
| `keepScroll` | `false` | see below |

What a card shows: **avatar** (the image thumbnail; otherwise initials on the entity's colour, or on
`base-300` when it has none), **name** (`<h3>`), **type label** in the subtitle row. Nothing else: no
nomination, no election or constituency, no confirmed/unconfirmed status, no completion state, no match
score `[CONTEXT D-14]`. An unconfirmed entity renders exactly like a confirmed one.

**The three additive `EntityCard` props** `[U-03]` (`EntityCard.type.ts`):

```ts
  /**
   * Whether to render the card header only: avatar, title and subtitle. Featured questions, sub-matches and sub-cards are neither rendered nor looked up, so the card needs no question data. @default false
   */
  headerOnly?: boolean;
  /**
   * Whether to show the entity’s type, e.g. “candidate” or “party”, in the subtitle. @default false
   */
  showType?: boolean;
  /**
   * Whether a link action keeps the scroll position. Set to `false` when the action navigates to another page rather than opening an overlay over the list. @default true
   */
  keepScroll?: boolean;
```

- `headerOnly` must **skip the `getCardQuestions` call**, not hide its output: `DataRoot.getQuestion`
  throws for a question the root has not loaded, and the E2E base dataset's `results.cardContents.candidate`
  names one `[RESEARCH R-4.1, P-8]`. It stays a boolean beside `variant` because `variant="list"` is locked
  and Phase 177 can pass the same flag to its selector cards.
- `showType` renders `<span class="small-label" data-testid="entity-card-type">{t(`common.${type}.singular`)}</span>`
  as the first child of the existing `#…_subtitle` element, so the article's `aria-describedby` picks it up.
  Text only, no icon `[U-05]`. Not rendered for `variant="subcard"`.
- `keepScroll={false}` omits `data-sveltekit-noscroll` from the card's `<a>`. The attribute is hard-coded
  today because every existing URL action opens the results drawer over a list `[tree]`; H navigates to
  another page, and a user who scrolled a long list must land at the top of the entity home, where the
  focused `<h1>` is.

**Ordering and grouping** `[CONTEXT D-14]`. Candidates, then organizations. Inside a group, ascending by
display name with a locale-aware comparison (`localeCompare(other, locale, { sensitivity: 'base' })`), ties
broken by id so the order is deterministic. A group with no entity is not rendered. The `<h2>` group
heading (`ucFirst(t('common.candidate.plural'))` / `…organization.plural`, the strings the voter results
tabs use) is rendered **only when both types are present**; with one type the cards follow the ingress
directly and the type label on each card carries the type `[U-04]`.

**States.**

| State | What renders |
|-------|--------------|
| Gate pending | Nothing of H — the user-level layout shows the gate view at this URL `[172 plan]`. |
| Zero entities | Never H. The root shows the "nothing to edit" view (S3). An H with an empty list is a defect. |
| One entity | Never H. The server redirects before paint; no flash of the list. |
| Loading | Title and ingress render at once (server-rendered). The list region shows `Loading` until the entity objects resolve from the `DataRoot`. Entities are provided in an effect, so this is the state of the first client frame on every visit, including a return from an entity `[RESEARCH R-4.3, P-5]`. |
| Populated | The groups and cards above. |
| More than 50 | `EntityList`'s existing "show more" pagination (`itemsPerPage` default). No search, filter or sort controls. |
| Error | Entity objects cannot be resolved after provision → `ErrorMessage inline` in the list region; the frame, header and menu stay usable. A failed or malformed list read is not an H state: it is the `loginFailed` sign-out `[CONTEXT D-11]`. |
| Answers locked | No change on H. Cards still navigate; the lock warning is the entity home's. |
| Arrived by a refused entity URL | H renders as usual, with **no notice** — nothing may reveal whether the refused id exists `[CONTEXT D-10]`. |

**Responsive.** Mobile first. One column at every width: `MainContent`'s `max-w-xl` (36rem) column, full
width below it with the frame's safe-area padding. Cards are full-width rows; the whole card is the tap
target (at least 82px tall: 50px avatar plus 2 × 16px padding). No horizontal scroll at 320px. Nothing
changes at larger breakpoints except the column centring.

**Accessibility.**

- Landmarks: the existing `<header>`, `<main id="mainContent">`, `<nav>`; H adds none.
- Headings: `<h1>` page title → `<h2>` group heading (only with both types) → `<h3>` card title. With one
  type the outline is `<h1>` → `<h3>`, the same shape as the voter results list.
- Focus order: skip link, header controls, then the cards in visual order (candidates A–Z, organizations
  A–Z), then a "show more" button if there is one. Each card is one tab stop.
- Card accessible name: computed from the link's content, so it contains the display name and the type
  label. No `aria-label` is added (it would replace, not extend, the content).
- Focus after arriving on H (sign-in, switch, refused URL, browser back): the `<h1>`, by the root layout's
  `afterNavigate` → `focusNavigationTarget()` with `preventScroll`; the route announcer speaks the title.
- Focus after picking a card: the entity home's `<h1>`, announced by its title, which names the entity
  (S4). The page is at scroll position 0.
- Keyboard focus on a card must be visibly indicated in both themes (browser focus outline on the link;
  no outline is removed).
- Target size: every card, nav item and button is at least 44 × 44px.
- Motion: no animation is added. The card's existing `transition-shadow` hover is not motion.

### S2 — The entity switcher

**What it is** `[CONTEXT D-15]`. A navigation-menu item, a plain link to the app root. A multi-entity user
is never redirected away from the root, so the link always lands on H `[CONTEXT D-08]`. There is no header
control, no dropdown, no in-page switcher, and no addition to the home screen.

**Where.** The **last item of the entity group** of `ContestantNav`, after Settings `[U-06]`:

```svelte
<NavItem
  href={getRoute.current('ContestantAppHome')}
  icon="list"
  text={t('contestantApp.entitySelection.switch')}
  data-testid="contestant-nav-switch-entity" />
```

**When.** Rendered only when `contestantCtx.selectedEntity` is set **and** `contestantCtx.entities.length > 1`.

| User | On entity-level pages | On user-level pages |
|------|-----------------------|---------------------|
| One entity | No switch item. The menu is the same list of items as today. | No switch item. |
| Several entities | The switch item, last in the entity group. | No switch item: the home item already links to the root, which is H. Two links to one place under two names would be noise. |
| No entity | — (cannot reach one) | No switch item. |

**What it shows about the current entity.** Nothing itself. The entity group's title, directly above the
group's items, names it (S4).

**Unsaved edits on a switch** `[CONTEXT D-16]` `[RESEARCH R-4.6]` `[U-13]`. The switch adds **no prompt and
no copy of its own**.

| Leaving from | What happens |
|--------------|--------------|
| Home, questions overview, preview, settings | Navigates to H at once. Nothing is lost: the persisted draft is keyed by entity and stays stored. |
| Profile editor or question editor, no unsaved edit | Navigates to H at once. |
| Profile editor or question editor, with an unsaved edit | The existing `PreventNavigation` native confirm, unchanged (`components.preventNavigation.unsavedChanges`). Cancel → the user stays; the drawer has already closed and focus is on the menu button. Confirm → the page's existing handler discards the edit and the navigation continues. This is what every link out of those two pages does today. |

After a switch every page shows the newly selected entity's saved data and that entity's own draft, never
the previous entity's; an in-memory image edit does not survive the change. Returning to an entity whose
persisted draft survived (a reload, a closed tab) shows the existing unsaved state of the editor — no new
"draft restored" notice is added.

**Accessibility.** Accessible name: the item's text, "Switch profile". It sits in the list labelled by the
group title, so a screen reader hears it in the context of the entity it switches away from. After
activation: the drawer closes, the navigation runs, focus moves to H's `<h1>` and the route announcer
speaks H's title. Target: `NavItem` is `min-h-touch`.

### S3 — The "nothing to edit" screen

**Condition.** The served-filtered entity list is empty `[CONTEXT D-11]`. The user is **signed in and stays
signed in**.

**Where.** View `nothingToEdit` of the root page. The page renders `<NothingToEdit />` and nothing else.

**`NothingToEdit`** — a full-view component that renders its own `MainContent`, in the mould of Phase 172's
gate view `[172 plan]`, so that Phase 178 can show the identical screen with one tag `[U-10]`.

```ts
// NothingToEdit.type.ts
import type { Snippet } from 'svelte';

export type NothingToEditProps = {
  /**
   * The page title. @default t('contestantApp.nothingToEdit.title')
   */
  title?: string;
  /**
   * Replaces the default explanation, e.g. to give another reason the user has nothing to edit.
   */
  children?: Snippet;
};
```

It reads the signed-in email from `contestantCtx.user?.email` (never a prop, never destructured).

**Structure.**

```
<MainContent title data-testid="contestant-nothing-to-edit">        default <h1>; no hero, no note
  <p class="text-center">                                            explanation (or `children`)
  <dl class="my-lg text-center">                                     omitted entirely when there is no email
    <dt class="small-label">                                         "Signed in as"
    <dd class="font-bold hyphens-none [overflow-wrap:anywhere]"
        translate="no" data-testid="contestant-nothing-to-edit-email">   the email, verbatim
  <p class="text-center">                                            next steps
  {#snippet primaryActions()}
    <ContactSupport variant="main" />
    <LogoutButton variant="normal" icon={undefined}
                  data-testid="contestant-nothing-to-edit-logout" />
```

- The email is a label/value pair rather than a sentence with a placeholder, so it needs no word order and
  can be emphasised without HTML in a message. `hyphens-none` is load-bearing: `html` is `hyphens-auto`,
  and a hyphen inserted into an address would misstate it.
- Background: the default `base-100`. No `pageStyles` overlay.
- No hero emoji: the screen is not an error, and the home screen that shares this URL has none in its
  ordinary state `[U-10]`.
- Actions sit in `primaryActions` (bottom of the viewport on a phone, as on home): **Contact support** is
  the one `main` button; **Log Out** is the same call as home's (`variant="normal"`, warning-coloured label,
  no icon). The header's logout icon is also present, as on every signed-in contestant page.
- No other route into the protected pages is offered `[CONTEXT D-11]`. The menu shows the user-level items
  only (S5).

**`ContactSupport`** — the reusable support block `[U-11]`.

   presses Home lands on H and picks again. The selection lives in the URL and is not remembered

## View Transitions

`CLAUDE.md` § Results Navigation Invariants: *a document View Transition must never run with names while a
modal is open.*

- **The new screens add no `view-transition-name`.** Not on a card, a group, the email, or the nav.
- They inherit the two standing names: `main-content` (the root element of `MainContent`) and
  `persistent-header` (`Header`). Root ↔ entity and entity ↔ entity navigations are ordinary document
  transitions carrying those two names, subject to `shouldAnimate` (no transition under
  `prefers-reduced-motion`, plus the stylesheet's `animation: none`).
- **How the rule is respected.** By the one global mechanism, untouched: `startViewTransition` in
  `apps/frontend/src/lib/utils/viewTransition.ts` strips every name (`html.vt-no-names`, `!important`)
  whenever a `dialog[open]` exists. The only modal reachable from these surfaces is `LogoutButton`'s timed
  modal, and the logout navigation it triggers is covered by that gate. The unsaved-changes prompt is a
  native `window.confirm`, not a `<dialog>`; the nav drawer is a DaisyUI drawer, not a top-layer dialog.
- **No overlay is introduced.** `isOverlayNavigation` keys on the route params `entity` + `id`. The
  contestant entity params are `entityType` + `entityId` `[CONTEXT D-07]` and must keep those names: named
  `entity` and `id`, every contestant navigation would be classed as an overlay navigation and silently
  lose its transition.
- The `(located)` half of the invariant has a contestant twin in this phase — the user-level and
  entity-level loads read no `url` property tracked `[CONTEXT O-4]`. It is a load contract, not a visual
  one; it is listed under *UI Considerations* because its failure is visible (a loading flash on every
  question).
