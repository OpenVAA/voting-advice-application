## Rulings and deviations carried by this plan

1. **Orchestrator ruling 3 — S1 is chosen.** The server builds a data root in the preview's load — two more reads, the elections and the constituencies, on a navigation to the preview and on no other — and calls the same rollup, the same filters and the same predicate the context calls. **Why not S2:** a pure function over the raw rows would write the applicability of a category and of a question a second time, and Phase 177 changes which questions follow a nomination; two statements of that rule would then have to move together, held only by a parity test. S1's cost is paid on one page that is opened rarely.
   **Planner assumption A-S1:** *a `DataRoot` can be built in a server load from the provider's election, constituency and question data, and resolves the nominations' elections.* **What falsifies it:** the helper's unit cases failing to construct the root, or the `preview:` tests red for a reason inside the helper. **What happens then:** S2 — a pure function over the raw rows with `match` from `@openvaa/data` — with a parity test, mandatory, that runs one table of fixtures through it and through the rollup; the summary says so.
2. **U-03 stands at its recommended option** (orchestrator ruling 1; it departs from no locked text and is listed, unticked when these plans were revised, under item D1 of the operator's decision document): "both filled" is a nomination, no unanswered required info question and no unanswered opinion question; the name does not count.
3. **Research assumptions A1 and A8.** A1 is tested by the `holds:` test that saves the last answer in the browser and clicks Preview. A8 — a hosted database reading its own write at once — is not testable here and nothing is deployed; it is recorded for the deployment milestone.
4. **What stays stale, by design** (research RQ-1 (d); UI contract S7): the browser's copy of the entity's data is that of its last load. Nothing here invalidates it. The second `preview:` test uses exactly that: it changes the database behind a loaded page and clicks.
5. **The refusal of a navigation inside the application is asserted through an entry the browser still shows open**, not through an entry of an entity whose preview the browser knows to be closed. Plans 176-15 and 176-16 turn a closed entry into a disabled button with no link target, which cannot be clicked; an entry made stale by a write behind the page stays a link under every rendering, so the assertion is written once and stands.
6. **A server-only module that builds a data root is new to this codebase.** A data root holds every object it was given; one kept at module scope would answer the next request from this one's rows. PROH-176-53, T-176-76 and a unit case pin that nothing outlives a call.
7. **Phase 175's spec changes here, and only in its state.** Its tests that open a preview keep every assertion; each gains, after the state step it begins with, a step that writes the answers the preview's rule asks for. That step is new on Phase 175's composition root and removes nothing.
8. **Nothing restores what `completeAnswers` writes, and that is that spec's own convention, not an omission.** As the spec stands (`<tree_facts>`), a test that needs an answer missing removes it in its own first step, and no test reads an answer's absence that it did not write; so an answer added by one test changes nothing a later test asserts, and the callers of `completeAnswers` restore nothing. That reading is of one commit, and the spec has changed twice since these plans were first written: Task 1's step 2 makes it again on the spec as it then stands, and where it finds a test that reads an absence it does not write, that test gets the `clearAnswers` it needs — the convention kept, and no `afterEach` added. The pre-commit run executes the spec whole, in file order, with every added answer in place.
