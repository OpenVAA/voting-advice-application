<ordering_hazard>
## ⚠ The one thing that must not happen — D-06a, the REPLACE trap, second occurrence

**`packages/shared-config/eslint.config.mjs:79-85` already sets `no-restricted-syntax`**, banning
`TSEnumDeclaration` with the message *"Use const assertion or a string union type instead."* ESLint flat
config **replaces** a rule's option array rather than merging it. Adding D-06's `ImportExpression`
selector as a fresh single-entry array therefore **silently deletes the enum ban for every file under
`apps/frontend/src/**`**.

What makes this plan-breaking rather than merely wrong: **there are zero enums in the frontend today**,
so the deletion produces **zero new errors**. `yarn lint:check` stays green. `yarn build` stays green.
`yarn test:unit` stays green. The regression ships invisibly and surfaces months later as *"someone
added an enum and nothing stopped them"*.

This is the **second** occurrence of a trap this same config file already documents for
`no-restricted-imports`, whose `patterns` array re-includes the inherited deep-relative-`lib` ban
verbatim for exactly this reason. The mitigation is the same artifact shape at the new site.

**Non-negotiable:**
1. The shipped array carries **both** entries — `TSEnumDeclaration` copied **verbatim** from
   shared-config, and `ImportExpression[source.value='svelte/store']`.
2. A **standing** matrix case in the guard spec asserts the inherited ban still fires. Not a one-time
   `--print-config` assertion: a standing case is the only mechanism that catches a recurrence.
3. That case gets its **own two-run control** (Task 3): observed RED against the naive single-entry
   patch, then GREEN against the shipped two-entry one. A case that has never been seen failing is
   exactly the fake guard this milestone exists to eliminate.

**Task order below is therefore not a stylistic preference:**
`Task 1 (config, both entries)` → `Task 2 (spec rewrite incl. the enum case)` →
`Task 3 (SC-9 two-run control)` → `Task 4 (NEW halves)` → `Task 5 (record corrections)`.

**No commit in this plan may contain a single-entry `no-restricted-syntax` array.** If a mid-task
interruption leaves the naive patch on disk, the correct recovery is to restore the two-entry array,
never to delete the enum case that is reddening.
</ordering_hazard>

  the D-05 glob widening's fallout on the inherited deep-relative-`lib` `patterns` ban, which research
  predicts at zero but which D-05 explicitly forbids assuming.

**vitest**, not the lint gate:

- `E-OLD` — with the naive single-entry patch applied, the enum case must go **RED**. That red proves

  the same naive patch stays **exit 0 with zero errors** — that is the invisibility this whole hazard
  is about, and it belongs in the record.

  the proof the inherited ban survived.

An executor pattern-matching on "green is good" will read a correct SC-9 control as a regression and

unguarded.
