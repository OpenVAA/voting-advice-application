<gate_preconditions>
## ⚠ Nothing in this plan may run until `143-02`'s last revert and last post-gate

Three independent reasons, all measured:

1. **The unit gate.** `turbo.json` declares `test:unit` with `dependsOn: ["build"]`. A root
   `turbo run test:unit` taken while an injection is live would build the injected tree and hand it to
   every dependent — whole-suite contamination, not per-file collateral.
2. **The lint gate.** A live `__store_guard_inject__*` fixture reds gate 2 for a manufactured reason,
   and the short-circuit then hides gates the chain would otherwise have run.
3. **The E2E gate.** A suite run overlapping an injection window or the Task-3 naive config patch would
   go red for a manufactured reason. This is 139 § 3.1's standing prohibition, carried verbatim.

**Entry check, before Task 1's first command:**

```bash
git status --porcelain -- apps packages tests                 # MUST print nothing
find apps/frontend/src -name '__store_guard_inject__*'        # MUST print nothing
git diff --exit-code HEAD -- apps/frontend/
grep -c 'TSEnumDeclaration' apps/frontend/eslint.config.mjs   # MUST be 1 — the naive patch is not on disk
git hash-object apps/frontend/eslint.config.mjs               # MUST equal the ledger's Post-change restoration target
```

**Cache handling differs per gate and is not uniform.** `turbo.json` sets `"cache": false` on
`test:unit`, so gate 1 is always a real run and needs no flag. It does **not** set it on `lint`, so
**gate 2 runs `TURBO_FORCE=true`** like every other lint measurement in this phase. Gate 4's build cache
is harmless — a cached build of an unchanged tree is the correct answer.

⚠ **`apps/frontend/tsconfig.tsbuildinfo` is a tracked generated artifact.** Prefer
`yarn workspace @openvaa/frontend check` over a bare `npx tsc --noEmit`: the latter rewrites that file
and dirties the tree mid-protocol. If it is dirtied anyway, restore it with `git checkout HEAD --` and
say so in the SUMMARY rather than committing it.
</gate_preconditions>
