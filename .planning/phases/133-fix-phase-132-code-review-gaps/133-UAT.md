### 1. Loud-failure path fires when the Continue button genuinely never advances (WR-01)

steps: |
  Deliberately break the elections or constituencies Continue button so it never advances
  (e.g. stub the click handler, or disable the route it targets), then run a voter journey
  through `navigateToFirstQuestion` — or any perm spec that uses it
  (perm-hide-election-tags / perm-hide-category-tags / perm-hide-if-missing-answers /
  perm-disable-allow-open).
expected: |
  The run FAILS with a Playwright timeout and NO `page.goto()` redirect occurs. The journey must
  not silently complete. The failure surfaces differently depending on how you break the button —
  BOTH are a PASS:

  (a) Click no-ops (button renders, click does nothing) — the case WR-01 actually targets.
      Budget ~10 x 5 s + 5 s = ~55 s, inside the 90 s `TIMEOUTS.testMax` ceiling, so the loop DOES
      exhaust `maxSteps` and fails at the terminal `stopAt` wait — `answerOption.waitFor` /
      `questionsStart.waitFor` / `categoryStart.waitFor`, whichever `stopAt` applies.

  (b) Button never renders. Each iteration burns the full `TIMEOUTS.slowPage` (10 s), so
      10 x 10 s = 100 s exceeds the 90 s ceiling: the test is killed inside iteration 9's
      `waitFor` and the terminal `stopAt` wait is never reached. Expect
      `waiting for getByTestId('voter-elections-continue') to be visible`. This is still a loud,
      correct failure (arguably more diagnostic) — see 133-REVIEW.md WR-01, which notes the
      in-code comment describing `maxSteps` as the binding constraint is wrong for this case.
why_human: |
  No automated test in this phase — including the 3x full-suite gate — deliberately breaks the
  Continue button to exercise the loud-failure path. The three green runs only exercised the
  happy path (Continue always eventually succeeded, sometimes after a transient stall-then-retry).
  The terminal `waitFor` block is pre-existing, unchanged code that this phase's diff did not
  touch, so its correctness is a strong logical inference from static reading — but grep and
  wiring checks cannot observe runtime failure-path behavior. Only a deliberately-broken build
  or a dedicated regression test can confirm it.
