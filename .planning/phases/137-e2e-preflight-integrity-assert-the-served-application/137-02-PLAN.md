<objective>
Make the escape hatch real, close the drift at source, and remove the competing half-check.

Three edits, all small, all consequential, in a deliberate order.

**First, D-16.** `apps/frontend/vite.config.ts` reads `FRONTEND_PORT` through Vite's `loadEnv` with
`envDir` at the repo root, so a value in the root `.env` actually moves the dev server. Today it does
not: the config reads `process.env` at config-evaluation time and nothing loads the root `.env` into
the frontend's process env, so `.env` moves Playwright's `baseURL` and nothing else. That makes the
"legitimate escape hatch" D-07 and D-15 both rest on only half-wired — measured as RESEARCH QUAL-2.
This task dissolves the finding rather than documenting around it. Precedence is verified, not
assumed: `loadEnv` parses the `.env` files, filters by prefix, then overlays `process.env` last
(`node_modules/vite/dist/node/chunks/config.js:9379`), so the shell still beats `.env` and the
one-off `FRONTEND_PORT=<port> yarn dev` override keeps working.

**Then D-08.** `strictPort: true` turns the silent same-address port drift — the measured mechanism
of the original incident — into a loud bind failure. It is gated behind the `checkpoint:decision`
CONTEXT.md D-08 mandates, because it alters shared developer workflow. D-16 is deliberately
sequenced BEFORE it and is deliberately NOT behind that gate: D-16 is a correctness fix with no
ergonomic downside and lands regardless of how the operator rules, and once `.env` genuinely sets the
dev-server port, choosing a persistent alternate port becomes a one-line edit — which is exactly what
makes a loud failure on a contended 5173 cheap to live with. The checkpoint says so, so the operator
decides with that in view.

**Then D-05.** Deleting CI's two blind, fail-open `curl` wait loops leaves exactly one readiness
mechanism, the preflight built in plan 01.

The default port stays 5173; moving it is explicitly deferred (D-10).

An honest qualification the plan carries throughout, per RESEARCH QUAL-1: `strictPort` closes
**same-address drift** and was measured doing so. It does NOT close the **wildcard shadow-bind**,
where a process holding `*:5173` lets Vite additionally bind `[::1]:5173` with no `EADDRINUSE` at
all — measured live on this machine with `--strictPort` in effect. The preflight is what closes
that. Nothing in this plan may claim `strictPort` "prevents the cause" unqualified.

Purpose: after this plan, an alternate port is a one-line configuration rather than a per-command
ritual, and a port collision is either refused at bind time or caught at preflight time — never
absorbed silently.
Output: a reworked `server` block plus the `loadEnv` conversion in `apps/frontend/vite.config.ts`;
two deleted steps in `.github/workflows/main.yaml`.
</objective>

**What changes today.** `apps/frontend/vite.config.ts:24-26` sets `port` with no `strictPort`. When
5173 is already held by a same-address listener, Vite prints `Port 5173 is in use, trying another
one...`, serves on 5174, and exits 0 — while Playwright's `baseURL` keeps pointing at 5173. That
drift is the measured mechanism of the original incident (finding F6; reproduced live as RESEARCH
§R5.2 test A2).

**What changes after.** The same situation produces `error when starting dev server: Error: Port 5173
is already in use` and the process EXITS (§R5.2 test B2, measured). Every contributor whose 5173 is
occupied must either free it or move to a different port.

**Decide this with task 1 in view — that is why it is sequenced first.** Before task 1, moving to a
different port meant remembering to prefix two separate commands every session, because the root
`.env` moved Playwright's target and never moved the dev server. Task 1 (D-16) fixes that: one
`FRONTEND_PORT` line in the root `.env` now sets the port for the dev server AND for Playwright,
persistently — while a one-off `FRONTEND_PORT=<port> yarn dev` prefix still overrides it, because
`loadEnv` overlays the process environment last (verified at
`node_modules/vite/dist/node/chunks/config.js:9379`). That materially lowers the cost of this
decision: a contributor with a permanently contended 5173 edits one line once, rather than adapting
their muscle memory to a hard failure. Task 1 lands regardless of how you rule here.

**What does NOT change.** With `FRONTEND_PORT` set in neither the root `.env` nor the shell,
`yarn dev` still binds 5173 — task 1 keeps an explicit `|| 5173` fallback, and the prior `NaN` path
was independently measured safe alongside `strictPort` anyway (§R5.2 tests D/E, tested precisely
because it was the obvious way this could break every developer's `yarn dev`). `vite preview` and the
production `adapter-node` container are unaffected — `server.strictPort` does not apply to either
(§R5.1).

**Honest limitation.** This does NOT catch the wildcard shadow-bind. Measured on this machine right
now: Docker Desktop holds `*:5173`, macOS permits Vite to additionally bind `[::1]:5173`, and Vite

`curl 127.0.0.1:5173` reaches the foreign one, and no `EADDRINUSE` ever occurs (QUAL-1). Only the
preflight catches that case.
