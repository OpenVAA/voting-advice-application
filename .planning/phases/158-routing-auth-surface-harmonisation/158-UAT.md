expected: The opt-in `PLAYWRIGHT_BANK_AUTH` suite (`bank-auth`, `bank-auth-journey`
projects) passes against a live mock OIDC issuer, per `tests/IDURA-TEST-RUNBOOK.md`.
The authorize → callback → token-exchange → session-cookie chain completes and the
candidate lands authenticated.

why a human: needs the mock OIDC issuer stood up plus the frontend's own IdP-pointing
env — operator/deployment-environment responsibility, unavailable to an agent. No static
check substitutes for a live external-IdP round trip.

what changed under it, and why it matters: 158-03 rewrote four cookie names across 17–18
sites; 158-06 moved the candidate auth callback and logout to `/api/candidate/auth/*`.
Both touch exactly the surface this flow uses.

what IS proven (and was re-proven live during verification): the static byte-identity
proof over the rewrite diff; `yarn assert:cookie-names` scanning 783 files with 0
violations and **failing at exit 1 on a planted literal**, naming file and line; six
negative controls; unit coverage of the individual read/write sites.

what is NOT proven: that the live handshake completes with the renamed cookies at the
moved endpoints. The guard firing is not the round trip.

operational note: these specs join the tail of the perm serial chain and perform an
authoritative `app_settings` REPLACE against the target database.

result: [deferred — accepted as tracked follow-up 2026-09-02]

### 2. The in-app forgot-password PKCE `?code=` branch

expected: Either the flow is fixed to accept both PKCE forms, or it is formally accepted
as a pre-existing, phase-158-independent defect.

why a human: this is a disposition decision, not a measurement. The measurement is already
done and reproduced twice.

what was measured: following a *real* recovery mail (not a generated `token_hash`), the
PKCE verify hands the callback `?code=`, which the handler never reads — it reads only
`?token_hash=` — so the flow lands on the login error page. 158-06 found it; the verifier
reproduced it by reading the callback handler.

why it is not a phase-158 defect: it predates the route move and reproduces on the
pre-move path. The suite cannot see it because `toCallbackUrl` bypasses the verify
redirect. The obvious fix does not work — the `code_verifier` lives in browser storage,
unreachable from the server client — so the remedy is architectural, which is why 158-06
filed it rather than guessing at it.

already filed: `WINDOWS.md` row 219, and
`.planning/todos/pending/2026-09-02-forgot-password-pkce-code-not-exchanged.md`.

result: [deferred — accepted as tracked follow-up 2026-09-02]
