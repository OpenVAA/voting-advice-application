<objective>
Convert `Alert.svelte`'s two ad-hoc spacing values to design-system classes per D-H6, which chose BOTH
values rather than only the one the roadmap names.

Purpose: this project deliberately cleared Tailwind's default spacing scale and redefined it in
`app.css` to enforce a restrictive design system; a bracketed arbitrary value bypasses that system and
is the actual defect. The second site is subtler and is why this plan has a checkpoint: the value the
reviewer flagged is already a project theme token, and the named token the reviewer suggested resolves
to four times its length, which would violate D-H6's own requirement that the rendering not change
perceptibly. That conflict is an operator decision.

Output: `Alert.svelte` with the arbitrary value replaced by its exact-equivalent token, and the second
site resolved per the operator's answer.
</objective>

  <decision>Does the close-button offset pair at Alert.svelte:117 change to the named token the reviewer suggested, accepting a rendering change, or stay as it is with the reason recorded?</decision>
  <context>
    D-H6 says convert both ad-hoc spacing values to the closest semantic classes, AND that the rendering
    must not change perceptibly. At this one site those two clauses conflict, and the conflict is only
    visible once the project's actual spacing scale is in view.

    This project clears the framework's default spacing scale in `app.css` and redefines its own. Under
    that scale the numeric token at the flagged site resolves to 0.125rem, which is 2px. The named token
    the reviewer suggested resolves to 0.5rem, which is 8px — four times the current value. There is no
    named token at 0.125rem; the nearest named one is 0.25rem, still double. So the flagged pair is
    already a project theme token, not an arbitrary value, and every named alternative changes the
    rendering.

    It is also not Alert-local. The identical close-button class string appears verbatim at
    `Video.svelte:858`, `Modal.svelte:100` and `Drawer.svelte:90` — a four-site house idiom rather than a
    one-file defect. Changing only Alert would create a four-way inconsistency where none exists today.

    The margin site at `:114` is NOT part of this question. It is a genuine bracketed arbitrary value, an
    exact-equivalent theme token exists for it, and Task 2 applies that unconditionally under either
    answer here.
  </context>
  <options>
    <option id="keep-and-record">
      <name>Keep the offset pair and record why (recommended)</name>
      <pros>Rendering is provably unchanged, honouring D-H6's own constraint. No baseline churn. The four-site idiom stays consistent. The recorded comment answers the reviewer's point permanently rather than leaving it to be re-raised.</pros>
      <cons>The literal text of the reviewer's suggestion is not applied, so a reader comparing the review comment to the diff sees a divergence — which is why the reason must be recorded in the file, not only in a summary.</cons>

    </option>
