## 1. Criterion 1, and why this artifact exists

ROADMAP Phase 159 success criterion 1, quoted verbatim:

> 1. The `$effect` calls at `PasswordSetter.svelte:55` are converted to `$derived` where the value is
>    a pure function of its inputs, and **every other `$effect` in the frontend is audited against the
>    same test** with the disposition recorded per site - a census, not a spot fix.

An audit "against the same test" is only meaningful if the test is one test. A census of 90 sites
written by hand is 90 judgement calls, each defensible in isolation and none reproducible
together, which is exactly what `159-CONTEXT.md` open item O5 bullet 1 warned about:

> Define it in the plan, in one sentence, and apply it uniformly - otherwise the census's
> dispositions are judgement calls.

So the predicate is stated once, as executable code, and the table is generated from it. A reviewer
who doubts a row re-runs the script rather than re-deriving the claim; a later phase that adds an
effect re-runs it and gets a new table. That is the difference between a census and a snapshot of
one person's reading.

The classifier is committed alongside this document at
`.planning/phases/159-component-context-consolidation/classify-effects.mjs`. It is deliberately NOT
under `apps/frontend/src`, so it can never be collected by the frontend unit suite and can never move
the test-file count that Phase 153's gate pins.

## 2. The predicate, and the precedence order that makes buckets exclusive

Quoted verbatim from `159-RESEARCH.md` section "Census Mechanics", and quoted again in the script's
own header so the census's uniformity is inspectable rather than asserted:

> A site is CONVERTIBLE iff, on every execution path through its body, it performs exactly one
> assignment, to exactly one target, where that target is a plain local `$state` binding declared in
> the same module (not a prop, not a member expression on another object), and the body contains no
> `untrack`, no returned cleanup function, no `await`/`async`/`.then`, no navigation call, and no DOM
> access.

A body can satisfy several bucket tests at once, so the buckets are made mutually exclusive by a
precedence order declared at the top of the script. The first match wins. No site can be double
counted, and no total can drift on a tie:

1. DOC COMMENT (not a runtime site)
2. NO ASSIGNMENT (call-only side effect)
3. TEARDOWN (returns cleanup fn)
4. ASYNC
5. UNTRACK (read/write same state)
6. NAV
7. DOM
8. WRITES $bindable PROP
9. WRITES MEMBER / EXTERNAL OBJECT
10. MULTI-TARGET
11. CONDITIONAL SINGLE-TARGET (not total)
12. NON-LOCAL / NON-$STATE TARGET
13. SECOND WRITER IN MODULE (operational)
14. CHILD TWO-WAY BINDING (operational)
15. CONVERTIBLE

Two properties of that order are worth stating because they explain why these bucket counts differ
from the fourteen-bucket table `159-RESEARCH.md` published against an earlier tree.

**Bucket 2 sits above the disqualifier buckets deliberately.** A body containing zero assignments is
a first-class census input - it is the largest bucket here and the most ordinary thing an effect
does - so it is classified as call-only even when it also returns a cleanup or navigates. That is
why TEARDOWN, NAV and DOM are near-empty here where RESEARCH reported seven, three and one.

**"No assignment" means none anywhere in the body, nested callbacks included.** An effect whose only
write sits inside `untrack(() => { ... })` is therefore filed under UNTRACK, not under call-only.
Depth still decides TOTALITY - an assignment counts as total only at brace depth 0 and paren depth 0
and not as the single statement of a brace-less `if` - but depth does not decide existence.

Buckets 13 and 14 are OPERATIONAL. They record facts about reactive safety that no reading of the
effect body can produce: a second writer elsewhere in the module, and a target a child writes back
through a two-way binding. A site in either bucket PASSES the mechanical predicate and is still
recorded rather than converted. The script marks them by a stated heuristic and flags them for
section 7 rather than deciding them silently.

**The two file numbers are different numbers and must not be swapped.** 54 files hold the
90 census sites. 88 files contain some `$effect` token: that larger figure is a
SUPERSET and is NOT the census population, because it also counts the 16 files whose only
token is `$effect.root(` plus files where the token appears only in a comment or a type position.

Two further facts, measured the same way. `$effect.pre(` returns 0 - the form does not appear in this
tree at all. And of the 90 sites, 0 are in `*.test.*` files, so the census is
entirely production surface.

**Concentration is low and reproduces the qualitative claim the discussion document made.** The
heaviest files hold 5 each - `lib/contexts/voter/voterContext.svelte.ts` and `routes/+layout.svelte`
tie - then three files at 3.

**Why the live number is not the base number.** The census population MOVES within this phase's own
execution. Plan 159-02 removed one net effect from `PasswordSetter.svelte` when it converted the
component's two bindable outputs to derived values behind one callback, taking the population from 91
to 90. That is why this document asserts an EQUALITY - the classifier's row count equals the
criterion's own grep re-run at generation time - rather than a frozen literal. The literal was only
ever the equality's proxy.

## 8. The conversions this phase made, and why they are absent from the table

Criterion 1's conversion set is exactly two sites. Neither appears in section 5, and their absence is
correct rather than an omission: **converting an effect to a derived deletes the effect**, so a
converted site is no longer an `$effect(` occurrence and cannot be a row in a census of `$effect(`
occurrences. This is also why no row's disposition reads `CONVERTED`.

## 9. Claude's Discretion under D-H1: the script is committed

D-H1 requires only that the TABLE be committed; whether the classification script is a throwaway or
an artifact is explicitly Claude's Discretion, and `159-RESEARCH.md` recommended committing it. It is
committed, for three reasons.

**The census is a claim about 90 sites.** Without the script a reviewer who doubts one row has to
re-derive the predicate and re-apply it by hand. With it, they re-run one command.

**The population moves.** Any later phase that adds or removes an effect invalidates this table. A
committed script makes regenerating it a command rather than a project.

**The predicate is only uniform if it is executable.** A predicate written in prose and applied by
hand is 90 readings of a sentence. The whole point of O5 bullet 1 is that those readings differ.

The one constraint the placement carries: the script lives under the phase directory and never under
`apps/frontend/src`, so it cannot be collected by the frontend unit suite and cannot move the
test-file count. Verified: `ls apps/frontend/src/**/classify-effects.mjs` matches nothing, and
`yarn workspace @openvaa/frontend test:unit` reports 85 files / 1564 tests, unchanged from the count
`159-05-SUMMARY.md` recorded at the preceding commit.
