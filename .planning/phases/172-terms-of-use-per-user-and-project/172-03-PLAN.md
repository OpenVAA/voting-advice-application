## Deviations from CONTEXT.md for operator review

1. **D-05's upsert is issued through a new `upsert` member on the guarded `scopedFrom` helper**, which always
   sends ignore-duplicates, and the table joins `PROJECT_SCOPED_TABLES` and the `ProjectScopedTable` union.
   D-05 names the upsert but not the helper change. D-05's fallback (a plain insert treating the unique
   violation as success) is not used: research measured that the upsert works under the column grant.
2. **D-06: a failed acceptance read yields `null` and is logged; it does not throw.** The gate then shows for
   that user, and accepting again is harmless because the write is idempotent. A throw would also fail the
   Admin app's `getBasicUserData` callers, which have no use for this field.
3. **D-06 cost, accepted:** every `getBasicUserData` caller pays one more read (the Admin identity check, two
   Admin page actions, `getUserData`), and a protected contestant load runs it twice, because the entity read
   calls `_getBasicUserData` itself. Phase 173 reshapes that call.
4. **Open point, not changed here (D-06 against the 178-B1 note):** acceptance stays a table read, exposed as
   `BasicUserData.termsOfUseAccepted`, so Phase 178's "password set" fact can sit beside it whatever its
   source. If the operator wants one RPC to carry every user-level fact, that is a change to D-06 and is best
   said before this plan runs.
