1. **D-20 says "three plans"; the phase is delivered as three stages in nine plan files** (01–04 expand,
   05–07 contract, 08–09 close). The reason is the executor's context budget, not scope: each stage still
   closes on the full static gate set and a full E2E run, the column still survives stage 1 unread, and a
   failure in stage 2 is still attributable to the removal alone. Full E2E runs close 172-01 (the baseline),
   03, 04, 06, 07, 08 and 09. 172-02 and 172-05 close on their own targeted gates (172-02 also on the slice
   of the suite its fixtures feed), and each names the next plan's full run as its boundary proof.
2. **D-05: `REVOKE ALL … FROM anon, authenticated, public` precedes the two grants.** D-05 does not mention
   it. The default ACL gives both API roles ALL on a new public table, so without the revoke the column-level
   INSERT grant constrains nothing (RESEARCH H-4).

   policies that ask no authority question. That list is a security surface. The entries are added only if
   check 9001 is observed to report the two policies on the applied schema, and each carries its reason.
4. **An index on `project_id` is added** (`idx_terms_of_use_acceptances_project_id`). Not in D-02; the
   unindexed-foreign-key advisor asks for it and the future Admin rule joins by project (RESEARCH H-6).
5. **Two helper scripts are created in the phase directory** (`172-gates.sh`, `172-e2e.sh`), following Phase
   169's practice, so every later plan reads gate status from an exit code or a run directory.
6. **One baseline run of the gates and of the E2E suite precedes the first edit**, so a red inherited from
   Phase 170 or 171 is reported as theirs.
