## B. Mechanism — how the duplication collapses

### B1 ⚠ DECIDE — Which collapse shape?

Fact 5 rules out "providers just call the helper" as written.

| | Shape | What it costs | What it risks |
|---|---|---|---|
| **(a)** | Generalise `getIdTokenClaims()` to take an optional `AuthConfig` and return `extractedClaims`; providers call it with their config | Changes the helper's public signature and return type; `preregister/+layout.server.ts` and the 5 existing helper tests must absorb it | Widest blast radius; the helper's own green tests stop being an untouched control |
| **(b)** | Extract `decryptAndVerifyIdToken(idToken, options) → JWTPayload` carrying the three coded throws + the lazy parse. The helper keeps its exact signature and maps its hardcoded claims on top; each provider maps via its own `authConfig` on top | One new module; helper's signature, return type, callers and 5 tests **byte-unchanged** | Two claim-mapping sites remain (by design — they genuinely differ) |
| **(c)** | Delete both provider methods; `getActiveProvider()` returns a shared implementation bound to `authConfig` | Restructures the provider object graph | Largest diff on an auth path; the per-provider test files lose their subject |

- [ ] **(a) Generalise the helper**
- [x] **(b) Extract the common decrypt→verify core** — ★ RECOMMENDED — criterion 1 permits it verbatim
      ("*either delegate to it or are replaced by a common extracted path*"); it is the only option that
      leaves the helper's existing tests as an untouched control while the phase measures negative-control
      pairs; and the thing that actually duplicated is the decrypt→verify→coded-error path — **not** the
      claim mapping, which is legitimately per-provider (`authConfig.ts:24-47`). One `JSON.parse`, one kid
      lookup, one `compactDecrypt`, one `jwtVerify`, three codes — in one place.
- [ ] **(c) Shared implementation bound to `authConfig` in the factory**

### B2 — Where the lazy env parse lands, and the eager-snapshot hazard

`getIdTokenClaims.ts:16-25` defers **only** the JWKS parse to a getter. `:26-28`
(`publicSignatureJWKSetUri`, `audience`, `issuer`) are **plain properties evaluated at module load**. The
provider copies read all four *per call* (`idura.ts:116,128,130-131`). A careless extraction that hands
providers the existing `defaultOptions` object silently converts three per-call reads into import-time
snapshots — which breaks under the very test mock pattern **C1** adopts (a `beforeAll` that mutates
`mockConstants` would be missed).

- [ ] **(a) All four fields of the shared default options become getters** — ★ RECOMMENDED — criterion 2's
      "inherits the lazy env parse" is then true of the whole option set, not just the JWKS, and the test
      seam stays honest. The `Do not simplify this back into a plain property` comment
      (`getIdTokenClaims.ts:13-14`) is carried onto each.
- [ ] **(b) Only the JWKS stays lazy** — matches today's helper exactly; leaves the snapshot hazard live and
      makes **C1**'s mocking fragile.
- [ ] **(c) No shared defaults — each provider builds its own per-call options object** — preserves today's
      per-call reads precisely; duplicates the four reads across three call sites again.

### B3 — Error-code set

- [ ] **(a) Exactly A-07's three: `ERR_JWKS_MALFORMED`, `ERR_JWKS_EMPTY`, `ERR_JWK_KID_MISMATCH`** —
      ★ RECOMMENDED — jose's own `code` values keep flowing through the existing catch arm unchanged
      (`getIdTokenClaims.ts:85-98`, mirrored at `idura.ts:148-161` / `signicat.ts:111-124`). Inventing a
      fourth code here would be an unmeasured product change.
- [ ] **(b) Add a fourth code for decrypt/verify failure** — more operator signal; a new product change
      needing its own control pair, and a leak-safety review of what "verify failed" may say.

### B4 ⚠ DECIDE — Does anything *consume* the code on the production path?

Criterion 1 requires the two incidents be "distinguishable **on the production path**". After the collapse
the code is *present* in the returned result — but `token/+server.ts:28-30` and `callback/+server.ts:74-76`
both discard it, so nothing an operator can see changes. On the other side, criterion 5 forbids leaking any
of it to an unauthenticated caller.

- [ ] **(a) Log the code server-side; change no response** — ★ RECOMMENDED — one `console.error` per call
      site emitting the opaque code **only** (never `error.message`, which carries the incoming kid), while
      the HTTP response stays exactly `401 { message: 'Unauthorized' }` / the existing redirect. The minimum
      that makes "distinguishable on the production path" true rather than nominal, and the same discipline
      `token/+server.ts:41-47` already applies.
- [ ] **(b) No consumption — reaching the code is enough** — zero endpoint code changes; criterion 1's
      second sentence is then satisfied only in the sense that the code exists in memory.
- [ ] **(c) Log it *and* return an opaque code in the response body** — best for a client-side diagnostic;
      crosses criterion 5's line unless the code set is re-reviewed as caller-safe (see **E3**).

### B5 — Provider return contract

- [ ] **(a) `IdTokenClaimsResult` unchanged; `extractedClaims` stays required** — ★ RECOMMENDED —
      `/api/oidc/*` consumers untouched apart from **B4**'s logging.
- [ ] **(b) Make `extractedClaims` optional** — lets the helper satisfy the provider type directly; weakens
      a contract every provider currently honours, and makes a dropped claim a silent `undefined`.

## C. Test strengthening design (criterion 3)

### C1 — `signicat.test.ts` cannot inject generated keys as written (fact 10)

`constants.ts:3-19` is an eager literal, so `signicat.test.ts:26-34`'s static `$env/dynamic/private` mock

- [ ] **(a) Port `idura.test.ts`'s getter-mock pattern into `signicat.test.ts`** — ★ RECOMMENDED —

- [ ] **(b) Add dependency injection instead** — give `getIdTokenClaims(idToken, options?)` an options
      parameter on the `IdentityProvider` interface so tests pass keys directly. Cleaner seam; changes a
      public interface (`providers/types.ts:206`) that production callers would then be free to misuse.

### C2 — Replacing `jose.createRemoteJWKSet`

- [ ] **(a) Reuse `getIdTokenClaims.test.ts:51-64` verbatim** — ★ RECOMMENDED — `vi.mock('jose',
      importOriginal)` returning `createLocalJWKSet`'s getter, with the same cast-through-unknown comment.
      ESM exports are not configurable, so `vi.spyOn` is not an option; this is settled in-tree precedent.
- [ ] **(b) Stand up a local HTTP JWKS endpoint and let the real remote fetcher run** — exercises more of
      the real path; adds a network seam and a new dependency to two unit test files.

### C3 — Token/key fixtures

`__fixtures__/keys.ts` and `__fixtures__/tokens.ts` sit beside the two test files and are currently imported
only by their own smoke test.

- [ ] **(a) Use the existing factories** — ★ RECOMMENDED — `createTestKeySet({ encAlg: 'RSA-OAEP-256',
      kid })` for Idura, `{ encAlg: 'RSA-OAEP' }` for Signicat; `createTestJwe(claims, keys, {…})` for

- [ ] **(b) Hand-roll a local `buildJwe` per test file** — mirrors `getIdTokenClaims.test.ts:102-125`;

### C4 — What the success-path assertion pins

The assertion must go red if the claim mapping silently drifts — the exact drift the `typeof` guard was
blind to.

- [ ] **(a) Deep-equality on the configured mapping** — ★ RECOMMENDED — **Idura:** a token carrying
      `given_name`/`family_name`/`sub`/`birthdate`/`hetu`/`country` asserts `firstName`, `lastName`,
      `identifier === <sub>` (**not** the birthdate), and `extractedClaims` **deep-equal** to
      `{birthdate, hetu, country}`. **Signicat:** `identifier === <birthdate>` and `extractedClaims`
      deep-equal to `{birthdate}`. Deep-equality, not `toContain`/`toHaveProperty` — a superset or a dropped
      claim must red (F20-4's lesson, `142-NEGATIVE-CONTROL-LEDGER.md` row 10).
- [ ] **(b) Assert names + identifier only; `extractedClaims` via `toMatchObject`** — less brittle to a
      future added claim; blind to exactly the "extra/dropped key" drift that motivated F20-4.

### C5 — Which failure branches get coded assertions

- [ ] **(a) All three codes per provider** — ★ RECOMMENDED — empty configured set → `ERR_JWKS_EMPTY`; a set
