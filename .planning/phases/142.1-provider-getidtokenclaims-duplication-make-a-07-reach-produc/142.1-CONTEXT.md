### D-01 — `/api/oidc/callback/+server.ts:73` is in scope, stated explicitly (discussion A1(a))

Criterion 1 names only the token endpoint, but fact 2 shows the callback makes the identical call.
One collapse serves both, at no extra cost. This is load-bearing for **D-25**: the E2E project that
walks the changed path walks the **callback**, not the token endpoint.

### D-02 ⚠ OPERATOR OVERRULE — `preregister/+layout.server.ts:30` is repointed and the standalone helper export is deleted (discussion A2(c))

The recommendation was A2(a) — leave the call site, name it as residue. **The operator ticked
A2(c).** The phase therefore closes the split now and leaves exactly **one** entry point to
decrypt→verify→claim-mapping in `apps/frontend/src`.

- `preregister/+layout.server.ts:2,30` imports `getActiveProvider` from
  `$lib/api/utils/auth/providers` and calls `getActiveProvider().getIdTokenClaims(idToken)`.
- Its consumption at `:32-42` is unchanged: `.success` gate, `id_token` cookie delete on failure,
  `{ firstName, lastName }` returned. The provider result is a **superset** of the helper's shape
  (it adds `extractedClaims`), so `:42` compiles and behaves identically.
- The standalone `export async function getIdTokenClaims` is **deleted**, not merely unexported.

**Measured behaviour delta this creates** (state it in the phase record; it is small, and both
directions are improvements or no-ops):

| Under | Helper today | Provider after repoint | Observable at `:42`? |
|---|---|---|---|
| Signicat (default provider) | `identifier` ← `birthdate` (`getIdTokenClaims.ts:82`) | `identifier` ← `birthdate` (`SIGNICAT_AUTH_CONFIG.identityMatchProp`, `authConfig.ts:25`) | **No change** |
| Idura | `identifier` ← `birthdate` | `identifier` ← `sub` (`authConfig.ts:43`) | **No** — the layout consumes only `firstName`/`lastName` |

### D-02b ⚠ DERIVED — `getIdTokenClaims.test.ts`'s five tests are repointed to the extracted core, not deleted

The discussion's `A2(c)` text records that these five tests "lose their subject". They must not
lose their **coverage**: they are the only in-tree tests that exercise real JWE decryption end to
end for both `RSA-OAEP` and `RSA-OAEP-256`. Disposition:

| Existing test | Site | Becomes |
|---|---|---|
| `decrypts RSA-OAEP JWE and returns identifier from birthdate` | `:128-154` | a core test asserting the **decrypted payload** carries `birthdate` |
| `returns correct names from OIDC claims` | `:155-181` | a core test asserting the payload carries `given_name`/`family_name` |
| `decrypts RSA-OAEP-256 JWE successfully` | `:183-214` | unchanged in intent; asserts the payload |
| `returns success=false when kid not in JWKS` | `:216-243` | `await expect(...).rejects.toMatchObject({ code: 'ERR_JWKS_EMPTY' })` |
| `returns success=false when kid does not match available keys` | `:244-272` | same shape, `ERR_JWK_KID_MISMATCH` |

The core **throws** its coded errors (**D-06**); the `{ success: false, error: { code } }` mapping
lives in each provider's catch arm. The file is renamed to match the core module and its
`describe` title updated. The `NOTE: getIdTokenClaims uses hardcoded 'birthdate' for identifier`
comment at `:207` is removed — after this phase nothing hardcodes it.

### D-06 ⚠ — Collapse shape: extract the common decrypt→verify core (discussion B1(b), operator-confirmed)

Fact 5 rules out "providers just call the helper" as written. The phase extracts:

```
decryptAndVerifyIdToken(idToken, options) → Promise<jose.JWTPayload>
```

carrying the **three coded throws** and the **lazy parse**. Claim mapping stays per-provider, on top
of the core, via each provider's `authConfig` — because that is the part that legitimately differs
(`authConfig.ts:24-47`), while the decrypt→verify→coded-error path is the part that actually
duplicated. One `JSON.parse`, one kid lookup, one `compactDecrypt`, one `jwtVerify`, three codes —
in one place.

Criterion 1 permits this verbatim: "*either delegate to it or are replaced by a common extracted
path*".

Both provider `getIdTokenClaims` methods keep their signature and their catch arm
(`idura.ts:147-161` · `signicat.ts:110-124`, which already map a `code`-carrying error to
`{ success: false, error: { code } }`); their bodies reduce to `core → map claims via authConfig`.

### D-07 — All four shared default-option fields become getters (discussion B2(a))

`getIdTokenClaims.ts:16-25` defers **only** the JWKS parse; `:26-28`
(`publicSignatureJWKSetUri`, `audience`, `issuer`) are plain properties evaluated at module load,
whereas the provider copies read all four **per call** (`idura.ts:116,128,130-131`). Handing
providers the existing object as-is would silently convert three per-call reads into import-time
snapshots — breaking the very `beforeAll`-mutates-`mockConstants` seam **D-11** adopts.

All four become getters. The `Do not simplify this back into a plain property` comment
(`getIdTokenClaims.ts:13-14`) is carried onto each. Criterion 2's "inherits the lazy env parse" is
then true of the whole option set.

### D-08 — Error-code set is exactly A-07's three (discussion B3(a))

`ERR_JWKS_MALFORMED`, `ERR_JWKS_EMPTY`, `ERR_JWK_KID_MISMATCH`. jose's own `code` values keep
flowing through the existing catch arms unchanged. No fourth code — that would be an unmeasured
product change needing its own pair and its own leak-safety review.

### D-09 ⚠ — The code is consumed server-side by a log; no response changes (discussion B4(a))

After the collapse the code is *present* in the result, but `token/+server.ts:28-30` and
`callback/+server.ts:74-76` both discard it — nothing an operator can see would change. So each
call site gains **one** `console.error` emitting the **opaque code only** — never `error.message`,
which carries the incoming kid. The HTTP surface stays exactly as it is (**D-24**). This is the
minimum that makes criterion 1's "distinguishable **on the production path**" true rather than
nominal, and it is the discipline `token/+server.ts:41-47` already applies.

**Integration note:** `__tests__/token-endpoint.test.ts` mocks no provider — it drives the real
path with a mock token (`:307,355`), so this log will now emit during those tests. That is noise,
not failure; if a plan chooses to silence it, it does so with a `console.error` spy in that file
and **not** by weakening the log.

### D-14 — Success-path assertions are deep-equality on the configured mapping (discussion C4(a))

The assertion must go red if the claim mapping silently drifts — the exact drift the `typeof` guard
was blind to.

- **Idura**: a token carrying `given_name`/`family_name`/`sub`/`birthdate`/`hetu`/`country` asserts
  `firstName`, `lastName`, `identifier === <sub>` (**not** the birthdate), and `extractedClaims`
  **deep-equal** to `{ birthdate, hetu, country }`.
- **Signicat**: `identifier === <birthdate>`, `extractedClaims` deep-equal to `{ birthdate }`.

Deep-equality, **not** `toContain` / `toHaveProperty` — a superset or a dropped claim must red.
(F20-4's lesson, `142-NEGATIVE-CONTROL-LEDGER.md` row 10.)

### D-15 — All three codes get coded assertions, per provider (discussion C5(a))

evidence** and has no counterpart anywhere today. Assertion form
`expect(result).toMatchObject({ success: false, error: { code: '…' } })`, matching
`getIdTokenClaims.test.ts:241,268`, plus A-07's `Do not weaken this back to a bare success check`

### D-17 ⚠ — Negative-control ordering: OLD half first, per axis, with dual site naming (discussion D1(a))

2. Revert.
3. Land the collapse (**D-06**/**D-07**), the endpoint logging (**D-09**), the repoint (**D-02**)

line, and pretending otherwise is how a pair stops being a pair.

**Carried into every injection task, verbatim, at the top:** strengthening before collapsing reds
the new assertions against the uncoded copies. **That red is the correct diagnosis, not a
regression** — the same inversion warning Phase 142 put at the top of each of its injection tasks.
