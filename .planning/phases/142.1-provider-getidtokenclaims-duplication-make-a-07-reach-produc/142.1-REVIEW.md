## Summary

The collapse itself is mechanically sound. I verified the four bars the phase committed to
and all four hold **as code**, not merely as claims:

- The three coded messages carry no JWKS contents, no configured kid, no issuer and no
  audience; the incoming kid is still present in the kid-miss message and is asserted
  (`decryptAndVerifyIdToken.test.ts:270-276`).
- The HTTP surface is unchanged: `token/+server.ts` still yields `401 {message:'Unauthorized'}`
  and `callback/+server.ts` still redirects with `?error=invalid_token`; no coded body reaches
  an unauthenticated caller, because `IdTokenClaimsResult`'s failure branch carries only `{code}`.
- Both new `console.error` lines emit `claims.error.code ?? 'none'` and never `error.message`.
- All four shared defaults are getters; I confirmed `ERR_JWKS_MALFORMED` is reachable and asserted.
- `decryptAndVerifyIdToken.ts` is **not** re-exported from `providers/index.ts`, and there is
  exactly one decrypt→verify path left in `apps/frontend/src` (grep-verified; no dangling
  references to the deleted `getIdTokenClaims`). `yarn vitest run src/lib/api/utils/auth`
  passes 65/65.

What the phase did **not** look at is where the defects are. Three of them are blockers.

The most serious is in the new canonical core itself: `audience` and `issuer` are sourced from
constants that default to the **empty string**, and jose treats a falsy `issuer`/`audience`
option as "require the claim to be present, but do not check its value"
(`node_modules/jose/dist/webapi/lib/jwt_claims_set.js:105-121`). A deployment that has not set
`IDENTITY_PROVIDER_ISSUER` / `PUBLIC_IDENTITY_PROVIDER_CLIENT_ID` therefore performs *no*
issuer or audience binding while every comment in the file reads as though it does. The phase
created the single chokepoint where this can be fixed once; it should be fixed there.

The other two blockers are in the Deno fourth copy, which the phase deliberately left out of
scope but explicitly invited defect reports on. That copy is not merely duplicated — it is
**strictly weaker** than its frontend twin on three separate axes: it echoes jose's internal
verification and decryption error messages back to unauthenticated callers (an oracle, and a
direct inversion of the leak-safety bar this phase spent a plan establishing), it selects the
key-import algorithm from the attacker-supplied protected header, and — with the Signicat
config — it derives its Supabase account key from `birthdate`, which collapses every user
sharing a date of birth into a single auth user.

`tests/tests/support/preflight.ts` clause (b2) was scrutinised closely per the brief. The
replacement is **not** a weakened form of the old assertion — I confirmed via
`node_modules/@sveltejs/kit/src/exports/vite/dev/index.js:136` and
`src/utils/filesystem.js:145-151` that SvelteKit dev really does emit
`/@fs<abs outDir>/generated/client/app.js`, that `kit.outDir` is not customised here, that no
route sets `csr = false`, and that maintenance mode renders inside `+layout.svelte` and so
still emits the bootstrap. The fail-closed sentinel branch is correct. Two problems remain:
clause (b) as a whole is satisfiable by a listener that simply **redirects** to the genuine dev
server (both `fetch` calls follow redirects and no clause compares the final origin to the
probed one), and **neither** of the two branches added by this phase has any test — the one
test that names "HTML that has none" sets `probeStatus: 403`, so it fails at (b1) and never
reaches (b2).

`packages/dev-seed/src/templates/e2e/perm/perm-bankauth-notloc.ts` is a pure Prettier reflow;
no defect. `mockOidcIssuer.ts` and `tests/README.md` are comment/doc repointing only.

## Critical Issues

### CR-01: Shared core silently disables `aud` and `iss` verification when the env vars are unset

**File:** `apps/frontend/src/lib/api/utils/auth/decryptAndVerifyIdToken.ts:61-80, 120-124`
**Issue:**
`defaultOptions.audience` returns `publicConstants.PUBLIC_IDENTITY_PROVIDER_CLIENT_ID` and
`defaultOptions.issuer` returns `constants.IDENTITY_PROVIDER_ISSUER`. Both constants are
`?? ''`-defaulted (`apps/frontend/src/lib/server/constants.ts:8`,
`apps/frontend/src/lib/utils/constants.ts:8`), so an unset env var yields `''`, not `undefined`.

jose then does this (`node_modules/jose/dist/webapi/lib/jwt_claims_set.js:101-121`, v6.2.1):

```js
if (audience !== undefined) presenceCheck.push('aud');   // '' !== undefined -> claim must EXIST
if (issuer   !== undefined) presenceCheck.push('iss');
...
if (issuer   && !( ... ).includes(payload.iss)) throw ...  // '' is FALSY -> value NEVER compared
if (audience && !checkAudiencePresence(...))    throw ...  // '' is FALSY -> value NEVER compared
```

Net effect: with either variable unset the token must merely *carry* an `iss`/`aud`, with any
value at all. Any token signed by a key in the configured JWKS is accepted — including one
minted by the same IdP for a completely different relying party. This is an authentication
bypass on a misconfiguration that produces no error, no warning and no log line, in the module
that is now the sole entry point for ID-token verification in the app.

The behaviour is carried forward from the deleted `getIdTokenClaims.ts:26-28` rather than
introduced here — but this phase created the one place it can be fixed once, the getters are
brand-new code, and every comment in the block reads as though the checks are enforced. No test
in the phase exercises a wrong-audience or wrong-issuer token, so nothing would notice.

**Fix:** fail closed at the getter, and hand jose `undefined` only when an operator has
deliberately opted out:

```ts
get audience(): string {
  const audience = publicConstants.PUBLIC_IDENTITY_PROVIDER_CLIENT_ID;
  if (!audience) {
    throw Object.assign(
      new Error('Cannot verify ID token: no expected audience is configured.'),
      { code: 'ERR_AUDIENCE_UNCONFIGURED' }
    );
  }
  return audience;
},
get issuer(): string {
  const issuer = constants.IDENTITY_PROVIDER_ISSUER;
  if (!issuer) {
    throw Object.assign(
      new Error('Cannot verify ID token: no expected issuer is configured.'),
      { code: 'ERR_ISSUER_UNCONFIGURED' }
    );
  }
  return issuer;
}
```

Both throws land inside each provider's existing `try`, so they surface as coded failures
exactly like the other three, with no public-type change. Add two negative tests to
`decryptAndVerifyIdToken.test.ts` that mint a token with a wrong `aud` and a wrong `iss` and
assert rejection — today there are none, which is why this survived.

### CR-02: Edge Function returns internal decryption/verification error text to unauthenticated callers

**File:** `apps/supabase/supabase/functions/identity-callback/index.ts:206-212, 220-228, 237-245, 389-397`
**Issue:**
Every failure arm echoes the caught error's message straight into the response body:

```ts
const message = e instanceof Error ? e.message : 'JWE decryption failed';
return new Response(JSON.stringify({ error: 'Token decryption failed', details: message }), { status: 401, ... });
```

The messages this surfaces are exactly the ones the frontend twin was hardened against:
`No matching decryption key found for kid=<incoming kid>` (line 59), jose's
`unexpected "iss" claim value` / `unexpected "aud" claim value` / `signature verification failed`
/ `missing required "aud" claim`, and — on the 500 arm at line 393 — Supabase admin-API error
text including `Failed to create auth user: …`, `Failed to list users: …`, and any Postgres
error string those carry.

`/functions/v1/identity-callback` is reachable with the public anon key (and is documented as
served `--no-verify-jwt` for tests), so this is an unauthenticated caller distinguishing
*why* a token was rejected: a step-by-step verification oracle telling an attacker whether the
kid matched, whether decryption succeeded, whether the signature verified, and whether the
issuer/audience bound. It is the direct inverse of the bar this phase spent plan 02 establishing
five files away, and it is a bigger hole than the duplication that was filed as the standing todo.

**Fix:** log internally, return a fixed string:

```ts
} catch (e) {
  console.error('[identity-callback] token decryption failed:', e);
  return new Response(JSON.stringify({ error: 'Token decryption failed' }), {
    status: 401,
    headers: { ...corsHeaders, 'Content-Type': 'application/json' }
  });
}
```

Apply identically to the verify arm (line 224), the claims arm (line 241) and the 500 arm
(line 393). If a correlation handle is wanted, return a random request id and log it alongside
the error rather than the message itself.

### CR-03: Signicat identity match on `birthdate` collapses every user sharing a date of birth into one auth account

**File:** `apps/supabase/supabase/functions/identity-callback/index.ts:253-287, 336-344`
(with `apps/supabase/supabase/functions/identity-callback/claimConfig.ts:34-39`)
**Issue:**
`PROVIDER_CONFIGS.signicat.identityMatchProp` is `'birthdate'`. That value becomes both the
lookup key and the account key:

```ts
let userId = await findUserByIdentityMatch(supabaseAdmin, identityMatchValue); // matches app_metadata.identity_match_value
const placeholderEmail = `${identityMatchValue}@bank-auth.placeholder`;        // e.g. 1985-06-15@bank-auth.placeholder
```

Two different bank-authenticated people born on the same day resolve to the **same**
`identity_match_value` and the **same** placeholder email. The second one to arrive is matched
to the first one's `userId` at line 253, skips user creation, finds the first one's candidate
row at line 290, and is handed a magic link for that account at line 338. That is a full account
takeover between unrelated, correctly-authenticated users — no attacker required, just a
birthday collision, which for any realistic candidate population is a near-certainty.

Idura (`identityMatchProp: 'sub'`) is unaffected; this is the Signicat path only. It is
pre-existing rather than introduced here, but it lives in a file this review was explicitly
asked to report defects in, and it is the most severe thing in the reviewed set.

**Fix:** an identity key must be unique per person. Either bind Signicat to a stable subject
claim (`sub`) as Idura does, or compose the key from a genuinely unique claim (`hetu` plus a
provider discriminator) — and make the placeholder email a hash of that key rather than the raw
value, so a claim value can never be reconstructed from, or collide inside, an email local part:

```ts
const identityKey = `${providerType}:${identityMatchValue}`;
const placeholderEmail = `${await sha256Hex(identityKey)}@bank-auth.placeholder`;
```

Until it is fixed, do not run the Signicat provider against the Edge Function path. A migration
plan is needed for any existing `identity_match_value: '<birthdate>'` rows.

## Warnings

### WR-01: Preflight clause (b) is satisfiable by a listener that redirects to the genuine dev server

**File:** `tests/tests/support/preflight.ts:182, 401-402, 409-410, 429-445`
**Issue:** Both network reads follow redirects, and nothing ever asserts that the response the
identity clause inspects came from the origin the specs will drive.

- Clause (a) fetches with `redirect: 'follow'` (line 182) — deliberate, to close the measured
  `301 -> /sv/` hole. But `observed.finalURL` is recorded for diagnostics only; no clause
  compares `new URL(finalURL).origin` to `new URL(baseURL).origin`.
- Clause (b2) then extracts its identity evidence from *that* body (line 402).
- Clause (b1)'s probe (line 410) also follows redirects by default.

So a process holding the port that answers `302 -> http://localhost:5174/...` (the real dev
server) passes (b1) with a 200, passes (b2) with the real checkout's absolute module root, and
passes (c) with the real title — while every spec afterwards drives the foreign listener. The
module's own framing ("a false green produced by a foreign server is undetectable after the
fact") is what makes this worth fixing rather than tolerating: the guard reports OK for a server
it did not actually verify.

**Fix:** pin the origin, and stop the probe from following redirects:

```ts
// clause (a), after the poll succeeds
if (new URL(outcome.live.finalURL).origin !== new URL(baseURL).origin) {
  fail(`the listener redirected off-origin to ${outcome.live.finalURL}; the identity evidence ` +
       `would come from a server the specs never drive`);
}
// clause (b1)
const probe = await fetch(probeURL, { redirect: 'manual' });
```

### WR-03: `getActiveProvider()` can now throw out of the preregister `load`, where the old helper could not

**File:** `apps/frontend/src/routes/candidate/preregister/+layout.server.ts:30`
**Issue:** The deleted `getIdTokenClaims` wrapped everything in `try`/`catch` and could not
throw — a bad token degraded to `{ claims: undefined }` and the page rendered. The replacement
splits into two calls, and the first one is not total: `getActiveProvider()`
(`providers/index.ts:37-39`) throws on an unrecognised `PUBLIC_IDENTITY_PROVIDER_TYPE`. That
throw is uncaught in `load`, so a typo in one public env var turns a graceful degradation into
a 500 on the preregister route for every visitor — including the `!idToken` early-return path,
because the provider is resolved before the token is even inspected.

`/api/oidc/token` and `/api/oidc/callback` both call it inside a `try`; this is the one site
that does not.

**Fix:** resolve the provider only once a token exists, and keep the previous degradation:

```ts
const idToken = cookies.get('id_token');
if (!idToken) return { claims: undefined };

let claims;
try {
  claims = await getActiveProvider().getIdTokenClaims(idToken);
} catch (e) {
  console.error('[preregister] identity provider unavailable:', e);
  claims = { success: false as const, error: {} };
}
```

### WR-04: The claim-mapping block is still duplicated byte-for-byte across both providers

**File:** `apps/frontend/src/lib/api/utils/auth/providers/idura.ts:115-146` and
`apps/frontend/src/lib/api/utils/auth/providers/signicat.ts:82-113`
**Issue:** After the collapse the two `getIdTokenClaims` bodies are **identical** apart from the
config identifier — same 15-line extraction, same catch arm, same `String(… ?? '')` calls. A
phase whose purpose was removing this duplication removed only the decrypt/verify half and left
the other half in place, so the "one entry point" property holds for decrypt→verify but not for
claim mapping: a fix to the mapping (e.g. WR-05, or a `String(object)` guard) must still be made
twice or it silently diverges.

Compounding it, each body reads the **imported module constant** (`IDURA_AUTH_CONFIG` /
`SIGNICAT_AUTH_CONFIG`) rather than the provider's own `authConfig` property that it exposes on
the very same object literal (idura.ts:48, signicat.ts:35). `iduraProvider.authConfig` and the
mapping the provider actually applies are two independent references to the same value today,
and nothing keeps them in sync tomorrow — `idura.test.ts:150-156` asserts the former while
`idura.test.ts:266-274` asserts the latter, so a divergence would need both to be edited to go
unnoticed, but neither test can see the aliasing itself.

**Fix:** put the mapping next to the core it already delegates to, and drive it from the passed
config:

```ts
// decryptAndVerifyIdToken.ts (or a sibling claimMapping.ts)
export function mapClaims(payload: jose.JWTPayload, authConfig: AuthConfig): IdTokenClaimsResult {
  return {
    success: true,
    data: {
      firstName: String(payload[authConfig.firstNameProp] ?? ''),
      lastName: String(payload[authConfig.lastNameProp] ?? ''),
      identifier: String(payload[authConfig.identityMatchProp] ?? ''),
      extractedClaims: Object.fromEntries(
        authConfig.extractClaims.map((c) => [c, String(payload[c] ?? '')])
      )
    }
  };
}
```

then in each provider: `return mapClaims(await decryptAndVerifyIdToken(idToken), this.authConfig);`
— which also closes the aliasing. The catch arm is identical in both files too and can move into
the same helper.

### WR-05: `identifier` and `extractedClaims` (including `hetu`, a Finnish national identity code) are computed on every successful auth and consumed nowhere

**File:** `apps/frontend/src/lib/api/utils/auth/providers/idura.ts:119-129`,
`apps/frontend/src/lib/api/utils/auth/providers/signicat.ts:86-96`
**Issue:** Grepping every consumer of the result shows nothing reads either field in production
code. The three call sites use only `claims.success` (`token/+server.ts:28`,
`callback/+server.ts:74`) and `claims.data.firstName` / `claims.data.lastName`
(`preregister/+layout.server.ts:42`). The one place `identifier` is threaded further explicitly
discards it:

```ts
// apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:132
// identifier is intentionally ignored -- Supabase uses email-based invite, not personal ID.
```

The only references to `extractedClaims` outside the two providers are the two tests that assert
it. So this is dead output — and for Idura the dead output is `hetu`, the Finnish personal

`IdTokenClaimsResult` (`providers/types.ts:150-160`) and from both providers, and delete the two
test assertions that pin them. Do not leave a national identity code in a dead field.

### WR-06: Login-CSRF — state verification is skipped entirely when the cookie is absent, and the nonce is never verified

**File:** `apps/frontend/src/routes/api/oidc/callback/+server.ts:42-51, 88-93`
**Issue:** Two independent gaps in the same handler.

1. `if (storedState) { …verify… }` — when no `oidc_state` cookie is present the CSRF check is
   *skipped*, not failed. The comment calls it "backward compat with Signicat PKCE", but the
   effect is that an attacker who can induce a victim's browser to hit
   `/api/oidc/callback?code=<attacker's code>` with no state cookie gets the attacker's
   `id_token` planted as the victim's httpOnly cookie (line 96), and the victim then
   pre-registers under the attacker's bank identity. Exploitability is currently limited —
   Idura always sets the cookie, and the Signicat path would fail the exchange without the PKCE
   verifier — but the guard is structured to fail *open*, which is the wrong shape for a CSRF
   control and will stop being limited the moment a third provider is added.
2. The `nonce` is generated (`idura.ts:55`), embedded in the JAR (line 65) and stored in a
   cookie, then read back at line 90 solely to be deleted. `// Nonce verification against the
   id_token nonce claim is a future enhancement.` So ID-token replay protection is absent
   despite the whole mechanism being wired.

**Fix:** for (1), fail closed and let PKCE be the documented exception rather than the silent one:

```ts
const storedState = cookies.get('oidc_state');
const usesPkce = Boolean(cookies.get('oidc_code_verifier'));
if (!storedState && !usesPkce) {
  throw redirect(303, '/candidate/preregister?error=invalid_state');
}
```

For (2), thread the payload's `nonce` out of the provider and compare it to `storedNonce` before
setting the cookie, or file it as a tracked security todo rather than an inline comment.

### WR-07: Edge Function applies `aud`/`iss` verification only when configured

**File:** `apps/supabase/supabase/functions/identity-callback/index.ts:70-95`
**Issue:** Same class as CR-01, and here it is explicit rather than accidental:
`if (clientId) verifyOptions.audience = …` / `if (issuer) verifyOptions.issuer = …`. A
deployment missing either secret verifies the signature and nothing else, on an endpoint that
is publicly reachable with the anon key. The in-file comment justifies it as
"a deployment that has not set IDENTITY_PROVIDER_ISSUER keeps its current behaviour instead of
failing closed on upgrade" — that is a deliberate choice to leave the weaker path callable, and
it is only defensible for as long as someone is tracking it.

**Fix:** fail closed with a 500 (misconfiguration, not a caller error) when either is unset:

```ts
if (!clientId || !issuer) {
  console.error('[identity-callback] IDENTITY_PROVIDER_CLIENT_ID / _ISSUER not configured');
  return new Response(JSON.stringify({ error: 'Identity verification is not configured' }), {
    status: 500, headers: { ...corsHeaders, 'Content-Type': 'application/json' }
  });
}
```

If a staged rollout is genuinely required, gate the leniency behind an explicit
`IDENTITY_PROVIDER_ALLOW_UNVERIFIED_ISSUER=1` so it is visible in the deployment config rather
than implied by an absent one.

### WR-08: A JWKS whose keys omit `alg` produces an uncoded failure, defeating the phase's diagnosability goal

**File:** `apps/frontend/src/lib/api/utils/auth/decryptAndVerifyIdToken.ts:119`
**Issue:** `jose.importJWK(privateEncryptionJWK)` is called with no `alg` argument, so jose
requires `jwk.alg` to be present and throws a plain `TypeError` when it is not. `TypeError` has
no `code`, so the providers' catch (`idura.ts:133`, `signicat.ts:100`) falls through to
`return { success: false, error: {} }` and the new log line prints `code= none`.

Publishing a JWK set without per-key `alg` is entirely normal — `alg` is optional in RFC 7517
and many IdP-issued sets omit it. So the single most likely real-world configuration error in
this module lands in the exact bucket the phase set out to eliminate: an opaque, uncoded,
undiagnosable failure that looks identical to a malformed token. The three coded failures cover
the three cases that were already easy to spot.

**Fix:** either pass the algorithm explicitly from the JWE header (validated against an
allowlist), or convert the missing-`alg` case into a fourth coded failure:

```ts
if (!privateEncryptionJWK.alg) {
  throw Object.assign(
    new Error('Cannot decode ID token: the matched decryption JWK declares no "alg".'),
    { code: 'ERR_JWK_ALG_MISSING' }
  );
}
```

The message stays leak-safe (it names no key material and no kid), and the code is opaque.

### WR-09: The new core's own test file does not cover the third coded failure, nor any claim-validation rejection

**File:** `apps/frontend/src/lib/api/utils/auth/decryptAndVerifyIdToken.test.ts:1-14, 204-278`
**Issue:** The header states the file tests "the three discriminating coded failures", and the

`ERR_JWKS_MALFORMED` is never exercised here — it is only reachable through `defaultOptions`,

Separately, and more consequentially for CR-01: there is no test anywhere that a token with the
wrong `aud` or the wrong `iss` is rejected. Both are options this module passes to `jwtVerify`
and both are silently no-ops under the default configuration.

**Fix:** correct the header to say two of the three are covered here and name where the third is,
and add the two claim-validation negatives (mint via `createTestJwe` with
`audience: 'other-client'` / `issuer: 'https://other.example'`, assert the promise rejects).
Those tests are what would have turned CR-01 red.

### WR-10: The getter rationale on three of the four defaults asserts a property the code does not have

**File:** `apps/frontend/src/lib/api/utils/auth/decryptAndVerifyIdToken.ts:51-80`
**Issue:** Each of `publicSignatureJWKSetUri`, `audience` and `issuer` carries:

> *"A getter, not a plain property (D-07). The providers read this per call; a plain property
> would evaluate it once at module load. Do not simplify this back into a plain property: that
> converts a per-call read into an import-time snapshot…"*

The values are already an import-time snapshot. `constants` and `publicConstants` are eager
object literals evaluated once when `$lib/server/constants` / `$lib/utils/constants` are first
imported (`constants.ts:3-19`, `utils/constants.ts:3-15`); the getter re-reads a property off a
frozen-in-practice object and can never observe a different value than a plain property would.
Only `privateEncryptionJWKSet` buys something real — it defers a `JSON.parse` that would
otherwise throw an uncatchable `SyntaxError` at import.

A "do not simplify this back" comment that names a false invariant is worse than no comment: the
next maintainer who checks it will find it wrong and will reasonably distrust the *fourth* one,
which is the one that matters. The provider tests do mutate `mockConstants` between calls, so
the getters are load-bearing **for the tests** — that is the honest rationale.

**Fix:** replace the three rationales with the accurate one, e.g.
`// A getter so the provider tests can mutate the mocked `constants` between calls; the
production value is fixed at import either way.` Keep the strong "do not simplify" wording only
on `privateEncryptionJWKSet`, where it is true.

### WR-11: Edge Function picks the key-import algorithm from the attacker-supplied JWE header

**File:** `apps/supabase/supabase/functions/identity-callback/index.ts:52-65`
**Issue:**

```ts
const header = jose.decodeProtectedHeader(jweToken);            // fully attacker-controlled
const privateKey = privateJWKSet.find((jwk) => jwk.kid === header.kid);
const { plaintext } = await jose.compactDecrypt(jweToken, await jose.importJWK(privateKey, header.alg || 'RSA-OAEP'));
```

The import algorithm comes from the token, not from the configured key, and `compactDecrypt` is
called with no `keyManagementAlgorithms` / `contentEncryptionAlgorithms` allowlist. The caller
therefore chooses which algorithm our private key is imported under, within whatever jose
supports. The frontend twin does it correctly — `importJWK(privateEncryptionJWK)` with no `alg`
argument (`decryptAndVerifyIdToken.ts:119`), which derives it from the configured JWK — so this
is another axis on which the fourth copy is strictly weaker than the one it duplicates, not
merely redundant.

`JSON.parse(Deno.env.get('IDENTITY_PROVIDER_DECRYPTION_JWKS')!)` on line 53 is also unguarded:
a malformed value throws a bare `SyntaxError` into the outer 500 handler, which then echoes the
parser's message (see CR-02). This is precisely the failure mode the frontend's lazy getter was
built to eliminate.

**Fix:** derive the algorithm from the configured key and pin the allowlists:

```ts
const privateKey = privateJWKSet.find((jwk) => jwk.kid === header.kid);
if (!privateKey) throw new Error('decryption key not found');
const { plaintext } = await jose.compactDecrypt(jweToken, await jose.importJWK(privateKey), {
  keyManagementAlgorithms: ['RSA-OAEP', 'RSA-OAEP-256'],
  contentEncryptionAlgorithms: ['A128CBC-HS256', 'A256GCM']
});
```

and wrap the env parse in a `try` that raises a coded configuration error.

### WR-12: `Access-Control-Allow-Origin: *` on a response carrying session-granting credentials

**File:** `apps/supabase/supabase/functions/identity-callback/index.ts:33-37, 369-388`
**Issue:** The success response body includes `session.action_link` and `session.hashed_token` —
a magic link and a verification token that together establish an authenticated Supabase session
for the matched candidate. It is served with `Access-Control-Allow-Origin: '*'`, so any origin
on the internet can invoke this endpoint from a page in a victim's browser and read the
credential out of the response.

The mitigating factor is that the caller must already supply a valid `id_token`, so this is not
by itself a takeover. It does mean the wildcard turns any XSS or malicious page anywhere into a
credential exfiltration path the moment an `id_token` is reachable to it, and it makes the
blast radius of CR-02's oracle larger.

**Fix:** restrict the origin to the configured `SITE_URL` (echoing only when the request's
`Origin` matches), and prefer setting the session as an httpOnly cookie from a first-party
route over returning `action_link` / `hashed_token` in a CORS-readable body.

### IN-08: The probe URL is built by string concatenation without encoding

**File:** `tests/tests/support/preflight.ts:409`
**Issue:** `` `${origin}/@fs${probeAbsolutePath}` `` interpolates a raw filesystem path into a
URL. A checkout under a path containing `#` truncates everything after it into a fragment, and
`?` starts a query string — either way the probe targets a different resource, gets a non-200,
and a perfectly correct checkout is reported to the operator as a foreign server. Also,
`origin = baseURL.replace(/\/+$/, '')` keeps any path component of `baseURL`, so a `baseURL`
with a subpath produces `…/subpath/@fs…`.
**Fix:** encode the path segment and derive the origin from the parsed URL:

```ts
const parsed = new URL(baseURL);
const probeURL = `${parsed.origin}/@fs${probeAbsolutePath.split('/').map(encodeURIComponent).join('/')}`;
```
