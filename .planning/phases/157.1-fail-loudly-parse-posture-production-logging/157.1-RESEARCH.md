## Summary

This phase has three mechanically independent halves and one that is not independent at all.

**The parse half** is well-conditioned. All six `safeParse` sites are within 40 lines of each other in three
files, every anchor in CONTEXT's fact table still holds at HEAD, and the A2 "unknown top-level key" hole turns
out to have a **one-line, empirically verified** closure: zod 4.3.6 reports an unrecognised key as
`{ code: 'unrecognized_keys', keys: ['bogusTop'], path: [] }`, so the key that names no member on `path[0]`
names itself on `issue.keys`. The current implementation's `String(issue.path[0])` evaluates to the literal
string `"undefined"`, drops nothing, and the retry fails identically — exactly as its own docstring predicted.
Reading `issue.keys` closes it.

**The logging half contains the phase's one genuine conflict, and it cannot be resolved without a deviation.**
C2 requires the same level in the browser; C3 chose a `LOG_LEVEL` env and explicitly rejected `PUBLIC_LOG_LEVEL`.
Measured against the installed SvelteKit 2.55.0: `kit.env.publicPrefix` defaults to `'PUBLIC_'` and
`privatePrefix` to `''` (`core/config/options.js:124-125`), `filter_env` (`utils/env.js:7-12`) partitions on
exactly that prefix, only `public_env` is serialised into the page (`runtime/server/page/render.js:404`), and
importing `$env/dynamic/private` from a client entrypoint — **`hooks.client.ts` is enumerated as one**
(`exports/vite/index.js:600-618`) — is a build error. There is no configuration that makes a bare `LOG_LEVEL`
readable in the browser. The build-time bake CONTEXT guessed at is also dead: `apps/frontend/Dockerfile:50`
runs the build **inside the image with no `ARG` and no env**, which is precisely why `constants.ts:1` reads
`$env/dynamic/public` at runtime. The recommendation is `PUBLIC_LOG_LEVEL`, and the recorded objection to it —
*"it lets a client set its own logging"* — is **factually wrong** for this codebase: the value is *visible*, not
*settable*, and there is no write path back into `env`.

**The guard half** is fully designed and **measured**. The mechanism is not a custom rule plugin — both in-tree
precedents are `no-restricted-syntax` esquery selectors in `apps/frontend/eslint.config.mjs`, locked in by a
vitest spec that lints virtual fixtures through the real config. Five selectors were written and executed against
17 fixtures (11 violation forms including 4 deliberate evasions, 6 compliant forms). Result: 5/5 selectors fire
correctly, **zero false positives** across the compliant set, and the two forms no selector catches are named
honestly below. One esquery trap was discovered and must not be repeated: `[argument.name='undefined']` matches
whenever the attribute is JS-`undefined`, silently over-firing on every object literal.

**Primary recommendation:** land C3's logging resolver first (D9 says "first plan"), using `PUBLIC_LOG_LEVEL`
behind a `checkpoint:human-verify` for the naming deviation; encode B1 as a plain discriminated union
`ParseOutcome<T>` in `apps/frontend/src/lib/api/adapters/supabase/utils/` (**not** `app-shared` — the guard cannot
reach `app-shared`, and that is decisive); keep every `DataProvider`/`DataWriter` **public** signature unchanged
so the four voter loaders that spread `appSettingsData` are untouched; and build the ESLint guard from the five
measured selectors in this document rather than re-deriving them.

## Q1 — The concrete encoding of the parse outcome (B1)

### Recommendation: a plain discriminated union, `status` as the tag

```ts
// apps/frontend/src/lib/api/adapters/supabase/utils/parseOutcome.type.ts

/**
 * One zod issue, reduced to what is safe to log: the dotted path, and — for an `unrecognized_keys`
 * issue, whose path names the CONTAINING object rather than the offending key — the key names.
 * The offending VALUE is never carried (T-157-17).
 */
export type ParseIssue = {
  /** The dotted path zod reported, `''` for an issue at the root. */
  path: string;
  /** Present only for `unrecognized_keys`: the keys zod refused. */
  keys?: Array<string>;
};

/**
 * The result of validating one JSONB value at the adapter boundary.
 *
 * `absent` and `malformed` are distinguishable WITHOUT any narrowing helper: a consumer that does
 * nothing special still sees two different `status` literals. That is the whole point of D8 — a
 * degrade-to-empty made them the same VALUE.
 */
export type ParseOutcome<TValue> =
  | { status: 'ok'; value: TValue; issues?: undefined }
  | { status: 'absent'; value?: undefined; issues?: undefined }
  | { status: 'malformed'; value: TValue | undefined; issues: Array<ParseIssue> };
```

**Why a discriminated union and not the alternatives.**

| Rejected | Why |
|----------|-----|
| **A class** (`class ParseOutcome<T> { … }`) | The values cross a SvelteKit **load-data serialization boundary** in several paths (`+layout.ts:36-41` returns loader data that SvelteKit `devalue`-serialises for hydration). A class instance does not survive that; a plain object does. It also costs `instanceof` checks, which `CLAUDE.md` records as historically problematic in this repo ("Instance Checks", commit `87efe19a`). |
| **A `Result`-alike** (`ok`/`err`, `unwrap()`) | Two states, not three. D8's entire content is that `absent` is a **third** state, not an error. Shoehorning it into `err` re-erases exactly the distinction. |
| **A branded/`Symbol` empty** | CONTEXT B1 already rejected this as option (d): the tag is erased at every `??` and spread — which is where the bug lives (`supabaseDataWriter.ts:300`). |
| **A tuple** `[status, value, issues]` | Unreadable at 10 image call sites; no field names in the type error when a site is missed. |

**Field-name justification.**

- `status` over `type`: `type` is already the discriminant on `DataApiActionResult`
  (`lib/api/base/actionResult.type.ts:5`, `'failure' | 'success'`) and on every entity variant
  (`ENTITY_TYPE`). Reusing it invites a `result.type === 'success'` typo that typechecks against the wrong union.
- `value` over `data`: `data` is the Supabase-client destructuring name in every adapter method
  (`const { data, error } = await this.supabase…`). Two `data`s in one scope is a readability tax at ten sites.
- `issues` over `errors`: matches zod's own `error.issues` and — load-bearing — is the identifier the
  **G5 guard selector** keys on (see § "The ESLint guard"). Renaming it silently weakens the guard.
- `value` is present-but-`undefined` on `malformed` **on purpose**: that is where A2's partial-preserve
  survivor lives. A malformed outcome with a survivor is `{ status: 'malformed', value: {…}, issues: [...] }`;
  one without is `{ status: 'malformed', value: undefined, issues: [...] }`. Consumers that only care "did I get
  something" read `outcome.value`; consumers that care "was it complete" read `outcome.status`.
- The `issues?: undefined` / `value?: undefined` members on the non-malformed arms are deliberate: they make
  `outcome.issues` **readable without narrowing** (TypeScript allows a property access when every arm declares
  it), which keeps the 10 image call sites from needing a type guard just to compile.

**Constructor helpers, co-located, three of them** — these are what keep ten call sites honest and are the
only functions the guard's G5 selector needs to stay silent on:

```ts
export function parseAbsent<T>(): ParseOutcome<T>;
export function parseOk<T>(value: T): ParseOutcome<T>;
export function parseMalformed<T>(issues: Array<ParseIssue>, value?: T): ParseOutcome<T>;
```

## Q2 — Where the outcome type lives

### Recommendation: `apps/frontend/src/lib/api/adapters/supabase/utils/` — **not** `packages/app-shared`

Three pieces of measured evidence, the first of which is decisive on its own.

**1. The ESLint guard cannot reach `app-shared`.** D1(a) puts the class guard in
`apps/frontend/eslint.config.mjs`, whose every block is scoped `files: ['src/**/*.{ts,js,mjs,cjs,svelte}']` —
i.e. `apps/frontend/src`. `packages/app-shared` is linted by its own `eslint --flag v10_config_lookup_from_file
src/` against `packages/shared-config/eslint.config.mjs`, whose `no-restricted-syntax`
(`shared-config/eslint.config.mjs:79-85`) carries only the `TSEnumDeclaration` ban. **If the generalised parse
helper lives in `app-shared`, the code the guard exists to protect is outside the guard's scope** and criterion 6
closes by inspection — the exact failure mode this phase was created to retire. Putting the helper in the adapter
puts it inside the guard.

**2. `app-shared` is documented as environment-agnostic, and this helper is not.** `logger.type.ts:32-37`:

> *"Nothing is read from the environment: `@openvaa/app-shared` is consumed by browser, SSR and plain-Node
> workspaces… The Vite compile-time constants and the SvelteKit virtual env modules are both unavailable here."*

The parse helper carries `JsonbColumnSource` (`{ column: string; id?: string | null }`,
`parseJsonbColumn.ts:12-17`) — a Supabase `table.column` concept with no meaning in `apps/supabase`'s Deno
functions or in `packages/matching`. Phase 157 already made this split deliberately: the **schemas** went to
`app-shared` (`packages/app-shared/src/data/schemas/`), the **parse helpers** stayed in the adapter
(`utils/parseJsonbColumn.ts`, and `parseStoredCustomization` inline at `supabaseDataProvider.ts:72-90`).

**3. No `app-shared` schema references the outcome type.** The five schemas export only `z.strictObject` /
`z.record` values and their `z.infer` types. Nothing in `packages/app-shared/src/data/schemas/index.ts` needs to
know that a *frontend adapter* wraps a failed parse in a status.

**Concrete placement.**

```
apps/frontend/src/lib/api/adapters/supabase/utils/
  parseOutcome.type.ts   ← ParseOutcome<T>, ParseIssue           (NEW)
  parseOutcome.ts        ← parseOk / parseAbsent / parseMalformed,
                           parseWithPartialPreserve(schema, value),
                           toIssues(zodError)                     (NEW)
  parseOutcome.test.ts   ← unit coverage incl. the A2 hole        (NEW)
  parseJsonbColumn.ts    ← parseImageColumn / parseAnswersColumn  (CHANGED: return ParseOutcome)
```

`parseStoredCustomization` (`supabaseDataProvider.ts:72-90`) moves **into** `parseOutcome.ts` as the generic
`parseWithPartialPreserve`, which is what A2(a) means by "generalise it into the shared parse helper".

**Rejected: `packages/app-shared/src/data/parse/`.** It would put the generic helper next to the schemas it
consumes, which reads tidier, and `app-shared` already depends on zod (`package.json:25`). Rejected on evidence
1: the guard would not cover it, and D1's whole content is that the guard covers the class.

### The three options, measured

**Option A — `PUBLIC_LOG_LEVEL` via `$env/dynamic/public` + `constants.ts`.** ✅ **RECOMMENDED.**
- Works in both module graphs at **runtime**, which is what the deploy path requires.
- Identical plumbing to `PUBLIC_DEBUG`, which both hooks already read at module scope — so the precedent that
  the value is populated before `configureLogger` runs is already shipped and proven in production.
- Costs one line in `constants.ts`, one block in `.env.example` (under the existing `# Debugging` heading at
  `:154-156`, **not** inside the cross-runtime pair block at `:1-47`, whose contiguity
  `scripts/assert-env-pair-registry.mjs` asserts), one entry in `render.example.yaml` beside `PUBLIC_DEBUG`
  (`:39-40`), and one in `docker-compose.dev.yml` beside `PUBLIC_DEBUG` (`:19`).
- **Deviation:** the variable is named `PUBLIC_LOG_LEVEL`, not `LOG_LEVEL`.

**Option B — build-time bake via Vite `define`, env named `LOG_LEVEL`.** ❌ **REJECTED — it does not work here.**
This is the resolution CONTEXT `<open>` Q3 guessed at ("resolved at build/config time and baked into both entry

the `production` stage declares no `ARG` for anything but `NODE_ENV` (`:45-46`). Render supplies `envVars` to the
*service* (`render.example.yaml:22`), and `docker-compose.dev.yml` supplies them under `environment:` (`:13`) —
both runtime. A baked value would therefore be the compile-time default **in every deployment, forever**, and no
operator setting would move it. That is a silent misconfiguration — the exact class C3's own NOTE exists to close.
It would also be untestable: the only way to change the level would be to rebuild the image.

**Option C — server-injected value passed to the client through the root layout.** ❌ **REJECTED.**
Mechanically possible: `hooks.server.ts` reads `$env/dynamic/private` `LOG_LEVEL`; a **new**
`routes/+layout.server.ts` (none exists — the tree has only `+layout.ts` and `+layout.svelte`) forwards it;
`+layout.svelte` calls `configureLogger` on the client. Three costs, the last decisive:
1. The browser logger stays `'silent'` from bundle-eval until the root layout mounts. Every record emitted during
   client bootstrap — including anything from `hooks.client.ts` itself — is dropped. C2 asks for the same level
   in both; this gives the same level *eventually* in one.
2. It adds a `+layout.server.ts`, which forces every route under it through a server load and interacts with the
   `+layout.ts` universal load that `:9-12` documents as deliberately fully-awaited.
3. **It publishes the value to the browser anyway, through a side channel, while hiding that fact from the
   reviewer.** `.env.example:12-15` states the house rule verbatim: *"`PUBLIC_` is a BUNDLING CONTRACT meaning
   'embedded in client JavaScript', not a naming convention: reusing it in a server-only runtime, where it means
   nothing, erodes the only browser-safety signal a reviewer has."* The inverse is equally true. Option C ships a
   non-`PUBLIC_` value into client JavaScript and thereby erodes the same signal, with none of the documentation
   the prefix carries.

### The recorded objection to `PUBLIC_LOG_LEVEL` is factually wrong

`157.1-DISCUSSION-POINTS.md:222-223` rejects option (c) as *"same as (b) plus a browser-settable level; widest
surface, and it lets a client set its own logging."*

Measured: a `PUBLIC_` variable is set by the **deployer**, filtered by `filter_env` (`utils/env.js:7-12`), and
serialised **read-only** into the page (`render.js:404`). There is no client-side write path back into `env` —
`$env/dynamic/public` in the browser re-exports the frozen payload. A client can of course tamper with its own
JavaScript at runtime, but that is true of every client value and the only consequence is that *that one
browser's own console* becomes chattier. Nothing reaches a shared sink (C4(a): there is no sink). The value is
**visible, not settable**, and its visibility discloses nothing — a log level is not a secret. The stated risk
does not exist on this codebase.

### Recommendation, and the minimum deviation stated plainly

> **Use `PUBLIC_LOG_LEVEL`.** Every other clause of C3 is honoured exactly: one env, `'warn'` as its default
> (C1), the same resolved level in both entry points (C2), and an `error`-level record on a missing or invalid
> value emitted **after** the fallback level is in force. The **only** deviation from the literal decision set is
> the six-character `PUBLIC_` prefix, which SvelteKit's `filter_env` makes non-negotiable for a browser-readable
> runtime variable.

Because this reverses an explicit operator rejection, the planner **must** gate it behind a
`checkpoint:human-verify` task before the plumbing lands, presenting: (a) the impossibility proof above, (b) the
falsity of the recorded objection, (c) Option C as the only alternative that keeps the name, and its three costs.

**If the operator refuses the prefix:** the minimum deviation flips to *C2 is honoured only after mount* —
i.e. Option C. Do not pick Option B under any circumstance; it is broken, not merely inelegant.

### Why "keep most untouched" is not available

Keeping a site untouched requires `parseImageColumn` to keep returning `Image | undefined`. That is the defect.
There is no third position: either the helper's return type carries the distinction (and every consumer must
acknowledge it, because TypeScript says so) or it does not (and D8 is not closed). CONTEXT B1(a) already accepted
this cost; the only open question was whether the cost could be *reduced*.

### The accessor, and why it is not option (d)


Option (d), which CONTEXT rejected, was *"a branded/Symbol empty — the tag is erased at every `??` and spread,
which is exactly where the bug lives."* Three properties separate `imageOf` from it:

1. **The erasure is a named, greppable function call**, not an implicit coercion. `grep -n imageOf` enumerates

**zod version: 4.3.6** (`yarn.lock:11682-11684`, `zod@npm:^4.3.6` → `version: 4.3.6`). Confirmed at runtime:

`undefined` and `String(undefined)` is the literal string `"undefined"`. `rejected` becomes `["undefined"]`; the
filter at `:87` drops nothing (no key is literally named `undefined`); the retry at `:88` re-parses the identical
value and fails identically; `:89` returns `{}`. Whole-column degradation, exactly as `:66` documents.

Also: `issue.path.join('.')` for that issue is `''` — an **empty string** in the logged `issues` array, which is
what "reported at the empty path" means in the record.

**The closure.** `path` names the *containing object*; `keys` names the *offending keys*. Read both:

```ts
/** Reduce a zod error to the top-level member names to drop, closing the empty-path hole (A2 NOTE, fact 3). */
function rejectedTopLevelMembers(error: z.ZodError): Array<string> {
  const rejected = new Set<string>();
  for (const issue of error.issues) {
    if (issue.path.length > 0) {
      rejected.add(String(issue.path[0]));            // nested or typed failure -> drop its top-level ancestor
    } else if (issue.code === 'unrecognized_keys') {
      for (const key of issue.keys) rejected.add(key); // THE HOLE: the key names itself here, not on `path`
    }
    // else: a root-level failure with no key to drop (e.g. the value is a string, not an object)
    //       -> no member can be removed; the outcome is `malformed` with no survivor.
  }
  return [...rejected];
}
```

Note `keys` is an **array** (zod batches all unrecognised keys of one object into one issue), so the loop is
required — a `keys[0]` read would leave a second unknown key in place.

`if (raw == null || typeof raw !== 'object' || Array.isArray(raw)) return {};` — a non-object value has no
members to preserve. In the generalised helper this becomes `parseMalformed(issues)` with no survivor, which is
still distinguishable from `absent`.

### What "pino/OTel-conformant" concretely means here (C4 NOTE 1)

The record is a flat JSON object with pino's three wire fields (`level` numeric, `time` epoch-ms, `msg`), OTel's
`severityText`, an OTel-style `attributes` bag for everything caller-supplied, and a serialised `err`
(`logger.ts:43-57`, present because `JSON.stringify(new Error('x'))` is `{}`).

**Three concrete obligations this places on every record this phase writes or touches:**

1. **A stable `msg` string with no interpolation.** Every new record's `msg` must be a constant; all varying
   data goes in `fields` and lands in `attributes`. A PostHog transport keys events on a stable name; an
   interpolated `msg` produces a distinct event per row id. The four existing sites already comply
   (`parseJsonbColumn.ts:30`, `supabaseDataProvider.ts:79,114`, `supabaseAdminWriter.ts:99`).
2. **A flat property bag.** `attributes` values should be primitives or arrays of primitives. The existing
   `issues: issues.map(i => i.path.join('.'))` (`parseJsonbColumn.ts:33`) is the right shape and should be kept
   — including for `unrecognized_keys` issues, where the recommended addition is a **sibling** flat field
   (e.g. `rejectedKeys: ['bogusTop']`) rather than a nested object.
3. **Never the offending value.** `parseJsonbColumn.ts:8-11` and the T-157-17 references make this a standing
   rule; `parseJsonbColumn.test.ts:52-56` and `supabaseDataProvider.test.ts:269` are its assertions. The new
   `rejectedKeys` field carries **key names**, never values — worth a dedicated assertion.

**Known non-conformance already in the tree, for the planner's awareness (not necessarily this phase's to fix):**
`isValidResult.ts:21` emits `log.error(\`Invalid result from DataProvider: ${error}\`)` — a free-form
interpolated string with no `attributes`. It is on the path B2 touches. Fixing it is a two-line, in-blast-radius
improvement; leaving it is defensible. Name the choice rather than drifting into it.

### The `LOG_LEVEL` resolver, and how C3's error is made visible

`app-shared` must **not** read the environment (`logger.type.ts:35`). The resolver therefore lives in the
frontend and is called by both entry points.

```ts
// apps/frontend/src/lib/utils/logLevel.ts  (NEW)
const EMITTABLE = ['debug', 'info', 'warn', 'error'] as const;   // NOT 'silent' — see below

export function resolveLogLevel(raw: string | undefined, dev: boolean, publicDebug: boolean):
  { level: LogLevel; problem?: { reason: 'missing' | 'invalid'; provided?: string } } {
  if (raw == null || raw === '') {
    return { level: dev || publicDebug ? 'debug' : 'warn', problem: { reason: 'missing' } };
  }
  const normalised = raw.trim().toLowerCase();
  if ((EMITTABLE as ReadonlyArray<string>).includes(normalised)) return { level: normalised as LogLevel };
  return { level: dev || publicDebug ? 'debug' : 'warn', problem: { reason: 'invalid', provided: normalised } };
}
```

Both hooks then become (identical text in both files, as `:15`/`:7` are today):

```ts
// ORDER IS LOAD-BEARING (C3 NOTE): configureLogger FIRST, so the fallback level is in force before the
// record about the fallback is emitted. Emitting first would make the message about silence itself silent.
const { level, problem } = resolveLogLevel(constants.PUBLIC_LOG_LEVEL, import.meta.env.DEV, constants.PUBLIC_DEBUG);
configureLogger({ level });
if (problem) log.error('PUBLIC_LOG_LEVEL is unusable; the logger fell back to a default level.', { ...problem, level });
```

**Four design points the planner must decide or inherit:**

1. **`'silent'` is deliberately not in the accepted vocabulary.** Accepting it would let one env value
   reintroduce the exact production silence this phase closes, with no signal. Recommendation: treat `'silent'`
   as `invalid` — it produces an `error` record naming it and falls back to `'warn'`. This is a judgement call
   CONTEXT does not settle; flag it in the plan.
2. **`missing` is the default case, and it will fire on every existing deployment.** Neither `.env.example`,
   `render.example.yaml` nor `docker-compose.dev.yml` sets the variable today, so until they are updated *every*
   boot emits one `error` record. That is what "log an error if the env is missing" asks for, and it is
   self-limiting (one record per module graph per boot). The three config files must all be updated in the same
   plan so a fresh checkout is quiet.
3. **`DEV || PUBLIC_DEBUG` is retained as the *fallback*, not overridden.** An explicit `PUBLIC_LOG_LEVEL` wins;
   with none set, dev keeps its `'debug'`. This preserves developer DX and is behaviour-neutral for anyone who
   never sets the new variable — except that production moves from `'silent'` to `'warn'`, which is the point.
4. **`constants.ts` gets one line**, matching the shape at `:11-12`:
   `PUBLIC_LOG_LEVEL: env.PUBLIC_LOG_LEVEL ?? ''` (a raw passthrough; `resolveLogLevel` owns the normalisation
   so it can distinguish `missing` from `invalid`).

## Common Pitfalls

### P1 — Letting the outcome type escape the adapter
**What goes wrong:** `_getAppSettings` returns `ParseOutcome<StoredSettings>`; four voter loaders
(`(voters)/elections/+page.ts:27` and three siblings) call
`mergeAppSettings(staticSettings, await appSettingsData)` with **no** `instanceof Error` or status guard, and
spread `status` / `issues` into the app's settings object.
**Why it happens:** the natural refactor pushes the new type outward.
**Avoid:** the `DataProvider` / `DataWriter` **public** signatures are frozen. The outcome is consumed inside the
method that produced it.
**Warning sign:** `svelte-check` reports errors in `routes/(voters)/**` — none of those files should change.

### P2 — Assuming `parseImageColumn`'s callers can absorb a type change silently
**What goes wrong:** eight of the ten sites sit inside `as ElectionData` / `as AnyEntityVariantData` casts
(`supabaseDataProvider.ts:229,262,284,509,561,610`). A cast can **swallow** the wrong property type.
**Avoid:** after changing the return type, verify the RED by reverting one wrapper call and confirming
`svelte-check` (not `vite build`) reports it. `E2`'s inclusion of `svelte-check` exists for exactly this.

casually — it is outside scope (fact 16) — but do not rely on the teardown clearing the sink either.

### The generalised partial-preserve helper (the A2 core)

```ts
// apps/frontend/src/lib/api/adapters/supabase/utils/parseOutcome.ts
// Source: generalised from supabaseDataProvider.ts:72-90 (shipped); the `issue.keys` branch is new and
// closes the hole that file's own docstring names at :66. zod issue shapes verified against zod 4.3.6.

/**
 * Validate a JSONB value, preserving the top-level members zod accepts when one of the others is malformed.
 *
 * Three outcomes, never an empty value that means two things (D8):
 *  - `absent`    — the column held null/undefined. No record is emitted; absence is not a failure.
 *  - `ok`        — the whole value parsed.
 *  - `malformed` — it did not. `value` carries the re-parsed survivor when there is one, `undefined`
 *                  when nothing could be preserved, and `issues` always names what was rejected.
 */
export function parseWithPartialPreserve<TSchema extends z.ZodType>(
  schema: TSchema,
  raw: Json | undefined
): ParseOutcome<z.infer<TSchema>> {
  if (raw == null) return { status: 'absent' };

  const parsed = schema.safeParse(raw);
  if (parsed.success) return { status: 'ok', value: parsed.data };

  const issues = toIssues(parsed.error);

  // Nothing to preserve members OF: a non-object value has no top-level members.
  if (typeof raw !== 'object' || Array.isArray(raw)) return { status: 'malformed', value: undefined, issues };

  const rejected = rejectedTopLevelMembers(parsed.error);
  if (rejected.length === 0) return { status: 'malformed', value: undefined, issues };

  const retained = Object.fromEntries(Object.entries(raw).filter(([key]) => !rejected.includes(key)));
  const retry = schema.safeParse(retained);
  return { status: 'malformed', value: retry.success ? retry.data : undefined, issues };
}
```

Note the trailing ternary `retry.success ? retry.data : undefined` — measured **silent** under the published G2
selector (fixture C4). Under the earlier, wider G2 draft it fired. The narrowing is load-bearing.
