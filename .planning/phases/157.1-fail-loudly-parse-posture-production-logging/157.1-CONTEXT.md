## Phase Boundary

**Retire the degrade-to-empty class at the Supabase adapter boundary, and make the production logger
actually speak.**

A `safeParse` failure at the boundary currently degrades to an empty value (`{}` / `undefined`), which is
byte-identical to what an ABSENT column returns — so one unacceptable field silently discards every other
value in the column and the caller cannot tell "absent" from "malformed". Widening the schemas in Phase 157
removed the known triggers; it did not remove the class. In parallel, `hooks.server.ts:15` /
`hooks.client.ts:7` pin the log level to `'silent'` outside dev, so every "degrades with one warning"
comment in the adapter layer is FALSE in production.

**Six deliverables:**

1. All **six** parse sites at the boundary return an outcome that distinguishes `absent` from `malformed`
   from `ok` (decisions A1, B1).
2. The read path preserves known-good members instead of discarding the column, generalised from the one
   place it already exists (A2) — including the hole where an unrecognised **top-level** key names no member
   to drop (A2 NOTE, fact 3).
3. `app_settings.settings` malformed no longer takes the whole app down: render on static∪dynamic defaults
   and emit one `error` record (B2).
4. `_setAnswers` no longer reports success on an unverified write, and no longer lets `resetAnswers()`
   discard the candidate's typing (B3, B4).
5. Production logging is on: a **`PUBLIC_LOG_LEVEL`** env defaulting to `'warn'`, same level server and
   browser, with a loud `error` record when the env is missing or invalid (C1, C2, C3).
6. A guard closes the class: an ESLint rule plus a `_guards/*.test.ts` lock-in self-test banning the
   defect *shape* (D1, D2).

**Package reach.** `apps/frontend/src/lib/api/adapters/supabase/**` (parse sites, provider, writer,
adminWriter), `apps/frontend/src/routes/+layout.svelte` + `+layout.ts` + `lib/utils/settings.ts` (the
validity gate, B2), `apps/frontend/src/lib/contexts/candidate/candidateUserDataState.svelte.ts` (B3/B4),
`apps/frontend/src/{hooks.server.ts,hooks.client.ts,lib/utils/constants.ts}` + `.env.example` +
`render.example.yaml` (C3),
`packages/app-shared/src/logging/**` (C4 NOTE — structure only), and `apps/frontend/src/lib/_guards/**`
plus the ESLint config (D1).

**Not in scope:**
- **Any further schema widening.** E3(a): widening is done (A-CR-01/02); this phase changes *posture* only.
  Re-widening would blur what the negative controls prove.
- **A durable log sink.** C4(a) and ruling D9: no Sentry, no JSON stdout sink, no third party. The `console`
  fallback (server-side: container stdout) stays.
- **Adapter instancing / concurrency.** That is Phase 157.2 (ruling D11).
- **Routing, auth surface, the admin outage.** That is Phase 158 (ruling D10).
- **New user-facing copy.** B4(a) reuses the existing save-failure path.

### A1 — Which parse sites are in scope · **(a) all six** `[★]`
The class is defined by the **shape**, not by the count the ruling enumerated. `StoredImageSchema` at
`parseJsonbColumn.ts:55` has the identical shape (safeParse fails → one warning → degrade to `undefined`)
and 10 downstream call sites (correction C-1). Leaving it out would repeat exactly the mistake the `157-18` gate made when it
fixed two instances without generalising.

**The six sites:** `parseJsonbColumn.ts:55` (image) · `parseJsonbColumn.ts:77` (answers) ·
`supabaseDataProvider.ts:73` + `:88` (customization, two-pass) · `supabaseDataProvider.ts:111` (settings) ·
`supabaseAdminWriter.ts:96` (sendEmail).

### A2 — The existing partial-preserve · **(a) generalise it** `[★]`
`parseStoredCustomization` (`supabaseDataProvider.ts:73-90`) already implements the ruling's option (a) — it
drops the top-level members zod flagged and re-parses the remainder — for one schema only. Generalise it
into the shared parse helper so **every read-path site** preserves known-good members. It is measured,
shipped behaviour with a test; making it the default removes a one-off and makes "one bad field discards the
column" false at every read site rather than at one.

**[NOTE] — binding, and it changes the work.** Fact 3: the existing implementation's own docstring names its
hole — an unrecognised **top-level** key is reported by zod at the empty path, so it names no member to drop,
the retry fails identically, and the whole column degrades anyway. **This hole must be closed explicitly**,
or partial-preserve keeps degrading whole-column on exactly the input D8 is about. Closing it is a required
task, not an optional refinement.

### B1 ⚠ — What "distinguishable from absence" means at the return type · **(a) a discriminated parse outcome** `[★]`
The phase's central decision; A2, B2, B3 and D2 all read off it.

Adapter parse helpers return a discriminated outcome — shape along the lines of
`{ status: 'ok' | 'absent' | 'malformed', value, issues }` — and each call site decides what to do with it.

**Why:** it is the only option that literally delivers the ruling ("the caller decides"); it does not force
one posture on six different consumers; and it makes the malformed case **typed** rather than conventional.
Accepted cost: it touches every call site, including the `parseImageColumn` callers — **10 of them, not 13**;
see correction C-1 below.

**Rejected:** (b) throw and ride the `Error`-passthrough — fact 8 makes that an app-wide error screen on one
malformed `app_settings` key, a worse production outcome than the defect. (c) an out-of-band signal — leaves
"absent" and "malformed" the same *value*, i.e. the class open while looking closed. (d) a branded/Symbol
empty — the tag is erased at every `??` and spread, which is exactly where the bug lives.

**The exact field names and whether the outcome is a discriminated union, a class, or a `Result`-alike is
Claude's discretion** — the constraint is that `absent` and `malformed` are distinguishable at the type
level by a consumer that does nothing special, and that the issues survive to the log record.

### B2 ⚠ — What the root layout does when `app_settings.settings` is malformed · **(a) render on defaults + one `error` record** `[★]`
The settings column is an **override** layer; the app has working defaults without it. Facts 8 and 9: the
merge at `lib/utils/settings.ts:35-41` already tolerates an `Error` and falls back to static∪dynamic
defaults — the outage comes from `+layout.svelte`'s `validity` `$derived` gate (`:71-84,86-87`), not from
the merge. So **the validity gate is what changes**: a malformed settings column must not set `ready = false`
and must not render the app-wide error branch.

`access.underMaintenance` / `access.answersLocked` defaulting to their static values is the correct fail-safe.
Failing the whole app closed over one unknown key would trade a silent defect for a loud outage, which is not
what D8 asked for.

Under C5(b) below, that one record is at `error` level.

**⚠ CORRECTED after research — the premise inverts and the work moves.** This decision was written assuming
the `validity` gate rejects an empty settings result. Measured at HEAD it does not: `+layout.svelte:72` calls
`isValidResult(data.appSettingsData, { allowEmpty: true })`, and `isValidResult`
(`lib/api/utils/isValidResult.ts:13-19`) returns `false` only for nullish, `Error`, or
empty-and-`allowEmpty:false`. **A `{}` settings result is already valid today.** The gate only becomes the
problem under design **(b)** — throw / return an `Error` — which B1 **rejected**. So under B1(a) + A2 a
malformed settings column already renders on defaults: **criterion 3 is satisfied by partial-preserve, not by
a gate edit. Do not loosen the gate.**

**What genuinely must change is `+layout.svelte:87-89`, which this document originally did not name:**

```ts
const underMaintenance = $derived(
  !('error' in validity) && (validity.appSettingsData.access?.underMaintenance ?? false)
);
```

It reads `underMaintenance` off the **raw loader payload**, bypassing the static∪dynamic merge, and duplicates
the shipped default inline as `?? false`. Today that coincides with
`packages/app-shared/src/settings/dynamicSettings.ts:79-80`, so there is no observable defect — but it means a
malformed column silently **un-maintenances** an instance whose build-time `dynamicSettings` set
`underMaintenance: true`. That is exactly criterion 3's `access.underMaintenance` fail-safe clause. One-line
fix: read the merged value already in scope at `:50` — `appSettings.access?.underMaintenance`.

**Anchor drift:** the `:71-84,86-87` citation above is off by one at both ends. Measured: `validity` spans
`:65-83` (`$derived.by` opens `:71`, closes `:83`), `error` `:85`, `ready` `:86`, `underMaintenance` `:87-89`.

### B3 ⚠ — What `_setAnswers` does when the RPC read-back is malformed · **(a) surface a failure; do NOT clear the buffer** `[★]`
Fact 5 is the chain: `supabaseDataWriter.ts:300` returns `parseAnswersColumn(data, …) ?? {}`; the `{}` is
truthy so it passes `if (!updatedAnswers) throw`; it reaches `#mergeCandidateAnswers({})`; then
`resetAnswers()` clears the edit buffer and the caller returns `{ type: 'success' }`
(`candidateUserDataState.svelte.ts:244,248,250,263,267`).

The catastrophic half is **not** the empty return — it is `resetAnswers()` discarding the candidate's typing
on the strength of it. Keeping the buffer is recoverable; clearing it is not. The write itself succeeded; only
the read-back failed to parse, and the adapter must say so rather than report success.

**Rejected:** (b) re-read the row — a round trip on the write path, and it only moves the question to "what
if *that* read is malformed". (c) echo the input — reports a state the adapter did not verify. (d) keep `{}`
but block `resetAnswers()` — leaves a success-shaped return for the next consumer to trust the same way.

### B4 — What the candidate sees · **(a) reuse the existing save-failure path** `[★]`
No new UI surface in a phase with no UI scope. The user-visible outcome the existing path already renders —
"your answers were not saved, they are still here" — is the correct one. No new copy in 4 locales.

### B5 — What the inverted test asserts · **(a) assert the survivor, the record count, the issue paths, and rename** `[★]`
`supabaseDataProvider.test.ts:248-270` currently **specifies the defect**: its name says *"degrades to empty
settings and warns once when a nested key is unknown, rather than rejecting"* and it asserts
`expect(result).toEqual({})` on a fixture holding a valid `access: { candidateApp: true }`. The ruling forbids
deleting it.

Invert it: assert the **surviving** `access: { candidateApp: true }` value, **exactly one** log record, and
the issue paths — and **rename the test**, because its name states the old posture and would otherwise become
a lie. It then serves as the positive control for A2's partial-preserve and for B1's outcome in one spec.

**⚠ There is a SECOND defect-specifying test — invert it too.** `parseJsonbColumn.test.ts:42-50` asserts
`expect(result).toBeUndefined()` for `{ path: 'a.png', focalPoint: { x: 1, y: 2, bogus: 3 } }`, under the name
*"degrades on an unknown key at the nested focalPoint level, which top-level strictness does not reach"*.
Under A2 the offending top-level member `focalPoint` is dropped, `{ path: 'a.png' }` re-parses cleanly, and
the result becomes a **usable image with the focal point discarded** — the correct partial-preserve outcome.
Name and both assertions must be rewritten. **Treat it as B5's sibling: invert, do not delete.**
(`parseJsonbColumn.test.ts:33-40`, the `{ path: 42 }` case, keeps its outcome — dropping the required `path`
fails the retry too — but its return type changes.)

### C1 ⚠ — What level production runs at · **(a) `'warn'`** `[★]`
Fact 10: all four `log.warn` sites in the entire non-test tree are these parse degradations; 50 `log.error`
sites carry everything else; 36 `log.debug`; 0 `log.info`.

`'warn'` is the lowest level at which every degradation this phase is about becomes visible, and it admits
the 50 error sites for free. The 36 debug sites stay out, which is what keeps production logs readable.

**Interaction with the C5 overrule — checked, and it is coherent.** C1(b)'s objection to `'error'` was that
it would silence the four parse warnings; the operator did not choose `'error'`, they chose `'warn'` (by
leaving C1 untouched) **and** promoted the four sites to `error` (C5). Both changes point the same way: at
`'warn'`, all four promoted sites and all 50 error sites are visible. No conflict.

### C2 — Server and browser at the same level · **(a) same in both** `[★]`
One expression, two entry points (`hooks.server.ts:15`, `hooks.client.ts:7`), no divergence to keep in sync.
The browser half is where the candidate's lost-answers degradation actually happens, so silencing it would
cost exactly the signal B3 exists to produce.

### C3 — How the level is set · **(b) an env, named `PUBLIC_LOG_LEVEL`** `[✓ OPERATOR OVERRULE, amended 2026-08-31]`

**AMENDED after research.** The operator ticked (b) — *a `LOG_LEVEL` env* — over (c) *a `PUBLIC_LOG_LEVEL`
env*. Research proved (b) and **C2** (same level server and browser) are **mechanically exclusive**, and the
operator ruled on the conflict the same day: **take the substance of (b), take the name from (c).**

**Why (b)'s literal name is impossible.** Measured in `@sveltejs/kit@2.55.0`: `publicPrefix: 'PUBLIC_'` /
`privatePrefix: ''` (`options.js:124-125`), `filter_env` (`utils/env.js:7-12`), and only `public_env` is
serialised into the page (`render.js:404`). Importing `$env/dynamic/private` from `hooks.client.ts` is a
**build error**, not a runtime `undefined` (`vite/index.js:600-618`). The build-time bake CONTEXT originally
guessed at is dead too: `apps/frontend/Dockerfile:50` runs the build inside the image with no build `ARG`,
which is exactly why `constants.ts:1` reads `$env/dynamic/public` at runtime.

**And (c)'s recorded objection is factually wrong.** The discussion rejected `PUBLIC_LOG_LEVEL` because *"it
lets a client set its own logging"*. A `PUBLIC_` env is **baked and served to** the browser — the client reads
the value, it cannot set it. The objection describes a capability SvelteKit does not grant.

**Resolved:** introduce **`PUBLIC_LOG_LEVEL`**, read through `$env/dynamic/public` exactly as `PUBLIC_DEBUG`
is (`lib/utils/constants.ts:1,11`), with **`'warn'`** (C1) as its default, applied identically in
`hooks.server.ts` and `hooks.client.ts` (C2). Everything else about (b) stands unchanged.

The original (b) rationale, retained: fact 13 — none exists Fact 13: none exists
today — the only knob is `PUBLIC_DEBUG` (`lib/utils/constants.ts:11`); `LOG_LEVEL` appears only inside a
docstring (`logger.ts:26`) and a test comment (`logger.test.ts:180`) as a hypothetical. The logger's own
docstring anticipates it.

Required surface: `.env.example`, the constants module, the deploy config (`render.example.yaml` /
`docker-compose.dev.yml` as applicable), and the docs.

**Every occurrence of the name, here and in the plans, reads `PUBLIC_LOG_LEVEL`.** A plan or a checker that
regresses to a bare `LOG_LEVEL` is reintroducing a build error.

**[NOTE] — binding, and it closes this option's own stated risk.** *"Log an error if the env is missing or
wrong."* The recorded objection to (b) was that an unset or typo'd value is a silent misconfiguration — the
exact class this phase exists to close. So the resolution is not merely "read the env": an **absent** value
and an **unparseable/out-of-vocabulary** value must each emit an `error`-level record and then fall back to
the `'warn'` default. Fail loudly, do not fail closed — a bad `LOG_LEVEL` must not prevent the app booting,
because that would reintroduce B2's outage shape in the logging layer.

The record must be emitted at a point where it is actually visible — i.e. after the fallback level is in
force, not before, or the message about silence would itself be silent.

### C4 — Durable sink · **(a) none** `[★]`
Matches ruling D9. Keep the `console` default: fact 12 — with no sink configured the logger falls back to
`console.error` for level ≥ 40 and `console.info` below, so on the server that is container stdout, a real
and collectable sink. What is missing is *durable* and *client-side* reporting, and that stays out.

**[NOTE] — binding, two parts.**
1. *"Just make sure that logging structure is such that we can easily pipe it to Posthog or similar later."*
   This is a **structural constraint on this phase's records**, not deferred work: the records this phase
   emits (and the existing ones it touches) must carry a machine-readable, stable field shape — event name,
   level, and a flat property bag — so a later sink is a transport swap and not a re-instrumentation. The
   logger is already documented as pino/OTL-conformant (Phase 157 `157-01`); this note says do not regress
   that, and do not emit free-form interpolated strings for the new records.
2. *"Add as a todo to setup locally-hosted Posthog but to also compare to alternatives."* — **a backlog
   item, not phase work.** File it via `/gsd-capture` / the backlog: *evaluate self-hosted PostHog against
   alternatives for a durable log/analytics sink*. It must be filed by the end of this phase; it must not be
   implemented in it.

### C5 — warn→error promotion · **(b) promote all four to `error`** `[✓ OPERATOR OVERRULE]`
All four parse-degradation sites — `supabaseDataProvider.ts:78`, `:114`, `supabaseAdminWriter.ts:99`,
`parseJsonbColumn.ts:30` — move from `log.warn` to `log.error`. The write-path read-back failure (B3) is an
`error` as well.

**[NOTE] — the operator's stated reason:** *"Read degradations may also be critical."* This is the ground:
the recommended (a) rested on "a read-path degradation with preserved members is genuinely a warning", and
the operator rejected that premise. A read that silently returns fewer answers than the database holds is
not a warning in a voting-advice application.

Consequence to carry into the plans: after this change the tree has **zero** `log.warn` sites. That is
acceptable and expected; do not invent warn-level records to fill the gap, and do not treat the empty warn
tier as a defect in any guard or test that counts levels.

### D1 ⚠ — What enforces criterion 6 · **(a) ESLint rule + `_guards/*.test.ts` lock-in self-test** `[★]`
Fact 15: two in-tree precedents of exactly this shape —
`lib/_guards/eslint-adapter-boundary-guard.test.ts` and `lib/_guards/eslint-store-guard.test.ts` — each
linting virtual fixtures through the **real** config. It fires in the editor and in `lint:check`, and the
self-test proves the guard fires rather than assuming it.

**Rejected:** (b) a vitest source-scan — no editor feedback, hand-rolled matching. (c) a type-level
constraint — cannot see the `?? {}` and the empty-literal returns that are the actual defect shape.
(d) convention + review — zero mechanism; it is what was in place when the class opened.

### D2 — What the guard bans · **(a) the defect shape** `[★]`
Ban **a `safeParse` failure branch that returns an empty literal (`{}`, `[]`, `undefined`) inside the adapter
directories.** Banning the shape rather than a library call means it still fires when someone writes a new
schema, a new column or a new helper.

**Rejected:** (b) banning `z.strictObject` at the boundary — a `z.object` with the same degrade branch sails
through, and strictness is not itself the defect. (c) banning `?? {}` on a parse result — catches fact 5's
exact line and is trivially evaded by an intermediate variable.

### E1 — Negative-control discipline · **(a) one RED→GREEN round trip per instance** `[★]`
Prove the **old** posture fails the **new** assertion before the fix lands, per instance. It is the
milestone's stated non-negotiable ("prove the guard fails before claiming it guards") and it is how the six
Phase 157 review fixes were landed. Record each RED verbatim in the plan SUMMARY.

This applies to: each of the six parse sites' outcome change, the A2 top-level-key hole, B2's validity gate,
B3's buffer preservation, C3's missing/invalid-env error, and D1's guard self-test.

### E2 — The closing gate · **(a) full gate, single run** `[★]`
`yarn db:reset` first, then: **full E2E** + `build` + `lint` + `format` + `test:unit` + `svelte-check` +
pgTAP.

`svelte-check` is included because it caught three defects in Phase 157 that a green build and a green unit
suite did not. The DB prerequisite is **`db:reset`**, *not* `db:reset-with-data`.

**Measured correction:** `svelte-check` is **already inside `lint:check`** — root `lint:check`
(`package.json:45`) runs `yarn typecheck` → `turbo run typecheck` → the frontend's
`svelte-kit sync && svelte-check --tsconfig ./tsconfig.json`. The stricter `apps/frontend` `check` script adds
`--fail-on-warnings` and is in **no** chain. Plans must say which of the two they mean rather than listing
`svelte-check` as a bare extra link.

Not chosen: (b) skipping E2E — the cardinal rule admits no exemptions and the answers write path is
E2E-covered. (c) a 3× determinism run — no known flake in this phase's blast radius.

### E3 — Further schema widening · **(a) no** `[★]`

## Open Questions — RESOLVED by research (`157.1-RESEARCH.md`, 2026-08-31)

All five were answered with measured evidence. Kept here with their answers so a planner sees both the
question and its resolution rather than re-opening one.

1. **The parse-outcome encoding (B1) — RESOLVED.** A plain **discriminated union** `ParseOutcome<T>` tagged on
   `status`, with `value` and `issues`. A **class** was rejected: the value crosses SvelteKit's `devalue`
   load-data boundary, and CLAUDE.md records prior `instanceof` trouble in this repo. A `Result`-alike was
   rejected: two states, and D8 needs three. **The field names are load-bearing** — `status` avoids colliding
   with `DataApiActionResult.type`, `value` avoids shadowing Supabase's `data`, and **`issues` is the
   identifier the D2 guard's esquery selector keys on.**

2. **Where the type lives — RESOLVED: `apps/frontend/src/lib/api/adapters/supabase/utils/`, NOT
   `packages/app-shared`.** Decisive and non-obvious: the ESLint guard from D1 is scoped to `src/**` in
   `apps/frontend/eslint.config.mjs`, so a helper placed in `app-shared` sits **outside the guard's reach** —
   criterion 6 would close by inspection rather than by enforcement.

3. **`PUBLIC_LOG_LEVEL` (was: is `LOG_LEVEL` reachable in the browser?) — RESOLVED, and it changed a
   decision.** It is not reachable, honouring C2 and C3(b) literally is impossible, and the operator ruled

4. **Do all `parseImageColumn` call sites change? — RESOLVED: yes, all 10, and the compiler enforces it.**
