# Phase 157.1 Plan 05: Wave 4 — the last four parse sites, the retired one-off, and the inverted test Summary

The customization and settings reads and the email send-result validation now run through the shared
partial-preserve seam; the donor implementation that shipped that behaviour for one schema is gone; the
email path stopped reporting a success it never verified; and the test that specified the settings
defect asserts the surviving value under a rewritten name.

## What was built

**Task 1 — sites 3, 4 and 5 (`ad5757c3d`).** `parseStoredCustomization` kept its name and its role and
lost its body: it hands the schema and the raw value to `parseWithPartialPreserve` and answers
`outcome.value ?? {}`. The filter-and-retry loop, the `String(issue.path[0])` derivation that WAS the A2
hole, and the `log.warn` call all went with it. `_getAppSettings` was rebuilt the same way, with the
outcome consumed inside the method and the public return type untouched. Both degradation records are
now `error` (C5(b)) under re-authored constant event names; the settings message no longer says it is
falling back to empty settings, which partial preserve usually makes false. The `null` column now
reaches the helper unsubstituted, so an absent column is `absent` and emits no record.

**Task 2 — site 6 (`2464af32b`).** `sendEmail`'s declared return type widened to `SendEmailOutcome`, a
union whose failure arm speaks the `type` discriminant `DataApiActionResult` already carries. The
malformed branch returns that arm instead of the fully-populated object reporting zero sends, zero
failures and no results. `absent` joins it and emits its own record.

**Task 3 — the inverted case and ledger row 2 (`04ee9cc88`).** The defect-specifying case was inverted
and renamed on a byte-identical fixture, two new cases drive the top-level-key input end to end, and
ledger row 2's `2-NEW-E2E` cell was filled with a verbatim transcript of the same command `2-OLD` failed
under.

## Criterion conflicts — read these

Two acceptance criteria could not be satisfied exactly as written. Neither was worked around silently.

### 1. Task 3 — `grep -rn "log\.warn" apps/frontend/src packages/app-shared/src` returns nothing outside test files

**Unsatisfiable as written, and the plan's own prohibitions are why.** The grep returns exactly ONE
non-test line, and it is not a call site: it is a prose sentence inside the
`StoredNotificationSchema` docstring at `packages/app-shared/src/data/schemas/storedSettings.schema.ts:13`,
which describes the degradation this phase has just retired and refers to *"the accompanying
`log.warn`"*. This is the substring-not-declaration trap the brief flagged, hit for the third time in
this phase.

Fixing it means editing `packages/app-shared`, which the plan forbids twice: the prohibition *"MUST NOT
widen any schema … `git diff --name-only HEAD -- packages/app-shared` is empty"*, and task 1's criterion
requiring `git diff --name-only HEAD -- apps/frontend/src/routes packages` to be empty. Both are
satisfied, so the docstring stands.

**Discharged against the thing the criterion is about.** Zero `log.warn` CALL sites remain anywhere in
the non-test tree:

```
$ grep -rn "log\.warn(" apps packages | grep -v "\.test\."
(no output)
```

All four promotion sites are done. The stale docstring is logged as `DEF-1` in
`deferred-items.md`, with a note that it is now doubly false — the degradation it describes is gone AND
the level it names has moved.

### 2. Task 3 — "keep … the assertion that the serialised record does not contain the offending key's value"

**Satisfiable only after re-authoring, because two earlier decisions collide here.** The inherited
assertion is `expect(JSON.stringify(records[0])).not.toContain('bogusNestedKey')`, and
`157.1-RESEARCH.md` § "The inverted test (B5), stated concretely" transcribes it unchanged into the
inverted body. It cannot pass: wave 2's `reportParseFailure` deliberately emits `rejectedKeys`, and for
this fixture that array IS `['bogusNestedKey']`. Disclosing the refused key NAME is not an oversight —
it is the field that closes the A2 hole at all, because zod reports an unrecognised key at the empty
path and nothing else identifies it.

The plan's own `<behavior>` line already anticipates the correction, saying the offending key's **VALUE**
must not appear. But the fixture is frozen byte-identical by criterion 5, and that value is the number
`1`, which no substring assertion can meaningfully exclude.

**Resolution.** The assertion is replaced by an exhaustive `toEqual` on `records[0].attributes` — which
proves nothing at all rode along, rather than proving one named thing did not — plus
`expect(JSON.stringify(records[0])).not.toContain('"T"')`, which asserts the notification COPY from the
offending object is absent. That is the T-157-17 guarantee this fixture can actually express. Recorded
rather than quietly substituted, because the RESEARCH transcription will otherwise be copied again by
`157.1-08`.

## Deviations from Plan

### Auto-fixed / auto-added

**1. [Rule 2 — missing critical functionality] The `absent` arm at site 6 emits its own record**

- **Found during:** Task 2.
- **Issue:** The plan enumerates only `ok` and `malformed`. Under the shared helper an invocation
  returning `data: null` with no transport error resolves to `absent`, for which the helper is silent by
  design. Branching everything non-`ok` to failure without a record would have replaced one silent
  unverified outcome with another — a write path that ran, reported nothing, and logged nothing.
- **Fix:** the `absent` branch calls `reportParseFailure` with the SAME constant event name and an empty
  issue list, so exactly one `error` record is emitted on every non-`ok` path and the tier gains no
  second message. Annotated in the method's docstring with why a read column and an invocation response
  differ on this point.
- **Files modified:** `supabaseAdminWriter.ts`, `supabaseAdminWriter.test.ts` (one new case).
- **Commit:** `2464af32b`.

**2. [Rule 2] A narrowing helper in the admin writer spec**

- **Found during:** Task 2.
- **Issue:** widening `sendEmail`'s return type to a union broke the direct `result.sent` reads in the
  two passing cases, and `expect(result.type).toBe('success')` does not narrow a TypeScript type.
- **Fix:** a local `asSuccess` helper that throws with a useful message when the arm is wrong, so the
  reads stay direct property accesses rather than casts.
- **Files modified:** `supabaseAdminWriter.test.ts`. **Commit:** `2464af32b`.

**3. [Scope boundary — logged, not fixed]** `DEF-1` above. See `deferred-items.md`.
