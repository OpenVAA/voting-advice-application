# Phase 157.1 Plan 06: Consumer-Side Fail-Safe and Buffer Preservation Summary

Closed the two consumer-side defects the ruling called the severe ones: the answers write path can no longer report success on a read-back it did not verify, and the candidate's typing now survives that path because none of the three post-save resets runs on it. Also made the maintenance availability gate fail to its safe value by reading the merged settings rather than the raw loader payload.

## What was built

**Task 1 — the maintenance gate (`08f62b3d6`).** `+layout.svelte`'s `underMaintenance` derivation now reads `appSettings.access?.underMaintenance` — the merged static ∪ dynamic ∪ column value already aliased near the top of the file — instead of `validity.appSettingsData.access?.underMaintenance ?? false`, the DB column alone with the shipped default duplicated inline. A malformed settings column degrades to an empty object under wave 3's partial-preserve, so the inline default used to resolve the gate to OFF regardless of what the build-time `dynamicSettings` declared. The merged read falls back to the build-time value instead. Four merge-behaviour cases and one source-level case were added to `settings.test.ts`.

**Task 2 — the writer (`d0e079e5e`).** `_setAnswers` branches on the read-back's parse status: `ok` returns the parsed answers, `absent` and `malformed` both return the new `UNVERIFIED_ANSWERS` signal. The answers setter's declared return widened to `SetAnswersResult` at all three declaration points. Five cases added to the writer spec, including an exhaustive assertion on the record's attribute bag plus a `not.toContain` proving no part of the answer payload reaches the log.

**Task 3 — the store (`ffd6b0f0b`).** The answers branch exits with `{ type: 'failure' }` before the merge and before all three resets. The pre-existing nullish guard kept its position; only its consequent changed. Four cases added to the store spec.

### Deliberate scope refusals

**The third save caller was left alone, as the plan requires.** `apps/frontend/src/routes/candidate/(protected)/+layout.svelte` — the terms-acceptance path — does `await userData.save()` inside a `try` with **no result check**, then unconditionally sets `status = 'success'`. Measured at `handleSubmit()`, lines 43-55.

This is a knowingly-unchecked entrance and it is **not** fixed here. Worth stating precisely, because the interaction is slightly worse than "it ignores a return value": that handler saves terms acceptance, but `save()` is a composite — if the candidate also has buffered answers, the answers branch runs first, and an unverified answers read-back now returns `{ type: 'failure' }` **before** the property write is attempted. This caller would report success for a save that did neither. That is a pre-existing gap in the same shape it had before this plan (a throw would have been caught and shown the error branch, where a failure return is now silently discarded), and widening scope to it has no decision behind it. Flagged for a future plan; logged below.

**The read-path collapse at `supabaseDataWriter.ts:206` was left alone.** `answersOf(parseAnswersColumn(...)) ?? {}` on the candidate's own answers READ is the recorded discretion call `157.1-04 D-DISC-3`, not this plan's site.
