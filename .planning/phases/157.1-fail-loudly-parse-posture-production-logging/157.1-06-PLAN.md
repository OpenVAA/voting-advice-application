<objective>
Close the two consumer-side defects the ruling called the severe ones, and make the availability gate
fail safe.

**Purpose, half one — the write path.** Fact 5 is the measured chain: after a SUCCESSFUL upsert, the
writer returns the parsed read-back coalesced to an empty object; that empty object is truthy, so it
passes the store's nullish guard, reaches the merge, and then three resets run and the caller returns a
success result. The catastrophic step is not the empty value — it is the reset discarding the
candidate's typing on the strength of it. Keeping the buffer is recoverable; clearing it is not. The
write itself succeeded; only the read-back failed to parse, and the adapter must say so rather than
report a success it did not verify.

**Purpose, half two — the availability gate.** Research correction C-2 found that decision B2's premise
inverts: the layout's validity gate already accepts an empty settings result, so criterion 3 is
satisfied by plan 05's partial-preserve and NOT by a gate edit. But the correction also found a line
CONTEXT never named. The maintenance derivation reads its value off the RAW loader payload, bypassing
the static-and-dynamic merge entirely, and duplicates the shipped default inline. Today that duplicate
coincides with the shipped default, so there is no observable defect — but it means a malformed column
silently UN-maintenances an instance whose build-time settings declared maintenance on. That is exactly
criterion 3's fail-safe clause, and the fix is one line: read the merged value the layout already has
in scope.

**Decision B4(a) needs zero new code, and that is a measured finding rather than an assumption.** Both
candidate route components already branch on a non-success save result and render the existing
save-failure message; that message exists in every shipped locale. A failure-typed return lands in the
identical branch a throw does. Research also found a THIRD caller — the terms-acceptance path in the
protected layout — which awaits the save with no result check at all. It is flagged here as a
knowingly-unchecked entrance and is deliberately NOT fixed: widening scope to it has no decision behind
it, and doing so silently is what decision B4(a) exists to prevent.

**One discretion call is recorded here. D-DISC-6:** the writer's answers method widens its declared
return to admit an unverified outcome, and the store's existing nullish guard keeps its position but
returns a failure-typed result instead of throwing. Rationale: research recommends returning the failure
rather than throwing, because a throw is logged as an interpolated string; and the guard is retained
rather than removed, which is what decision E1 requires of a guard whose negative control has not been
re-run. Both the genuinely-nullish case and the malformed case now preserve the buffer, which is
strictly better than today at both.
</objective>
