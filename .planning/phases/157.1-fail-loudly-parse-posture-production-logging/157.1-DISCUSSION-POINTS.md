## A. Scope boundary

### A1 — Which parse sites are in scope?

The ruling enumerated five schemas; fact 1 measures **six** sites. `StoredImageSchema` at
`parseJsonbColumn.ts:55` has the identical shape — `safeParse` fails, one warning, degrade to `undefined`,
13 call sites downstream.

- [ ] **(a) All six sites** — ★ RECOMMENDED — the class is defined by the *shape*, not by the count the
      ruling happened to enumerate. Leaving the sixth out is precisely the mistake the `157-18` gate made
      when it fixed two instances without generalising.
- [ ] **(b) Only the five the ruling named** — smaller diff, but ships a phase whose stated goal is "retire
      the class" while one member of the class stays untouched, on no principle.
- [ ] **(c) The two write-path sites only** (`_setAnswers`, `app_settings.settings`) — closes the severe
      instances fast; the class stays open and reopens on the next schema drift.

### A2 — What happens to the partial-preserve that already exists?

`parseStoredCustomization` (fact 2) is the ruling's option (a), already built, for one schema.

- [ ] **(a) Generalise it into the shared parse helper, so every read-path site preserves known-good members**
      — ★ RECOMMENDED — it is a measured, shipped behaviour with a test; making it the default removes a
      one-off and makes "one bad field discards the column" false at every read site rather than one.
- [ ] **(b) Leave it bespoke to customization** — no new abstraction, but the phase then hands the next
      reader two different postures at adjacent call sites with no rule distinguishing them.
- [ ] **(c) Remove it in favour of whatever B1 picks** — one posture everywhere; costs the publisher-name
      preservation that motivated it, which is a visible regression on a pure-presentation column.

**NOTE:** whichever wins, fact 3's hole (an unknown top-level key names no member to drop) must be closed
explicitly, or partial-preserve keeps degrading whole-column on exactly the input D8 is about.

## B. The fail-loudly shape ⚠

### B1 ⚠ DECIDE — What does "distinguishable from absence" actually mean at the return type?

This is the phase's central decision; A2, B2, B3 and D2 all read off it.

- [ ] **(a) A discriminated parse outcome returned by the adapter helpers** — e.g.
      `{ status: 'ok' | 'absent' | 'malformed', value, issues }` — each call site then decides — ★ RECOMMENDED
      — it is the only option that literally delivers the ruling ("the caller decides"), it does not force a
      posture on six different consumers, and it makes the malformed case *typed* rather than conventional.
      Cost: it touches every call site, including the 13 `parseImageColumn` callers.
- [ ] **(b) Throw at the adapter, ride the existing `Error`-passthrough** (fact 7) — smallest new surface and
      it reuses a real in-tree idiom. But fact 8: for `app_settings` that is an **app-wide error screen on one
      malformed key**, which is a worse production outcome than the defect being fixed unless B2 also changes.
- [ ] **(c) Keep bare return values, add an out-of-band signal** (a `lastParseFailure` on the adapter, or a
      thrown-away sentinel) — smallest diff, no call-site churn; but "absent" and "malformed" remain the same
      *value*, so the caller still cannot distinguish them without remembering to consult a side channel.
      This is the option most likely to leave the class open while looking closed.
- [ ] **(d) A branded/`Symbol`-tagged empty value** — type-level distinction with no signature change;
      clever, but the tag is erased at every `??` and spread in the existing consumers, which is where the
      bug lives.

### B2 ⚠ DECIDE — What does the ROOT LAYOUT do when `app_settings.settings` is malformed?

Facts 8 and 9: the merge already tolerates an `Error` and falls back to static defaults, but
`+layout.svelte`'s `validity` gate turns it into an app-wide error screen.

- [ ] **(a) Render normally on static∪dynamic defaults, and emit one `error`-level record** — ★ RECOMMENDED —
      the settings column is an *override* layer; the app has working defaults without it. Failing the whole
      app closed over one unknown key trades a silent defect for a loud outage, which is not what D8 asked
      for. `access.underMaintenance` / `access.answersLocked` defaulting to their static values is the
      correct fail-safe.
- [ ] **(b) Show the app-wide error screen (fail closed)** — maximally loud and unambiguous. Accepts that one
      bad JSONB key takes the site down, including for voters, and that nobody sees it until someone reports
      an outage.
- [ ] **(c) Enter maintenance mode** — visible and recoverable, but it hard-codes a product decision
      (site down for everyone) into a parse failure.

**NOTE:** if (b) is chosen, criterion 5's production logging becomes load-bearing for *diagnosing* the
outage, and C1 should be raised accordingly.

### B3 ⚠ DECIDE — What does `_setAnswers` do when the RPC read-back is malformed?

Fact 5. The write **succeeded**; only the read-back of what was written failed to parse.

- [ ] **(a) Surface a failure to the caller so the edit buffer is NOT cleared** — ★ RECOMMENDED — the
      catastrophic half of this defect is not the empty return, it is `resetAnswers()` discarding the
      candidate's typing on the strength of it. Keeping the buffer is recoverable; clearing it is not.
- [ ] **(b) Re-read the row and return the stored answers** — the write did land, so a second read is the
      most truthful answer. Costs a round trip on the write path and leaves the question of what to do when
      *that* read is malformed too.
- [ ] **(c) Return the answers that were just sent** (echo the input) — no round trip, buffer safe; but it
      reports a state the adapter did not actually verify, which is a smaller version of the same lie.
- [ ] **(d) Keep `{}` but block `resetAnswers()` on it** — minimal diff; leaves a success-shaped return that
      the next consumer will trust the same way this one did.

### B4 — Does the candidate see anything different?

- [ ] **(a) Reuse the existing save-failure path — the generic error the save flow already renders** —
      ★ RECOMMENDED — no new UI surface in a phase with no UI scope, and the user-visible outcome ("your
      answers were not saved, they are still here") is correct.
- [ ] **(b) A distinct message naming a data problem** — more honest to the user, but it is new copy in
      4 locales for a state that should be near-impossible after this phase.
- [ ] **(c) Nothing user-visible; log only** — keeps the diff smallest and leaves the candidate unable to
      tell a save happened or not, which is the defect.

### B5 — What does the inverted test at `supabaseDataProvider.test.ts:248-270` assert?

The ruling forbids deleting it. Fact 6: its *name* also states the old posture and would become a lie.

- [ ] **(a) Assert the surviving `access: { candidateApp: true }` value, plus exactly one record, plus the
      issue paths, and rename the test** — ★ RECOMMENDED — it becomes the positive control for A2's
      partial-preserve and for B1's outcome in one spec, and the rename stops the file describing the
      behaviour it no longer has.
- [ ] **(b) Assert only the new outcome discriminant** (`status: 'malformed'`) without asserting the
      surviving value — proves B1 landed, proves nothing about A2.
- [ ] **(c) Keep the assertion and add a second test for the new posture** — preserves history, but leaves a
      green test asserting `toEqual({})` on a valid `access` value, which is the specification of the defect.

## C. Production logging ⚠

### C1 ⚠ DECIDE — What level does production run at?

Fact 10: all four `log.warn` sites are the parse degradations; 50 `log.error` sites carry everything else.

- [ ] **(a) `'warn'`** — ★ RECOMMENDED — it is the lowest level at which every degradation this phase is
      about becomes visible, and it admits the 50 error sites for free. `'debug'`'s 36 sites stay out, which
      is what keeps production logs readable.
- [ ] **(b) `'error'`** — quietest option that still reports; **silences all four parse warnings**, i.e. it
      does not satisfy criterion 5's own sentence ("every 'degrades with one warning' comment is observed to
      be TRUE in a production build"). Only coherent if C5 also promotes them to `error`.
- [ ] **(c) `'info'`** — includes info records; there are currently zero, so it is `'warn'` plus a promise.
- [ ] **(d) `'debug'`** — everything on, everywhere. 36 debug sites in production output; effectively
      turning `PUBLIC_DEBUG` on permanently.

### C2 — Do the server and browser graphs run at the same level?

- [ ] **(a) Same level in both** — ★ RECOMMENDED — one expression, two entry points, no divergence to keep in
      sync; and the browser half is where a candidate's lost-answers degradation actually happens.
- [ ] **(b) Server at C1's level, browser stays `'silent'`** — no console noise for end users and no chance of
      leaking a record into a shared screen. Costs exactly the client-side signal the answers defect needs.
- [ ] **(c) Server at C1's level, browser at `'error'`** — a middle setting that silences the four warn sites
      in the browser, which is where three of them can fire.

### C3 — How is the level set?

- [ ] **(a) Change the false branch of the existing ternary from `'silent'` to C1's level, in both files** —
      ★ RECOMMENDED — two-line diff, no new configuration surface, no new env to document or plumb into
      Render/Docker, and it is exactly the scope D9 authorised.
- [x] **(b) Introduce a `LOG_LEVEL` env with C1's level as its default** (fact 13: none exists) — operationally
      nicer, and the logger's own docstring anticipates it. Adds an env to `.env.example`, the constants
      module, the deploy config and the docs — and an unset/typo'd value is a silent misconfiguration, the
      exact class this phase exists to close.
- [ ] **(c) A `PUBLIC_LOG_LEVEL` public env** — same as (b) plus a browser-settable level; widest surface,
      and it lets a client set its own logging.

**INFO**: Log an error if the env is missing or wrong.

### C4 — Is a durable sink in scope?

D9 says no. Confirming it here so the planner does not re-open it.

- [x] **(a) No sink. Keep the `console` default (fact 12: server-side that is container stdout)** —
      ★ RECOMMENDED — matches the ruling, and stdout on the server is already a real, collectable sink.
- [ ] **(b) Add a structured JSON stdout sink on the server** — modest, no third party, better machine
      readability. Still scope the ruling did not grant.
- [ ] **(c) Wire Sentry or equivalent** — explicitly deferred to backlog by D9; would make this phase a
      logging-infrastructure phase.

**NOTE**: Just make sure that logging structure is such that we can easily pipe it to Posthog or similar later. Add as a todo to setup locally-hosted Posthog but to also compare to alternatives.

### C5 — Do any parse degradations get promoted from `warn` to `error`?

- [ ] **(a) No — all four stay `warn`; the write-path read-back failure (B3) is the one new `error`** —
      ★ RECOMMENDED — a read-path degradation with preserved members is genuinely a warning; a write that
      reports success without verifying what it wrote is not.
- [x] **(b) Promote all four to `error`** — makes them survive a C1 = `'error'` setting; costs the level
      distinction entirely.
- [ ] **(c) Keep all four at `warn`, including the write-path one** — one uniform level; loses the severity
      signal exactly where it matters most.


**NOTE**: Read degradations may also be critical.

## D. Keeping the class closed ⚠

### D1 ⚠ DECIDE — What mechanism enforces criterion 6?

Fact 15: two in-tree precedents already do this shape.

- [ ] **(a) An ESLint rule plus a `_guards/*.test.ts` lock-in self-test** — ★ RECOMMENDED — it is the
      established pattern in this exact repository (`eslint-adapter-boundary-guard.test.ts`,
      `eslint-store-guard.test.ts`), it fires in the editor and in `lint:check`, and the self-test proves the
      guard fires rather than assuming it.
- [ ] **(b) A vitest source-scanning test** (the `translations.test.ts` shape) — no ESLint config surgery,
      but it only fails in `test:unit`, gives no editor feedback, and hand-rolls its own matching.
- [ ] **(c) A type-level constraint** — strongest guarantee where it applies; it cannot see the `?? {}` and
      the empty-literal returns that are the actual defect shape.
- [ ] **(d) Convention + code review** — zero mechanism. This is what was in place when the class opened.

### D2 — What exactly does the guard ban?

- [ ] **(a) A `safeParse` failure branch that returns an empty literal (`{}`, `[]`, `undefined`) inside the
      adapter directories** — ★ RECOMMENDED — it bans the defect *shape* rather than a library call, so it
      still fires when someone writes a new schema, a new column or a new helper.
- [ ] **(b) `z.strictObject` at the boundary** — bans the narrow-schema half; a `z.object` with the same
      degrade branch sails through, and strictness is not itself the defect.
- [ ] **(c) `?? {}` / `?? undefined` applied to a parse helper's result** — catches fact 5's exact line;
      trivially evaded by an intermediate variable.
