## Issues Encountered

### Pitfall P2 is REAL, and the compiler enumerated 8 of the 10 image sites, not 10

The plan asked for a single deliberate revert to prove the type checker is the detector. That probe passed — reverting `supabaseDataProvider.ts:225` produced, verbatim:

```
ERROR "src/lib/api/adapters/supabase/dataProvider/supabaseDataProvider.ts" 220:14
"Conversion of type '{ date: string | undefined; round: number | undefined; subtype: string | undefined;
image: ParseOutcome<Image>; constituencyGroupIds: string[]; }' to type 'ElectionData' may be a mistake
because neither type sufficiently overlaps with the other. If this was intentional, convert the
expression to 'unknown' first."
```

The wrapper was restored and the file re-verified byte-identical against a pre-probe copy.

Because P2's whole point is that an assertion can SWALLOW the change, one probe proving one site is caught is weak evidence about the other nine. So the probe was widened: all ten `imageOf` wrappers were unwrapped in one pass and `svelte-check` run once. Result — **8 of 10 reported, 2 swallowed**:

| # | Site | Reported? | Mechanism |
|---|------|-----------|-----------|
| 1 | `supabaseDataProvider.ts` `elections.image` | yes | `as ElectionData` |
| 2 | `supabaseDataProvider.ts` `constituency_groups.image` | yes | `as ConstituencyGroupData` |
| 3 | `supabaseDataProvider.ts` `constituencies.image` | yes | `as ConstituencyData` |
| 4 | `supabaseDataProvider.ts` `nominations.image` | **NO** | flows into `const nominationOut: Record<string, unknown>` — every property type is already `unknown` |
| 5 | `supabaseDataProvider.ts` `get_nominations.entity_image` | yes | reported indirectly, at the four entity-variant assignments consuming `base` (416, 424, 426, 428) |
| 6 | `supabaseDataProvider.ts` `` `${table}.image` `` | yes | `as AnyEntityVariantData` |
| 7 | `supabaseDataProvider.ts` `question_categories.image` | yes | `as QuestionCategoryData` |
| 8 | `supabaseDataProvider.ts` `questions.image` | yes | `as AnyQuestionVariantData` |
| 9 | `supabaseDataWriter.ts` `getCandidateUserData` | yes | `as LocalizedCandidateData` |
| 10 | `supabaseDataWriter.ts` `_updateEntityProperties` | **NO** | `as unknown as LocalizedCandidateData` — the double assertion defeats the overlap check entirely |

**What this means, stated plainly.** The plan's must-have truth *"the compiler — not discipline — is what enforced that none was missed"* is **true for eight sites and false for two**. Sites 4 and 10 were migrated because research's enumerated table named them, i.e. by discipline. Had that table been wrong, `yarn lint:check` would still have exited 0 with two sites silently handing a `ParseOutcome<Image>` object into a field typed `Image | undefined` — which at site 10 would have put `{ status, value, issues }` on a candidate profile's `image` property at runtime.

Note also that research's P2 write-up named the swallowing lines as `229, 262, 284, 509, 561, 610` — none of which is site 4 or site 10. The two sites that actually swallow were **not** among the ones P2 predicted, and the mechanism at site 4 (`Record<string, unknown>`) is not an assertion at all.

**Not fixed here, and why.** Removing the `as unknown as` at site 10 or typing `nominationOut` is a change to code this plan does not own, would alter shapes consumed elsewhere, and is squarely a Rule 4 architectural call rather than a Rule 1–3 auto-fix. It is surfaced instead, because `157.1-07`'s ESLint guard is the natural home for a lock against it and `157.1-08` reads this record at phase close.
