## Why this ledger exists — and what it does NOT claim

The standing milestone rule, quoted through `157-NEGATIVE-CONTROL-LEDGER.md` from `REQUIREMENTS.md:7-13`:

> **prove the guard fails before claiming it guards** — negative control run twice, once against the old
> assertion to demonstrate blindness, once against the new one to demonstrate the catch.

A blindness measurement taken *after* the subject moved is not a measurement of blindness. That is why
this register is opened in wave 0, before `157.1-02` touches the first application file: **every OLD half
is scheduled in the plan that is about to move that row's subject**, which is the only ordering under
which the OLD half is a measurement of the pre-change tree rather than a claim about it. Once a subject
moves, its OLD half can never be taken again.

**What this ledger does NOT claim.**

1. It does not claim any behaviour is fixed. At `157.1-01` close, nothing is fixed; three spec files and
   this document are the entire output of wave 0.
2. It does not claim the seven rows exhaust the phase's verification. They are the **negative controls**;
   the positive assertions live in the specs and in `157.1-VALIDATION.md`'s criterion map.
3. It does not claim row 6's twelve fixtures exhaust the defect class. `157.1-RESEARCH.md` § "What the
   guard cannot see" lists four forms no esquery selector can reach; the guard is a lock against
   *reopening the measured shape*, not a proof of impossibility.

## Row 1 — Six parse sites: malformed is indistinguishable from absent

- **Owner:** `157.1-04` (both halves).
- **Subject files:** `apps/frontend/src/lib/api/adapters/supabase/utils/parseJsonbColumn.ts`.
- **Instance class:** `157.1-CONTEXT.md` § E1, "each of the six parse sites' outcome change"; criterion 1.
- **OLD-half command:** a vitest case asserting that `parseImageColumn` given a structurally malformed
  stored value and `parseImageColumn` given `null` return values that **differ**. At HEAD both return
  `undefined`, so the assertion must be observed RED.
- **NEW-half command:** the same assertion, unchanged, after the site returns a parse outcome. The two
  calls must then yield different `status` literals.
- **Expected:** OLD — RED, the two returns are `===`. NEW — GREEN, `malformed` ≠ `absent` by value.

**The blind state, stated exactly, as it was at the moment `1-OLD` was taken.** `parseImageColumn`
(`parseJsonbColumn.ts:48-62`) returned `Image | undefined`, and both of its exits produced the *same*
value: `:53` `if (stored == null) return undefined;` for an ABSENT column, and `:58` `return undefined;`
six lines later for a MALFORMED one. The two were indistinguishable **by construction** at all ten call
sites — a `??` chain, a spread, or an `expect(...).toBeUndefined()` cannot tell them apart, and no
logging change could, because the returned VALUE is what the call sites consume. That is fact 4 and the
D8 class in its purest form. The measurement was taken by adding **one** temporary case to the util spec
— asserting only that the two returns *differ*, with no reference to any new type — and running it
against the otherwise byte-identical tree. The probe was reverted immediately afterwards and the revert
proven by blob hash (below); no source file was changed at any point before the measurement.

**Why the assertion is `not.toEqual` rather than `not.toBe`.** `toBe` would pass trivially for two
distinct object references once the site returns an outcome, which would make the GREEN half prove
nothing. Deep inequality is the honest form of the question: *do the two calls yield different values?*
At HEAD both yield `undefined`, so it fails; after the change they yield `{ status: 'malformed', … }`
and `{ status: 'absent' }`, so it passes on the substance rather than on identity.

## Row 3 — B2 `underMaintenance` fail-safe (correction C-2)

- **Owner:** `157.1-06` (both halves).
- **Subject file:** `apps/frontend/src/routes/+layout.svelte`.
- **Instance class:** `157.1-CONTEXT.md` § E1, "B2's validity gate", as corrected by
  `157.1-RESEARCH.md` § C-2; criterion 3.
- **OLD-half command:** with the build-time dynamic settings declaring maintenance **on** and the stored
  settings column **malformed**, assert that the root layout's `underMaintenance` derivation yields the
  **maintained** value. At HEAD it yields the un-maintenanced value, so the assertion must be observed
  RED. The fail-safe direction is load-bearing: a malformed column must not be able to switch maintenance
  mode off.
- **NEW-half command:** the same assertion after the derivation reads the parse outcome.
- **Expected:** OLD — RED, the derivation yields the un-maintenanced value. NEW — GREEN, it yields the
  maintained value.

**Correction to this row's own pre-registered halves.** The `Half` descriptors above were written under
CONTEXT **B2**'s premise — that the layout's *validity gate* is what changes, and that the maintenance
derivation would come to read a `ParseOutcome`. Research **C-2** measured that premise as inverted:
`isValidResult(data.appSettingsData, { allowEmpty: true })` already accepts an empty settings result, so a
malformed column never reaches the app-wide error branch and the gate needed **no** edit. No `ParseOutcome`
reaches `+layout.svelte` at all — the loader payload is a plain settings object either way. What actually
changed is the derivation's **source**: from the RAW loader payload (the DB column alone, with the shipped
default duplicated inline) to the MERGED static ∪ dynamic ∪ column value already aliased in the file. The
halves are restated accordingly. The fail-safe direction the row registered is unchanged and is what was
measured.

**The blind state, stated exactly, as it was at the moment `3-OLD` was taken.** `+layout.svelte:87-89` read:

```ts
const underMaintenance = $derived(
  !('error' in validity) && (validity.appSettingsData.access?.underMaintenance ?? false)
);
```

`validity.appSettingsData` is the DB column alone. Under decision **B1(a)** plus **A2**, a malformed
settings column is degraded by partial preserve to an empty object rather than to an `Error`, so the
`access` member is absent from the payload and the inline `?? false` resolved the gate to OFF — regardless
of what the build-time `dynamicSettings` declared. The duplicate coincides with the shipped default
(`dynamicSettings.ts:79-80`), which is precisely why nothing was observably broken and why only an
assertion in the **fail-safe direction** can catch it.

**Two measurements, because one alone would prove nothing.** `+layout.svelte` is a route component with no
unit harness, so the row is measured at two levels:

1. **Merge-model** — a temporary probe asserting the merged read resolves ON while the raw-payload read,
   transcribed verbatim from HEAD, resolves OFF from the same inputs. This isolates *which of the two
   sources* produces the wrong answer, and the merged assertion is deliberately placed FIRST so the
   transcript shows it passing before the raw-payload one fails.
2. **Source-level** — the permanent case reading `+layout.svelte` off disk and asserting the derivation
   contains `appSettings.access` and contains neither `validity.appSettingsData` nor the inline default.
   This is the half that is genuinely coupled to the source: the merge has *always* resolved fail-safe, so
   a merge-only assertion would have been green before the fix and would have measured nothing.
