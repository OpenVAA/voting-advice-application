<objective>
Build the seam the whole phase reads off: a three-state parse outcome, and one shared helper that
preserves the members zod accepts instead of discarding the column.

**Purpose.** Ruling **D8** retires a class, not its instances: a strict schema describes a JSONB column
more narrowly than the database permits, the consuming validation degrades a failure to an empty value,
and that empty value is byte-identical to what an ABSENT column returns. Fact 4 is the class in its
purest form — one parse helper returns the same `undefined` for "the column held nothing" and "the
column held something unacceptable". No amount of added logging closes that; only a return type can.

**Decision B1(a) is settled and research fixed its encoding**: a plain discriminated union
`ParseOutcome<T>` tagged on `status`, with `value` and `issues`. The field names are load-bearing, not
stylistic — `status` avoids colliding with the action-result discriminant, `value` avoids shadowing the
Supabase destructuring name present in every adapter method, and `issues` is the identifier the guard
selector in plan 07 keys on.

**Decision A2's NOTE is the other half, and it changes the work.** Partial-preserve already ships, for
one schema, at `supabaseDataProvider.ts:63-90` — and that function's own docstring names its hole: an
unrecognised top-level key is reported by zod at the empty path, so it names no member to drop, the
retry fails identically, and the whole column degrades anyway. Research measured the closure against
zod 4.3.6: the key that names no member on the path names itself on the issue's `keys` array. Reading
`keys` closes it. `keys` is an array — zod batches every unrecognised key of one object into one issue
— so the loop is required.

**Placement is decisive and non-obvious.** Both new modules live in the adapter's own `utils` directory,
NOT in `packages/app-shared`. The plan-07 guard is scoped to the frontend `src` tree; a helper in
`app-shared` sits outside its reach, and criterion 6 would then close by inspection rather than by
enforcement — the exact failure mode this phase exists to retire.

This plan is additive. It migrates nothing; plans 04 and 05 move the six sites onto it.
</objective>

  <behavior>
    - `parseWithPartialPreserve(schema, raw)` with a nullish raw value returns the `absent` arm and emits nothing; absence is not a failure.
    - The same call with a fully valid value returns the `ok` arm carrying the parsed value.
    - With a value whose single defect is an unrecognised NESTED key, the offending top-level ancestor is dropped, the remainder re-parses, and the result is the `malformed` arm carrying the surviving members.
    - With a value whose single defect is an unrecognised TOP-LEVEL key, that key is read off the issue's `keys` array, dropped, and the remainder re-parses — the `malformed` arm carries the surviving members. This is the A2 hole closed.
    - With BOTH defects at once, both members are dropped in one pass and whatever survives re-parses.
    - With a wrong type at a required member, dropping that member makes the retry fail too, so the arm is `malformed` with no survivor — still distinguishable from `absent`.
    - With a non-object value (a string, a number, an array), there are no top-level members to preserve; the arm is `malformed` with no survivor.
    - The helper never throws for any input.
    - `reportParseFailure` emits one `error`-level record whose message is a constant, carrying column, row id, issue paths, the rejected key names, and whether anything was preserved — and never the offending value.
