# Phase 157.1 — Over-Disclosure Audit: every interpolated `error` record, read once

**Threat `T-157.1-03`. Requirement D9 raised the production log level from `'silent'` to `'warn'`; that
single change promoted every pre-existing `error`-level record in this tree from developer-only to
collectable-from-container-stdout. This document is the control on what now crosses that boundary.**

- **Phase:** 157.1 (fail-loudly-parse-posture-production-logging)
- **Owning plan:** `157.1-08` (wave 7). The threat register assigned this mitigation here, after every
  record the phase promotes exists — an audit taken before wave 6 would have missed the records waves
  2–6 wrote.
- **HEAD read at:** `1fbd77966`
- **Corpus:** the non-test, non-build tree under `apps/` and `packages/`, i.e.
  `grep -rn "log\.error(" apps packages --include='*.ts' --include='*.svelte' --include='*.js'`
  minus `node_modules`, `/build/` and `*.test.*`.
- **Scope of ACTION, and its limit:** this audit **reads** every interpolated record once and
  dispositions each. It **restructures exactly one** — `isValidResult.ts`, decision **D-DISC-8**,
  recorded in `157.1-08-PLAN.md`'s objective and in research open question 4. Restructuring the others is
  a different piece of work with no decision behind it, and `157.1-08-PLAN.md`'s front-matter prohibition
  is what keeps it out of this phase. Every non-restructured finding below therefore names **what would
  have to change**, so it is actionable rather than a list.

---

## Why "interpolated" is the thing being counted

`157.1-RESEARCH.md` § "What \"pino/OTel-conformant\" concretely means here (C4 NOTE 1)" states the three
standing obligations a record must meet. The first is that the **message is a constant** and every
varying value travels in a **flat attribute bag** beside it, because a downstream sink keys events on a
stable `msg`. The second is that **the offending value never travels** — paths and refused key names may,
the content under them may not (`T-157-17`).

An interpolated message fails both at once. It makes the event name unkeyable, and it is the mechanism by
which an arbitrary runtime value — a caught provider error, a request parameter, an author-supplied
string — ends up inside a log line. So the interpolation is not a style question here; it is the carrier.

**What raising the level did NOT do.** It added no record. Every site below was already being written; it
was simply never emitted in production. That is why this audit is a control on an existing surface rather
than a review of new code, and why it is scheduled in the phase's last plan rather than its first.

### The empty `warn` tier is the intended end state, not a regression

**Decision C5(b) retired `warn` as a level this codebase emits at.** A JSONB column that does not match
its schema is a data defect a production operator has to act on, so the parse-failure record is `error`;
and the record that reports the logger's own misconfiguration must be visible at the level the logger
falls back to, so it is `error` too. Nothing was left that warranted the middle tier, and the tier emptied
as a consequence.

Three things follow, and pitfall **P7** exists because each has been got wrong before:

1. **No record may be invented to fill the tier.** An empty tier is a fact about this codebase's severity
   vocabulary, not a hole in it.
2. **No gate may count levels.** A check of the form "at least one site per level" would fail here for the
   correct code and pass for a codebase that downgraded a real defect to a warning to satisfy it.
3. **`'warn'` remains the production THRESHOLD and must not be raised to `'error'` on the strength of this
   census.** The threshold and the emitted levels are different things: `'warn'` is what
   `resolveLogLevel` returns when `PUBLIC_LOG_LEVEL` is unset, and leaving headroom below `error` is what
   lets a future `warn` record appear without a deployment-wide configuration change.

One textual reference to the retired level survived the phase and was corrected in `157.1-08`: a doc
comment at `packages/app-shared/src/data/schemas/storedSettings.schema.ts:13` narrated the settings-column
incident as reported by "the accompanying `log.warn`". That record is `log.error` since `157.1-03`. The
comment was prose about a record, not a record; correcting it is what makes
`grep -rn "log\.warn" apps/frontend/src packages/app-shared/src` return nothing outside test files, which
is `157.1-08`'s own acceptance criterion.

## How each site is dispositioned

Two facts decide it.

**(A) Can the record reach container stdout?** Requirement D9 configures the level in BOTH module graphs
(`hooks.server.ts` and `hooks.client.ts`). A record emitted on the server reaches the operator's
collectable stdout, which is a **new party**. A record emitted only in a browser reaches the console of
the very user whose own session produced it, which is **not** a new party and is not a disclosure in the
sense this threat is about. Where a site sits inside a `$effect` or a DOM event handler it is
client-only; where it sits in a `*.server.ts`, a `+server.ts`, a universal `+layout.ts`/`+page.ts` or a
`$derived` evaluated during SSR, it is server-reachable.

**(B) What can the interpolated value carry?** A code-authored constant, a route name or a UUID is not a
disclosure. A caught **provider** error's `message` is, on this stack: PostgREST surfaces the failing
statement's detail, so a Supabase error message can echo query text and therefore column values. A raw
request parameter is, because it is unbounded and attacker-chosen.

**Dispositions:** `restructure` — changed in this phase. `defer` — server-reachable and carrying something
that can be more than a name; a finding for a later phase, with the remediation named. `keep` — reading
it once was the point, and there is nothing to do.

## Finding 1 — RESTRUCTURED in this plan

| File:line (at `1fbd77966`) | Interpolated | Can carry | Disposition |
|---|---|---|---|
| `apps/frontend/src/lib/api/utils/isValidResult.ts:21` | `${error}`, where `error` is `result.message` for the `Error` branch — i.e. a **provider** error's own text | **Yes.** A Supabase/PostgREST error message can echo the failing query, and therefore column values | **restructure** |

**Why this one and not the others.** It is the only interpolated record that is simultaneously
(a) server-reachable — the root `+layout.svelte:72-77` guards `appSettingsData` and
`appCustomizationData` through it during SSR; (b) directly on the path this phase rebuilt, so a malformed
`app_settings.settings` column now travels through it; and (c) interpolating a provider error rather than
a message the application itself authored. Research open question 4 recommended it on exactly those
grounds and noted it is two lines and inside the blast radius.

**What changed.** The message became the constant `INVALID_RESULT_MESSAGE`; the branch that fired became
a flat `reason` attribute (`'nullish' | 'error' | 'empty'`); an optional `dataKey` was added to the
existing options bag so a caller that knows which collection it is validating can make the record
self-describing. The provider error is neither interpolated **nor** passed as `err` — `serialiseError`
would carry both its `message` and its `stack` into the same sink, so passing it there would move the
disclosure rather than remove it. The boolean contract is byte-for-byte the same for every input.

**Recorded deviation.** `157.1-08-PLAN.md` task 1 asks for "which data key was being validated" as a flat
attribute, and separately requires the diff to be exactly two paths. **No existing call site passes a data
key** — all twenty narrow `TData` from `result` alone — so a required parameter would have touched twenty
files and broken the plan's own diff criterion. It is therefore **optional** on the options bag: the
attribute exists and is asserted, existing callers are untouched, and adopting it is a one-word edit per
call site whenever a later phase wants it.

**Proof it is closed.** `isValidResult.test.ts` plants a sentinel inside a provider error's message,
serialises the WHOLE record and asserts the sentinel is absent while `reason === 'error'` is present. The
whole record rather than `msg` alone, deliberately: that also catches a future "fix" that moves the
provider text into `err` or into an attribute. Measured RED against the pre-fix helper —
`expected '[{"level":50,…,"msg":"Invalid result from DataProvider: SENTINEL_…"}]' not to contain 'SENTINEL_…'`.
