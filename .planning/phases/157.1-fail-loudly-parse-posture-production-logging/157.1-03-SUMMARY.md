# Phase 157.1 Plan 03: The ParseOutcome Seam Summary

**A malformed JSONB column is now a different value from an absent one — three `status` literals rather than one shared `undefined` — and an unrecognised top-level key names itself on `issue.keys`, is dropped by name and lets its valid siblings survive, which is the A2 hole closed against a RED that was measured on the shipped implementation before anything moved.**

## Accomplishments

- **Measured ledger row 2's blind half against the untouched provider.** One temporary vitest case fed `getAppCustomization` a stored customization carrying one valid `publisherName` plus one unrecognised top-level key and asserted the publisher name survives. It failed with `expected undefined to be 'Publisher EN'` at HEAD `ba989537c` — the whole column degraded to `{}`, exactly as `supabaseDataProvider.ts:66`'s own docstring predicts. The probe was reverted and the revert proven by blob hash (`3374080661708c4e5c09ff4efac409f700d514b1`, identical pre- and post-probe), not by claim.
- **Built the three-state outcome.** `ParseOutcome<TValue>` is a plain discriminated union tagged on `status` with arms `ok` / `absent` / `malformed`. Every arm declares the members it does not carry as optionally-undefined, so `outcome.value` and `outcome.issues` are readable without narrowing — which is what will keep the ten `parseImageColumn` call sites in `157.1-04` from each needing a type guard just to compile. It is not a class: the value crosses SvelteKit's `devalue` load-data boundary, and `CLAUDE.md` records prior `instanceof` trouble in this repository.
- **Closed the A2 hole, by iteration.** `rejectedTopLevelMembers` drops the path's first element for a non-empty path (the donor's correct behaviour for nested and mistyped members) and, for an EMPTY-path `unrecognized_keys` issue, iterates `issue.keys`. The loop is load-bearing: zod batches every unrecognised key of one object into one issue, so a `keys[0]` read would leave a second unknown key in place. The spec's shape-4 case feeds two top-level unknown keys at once and asserts both are dropped.
- **Generalised partial-preserve into a property of the helper** rather than of one schema (decision A2(a)), transcribing the donor's four structural moves in order and replacing its three defective lines: `String(issue.path[0])`, the two `return {}` degrade arms, and `log.warn`.
- **Guarded the retry.** It runs only when at least one member was actually rejected. Re-parsing an unchanged value is the exact loop the hole produced, and skipping that guard would reintroduce it under a different name.
- **Filled the spec against the four measured zod 4.3.6 issue shapes**, so a zod upgrade that moved the unrecognised-key reporting off `issues[].keys` breaks a test rather than silently reopening the hole. Eleven cases, zero `todo` remaining in this file.
- **Kept the tree green at every commit.** `yarn test:unit` → 961 passed / 87 todo across 25/25 tasks (the 87 are `157.1-07`'s guard self-test, untouched here). `yarn lint:check` → 22/22, `svelte-check` 0 errors 0 warnings. `yarn format:check` clean.

## Decisions Made

1. **`ParseSource` is declared here, not imported from `parseJsonbColumn.ts`.** The two are structurally identical and therefore mutually assignable, so nothing is blocked; but the dependency arrow has to point from the read paths INTO the seam, not out of it, or `157.1-04` inherits a cycle at the moment it makes `parseJsonbColumn` depend on this module. The type's own docstring records the duplication and names `157.1-04` as the converger.
2. **`reportParseFailure` keeps the donor's `message`-first parameter.** A single shared message string would have been simpler, but the two `parseJsonbColumn` sites `157.1-04` migrates already ship distinct constants ("A stored image did not match its schema and was dropped.", "Stored answers did not match their schema and were dropped."), and C4 NOTE 1's requirement is that the message be a CONSTANT, not that it be the same constant everywhere. `parseWithPartialPreserve` passes a module-level constant.
3. **The signature follows the scaffold, not research's code example.** Research wrote `<TSchema extends z.ZodType>(schema: TSchema, raw: Json | undefined)`; the wave-0 scaffold's nine call sites are written `parseWithPartialPreserve<Probe>(ProbeSchema, raw, source)`, which does not typecheck against a schema-generic signature and carries a third `source` argument. The plan states the scaffold's declared cases are this task's specification, so the scaffold wins: `<TValue>(schema: z.ZodType<TValue>, raw: unknown, source: ParseSource)`.

### 2. [Rule 2 — Missing critical functionality] The no-survivor-on-required-member behaviour had no assertion, and needed a second schema to have one

- **Found during:** Task 3.
- **Issue:** Task 2's `<behavior>` list states "With a wrong type at a required member, dropping that member makes the retry fail too, so the arm is `malformed` with no survivor — still distinguishable from `absent`." The scaffold has no case for it. Worse, **it cannot be written against `ProbeSchema` at all**: every one of that schema's top-level members is optional, so dropping the rejected member leaves `{}`, which re-parses successfully and yields a survivor. The first attempt at this case failed with `expected {} to be undefined` — the helper behaving correctly against a fixture that could not express the behaviour.
- **Fix:** The case declares a second local strict schema with a genuinely required member, `z.strictObject({ slug: z.string() })`, and feeds it `{ slug: 42 }`. Dropping `slug` leaves `{}`, the retry fails on the missing required member, and the arm is `malformed` with `value` undefined and `attributes.preserved === false`.
- **Files modified:** `parseOutcome.test.ts`.
- **Verification:** case passes; the failed first attempt and its cause are recorded in the ledger's row-2 prose rather than papered over.
- **Committed in:** `785943d7d`.
