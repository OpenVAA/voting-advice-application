## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. Verified, not asserted: every off-diagonal cell of the pairwise
overlap matrix is `0`, and the eleven cut slices plus the untouched remainder reproduce the
development branch's tree hash `40f5d20c5` exactly. The partition arithmetic closes at a gap of `0`:
252 + 97 + 119 + 162 + 195 + 533 + 214 + 330 + 152 + 129 + 2,321 = **4,504**, the comparable file
total. And the remainder decomposes independently of that: after the next PR, the only files left are
`.planning/`, `.claude/`, `.agents/` and `CLAUDE.md` — **zero** files outside the final PR's own
pathspec.

## Six things worth going to directly

### 1. The front page's image was broken, and nobody could see it

`README.md:12` rendered `<img … src="./docs/static/images/shiba-inu-facing-front.png">`. **That path
does not exist.** The v1.1 layout move took the image to `apps/docs/static/images/`, and the README
was not updated with it — so the first thing a visitor to the repository sees has been a broken image.

It stayed invisible for a structural reason worth naming, because it applies to more than this file:
`README.md` is **byte-identical at both ends of this stack**, so PR 1 renders it as a rename and no
later PR's diff contained it. A reviewer working through twelve PRs would never have been shown it.
It is in this diff only because the slice's file scope was deliberately widened to claim it.

### 2. 273 source links pointed at a path that no longer exists

Across **117 files**, links of the form
`github.com/OpenVAA/voting-advice-application/blob/main/frontend/…` pointed at the pre-move location.
**240 of the 252 distinct targets resolve** once the `apps/` prefix is added; that was verified target
by target rather than assumed, with `git cat-file -e` against each.

**The 12 that still do not resolve are named rather than hidden** — they point at files v0.2 deleted
(the Strapi data adapter, the store-era state modules, three components that were rewritten). All 12
are in hand-authored pages, not in the 98 generated ones, and each needs a semantic re-target rather
than a path prefix. They are recorded as an open item with their carrying pages listed.

Worth knowing about the timing: these links resolve on `main` **today** and stop resolving the moment
this work merges, because v0.2 both moves the tree and deletes those files. So the repair is correct
for the state this stack produces, and you cannot check it by clicking the *old* link.

### 3. Fifteen pages cited `apps/strapi/`, a path that has never existed

v0.2 rewrote the Strapi source links in the backend guides from `backend/vaa-strapi/…` to
`apps/strapi/…` — **48 occurrences**. The Strapi backend was *deleted* by v0.2, not moved to
`apps/strapi`: that directory has never existed in this repository, at either end of this stack. It is
the same defect that was found and fixed in `.prettierignore`, which shipped six ignore rules for the
same imaginary path, and it comes from the same blanket rewrite.

They are restored to `backend/vaa-strapi/…`, the path that did exist. **22 of the 30 distinct targets
resolve at `origin/main`; the other 8 were already dead there**, before any of this work — recorded,
not chased. Every one of these pages carries v0.2's own banner saying it documents the legacy backend.

### 4. Four guides documented commands that no longer exist

A guide naming a removed script is worse than a guide saying nothing, so each was replaced with the
command as it exists now — checked against the root `package.json`'s actual script list, not against
the pre-harmonisation names:

- `yarn dev:down` and `yarn dev:stop` (3 sites) → `yarn db:stop` and `yarn db:reset`. The Docker dev
  stack those belonged to was replaced by a local Supabase instance.
- `yarn build:app-shared` → `yarn build --filter=@openvaa/app-shared`.
- `yarn prod` → `docker compose -f docker-compose.dev.yml up --build`, which is the command that
  compose file's own header documents. The same paragraph promised a backend container that no longer
  exists.

The paragraph describing `yarn dev` as "development Docker images for the entire stack (frontend,
backend and DB)" is corrected too: it now describes what the script actually does.

### 5. The workspace inventory listed two workspaces that are gone and missed four that exist

`developers-guide/app-and-repo-structure` enumerated 13 workspaces, including `@openvaa/strapi` and
`@openvaa/strapi-admin-tools` (deleted by this body of work) and omitting `@openvaa/supabase`,
`@openvaa/dev-seed`, `@openvaa/dev-tools` and `@openvaa/supabase-types`. The repository has **15**.

Verified by set comparison against `yarn workspaces list --json` rather than by reading: **the
symmetric difference is empty in both directions** — nothing listed that is not a workspace, no
workspace unlisted. The page's "parts of this page reference the legacy Strapi backend" banner is
removed with the two dead entries, because after they go the page has no legacy content left, and a
banner that no longer applies is itself a documentation defect.

### 6. The landing page's external link had no `rel`, and the page was unformatted

`src/routes/+page.svelte` gained a block from `main` through an integration merge. Its
`target="_blank"` anchor carried no `rel="noopener noreferrer"`, while the sibling component in the
same app does. Modern browsers imply `noopener`, so the severity is low — the argument is the
codebase's own convention, and the block is produced by no v0.2 commit, so no other slice's diff would
ever have shown it to anyone.

The same merged block was indented one space where its siblings use two, which made the docs
workspace's **own** `format:check` fail. That gate had never run during this review: the repository's
root `format:check` chains the two checks with `&&` and short-circuits on two pre-existing, cosmetic
failures elsewhere, so the docs half was never reached. It is now green.

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-08-i18n-messages`, a sibling branch, so **no checks run — and that is correct
behaviour, not a misconfiguration.** Only PR 1 of the stack fires CI at all. Asserted, not predicted:
`gh pr checks` on each already-open stacked PR returns *"no checks reported"*.

**The reason is the base branch, not the file types in the diff.** The workflow does carry a
`paths-ignore` for `**.md`, and it does not apply here: 7 of this slice's files are `.svelte`, `.ts`,
`.mjs` and `.json`, and in any case `paths-ignore` only filters a run the trigger already selected.

**Do not read "no checks" as "the jobs exist and were skipped."** The workflow file at this branch's
head is still `main`'s — byte-identical, blob `c2fdcedb2`, verified at this commit — and it defines
exactly three jobs: `frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. The
branch-tip workflow, with Yarn 4.13 and four additional jobs (`skill-drift-check`, `supabase-tests`,
`dev-seed-integration`, `e2e-visual`), **arrives with the next PR** — verified by comparing the file
at both heads, not assumed.

Had the three that are present run, they would have failed at the same place PR 1 fails, for a reason
unrelated to this PR. Observed on PR 1's run and re-verified against it: all three fail at step
**`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

`threeal/setup-yarn-action@v2` performs the install itself as part of its caching, so the workflow's
own `Install all dependencies` step is never reached and is reported `skipped`. The cause is that the
root `package.json` at this head still declares `frontend`, `docs` and `backend/vaa-strapi` as
workspaces — read at this exact commit — while PR 1 moved two and PR 2 deleted the third. **The next
PR is where that stops being true**: it carries the corrected `package.json` and `yarn.lock`, so every
stack state from PR 1 up to and including this one — ten branches — cannot `yarn install`.

**What was actually run, locally, against the development branch tip these slices are cut from, after
this PR's fixes landed:** `yarn build` 14/14 packages, `yarn test:unit` **1,522 tests across 149
files**, `yarn lint:check` **0 errors / 20 warnings**, `yarn format:check` failing on exactly the two
pre-existing cosmetic files it failed on before — each under a forced, uncached run and each identical
to the pre-review baseline. Additionally, and specific to this slice: the docs site **builds**, its
link validator reports **0 broken internal links**, and its own `format:check` is **green**. **The 43
end-to-end specs were not run**; that suite needs a dev server and a seeded local database, and this
project's rule is that a did-not-run E2E test counts as a failure rather than a pass, so **no green
suite is claimed for this PR.**
