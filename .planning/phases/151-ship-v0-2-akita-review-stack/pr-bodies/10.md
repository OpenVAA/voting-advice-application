## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that
it can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack
   and the tip of the development branch have the same git tree hash, and `git diff` between them
   reports zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly
one slice's diff, in its final state. Verified, not asserted: every off-diagonal cell of the pairwise
overlap matrix is `0`, and the twelve slices reproduce the development branch's tree hash exactly.
The partition arithmetic closes at a gap of `0`:
252 + 97 + 119 + 162 + 195 + 533 + 214 + 330 + 152 + **129** + 2,325 = **4,508**, the comparable file
total. The final catch-all — everything not claimed by any slice — is **empty**.

## The three files a sceptical reader will challenge

Slice boundaries in this stack were chosen so each PR's title describes every file in it *without an
"and also"*. This slice is the one most open to the objection **"this is three things."** It is
deliberately not re-partitioned, and here is the reasoning in full, so the objection can be made or
dropped on the strength of this text rather than on trust.

- **`apps/frontend/README.md`** rides here on a rule applied consistently across the whole stack:
  **a README is reviewed with the thing it documents.** That is also why every `packages/*/README.md`
  rides in PR 3 with the packages rather than in PR 10 with the documentation. What this particular
  README documents *is* this slice's subject — how to install, build and run the app.
- **`apps/frontend/scripts/{flatten-current,store-to-state}-codemod.mjs`** are dead one-shot
  migration tooling from the Svelte 5 rune migration (recorded as finding F-03). They are dead by
  measurement, not by impression: **no `package.json` script in the repo references either**, and
  the *only* mention of either file anywhere outside the planning record is a comment inside the
  other one — they reference each other and nothing else. They are tooling, and they are
  dispositioned here as tooling.
- **`apps/frontend/tsconfig.tsbuildinfo`** is a tracked build artifact (finding F-08) — a
  TypeScript incremental-build cache that should almost certainly be gitignored rather than
  committed. **It is not alone: three are tracked**, in `apps/frontend/`, `apps/docs/` and
  `packages/supabase-types/` (finding F-87). It is recorded rather than removed in this PR, because
  the other two live in slices that are already open and a cross-slice fix would put this PR in the
  business of fixing itself.

## The removal you should be able to object to

**This PR deletes 89 files of Capacitor native scaffolding — `apps/frontend/{android,ios}` — plus a
dead `jest.config.json`.** It is called out here because it is a removal a reviewer should be able
to challenge, and because the evidence for it is worth stating in a body rather than only in a
commit message.

Every in-repo signal says the scaffold is dead, measured at the development branch tip:

- `@capacitor/*` appears in **no** `package.json` — zero matches across all sixteen workspaces.
- `yarn.lock` has **zero** capacitor entries.
- No source file imports it. Excluding `yarn.lock`, `.yarn/` and the planning record, the string
  `capacitor` (case-insensitive) appears **zero** times anywhere in the final tree.
- The only `@capacitor` strings that existed were *inside the scaffold itself*.
- `capacitor.config.ts` is deleted by v0.2 independently of this cleanup — so a reviewer of this PR
  would otherwise watch the config go and reasonably assume the removal was already complete.

**What no in-repo measurement can see is an external build.** If a Capacitor or app-store pipeline
outside this repository consumes that scaffold — a mobile release job, a store submission workflow,
a developer's local native build — **this removal breaks it, and nothing in this repository would
warn you.** The maintainers accepted that risk explicitly and knowingly. It is stated here in those
terms, and not as a risk-free cleanup, so that anyone who knows of such a pipeline can object from
this text alone.

The `jest.config.json` removal is smaller and unambiguous: the repository tests with vitest, and the
file configured a runner nothing uses. It is also a file that **no slice's diff would ever have
shown you** — its blob is byte-identical across the v1.1 layout move, so PR 1 renders it as a rename
and no later PR contained it. It is in this diff only because the slice's scope was deliberately
widened to claim it.

Measured at each head rather than assumed:

- At **`origin/main`**, all five original globs resolve. Nothing is wrong there.
- At **every stacked head from PR 1 through PR 10**, four of the five resolve to **nothing** —
  `backend/vaa-strapi`, `backend/vaa-strapi/src/plugins/*`, `frontend` and `docs` — because PR 1
  moved two of those trees under `apps/` and PR 2 deleted the third, while the root `package.json`

- At **this head**, both globs resolve: `packages/*` → 12 workspaces, `apps/*` → 3. Fifteen
  workspaces plus the root, which is the repository's actual shape.

That is why every stack state below this one **cannot `yarn install`**, and why this PR is where
that stops being true.

## Why no checks run here

`.github/workflows/main.yaml` triggers only on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-09-docs`, a sibling branch, so **no checks run — and that is correct behaviour, not
a misconfiguration.** Only PR 1 of the stack fires CI at all.

**The reason is the base branch, not the file types in the diff.** The workflow does carry a
`paths-ignore` for `**.md`, and it is irrelevant here — this slice is overwhelmingly `.json`, `.ts`,
`.mjs`, `.cjs`, `.yml` and lockfile content, and in any case `paths-ignore` only filters a run the
trigger already selected. **Checked at this exact head**, not at `main`: the workflow file at this
commit still declares `pull_request: branches: [main]`.

**This PR is where the CI configuration itself changes**, which is worth knowing precisely:

- At PR 10's head and below, `main.yaml` is byte-identical to `main`'s (blob `c2fdcedb2`) and defines
  **three** jobs: `frontend-and-shared-module-validation`, `backend-validation`, `e2e-tests`.
- **At this head** it is blob `4dcd9bdde` and defines **six**: `skill-drift-check`,
  `frontend-and-shared-module-validation`, `supabase-tests`, `dev-seed-integration`, `e2e-tests`,
  `e2e-visual`. So four jobs arrive with this PR and with no earlier head.

**One forward reference is worth naming, because it would otherwise look like a bug.** The
`skill-drift-check` job runs `.claude/scripts/audit-skill-drift.sh`, and that script lives under
`.claude/` — which ships in **PR 12**, the slice *above* this one. So at this head the workflow
references a script that does not yet exist. It never fires within this stack, because no stacked PR
triggers the workflow at all; and it is correct at the point that matters, since the development
branch tip has both. It is a consequence of a dependency running the opposite way to the stack
order, and it resolves at the top.

**What PR 1 actually reports, read from the run rather than predicted:** run `32017478048` shows
exactly **three** failing jobs — `frontend-and-shared-module-validation`, `backend-validation` and
`e2e-tests` — plus CodeQL, which is a separate workflow and **passes**. `skill-drift-check` is *not*
among them, because the workflow at PR 1's head is `main`'s three-job version. All three fail at step
**`Setup Yarn 4.6`** with

```
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

`threeal/setup-yarn-action@v2` performs the install itself as part of its caching, so the workflow's
own `Install all dependencies` step is never reached and is reported `skipped`. The cause is the
stale workspace globs described above — which this PR fixes.
