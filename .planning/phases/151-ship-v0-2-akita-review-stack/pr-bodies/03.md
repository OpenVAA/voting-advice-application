## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. You will never review a version that a later PR undoes. (Verified:
every off-diagonal cell of the pairwise overlap matrix is `0`, and the slices plus an empty remainder
reconstruct the target tree exactly. Re-verified after the slice above this one was cut: the five cut
slices plus the untouched remainder produce tree `c5b0fecde`, which is the development branch's tree
hash.)

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-02-shared-packages`, a sibling branch, so **no checks run — and that is correct
behaviour, not a misconfiguration.** Only PR 1 of the stack fires CI at all.

**There is a second reason worth stating, because it is specific to this PR.** The workflow file at
this branch's head is still `main`'s — byte-identical, blob `c2fdcedb2` — and it defines exactly three
jobs: `frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. **The
`supabase-tests` job that runs the pgTAP suite does not exist at this head.** It arrives with PR 11,
which is where this branch's own updated workflow file lands. The job called `backend-validation` that
*does* exist here builds and validates `@openvaa/strapi` — the workspace PR 2 deleted. So even setting
the base aside, there is no CI job at this point in the stack that could exercise this PR's contents.

Had the three jobs run, they would have failed at the same place PR 1 fails, and for a reason that has
nothing to do with this PR. Observed on PR 1's run: all three fail at the step **`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Note *which* step that is: `threeal/setup-yarn-action@v2` performs the dependency install itself as part
of its caching, so the workflow's own, more obviously named `Install all dependencies` step is never
reached and is reported `skipped`. The cause is that the root `package.json` still declares `frontend`,
`docs` and `backend/vaa-strapi` as workspaces, while PR 1 moved two of them under `apps/` and PR 2
deleted the third. Those 412 packages dropping out of the resolution are the dependency closure of the
moved-away workspaces. The root `package.json` and `yarn.lock` are corrected in
`ship/v0.2-akita-10-root-config` (PR 11), so **every stack state from PR 1 up to and including PR 10 —
ten branches — cannot `yarn install`.** That is the stack contract's point (1) working as designed.

**The green signal for this PR is therefore a local run, and it is a real one.** Against a database
reset from migrations — `yarn db:reset` applying 00001, 00002 and 00003 plus `seed.sql` — the pgTAP
suite reports:

```
Files=11, Tests=272, All tests successful, Result: PASS
```

It did not start there. See below.

The order in that last row is the point: in both `invite-candidate` and `send-email` the caller check
*completes* before the privileged client is constructed, so there is no window in which a `service_role`
client exists for an unverified caller.

**Six findings were fixed on the development branch *before* this slice was cut**, so what you are
reading is the corrected code and this PR contains no fix of itself. Three of them are worth naming:

- **The `send-email` Edge Function had never worked.** It called the `resolve_email_variables` RPC with
  the argument names `user_ids` / `template_body` / `template_subject`; the SQL function declares
  `p_user_ids` / `p_template_body` / `p_template_subject`. PostgREST resolves overloads *by argument
  name*, so every invocation returned `PGRST202` and the handler faithfully converted it to HTTP 500.
  Verified against the running instance in both directions rather than argued from the source: the
  un-prefixed POST returns PostgREST's own hint naming the correct parameters, and the `p_`-prefixed
  POST returns `[]`. The error handling around it was well built and permanently taken.
- **The pgTAP suite was red, 2 of 272, and the mandated test pattern was the cause.** Migration 00002
  tightened `anon_select_candidates` to require `terms_of_use_accepted < now()`, and `create_test_data()`
  inserted the published fixture candidates with `ToU = now()` specifically to keep those assertions
  passing. But pgTAP wraps each file in one transaction — the `BEGIN`/`ROLLBACK` boundary the checklist
  itself requires — and `now()` is `transaction_timestamp()`, frozen for the transaction. So the guard
  evaluated `now() < now()`, which is false. Measured directly: `BEGIN; SELECT now() < now();` → `f`.
  Fixed in the fixture; no schema change.
- **`scripts/lint-schema.mjs` had never run against this project's database.** Its fallback URL named
  port `54332`; `config.toml` declares `54322`. A digit transposition. On the sweeping machine another
  Supabase instance answered on 54332, so the script silently linted *that* database and reported 149
  warnings about tables that do not exist in this repository. Pointed at the right database it then
  reported 51 warnings, because its foreign-key check compared `pg_constraint.conkey`, a 1-based
  `smallint[]`, against `pg_index.indkey`, an `int2vector`, **which is 0-based** — so every single-column
  foreign key was reported unindexed, including ones whose index demonstrably exists. Both defects are
  fixed; the corrected gate reports `0 errors, 2 warnings`, and those two rows match an independent
  static read of `200-indexes.sql` against the declared foreign keys.

**Two findings are escalated rather than deferred quietly**, and a reviewer should know they are open:

- **`yarn db:lint:sql` still exits non-zero**, on four `plpgsql_check` warnings. Two of them are unused
  parameters on `resolve_email_variables`, and the only change that turns the gate green is dropping
  them — a breaking signature change to a public RPC that is granted to two roles, present in the
  generated types, and called by a pgTAP test. Whether per-template variable resolution is still
  intended is a product question, not a cleanup, so it is left open deliberately.
- **The Signicat identity path keys account identity on `birthdate`.** `claimConfig.ts` sets
  `identityMatchProp: 'birthdate'`, and that value is used both to find an existing auth user and to
  derive the account's placeholder email — so two candidates sharing a birth date resolve to the same
  auth user and the same candidate record. `IDENTITY_PROVIDER_TYPE` defaults to `signicat`. This is
  **not** an Edge Function slip: the frontend states the same design independently, so changing this half
  alone would desynchronise the two. It is being decided across both halves at once. (Idura, the newer
  provider, correctly uses `sub`.)

**Three further items are recorded as knowingly shipping unfixed**: two join-table foreign keys lack a
covering index (the trailing columns of composite primary keys, so the reverse lookup and the
`ON DELETE CASCADE` are sequential scans); 22 of 52 triggers use naming prefixes the checklist does not
list, consistently but undocumented; and `public.storage_config` stores a service-role key in a plaintext
column, which is fail-closed today (RLS on, zero policies, `REVOKE ALL … FROM anon, authenticated,
public`) but whose production remedy is Supabase Vault.

**One item is deferred to a later PR in this stack**: the Developers' Guide still documents the Strapi
backend these 119 files replace, with no Supabase equivalent page. Those pages live under `apps/docs/**`
and are reviewed in PR 10.
