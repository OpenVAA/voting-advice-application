## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. You will never review a version that a later PR undoes. (Verified:
every off-diagonal cell of the pairwise overlap matrix is `0`, and the slices plus an empty remainder
reconstruct the target tree exactly. Re-verified after the slice above this one was cut: the six cut
slices plus the untouched remainder produce tree `8459312c9`, which is the development branch's tree
hash, and the partition arithmetic closes at a gap of `0` — 252 + 97 + 119 + 162 + 195 + 3,458 = 4,283,
the comparable file total.)

## What you are looking at

`@openvaa/dev-seed` — the package that generates the local development dataset and every dataset the
E2E suite runs against. It replaces the Strapi-era `GENERATE_MOCK_DATA_ON_RESTART` bootstrap that PR 2
deleted, and it writes into the Supabase schema PR 4 added, through that schema's `bulk_import` RPC
with a service-role client.

2 `.json`.

Four things are worth going to directly:

- **The two CLIs are the whole user-facing surface**: `yarn db:seed` (`src/cli/seed.ts`) and
  `yarn db:seed:teardown` (`src/cli/teardown.ts`). Both run `parseArgs` with `strict: true` and
  `allowPositionals: false`, so an unknown flag is rejected rather than ignored, and `--seed` is
  validated against `/^-?\d+$/` on the whole token before `parseInt` — because `parseInt('12abc')`
  returns `12`, and a typo'd seed that silently becomes a different-but-valid dataset is the worst
  failure mode a deterministic generator has.
- **Determinism is the point.** A given `--seed` plus `--external-id-prefix` produces the same dataset
  every time, which is what lets the E2E suite assert exact counts and exact match scores rather than
  ranges. The answer model is a latent-factor emitter (`src/latent/**`), not per-row randomness.
- **`src/templates/` is 33 of the 113 `src` files and holds 30 built-in templates** — `default` (the
  Finnish demo, 4 locales), `e2e/base` (the canonical E2E dataset), and 28 `e2e/perm/*` permutation
  overlays, one per app-settings configuration the suite exercises. 17 of the 30 compose the shared
  `_helpers/buildMinimal.ts`; the 13 that do not are individually justified at
  `src/templates/index.ts:104-124` as layouts the helper cannot express.
- **`seed:teardown` deletes rows.** It is prefix-scoped and the allowed table list is a single exported
  constant (`src/cli/teardown.ts:73-85`) that the tests import rather than mirror — but read the
  locality note under "Two things a reviewer should know are open" below before running it.

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-03-supabase`, a sibling branch, so **no checks run — and that is correct behaviour,
not a misconfiguration.** Only PR 1 of the stack fires CI at all.

**Do not read that as "a job exists and was skipped."** The workflow file at this branch's head is
still `main`'s — byte-identical, blob `c2fdcedb2` — and it defines exactly three jobs:
`frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. **The
`dev-seed-integration` job that exercises this package does not exist at this head.** It arrives with
PR 11, where this branch's own updated workflow file lands. (For the record, because it is easy to
assume the opposite: that job deliberately carries **no** paths filter — `main.yaml:130-136` in the
newer file names the incident that made it unconditional. It is not conditional; it is simply not
present yet.)

Had the three jobs that *are* present run, they would have failed at the same place PR 1 fails, and for
a reason that has nothing to do with this PR. Observed on PR 1's run: all three fail at the step
**`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Note *which* step that is: `threeal/setup-yarn-action@v2` performs the dependency install itself as part
of its caching, so the workflow's own, more obviously named `Install all dependencies` step is never
reached and is reported `skipped`. The cause is that the root `package.json` still declares `frontend`,
`docs` and `backend/vaa-strapi` as workspaces, while PR 1 moved two of them under `apps/` and PR 2
deleted the third. Those 412 packages dropping out of the resolution are the dependency closure of the
moved-away workspaces. The root `package.json` and `yarn.lock` are corrected in
`ship/v0.2-akita-10-root-config` (PR 11), so **every stack state from PR 1 up to and including PR 10 —
ten branches — cannot `yarn install`.** That is the stack contract's point (1) working as designed.

**The green signal for this PR is therefore a local run, and it is a real one.**

## Two things a reviewer should know are open

Neither is deferred quietly; both are recorded with the reason.

- **`seed:teardown` has no locality guard, and the README now says so instead of claiming one.** The
  documentation previously asserted "the writer refuses to run without `SUPABASE_URL` set" as the
  package's guard. That is true of `Writer` — and false of the destructive command, which never
  constructs a `Writer`: `seed:teardown` goes through `SupabaseAdminClient` directly, whose module-level
  fallbacks supply a URL and the demo key with no enforcement. Both CLIs additionally fall back
  `SUPABASE_URL ??= PUBLIC_SUPABASE_URL` — the *deployed frontend's* variable — so a repo-root `.env`
  configured for a non-local Supabase silently retargets both commands, including the mass-delete. **The
  documentation is fixed; the guard itself is left to a deliberate decision**, because adding one changes
  the behaviour of a command that deletes rows and CI legitimately points these CLIs at a non-`localhost`
  test instance. Deletes are prefix-scoped and the prefix guard rejects prefixes under two characters, so
  the blast radius is bounded even in that case — but it is bounded by the prefix, not by the host.
- **This package contributes 15 of the repository's 20 `lint:check` warnings, and they are staying.**
  All 15 are one deliberate class: `'ctx' is defined but never used` on the uniform
  `generate(fragment, ctx)` generator signature, which every generator implements whether or not it needs
  the context, plus one deliberately discarded `external_id`. The rule's own remedy is an underscore
  prefix, and applying it would take the repository-wide gate from `0 errors / 20 warnings` to `0 / 5` —
  moving a number that this review stack's own verification compares "unchanged" against, in eight
  separate places. Re-baselining a shared gate mid-stack to make one slice look tidier is worse than
  recording the gap, so it is recorded.

**One documentation fix for this package landed in a different PR, and it is worth knowing where.** The
Developers' Guide's testing page made three false claims about this package — the template name, a
`variant-*.ts` path that matches zero tracked files, and "seeded via the Admin Tools API" (it is the
`bulk_import` RPC; Admin Tools was the Strapi plugin PR 2 deleted). Those pages live under `apps/docs/**`
and are reviewed in **PR 10**.
