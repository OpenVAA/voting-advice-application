## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. You will never review a version that a later PR undoes. Verified,
not asserted: every off-diagonal cell of the pairwise overlap matrix is `0`, and the nine cut slices
plus the untouched remainder produce tree `276d89a94`, which is the development branch's tree hash.
The partition arithmetic closes at a gap of `0`:
252 + 97 + 119 + 162 + 195 + 533 + 214 + 330 + 2,394 = **4,296**, the comparable file total. The
remainder also decomposes independently, without reference to that catch-all measurement:
39 + 37 + 2,318 = 2,394.

instead of beside `turbo.json` and `yarn.lock`. The other six `src/` shell files came with it.

Three things are worth going to directly:

- **`hooks.server.ts`** — three sequenced handlers, in a load-bearing order (`supabaseHandle` first so

### Accessibility was swept over every route, including the 31 no gate reaches

This is the part of the checklist a reviewer is least able to verify from a diff, so the reach of the
automated gate was measured before anything was claimed. **The end-to-end accessibility scan's route
table resolves to 5 distinct URLs × 2 themes.** This slice contains **36 page routes**. So **31 of
them are examined by no automated gate at all** — every candidate-app route (18), every admin route
(5), and 8 voter routes including `questions/[questionId]`, the page a voter spends most of the
journey on.

The five it does reach: `/`, `/elections`, `/constituencies`, `/questions`, `/results`.

The other 31 were swept by hand for the classes the scan would have applied, and each has a recorded
verdict rather than a shrug. Per-class totals over those 31 routes:

**The two heading-level skips are the whole argument for doing this by hand.**
`results/[[electionTab]]/statistics/+page.svelte` went straight from the shell's `<h1>` to `<h4>` at
two sites — an axe `heading-order` failure and a WCAG 1.3.1 defect for anyone navigating by heading
level. That route is not in the scan's table, so nothing would ever have reported it. Both are now
`<h2>`, and that this is the correct level was verified rather than assumed: the only candidate for an
intermediate heading is the `<Expander>` wrapping each question, and it renders its title in a plain
`<div>` with no heading role, so the page's real heading tree is the `<h1>` and then these two. The
rendered size is unchanged — the stylesheet sets heading sizes in the base layer, so a size utility on
the element overrides it and leaves the font weight identical.

The structural reason the other 30 come out clean is worth knowing, because it is also a caveat:
**30 of the 31 render through `MainContent` or `SingleCardContent`**, the shell components in this
same PR, which supply the `<h1>` and the `[data-focus-on-nav]` post-navigation focus target. Their
own accessibility structure is therefore load-bearing for the whole app and lives here:
`Layout.svelte` provides the skip link and the `<main>` landmark, `Header.svelte` the menu button with
`aria-expanded` / `aria-controls`, and the root `+layout.svelte` an always-present `aria-live` route
announcer plus an `afterNavigate` focus reset. The 31st route is
`questions/[questionId]/+page.svelte`, a deliberately empty leaf whose rendering is owned by its
parent layout.

**What that sweep does not establish:** it is a static one. Contrast ratios were not measured, and
**keyboard navigation has no automated gate anywhere in this project** — the scan is a static-DOM
auditor and does not tab through the UI, so the keyboard half of the requirement is uncovered on the
five scanned URLs as much as on the other 31. The drawer's close path was traced by hand and does have
proper focus management (open focuses the close button, close returns focus to the opener, and the
overlay that carries a click handler is `aria-hidden` and duplicates a keyboard-reachable control),
but that is one path read carefully, not a gate.

### Six defects were fixed on the development branch before this slice was cut

So what you are reading is the corrected code, and this PR contains no fix of itself.

- **A reactivity defect whose own comment said it was correct.**
  `results/[[electionTab]]/+layout.svelte` destructured two context properties, `appSettings` and
  `dataRoot`, above a comment asserting that both were stable and that destructuring them was fine.
  That was true before those two became bare reactive accessors, and false afterwards. The consequence
  was concrete: the multi-election selector is gated on `{#if dataRoot.elections.length > 1}`, and a
  destructured `dataRoot` takes its version dependency once at component init, so that guard never
  re-evaluated when election data arrived after mount. `appSettings` now reads through a `$derived`
  alias (correct for a value-replacing accessor) and both `dataRoot` reads go directly through the
  context inside their own tracking scope (the only correct form for an identity-stable one, because a
  `$derived` alias would yield the same object reference every time and referential equality then
  suppresses downstream notification). **The stale comment was rewritten too** — a comment asserting
  the wrong rule is how this survived four phases.
- **A second instance of the same defect, in the root layout, which a previous scan had missed.**
  `routes/+layout.svelte` destructured `appSettings` out of the app-context initialiser, whose own
  type declaration reads *"MUST be read off `ctx` (never destructured)"*. The earlier scan matched
  `get*Context()` call sites and the initialiser is not one of those, so a scan that reported one
  violation in this tree had in fact found one of two. Re-run over all **84** context-destructuring
  sites here, both were found and both are fixed.
- **An unvalidated post-login redirect, on both login actions.** Both the candidate and admin login
  form actions read a `redirectTo` field — which arrives from `?redirectTo=` on the login URL and is
  therefore caller-controlled — and interpolated it straight into their redirect target. What made
  that safe was incidental rather than intended: the target is built as `/{locale}/{redirectTo}`, and
  the leading segment stops the value from ever forming a protocol-relative or absolute URL. It did
  not stop a crafted link from steering a just-authenticated user to an arbitrary in-origin path, and
  the voter half of this same PR already validates its equivalent parameter against an allowlist
  *twice*, with a comment naming defence in depth. The guard is now shared by both actions and is
  fail-safe: a rejected value falls through to the app home, which is exactly the existing behaviour
  when no `redirectTo` is present. The application has exactly one legitimate producer of that
  parameter (`hooks.server.ts`), and the predicate was exercised against the four values it actually
  produces plus 20 hostile ones.
- **Nineteen debug `console.*` statements in the two admin form actions** — including three whose only
  purpose was to print `typeof` and `Object.keys` of a value, one block commented `// DEBUG:` that made
  an **extra network round-trip on every admin job start** purely to feed a log line, and one that
  logged the admin's free-text LLM prompt content to the server console at INFO level on every submit.
  This was the route half of a defect already fixed one PR below in the library half of the same two
  features. The two `console.error` calls in the catch blocks now use the project's development-only
  logger, which is what all 22 other route files here use, and both catches already return the message
  to the admin UI.
- **A heading-order skip on an unscanned route** — described above.
- **The routes README omitted two whole route trees this PR adds** — `admin/` and `api/`, 22 of the
  slice's 114 files, i.e. the entire server-side API surface and the entire admin app, missing from the
  one file whose job is to say where routes live. It now describes both, and names the non-route shell
  files, because a reader who knows SvelteKit will otherwise read every `.svelte` in the top directory
  as a route.

Separately, **28 comments the project's automated planning-reference cleanup had left ungrammatical
were repaired.** Nine had collapsed into a fragment with no verb; several had lost the subject a
preposition was governing (`per CONTEXT.`, `per -01 small-fix constraint`); one had had the call
parentheses stripped off a function name one clause before the words "returns an object literal"; and
one had been broken *by the earlier repair pass itself*, while its untouched sibling file still reads
correctly. These were found by diffing the cleanup commits' own before/after line pairs, not by
grepping the tree for damage — the damage signature depends on the original wording, so a grep
under-reports it.

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-06-frontend-lib`, a sibling branch, so **no checks run — and that is correct
behaviour, not a misconfiguration.** Only PR 1 of the stack fires CI at all. Asserted, not predicted:
`gh pr checks` on each already-open stacked PR returns *"no checks reported"*.

**Do not read that as "the jobs exist and were skipped."** The workflow file at this branch's head is
still `main`'s — byte-identical, blob `c2fdcedb2` — and it defines exactly three jobs:
`frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. Those are the jobs that
*exist* here; they simply do not fire on a sibling-based PR. The branch-tip workflow, with its newer
Yarn and its additional jobs, arrives with PR 11.

Had the three that are present run, they would have failed at the same place PR 1 fails, and for a
reason that has nothing to do with this PR. Observed on PR 1's run: all three fail at the step
**`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Note *which* step that is: `threeal/setup-yarn-action@v2` performs the dependency install itself as
part of its caching, so the workflow's own, more obviously named `Install all dependencies` step is
never reached and is reported `skipped`. The cause is that the root `package.json` still declares
`frontend`, `docs` and `backend/vaa-strapi` as workspaces, while PR 1 moved two of them under `apps/`
and PR 2 deleted the third. Those 412 packages dropping out of the resolution are the dependency
closure of the moved-away workspaces. The root `package.json` and `yarn.lock` are corrected in
`ship/v0.2-akita-10-root-config` (PR 11), so **every stack state from PR 1 up to and including PR 10 —
ten branches — cannot `yarn install`.** That is the stack contract's point (1) working as designed.

**What was actually run, locally, against the development branch tip these slices are cut from, after
this PR's six fixes landed:** `yarn build` 14/14 packages, `yarn test:unit` **1,522 tests across 149
files**, `yarn lint:check` **0 errors** — each under a forced, uncached run, and each identical to the
pre-sweep baseline. **The 43 end-to-end specs were not run**; that suite needs a dev server and a
seeded local database, and this project's own rule is that a did-not-run E2E test counts as a failure
rather than a pass, so **no green suite is claimed for this PR**. That matters more here than
elsewhere, because two of this PR's fixes are reactivity fixes and reactivity is what an end-to-end
test is uniquely able to catch. The nearest covering spec is named in the fix's own commit message
along with what it does and does not cover, and the full-suite run against the post-review tip is the
stack's collective proof.

## How GitHub will render this

**165 files and 13,135 changed lines as GitHub counts them — comfortably inside both budgets** (the
~300-file limit before the Files-changed tab truncates, and the 20,000-line limit before diffs collapse
behind "Load diff"). The tab will render this PR in full. If you want a reading order:
`hooks.server.ts` and `hooks.ts`, then `routes/api/`, then the app shell files in the top directory,
then the three app trees.

**Reconciling the two file counts, because you will see one number here and another in the stack table
below.** GitHub applies rename detection and reports `165 files, +7,593, −5,542`; the stack table's
rows are measured with rename detection *off*, which gives `214 files, +10,319, −8,268` for this same
commit. The cause is this slice's defining change: 97 of its 99 deletions are the old
`[[lang=locale]]/**` route tree, and each of those files has a counterpart added at the same path minus
the locale segment. **GitHub matches 49 of those pairs as renames**, so it shows one entry per pair
instead of two, and the 2,726 insertions and 2,726 deletions of the matched content stop being counted
twice. Reproduce either with `git show --shortstat ship/v0.2-akita-07-frontend-routes` (GitHub's view,
renames on) or the same command with `--no-renames` (the table's view); the rename-aware status
breakdown is `60 A / 50 D / 6 M / 49 R`.

That is the better rendering for review, not the worse one: a renamed file with a small edit reads as
one diff you can scan, where a delete-plus-add pair asks you to reconstruct the change by eye. For the
48 pairs GitHub does *not* match — the ones whose contents changed too much to pair up — reading the
deleted file beside its added counterpart is still the fastest way to see what actually changed inside
it.
