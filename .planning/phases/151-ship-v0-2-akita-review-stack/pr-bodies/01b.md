## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not — including this one. See "The state this PR leaves behind" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files. The proof is recorded in the phase record alongside the partition.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time. Nothing
   about this stack's shape constrains where a fix goes.

**No file is shown to you twice in two different content versions.** The partition was built so that
every file appears in exactly one slice's diff, in its final state. You will never review a version
that a later PR in the stack undoes. (Verified: every off-diagonal cell of the twelve-by-twelve
pairwise overlap matrix is `0`, and the twelve slices plus an empty remainder reconstruct the target
tree exactly.)

**This PR fires no CI, and that is correct.** `.github/workflows/main.yaml` triggers on pull requests
whose base is `main`. This PR's base is the branch below it in the stack, so no workflow runs. Only
PR 1 of 12 targets `main` and only PR 1 fires CI — where it is red, for reasons stated in its own body
and summarised below.

## The state this PR leaves behind

Worth stating plainly so an unexpected local failure is not read as a defect: **the tree at this commit
cannot `yarn install`.**

The repository root `package.json` here still declares:

```json
"workspaces": ["packages/*", "backend/vaa-strapi", "backend/vaa-strapi/src/plugins/*", "frontend", "docs"]
```

Three of those five entries are now stale. `frontend` and `docs` moved to `apps/` in PR 1 (a pure
rename set, which by rule does not touch `package.json`), and `backend/vaa-strapi` is deleted by *this*
PR — while `yarn.lock` still records all three as workspaces. `yarn install --frozen-lockfile` (Yarn 4's
`--immutable`) therefore fails: the declared workspace set no longer matches the tree, so the lockfile
either cannot be resolved or would have to change, and both are failures.

The root `package.json` and `yarn.lock` are corrected in **PR 11 of 12**
(`ship/v0.2-akita-10-root-config`), where `workspaces` becomes `["packages/*", "apps/*"]`. **Every stack
state from PR 1 up to and including PR 10 — ten branches — cannot install.** This is the stack
contract's point (1) working as designed: the layout move has to be content-free to be readable, and
the configuration that describes the layout is content, so it necessarily lags the move.

The green signal that does exist for this body of work is the **full test suite run against the
development branch's tip**, recorded in the phase record. That is the collective proof the stack is
measured against; per-PR CI on a deliberately partial state is not, and cannot be.
