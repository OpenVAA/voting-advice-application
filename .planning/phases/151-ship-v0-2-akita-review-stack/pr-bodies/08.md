## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. You will never review a version that a later PR undoes. Verified,
not asserted: every off-diagonal cell of the pairwise overlap matrix is `0`, and the eleven cut slices
plus the untouched remainder reproduce the development branch's tree hash exactly — most recently
`40f5d20c5`, measured after slices 09 and 10 were cut. The partition arithmetic closes at a gap of
`0`: 252 + 97 + 119 + 162 + 195 + 533 + 214 + 330 + 152 + 129 + 2,321 = **4,504**, the comparable file
total. And the remainder decomposes independently of that measurement: after slice 10 the only files
left are `.planning/`, `.claude/`, `.agents/` and `CLAUDE.md` — **zero** files outside slice 11's own
pathspec.

**No key is present in one locale and missing in another.** The scripts that produce these numbers are

**Why this had to be measured directly rather than left to a test.** The translation wrapper returns
**the key string itself** when it cannot resolve a message, so a locale missing a key renders a raw
dotted identifier like `candidateApp.settings.title` into the page instead of failing. There is a
check for that — but its reach is the accessibility scan's route table, which resolves to **5 URLs**,
none of them in the candidate or admin apps. A parity defect in a Finnish candidate-app string is
outside that check by construction. The compile-time key union does not close the gap either: it is
generated from the *legacy* catalogue that ships in PR 7, not from these files.

### Placeholder parity — the second measurement, and it found the slice's one defect

A key can be present in all seven locales and still be broken, because `{name}` refers to a **declared
input** and the declared names are part of the message's callable signature. Compared across all 598
keys × 7 locales, recursing into plural and selector bodies — **147 message bodies are arrays rather
than strings, and a check that skipped them would have reported a clean result and been wrong**:

| | Before | After |
| --- | ---: | ---: |
| placeholder-set divergences against `en` | **2** | **1** |

- **Fixed before this PR opened.** `sv/components.json` → `components.video.timeLeft` declared its
  inputs as `minuter` / `sekunder` and interpolated `{minuter}` / `{sekunder}`, where all six other
  locales declare `minutes` / `seconds`. The Swedish variant therefore had a **different callable
  signature** from its siblings and could not receive what a caller passes. Only the four
  declarations, two selector names and two interpolations were renamed — **the Swedish text is
  untouched**, so no translation decision was taken. Severity stated rather than inflated: the key has
  **zero call sites** in the repository today, so nothing renders it; it was fixed because the repair
  is mechanical and lossless. It is also inherited rather than introduced — the pre-Paraglide
  catalogue carries the same names.
- **One divergence remains, and it is deliberate.** `questions.intro.start` is
  `Answer {numQuestions} Questions` in `en` and interpolates `numQuestions` in five other locales;
  `sv` reads `Börja svara på frågor` with no placeholder. That one **is** live — it is the
  questions-intro call to action — but the remedy is Swedish copy, which is a publisher's decision
  and not a reviewer's or an implementer's.

Two further measurements, neither of which is a defect: **12 empty-string values**, of which 7 are one
key that is empty in all seven locales by design (a publisher-overridable default whose render site is
guarded on truthiness) and 5 are a shared suffix; and **31 values identical to `en` in all six other
locales**, of which 24 are emoji, 7 are the language endonyms in `lang.json` (`Suomi`, `Svenska`, …,
correctly untranslated), and one is that same empty default.

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-07-frontend-routes`, a sibling branch, so **no checks run — and that is correct
behaviour, not a misconfiguration.** Only PR 1 of the stack fires CI at all. Asserted, not predicted:
`gh pr checks` on each already-open stacked PR returns *"no checks reported"*.

**The reason is the base branch, not the file types in the diff.** The workflow does carry a
`paths-ignore` for `**.md`, and it is irrelevant here twice over: this PR is 329 `.json` files and one
`.md`, and `paths-ignore` only ever applies to a run the trigger already selected.

**Do not read "no checks" as "the jobs exist and were skipped."** The workflow file at this branch's
head is still `main`'s — byte-identical, blob `c2fdcedb2` — and it defines exactly three jobs:
`frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. Those are the jobs that
*exist* here. The branch-tip workflow, with its newer Yarn and its four additional jobs
(`skill-drift-check`, `supabase-tests`, `dev-seed-integration`, `e2e-visual`), arrives with PR 11.

Had the three that are present run, they would have failed at the same place PR 1 fails, and for a
reason that has nothing to do with this PR. Observed on PR 1's run, and re-verified against that run
rather than copied: all three fail at step **`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Note *which* step that is: `threeal/setup-yarn-action@v2` performs the dependency install itself as
part of its caching, so the workflow's own, more obviously named `Install all dependencies` step is
never reached and is reported `skipped`. The cause is that the root `package.json` at this head still
declares `frontend`, `docs` and `backend/vaa-strapi` as workspaces — verified at this exact commit —
while PR 1 moved two of them under `apps/` and PR 2 deleted the third. Those 412 packages dropping out
of the resolution are the dependency closure of the moved-away workspaces. The root `package.json` and
`yarn.lock` are corrected in `ship/v0.2-akita-10-root-config` (PR 11), so **every stack state from
PR 1 up to and including PR 10 — ten branches — cannot `yarn install`.** That is the stack contract's
point (1) working as designed.

**What was actually run, locally, against the development branch tip these slices are cut from:**
`yarn build` 14/14 packages, `yarn test:unit` **1,522 tests across 149 files**, `yarn lint:check`
**0 errors**, each under a forced, uncached run and each identical to the pre-review baseline. **The
43 end-to-end specs were not run**; that suite needs a dev server and a seeded local database, and
this project's own rule is that a did-not-run E2E test counts as a failure rather than a pass, so **no
green suite is claimed for this PR.** The full-suite run against the post-review tip is the stack's
collective proof.
