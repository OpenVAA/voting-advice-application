## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why no checks run here" below.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time.

**No file is shown to you twice in two different content versions.** Every file appears in exactly one
slice's diff, in its final state. You will never review a version that a later PR undoes. Verified,
not asserted: every off-diagonal cell of the pairwise overlap matrix is `0`, and re-verified after the
two slices above this one were cut — the nine cut slices plus the untouched remainder produce tree
`276d89a94`, which is the development branch's tree hash, and the partition arithmetic closes at a gap
of `0`: 252 + 97 + 119 + 162 + 195 + 533 + 214 + 330 + 2,394 = **4,296**, the comparable file total.
The remainder also decomposes independently, without reference to that catch-all measurement:
39 + 37 + 2,318 = 2,394.

## The two reactivity rules a reviewer cannot see, and how this PR was checked against them

The contexts expose two classes of property with **different reactivity semantics under
destructuring**, and getting it wrong produces a component that renders once and then silently stops
updating. Nothing enforces either rule — not `tsc`, not ESLint, not a test.

1. **Value-replacing reactive accessors** (`appSettings`, `locale`, and the array getters like
   `selectedElections`, `opinionQuestions`, `matches`). Destructuring one invokes the getter **once**
   at component init and binds the value; later reads are reads of a dead local. They must be read as
   `ctx.X`, optionally aliased through `$derived(ctx.X)`.
2. **Identity-stable accessors** — `dataRoot`, whose object reference *never changes* and whose only
   reactive signal is a private version counter bumped on update. For this one a `$derived` alias is
   **also** wrong: the alias recomputes on every bump, yields the same reference every time, and
   Svelte 5's referential-equality rule then skips downstream notification. The consumer keeps the
   pre-mount snapshot. Warm navigation masks it; a cold direct-URL entry exposes it. The only safe
   form is `ctx.dataRoot.<prop>` read **directly inside the consuming tracking scope**.

Rather than sample, every consumer in this slice was enumerated mechanically and read individually:

| Check | Result |
| --- | ---: |
| context destructuring sites in `src/lib` | **60** |
| of those, destructuring a reactive accessor | **0** |
| `dataRoot` consumers in `src/lib` | **5** |
| of those, bound to an intermediate `$derived` alias | **0** |

All five `dataRoot` consumers read through the accessor inside their own tracking scope and say so in
a comment; one defers the read into the consumer with an explicit thunk (`dataRoot: () => DataRoot`,
called inside `$derived.by`). **This slice is clean, and clean deliberately.** The same scan was then
extended past the pathspec boundary into the routing surface, because the same contexts are consumed
there — and that is where three findings were: one genuine defect and two look-alikes. All three are
handled in PR 8, which is where those files live.

## Three things a reviewer should know are open

None is deferred quietly; each is recorded with its reason.

- **The accessibility gate cannot see most of this slice.** The axe scan reaches **5 distinct URLs ×
  2 themes** — measured, not estimated — and it reaches components only *transitively*, through what
  those five URLs happen to render. Of this slice's 110 components, any not mounted on `/`,
  `/elections`, `/constituencies`, `/questions` or `/results` is **not examined by that gate at all**,
  including every candidate-app and admin-app component. The raw-translation-key scan has exactly the
  same reach, because its only call site is inside the axe helper. And axe is a static-DOM auditor: it
  does not tab through the UI, so the **keyboard** half of the requirement is uncovered even on the
  five URLs it does reach — and this slice contains the hand-rolled interactive primitives that make
  that requirement real (`Select` with `aria-activedescendant` and index navigation, the radio-group
  focus-out handling in `QuestionChoices`, `Tabs`, `Expander`, `Modal`). Widening the route table and
  adding a keyboard gate is net-new test authorship and is scoped to a later phase.
- **A real duplication is shipping unfixed.** `EntityListControls` and `EntityListWithControls` carry
  the same three filter handlers — including an identical tracking guard and an identical five-line
  active-filter chain — followed by near-identical control markup, and the extraction target already
  exists beside them. Not fixed because extracting a shared handler is code restructuring, which this
  review pass deliberately excludes, and because it is behaviour-adjacent in the filter path with no
  end-to-end gate available to prove it safe. The remedy is recorded so nobody has to re-derive it.
- **The write half of the row-mapping contract has no production consumer.** `mapRowToDb` and the
  reverse property map are exported and unit-tested with **zero call sites** anywhere in the
  repository, and the write that would want them cannot use them: the shared column map lacks the
  operational columns of the admin-jobs table, so the writer that would need `mapRowToDb` correctly
  spells twelve snake_case keys by hand. Both docblocks now state that and the precondition for future
  use. Widening the map is a change to the package in PR 4, which is already open.

## Why no checks run here

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This PR's base is
`ship/v0.2-akita-05-e2e-tests`, a sibling branch, so **no checks run — and that is correct behaviour,
not a misconfiguration.** Only PR 1 of the stack fires CI at all. Asserted, not predicted:
`gh pr checks` on each already-open stacked PR returns *"no checks reported"*.

**Do not read that as "the jobs exist and were skipped."** The workflow file at this branch's head is
still `main`'s — byte-identical, blob `c2fdcedb2` — and it defines exactly three jobs:
`frontend-and-shared-module-validation`, `backend-validation` and `e2e-tests`. Those are the jobs that
*exist* here; they simply do not fire on a sibling-based PR. The branch-tip workflow, with its newer
Yarn and its additional jobs, arrives with PR 11.

Had the three that are present run, they would have failed at the same place PR 1 fails, and for a
reason that has nothing to do with this PR. Observed on PR 1's run: all three fail at the step
**`Setup Yarn 4.6`** with

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, ... and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Note *which* step that is: `threeal/setup-yarn-action@v2` performs the dependency install itself as
part of its caching, so the workflow's own, more obviously named `Install all dependencies` step is
never reached and is reported `skipped`. The cause is that the root `package.json` still declares
`frontend`, `docs` and `backend/vaa-strapi` as workspaces, while PR 1 moved two of them under `apps/`
and PR 2 deleted the third. Those 412 packages dropping out of the resolution are the dependency
closure of the moved-away workspaces. The root `package.json` and `yarn.lock` are corrected in
`ship/v0.2-akita-10-root-config` (PR 11), so **every stack state from PR 1 up to and including PR 10 —
ten branches — cannot `yarn install`.** That is the stack contract's point (1) working as designed.

**What was actually run, locally, against the development branch tip that these slices are cut from:**
`yarn build` 14/14 packages, `yarn test:unit` **1,522 tests across 149 files**, `yarn lint:check`
**0 errors** — each measured under a forced (uncached) run. **The 43 end-to-end specs were not run**;
that suite needs a dev server and a seeded local database, and this project's own rule is that a
did-not-run E2E test counts as a failure rather than a pass, so **no green suite is claimed for this
PR**. The suite is run once, in full, against the post-review tip, and that run — not per-PR CI — is
the stack's collective proof.
