## Read this first — the stack contract

This is one PR in a **review-only stack of twelve**, cut from the v0.2 "Akita" body of work so that it
can actually be read. Four things follow from that, and all four are deliberate:

1. **Individual PRs need not build, lint, or pass tests. Only the whole matters.** The stack is a
   *reviewing* device: it slices one large final state into twelve diffs, each holding changes of a
   similar nature. Intermediate states are therefore not required to be working states, and several
   are not. See "Why this PR is red" below for exactly which checks fail here and why.
2. **The stack's final state is byte-identical to the development branch's final state.** The twelve
   slices are a re-partition of the same tree, not a re-implementation of it: the top of the stack and
   the tip of the development branch have the same git tree hash, and `git diff` between them reports
   zero files. The proof is recorded in the phase record alongside the partition.
3. **Because of (2), the stack does not need to be merged.** It exists to be read. Merging the
   development branch, or merging the stack, produces the identical tree.
4. **Review comments do not have to be implemented inside the stack.** Fixes can land on a separate
   branch targeting whichever of the development branch or the stack is easier at the time. Nothing
   about this stack's shape constrains where a fix goes.

**No file is shown to you twice in two different content versions.** The partition was built so that
every file appears in exactly one slice's diff, in its final state. You will never review a version
that a later PR in the stack undoes. (Verified: every off-diagonal cell of the twelve-by-twelve
pairwise overlap matrix is `0`, and the twelve slices plus an empty remainder reconstruct the target
tree exactly.)

**Only this PR targets `main`.** Every other PR in the stack targets the branch below it, so GitHub
shows you each one's own diff and nothing else.

## What you are looking at

The monorepo layout move: `frontend/` → `apps/frontend/` and `docs/` → `apps/docs/`.

**Paths change. Contents do not.** This commit was reconstructed specifically so that it is a pure
rename set — every output blob is the identical object from the base commit, re-pointed at a new path.
Measured on this commit:

| Measurement | Value |
| --- | --- |
| `git show -M --shortstat` | `1316 files changed, 0 insertions(+), 0 deletions(-)` |
| File-status taxonomy at `diff.renameLimit=1` | **`1316 R`** — and `0 A`, `0 M`, `0 D` |

That taxonomy is asserted at `diff.renameLimit=1`, the maximally hostile setting — the one at which
git is *least* willing to call something a rename. It still reports all 1,316 as renames, so the
result does not depend on a generous rename-detection threshold. A `D` or an `A` in that set would
mean this commit had lost or invented a file; there are none of either.

**So the review here is a single question: are these the right paths?** There is no code to read. It
is a large file count and a trivial diff, and those two facts are not in tension — a rename consumes
a *file* slot and no *line* budget.

Content changes to these same files arrive later in the stack, as ordinary edits at their new paths.
That separation is the entire purpose of doing the move as its own PR: without it, roughly 1,300 files
would render as delete/add pairs inside a content PR, and the real changes would be invisible inside
64,860 added and 64,860 deleted lines that mean nothing. (That is exactly what
`git show --no-renames` reports for this commit: `2632 files changed, 64860 insertions(+),
64860 deletions(-)`. It is the add-plus-delete *rendering* of a move, not a review cost.)

## Why this PR is red, and why that is expected

`.github/workflows/main.yaml` triggers on pull requests whose base is `main`. This is the only PR in
the stack whose base is `main`, so **this is the only PR in the stack that fires CI at all**. On the
other eleven, "no checks ran" is correct behaviour and not a misconfiguration.

All three jobs in that workflow fail here, and **all three fail at the same step with the same error**
— as observed on the run this PR actually triggered:

| Job | Fails at | Error |
| --- | --- | --- |
| `frontend-and-shared-module-validation` | step 3, `Setup Yarn 4.6` | `YN0028` |
| `backend-validation` | step 3, `Setup Yarn 4.6` | `YN0028` |
| `e2e-tests` | step 4, `Setup Yarn 4.6` | `YN0028` |

Note *which* step that is. The dependency install happens **inside** `Setup Yarn 4.6` —
`threeal/setup-yarn-action@v2` installs dependencies itself as part of its caching — so the workflow's
own, more obviously named `Install all dependencies` step is never reached. It and every lint, format,
type-check, test and build step after it are reported as `skipped`, not as failures.

The error, verbatim from the run:

```
YN0085: │ - @adobe/css-tools@npm:4.4.1, @alloc/quick-lru@npm:5.2.0, @capacitor/android@npm:5.7.8,
          @capacitor/cli@npm:5.7.8, @capacitor/core@npm:5.7.8, and 407 more.
##[error]The lockfile would have been modified by this install, which is explicitly forbidden. (YN0028)
```

Those 412 packages dropping out of the resolution *are* the symptom: they are the dependency closure
of the two workspaces this PR moved out from under the paths the root `package.json` still names.

**What passes:** the repository's CodeQL default-setup checks — `Analyze (javascript-typescript)`,
`Analyze (actions)` and `CodeQL` — all pass on this PR. The red is confined to the three `main.yaml`
jobs above.

**The cause, precisely.** The repository root `package.json` at this commit declares:

```json
"workspaces": ["packages/*", "backend/vaa-strapi", "backend/vaa-strapi/src/plugins/*", "frontend", "docs"]
```

That is unchanged by this PR — and it *has* to be, because this PR is renames only and root
`package.json` is not one of the renamed files. But `frontend/` and `docs/` are now
`apps/frontend/` and `apps/docs/`, and `yarn.lock` at this commit still resolves
`@openvaa/frontend@workspace:frontend` and `@openvaa/docs@workspace:docs`. Two of the five declared
workspaces therefore no longer exist on disk while the lockfile still names them.

What the run shows happening: yarn resolves the workspaces that *do* exist, which is a strictly
smaller set than the lockfile records — hence the 412 dropped packages — and `--frozen-lockfile`
(Yarn 4's `--immutable`) then refuses the resulting lockfile change outright. The install fails
before any lint, format, type-check, test or build step in those jobs is reached, which is why none
of them reports anything.

**This is not confined to this PR.** A third declared workspace, `backend/vaa-strapi`, is deleted by
the next PR in the stack. The root `package.json` and `yarn.lock` are only corrected in
`ship/v0.2-akita-10-root-config` (PR 11 of 12), where `workspaces` becomes
`["packages/*", "apps/*"]`. **Every stack state from this commit up to and including
`ship/v0.2-akita-09-docs` — ten branches — therefore cannot `yarn install`.** That is the stack
contract's point (1) working as designed, not a defect discovered late: the layout move must be
content-free to be readable, and the configuration that describes the layout is content.

If you want a green signal for this body of work, the one that exists is the **full test suite run
against the development branch's tip**, recorded in the phase record. That is the collective proof
the stack is measured against. Per-PR CI on a deliberately partial state is not, and cannot be.

## How GitHub will render this

- **1,316 files exceeds GitHub's 300-file single-diff render limit.** Expect the diff view to
  truncate and to need "Load more". Because every entry is a rename with zero line changes, what you
  are loading is a path list, not code.
- **The line budget is zero, so no line-based truncation applies.** A render flag on this PR is a
  file-count flag only.
- GitHub does report renames as renames (`renamed` entries in the diff and in the API), so the file
  list should read as `frontend/x → apps/frontend/x` pairs throughout. If you see delete/add pairs
  instead, something is wrong and it is worth saying so — that would contradict the measurement above.
