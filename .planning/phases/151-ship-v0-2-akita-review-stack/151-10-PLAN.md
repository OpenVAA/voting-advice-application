## Why this plan is gated

Three facts, all measured, make the first push materially different from every action before it:

1. **The remote is the real project.** `origin` is `OpenVAA/voting-advice-application`. A pushed
   branch and an opened PR are visible to the project.
2. **Repo ruleset 8477541 fires an unbypassable Copilot review on every branch, including drafts.**
   Measured: `enforcement: active`, `ref_name.include` covering all refs, `review_draft_pull_requests: true`,
   `bypass_actors: []`, `current_user_can_bypass: "never"`. A 12-PR stack therefore means **12
   automatic AI reviews**, sitting on top of the human review the stack exists to enable. Draft
   status does not suppress them.
3. **PR #860 is already open** on `origin`, head `feat-gsd-roadmap`, base `main`, 3,959 changed
   files, stale at `97f55cb41` — 1,603 commits behind local at research time. Left alone, the
   reviewer meets a stale duplicate of the entire body of work standing next to the new stack.

## Corrections applied

- **C-10** — PR #860's existence and its staleness are measured facts, not speculation. Re-measure
  both at execution time with `gh pr view 860` and `git ls-remote`, since the numbers will have
  moved.
- **Pitfall 7** — PR 01a will be red, and for a more specific reason than D-24 states: the
  skill-drift CI job runs a script that **does not exist at the stack's base commit** — it is added
  by the planning slice at the *top* of the stack — so the job fails on a missing file before
  anything else runs, and the frontend validation job fails because the root workspace globs no
  longer resolve after the layout move. Annotate PR 01a with the specific failures. Do not treat
  that red as a phase blocker.
- **Pitfall 8** — slice 01a exceeds GitHub's documented 300-file render budget but costs **zero
  lines**: renames consume a file slot and no line budget, and GitHub does report them as renames.
  Say so in the PR body so a reviewer meeting a 1,300-file PR knows to expect a clean rename list.

  <name>Task 1: Consent to publish — the first push and 12 automatic Copilot reviews</name>
  <decision>
May the stack be pushed to `OpenVAA/voting-advice-application`, accepting that repo ruleset 8477541
will fire an automatic Copilot review on every one of the ~12 stack pull requests, including drafts,
and that this cannot be bypassed per-PR?
  </decision>
  <context>
Everything up to this point has been local. This is the first outward-facing action of the phase and
it is not cleanly reversible: a pushed branch and an opened PR are visible to the project, and
deleting them later leaves traces in notifications and the audit log.

The ruleset's measured shape: `enforcement: active`, ref pattern covering all branches,
`review_draft_pull_requests: true`, `bypass_actors: []`, `current_user_can_bypass: "never"`. You are
repo admin, so you *can* change the ruleset — but you cannot bypass it per-PR, and changing a
repo-wide policy is a decision for you, not for an agent to take quietly.

Rate limits are not a concern: `gh api rate_limit` showed core well within budget and 12 PRs is
negligible against it.

Also note what happens to CI: `main.yaml` triggers on pull requests targeting `main` only. **PR 01a
is the only PR in the stack that fires CI at all**; every stacked PR targets a sibling branch and
fires nothing. So "no CI ran" on ten PRs is expected, not a misconfiguration — and D-24 already
establishes that the full suite run on the branch tip, not per-PR CI, is the gate.
  </context>
  <options>

      <pros>No repo-wide policy is touched. The stack opens as planned. Copilot's comments are noise you can ignore or collapse per PR.</pros>
      <cons>~12 automatic AI reviews over roughly 4,000 files, sitting on top of the human review the stack exists to enable. Review noise is the specific thing this phase is trying to reduce.</cons>
    </option>
