# Phase 179 — UI Design Contract

> Visual and interaction contract for the surfaces Phase 179 adds or reshapes in the Contestant app: the
> identity provider's option of the registration-mode selector (C) with its **entity-type choice**, the
> start of the provider's flow from C (CI), the **success view (CI1)** — a gate view of the protected layout
> in which a new user gives the email they will sign in with and, for an organization, its name and
> abbreviation, and in which a returning user is told they have already registered — the **error screen
> (CI2)** in its three classes, the **pending-address reminder** on the entity's home and in settings,
> the confirmation mail, and the removal of the legacy `preregister/` chain. Generated by
> gsd-ui-researcher, to be verified by gsd-ui-checker. It is the sequel of `178-UI-SPEC.md`, built the same
> way and on the same components; the same executors and verifier read both.
>
> **This phase adds no design language.** SvelteKit 2 + Svelte 5 runes, Tailwind 4 + DaisyUI 5, Inter,
> theme colours in `packages/app-shared/src/settings/staticSettings.ts`. The token sections below
> **document the established contract** the surfaces obey; they introduce **no new token, font, spacing
> step, colour, icon or component library**. The load-bearing content is in *Surface Contracts*,
> *Copywriting Contract*, *Locator Contract*, *Axe Scan Entries*, *UI Considerations* and the closing
> *PROPOSED — Operator to Confirm*.
>
> **How to read the evidence marks.** `[tree]` = read on this worktree, branch
> `feat/entity-signup-multi-grant`, at HEAD `baf15c4d6` on 2026-10-21. Phases 170–178, 174.1 and 177.1
> are executed on that tree, and so are the v2.17 deployment workstream's phases 181.1 and 182, which
> share the branch. `[run]` = the output of a command run for this document — the component count, the four
> resolved versions, the key counts of the seven catalogues and the searches that derive a population —
> each quoted where it is used. **Nothing was rendered**: no dev server, no browser, no database, no unit
> test and no E2E run stands behind any sentence here (the local stack is shared with another worktree).
> `[CONTEXT D-nn]` = a decision of `179-CONTEXT.md`; `[CONTEXT J-n]` = one of its seven items marked
> ⚠ OPERATOR REVIEW, **written here at the option the context proposes and not resolved by this
> document**; `[178 U-nn]` / `[178 S-n]` = a proposal or surface of `178-UI-SPEC.md`, all of which the
> operator left at their ★ on 2026-10-11 and which are built. `[OD-mm-dd Xn]` = an item of
> `.planning/v2.16-OPERATOR-DECISIONS-2026-mm-dd.md`. `[computed]` = calculated from the theme tokens for
> this document. `[not read]` and `[not run]` = a fact this document could not establish; each is listed
> under *What reading could not establish*. `[U-nn]` = a rule proposed in this document — **PROPOSED —
> operator to confirm** — all listed together at the end. Code is cited by path and a content anchor (a
> symbol or a quoted line), never by line number. Names of symbols, routes, message keys and test ids this
> phase introduces are suggestions unless a `[CONTEXT]` mark fixes them; what they must do is the contract.
> Frontend paths are relative to `apps/frontend/src/` unless they start with `apps/`, `packages/` or
> `tests/`; `ENTRY/` abbreviates `routes/contestant/`. The letters are the screens of `CAND-APP-PLAN.md`:
> A login, B sign in, C the registration-mode selector, CI the provider's flow, CI1 its success view, CI2
> its error screen, F the set-password gate, G the terms-of-use gate, H the profile selection, I the
> entity's home.
>
> **This run was non-interactive.** `179-CONTEXT.md` was gathered on 2026-10-06, before Phases 175, 177,
> 177.1 and 178 ran, and no `179-RESEARCH.md` exists yet. Where the context and the tree disagree the tree

### Shared premises

- **Where each surface lives** `[CONTEXT D-13]` `[CONTEXT J-7]` `[U-19]`:

  | Surface | Where | Route key | Title — `<h1>`, document title and route announcement |
  |---------|-------|-----------|--------------------------------------------------------|
  | C, the provider's option | `ENTRY/register/` (existing) | `ContestantAppRegister` | "Registration" (existing) |
  | CI, the start | inside C: Continue posts to `/api/oidc/authorize` and the browser leaves for the provider | — | — |
  | The return | `/api/oidc/callback` (path unchanged) | `ContestantAppIdentityProviderCallback` (renamed from `ContestantAppPreregisterIdentityProviderCallback`) | — |
  | CI1 | a gate view of `ENTRY/(protected)/`, shown at whatever protected address was asked for; the callback redirects to `ContestantAppHome` | none | "Complete your registration", or "You have already registered" (S3) |

  | Settings, pending | the entity's settings page | `ContestantAppSettings` | the page's own |

  **No two surfaces a user meets one after another share a title** — the route announcer is a live region,
  and a region whose text does not change announces nothing.
- **The three address states** `[CONTEXT D-06]`: an identity-provider account's address is **none** (the
  placeholder, nothing pending), **pending** (the placeholder, a typed address awaiting its link) or
  **proved**. Every rule below names the state it applies in. An account that is not the provider's is
  always *proved* for these surfaces.
- **The placeholder address is never rendered, sent to a password manager or spoken.** It is
  `<sub>@bank-auth.placeholder`, an identifier derived from the provider's persistent id. Wherever a surface
  shows "the account's address" (T-6), an account in state *none* or *pending* has none: the label and the
  address are left out together, as each of the four surfaces already does for an empty value, and
  `PasswordSetter` is given no `username`. The **pending** address is shown only where this document names
  it, always under "Awaiting confirmation", never under "Signed in as". The server load decides; no
  component tests a domain.
- **What the provider's flow is offered for is one list** `[178 U-29]`. `listedRegistrationModes` lists
  `identity_provider` where the matrix allows it **for any served type**, and every surface that offers
  registration — A's Register, C, the menu and the guard of `register/` — keeps reading that one function.
  The entity types the provider's panel offers are the served types whose row allows `identity_provider`, in
  the order candidate, organization: a second function beside the first, over the same settings argument,
  and the copy the function's conformance test holds equal to `identity-callback`'s check
  `[CONTEXT D-03]`.
- **Every form is one `<form method="POST" novalidate>`, and one form is one process** `[178 U-01, U-16]`.
  Its main button is a `type="submit"` in `primaryActions`, tied by the `form` attribute; a press with
  something missing sends nothing, says what at the field and moves focus to the first field in error
  `[178 U-06]`; the main button is natively `disabled` until the page's script has loaded `[178 U-05]`.
- **No oracle beyond the three the context allows.** C and CI2 never differ by whether an identity is
  known. CI1 differs by the account's own state, shown to its own signed-in owner `[CONTEXT D-12]`; the
  one refusal that names another account's address is `[CONTEXT D-07]`'s, behind the per-address throttle.
- **Reactive accessors are read, never captured** (`CLAUDE.md` § Context Destructuring Rule). `appSettings`,
  `answersLocked`, `user`, `selectedEntity` and `locale` are read as `contestantCtx.X` inside the tracking
  scope.
- **Vocabulary.** "Sign in", never "log in" — and **never `common.login`'s Swedish string** (T-18). "Bank ID"
  as each catalogue already names the provider (`contestantApp.register.modes.identityProvider`: "With a
  Bank ID", "Pankkitunnuksilla", "Med bank-id", …). "Party" for an organization, as the catalogues do. The
  UI never says "placeholder", "pending" or "proved": it says "has not been confirmed yet" and "confirmed".
- **RTL is out of scope on this branch.** New markup uses logical utilities (`text-start`, never `text-left`).
