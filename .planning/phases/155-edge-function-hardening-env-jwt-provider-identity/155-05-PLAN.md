Check 1, the class D-D2 names. Scan every TypeScript file under `apps/supabase/supabase/functions/` for
an environment read immediately followed by a nullish-coalescing or logical-or operator, using the
predicate RESEARCH validated:
`/Deno\.env\.get\(\s*['"\`][^'"\`]+['"\`]\s*\)\s*(\?\?|\|\|)/g`. Two implementation properties are
load-bearing and must not be simplified away. First, scan the WHOLE file rather than line by line: the
current formatter keeps every such expression on one line today, but a longer identifier would wrap the
operator onto the next line and a line-scoped scan would miss it. Derive the reported line number from the
match index. Second, strip comments before scanning, replacing block-comment bodies with spaces rather
than deleting them so line numbers survive the strip, because this phase deliberately writes doc comments
that describe the forbidden shape and the guard must not trip on its own prose.

The predicate is anchored on the environment read, not on the start of the assignment, and that is the
point: the project-id site's fallback chain begins with a request-body operand, so a matcher anchored on
the assignment would silently exempt the worst site in the set. Say so in a comment above the pattern.
Equally, the predicate must not match a logical-or default on an ordinary value, so the decoded roles
claim's absent-claim default stays legal.

Check 2, duplication drift. The tree has no shared-module directory and each top-level function directory
is a deployment unit, so three modules exist as verbatim copies. Assert that every file named
`jwtSegment.ts` under the functions tree is byte-identical to every other, and likewise for every file
named `envConfig.ts`. Compare contents, not sizes. Name the drifting pair in the message.

Check 3, the testability contract. For every module under the functions tree that has a `*.test.ts`
beside it, assert the module contains no URL import from a remote origin and no reference to the Deno
global. That property is the only reason vitest can reach these files, and losing it turns a passing test
file into an unresolvable import at the next run.

Every violation message follows the house voice: what changed, what it costs, and the requirement
identifier in parentheses. For check 1 the message names the offending file and line, states that a
missing variable must fail loudly naming the variable rather than silently substituting a value, and tells
the reader to replace the default with a throw naming the variable.

Comment convention, per D-N1: Phase 152's comment scan has not executed and is not a link of
`lint:check`, so write this script's header and its inline comments to the convention by hand. Note the
spelling split this tree already observes -- a double hyphen stands for an em dash inside TypeScript
comments, while the em dash character itself is used in guard output strings and in markdown, so match
the sibling guard scripts rather than the sibling TypeScript modules.

Then prove the guard catches rather than merely runs. Temporarily inject one defaulting expression into
one Edge Function file, run the guard, and record that it exits non-zero with a message naming that exact
file and line; then revert the injection and record that it exits zero on the restored tree. Capture both
outputs to absolute paths under the resolved temp directory and cite them in the plan summary. Confirm the
working tree is clean for that file afterwards before continuing.
