## Summary

Phase 179.1 moved the ground under CONTEXT.md. The landing no longer lives in `api/auth/callback/+server.ts`: that route now only 303s a link to the app-neutral confirm page (`/auth/confirm`), whose form action calls `verifyMailedLink` in `apps/frontend/src/lib/server/auth/mailedLink.ts`. That function is the one place a mailed link is spent and landed. Its `recovery` arm always lands on `ContestantAppResetPassword`. Its `magiclink` arm lands on a `next` checked by a **regex** (`safeRedirectTarget`), not by an allow-list. No mailed link carries a `next` today: `account-access` builds exactly `?token_hash=…&type=…`, and its docstring states as an invariant that "A request names no page, path or URL". So D-03 rule 1 needs a new field in the request contract, a new parameter on the mailed link, and an allow-list in `verifyMailedLink`. All three must agree on one `next` contract.

Four premises in CONTEXT.md / DISCUSSION-POINTS no longer match the tree, and the planner must not build them as written:
1. **F7 (the mixed-grant lockout) is already fixed.** Since `f8c369121` (173-05, 2026-10-06), `_getBasicUserData` tests `ADMIN_GRANTS` first, so `role === 'admin'` is exactly `hasAnyGrant(grants, ADMIN_GRANTS)`. D-04 reduces to proof (unit + E2E in both apps), closing the stale todo and fixing the docs sentence that still says otherwise.
2. **`passwordField` is not a component.** It is a local variable inside `PasswordSetter`.
3. **`logoutButton` collides.** `$lib/dynamic-components/logoutButton` (the Admin App's own) already exists, and the Contestant one is built on contestant tasks and questions. No Admin App screen in this phase uses either one.
4. **`private.email_holds_grant_in_project` has two callers.** Widening it (D-09) also widens `invitation_link_request` (sign-in links), and four existing pgTAP rows pin the old refusal.

The work splits into five parts:
- **Shared gate runner and gate outlet.** `$lib/auth/gates` exports a generic `firstNeededGate`, plus one `setPassword` predicate used by `CONTESTANT_GATES` and a new `ADMIN_GATES`.
- **Shared account components.** Moved under `$lib/components` and `$lib/dynamic-components`, with their contestant-context reads replaced by app-context reads or props. The entry-flow holder (the state behind "email sent") is extracted so both contexts compose it.
- **The landing contract.** `app` enum in the request, a fixed `next` in the link, an allow-list in `verifyMailedLink`, the recovery arm by `next`, and the Contestant fallback redirect placed before its gates.
- **The SQL widening.** Migration `00021`, the `schema/` edit, the manifest line and pgTAP.
- **New Admin App routes and E2E.** Forgot-password, email-sent, password-reset and the protected server load, with E2E in a new fast leaf project rather than `admin-access`, which pulls the whole perm chain.

**Primary recommendation:**
- Build `next` as a **closed app enum** end to end: the request carries `app: 'admin'`, the Edge Function maps it to the fixed `next=/admin`, and `verifyMailedLink` accepts only allow-listed values and picks the reset page by them.
- Put the Contestant fallback redirect **before** stage 2 of its protected server load.
- Give the Admin App a `(protected)/+layout.server.ts` that owns the user-level read and the gate. The universal `+layout.ts` keeps its browser sign-out path and consumes the server's `user` instead of reading it again.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Which mail an address earns (sign-in / recovery / none) | Database (`recovery_link_request`, `invitation_link_request`, `private.email_holds_grant_in_project`) | Edge Function (`account-access`) | Eligibility reads `auth.users` and other users' grants; only the service role may. The function never decides eligibility. |
| Which app a mailed link names (`next`) | Edge Function (maps a closed `app` enum to a fixed path) | Frontend (sends the enum from the page the request was made on) | The link's content is built from configuration only. The request may pick from a closed set, never send a path. |
| Validating `next` and landing the user | Frontend server (`verifyMailedLink`, called by the confirm page's form action) | — | The one place a link is spent. An allow-list is applied there after verification. |
| Gate decision (set password before any page) | Frontend server (`+layout.server.ts` of each app's `(protected)` group) | Shared pure runner `$lib/auth/gates` | Decided on user-level data the server reads with this request's cookies. The runner is pure, frozen module state. |
| Gate rendering and focus | Browser (each protected `+layout.svelte`, through a shared outlet) | — | The view replaces the page; focus moves when the view changes without a navigation. |
| Fallback: admin-only user away from the Contestant App | Frontend server (Contestant `(protected)/+layout.server.ts`, before stage 2) | Confirm page's Cancel target (same predicate) | Decided from the verified session's grant claim, with no extra round trip. |
| App-entry gating on grant shapes | Frontend server (`passwordLogin` / `admitSession`, the protected loads) | Database RLS is authoritative | `ADMIN_GRANTS` / `CONTESTANT_GRANTS` are entry gates, not the authorisation boundary (`roles.ts` docstrings). |
| Entry flow (the held link request behind "email sent") | Browser (a per-context-instance `$state`) | — | Per-visitor memory. The server builds a context per render. |

### Pattern 1: Gate runner generic over id and facts

**What:** one pure runner, with each app's frozen list built from shared and own entries.
**When:** D-07 and D-08.

```typescript
// $lib/auth/gates/gates.ts — pure, frozen, no Svelte import
import type { BasicUserData } from '$lib/api/base/dataWriter.type';

/** The facts every gate list has: the signed-in user's user-level data. */
export type UserGateFacts = { readonly user: BasicUserData };

export type Gate<TId extends string, TFacts extends UserGateFacts> = {
  readonly id: TId;
  readonly isNeeded: (facts: TFacts) => boolean;
};

export function firstNeededGate<TId extends string, TFacts extends UserGateFacts>(
  facts: TFacts,
  gates: ReadonlyArray<Gate<TId, TFacts>>
): TId | null {
  return gates.find((gate) => gate.isNeeded(facts))?.id ?? null;
}

/** Exactly `false` and a proved address — the predicate `CONTESTANT_GATES[0]` has today. */
export const SET_PASSWORD_GATE: Gate<'setPassword', UserGateFacts> = Object.freeze({
  id: 'setPassword',
  isNeeded: ({ user }: UserGateFacts) => user.passwordSet === false && user.addressState === 'proved'
});
```

`ADMIN_GATES = Object.freeze([SET_PASSWORD_GATE])`. `CONTESTANT_GATES = Object.freeze([SET_PASSWORD_GATE, IDENTITY_PROVIDER_GATE, TERMS_OF_USE_GATE])`, typed over `ContestantGateFacts extends UserGateFacts`. The default argument (`gates = CONTESTANT_GATES`) goes away: every caller names its list. `gates.test.ts`'s freeze, Proxy-read and order cases move with it, and a new admin-list case pins `['setPassword']`.

### Pattern 2: The `next` contract as a closed enum

**What:** the page says which app it is in, the function maps that to a fixed path, and the landing allow-lists it.

The landing builds the target with `buildRoute(route key, locale)`, never by interpolating `next`.

### Pattern 3: Contestant fallback before stage 2

```typescript
// routes/contestant/(protected)/+layout.server.ts, between stage 1 and stage 2
const { session } = await locals.safeGetSession();
if (!session) return redirect(307, buildRoute({ route: 'ContestantAppLogin', locale: lang }));
// Rule 2: a session whose grants open the Admin App and not this one goes there; no user data is read.
if (isAdminOnly(readSessionGrants(session))) return redirect(303, buildRoute({ route: 'AdminAppHome', locale: lang }));
```

`isAdminOnly = (g) => hasAnyGrant(g, ADMIN_GRANTS) && !hasAnyGrant(g, CONTESTANT_GRANTS)`. The confirm page's `cancelHome` then calls the same helper (one declaration). It reads no `url`, so `layout.tracking.test.ts` stays green. A mixed-grant user is not redirected (D-04).

### Pattern 4: Admin protected loads, server owns the gate

- `(protected)/+layout.server.ts`: session (none → `redirect(307, AdminAppLogin, errorMessage:'loginFailed')`), then `createDataWriter({ fetch, locals }).getBasicUserData()`, then:
  - A read failure → **no sign-out**, to keep the admin-access cases "a read of the user data that fails at sign-in ends on the error page". Mirror the universal load: `isSessionGone` → redirect, else `error(503)`.
  - A non-boolean `passwordSet` is treated as a failed read.
  - Then `firstNeededGate({ user }, ADMIN_GATES)`, returning `{ gate, user }`. **Never return the session** (`assert:no-session-in-loads`).
- `(protected)/+layout.ts` (universal): keep the no-session redirect and the `handleError` browser path (announce, discard drafts, error 403/redirect). Replace its own `getUserData` call with `data.user` from the server. Replace `userData.role !== 'admin'` with the D-04 check, then return `{ userData: data.user, gate: data.gate }`.
- For the D-04 check, the measured equivalence `role === 'admin' ⇔ hasAnyGrant(grants, ADMIN_GRANTS)` means either form is behaviour-preserving. Reading the grants explicitly matches the D-04 wording. The universal load holds a client: in the browser `supabaseClient.auth.getSession()` gives an unverified token, so either keep the role (derived server-side from the verified token in `_getBasicUserData`) or have the server load return `admitted: hasAnyGrant(readSessionGrants(session), ADMIN_GRANTS)` alongside `user`. **Recommend the latter.** It is computed on the verified session, and the universal load only reads a boolean.
- The order of decisions on the server is session → **admin check** → user data → gate, so a non-admin is never shown the set-password view. If the server load finds the user not admitted, it returns `{ admitted: false }` and reads nothing further. The universal load then runs its existing sign-out path.
- Update `routeConsistency.test.ts`'s `ADMIN_PROTECTED_LAYOUT_FILE` if the `loginFailed` redirect moves or is duplicated. Rename or extend `routes/admin/(protected)/layout.server.test.ts`: today it tests the two **subtree** loads, so a new spec for the group load needs its own name.

### Pattern 5: Entry-flow holder composed by both contexts

Extract `sendEntryLink`, `resendEntryLink`, `clearEntryFlow`, `holdEntryCode`, the `entryFlow` getter and `#requestLink` into a small `$state.raw` class constructed per context instance. Its request function is injected: the Contestant passes the current calls, and the Admin passes `requestPasswordRecovery({ email, locale, app: 'admin' })`. `ContestantContextProvider` and `AdminContextProvider` each hold one instance and forward the members as arrow fields. No spread, per the getter-collision notes in both classes. `entryFlow` stays a **reactive accessor** (`ctx.entryFlow`, never destructured). The admin's `logout` must also clear it (the Contestant's `#reset` does).

### Anti-Patterns to Avoid

- **Validating `next` with `safeRedirectTarget`.** It admits any in-origin path. D-03 needs an allow-list.
- **Interpolating `next` into the redirect.** Use route keys and `buildRoute`.
- **Running the fallback after the gates.** The admin-only invitee would meet the Contestant set-password or terms view first (SC-1 says "never sees the Contestant App's gates").
- **Widening the helper to every role at global or account scope.** `(global, editor)` and `(account, editor)` carry no permission. Match the `ADMIN_GRANTS` shapes (`role = 'admin'`) at those two scopes.
- **Copying `SetPasswordGate` into the Admin App.** Forbidden by D-06 and D-07. Parameterise it instead.
- **Letting the admin set-password view's Log out do nothing visible.** `AdminContext.logout` does not navigate (only its header `LogoutButton` does `goto` and `leaveByFullLoad`). The shared view's logout must navigate to the app's login, or reuse the admin `LogoutButton`.
- **Leaving historical narrative** in the moved files' docstrings (comment hygiene).

## Common Pitfalls

### Pitfall 1: The widened helper changes sign-in links too
**What goes wrong:** pgTAP rows 4110-4125 and 6271-6289 of `39-invitations.test.sql` go red, and `invitation_link_request` starts mailing global and account admins sign-in links.
**Why:** `email_holds_grant_in_project` is shared by both RPCs.
**How to avoid:** decide explicitly. The recommendation is to widen both, because the admin's "I have not set a password yet" also goes through recovery, and a returning account admin should be able to get a link. Rewrite all four rows to assert the new outcome. Add the account-on-another-account refusal for **both** callers. Update the three comments.
**Warning signs:** `yarn workspace @openvaa/supabase test:db` failures naming "root admin" or "admin of the project's account".

### Pitfall 2: A failed admin link lands on the Contestant login
**What goes wrong:** an expired admin link shows the Contestant App login with "link failed". That is the A2 problem in another form.
**Why:** every failure branch of `verifyMailedLink` and the confirm page targets `ContestantAppLogin`, and the admin `LoginError` has no `authError`.
**How to avoid:** route failures by the allow-listed `next` too. This needs `authError` added to the admin `LoginError` (and its message key in 7 locales). The confirm page's load and action refuse a malformed link **before** reading `next`, so those keep the Contestant login unless the page also reads `next` there. See Open Question 3.

### Pitfall 3: The set-password view renders for a non-admin
**What goes wrong:** a contestant-only user typing `/admin` sees "Choose a password".
**Why:** the server gate runs before the universal role check.
**How to avoid:** the server load checks admission before reading user data or gates (Pattern 4). Add a unit test.

### Pitfall 4: Double user-data reads on SSR
**What goes wrong:** both the new server load and the universal load call `getBasicUserData`, costing four extra round trips per admin page.
**How to avoid:** the universal load consumes `data.user`.

### Pitfall 5: `routeConsistency` C5 and other text-reading guards
**What goes wrong:** C5 reads `admin/(protected)/+layout.ts` as text for `loginFailed`. `assert:no-session-in-loads` scans every server load. `assert:a11y-scan-wiring` lists axe-declaring spec files.
**How to avoid:** update the constant and the lists in the same commit as the change.

### Pitfall 6: The recovery-mail label drifts from the Admin login label
See F-H. `mailTemplates.test.ts` asserts the mail quotes `contestantApp.login.forgotPassword`. Render the same key on the Admin login, or extend the test to the admin label.

### Pitfall 7: Context destructuring in moved components
The moved `ContactSupport` reads `ctx.appSettings`, and the holder exposes `entryFlow`. Both are reactive accessors. Destructuring them captures a stale value.

### Pitfall 8: Test ids that name an app
`contestant-set-password-gate`, `contestant-forgot-password`, `contestant-email-sent` and `contestant-password-reset` sit on page roots and the gate root. If the shared view keeps the Contestant root id, admin specs assert on a "contestant" id. Choose neutral ids for the shared view root, or have the app pass a `data-testid`. Renaming ids costs edits across `testIds.ts`, the fixtures and the specs (measured: several fixtures read them).

### Pitfall 9: Treating a targeted `admin-access` run as quick
It pulls the full perm chain (full-suite time). Plans whose source change serves `admin-access` routes (the admin protected layout) must budget for that run, or the planner should consider which admin-access tests the change actually serves.

### Pitfall 10: Global grants in the shared E2E stack
A test-created global admin can read every project the stack holds. That is harmless locally, but the user must be removed with its grants by the spec's own hooks, and its address must use the spec's prefix, as `invitation-landing` does.

## Code Examples

### Widened helper (migration 00021 and `schema/506-invitation-rpcs.sql`, same text)

```sql
-- Sketch; the body keeps the function's catalogue signature (private, STABLE, search_path '', no API EXECUTE)
CREATE OR REPLACE FUNCTION private.email_holds_grant_in_project (p_project_id uuid, p_email text) RETURNS boolean LANGUAGE sql STABLE
SET
  search_path = '' AS $$
  SELECT EXISTS (
    SELECT 1
    FROM auth.users u
    WHERE lower(btrim(u.email)) = p_email
      AND u.email_confirmed_at IS NOT NULL
      AND EXISTS (
        SELECT 1
        FROM public.grants g
        WHERE g.user_id = u.id
          AND (
            (g.scope = 'project' AND g.target_id = p_project_id)
            OR (g.scope = 'entity' AND private.entity_project_id(g.target_type, g.target_id) = p_project_id)
            OR (g.scope = 'global' AND g.role = 'admin')
            OR (g.scope = 'account' AND g.role = 'admin' AND EXISTS (
                  SELECT 1 FROM public.projects p WHERE p.id = p_project_id AND p.account_id = g.target_id))
          )
      )
  );
$$;
```

The scope, role and project/account identifiers are quoted from `300-auth-tables.sql:10-27`, `301-auth-functions.sql:518-523` and `506-invitation-rpcs.sql:758-776`. The `g.role = 'admin'` conjunct at the two new scopes is a recommendation [ASSUMED: matches the `ADMIN_GRANTS` shapes; see Assumptions A1]. A null `p_project_id` is already refused by both callers before the helper runs. The `projects` join also refuses a project that does not exist.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Supabase Auth; recovery and magic links are single-use tokens verified on `POST` (confirm page); the password is set through `setPassword` on the verified session |
| V3 Session Management | yes | cookie sessions via `@supabase/ssr`; `withdrawLogoutCount`; held session signed out before a link is verified |
| V4 Access Control | yes | entry gates `ADMIN_GRANTS`/`CONTESTANT_GRANTS` (not authoritative); RLS via `user_can` is the boundary |
| V5 Input Validation | yes | `parseAccountAccessRequest` (closed enum, malformed → 400); `next` allow-list; `isMailedLinkType` |
| V6 Cryptography | no new | token hashing by the auth service; none hand-rolled |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Open redirect through `next` | Spoofing/Tampering | allow-list lookup to route keys; never interpolate; the function writes `next` from a constant map |
| Account enumeration through recovery | Information disclosure | the uniform `{ accepted: true }` answer built before any work; the email-sent screen reads nothing of the answer (unchanged; do not add admin-specific answers) |
| Mail bombing an admin address | DoS | existing slots: one per address per project per 60 s, twenty per address per day (A6) apply to the widened eligibility unchanged |
| Login CSRF and scanner token spend | Spoofing | confirm page POST with SvelteKit's origin check (179.1); admin links reuse it |
| Privilege confusion: a contestant user sees the admin set-password view | Elevation (UI) | admission check before the gate on the server (Pattern 4) |
| Global grant created in tests leaking | Elevation | spec-prefixed users removed with their grants in hooks; `afterAll` asserts nothing is left |
