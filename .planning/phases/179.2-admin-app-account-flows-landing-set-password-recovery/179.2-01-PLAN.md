Why the plan is this large: the moves touch every contestant screen and the header, so the plan's one targeted run is a run of every leaf (`--project perm-closed-project`, about one full run, accepted explicitly per the execution rules). Putting all of D-06 here keeps that cost to one run instead of one per component.

Design choice recorded (Claude's discretion, D-07): the Admin App's universal load keeps reading the user data with the tab's own client in the browser, and takes the server load's `user` during server rendering. The server load reads for the gate; in the browser the universal load's own read keeps the failure handling that `admin-access`'s two "a read of the user data that fails" cases drive through the browser (they fail the browser's `get_user_entities` request, which a server-side read would never make). The double read is on client navigations only; the server-rendered request reads once (research Pitfall 4).

Output: `$lib/auth/gates`, `ADMIN_GATES`, the Admin App's server gate, the shared `SetPasswordGate` and `GateOutlet`, the seven moved or merged components, the new leaf project `admin-account-flows` with its first journey, the totals check, the ledger and the deltas table.
