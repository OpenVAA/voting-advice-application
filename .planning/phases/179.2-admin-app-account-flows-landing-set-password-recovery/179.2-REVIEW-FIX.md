## Findings

### CR-01: redirect loop on a document request to an Admin protected page. Disposition: **no_change_needed**, because it did not reproduce

The cause was unconfirmed, so it was checked by observation first. A new E2E case signs a candidate in to the Contestant App and then opens `/admin` with `page.goto`, which is a full page load. It passed on the unchanged tree (`tests/e2e-runs/179.2/179.2-fix-red-1`, 22 of 22). The browser ended on the Admin login with `userNotAuthorized` and its sentence, and the next open of the Contestant App asked for a sign-in, so the session had ended.

The reviewer's trace missed two mechanisms. Each of them ends the session on its own during server rendering:

1. `UniversalDataWriter.logout()` posts to `/api/auth/logout` through the load's `fetch`. On the server, SvelteKit runs that as an internal request, and it copies the endpoint's `Set-Cookie` headers onto the document response (`@sveltejs/kit/src/runtime/server/fetch.js`, `set_internal`). The cookies are therefore cleared.
2. `signOut({ scope: 'local' })` is not a no-op. auth-js calls `admin.signOut(accessToken, 'local')`, which is a `POST /logout?scope=local` to the auth service and ends the session there. After it, `safeGetSession` finds no session, so the request hook does not send the login page back to the home.

Each mechanism was tested by mutating the working tree only. With the universal load's `logout()` replaced by `backendLogout()`, so that only mechanism 2 remained, the case still passed (`179.2-fix-red-1b`). With the sign-out removed altogether, the case failed with `page.goto: net::ERR_TOO_MANY_REDIRECTS at …/admin` (`179.2-fix-red-1c`). So the loop the reviewer described is real only if both mechanisms are missing, and the new case catches it. Both mutations were reverted with `git checkout`, and no product change was made.

The case is kept because the server-rendering path of this refusal had no E2E coverage: every earlier case used a client-side navigation. Commit `178b2ee4d`. Ledger row 179.2-RF-1.

### WR-01: admin-app mailed links strand non-admins. Disposition: **fixed** (`f8eaa5f79`)

`verifyMailedLink` keeps choosing the landing from `next`. After the claim, for a link that names the Admin App, it now also reads the grants that reach this project. If `isContestantOnly` says those grants open the Contestant App and not the Admin App, the link lands on the Contestant App's page instead: the home for a sign-in link, the password reset for a recovery link. `isContestantOnly` is the new mirror of `isAdminOnly`, and no grant set is true for both, which a unit case pins. So there can be no loop with the Contestant App's fallback. A mixed-grant user, an admin, and a user with no grant that opens either app keep the Admin App landing. A read of the grants that fails also keeps it, and is logged. A link that names no app reads nothing.

The fix sits at the landing, not as a general redirect in the Admin protected load. The operator's ruling names a user who lands in the Admin App *from a mailed link*. A general redirect would also have changed the three existing `contestant-entity-selection` cases, in which a non-admin who follows a link into the Admin App is signed out there. See Deviations.

- Unit tests: `mailedLink.test.ts`, the four grant-set rows on both arms, the failed read, and a link with no `next`. Ledger row RF-6.
- E2E (`179.2-fix-red-2` red, `179.2-fix-green-2` green, row RF-2): a candidate invited by email starts at the Admin login, follows "I have not set a password yet" and sends the request. The link it receives names `/admin`. Opened, it shows the Contestant App's set-password view. A password is saved, and then signs the user in at the Contestant login.

### WR-02: app-entry checks ignore the project a grant is for. Disposition: **fixed** (`ec439465c`, `f8eaa5f79`)

First, what the session carries. The token's `grants` claim lists every grant the user holds, each with its `target_id`, in every project. The project id is known, from `PUBLIC_PROJECT_ID`. The project's account id is not in the token, and neither is the project an entity belongs to. Under row-level security, `projects` can be read only by someone who holds a grant in that project. So only the database can apply migration 00021's rule, and the check is made there.

- **Database.** `private.grant_reaches_project(scope, target_type, target_id, project)` states the 00021 rule once: a project grant on the project, an entity grant on one of its entities, any global grant, or an account grant on its account, whatever the role. `email_holds_grant_in_project` now asks it, with an unchanged answer, which pgTAP file 39 confirms. `public.get_user_project_grants(p_project_id)` is SECURITY DEFINER, has an empty search_path, and only `authenticated` may execute it. It returns the caller's own rows that reach the project, in the claim's shape. Migration 00022 and its manifest line, `yarn check:schema-equivalence` 0, `db:types`, `db:lint:sql` 0.
- **Frontend.** The writer's `getProjectGrants()` reads that function. Where it is used:
  - The Admin protected load admits only on an admin grant that reaches this project. A failed read is answered as a failed user-data read is.
  - The Admin login gate (`admitSession` with the context's optional `getProjectGrants`) refuses an admin of another project only with 403 `grantNotAllowed`. A failed read refuses with 500 `grantsUnread`, and the session is signed out in both cases. This gate was not in the brief's list; see Deviations.
  - `isAdminOnlyInProject` serves the Contestant fallback and the confirm page's Cancel. It reads the project's grants only when the token holds an admin grant somewhere, so a candidate's load makes no extra call. A failed read sends nobody to the Admin App.
  - `scripts/assert-project-scoped-queries.mjs` lists the new RPC.
- **Tests.**
  - pgTAP: `58-user-project-grants.test.sql` (17 `UPG:` rows) and the `authenticated` census in file 07. Red `179.2-fix-pgtap-red-1`, green `179.2-fix-pgtap-green-1` (58 files, 2898 tests). Row RF-4.
  - Unit: rows RF-5, RF-6 and RF-7.

## Deviations

1. **WR-01 lands at the mailed link, not as a general redirect in the Admin protected load.** The ruling's scope is "from a mailed link". A general mirror would also have redirected a signed-in candidate who types `/admin`, and that would have rewritten three existing `contestant-entity-selection` cases. The no-loop property holds because no grant set is both `isAdminOnly` and `isContestantOnly`.
2. **WR-02 also scopes the Admin login gate**, which the brief did not list. Without it, an admin of another project passed the login, was refused by the protected load, and came back to the reused login component with no message: the page reads its reason once, when it mounts. Scoping the gate shows the existing 403 sentence. The Contestant login and the code sign-in still gate on the token. A candidate of another project only is therefore still admitted at the Contestant login, which then lists nothing.
3. **The project's grants are read only when the token holds an admin shape.** This applies to the Admin admission, the Contestant fallback and Cancel. It saves a call on every candidate load. A grant written after the token was issued counts once the token is refreshed, as it did before.
4. **No `--project perm-closed-project` targeted run.** The served set is the broad case. The one full run of record on the same head, which runs all 129 projects against perm-closed-project's 128, stands in for it.
5. **`179.2-totals.mjs` accepts `RF` as a row label** (`179.2-(?:\d+|RF)`), so that the review-fix row is summed without posing as a plan number.
6. **IN-03 adds a `catch`** beside the review's `finally`. See above.
7. **Two pairs of red runs.** The WR-01 and WR-02 E2E cases sit in one serial describe, so one red run could show only the first failure. The WR-02 red (`179.2-fix-red-3`) was therefore run with the WR-01 case marked `test.skip` in the working tree only, and the spec was restored before the green run.
