## The shell

- Begin every shell call that runs `yarn`, `npx` or `node` with `export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"`.
- A status is read from the command itself, **never through a pipe**. A commit follows a gate with `&&`.
- No E2E run, pgTAP run, `yarn db:reset`, `yarn lint:check`, `yarn build`, `yarn test:unit` or `yarn check:schema-equivalence` runs in the foreground. Launch it in the shell tool's background mode as `( caffeinate -dimsu <command>; echo $? > <marker>.exit ) > <marker>.log 2>&1` and poll with one short foreground command per poll (a bounded loop of at most 45 one-second waits that ends when the `.exit` marker exists). Ceilings: 30 minutes for a `perm-closed-project` or full run, 15 for any other. A foreground long gate trips the executor's 600-second watchdog.
- Before a long run: `pmset -g batt`; no run on battery below 30 %. On `ENOSPC`: `docker builder prune -af` first.
- An `<automated>` block is written byte for byte into `$U/<plan>-t<N>-verify.sh` and run with `bash` (backgrounded and polled when it holds a long gate), its log, status and head kept beside it.
- `.env` is never read, listed or tested for; the template is `.env.example`.

## The stack

The shared Supabase stack is free for this phase under the standing authorisation (2026-10-20): no plan asks for it and no checkpoint asks whether it is free. No two tasks use it at once; plans run one after another. `yarn db:reset` never runs while an E2E run is in flight (a `started` marker without an `ended` beside it under `tests/e2e-runs/`). ### The stack check (first stack use of every plan)

The stack is shared with the `-infra` worktree, which uses it with its own schema and functions (operator note, 2026-11-12: at planning it served `-infra`'s schema, 1 applied migration against this tree's 20, and its edge runtime mounted `voting-advice-application-infra/apps/supabase/supabase/functions`). So **before the first stack-dependent command of every plan** (`yarn test:unit`, `yarn workspace @openvaa/supabase test:db`, `yarn db:*`, `yarn check:schema-equivalence`, any `tests/scripts/e2e-run.sh`), and again before such a command whenever the stack may have been used from another worktree since the last check (after a pause, a resumed task or a host restart), the executor runs this check from this worktree's root, `/Users/kallejarvenpaa/Desktop/OpenVAA/voting-advice-application-gsd`. It is no human checkpoint.

1. **Restart from this worktree.** `yarn db:stop 2>&1 | node tests/scripts/withhold-stack-keys.mjs > $U/<plan>-stack-stop.log; test "${PIPESTATUS[0]}" = 0`, then the same with `yarn db:start` into `$U/<plan>-stack-start.log`. The keys never reach a log.
2. **(a) The schema is this tree's.** `docker exec -i supabase_db_openvaa-local psql -U postgres -d postgres -X -q -t -A -c "select count(*) from supabase_migrations.schema_migrations"` equals `node -e 'console.log(require("./apps/supabase/supabase/migrations.manifest.json").migrations.length)'`. When it does not, `yarn db:reset` (in the background, polled) and then `yarn db:seed:default`, and the comparison is made again; a second mismatch stops the plan and is reported.
3. **(b) The functions are this tree's.** `docker inspect supabase_edge_runtime_openvaa-local --format '{{range .Mounts}}{{.Destination}}{{"\n"}}{{end}}'` lists exactly `$PWD/apps/supabase/supabase/functions` as one of its lines. When it does not after step 1, the plan stops and reports.
4. **The record.** `$U/<plan>-stack.txt` holds three lines, `migrations_applied=<n>`, `migrations_manifest=<n>` and `functions_mount=<the matching destination>`, plus `checked_at=<UTC time>`, written only when (a) and (b) hold. Each plan's first task's `<verify>` reads it. A later re-check overwrites it.

The E2E wrapper restores the stack at its own end with `yarn db:stop` and `yarn db:start` run from this worktree, so a run leaves the stack serving this tree; another worktree may still take it over between plans, which is why the check opens every plan.

### An interrupted or resumed task

Every task ends in its own commit(s), so the tree between tasks is always a committed state. A fresh executor may take any task. On a resume it re-reads this file, the plan's `<resume_points>` section and the summaries of the plans before it; reads `git log --oneline 73100378b..HEAD` to see which of the plan's task commits exist; reads the ledger and the deltas table; and runs the stack check. A working tree with uncommitted changes outside `.planning/` means a task was interrupted: the executor compares them with that task's `<files>`, and either continues from them (the red evidence already under `$U` and `$R` still counts when its `.head` is the current `HEAD`) or discards them with `git checkout -- <the task's files>`, deletes the task's new files, and starts the task again.

- **pgTAP:** the new and rewritten assertions alone, `yarn workspace @openvaa/supabase test:db` in the background, kept as `$U/<plan>-pgtap-red-<n>.{log,exit,head}`, red in `39-invitations` only.

Then the product change is added and the same project is run again as `$R/<plan>-green-<n>`, judged with `--passed-test "<title part>" … --no-flaky`. Then the one commit of spec, fixtures and product change. **No red E2E test is ever committed, and no commit turns a committed test red.**
- Every such test has a row in the ledger, written by the plan that adds it: `| <plan>-<n> | <file> › <title> | <what was withheld> | <red run or log, first failing line> | <green run or log> | confirmed |`. A row whose red was not observed says `pending` in its last cell and is never written as confirmed. Plan 04 does not close while a row is `pending`.

## Targeted E2E (operator ruling, 2026-11-09)

Within the phase no plan makes a full run except plan 04, the final plan. A plan's browser proof is its one-project red and green runs plus **one targeted green run after its last code commit** for every project its changes serve: every project whose spec, fixture or setup the plan adds or changes, and every project whose tests drive a route, a component, a context or a helper the plan's source change edits. The wrapper keeps only its last `--project`, so it is one run per project.

**The broad case, accepted explicitly.** `--project admin-access` pulls 108 of the suite's 129 projects (the perm serial chain), and the Contestant App's protected layout, its context, the header's Log out and the mailed-link landing are reached by nearly every contestant and admin project. A plan whose served set holds any perm-chain project, `admin-access` or `contestant-journey` makes its targeted run as the single `tests/scripts/e2e-run.sh --run-dir $R/<plan>-targeted --no-db-reset --project perm-closed-project`, whose dependencies are 128 of the 129 projects (every one but `_probes`; measured at planning). It costs about one full run; the 179.1-88 precedent did the same. Plans 01 and 02 are such plans; plan 03 names its own set.

**Judging a targeted run.** After `node tests/scripts/e2e-evidence.mjs <run>`:
1. `node $P/179.2-totals.mjs <run> --slice` exits 0 (contract below);
2. `node tests/scripts/e2e-spec-verdict.mjs <run> --no-flaky` plus one `--passed-test "<title part>"` per title the plan pins exits 0;
3. `git diff --quiet "$(cat <run>/head)" HEAD -- . ':(exclude).planning'` exits 0 (the run is of the committed tree).
A status 8 run (marker `VOID-host-suspend.txt`) is void: kept, never diagnosed, made again as `<label>-r2`. A red run without the marker is a failure; with no other cause, `pmset -g log` is read before the tree is blamed. A did-not-run test is a failure. Nothing is retried until green on an unchanged tree; no test is skipped or annotated to pass.

**The visual project is not run.** `visual-regression` is opt-in and outside the default run; it captures the voter results and the contestant preview, whose markup no plan of this phase changes (the moved components render what they rendered). A plan that finds its change alters what either of those pages renders stops and reports.

**The deltas.** Each plan appends one row per project whose test count it changes to `$P/179.2-E2E-DELTAS.md`, under the table header `| plan | project | delta | titles added or renamed |`, rows shaped `| 179.2-NN | <project> | +N | <title>; <title> |`. A project with no changed count gets no row. Plan 04's full run is judged with every row summed.

## The totals check (`$P/179.2-totals.mjs`, created by plan 01)

`node $P/179.2-totals.mjs <run-dir> --slice|--full [--baseline <dir>] [--deltas <file>]`, with defaults `--baseline tests/e2e-runs/179.1-e2e/179.1-90-final` and `--deltas $P/179.2-E2E-DELTAS.md`. It reads `<run-dir>/summary.json` (written by `tests/scripts/e2e-evidence.mjs`) and the baseline's `summary.json`, sums the deltas file's rows per project (rows matching `^\| *179\.2-\d+ *\| *<project> *\| *[+-]?\d+ *\|`), and exits 0 only when: `void` is null, `wrapperExit` is 0, `counts.total` > 0 and `counts.passed` equals `counts.total`; every project of the run has `total` equal to the baseline's `total` for it (0 when absent) plus its summed delta; and, with `--full`, every project of the baseline and of the deltas file is present in the run. Every mismatch is printed on its own line; any other outcome exits 1, and an unreadable file exits 2. It writes nothing.
