## Critical Issues

### CR-01: A non-admin's document request to an Admin App protected page redirects in a loop

**File:** `apps/frontend/src/routes/admin/(protected)/+layout.ts:38,62-85` (with `apps/frontend/src/routes/admin/(protected)/+layout.server.ts:37`, `apps/frontend/src/lib/supabase/universal.ts:51-61`, `apps/frontend/src/hooks.server.ts:157-160`)

**Issue:** The server load answers `{ admitted: false }` and leaves the sign-out to the universal load's `handleError`. During server rendering, that load's client is `createSupabaseUniversalClient`'s server arm, which has `getAll` and deliberately no `setAll` (`universal.ts`: "a setter here could only be a silent no-op"). `dataWriter.logout()` skips the logout endpoint when `window` is undefined (`supabaseDataWriter.ts:461`) and calls `signOut({ scope: 'local' })`. That call makes no network request and removes the session only from a storage that writes nothing, so it resolves with no error. `signedOut` is then `true`, `sessionEnded` is `true`, and the load redirects 307 to `AdminAppLogin?errorMessage=userNotAuthorized`. The browser still holds valid session cookies. The request hook sends a session on an entry route to the app's home (`hooks.server.ts:157-160`, `whenAuthenticatedOnLogin` is `AdminAppHome`), and the home's SSR pass refuses the user again. The browser ends on `ERR_TOO_MANY_REDIRECTS`, and the user is never signed out. `handleError`'s own comment states this mechanism for a failed sign-out ("after its own failed sign-out it answers no session while the browser still holds one, and a redirect would come straight back"), but a sign-out that worked on the server has the same effect.

The cases that reach it: a reload, a typed or bookmarked `/admin` URL, a link that opens in a new tab, and a mailed link with `next=/admin` whose Continue is posted natively, before hydration or without JS. That last case leads to a 303 document request for `AdminAppHome`, which WR-01 makes reachable for non-admins. Every E2E for this refusal (`contestant-entity-selection.spec.ts:1898-1979`) uses `followLinkInsideTheApp`, a client-side navigation whose browser sign-out clears the cookies through the endpoint, so the SSR path is not covered. The mechanism predates the phase. This phase rewrote this admission and added a server load that holds `locals.supabase`, the one client that can clear the cookies, without using it. Traced statically, not executed, because the stack was off limits.

**Fix:** End the session in the server load, on the cookie-writing client, the way the Contestant App's `signOutToLogin` does:
```ts
// +layout.server.ts
if (!hasAnyGrant(readSessionGrants(session), ADMIN_GRANTS)) {
  const { error: signOutError } = await locals.supabase.auth.signOut({ scope: 'local' })
    .catch((e: Error) => ({ error: e }));
  if (signOutError && !(await dataWriter.isSessionGone())) return error(403, { message: t('error.403') });
  withdrawLogoutCount(event);
  return redirect(307, buildRoute({ route: 'AdminAppLogin', locale: lang, errorMessage: 'userNotAuthorized' }));
}
```
Keep the universal `handleError` for the browser only, where it also announces the logout and discards drafts. At the least, treat `!browser` as unable to end the session (`const sessionEnded = browser && (signedOut || await dataWriter.isSessionGone())`), so the SSR pass ends on the 403 page instead of looping. Add an E2E that opens `/admin` with `page.goto` as a signed-in candidate.

## Warnings

### WR-01: Admin-app mailed links land non-admins in the Admin App, which signs them out; there is no reverse fallback

**File:** `apps/frontend/src/lib/server/auth/mailedLink.ts:154,174,184` (with `apps/frontend/src/lib/contexts/admin/adminContext.svelte.ts` `#requestLink`, `apps/frontend/src/routes/admin/(protected)/+layout.ts:38`)

**Issue:** The Admin App's forgot-password page asks a recovery for any typed address, with `app: 'admin'`. Both mails `request-recovery` can send (`linkIssue.ts`, `app: request.app`) then carry `next=/admin`, and `verifyMailedLink` lands every verified link by `next` alone, whatever grants the claim wrote.

- An address with only a candidate or organization invitation gets the sign-in mail. The candidate opens it from the Admin App's "I have not set a password yet", the claim writes an entity editor grant, and the user goes to `AdminAppHome`. There the user is refused and signed out with "You need admin privileges". The one-time link is spent, and the password was never set.
- A contestant-only account holder gets a recovery mail, sets a password on `AdminAppResetPassword`, and is then signed out in the same way.

The phase builds the fallback in one direction only (Contestant to Admin for `isAdminOnly`). The opposite case, a session that opens only the Contestant App arriving in the Admin App, is refused rather than redirected. With CR-01, a native (non-enhanced) Continue makes it a redirect loop instead of a sign-out.

**Fix:** Land by the refreshed session's grants. After `claimAndRefresh`, read the session's grants and take `landing.home` or `landing.resetPassword` only when they open that app; otherwise fall back to `CONTESTANT_APP_LANDING`. Alternatively, mirror `isAdminOnly` in the Admin App's server load: a session with a `CONTESTANT_GRANTS` shape and no `ADMIN_GRANTS` shape is redirected (303) to `ContestantAppHome`, not signed out.

### WR-02: The app-entry gates ignore a grant's target, so grants in other projects admit and redirect

**File:** `apps/frontend/src/lib/auth/roles.ts:13-22,58-62`; used by `apps/frontend/src/routes/admin/(protected)/+layout.server.ts:37`, `apps/frontend/src/lib/auth/homeApp.ts:12`, `apps/frontend/src/routes/contestant/(protected)/+layout.server.ts:58`, `apps/frontend/src/routes/auth/confirm/+page.server.ts:39`

**Issue:** `hasAnyGrant` matches `(scope, role[, target_type])` and never `target_id`. Migration 00021 now carefully limits an account grant to the project's own account, but the frontend gates that this phase made decisive do not:

- A project admin of project B is admitted to project A's Admin App, with the set-password gate and an empty view.
- A user whose only grant is a project-B admin grant is redirected from project A's Contestant App to project A's Admin App.
- A user who edits a candidate in project B and is an admin in project A counts as not `isAdminOnly`, so stays in project A's Contestant App with "nothing to edit" and is never sent to the Admin App where they are an admin.
- The confirm page's Cancel follows the same unscoped reading.

Row-level security still protects the data, which `ADMIN_GRANTS`' own comment notes. The phase moved admission onto this match, though, and added a cross-app redirect that depends on it, so a wrong app, a wrong gate and a wrong redirect are now user-visible.

**Fix:** Scope the project-scope shapes to the deployment's project, e.g. `isAdminOnly(grants, projectId)` and `hasAnyGrantIn(grants, ADMIN_GRANTS, { projectId: constants.PUBLIC_PROJECT_ID })` comparing `claim.target_id` for `scope === 'project'`. Answer account scope on the server through the database (`user_has_account_grant` / `user_can`), because the token does not say which account a project belongs to. Apply the same scoping to `CONTESTANT_GRANTS` through `private.entity_project_id`'s public equivalent, or leave it to the entity list, which is already scoped.

### IN-02: Eligibility for recovery and sign-in mail is now wider than any app admits

**File:** `apps/supabase/supabase/migrations/00021_email_holds_global_or_account_grant.sql:26-38`

**Issue:** Under the operator's ruling (any role at global or account scope), a global or account **editor** is mailed a recovery or sign-in link. No app admits them: `ADMIN_GRANTS` lists only `admin` at those scopes, and `CONTESTANT_GRANTS` only entity editors. The link signs them in. The Admin App then signs them out with "userNotAuthorized" (or loops, as in CR-01, on a document request), and the Contestant App shows "nothing to edit". This follows the ruling and is recorded only so the follow-on behaviour is a known consequence.

**Fix:** None required by the ruling. If the dead end matters, either narrow the mail eligibility to roles some app admits, or let the landing (WR-01) send such a user to a page that explains their access.

### IN-03: The shared forgot-password screen stays "loading" when its navigation rejects

**File:** `apps/frontend/src/lib/dynamic-components/accountScreens/ForgotPasswordScreen.svelte:67-70`

**Issue:** `requesting = true; await sendEntryLink(...); await goto(emailSentHref); requesting = false;` has no `try`/`finally`. A rejected `goto`, such as an aborted navigation, leaves the button spinning, and further presses return at once (`if (requesting) return`). The code was carried over from the Contestant page and now serves both apps.

**Fix:** Wrap the navigation in `try { await goto(emailSentHref); } finally { requesting = false; }`.

### IN-04: The Admin App's support mail names the app inconsistently

**File:** `apps/frontend/src/lib/dynamic-components/contactSupport/ContactSupport.svelte:81`

### IN-05: Impossible-state guard: optional chaining on non-optional arrays in `contestantLogoutWarning`
