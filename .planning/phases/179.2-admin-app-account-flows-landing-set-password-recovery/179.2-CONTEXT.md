# Phase 179.2: Admin App Account Flows — Landing, Set Password & Recovery - Context

**Gathered:** 2026-10-25
**Status:** Ready for planning (after Phase 179.1 closes)

<domain>
## Phase Boundary

A user who holds only admin grants never meets the Contestant App. An invitee requests and opens their link from
the Admin App. The Admin App asks for a password before any page when none is set. A holder of a global or
account grant can get a recovery mail and reset the password in the Admin App. The screens and the gate
mechanism are the Contestant App's own, shared rather than copied, and the Admin App runs them over its own
shorter list of user-task gates.

The phase builds review items A2 and A4 (overruled by the operator to "build it in the Admin App" and "give them
their own recovery eligibility") and E2, the CLAUDE.md Auth sentence. It depends on 179.1, whose app-neutral
confirm page (179.1 CONTEXT D-08) the Admin App's links also use.

Sources, in order of precedence: this file, then `.planning/v2.16-179.1-179.2-DISCUSSION-POINTS.md` (every
decision was taken at its ★ RECOMMENDED; the operator ticked nothing and added no NOTE, confirmed 2026-10-25),
then `.planning/REVIEW-DECISIONS-166-179.md` A2 and A4 and the operator's notes on them.

**Operator's standing notes (A2, A4):** make every possible part reusable; the Admin App should work the same way
as the Contestant App for these accounts, with its own, shorter list of user-task gates.

</domain>

## Implementation Decisions

### Inherited from the cross-phase decisions
- **D-01:** Schema changes are appended numbered migrations following 179.1's, each with its `schema/` edit,
  manifest line and pgTAP, then `yarn db:types` and `yarn db:lint:sql` (X3).
- **D-02:** Closing gate: one full E2E run green through `tests/scripts/e2e-run.sh`, pgTAP green and every gate
  green, all on one tree. Every new test is shown failing without its change (X4).

### A. Landing
- **D-03 (A1):** Both rules are built.
  - **Rule 1.** The Admin App's login gets the same two entries as the Contestant App's: "I have not set a password
    yet" and "Forgot password". A link requested there carries the Admin App as its `next`, so the callback (after
    179.1's confirm page) lands it there. This replaces F11, where every recovery link went to
    `ContestantAppResetPassword` and every other type went to the Contestant App.
  - **Rule 2, the fallback.** A signed-in user who reaches the Contestant App holding admin grants but no
    contestant grant is redirected to the Admin App. This covers an invitee who started from the Contestant App's
    login.

  `next` must be validated against an allow-list of in-app paths, so it can never become an open redirect.
  — **Reversibility:** costly — the `next` contract is shared by the confirm page, the callback, the
  `account-access` Edge Function and the E2E specs.
- **D-04 (A2):** Folds in the todo `2026-10-02-admin-with-candidate-grant-locked-out-of-admin-app.md`. The Admin
  App admits on an `ADMIN_GRANTS` match rather than on the single resolved `userData.role`, so a user holding an
  admin grant and an entity editor grant can use both apps (F7). Rule 2's redirect does not apply to such a user.
- **D-05 (A3):** Project editors are out of scope. `(project, editor)` is **not** added to `ADMIN_GRANTS`. The todo
  `2026-10-07-174-admin-grants-admit-no-project-editor.md` stays with the phase that builds Admin App screens for
  project editors.

### B. Shared building blocks
- **D-06 (B1):** The account components move to a shared folder: `passwordSetter`, `passwordField`,
  `passwordValidator`, `emailEntry`, `emailField`, `emailSentPanel`, `contactSupport` and `logoutButton`. They go
  under `$lib/components`, or under `$lib/dynamic-components` for those that read a context. Their
  `getContestantContext()` reads (F10: `contactSupport`, `logoutButton`) are replaced by props or by the app
  context. Both apps import from the new place; nothing is left behind in `$contestant/components` and no copy is
  made. — **Reversibility:** costly — every import site in the Contestant App moves, along with the docs pages that
  document these components.
- **D-07 (B2):** `firstNeededGate` is generalised into an app-neutral runner (e.g. `$lib/auth/gates`) that takes an
  ordered gate list. The Contestant App keeps `CONTESTANT_GATES` (`setPassword`, `identityProvider`,
  `termsOfUse`). The Admin App gets a server `+layout.server.ts` for `admin/(protected)` that runs its own list
  (F9: today it is a universal `+layout.ts` with no server load).
- **D-08 (B3):** The Admin App's gate list is `setPassword` only. Identity-provider accounts hold no admin grants,
  and the terms of use cover entity content, which admins do not publish.

### C. Recovery for global and account grant holders
- **D-09 (C1):** `private.email_holds_grant_in_project` is widened with the same reach `user_can` uses. It now also
  admits a global admin grant, or an account grant on the named project's account. The request still names the
  project (`PUBLIC_PROJECT_ID`). pgTAP covers both new cases, plus a refusal for an account grant on another
  account. The per-address mail cap (A6) applies unchanged.
- **D-10 (C2):** The recovery link lands by its `next`, as in D-03. A request from the Admin App's forgot-password
  page lands on an Admin App password-reset page built from the shared components. A request from the Contestant
  App lands where it does today.
- **D-11 (C3):** The existing per-locale mail templates are used. Any wording specific to the Contestant App is
  made app-neutral; no admin templates are added.

### D. Coverage, design, CLAUDE.md
- **D-12 (D1):** The E2E specs cover:
  - an invited project admin who asks for a link from the Admin App's login, sets a password there and reaches the
    Admin home;
  - a global or account admin who recovers a password from the Admin App;
  - the fallback redirect of D-03 rule 2;
  - the mixed-grant user of D-04, in both apps;
  - axe scans of the new Admin App screens in both themes.
- **D-13 (D2):** `/gsd-ui-phase` is skipped. The screens reuse the Contestant App's components and layouts, with no
  new visual design.
- **D-14:** The new Admin App screens' strings come in 7 locales (the CSCAN gate), flagged for a native-speaker
  check.
- **D-15 (E1 / review E2):** The CLAUDE.md § Backend Auth sentence is applied at 179.2's close. It is rewritten to
  name both apps' set-password gates, the confirmed-address precondition and the identity provider's address step
  (the original E2 proposal), and 179.1's confirm page.

## Operator rulings after research (2026-11-12)

Answered on the open questions of `179.2-RESEARCH.md`; these override the research's recommendations where they differ.

- **D-15 (Open Question 1, LogoutButton):** merge. One shared `$lib/dynamic-components/logoutButton` serves both apps; the Contestant App passes its "what is left to do" warning in as a prop from its own context. Nothing of it stays in `$contestant/components`. (Research recommended leaving both; overruled.)
- **D-16 (recovery widening):** `private.email_holds_grant_in_project` widens to **any** grant at global or account scope, whatever its role — not only `role = 'admin'`. This also widens sign-in links through `invitation_link_request`; the four pgTAP rows asserting the old refusal are rewritten. (Research recommended admin-only; overruled.)
- **D-17 (Open Question 3, refused admin link):** the confirm page reads the link's destination through the same allow-list before its own refusals (missing token, unknown type), so a refused or failed admin link lands on the Admin login, with an `authError` reason in the admin login errors and its strings in all 7 locales (flagged for native review per D-14).
- Open Questions 2, 4, 5 and 6 follow the research's recommendations.

## Operator rulings on the code review (2026-11-12)

Rulings on `179.2-REVIEW.md` findings:

- **CR-01** (non-admin full page load of an Admin App protected page loops between login and home): fix, red-first.
- **WR-01** (a link mailed from an Admin App request always lands in the Admin App): a non-admin who lands in the Admin App from a mailed link is sent on to the Contestant App, mirroring the Contestant-to-Admin fallback, so the link is not wasted.
- **WR-02** (app-entry checks ignore which project a grant is for): scope them to this project — count only grants for this project, its account, or global scope, the same rule migration 00021 uses.
- **IN-02** (global/account editors get mail but no app admits them): keep D-16 as ruled. Operator: "They'll be lead to the admin app but when it's fully implemented they'll only see parts of the functions there." No admission change in this phase; the partial Admin App for editors is future work.
- IN-01, IN-03, IN-04, IN-05: fix as the review recommends.
