## The design, settled before the first line of SQL

### The function set

Four declarations, appended to `apps/supabase/supabase/schema/301-auth-functions.sql` in this order:

| Function | Signature | Reads a table | Hardening |
|---|---|---|---|
| `public.grant_role_permissions` | `(p_scope public.grant_scope_type, p_role public.grant_role_type, p_target_type public.entity_type) RETURNS public.grant_permission[]` | no | `IMMUTABLE`, `SET search_path = ''`, **not** `SECURITY DEFINER` |
| `public.entity_project_id` | `(p_entity_id uuid) RETURNS uuid` | yes — the four entity tables, by primary key | `STABLE SECURITY DEFINER SET search_path = ''` |
| `public.is_child_nominee` | `(p_parent_type public.entity_type, p_parent_id uuid, p_child_id uuid) RETURNS boolean` | yes — `nominations`, one hop | `STABLE SECURITY DEFINER SET search_path = ''` |
| `public.user_can` | `(p_scope public.grant_scope_type, p_target_id uuid, p_permission public.grant_permission) RETURNS boolean` | only through the two above | `STABLE SECURITY DEFINER SET search_path = ''` |

**Why the matrix is its own function.** `162-CONTEXT.md` leaves the internal shape to discretion so long
as the matrix is encoded once. Splitting it out makes "once" checkable: 162-17's structural non-collapse
guard can look for the matrix's permission literals and find them in exactly one function body, and the
matrix can be diffed against § 3.3 by machine without executing a permission check. `user_can` is then
purely *reach* — which grants cover which asked object — and carries no cell of the matrix at all.

**Why `user_can` needs no target-type argument.** The asked object is identified by a uuid; ownership is
uuid identity, and the hierarchy hop resolves the type from the tables (M1, M2). The grant's *own*
`target_type` comes from the claim and is used only to select the matrix column. This is what keeps the
signature at three arguments for all 97 call sites.

### The two orthogonal questions

`user_can` answers one grant at a time, and a grant says yes only when **both** halves say yes:

1. **Verb** — is `p_permission` a member of `grant_role_permissions(grant.scope, grant.role, grant.target_type)`?
2. **Reach** — does the grant's target contain, or equal, the asked `(p_scope, p_target_id)`?

The `own` qualifier in § 3.3 is not a third mechanism: for an entity grant, reach is exactly equality
with the granted entity, so `own` falls out of the reach rule. The union over grants is the loop: the
first grant that satisfies both halves returns true, and no grant can subtract.

**Reach, stated per grant scope.** `global` reaches everything. `account` reaches that account, the
projects in it, and the entities in those projects. `project` reaches that project and the entities in
it. `entity` reaches that entity — and **two named exceptions, written as explicit branches rather than
as a general upward rule**:

- **The project-read branch.** § 3.4's *"any auth user can always read their project"*: an entity grant
  answers yes to `project.read_structure` asked at `project` scope when the granted entity's project is
  the asked project. The branch names that one permission as a literal. A general "reach upward through
  the hierarchy" rule would also let an entity grantee ask `entity.edit_answers` at *account* scope and
  be told yes, because that verb is in the entity column — a fail-open with no caller today and a
  guaranteed one later.
- **The child-nominee branch.** One cell, gated on `is_child_nominee`. **Which cell is contested and is
  ratified at Task 2's checkpoint** — see `<flagged_assumptions>`. Whichever way it lands, it is one
  branch in `user_can` and one element of one matrix vector in the test.

### Where the matrix stops and row state begins

`user_can` answers *may this role do this verb to this object*. It does **not** answer *is this object
currently in a state that admits the verb*. So `lock_nominations`, `open_for_voters`, a nomination's
`confirmed` flag and an entity's `confirmed` flag are conjuncts of the **policies** that call `user_can`
(162-08 and 162-12 per brief § 5), not members of the matrix. § 3.3's `own, unless locked` cells are read
as `own` in the matrix plus `AND NOT locked` in 162-12's policy, which is what the brief's § 5 entry for
162-12 already says. This line is the third item the Task 2 checkpoint ratifies, because drawing it
anywhere else changes `user_can`'s signature — a lock conjunct inside the function would need the project
of the asked object at every call, and none of those columns exists until 162-07.

### The claim

`user_can` reads `(SELECT auth.jwt() -> 'grants')`, copying `can_access_project`'s single-evaluation form.
Each entry is an object whose keys are the column names of `public.grants`: `scope`, `target_type`,
`target_id`, `role`. Fields are compared **as text against the enum's literals**, not cast to the enum
type: a cast throws on an unexpected value, and an exception raised inside a policy predicate is a
query-time error in 97 places, whereas an unrecognised entry that is simply skipped denies by default and
is assertable. An entry whose `scope` or `role` is not a declared literal is skipped; a claim of garbage
alongside one valid grant answers exactly as the valid grant alone does, and that is a test.
