act after — and that nothing else can.

## The design, settled before the first line of SQL

### What "data migration" means when there is no database to migrate

D-14 forbids a `000NN` file and § 10.2 records why: no Supabase database has been published, so there are no
deployed rows to transform. But D-19 is equally explicit that backfills still matter locally, because
`yarn db:reset` re-seeds from `seed.sql` and the E2E suite builds its own project. The tension is real and
it is resolved by restating what the migration *is*.

**A backfill against a deployed database is a one-shot script. Against a declarative schema it is a function
plus its call sites**, and the call sites are every path that creates an identity on a local database. So:

| Where rows come from after a `db:reset` | What creates the grant |
|---|---|
| `apps/supabase/supabase/seed.sql`'s two role rows | one call to `backfill_grants_from_user_roles()` at the end of the file |
| `create_test_data()`'s eight role rows | one call at the end of its body, after the role insert |
| `invite-candidate`, `identity-callback` at run time | the Edge Function writes the grant directly — that is the end state, not a migration |
| the E2E harness's three identity-minting sites | the harness writes the grant directly, for the same reason |
| `packages/dev-seed` | nothing: it writes no auth rows and no role rows (M6) |

**Idempotence is a property of the arbiter, not of a guard clause.** Every insert the function performs ends
`ON CONFLICT ON CONSTRAINT grants_user_scope_target_role_key DO NOTHING`, and it returns the number of rows
actually inserted so a caller can assert a second run inserts zero. That arbiter only bites because D-24
made the key `UNIQUE NULLS NOT DISTINCT`: `target_type` is NULL on every global, account and project grant,
and under default NULLS-DISTINCT semantics the conflict target would match none of them, so each reset would
add a second copy of every admin grant — duplicates that survive revoking one row, which is the
privilege-escalation surface D-24 documents for `user_roles` today.

**Its lifetime is the retired table's.** It reads `public.user_roles`, which 162-15 deletes. This plan
therefore hands 162-15 the obligation to delete the function and its two SQL call sites in the same commit,
and installs the same kind of tripwire 162-05 handed this plan: a pgTAP assertion that the function exists
**if and only if** `to_regclass('public.user_roles')` is non-null. Today both sides are true.

### The mapping, written once — and one word of B6's table that is superseded

`162-DISCUSSION-POINTS.md` B6's table is the accepted mapping (B6(a), unticked, so the recommendation
stands), but it was written before D-02 and it spells the entity role with a third level:

> | `candidate` / `candidate` / `<candidate_id>` | `(entity, candidate, <candidate_id>, owner)` |

**D-02 amended the vocabulary to two levels, `admin` and `editor`,** and § 3.1 maps every entity user type to
`editor`. `grant_role_type` (162-03) has no third member, so the literal in B6's table is not merely stale,
it does not exist. The mapping this plan encodes is § 3.1's, and the four rows that matter are: global
admin; account admin at the account; project admin at the project; and entity editor with `target_type` set
from the role name, for `candidate` and `organization`. Nothing maps to `faction` or `alliance` because
`user_role_type` has no member for either.

The second half is B6's own addition: every `candidates` or `organizations` row whose `auth_user_id` is not
null and which no role row covers gets `(entity, <its type>, <its id>, editor)`. M7 says that set is empty
here, which is exactly why it needs a constructed witness.

**The oracle is not this plan's.** 162-05 installed `test_grants_from_user_roles(uuid)` and recorded that it
is *"the one place the mapping is written down in a test"*, adding that this plan *"should diff its mapping
against this helper rather than re-derive it"*. It was written independently, before this plan, from the
same § 3.1 table. So the comparison is a genuine two-source agreement rather than a function compared with
itself, and it is asserted as a set identity per fixture identity.

### The claim

```
scope, target_type, target_id, role
```

Four keys, the column names of `public.grants` minus `id`, `user_id` and `created_at` — which is the shape
162-04 declared and built `test_grants_claim(uuid)` to produce. That plan's `key_links` say a divergence
here *"is a silent total denial, so 162-06 asserts equality against this helper"*. This plan does exactly
that, and asserts it **as a set in both directions with equal cardinality** rather than as string equality,
because `jsonb_agg` has no defined element order and an order-only difference is not a defect. The hook
nonetheless carries a deterministic `ORDER BY` so two calls for one user answer identically.

The retired key is not emitted alongside it. A2(c) — the both-keys option — is the one the standing
convention did not select, and K1's reason is the phase's own thesis: a claim outliving its table is the
second mechanism this phase exists to end.

### What the fixture does, and what the estate therefore does not need

`create_test_data()` calls the backfill, so the fixture's `grants` table holds the real image of its eight
role rows. `set_test_user` then builds its claim through `test_grants_claim(p_user_id)` — the same projection
the hook performs — so all 393 assertions run against a table-to-claim path rather than a synthesised one.
Its third parameter cannot be removed (an argument-list change is an overload, and all 66 call sites would
then bind ambiguously), so it becomes a **tripwire**: a non-empty role array for a user with no grant rows
raises, which catches a fixture that inserted role rows and forgot the backfill.

1. **`04-admin-crud.test.sql` carries a grant-row insert 162-04 added.** With the fixture now creating that
   same row, the hand-written insert violates `grants_user_scope_target_role_key` and the file errors. It is
   removed, and the assertion keeps its meaning because the claim now arrives through `set_test_user`.
2. **Any other pgTAP file that inserts grant rows for a fixture identity has the same collision.** The set
   is derived at run time rather than listed here — 162-04 and 162-05 wrote those files and may have built
   their rows differently.
3. **`13-shim-parity.test.sql` names functions this plan deletes.** It is rewritten, not gutted, class by

### What 162-05 proved, and what this plan therefore does not re-prove

162-05's Task 5 asserted, in one transaction over a catalogue-derived table list, that **every fixture
identity sees the same rows through a `grants` claim as through the retired one**. That is content-level
neutrality across the two authority models, and it is already committed and green. This plan's question is
strictly narrower: *does each identity now receive the claim that model was proven against?* Which is the
projection equality plus the backfill's completeness.

The composition is the argument, and it is stated rather than assumed: mapping complete + projection exact +
162-05's differential ⇒ no identity's view moved. The observable cross-check is the neutrality vector — the
per-identity, per-table visible-row-count vector recorded on the untouched tree at Task 1 and re-measured
after the switch. **Counts, not digests, and deliberately so**: the fixture's ids are compile-time constants
but `created_at` defaults to `now()`, so a row-content digest is not comparable across two runs, while a
count is. A count cannot see one row swapped for another; that weakness is real, it is named here, and it is
covered by 162-05's in-transaction content differential rather than by an instrument invented here.

### The two windows this plan opens, and where each closes

1. **The consumer window.** The hook changes in Task 3; the two Edge Function gates and the E2E harness move
   in Task 5. Between those commits, `invite-candidate` and `send-email` deny every caller — they fail
   closed, which is the correct direction, and neither is reachable from `yarn test:unit` in a way that
   depends on a live claim. The window is inside this plan and is closed before the E2E gate runs.
2. **The stale-token window.** A session minted before this commit carries the retired claim until its token
   is refreshed. The E2E setup projects mint fresh sessions on every run, so a suite run is unaffected — but
   a stale `tests/playwright/.auth/*.json` reused without the setup running would present a retired-shape
   token and produce denials that look like flakes. Named in `<flagged_assumptions>` with its remedy.

### Where this plan stops

No policy is converted. No column is added. `entities.confirmed` does not exist yet and is not referenced.
Entity-type selection at the identity entry point is § 6.1's by `162-CONTEXT.md`'s own exclusion list, so
only the grant write is generalised: the literal naming the candidate entity type appears once per Edge
Function, in the call that says which entity was created, and nowhere in the authorisation or the insert.
