## Phase decision record (canonical — cited by this plan's tasks)

### DR-1 — The requirement is amended in place and dated, never rewritten

House style in this repo is a dated in-place correction that says what changed and why, with the
still-accurate text preserved. The existing **Corrected 2026-08-28** notes on the roadmap entries for
161, 162, 163 and 164 are the form to follow, and the Phase 164 entry shows the pattern at criterion
granularity — an inline `⚠ **Line anchor corrected 2026-09-03:**` note inside criterion 3 that records
the wrong anchor, the measured one, and the reason the corrected form carries no line number at all.

Wholesale rewriting would destroy the audit trail on a blocking-ship requirement and would also make
the 2026-08-28 note's still-accurate finding — that criterion 2's read/write collapse is confirmed
present — indistinguishable from this plan's work.

### DR-2 — The storage census the requirement cites is wrong in every figure, and it is wrong in a way this repo has a standing rule about

`PRESHIP-02` and roadmap criterion 6 both assert that `400-storage.sql` calls `can_access_project` at
**11 sites**, and both cite ten line anchors — `:116,143,180,203,235,239,271,275,298,321`. Measured in
this worktree on 2026-09-15:

| Figure | Cited | Measured |
|---|---|---|
| Storage policies | 15 | **15** — the one figure that holds |
| `can_access_project` call sites | 11 | **10** |
| Policies routing through it | "already follows table access" | **8 of 15** |
| Policies not routing through it | none stated | **7** — the 6 `candidate_*` policies and `anon_select_public_assets` |
| Inline re-derivations in those policies | none stated | **12** `EXISTS` sub-selects |
| Line anchors correct | 10 cited | **0 of 10** — the real sites are at 109, 155, 219, 255, 308, 318, 371, 381, 413, 445 |

Two things follow, and both are load-bearing for how the correction is written.

**The count is a comment-inflated grep total.** `can_access_project` appears eleven times in the file,
but one of those is the `Depends on:` line in the file's own header comment block. Strip whole-line
comments and the count is ten. The requirement's figure was produced by the exact hazard the planning
rules warn about, and the corrected census is therefore defined as a comment-stripped count and gated
as one.

**The anchors are replaced by a content anchor, not by better numbers.** This repo already learned this
the hard way and wrote the lesson into the Phase 164 entry after a line anchor was found wrong in five
places at once. Ten wrong anchors in one citation is the same failure an order of magnitude larger, so
the corrected text names the policy families by name and carries a dated census token instead.

### DR-3 — The `candidate_*` family is six policies, not seven, and the discrepancy is surfaced rather than propagated

`162-CONTEXT.md` D-03 and the outline row for 162-14 both say "the **7** `candidate_*` ones". Measured,
`400-storage.sql` declares **six** policies whose name begins `candidate_`:
`candidate_insert_public_assets`, `candidate_insert_private_assets`, `candidate_update_public_assets`,
`candidate_update_private_assets`, `candidate_delete_public_assets`, `candidate_delete_private_assets`.

Seven is the count of policies that do **not** call `can_access_project` — those six plus
`anon_select_public_assets`, which is a legitimate non-caller today because it reads a `published`
column instead. Brief § 0's fact 3 states the seven correctly and then calls the anon policy "the
eighth non-caller", which is itself off by one; the label "7 `candidate_*`" is that slip propagated.

**The amendment is unaffected** — criterion 6 widens to all 15 storage policies either way, and the
anon policy is rewritten in this phase regardless because D-11b deletes the column it reads. What is
affected is whether the corrected requirement is itself true. So this plan writes the measured split
and does **not** transcribe the seven-`candidate_*` label, and the executor records the discrepancy in
the SUMMARY for 162-14 and 162-17, which are the plans that touch these policies.

**This plan does not edit `162-SPEC.md`.** The SPEC is 162-01's artefact and sits in the same wave;
editing it from here would put two plans on one file. The two documents do not contradict each other on
substance — both say all 15 storage policies route through `user_can`, the `candidate_*` family
included — and the requirement carries the precise measured split while the SPEC carries the amendment.

### DR-4 — `prettier` is a vacuous gate on anything under `.planning/`

`.prettierignore:37` is a bare `.planning/` entry, so `npx prettier --check` on a file under
`.planning/` matches **zero files and exits 0**. Measured in this worktree on 2026-09-15 against a
deliberately mis-formatted probe file, which passed. 162-01's planner filed the same finding as its
DR-4. Every gate in this plan is therefore a content assertion that prints the population it counted.

`yarn lint:check` and `yarn test:unit` are real gates but cover no file this plan touches, so they are
not run here; the blast-radius assertion in `<verification>` is what proves that claim rather than
assuming it.

### DR-5 — A harvested Phase 161 command is broken on macOS and is not used

The idiom `… | wc -l | grep -qx '0'` exits **1 on a clean tree**, because BSD `wc -l` emits its count
with leading spaces and `-x` anchors the whole line. Every clean-tree assertion in this plan uses the
capture-and-test form instead.

### DR-6 — The roadmap plans count is read at execution time, never hardcoded

162-01's planner replaced § Phase 162's `**Plans**: TBD` with a scoped edit reading "**1 of 19 written
so far**", and warned that whoever lands next should bump the count and append a row rather than
rewrite the block. That warning is already live: `162-02b-PLAN.md` landed after 162-01 and the stated
count is stale as written. Task 3 therefore derives the number from the `162-*-PLAN.md` files present
at edit time and reconciles the listed rows against them, and its gate asserts the three quantities
agree rather than asserting any particular value.
