<objective>
Close ROADMAP criteria 6 and 7, make criterion 2's non-collapse property permanent, and leave the phase
with a register that says which of its guards have been observed failing.

**Purpose.** Sixteen plans have each asserted their own work. What none of them can assert is the
property that only exists once all of them have landed: that the estate as a whole answers every
authority question through one mechanism, that every cell of § 3.3's matrix is read by something, and
that the two flows criterion 7 names are compatible with the matrix rather than assumed to be. And one
property none of them can make **durable**: criterion 2 does not ask for a measurement, it asks for a
test that fails if the two predicates ever collapse back into one. A plan-time scan cannot do that. A
check in `apps/supabase/scripts/lint-schema.mjs` — which a dedicated CI job already runs against a live
database — can.

**The failure this plan is built against.** An evidence plan's characteristic defect is an assertion
that cannot fail. Every guard here is therefore shown red before it is accepted, and the guard whose
red matters most is the structural one: the option text for F2(a) warns that a behavioural test
"can re-collapse the predicates and still pass", and a guard that merely compares two predicate strings
has the same hole one level up — it passes when both predicates collapse onto a **third** shared
expression. So the guard is built on the permission literal rather than on the predicate text, and it is
proven by planting exactly that collapse and recording that the string comparison stayed green while the
guard went red.

**Output.** One permanent check in `lint-schema.mjs`; four pgTAP files widening the estate across
§ 3.3's matrix, the two uniqueness keys and the storage/table pairing; three source-level flow gates;
`162-FLOW-CONFORMANCE.md`; `162-NEGATIVE-CONTROL-LEDGER.md`; the phase's documentation swept once; and
the closing full-suite run.
</objective>

## The design, settled before the first line of code

### Why F2(a)'s guard cannot be written as F2(a) words it — and what it becomes

F2(a) asks for a structural guard "asserting `can_edit_project` exists and is not definitionally equal
to `can_access_project`, plus that no policy pair on one table uses the identical predicate for SELECT
and UPDATE".

**Neither named function exists at the end of this phase.** `can_edit_project` was never created: the
phase replaced the split-predicate design with one `user_can` carrying a 23-member verb, and § 3.3's
`project.read_structure` / `project.edit_structure` pair is what criterion 2's separation became.
`can_access_project` is **deleted** by 162-15. A guard written to F2(a)'s literal wording would assert
the existence of an object the phase deliberately did not build and the non-equality of one it
deliberately removed — the same class of error D-27 caught in A4(a)'s wording, and the reason this
re-expression is ratified at Task 2 rather than assumed.

**The half that survives intact is the second half**, and it needs strengthening for the reason the
option text gives against (b): a test that passes while the thing it guards re-collapses is not a guard.
Comparing two predicate strings has exactly that hole one level up. Three collapses to catch:

| Collapse | What a two-string comparison does | What the guard does |
|---|---|---|
| Both policies re-predicated onto one expression, byte-identical | RED — catches it | RED |
| The write policy pointed at the read permission, on a table whose read predicate carries a public disjunct so the strings still differ | **GREEN — misses it** | RED, on set intersection |
| Both predicates replaced by calls to a third wrapper reaching no permission literal, with different arguments so the strings differ | **GREEN — misses it** | RED, on the reaches-neither-mechanism clause |

So the guard is built on **what the predicate reaches**, not on what it says:

1. Derive the 23 members of `grant_permission` from `pg_enum`. Floor the count at 23 and fail below it —
   a guard whose vocabulary came back empty would find no intersections anywhere.
2. For every policy in `public` and `storage`, extract from `qual || with_check` the set of enum members
   it names, matched as the enum-cast literal form PostgreSQL deparses into `pg_policies`.
3. Partition each table's policies by command: `SELECT` is read; `INSERT`, `UPDATE` and `DELETE` are
   write; `ALL` counts as both.
4. **ERROR** when a table's read-permission set and write-permission set intersect, naming the table and
   the shared member — unless the table is on the ratified same-permission allow-list.
5. **ERROR** when a read policy and a write policy on one table carry byte-identical `qual`.
6. **ERROR** when a policy's expression reaches neither a `grant_permission` member nor one of the named
   visibility helpers — unless the policy is on the ratified exemption list.
7. **ERROR** when any name on the visibility-helper list resolves to no function in `pg_proc`. An
   exemption naming a thing that does not exist is how a guard silently stops guarding.
8. Always print the policy count, the table count and the enum member count, and fail when the policy
   count is at or below a floor derived from the estate. **A clean verdict from an empty instrument is
   the failure mode this clause exists to exclude, and it is not hypothetical here** — the outline
   records a census in this phase where 0 of 10 cited line anchors were correct.

Clause 4's allow-list is not a convenience. 162-09 established one legitimate member by measurement:
`accounts` has no account-read permission distinct from `account.edit_settings` in § 3.2, so its SELECT
and its UPDATE name the same member **by the matrix's construction**. That is a true exception and it is
ratified with its reason at Task 2, not discovered by the guard's first red.

### Why the matrix grid is run against a closed project

Criterion 2's illustrative sentence is already true today by accident, and the brief says so: a candidate
holds no project-scoped role at all, so a behavioural test on a candidate passes against the collapsed
schema. The generalisation of that trap in this plan is the **public disjunct**. 162-09 wrote the
structure SELECT policies as two-term disjunctions — the authority term or the open-for-voters term — so
a read cell measured against an open project passes for a caller with no authority whatsoever, and the
grid becomes a second, weaker copy of 162-08's visibility test.

**Every operation in the matrix grid is therefore performed against a project whose open-for-voters flag
is false**, asserted in the file as the grid's own precondition. With the public term false by
construction, the observed outcome is the authority decision alone, which is the only thing § 3.3 states.

### The representative operation is derived, not authored

This plan cannot author a permission-to-operation mapping: the policy estate it maps does not exist
until sixteen predecessors have run. So the mapping is derived:

- For each of the 23 members, collect from `pg_policies` every policy whose expression names it.
- Order that set deterministically — schema, then table, then command in the order `SELECT`, `INSERT`,
  `UPDATE`, `DELETE`, then policy name — and take the first.
- That policy's `(table, command)` is the representative operation; the row it acts on is the fixture
  row of the closed project, created inside the test transaction.
- A member whose collected set is **empty** is not silently skipped. It joins the unenforced list, which
  must equal the list ratified at Task 2. **A permission the estate never reads is a cell of the matrix
  that grants nothing**, and no per-table plan can see it: each of them asserts only about its own
  tables, and a member nobody enforces is exactly the one nobody's scope contained.

### The two-mechanism partition, and why it is not "all fifteen through `user_can`"

A4(a) as ticked reads: all 15 storage policies route through `user_can`. D-27 measured that one of them
cannot — `anon_select_public_assets` serves a caller with no `grants` claim, which 162-04 denies **by
construction** as one of its named deny classes, so routing the public-read policy through `user_can`
makes every public asset unfetchable. D-27's resolution keeps A4(a)'s spirit and drops its literal
wording: one mechanism per question, no parallel implementation, with the visibility question answered by
162-08's helpers and the authority question by `user_can`.

⚠ **162-14's own truth set asserts the literal wording**: that the count of storage policies reaching
`user_can` equals the derived total. The two cannot both hold. This plan does not adjudicate between a
sibling's must-have and a phase decision: it derives the partition from `pg_policies`, prints both
counts, asserts their sum is the total and the reaches-neither count is zero, and — if the derived
figures contradict 162-14's SUMMARY — records the discrepancy as a finding naming both numbers and both
sources. That is what D-27 means by "162-17's criterion-6 evidence must assert the right thing".

### The two nominations that are the same row

§ 11.5 says the free-text branch and the independent-candidate branch are "byte-identical in every
column", and that consequently the admin queue "keys off that presence, not off a status column". The
first half of that sentence is a claim about the schema, and this plan **measures it** rather than
quoting it: two nominations are created differing only in the requested-parent key, and their full column
images — read from `information_schema.columns` so no column is forgotten, minus the identity, the two
timestamps and the custom-data column itself — are asserted equal. Only then does the queue assertion
mean anything: it is discriminating precisely because nothing else discriminates.
