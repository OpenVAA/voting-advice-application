## The design, settled before the first line of SQL

### The tension, stated plainly

162-04's `must_haves` record the window: between it and 162-06 no real JWT carries a `grants` claim,
because the access-token hook still emits `user_roles`. Three resolutions were available.

**(c) — the shims are behaviour-neutral by construction because no real authenticated caller reaches the
affected policies.** 162-04 could make that argument for `projects` alone, by census (M9). It cannot be
made for 95 policies: M4 counts 393 pgTAP assertions driven by `user_roles` claims and M5 counts 12 E2E
spec files that log in for real and go through `can_access_project`. Rejected, and rejected by
measurement — Task 1 derives both populations and halts the plan if either is zero, because a zero would
mean the tree moved and the whole argument has to be re-made.

**(b) — pull 162-06's backfill and hook change into this plan.** It would close the window immediately
and would re-cut a wave boundary the brief drew. 162-06 is not a small plan: it carries the data
migration, the `auth_user_id` backfill, the hook, four frontend claim readers and `invite-candidate` with
its swallowed-failure fix (D-20). Folding it in would produce one plan spanning the database, the
frontend and an Edge Function, and would leave the brief's wave 2 with a single entry. Rejected on size
and on fidelity to a settled decomposition.

**(a) — a legacy-claim fallback, for exactly one plan. Chosen.** It is also what K1 already describes: the
shim lifecycle is *a sequence of reviewable commits, not of migration files*, and every commit between
them is green under `db:reset`. A shim that denies everything is not green. The fallback is what makes
"every existing policy keeps working untouched" — brief § 5's own words — true rather than aspirational.

### The fallback, and why it is a dispatch rather than a disjunction

Each predicate's current body is **moved**, not rewritten, into a new function of the same argument list:
`public.has_role_legacy_claim` and `public.can_access_project_legacy_claim`. Byte-identity of the moved
text is the cheapest possible proof that the legacy path is today's behaviour, and it is checkable by
comparing `md5(prosrc)` on the applied database against the same digest taken at the base SHA. The shim
that replaces each is then genuinely thin: one dispatch, one delegation.

The dispatch is **exclusive**, not a disjunction:

| Token carries | Answered by |
|---|---|
| no `grants` key (every real token in this window; every pgTAP identity; `anon`) | the moved legacy body, verbatim |
| a `grants` key, including an empty array (every pgTAP identity in `12-user-can.test.sql` and `13-shim-parity.test.sql`; every real token after 162-06) | `user_can` |

A disjunction would answer from the union of two authority models for any token carrying both claims,
which is a third model nobody specified and which can only ever widen. An exclusive dispatch cannot
accumulate authority, and it makes the transitional window's neutrality a tautology for real callers
while leaving the `user_can` path fully exercised by the new test file. Two independent proofs, not one.

### The fallback cannot outlive its window

The fallback is dead the instant `custom_access_token_hook` emits `grants`, which is 162-06's first
substantive change. Leaving it alive past that point would mean a token carrying only the legacy claim
still confers authority while waves 3, 4 and 5 convert 96 policies — a dual-authority surface in exactly
the phase that exists to end parallel implementations.

So the expiry is written against the thing that closes the window, not against a date or a plan number:
`13-shim-parity.test.sql` asserts a **biconditional** — the two `*_legacy_claim` functions exist **if and
only if** a call to `custom_access_token_hook` returns claims with no `grants` key. Today both sides are
true and the assertion passes. The moment 162-06 changes the hook, the assertion goes red unless the
fallback is deleted in the same commit. That is a forcing function rather than a note in a SUMMARY, and
it is the reason this plan can hand 162-06 an obligation the brief's § 5 does not name. That obligation
is flagged below rather than assumed.

### The translations

Two probe permissions do all the work. Both are members of `grant_permission` as 162-03 declared it.

| Legacy call | Shim answers | Exact? |
|---|---|---|
| `can_access_project(X)` | `user_can('project', X, 'project.edit_project_settings')` | **yes** — M6 |
| `has_role('super_admin', …)` | `user_can('global', NULL, 'account.manage_admins')` | **yes** — only a `global` grant reaches global scope, and a `global`/`editor` shape carries the empty permission set per 162-04's fall-through |
| `has_role('account_admin','account',X)` | `user_can('account', X, 'account.manage_admins')` | widens by the global admin |
| `has_role('project_admin','project',X)` | `user_can('project', X, 'project.manage_editors')` | widens by the global and containing-account admins; **no executable call site** (M2) |
| `has_role('candidate','candidate',X)` | `user_can('entity', X, 'entity.edit_answers')` | widens by every grant reaching X's project; **no executable call site** (M2) |
| `has_role('organization','organization',X)` | `user_can('entity', X, 'entity.edit_answers')` | widens by every grant reaching X's project |
| `has_role(R, NULL, NULL)`, R not `super_admin` | **raises** | untranslatable; **no executable call site** (M2) |

`project.manage_editors` is the probe for the project-admin shape rather than
`project.edit_project_settings` only so that the two legacy predicates are not silently the same
question; either would do, because D-09 denies both to ProjEditor.

**Why the untranslatable shape raises rather than denying.** The unscoped form asks *does this caller hold
role R anywhere*, and `user_can` has no way to ask a question without a target. Answering `false` would be
a silent narrowing that no test would catch, because nothing calls it. Answering `true` would be a silent
widening. Raising a named exception, in the style `validate_nomination()` already uses for every hierarchy
violation (D-23), converts an unanswerable question into an immediate, attributable error for whoever
writes the first policy that asks it — and M2 proves nobody asks it today, so the exception is unreachable
from any policy in the tree. Task 1 re-derives that census; if it is not zero, this plan stops.

all — against seven call cells: the unscoped `super_admin` shape; the account shape at `account_a` and at
`account_b`; the organization shape at `org_a` and at `org_b`; and `can_access_project` at `project_a` and
at `project_b`. Sixty-three cells.

| Call cell | Identities where legacy says no and the shim says yes |
|---|---|
| `has_role('super_admin')` | — |
| `has_role('account_admin','account', account_a)` | `super_admin` |
| `has_role('account_admin','account', account_b)` | `super_admin` |
| `has_role('organization','organization', org_a)` | `super_admin`, `account_admin_a`, `admin_a` |
| `has_role('organization','organization', org_b)` | `super_admin`, `admin_b` |
| `can_access_project(project_a)` | — |
| `can_access_project(project_b)` | — |

**Seven deviation cells out of 63, every one of them upward.** If the executor's run-time derivation
differs, the fixture or the matrix moved and that is a finding, not a formatting difference. The oracle
that derives it in the test computes containment by plain joins over `public.grants`, `projects`,
`accounts` and the four entity tables — it never calls `user_can`, because an oracle that calls the
function under test asserts nothing.

**Every deviation is absorbed at its call site, and that is what the policy-level differential proves
rather than asserts.** The account shape appears twice, both times disjoined with the `super_admin`
shape in the same predicate. The organization shape appears four times: twice in SELECT policies that
already disjoin `can_access_project(project_id)`, and twice in `organization_update_own_organizations`,
whose table already carries `admin_update_organizations` gated on `can_access_project` — and row-level
security disjoins policies, so the table's writable row set is unchanged. Arguing that per site is what a
planner would do; measuring the row sets is what this plan does.

### Where the neutrality proof lives

Three proofs, and the third is the one that matters.

1. **Git.** `302-rls.sql` and `400-storage.sql` are byte-identical to the base SHA, and the two moved
   legacy bodies digest equal to the base SHA's. The legacy path *is* today's behaviour, by identity.
2. **The untouched estate.** All 393 pre-existing pgTAP assertions run on `user_roles` claims, take the
   legacy branch, and stay green with no edit. They are the control group and they are not given a grants
   claim.
3. **The differential.** For every identity and every row-level-security table, the row-set digest read
   through a `grants` claim equals the digest read through the `user_roles` claim, in one transaction, on
   one fixture. This is the claim the brief calls behaviour-neutrality, stated at the level the brief
   states it — the policy, not the function.

The digest is `md5` over the row-to-text of every visible row, ordered — generic, needing no knowledge of
each table's key, and stable within a transaction because `now()` is frozen. The table list is derived
from the catalogue at run time and the derived list is asserted equal to the list the matrix covers, so a
table that gains row-level security in wave 3 cannot be silently skipped. `public.projects` is the single
declared exception, and it is asserted rather than excluded: under the legacy claim every identity reads
zero rows there, because 162-04 already converted that policy with no legacy path (M9).

### Where this plan stops

`user_can` is not modified. No policy is converted. No column is added. The shims are a bridge with a
known demolition date, and the temptation this plan must resist is improving something while it is
standing on it: a policy fixed here would be indistinguishable, in the differential, from a shim that
changed behaviour.

  it, a fallback that silently outlives the window means the retired `user_roles` claim keeps conferring
  authority while waves 3 through 5 convert 96 policies against a model that no longer describes it.

- **`has_role`'s widening is accepted rather than eliminated, and the reason is structural rather than
  economic.** § 3.3 is hierarchical: no member of `grant_permission` is held by a lower column and denied
  to a higher one, so no single `user_can` call can express *is exactly a grantee at this level and no
  higher*. Exact shims are available — a complement term per translation, plus an entity-to-project hop
  per row on two hot SELECT policies — and that is Task 2's option (B). The posture is the operator's,
  not a planner's, and the plan halts rather than defaulting. Cost of being wrong: a rewrite of one
  predicate and a re-measurement of whichever waves have converted against the other posture.

- **`public.projects` is not neutral across this wave, and it is 162-04's departure rather than this
  plan's.** That plan converted `authenticated_select_projects` to a bare `user_can` call with no legacy
  path, and it did so deliberately, measuring the runtime population of authenticated readers at zero.
  Under a `user_roles`-only claim every identity therefore reads zero rows of that table, and an entity
  grantee reads their own project under a `grants` claim where the legacy predicate gave them nothing.
  This plan asserts both facts explicitly rather than excluding the table, so the exception is a
  measurement rather than a gap. Task 1 re-derives the reader census before the E2E run depends on it.

- **The moved legacy bodies are asserted byte-identical by `md5(prosrc)` on the applied database, not by
  reading the file.** `prosrc` is what PostgreSQL stores and what runs; the file is what a reviewer reads.
  A move that changed whitespace inside the body would redden, which is intended: the whole value of a
  move over a rewrite is that identity is checkable, and a "harmless" reformat is exactly the change that
  makes the next reviewer wonder whether anything else moved with it.

- **The differential's granularity is the table, not the policy.** A digest compares what an identity can
  read from a table, which is the disjunction of every policy on it. Two compensating errors in two
  policies on the same table would therefore cancel. That is accepted deliberately: it is the same
  granularity a user experiences, the brief states neutrality in those terms, and the per-policy
  statement is what waves 3 through 5 assert one block at a time as they convert them. The function-level
  grids in Tasks 3 and 4 are the finer-grained half of the evidence, and the two together are what the
  claim rests on.

- **`test_rls_digest` is a test helper with no owner rights, by design, and that is the one line whose
  inversion would silently void this plan.** It is asserted `prosecdef = false` from the catalogue rather
  than from the file. Declared only under `apps/supabase/supabase/tests/`, never in `schema/`, so it
  exists only on a database that has run the pgTAP estate and `supabase db reset` removes it.
