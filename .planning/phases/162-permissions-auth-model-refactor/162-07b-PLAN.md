<objective>
Move `organization_id` off `candidates` and onto `factions`, and sweep every consumer of the column
that is leaving — including two RPC return shapes that Phase 164 audited.

**Purpose.** The candidate-to-organization association is stated twice in this system: once as a column
on `candidates`, once as the `parent_nomination_id` edge that `validate_nomination()` already enforces.
Two statements of one relationship is the defect class this phase exists to end, and this one has a
measurable consequence outside the schema — `packages/supabase-types/src/column-map.ts` maps two
different columns to the same property, `PROPERTY_MAP` is a last-wins reversal, and the result is a
property name that resolves to a column on no table at all. That is RES-7 / T-144-11, open since
2026-08-23, and its sole cause is the duplicated column name.

**Why this is a plan of its own.** Two of its edits are contract changes rather than schema changes.
Dropping a column from a `RETURNS TABLE` shape is precisely what Phase 164's return-nullability guard
was installed to notice, across three artifacts of which only one regenerates itself; and the seed and
adapter blast radius is different in kind from the policy rewrite either side of it. Neither belongs
inside 162-07's settings work or 162-10's policy conversion.

**Measurement first, and it decides.** Two of `162-CONTEXT.md`'s three pre-code measurements are this
plan's, and each can break a green suite: whether any fixture emits a faction with no organization, and
what breaks when the candidates column leaves the two return shapes. Task 1 takes both with recorded
numbers and halts on the answers it is not expecting, because brief fact 38's consumer list was
assembled by reading and at least one entry in it — `302-rls.sql`, recorded there as a comment — needs
checking against a live predicate before anything is edited.

**Output.** `factions.organization_id` declared in its `CREATE TABLE` body; `candidates.organization_id`
absent from the declarative schema; two shortened RPC return shapes with Phase 164's override mechanism
engaged in all three of its artifacts; the SQL, seed, type and adapter sweep; a new pgTAP file;
a regenerated `00001_initial_schema.sql` and `packages/supabase-types/`; and RES-7 closed with a standing
assertion that reddens on any future duplicate, not only on this one.
</objective>

than a silent no-op. So after `yarn db:types` the package stops typechecking until the keys are removed

### Why the reference survives on `candidates` while the column does not

M10 is the reason and it is worth stating plainly, because "remove the column, remove the reference"
reads as the obvious move and is wrong. The template key `organization` on a `candidates` row has two
readers: `_bulk_upsert_record`, which resolves it to a FK column, and the latent answer emitter, which
reads it in memory before any write happens and never touches the database. Only the first is going
away. `permittedKeys.ts` already models exactly this distinction — `COLLECTION_NON_COLUMN_LIST.candidates`
carries `email` on the same footing, permitted on the row and stripped before the write — so the
resolution is to move the key from source (4) to source (3) rather than to invent a mechanism.

The alternative, deleting it, has no gate: `findOrganizationIndex` returns a negative index and the
emitter falls back to random answers without a warning, so every seeded dataset's matching data quietly
becomes noise and every gate stays green. That is the failure mode this plan is least able to detect
after the fact, which is why it is decided before rather than discovered after.

### Where Phase 164's mechanism is engaged, and where it would be bypassed

The guard is six checks over three artifacts. Dropping an output column touches all three, and each has
a different remedy:

| Artifact | Check | What the removal does to it | Remedy |
|---|---|---|---|
| `RPC-NULLABILITY.md` DERIVED region | 1a | a machine-derived row names a column the schema no longer declares | `--write` |
| `RPC-NULLABILITY.md` disposition tables | 1b | a hand-written row names a column the schema no longer declares | hand edit — `--write` copies this region through unchanged |
| `database.overrides.ts` | 5, plus the type constraint | an override key widens nothing | hand edit, forced first by the compiler |

**The bypass to refuse is the type error's.** After `yarn db:types` the package stops typechecking with
an error pointing at the override key. Silencing that with a cast, a suppression comment, or by widening
`Nullable`'s constraint would leave checks 1b and 5 to be discovered later and would disable the
mechanism for every future column. The only correct response is to remove the key, which is what the
constraint was installed to force.

**And the vacuity to refuse is check 4's.** The cast alternation is built from the harvested column set,
so removing a column removes it from the pattern. `entity_organization_id` leaves; `organization_id` does
not, because `get_nominations` still returns the nominations FK of that name. So the alternation shrinks
by exactly one, and a shrink of two would mean the wrong column was dropped somewhere.

### The `candidates` policy, and what is deliberately deferred

M7 makes resolving the disjunct a precondition of the schema applying, and M8 makes the resolution
cheaper than it looks. Two readings are available and Task 2 ratifies one:

- **Remove it now, 162-10 restores the reach.** Strictly more restrictive than today, so nothing becomes
  visible that is not visible today. The organization's read of its own candidates returns in 162-10
  through the nomination hierarchy, which is where the new model says the relationship lives, and 162-10
  already depends on this plan so the gap is ordered.
- **Re-express it now against `nominations`.** Preserves the reach for nominated candidates, but not for
  a candidate recorded as a member without being nominated — `candidate_a2` in the pgTAP fixture is
  exactly that row — and writes policy logic that 162-10 rewrites two waves later.

Either way the pgTAP assertions must change, because they name the column in a `WHERE` clause and would
be a syntax error rather than a failure.

### The email helper, restated as one join

`resolve_email_variables`'s candidate branch already walks `nominations` for the constituency and
election names. The organization name becomes one more thing read on that walk, through the parent
