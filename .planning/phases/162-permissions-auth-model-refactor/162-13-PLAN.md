<objective>
Make a confirmed entity's name immutable to the entity user and still correctable by an administrator, and
make the confirmation flag itself something only a holder of `entity.confirm` can move — as properties of
the database, enforced where a column grant cannot reach.

**Purpose.** § 11.2 says the name is frozen once `confirmed` is true; § 8.7(a) says frozen *for the entity
user*, still editable by a holder of `entity.edit_immutable`. That is a rule about the transition from one
row state to another, and fact 27 measured that the two mechanisms already in the tree cannot express it: a
column grant is a single global pair against one role and knows nothing about rows, and a policy's `USING`
and `WITH CHECK` see the old and the new row with no expression able to correlate them. So the rule is a
trigger reading `OLD.confirmed`, and `303-column-grants.sql` is reduced to the coarse outer bound it can
actually express.

**The characteristic failure of this plan is silence.** A trigger attached to the wrong verb, or carrying a
column list that omits the column it was written to protect, does not error — it permits, and permitting is
what the tree already does. A test file full of refusals would still pass against a trigger that refused
everything. So the plan is built round a three-celled grid rather than a two-celled one: the entity user is
refused on a confirmed row, **allowed on an unconfirmed row**, and the `entity.edit_immutable` holder is
allowed on the confirmed row. The middle cell is the only one that distinguishes a conditional rule from a
permission that simply denies the entity user, and it carries its own negative control.

**The reduction is a loss, and it is named.** The confirmation column is protected today by omission from
an allow-list on two of the four entity tables and by nothing at all on the other two. This plan puts it
*into* every allow-list — because confirming is an update and an authenticated administrator performs it
through the same role the column grant is written against, which is D-11a's finding and 162-12's resolution
on a different table — and moves that protection to the trigger. Every removed protection is stated with
where it now lives, and every one of those relocations is proven by an observed refusal rather than argued.

**Output.** One trigger function whose protected column set is an argument; four registrations, one per
entity table, restricted to the columns they guard so the candidate application's hottest write does not
pay for them; a column-grants file that covers all four entity tables and claims only what it enforces; a
new pgTAP file whose every allow has a paired deny and whose every deny has a paired allow; three inherited
assertions re-expressed rather than deleted; a regenerated `00001_initial_schema.sql` and
`packages/supabase-types/`; and the wave-4 gate including the full E2E suite.
</objective>

## The design, settled before the first line of SQL

### Why a trigger, stated as an exclusion rather than a preference

Three mechanisms could carry a rule about who may change a column. Two of them are already in this file's
neighbourhood and neither can express this one.

| Mechanism | Why it cannot carry § 8.7(a) |
|---|---|
| column grant | one global pair against one role (M3). It cannot distinguish two callers of the same role, and it knows nothing about the row at all, so *only while a flag is false* is not sayable |
| RLS policy | `USING` is evaluated against the old row and `WITH CHECK` against the new one, and no expression in either can reference the other. `OLD.confirmed` is therefore not addressable from any policy on these tables, which is fact 27's conclusion stated precisely |
| `BEFORE UPDATE` row trigger | sees `OLD` and `NEW` in one scope, can compare them column by column, and can ask `user_can` for the exception. M6 shows the tree already enforces one column's immutability exactly this way |

The third is what ships. **This plan adds no policy and modifies none**, and that is asserted rather than
merely intended: the `pg_policies` row count and expression set are recorded before and compared after.

### One function, four registrations, and the column list that keeps the hot path free

`public.enforce_entity_immutability()` is declared once, `SECURITY INVOKER` — it must see its caller's
effective role, which a `SECURITY DEFINER` body would replace with the owner's — and registered four times,
once per entity table, beside that table's existing `set_updated_at` registration.

Each registration is `BEFORE UPDATE OF <that table's protected name columns>, confirmed` and passes that
table's protected name columns as trigger arguments. Two things follow, and both are load-bearing:

- **The column restriction is the early exit, and it is free.** A column-restricted trigger fires only when
  one of its columns appears in the statement's `SET` list, and that is decided once per statement from the
  parse tree rather than once per row. `upsert_answers` sets only the answers column, so the candidate
  application's hottest write never enters this function at all. A trigger written without the restriction
  would fire on every answer write of every candidate and would have to serialise each row to compare
  columns generically — which is the same work, paid on the wrong path.
- **The argument list is D-21 made structural.** The body reads its protected set from `TG_ARGV` and
  compares each named column through a generic record projection, so it holds no entity-type literal, no
  per-table branch and no column name. `candidates` passes two names; the other three pass one. The
  consistency between the two lists — the trigger's `UPDATE OF` columns and its arguments — is derivable
  from `pg_trigger` and is asserted, because a registration whose `UPDATE OF` list omits a column it passes
  as an argument is a rule that silently never fires for that column.

The confirmation column is in every `UPDATE OF` list and in no argument list: it is the same column name on
all four tables, so it needs no parameterisation, and it is the subject of a different rule.

### The two rules, and why their order is a test

1. **The confirmation gate.** If the confirmation flag is being changed — old value distinct from new —
   and the caller's effective database role is `authenticated` and `user_can` answers false for
   `entity.confirm` at entity scope on this row, refuse with a named exception naming both values. This is
   the load-bearing half: an entity user who can set the flag to false can unfreeze their own name, so the
   direction that looks harmless is the one that matters, and **both** directions are refused.
2. **The conditional freeze.** If **`OLD.confirmed`** is true and any protected name column's old value is
   distinct from its new value and the caller's effective role is `authenticated` and `user_can` answers
   false for `entity.edit_immutable` at entity scope on this row, refuse with a named exception naming the
   column and both values.

**Rule 1 runs first, and that order is asserted rather than left to reading.** A caller holding
`entity.confirm` and not `entity.edit_immutable` — a combination § 3.3 produces no grant row for, since the
two permissions have identical columns, and which is therefore reachable only from a hand-built claim — may
turn the flag off and may **not** rename in the same statement, because rule 2 reads the old flag rather
than the new one. That single assertion is what distinguishes a trigger reading `OLD.confirmed` from one
reading `NEW.confirmed`, and nothing else in the grid would catch the substitution.

**The role scope is measured, not assumed.** Task 1 records what each of the three caller classes presents
as its effective role inside a transaction and reproduces the unscoped failure, and the expression is then
pinned to the measured behaviour rather than to a remembered one.

### The three-celled grid, and why two cells is not enough

For every protected name column on every entity table:

| Cell | Caller | Row state | Expected |
|---|---|---|---|
| 1 | entity grantee | confirmed | refused, naming the column |
| 2 | entity grantee | unconfirmed | **allowed**, new value read back |
| 3 | `entity.edit_immutable` holder | confirmed | allowed, new value read back |

Cell 1 alone is satisfied by a rule that simply denies the entity user, which is § 8.7(c) — an option the
operator did not take. Cell 3 alone is satisfied by a rule that denies nobody. **Cell 2 is the only one
that observes conditionality**, and it is the cell a plan in a hurry drops, so it carries its own negative
control: a variant of the trigger that ignores the old flag is run against the whole file and the number of
middle-cell assertions it reddens is recorded. That number is this plan's central evidence, in the same way
the stub-run reddened counts are 162-04's.

The confirmation gate gets its own three cells per table — entity grantee refused turning it on, entity
grantee refused turning it off, `entity.confirm` holder allowed either way — and the hot path gets a pair:
an answers write on a confirmed row by a caller with no `entity.edit_immutable` succeeds, and that same
caller's name write on that same row in that same transaction is refused.

### What this plan deliberately does not fix

§ 3.4's *basic data only, not answers unless public* cannot be expressed by a row-level policy, and 162-10
handed the question here because it is a column-grant question: the answers column sits on the entity row,
row-level security admits or refuses whole rows, and this file carries no SELECT grants at all. **This plan
does not add any.** Adding read-side column grants would be a new mechanism on a new verb for a reach whose
existence depends on 162-04 Task 2's ratified option letter — under the recommended reading the parent
reads no entity row at all and the gap does not arise. Task 1 reads that letter from `162-04-SUMMARY.md`
and the SUMMARY records the disposition: closed by the ratified reading, or still open and named for
162-17. It is **not** silently accepted, and it is not fixed here on a guess.
