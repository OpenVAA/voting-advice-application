<objective>
Move public visibility off ten per-row `published` flags and onto one project flag and two confirmation
states — in the policies, in their end state, in one commit — and prove the move in both directions before
accepting it.

**Purpose.** This is the plan where the voter application's visibility actually changes. § 3.4 and § 11.2
make public read an **all-of** rule that is transitive through the nomination: a nomination is public only
when its project is open for voters, the nomination is confirmed, and every entity it links is confirmed;
an entity is public only through such a nomination. 162-07 declared `open_for_voters` and `confirmed` and
shipped them **inert** — nothing reads them until now — so this plan is the first place their semantics are
observable at all.

**The problem this plan is built around: the two failure modes are opposite, and only one of them is
visible.** Too strict and the public application renders empty, which the E2E suite reports loudly at the
first spec. Too loose and unconfirmed or closed-project rows become world-readable, which **nothing**
reports, because a passing read test cannot tell "correctly visible" from "should have been hidden". So the
evidence is not that anon can see things. The evidence is a grid in which every table has a row that must be
visible and a row that must not, differing in **exactly one conjunct**, run first against three
deliberately wrong predicates — two over-permissive, one over-strict — with the reddened counts recorded.
A conjunct that is not independently load-bearing is a conjunct that is not there.

**`published` is absent, not merely unused.** § 8.4(b) deletes it and § 11.6 gives the deletion to 162-16,
so these thirteen predicates are written once in their end state rather than written with a term 162-16
would strip out again (D-11b). The structural assertion is that no anon policy in the applied database
mentions it.

**One new shape, and it cannot be written the obvious way.** An entity's anon policy has to ask whether a
confirming nomination exists — the same `nominations` hop `is_child_nominee` performs (§ 5). Written as an
inline `EXISTS` it does not merely perform badly: the project term returns **zero rows for every caller**
because `public.projects` has no anon policy, and the entity/nomination pair raises
`infinite recursion detected in policy for relation`. Both are measured in Task 1 in a rolled-back
transaction, and both are why the hop lives in three `SECURITY DEFINER` helpers beside `is_child_nominee`
rather than in thirteen policy bodies.

**Output.** Three hardened helpers in `301-auth-functions.sql`; thirteen converted anon predicates in
`302-rls.sql`; a fixture whose four entity tables all carry the A-visible / B-hidden polarity; two existing
pgTAP files re-expressed so they keep measuring what their description strings claim; a new visibility grid
file; a regenerated `00001_initial_schema.sql` and `packages/supabase-types/`; and a wave-3 gate including
the full E2E suite.
</objective>

## The design, settled before the first line of SQL

### Why there are helper functions at all

M2 and M3 are the whole argument, and they are the two things a reviewer should check first. The rule
§ 3.4 states reads naturally as three `EXISTS` clauses, and all three of them are unavailable inline:

| Written inline | What actually happens | Measured |
|---|---|---|
| `EXISTS (SELECT 1 FROM public.projects …)` | RLS on `projects` has no anon policy, so the sub-select is empty for every anon caller and the policy denies everything | M2 — 0 rows vs 1 |
| entity policy `EXISTS (… FROM nominations)` **and** nomination policy `EXISTS (… FROM candidates)` | mutual policy reference, detected at plan time | M3 — `infinite recursion detected in policy for relation "candidates"` |
| either one, alone | works today and breaks the moment its twin is written | the failure arrives in a later plan, in a different diff |

`STABLE SECURITY DEFINER SET search_path = ''` is what the three existing predicates in
`301-auth-functions.sql` already use, for the same reason: a policy predicate must be able to read a table
the caller cannot. So the helpers are not an optimisation, and they are not a style preference. They are
the only form in which the rule can be written at all.

### The three helpers

Appended to `apps/supabase/supabase/schema/301-auth-functions.sql`, beside `is_child_nominee`, in this
order. All three are `STABLE SECURITY DEFINER SET search_path = ''` and all three **deny when their lookup
finds no row** — the deny-by-default pattern `162-PATTERNS.md` records, and the one property a
visibility predicate must never get wrong in the other direction.

| Function | Signature | Reads | Answers |
|---|---|---|---|
| `public.project_open_for_voters` | `(p_project_id uuid) RETURNS boolean` | `projects`, by primary key | is this project open for voters (D-15) |
| `public.entity_has_confirmed_nomination` | `(p_entity_type public.entity_type, p_entity_id uuid, p_project_id uuid) RETURNS boolean` | `nominations`, one hop | does a non-unconfirmed nomination **in this project** link this entity |
| `public.nomination_entities_confirmed` | `(p_nomination_id uuid) RETURNS boolean` | `nominations` joined to the one entity table its FK names | is every entity this nomination links anon-readable |

**`entity_has_confirmed_nomination` is the reuse § 5 asks for, and the reuse is structural because it
cannot be anything else.** `is_child_nominee(p_parent_type, p_parent_id, p_child_id)` answers *is this
entity nominated under that one*; this answers *is this entity nominated at all, publicly*. They are
different questions over the same hop, and 162-04 Task 2 ratified the first signature as a published
interface that 96 policies are being written against, so it cannot be widened. What "one mechanism" means
here, and what 162-17's structural guard will check, is that **no policy holds a `nominations` sub-select**:
the hop exists in one file, in one idiom — matching an entity id against the four FK columns exactly as
`is_child_nominee` does — and the policies call it.

**The third argument on `entity_has_confirmed_nomination` is deliberate.** `nominations` carries a
`project_id` of its own and nothing in the schema forces it to agree with its entity's; `07-rpc-security`
creates exactly that row on purpose. Without the argument, an entity in an open project whose only
nomination lives in a closed one would be public. `get_nominations`' own comment makes the same point about
the same hazard, which is the precedent this follows.

### The thirteen predicates

| Policy | New `USING` |
|---|---|
| `anon_select_elections` · `_constituency_groups` · `_constituencies` · `_question_categories` · `_questions` · `_app_settings` | `(SELECT public.project_open_for_voters (project_id))` |
| `anon_select_constituency_group_constituencies` · `anon_select_election_constituency_groups` | `EXISTS (SELECT 1 FROM public.constituency_groups cg WHERE cg.id = constituency_group_id)` — see below |
| `anon_select_nominations` | `(SELECT public.project_open_for_voters (project_id)) AND NOT COALESCE(unconfirmed, false) AND (SELECT public.nomination_entities_confirmed (id))` |
| `anon_select_organizations` · `_factions` · `_alliances` | `(SELECT public.project_open_for_voters (project_id)) AND confirmed AND (SELECT public.entity_has_confirmed_nomination ('<type>', id, project_id))` |
| `anon_select_candidates` | the same three conjuncts **plus** the two existing terms-of-use terms, unchanged and in their existing order |

**The two join tables delegate rather than re-derive.** Neither carries a `project_id`, and both carry
`constituency_group_id`. Written as an `EXISTS` over `constituency_groups` the sub-select is evaluated under
the anon caller's own RLS, so it resolves to *the group is anon-visible* — which is the group's own policy
answering, not a second copy of the rule. There is no cycle, because `anon_select_constituency_groups` does
not reference the join tables. This is the one place an inline sub-select is correct, and it is correct
precisely because it delegates to a policy instead of re-deriving a predicate. **Task 1 measures it** —
it is an M3-shaped construction and it is not being taken on reasoning.

**`app_settings` is gated, and that has a consequence worth stating.** § 3.4 lists settings first among the
structure an anon reader may see *when the project is open for voters*, so the policy stops being
`USING (true)`. A closed project therefore returns the anon caller **no settings row at all**, and the voter
application has to be able to render that. Nothing in the tree is in that state today — every seeded project
is open (162-07) — so no gate will catch it, which is why it is put to the operator at Task 2 and recorded
in the SUMMARY as a handoff rather than discovered later. The alternative, leaving one anon policy ungated,
is the second visibility mechanism this phase exists to end.

**`published` does not appear.** Not as a conjunct, not as a fallback, not in a comment that spells it as
still meaningful (D-11b). The columns stay until 162-16; the term leaves now.

### What the grid has to prove, and why a visibility test cannot prove it

Three properties, and only the first is what a normal read test measures:

1. **The row that must be visible is visible.** Necessary, and on its own it is satisfied by
   `USING (true)`.
2. **The row that must be hidden is hidden, and it differs from the visible row in exactly one conjunct.**
   One pair per conjunct per policy: `open_for_voters` false with everything else true; the nomination
   unconfirmed with everything else true; the linked entity `confirmed = false` with everything else true;
   the candidate's terms of use unaccepted with everything else true.
3. **Each conjunct is independently load-bearing.** Property 2 still passes if two conjuncts happen to be
   the same predicate — for instance if `entity_has_confirmed_nomination` silently returned
   `project_open_for_voters`. So the grid is run against three **deliberately wrong** predicate sets before
   the real ones are accepted: drop the entity conjunct, drop the project conjunct, and AND `false`. Each
   run's reddened count is recorded; the two over-permissive runs must redden the negative half and the
   over-strict run the positive half. A grid that cannot be made to fail in both directions is not
   measuring.

### What this plan does not decide

The **authenticated** half of ROADMAP criterion 5 — *an unpublished project's non-entities are readable by
any grantee, and its entities by the grantees themselves and their parents* — is 162-09, 162-10 and
162-11's, and `is_child_nominee`'s read role lands there. This plan implements the first clause only, and
the SUMMARY says so, because a criterion recorded as satisfied when a third of it is built is the kind of
error that closes a phase early.
