## Measured facts this plan is built on

Four measurements taken in this worktree on 2026-09-15, against branch `integration/ship-12-squash`
with the local stack up. Each is a fact the plan depends on; none needs re-deriving, all are
re-checked by the verify blocks below.

**M1 — § 3.2 is machine-parseable and yields exactly 23, in the matrix's order.** The five group
rows of the brief's § 3.2 table carry 23 backticked `group.verb` tokens in column 2, and that
sequence is equal **in order** to the first column of § 3.3's 23-row matrix. The extraction used is
Task 1's, run verbatim at planning time. This is why the plan can insist on derivation rather than
transcription: the derivation works today.

**M2 — a plain `UNIQUE` over the grant key enforces nothing for three of the four scopes.** On this
tree's PostgreSQL 15.8, two byte-identical ProjectAdmin grants both inserted into a table keyed
`UNIQUE (user_id, scope, target_type, target_id, role)` — because `target_type` is NULL on every
non-entity row and default NULLS-DISTINCT semantics make no two such rows conflict. The same pair
against `UNIQUE NULLS NOT DISTINCT` failed on the second insert with
`duplicate key value violates unique constraint "grants_user_scope_target_role_key"`. This is the
same trap the brief's § 11.7 documents for `nominations`, and `user_roles` carries it today
(`UNIQUE (user_id, role, scope_type, scope_id)`, `scope_id` NULL for super_admin). `grants` must not
inherit it. `config.toml` pins `major_version = 15`, and `NULLS NOT DISTINCT` is a PostgreSQL 15
feature — available with no margin, which the constraint's comment must say.

**M3 — the proposed DDL is prettier-stable.** SQL is under the prettier gate in this repo
(`prettier-plugin-sql`, enabled by phase 163; `yarn format:check` runs `prettier --check .`), and
`apps/supabase/supabase/schema/` is currently clean. The exact `CREATE TABLE public.grants` body
below, including the `UNIQUE NULLS NOT DISTINCT` clause and both named CHECKs, passes through
prettier byte-identically. Formatting is therefore not a reason to reshape the declaration — but
`prettier --check` on the two edited schema files is still a gate, because a hand edit can drift.

**M4 — `seed.sql` creates two auth users with fixed UUIDs**, `00000000-0000-0000-0000-000000000010`
(admin) and `...011` (candidate). After `yarn db:reset` either can be the `user_id` of a probe row,
so the behavioural constraint checks need neither a created user nor a dropped foreign key.

### The shape of the table

`grants` is keyed `(user_id, scope, target_type, target_id, role)` per § 3.1 and D-05 — **one
`entity` scope with a `target_type` discriminator**, not four entity scopes. Its columns, in
declaration order: `id`, `user_id`, `scope`, `target_type`, `target_id`, `role`, `created_at`.

`target_type` takes the **existing** `public.entity_type` — `candidate`, `organization`, `faction`,
`alliance` — which is exactly D-05's discriminator domain. `162-PATTERNS.md` calls the reuse out by
name; declaring a fifth parallel entity vocabulary would be the duplication this phase exists to end.

Two named CHECKs, both total functions over non-null booleans, so neither has a NULL-passes hole:

- `grants_entity_scope_target_type_check` — `(target_type IS NOT NULL) = (scope = 'entity')`. This is
  D-05's constraint, and it is what makes the discriminator honest rather than advisory.
- `grants_target_id_scope_check` — `(target_id IS NULL) = (scope = 'global')`. This one states § 3.1's
  `target_id` column: global grants have no target, account/project/entity grants must have one. It
  says slightly more than D-05 literally does; its authority is § 3.1's table, and it is flagged as
  such in `<flagged_assumptions>` below. Keep it: without it a project grant with a NULL target is
  insertable and `user_can` has to decide what that means.

`created_at timestamptz NOT NULL DEFAULT now()` mirrors `user_roles`. There is deliberately no
`updated_at` and no `set_updated_at` trigger (`user_roles` has neither), and deliberately no
`granted_by` audit column — useful, un-asked-for, and 162-06's to propose if it wants one.

## Edge coverage

No `162-SPEC.md` § 8 existed when this plan was written — 162-01 creates it, and by execution time it
will, which is why Task 1 reads it as a derivation channel. The deterministic edge probe returned
**5 applicable, 0 resolved, 5 unresolved**. None is auto-dismissed; each is stated with what this
plan does about it and what it leaves open.

1. **`empty` — real content here, and deliberately left representable.** What does a user with **no
   grants at all** mean? Every `anon` request is that case, and so is every authenticated user before
   162-06's migration runs. The table permits it trivially — zero rows for a `user_id` — and nothing
   in this plan's constraints makes the no-grant case unrepresentable or ambiguous, which was the one
   obligation on the table's design. **The answer to what `user_can` returns for that user belongs to
   162-04**, and it must be deny-by-default; `162-PATTERNS.md`'s "deny-by-default security predicate"
   is the shape. Surfaced, not closed. The second `empty` case is the guard's: a parser that finds
   zero members reports equality between two empty sets, and the census plus the floor in Task 5 is
   the answer.

2. **`idempotency` — checked, in two places.** Regenerating `00001` from an unchanged `schema/` twice
   must produce a byte-identical file; 162-02b establishes and tests that, and Task 6 re-exercises it
   by requiring a second `yarn db:types` to leave no diff. The enum-specific form is that adding a
   type must not reorder existing members, since enum ordinals are persisted: Task 3 appends after
   `role_scope_type` and asserts exactly one deleted line in `000-enums.sql`, the header inventory.
   **Open:** under D-14 every `db:reset` rebuilds ordinals from scratch, so ordinal stability is a
   property of the *file*, not of any deployed database — which is the right guarantee today and
   stops being sufficient the moment a database is published.

3. **`adjacency` — a weak fit here, and saying so rather than inventing a predicate.** 162-02b's
   adjacency concern was column ordinal position under a declaration move; this plan moves no column
   and appends one table and three types at the end of two files. The nearest real adjacency
   question — where in `300-auth-tables.sql` the `grants` block sits — is answered by placement
   (after the `user_roles` REVOKE, before the `published` section) and has no failure mode beyond
   readability, because `00001` is a filename-order concatenation and nothing in it depends on
   intra-file position.

4. **`ordering` — partly checked, partly not this plan's.** Member order is checked three ways in
   Task 3 and again by the guard. File apply order is unchanged. **Open assumption:** that
   `000-enums.sql` still sorts first among `schema/*.sql`, so the three types exist before
   `300-auth-tables.sql` uses two of them. It does today by filename, and Task 4's `yarn db:reset`
   exiting 0 is the test — a type used before it is declared fails the reset loudly.

5. **`concurrency` — unresolved, and flagged rather than closed.** Two forms. The first is
   `162-02b`'s and is inherited verbatim: `config.toml` pins ten literal ports, so a second checkout's
   local stack answering on 54322 would make Task 1's baseline and Task 6's comparison describe
   different databases. Mitigation is procedural — one stack, one session — and the symptom is a
   policy delta far from 2. The second is racing writers to `grants`, which **belongs to 162-12**, not
   here: this plan's `UNIQUE NULLS NOT DISTINCT` is the serialization point for duplicate grants, and
   it is a constraint rather than a predicate precisely so that two concurrent inserts cannot both
   observe "no such grant exists" and both proceed. That is the same argument § 11.7 makes for the
   nominations key.

  the worse surprise — but it is a coupling, and it is recorded here so 162-04 and 162-14 can rely on
