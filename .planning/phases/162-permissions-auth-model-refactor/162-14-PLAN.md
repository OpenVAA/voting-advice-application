<objective>
Make the storage layer ask the table layer's question, in the table layer's words, per verb — and prove
before accepting it that a denial at the table level is a denial at the storage level, in both
directions.

**Purpose.** The ROADMAP records criterion 6 as already half-satisfied: `400-storage.sql` calls the
project predicate at several sites, so storage follows table access by construction and inherits the
rename automatically. Both halves of that sentence are measurably true for eight of the fifteen policies
and measurably false for the other seven (D-03). Six of them hardcode one entity type into a path segment
and re-derive ownership with a bare identity comparison, which is a parallel implementation in exactly
the sense the phase's goal sentence forbids; the seventh is an anon read policy still routed through a
storage-local copy of the visibility mechanism 162-08 retired everywhere else. This plan ends both.

**What remains of criterion 6 is the paired assertion, and it is the easiest thing in this phase to write
in a form that cannot fail.** "Storage agrees with tables" is satisfied by two policies that both say
`true`. It is satisfied by a pair whose two halves both call `user_can`, which asserts that a function
equals itself. It is satisfied by a denial observed on an identity that is denied everything. So the
evidence here is not that the grid passes. The evidence is that the grid is two-directional — an identity
denied at the table level is denied at storage AND an identity allowed at the table level is allowed at
storage — that its table half is a real table operation rather than a predicate call, and that it was
observed RED against three deliberately divergent policy sets before the real ones were accepted, with
the reddened counts recorded.

**K2 is what makes the verb load-bearing, and it needs an identity to be load-bearing against.** A policy
that honours `read` and `write` identically passes any grid that exercises only one of them. Two
independent read-but-not-write identities are therefore constructed, at two different scopes: an entity
grantee who may read another entity's publicly visible asset and may not write it, and a caller who holds
project read but not project structure edit and may read an election's asset and not write it. The second
exists only because the type path segment is mapped to a permission rather than to a boolean, which is
the concrete content of the operator's A4 note.

**The failure direction of the anon policy is exposure, and it is the one this plan can get wrong
silently.** A read test cannot tell "correctly visible" from "should have been hidden". So the anon set is
asserted as three negatives and one positive, the negatives are observed red against a visibility helper
returning true unconditionally, and the project-level asset path — unconditionally world-readable today —
is gated on the project being open for voters, which is a tightening stated as one rather than slipped in.

**Output.** One enum and two hardened helpers; fifteen converted predicates and twelve retired names in
`400-storage.sql`; the storage layer's copy of the retired visibility mechanism absent from `pg_proc`;
zero inline re-derivations; a new pgTAP grid file; the existing storage file re-expressed so its
assertions keep measuring what their description strings claim; a regenerated `00001_initial_schema.sql`
and `packages/supabase-types/`; and a wave-5 gate including the full E2E suite, whose candidate
portrait-upload step is the one application path that exercises a converted write policy for real.
</objective>

## Measured facts this plan is built on

Ten measurements taken in this worktree on 2026-09-16 against branch `integration/ship-12-squash`, HEAD
`bc4486108`. M1, M2, M9 and the fifteen policy names were read from the **applied** database, not only
from the file. Each is re-derived by Task 1 — the outline records that an earlier census of this same file
had **0 of 10 cited line anchors correct**, so nothing below is trusted as written.

**M1 — the census, derived.** `apps/supabase/supabase/schema/400-storage.sql` declares **15** policies on
`storage.objects`. **8** route through the legacy project predicate — the two `authenticated_select_*`
and the six `admin_*` — across **10** real call sites; an eleventh grep hit is the file's own
`Depends on:` header line, which is where the phase's earlier "11 sites" figure came from. **7** do not
route through it: the six `candidate_*` and `anon_select_public_assets`. This reproduces D-03's corrected
table exactly, including that seven is the non-caller total and six is the `candidate_*` count.

**M2 — the re-derivation split is NOT the caller/non-caller split, and the phase's ledger does not say
so.** There are **12** occurrences of the inline self-ownership comparison, inside **10** `EXISTS` blocks,
spread over **8** policies: `candidate_insert_public` 1, `candidate_insert_private` 1,
`candidate_update_public` 2, `candidate_update_private` 2, `candidate_delete_public` 1,
`candidate_delete_private` 1 — eight in the six `candidate_*` — and `authenticated_select_public` 2,
`authenticated_select_private` 2 — **four in two policies that already call the legacy predicate**. So two
of the eight "good" policies carry a third of the re-derivations, and `anon_select_public_assets` is a
non-caller carrying none. D-03's note that "the non-callers are not all the same problem" is correct and
understates it: the callers are not all the same thing either.

**M3 — the path type segment has a vocabulary of eleven, not four.** The storage cleanup trigger is
registered on **ten** tables — the four entity tables plus `elections`, `constituencies`,
`constituency_groups`, `nominations`, `questions`, `question_categories` — and the trigger builds the path
prefix from `TG_TABLE_NAME`, so all ten appear as segment `[2]`. An eleventh value, `project`, is the
project-level path the retired helper special-cases. A mapping that covers only the four entity types
would leave six table families reachable at project scope only, which is what they have today; a mapping
that resolves each to the permission its own table policy asks is what the A4 note describes.

**M4 — the retired publication helper has exactly two call sites and both are policies in the same file.**
It is referenced in `anon_select_public_assets` and in `authenticated_select_public_assets`, plus the
file's own header line and one stale header line in `06-storage-rls.test.sql` that also names a schema
filename that no longer exists. Nothing under `apps/supabase/scripts/`, `scripts/` or the pgTAP estate
asserts its existence, so deleting it costs one header rewrite and no test rewrite.

**M5 — it already denies rather than raises on a malformed path, and that is the property to inherit.** It
takes both segments as `text`, returns early for the project-level value before any cast, performs the
lookup through `format` with a dynamic table name, and carries an `EXCEPTION WHEN OTHERS THEN RETURN
false` arm. The `candidate_*` policies, by contrast, cast segment `[3]` to uuid inside their `EXISTS` and
are protected only by a preceding equality on segment `[2]` whose evaluation order PostgreSQL does not
guarantee. A helper taking text and denying inside an exception handler is therefore not a new idea in
this file; it is the form one of its two helpers already uses.

**M6 — the two bucket names are a frontend contract, not a database detail.** `public-assets` and
`private-assets` are declared in `apps/supabase/supabase/config.toml` under `[storage.buckets.*]`, not in
`schema/`, and `public-assets` is baked into the adapter's public URL builder, the stored-image schema's
documented meaning, the candidate upload path, the dev-seed portrait upload and teardown, and more than
twenty unit-test expectations. Reading the A4 note's word "bucket" literally is a frontend and seed

## The design, settled before the first line of SQL

### One enum, two helpers, fifteen predicates

| Object | Signature | Reads a table | Hardening |
|---|---|---|---|
| `public.storage_verb` | enum, two members: the read case and the write case | — | declared in `000-enums.sql` beside the phase's other enums |
| `public.storage_path_can` | `(p_scope public.grant_scope_type, p_project text, p_type text, p_id text, p_verb public.storage_verb) RETURNS boolean` | only through `user_can` and one existence lookup | `STABLE SECURITY DEFINER SET search_path = ''` |
| `public.storage_path_is_public` | `(p_project text, p_type text, p_id text) RETURNS boolean` | only through 162-08's three helpers | `STABLE SECURITY DEFINER SET search_path = ''` |

**Why the verb is a declared argument and not two functions.** K2's amendment says the verb argument of
`user_can` must be **honoured by storage policies, not discarded**. Two functions named for read and for
write would satisfy the sentence's letter while discarding the argument, and would make the read/write
split a property of which function a policy happened to call rather than a property the function
guarantees. A declared argument that the body branches on makes separability structural: the same call
with a different verb resolves to a different permission, and a body that ignored it would redden the two
read-but-not-write identities. A `text` argument was rejected for the reason K3 gives about settings
columns — a typo in a text literal inside a policy predicate denies silently, where a typo in an enum
literal fails to apply.

**Why the helpers live in `400-storage.sql` and not beside `user_can`.** § 11.4's rule is that a concern
file owns everything about its concern except the column declarations it used to append. Path parsing is a
storage concern, the file already declares one helper of exactly this kind, and the file loads after
`301-auth-functions.sql` in filename order, so calling `user_can` and 162-08's three helpers from here is
ordinary. The enum is the exception and goes to `000-enums.sql`, because that is where every enum this
phase has added lives.

### The mapping, which is the concrete content of the A4 note

One `CASE` in one function body, from the type path segment and the verb to the scope-appropriate
permission. **This is a statement about the storage layout, not a row of § 3.3** — it names which question
to ask, and `user_can` answers it.

| Type segment | Under entity scope | Under project scope |
|---|---|---|
| the four entity table names | read: `entity.read_answers` · write: `entity.edit_answers`, both on the id in segment `[3]` | read: `project.read_entities` · write: `project.edit_entities`, on the id in segment `[1]` |
| `elections`, `constituencies`, `constituency_groups` | not defined — deny | read: `project.read_structure` · write: `project.edit_structure` |
| `questions`, `question_categories` | not defined — deny | read: `project.read_structure` · write: `project.edit_questions` |
| `nominations` | not defined — deny | read: `project.read_entities` · write: `project.edit_nominations` |
| `project` | not defined — deny | read: `project.read_structure` · write: `project.edit_app_settings` |
| anything else | deny | deny |

Three properties of this table are load-bearing and each is asserted:

1. **It is where the read-but-not-write identity at project scope comes from.** § 3.3 gives Candidate,
   OrgEditor and Faction/Alliance grants `project.read_structure` and withholds `project.edit_structure`.
   So an entity grantee may read an election's banner and may not write it — a real, non-trivial instance
   of K2's separability that exists only because reads and writes map to different permissions.
2. **Under entity scope the row must exist in the table the segment names.** The retired helper provided
   that pairing implicitly, through a lookup on a dynamically named table; a conversion that asked
   `user_can` on the bare uuid would drop it and admit a path claiming one entity type while carrying
   another's id. It is asserted as a refusal, not assumed.
3. **The fall-through denies.** An unrecognised type segment is not a project-scope free-for-all; it is a
   denial, in both scopes and both verbs.

### The anon half, which is 162-08's rule and not a second copy of it

`storage_path_is_public` composes 162-08's three helpers and nothing else: the project in segment `[1]` is
open for voters, and — for a type segment naming an entity table — the entity in segment `[3]` carries its
own confirmation flag and a confirming nomination. For the project-level type segment there is no entity,
so the rule reduces to the project conjunct alone. **That is a tightening**: the project-level path is
unconditionally readable today, which means a closed project's assets are world-readable, and § 3.4 says
project structure is anon-readable only when the project is open for voters. It is stated as a tightening,
asserted as one, and named in the SUMMARY.

**`user_can` is deliberately NOT consulted for the anon case.** 162-04 resolved the `empty` edge by
denying a caller whose JWT carries no grants key at all, which is every anon caller, and 162-08's
prohibitions record that mixing an authority question into a visibility predicate would make one function
answer two questions. So the anon storage policy routes through the visibility mechanism, and the
authenticated policies route through `user_can`, and "all fifteen route through `user_can`" is read the
way the phase's own goal sentence reads it — one mechanism, not a parallel implementation — rather than as
a literal call-site count that `user_can`'s own contract makes unreachable for anon. **This reading is
flagged below and put to the operator's evidence rather than asserted.**

### The paired assertion, which is the deliverable

For each of the two verbs and each of the two scopes, **four** observations, of which two are the pair and
two are its opposite direction:

- an identity **denied** the corresponding operation on the content table is **denied** the corresponding
  storage operation on that row's folder;
- an identity **allowed** the corresponding operation on the content table is **allowed** the
  corresponding storage operation on that folder.

**The table half is a real table operation.** A SELECT whose row count is asserted, or an UPDATE whose
affected-row count is asserted — never a `user_can` call. Two halves calling one function assert that the
function equals itself, pass against any pair of policies whatsoever, and cannot detect the one thing
criterion 6 asks about. This is written as a prohibition because it is the natural thing to write and it
is silently worthless.

**Plus F3(a)'s third case, twice.** A principal granted read-but-not-write is observed reading the object
and failing to write it, at entity scope and at project scope. F3's own text says the third case is the
one that fails if the verb is accepted and then discarded, and F3(b) — the two denials alone — is rejected
in the ★ for exactly that reason.

**Plus the control run, three variants, counts recorded.** Before the real policies are accepted: a set
that ignores the verb argument and asks the read permission for writes; a set that asks project scope
where entity scope belongs; and a set that denies unconditionally. The first two must redden the deny
half, the third must redden the allow half, each count greater than zero and each recorded. F4(a)'s ledger
is the house instrument and 162-17 is where these counts are filed.

### Policy shape and names

Fifteen policies in, fifteen out, each predicate replaced in place — Task 2's Q4 decides this against the
alternative of collapsing the paired entity-scope and project-scope policies into one per bucket and verb.
Under the recommended shape the six `candidate_*` names lose the entity type from their actor segment per
D-21's naming clause, and the six `admin_*` names lose an actor that the conversion makes untrue: a
project editor holds the project-scope write permissions, so `admin_` would name a role that is not the
one the predicate asks about.

**D-21 made structural, inheriting 162-10's technique.** For each write verb, the policy expressions
normalised by replacing the bucket literal with a placeholder collapse to one string per scope; and no
policy expression compares the type segment against an entity-type or table-name literal at all, because
the type segment is an argument to the mapping. 162-10 proved the same property across four tables by
replacing the table name and the entity-type literal; this plan proves it across two buckets by replacing
the bucket name. Same mechanism, different placeholder, on the dimension this file actually repeats along.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> Supabase Storage API -> `storage.objects` -> RLS policy | The object **name is chosen by the caller**.
