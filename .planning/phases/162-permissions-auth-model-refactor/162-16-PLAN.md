<objective>
Delete the retired visibility mechanism from the tree, and prove — set by set, on two independently
rebuilt databases — that not one row changed hands.

**Purpose.** After 162-08 there is exactly one way to ask whether a row is public: is its project open for
voters, is its nomination confirmed, and is every entity that nomination links confirmed. Ten per-row
publication flags survive that as a mechanism nothing reads: dead weight in the schema, a live instruction
in three documents, and a default in the seeder that still stamps every seeded row. § 8.4(b) deletes them
inside this phase and § 11.6 makes this the named plan. After it, criterion 2's *one mechanism* is true of
visibility as well as of authority.

**The problem this plan is built around: this is a deletion with the widest blast radius in the phase, and
its characteristic failure is silent in both directions.** Remove the seeder's default without the
replacement flags standing and every seeded row vanishes from the voter application — loud, at the first
E2E spec. Remove a predicate's conjunct without its replacement and rows become world-readable — and
*nothing* reports that, because a passing read test cannot distinguish "correctly visible" from "should
have been hidden". So the evidence is neither a green suite nor a row count. It is an `md5` fingerprint of
the exact id set an anonymous caller can read, per table, on two rebuilt databases, taken before and
compared after — with the instrument first shown able to move, by planting three deliberate faults and
recording which fingerprints shifted.

**Almost everything the brief attributes to this plan has to be re-derived, and four items are not there.**
§ 11.6 names ten partial indexes; there are five. It names `seed.sql`; that file mentions the column zero
times. It names the bulk-import RPC's column lists; `bulk_import` builds its column list from the item
JSON and has no allow-list. It names the adapter's selects; every adapter read is `select('*')`. And it
names *the E2E specs that publish rows to make them visible*; zero of 41 tracked spec files name the
column — the publication happens in one branch of `SupabaseAdminClient.bulkImport`. Deriving the
populations is therefore not diligence, it is the difference between a plan that can be executed and a
plan whose acceptance criteria go red against a correct implementation. This phase has already corrected
three censuses for the same reason (D-03, D-16, D-25); this is the fourth.

**Output.** Ten columns and five partial indexes out of the declarative schema; the term out of the
comments in four schema files; the publication default and its table set out of the seeder; the mirrored
column lists, the column map and the four negative-control fixtures swept; twelve pgTAP files swept with
no assertion lost and three re-pointed; four documents that would otherwise teach the next author to
rebuild it corrected; a regenerated `00001_initial_schema.sql` and `packages/supabase-types/`; and the
wave-6 gate including the full E2E suite.
</objective>

## The design, settled before the first line of SQL

### The one instrument this plan turns on

A deletion is proven by what did not change. The property that must not change is *the exact set of rows an
anonymous caller can read*, and the instrument is a per-table fingerprint of that set:

| Property | Why a weaker form fails |
|---|---|
| Taken as `SET LOCAL ROLE anon` inside `BEGIN … ROLLBACK` | The policies are the subject; reading as `postgres` bypasses them entirely and measures nothing |
| `md5(string_agg(id::text, ',' ORDER BY id))`, not `count(*)` | A count is identical when one row leaves the set and another enters it — the exact shape of a mis-set replacement flag |
| On **two** independently rebuilt databases | `yarn db:reset-with-data` exercises the default template's paths; `yarn db:seed --template e2e/base` exercises the ones the E2E suite depends on. They do not overlap; 162-07 took its own census on both for the same reason |
| Vacuous cells named and excluded, non-vacuous count floored | `factions` yields `EMPTY` on every seed (M14). A comparison that treats `EMPTY = EMPTY` as agreement reports success on a wiped database |
| The instrument shown able to move, before it is believed | A fingerprint pair that agrees because both halves were taken wrongly is the failure mode a green run cannot distinguish from success |

**The three planted faults** that prove it moves, each in its own rolled-back transaction: set the
project's `open_for_voters` false and every non-vacuous fingerprint must move; set one candidate's
`confirmed` false and the candidates fingerprint must move and no other; add an unconditional anon SELECT
policy to one table and that table's fingerprint must move. The first two are the too-strict direction,
the third the too-loose one, and the moved counts are recorded as numbers in the SUMMARY. This is F4(a)'s
negative-control discipline applied to a deletion: the ledger row for this plan is *the instrument was
made to fail in both directions before it was used to certify anything*.
