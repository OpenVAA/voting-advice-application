<objective>
Give nominations a write model: entity users create and edit their own, a child nominee may originate the
parent it needs, an admin is the only one who can confirm anything — and make each of those a property of
the database rather than of a client.

**Purpose.** Every other plan in this wave converts policies that already exist. This one adds capability
that does not: fact 19 records that `nominations` is admin-only to write today, so there is no
entity-user policy to rename here, only ones to write from nothing. Writing a permission surface from
nothing is where the permissive failure lives, and the permissive failure is invisible — a policy that
admits a row it should have refused breaks no test, reddens no gate and ships. So every assertion in this
plan is paired, and the guards are proven load-bearing by being individually removed and watched to turn
green rather than by being argued for.

**Four things that must not be got wrong, stated before the design.** The uniqueness key must carry
`NULLS NOT DISTINCT` or it enforces nothing on this table (D-12c, D-24). The confirmation column must
become non-nullable and default to unconfirmed, because that default is exactly what makes "created
unconfirmed" true for a caller who cannot name the column (§ 11.5 guard 2). The insert column grant is a
privilege, not a predicate, and it is what makes that guard independent of getting every policy right
(fact 34). And the transition that turns confirmation off on edit is a review gate: an entity user who can
edit a nomination and keep it confirmed has defeated it.

**The mechanism is inherited, not re-derived.** Three of the five guards read `public.nominations` from
inside a policy on `public.nominations`. 162-08 measured what happens when a policy references a table
its own policy guards, and the answer is `infinite recursion detected in policy for relation`. The hops
therefore live in hardened helpers beside `is_child_nominee`, in its idiom, and Task 1 reproduces the
failure on this table before the helpers are written rather than taking it on 162-08's word.

**Output.** The confirmation column flipped and every reader with it; the operator's eight-column
uniqueness key; a deliberate ruling on the parent foreign key's delete action; the faction-parent rule in
`validate_nomination()`; eight policies on `nominations`, five converted and three new (the plan's prose said "seven" while its own Artifacts table enumerated eight -- MEASURED and corrected 2026-09-17); the first column
grant this table has ever carried; four helpers and one trigger function; a new pgTAP file whose every
assertion has a twin; a regenerated `00001_initial_schema.sql` and `packages/supabase-types/`; and the
wave-4 gate including the full E2E suite.
</objective>

**M2 — the confirmation column is nullable today and every reader compensates for it.**

**M3 — the retired column's trace population is 25 lines in 17 tracked files, and only 8 of them are the

**M4 — `303-column-grants.sql` mentions this table zero times** (fact 34), and the file's own header

**M5 — the bulk paths are unaffected by a column grant, and the measurement says why.** `bulk_import` and

**M6 — `bulk_delete` removes a collection with one statement per table**, built by `format` over the

**M7 — the seeder already has the exact mechanism the confirmation default needs, in one place.**

## The design, settled before the first line of SQL

### The confirmation column, and why its default is the interesting part

The column is renamed and its polarity inverted so that the two booleans this phase leaves behind read the
same way (D-11c): after this plan, `true` means confirmed on both the nomination and the entity, and there
is one polarity in the schema rather than two adjacent ones pointing in opposite directions.

It is declared `NOT NULL DEFAULT false`, and **the default is load-bearing rather than cosmetic**. § 11.5
guard 2 says the candidate-created parent is created unconfirmed and that the candidate cannot override
that; fact 34 says the mechanism is the insert column grant; and a column absent from a `GRANT INSERT`
column list takes its declared default rather than erroring. So `DEFAULT false` is what makes guard 2 true
in the only case that matters — the one where the caller does not name the column at all. A default of
`true` would make the grant list express nothing.

`NOT NULL` buys the other half: the null-coalescing wrapper every current reader carries becomes
removable, so the plan can assert its **absence** rather than its correctness (M2). There is no row to
migrate — D-14 records that no database has been published, so a reset builds from nothing — and the
question "what happens to pre-existing nulls" has a precise answer rather than a hopeful one: there are no
pre-existing rows, the creation paths are what supply the value, and `NOT NULL` is what stops a future
path from writing a null that a bare boolean read would silently drop.

**Because the default is the opposite of today's effective behaviour, the creation paths must say so.**
Today's `DEFAULT false` on the inverted column means every seeded nomination is effectively confirmed;
after the flip, a seeded nomination that says nothing is invisible to the voter application. This is
162-07's situation exactly, and it takes 162-07's answer: the value is supplied at the creation path, in
the one place that already performs that job (M7), and the property is asserted by a census over a real
rebuilt database in both directions, observed RED first.

### The eight-column key

```
CONSTRAINT nominations_entity_parent_contest_key
  UNIQUE NULLS NOT DISTINCT (
    candidate_id, faction_id, organization_id, alliance_id,
    parent_nomination_id, election_id, constituency_id, election_round
  )
```

Named, per the precedent two lines below it in the same body, and for the same reason: a `throws_ok` needs
a stable handle and 162-17 will assert this one by name. Its comment states the thing a future reader
cannot recover from the syntax — that the clause pins the PostgreSQL floor at the major version
`config.toml` declares, and that a downgrade would turn the constraint into a no-op rather than fail to
apply.

**The clause is asserted from `pg_index.indnullsnotdistinct`, never from the file.** That is the one
property review cannot see: the two forms differ by three words and behave completely differently on this
table, where the exactly-one-entity-FK CHECK guarantees three null columns in every row and the parent
column is null for every top-level nomination. Under default semantics no two rows would ever conflict.

**Three pairs, not one rejection.** A genuine duplicate is rejected; the same candidate under two
different parents at the same contest is accepted, which is the case the operator gave as the reason for
including the parent column; and two top-level nominations of the same entity in the same contest, both
with a null parent, are rejected — the pair that is green under a plain `UNIQUE` and red under the correct
one, so it is the pair that distinguishes them behaviourally.

### Where guard 3 needs more than the constraint

The constraint closes the race § 11.5 fact 33 described, but it is not the same predicate as guard 3 and
the difference must not be glossed. Guard 3 asks whether **any** nomination already exists for that
organization at that election, constituency and round; the constraint's key includes the parent, so an
organization already nominated under an alliance does not collide with a candidate-created parent carrying
a null parent of its own. Guard 3 therefore stays a real predicate — and the constraint stays the thing
that decides a concurrent race, exactly as § 11.7 says.

### Why every hop is a function

Three guards and the lock conjunct read a table from inside a policy. One reads `projects`; three read
`nominations` from a policy on `nominations`, which is a self-reference. 162-08 measured the mutual case
and recorded `infinite recursion detected in policy for relation`; the self-referential case is the same
detection and is reproduced here on this table before anything is written. The inline form is therefore
unavailable, not merely unattractive, and the helpers are the only shape in which these guards can be
expressed at all.

Four helpers, appended to `301-auth-functions.sql` beside `is_child_nominee`, all
`STABLE SECURITY DEFINER SET search_path = ''`, all denying when their lookup finds no row:

| Helper | Answers | Deny direction on no row |
|---|---|---|
| the project nomination-lock reader | is this project's nomination editing locked | returns **locked** — the inversion is deliberate, and it is still the denying answer |
| the contest-occupancy test | is this entity already nominated at this election, constituency and round | returns **false**, so absence of a row cannot fabricate an occupant; the guard that consumes it inverts the answer |
| the caller's-own-nomination test | does a nomination exist at this contest whose entity the caller holds a named permission on | returns **false** |
| the originated-unconfirmed counter | how many unconfirmed organization nominations did this caller originate | returns **0** |

The contest-occupancy test takes the entity type as an argument rather than naming one (D-21), and the
caller's-own-nomination test takes the permission as an argument and answers it by calling `user_can`, so
no cell of the matrix is written down a second time. That last one deserves its shape stated plainly: it
asks *is there a nomination at this contest whose entity I hold this permission on*, which is guard 5 and
the permission check in a single expression, with the matrix still living in exactly one function body.

### The five guards, and which of them is a predicate

| Guard | Where it lives |
|---|---|
| 1 — the inserted row is an organization nomination | a policy conjunct; the exactly-one-entity-FK CHECK is what makes the single non-null test sufficient |
| 2 — it is created unconfirmed | **a privilege, not a predicate** — the column is absent from the INSERT grant list so the caller cannot name it and the default supplies it. A policy conjunct is carried as well, because the two fail differently and the belt is not the braces |
| 3 — no nomination exists for that organization at that contest | a policy conjunct over the contest-occupancy helper; the constraint is what decides a race |
| 4 — the project's nomination lock is off | a policy conjunct over the lock helper |
| 5 — the caller already holds a nomination at that contest | a policy conjunct over the caller's-own-nomination helper |

**Guard 5 is implemented as its second clause, and that is a ruling rather than an omission.** § 11.5
states it as *is inserting their own child nomination in the same transaction, **or** already has one at
that contest*. A row-level `WITH CHECK` sees only the row being inserted, so the same-transaction clause
is not expressible in a policy at all — and the ordering makes it moot in the direction that matters: the
candidate needs the parent's id before they can point at it, so the parent is inserted first and the child
cannot exist yet. The enforceable reading is the second clause, and the flow it implies is legal today:
`validate_nomination()` already admits a candidate nomination with no parent, so a first-time candidate
creates their own nomination, then the parent, then repoints. This is put to the operator at Task 2
because § 6.2's interface inherits it.

### The originator column, and the cap

§ 8.9 asks for a cap on how many unconfirmed parents one candidate may originate, and for an admin queue
that shows who created each. **Neither is answerable today: no column records who created a nomination.**
So the cap is not a number waiting to be chosen, it is a column plus a number — and the column is what the
second half of § 8.9 asks for outright.

It is declared in the `CREATE TABLE` body (§ 11.4), defaulting to the calling user's id, nullable because
the service-role and owner paths have no calling user, and **absent from the INSERT column grant** so that
a caller cannot forge it. That absence is the second thing the grant list buys, and it is what makes the
cap a cap rather than a suggestion.

The cap is a literal in the policy with the reason beside it, not a setting: D-15's homes are for values
row-level security reads per project, and nothing has asked for a per-project knob. The recommended value
and its reasoning go to the operator at Task 2, because a number nobody chose is a number nobody owns.

### The delete action on the parent foreign key

D-12d requires a deliberate ruling and names the quiet path. Four options, and M6 decides between the two
that refuse:

| Action | What it does | Verdict |
|---|---|---|
| cascade | deleting a rejected placeholder silently deletes every candidate under it, including candidates who joined later | the quiet data-loss path the decision names. Rejected |
| set null | a candidate whose parent is deleted silently becomes an independent candidate's nomination, and a faction row violates the trigger's own must-have-a-parent rule on the way | misrepresents a candidate to voters without anyone seeing it. Rejected |
| refuse immediately | refuses to orphan children — and also refuses the project, election and constituency cascades that delete a whole subtree, because the check cannot wait for the rest of the statement | **breaks every teardown the seeder performs (M6).** Rejected |
| refuse at the end of the statement | refuses a targeted delete of a parent that still has children; permits a cascade that removes parent and children together, because by the time the check runs there are no referencing rows left | **recommended** |

The recommendation is the last. It is loud where the decision wants loud and silent nowhere, and M6 is why
it is not the one above it. Both halves are asserted behaviourally, because the catalogue value alone does
not distinguish the two refusing actions in the case that matters.

### The confirmation transition

USER-RIGHTS says *when editing, turn confirmed false* — the system sets it, so this is a trigger and not a
policy; a policy can refuse a row, it cannot rewrite one. It is `BEFORE INSERT OR UPDATE`, `SECURITY
INVOKER` (it must see its caller's effective role), and it reads no table directly — the only authority
question it asks is one `user_can` call, which is itself hardened.

Three rules, in order:

1. **On either verb**, a row being confirmed while its custom data carries the requested-parent key is
   refused with a named exception (D-12a). Confirming such a row publishes as an independent a candidate
   who asked for a party, which is the one place this feature touches the public read path.
2. **On update, when the caller's effective database role is `authenticated` and the caller does not hold
   the confirm permission on the row's project**: an attempt to turn confirmation on is refused with a
   named exception naming the permission; anything else has confirmation forced off. The refusal and the
   forcing are different failures and are asserted separately — silently ignoring an explicit request is
   how a client comes to believe it succeeded.
3. **Otherwise** the supplied value stands. That is what makes an admin's edit-and-confirm a single
   statement, and it is what keeps a service-role re-seed from unconfirming everything it touches.

**Rule 2's scope is the effective database role, and that choice is the one most likely to be got wrong.**
Scoping it to *has a JWT* would catch the service-role caller too, because PostgREST sets claims for that
role as well, and a second `yarn db:seed` would then unconfirm every row it upserted. The role test does
not depend on claim contents at all. M9 records that the pgTAP helper sets the role alongside the claims,
so both directions are exercisable from the estate; Task 1 measures the value the three caller classes
present before the expression is fixed, and the assertion is pinned to the behaviour rather than to the
expression.

A consequence worth stating rather than discovering: a **project editor** holds the edit permission and
not the confirm permission (§ 3.3), so a project editor's edit also turns confirmation off and only an
admin can restore it. That is the review gate working, not a defect.

### The faction-parent rule, and why the trigger has to be hardened

§ 11.8 tightens *an* organization to **the** organization: a faction's parent must be the nomination of
that faction's own organization. The lookup it needs is one more column on a `SELECT … INTO` that already
runs, plus one read of the faction's own organization — not a new round trip. The exception names **both**
organization ids, because in a seed log a message naming one is indistinguishable from the parent-type
error immediately above it (D-23).

The rule reads `public.factions`; the function already reads `public.nominations`. M10 is why both matter
now and did not before: the function is `SECURITY INVOKER`, so from the moment an entity user may insert,
both lookups run under that user's own row-level security, and a parent that exists but is unreadable is
reported by the existing not-found branch as a parent that does not exist. The function is therefore
hardened the way every other privileged predicate in this tree is hardened. The information the hardening
exposes — that a supplied identifier names a nomination of some type — is disposed of in the threat
register rather than inherited silently.

### The column grant, and the thing it cannot express

The file is a single global pair against one role (M4), so it cannot say *a candidate may not set this but
an admin may*. It is the **coarse outer bound**, exactly as D-11a describes the same file for the entity
tables, and the fine rules are policies and triggers. Two blocks:

- **INSERT** — the allowed list is the columns a nominating caller legitimately authors: the project, the
  four entity foreign keys, the election, the constituency, the round, the parent and the custom data.
  Protected, with the reason enumerated in the header the way the file's existing blocks do it: the
  confirmation flag and the originator (guard 2 and the cap), the identifier, the audit timestamps, the
  generated-data flag, the external identifier, the presentation order, the display fields and the
  election symbol — an organization's ballot number and display name are not a candidate's to author.
- **UPDATE** — the editable list is the contest fields, the parent, the custom data **and the confirmation
  flag**. The flag is present here and absent above, and that asymmetry is the design rather than an
  oversight: confirming is an update, an admin performs it through the same role, and the grant cannot
  tell the two callers apart. What stops an entity user is rule 2 of the trigger.

The consequence for an authenticated admin creating a nomination is two statements rather than one —
insert, then confirm. M5 measures that population at zero today, and the service-role and owner paths are
untouched, so the cost is stated and paid rather than discovered.

### The seven policies

| Policy | Predicate |
|---|---|
| the anonymous read | untouched but for the column rename — 162-08 wrote it in its end state |
| the authenticated read | the project read permission, OR the nomination read permission on the row's entity resolved from the four foreign keys, OR the public-visibility disjunct that replaces the publication term |
| admin insert / update / delete | the project nomination-editing permission, in place of the legacy project predicate |
| entity insert of own | the nomination-edit permission on the row's entity, AND the lock off, AND unconfirmed |
| entity update of own | the nomination-edit permission on the row's entity, AND the lock off, on both sides |
| entity insert of a parent | the five guards |

**The authenticated read keeps a public disjunct, and that is not an optimisation.** Today it carries
`OR published = true`, which is what lets a signed-in reader see a project they hold no grant in. Removing
the term without replacing it would make a logged-in candidate browsing the voter application see nothing
at all — and nothing in the anonymous policies would cover them, because those apply to a different role.
The replacement is the same three conjuncts 162-08 wrote for the anonymous reader, through the same
helpers, so the rule exists once and this policy calls it.

**The entity-scope argument is resolved from the row, not from a policy name.** Every entity-facing
predicate here coalesces the four foreign keys into one identifier and asks `user_can` about it (D-21), so
no policy names an entity type and the same predicate serves candidates, organizations, factions and
alliances.

**The parent hop is reached through `user_can`, not re-derived.** An organization reading its child
candidate's nomination is `user_can`'s child branch, which 162-04 Task 2 ratified by option letter; the
policy calls the function and the function calls `is_child_nominee`. ROADMAP criterion 3's *used wherever
policy allows that control* is satisfied by that chain, and the SUMMARY records the inherited option
letter so 162-17 asserts the same reading rather than a fresh one.

**One tightening is scoped to the new policies deliberately.** D-12b grants a candidate any organization
in the project, which needs the inserted row's organization and the row's project to agree — and no such
constraint exists on the table. 162-08 recorded why it must not be added table-wide: an existing pgTAP
control creates exactly that row on purpose, and tightening the table would void it. So the agreement is a
conjunct of the new entity-user policies only, the admin and service paths keep today's latitude, and the
general case is recorded as still open rather than quietly closed.

  exist survives every gate and then teaches the next agent the wrong schema. The split is principled, and
  it is stated here so it is not read as either plan breaking the other's rule.

- **The confirmation trigger's scope is measured, not reasoned.** Scoping rule 2 to *the caller has a
  token* would catch the seeder as well, because PostgREST sets claims for that role too, and a second
  seed run would unconfirm everything it upserted. The role test does not depend on claim contents at all.
  Task 1 measures what the three caller classes present before the expression is fixed, and the assertion
  is pinned to the behaviour — two seed runs, zero unconfirmed rows — rather than to the expression, so a
  future change of expression that breaks the property reddens.

- **A project editor's edit turns confirmation off.** § 3.3 gives that role the edit permission and
  withholds the confirm permission, so rule 2 applies to it, and only an administrator can restore the
  flag. This is the review gate working rather than a defect, but it is a behaviour nobody wrote down
  before, so it is stated here and in the SUMMARY rather than discovered by an editor wondering why their
  project went dark.

- **The hierarchy validator's exceptions are a weak existence oracle, and that is accepted rather than
  inherited.** A row-level check clause is evaluated after a before-insert trigger, so an entity user whose
  insert a policy would refuse still learns from the exception whether a supplied identifier names a
  nomination and of what type. The identifiers are unguessable, so the oracle requires knowledge that
  already implies access, and the alternative — a generic message — would retire D-23's discipline for
  every seed log in the project. Recorded in the threat register as an accepted finding.
