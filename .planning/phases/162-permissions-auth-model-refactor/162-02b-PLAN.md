## The ordinal-swap register — read this before Task 1

**This plan is behaviour-neutral, but it is NOT dump-identical, and the difference is exactly
enumerable.** `ALTER TABLE … ADD COLUMN` appends a column at the highest `attnum`. Moving a
declaration into a `CREATE TABLE` body moves it *earlier* in ordinal order. Because
`300-auth-tables.sql` keeps its 10 `published` columns as `ALTER`s (by ruling) while
`500-external-id.sql`'s `external_id` moves into the table bodies, **`external_id` and `published`
swap adjacent ordinal positions on 10 tables**:

| Table | `schema/` file whose `CREATE TABLE` receives the column | Before | After |
|---|---|---|---|
| `public.elections` | `101-elections.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.constituency_groups` | `101-elections.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.constituencies` | `101-elections.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.candidates` | `102-entities.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.organizations` | `102-entities.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.factions` | `102-entities.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.alliances` | `102-entities.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.questions` | `103-questions.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.question_categories` | `103-questions.sql` | `published`, `external_id` | `external_id`, `published` |
| `public.nominations` | `104-nominations.sql` | `published`, `external_id` | `external_id`, `published` |

`public.app_settings` is the eleventh `external_id` table and has no `published` column, so its
ordinal order is unchanged. `terms_of_use_accepted`, `answers` and `customization` do not move
relative to anything: they already preceded `published` and `external_id`, and they still do.

**This swap self-heals.** 162-16 drops `published` from the declarative schema; the moment it does,
the ordinal order is exactly what a fresh `CREATE TABLE` gives, which is what it would have been
either way. The swap is a transient of the two-plan split, not a lasting difference.

**Nothing else in the applied schema may change.** That claim was measured before this plan was
written: of the 118 lines the current parity signature reports as present in `schema/` and absent
from `00001`, 15 are unaccounted for by any of `00002`–`00008` — and **all 15 are SQL comment
lines**, prose that was written into the readable mirror and never copied into a migration.
Comments reach no catalogue. So the fold introduces **zero** semantic change from mirror-only
drift, and the only expected dump difference is the 10 ordinal swaps above. If the executor's
measured dump diff contains anything else, that is a finding, not noise — stop and report it.

## The dump recipe — one definition, used by Task 1 and Task 7

Both dumps MUST be produced by the identical command, from a database in the identical state
(`yarn db:reset`, nothing seeded on top).

- Dump: `PGPASSWORD=postgres pg_dump --schema-only --no-owner -h 127.0.0.1 -p 54322 -U postgres -d postgres -n public -n storage | grep -v '^\\restrict \|^\\unrestrict '`
- Ordinal census: `PGPASSWORD=postgres psql -h 127.0.0.1 -p 54322 -U postgres -d postgres -At -F'|' -c "SELECT table_name, ordinal_position, column_name FROM information_schema.columns WHERE table_schema = 'public' ORDER BY table_name, ordinal_position;"`

**The `\restrict` strip is not optional.** `pg_dump` 17.x emits a `\restrict <random-token>` /
`\unrestrict <random-token>` pair whose token is regenerated on every invocation; measured here,
two consecutive dumps of an unchanged database differ on those two lines and nowhere else. Without
the strip the byte comparison can never pass and the executor will chase a phantom. With the strip,
two consecutive dumps of an unchanged database are byte-identical — measured.

Keep both artefacts under `${TMPDIR:-/tmp}/162-02b/` — never inside the repository, so that
`git status --porcelain` stays a usable signal throughout.
