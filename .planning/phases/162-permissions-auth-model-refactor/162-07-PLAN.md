<objective>
Declare the three columns that will carry public visibility for the rest of the phase, and prove that each
one is `false` where it must be and `true` where it must be — on a database that has actually been rebuilt.

**Purpose.** After 162-08 there is exactly one way to ask whether a row is public: is its project open for
voters, is its nomination confirmed, and is every entity that nomination links confirmed. Two of those three
terms are columns this plan creates. Both default `false` and both have to be `true` on every row a
recreated local database produces — the no-regression rule brief § 5 states in so many words: every entity
visible today must stay visible, and a `false` backfill blanks the voter app.

**The problem this plan is built around.** Until 162-08 reads them, these columns are **inert**. No policy
consults them, no query filters on them, no assertion anywhere in the repository changes value depending on
them. A green E2E suite is therefore necessary and proves nothing: a column that nothing sets is
indistinguishable from a working one right up to the commit that starts reading it, at which point the
voter app renders empty and the cause is three plans back. So the evidence is not the suite. The evidence is
a census taken against a real `yarn db:reset-with-data` and a real `yarn db:seed --template e2e/base`,
asserted in both directions — every existing row `true`, every bare insert `false` — and **observed failing
first**, against the commit that declares the columns before the creation paths are wired.

**The third column is a repurpose, not an addition.** `elections.election_type` keeps its name and takes the
nomination shape (§ 8.2, D-16); its retired values leave the tree. That completeness claim is not made by a
grep — retyping the column to an enum makes every retired literal a compile error naming its own file, and
the grep is what confirms the compiler found them all.

**Output.** `open_for_voters` and `lock_nominations` on `projects`; `confirmed` on all four entity tables;
`election_type` as a three-member enum with its traces gone; the four creation paths that make the seeded
values true; `identity-callback` setting `confirmed` per D-10; `15-visibility-flags.test.sql`; a regenerated
`00001_initial_schema.sql` and `packages/supabase-types/`; and a wave-3 gate including the full E2E suite.
</objective>

## The design, settled before the first line of SQL

### What "backfilled `true`" means when there is nothing to backfill

This is the one place a reader could conclude the plan is doing what it was told not to, so it is settled
here rather than left to inference. `162-DISCUSSION-POINTS.md` D2 carries a free-text operator note in the
margin:

> **No backfills for any data**

and the standing convention is that free text beats a box. Taken alone it reads as a prohibition on exactly
what brief § 5 asks this plan for. It is not, and three documents say so in the same direction:

- **D-14 and brief § 10.2** remove the *reason* backfills existed: *"don't care about migrations, no
  supabase db has been published yet."* There are no deployed rows to transform, so the `ALTER`-plus-`UPDATE`
  migration D2's note is refusing has no subject.
- **Brief § 10.2 keeps the local half explicitly**: *"The one thing that does not change: backfills for the
  LOCAL database still matter, because `yarn db:reset` re-seeds from `seed.sql` and the E2E suite builds its
  own project. `open_for_voters` and `entities.confirmed` still need their seed-time values set (§ 11.2,
  162-07) — not to protect production rows, but so a reset local stack is not blank."*
- **D-19** restates it as a decision of its own.

**So the restatement is: a backfill against a deployed database is a one-shot script; against a declarative
schema it is the set of values the creation paths write.** 162-06 reached the same restatement for the
grant rows and resolved it by calling an idempotent function from the re-creation paths. This plan differs
from that one in a way worth stating rather than copying past: 162-06's rows were *derived* from other rows,
so a function was the right home for the derivation. These are three constants on four creation paths, with
no derivation to encode, so a function would be a layer over nothing. The mechanism here is the value at the
site — and the check is the same in both plans: a census against a rebuilt database.

**Where the values come from, path by path** (M5, M7):

| Path | Rows it produces | What it sets |
|---|---|---|
| `apps/supabase/supabase/seed.sql` | the default project; the seeded candidate | project open for voters; candidate confirmed |
| `SupabaseAdminClient.ensureProject` | the E2E project, and any project `yarn db:seed` targets | project open for voters, **including one it did not create** (M6) |
| `SupabaseAdminClient.bulkImport` | every entity row of all thirty templates | entity rows confirmed, unless the row says otherwise |
| `create_test_data()` | the pgTAP fixture's two projects and eight entities | A-true / B-false, mirroring M8's polarity |

`packages/dev-seed`'s generators are deliberately absent from that table. They emit rows; the client is what
supplies a column every row of a table should carry, which is where `published` already lives (M7) and where
a second copy of the same decision would be free to drift from the first.

### The three flags are not one decision, and the difference is the trap

They look alike — three booleans, all `NOT NULL DEFAULT false` — and two of them need a seeded value while
the third must not have one. The rule that separates them:

> A flag's **default** is the safe direction for a row nobody has spoken for. Its **seeded** value is today's
> behaviour. They need seeding exactly when those two differ.

| Flag | Safe default | Today's behaviour | Seeded? |
|---|---|---|---|
| `projects.open_for_voters` | closed — a project created this minute is not world-readable | every project is read anonymously today | **yes**, `true` |
| `entities.confirmed` | unconfirmed — nobody has vouched for this identity | every entity is visible today | **yes**, `true` |
| `projects.lock_nominations` | unlocked | nominations are admin-only to write, and § 3.3 grants admins `nomination.edit` unconditionally | **no** — the two coincide |

`lock_nominations` therefore **ships inert**, and this plan says so rather than implying activity it does not
have. Nothing reads it until 162-12 writes the entity-user nomination policies whose `own, unless locked`
cells are what it gates; nothing sets it; no behavioural assertion can observe it. Its claims here are
existence, type, `NOT NULL` and default. Declaring it now rather than in 162-12 is D-15's instruction and it
costs one line; pretending it is enforced would be the defect.

### Why the evidence is a census and not the suite

After this plan the three columns are **inert**: 162-08 writes the policies that read them, and until then no
query anywhere changes result depending on their value. Every gate in this repository would stay green
against a plan that declared the columns and wired nothing.

That is the same class of blindness `dev-seed`'s own comment records for `candidates` — *"A defect of that
shape can sit under a green suite indefinitely, because every other check in this repository reads as
service_role, which bypasses RLS entirely"* — and it is why the evidence is built the other way round:

1. **The seeded-true census**, taken against a database that has actually been rebuilt by
   `yarn db:reset-with-data` and again by `yarn db:seed --template e2e/base`: zero rows with the flag false,
   populations derived and printed, each floored above zero so a clean answer cannot come from an empty
   table.
2. **The default-false grid**, taken by inserting a row that names none of the flags and reading back what
   the column chose. The file says `DEFAULT false`; the assertion measures what PostgreSQL did.
3. **The observed red.** Task 3 commits the column declarations *before* the creation paths, runs the census,
   and records how many assertions fail. That number is the evidence. The green run that follows it is the
   consequence.

Three and one are different questions and both matter, because the two failures are opposite: a flag wrongly
`true` over-exposes a project nobody opened, and a flag wrongly `false` blanks an application that worked
yesterday. Only the second is loud, and only once 162-08 has landed.

### The repurposed column

`elections.election_type` keeps its name — the operator's § 8.2 note is explicit — and takes
`public.nomination_shape`, whose three members are `organization_only`, `candidate_only` and
`organization_list`. The type is named for what it holds rather than for the column that holds it, following
`role_scope_type`, which is the type of `user_roles.scope_type` and is named for the concept.

**`NOT NULL DEFAULT 'organization_list'`**, and the default is the operator's own reading — *"most or perhaps
all will be of the party list type"* — not a planner's. The nullable alternative buys an "unknown shape"
state that nothing in § 6.2's flow could act on, and would push a NULL branch into every consumer of a
setting whose whole purpose is to say which of three flows to run.

**The retired values become unrepresentable rather than merely unused.** They are not members of the type, so
a row carrying one is a PostgreSQL error, not a stored string. That is what makes the sweep's completeness a
property of the schema rather than of the diligence of a grep.

**The population is found by the compiler.** `TablesInsert<'elections'>['election_type']` becomes the enum,
so every retired literal in a `fixed[]` row is a TypeScript error naming its file and line. `yarn typecheck`
is the instrument; the run-time grep at Task 5 confirms it found them all and catches the traces that live
outside typed code — the README, the skill document, and the generator.

**Per-template shape is derived, not assumed.** The operator's note ends *"confirm per template rather than
assuming"*, so the rule is mechanical and reads each template's own nomination rows:

| What the template's nominations show for that election | Shape |
|---|---|
| an organization nomination **and** a candidate nomination naming it as parent | `organization_list` |
| candidate nominations only, none with a parent | `candidate_only` |
| organization, faction or alliance nominations only | `organization_only` |

A template no rule classifies halts the task naming the file. The derived table goes in the SUMMARY, because
§ 6.2 will read these values as flow selectors and a wrong one there is a wrong user journey.

**And the production read is decided rather than allowed to change meaning.** D-16 records the hazard
precisely: repurposing the column means `subtype` *"would start receiving nomination shapes"*. The term
reading `election_type` comes out of the elections mapping, leaving `subtype` carrying `elections.subtype`
and nothing else. The six adapter assertions that pinned the old mapping are rewritten, not deleted — they
are the only place in the repository that states what that mapping is.

### Where this plan stops

No policy is written. No index is added — the predicate that would justify one is 162-08's, and an index
chosen for a policy nobody has written is a guess recorded as a fact; the handoff is named in the SUMMARY
instead. `candidates.organization_id` is not touched, `published` is not touched, `elections.subtype` is not
dropped. `confirmed` is written by exactly one runtime path, `identity-callback`, because § 11.2's second
route needs columns brief § 6.1 owns.
