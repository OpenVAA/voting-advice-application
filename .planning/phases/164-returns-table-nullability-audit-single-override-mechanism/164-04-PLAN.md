<the_load_bearing_finding>
**The obvious framing of criterion 2 is wrong, and the plan must not repeat it.**

`164-RESEARCH.md` § R4 measured the decisive fact: **removing the runtime null-guard at
`supabaseDataProvider.ts:301` does NOT redden the unit suite.** For the root nomination
(`orgNomRow`, `parent_nomination_id: null`), deleting the `parentNominationId != null ?` ternary leaves
`nominationTypeById.get(null)`, and `Map.prototype.get` on an absent key returns `undefined`, and
`undefined ?? null` is `null`. The guarded and unguarded expressions produce the identical value. The
`:335` branch takes its `else` either way and `:317` yields `null` either way.

**The guard's live effect is type-level**, which is exactly what CIGATE-05 is about. Once
`parent_nomination_id` is `string | null`, removing the guard makes
`nominationTypeById.get(parentNominationId)` a compile error — TS2345, "Argument of type
`string | null` is not assignable to parameter of type `string`" — under `"strict": true`
(`packages/shared-config/tsconfig.base.json:15`).

So: **row `NC-1` (a typecheck under mutation) is the failure proof. The committed unit test from plan
`164-01` Task 3 is NOT.** A task worded "add a test that fails when the guard is removed", with no
typecheck instrument named, is the exact pitfall this ledger exists to avoid. Row `NC-2` records the
green honestly; recording it is what makes `NC-1`'s red mean something.

**One further measurement, taken during planning, that shapes `NC-3`:**
`packages/shared-config/eslint.config.mjs:39` extends `plugin:@typescript-eslint/recommended` — the
**non**-type-checked preset. `@typescript-eslint/no-unnecessary-condition` requires type information
and is not in that preset, so it is almost certainly **off**. That predicts `NC-3` goes **GREEN**: with
the override reverted, an un-overridden `string` type makes the guard dead-but-legal and nothing
flags it. **That green is the original defect, and it belongs in the record.** But the verdict must
still be **observed, not predicted** — confirm the rule's status by reading the config during the run
and record what the command actually printed (PROH-01).
</the_load_bearing_finding>
