## Decisions Made

**1. The `#supabase` read-back tag rides on `survey.linkTemplate`, not a bare `tag` key.** `157.2-RESEARCH.md` § "Interleaving A" sketches the fake resolving `{ data: { settings: { tag } } }` and asserting on `.tag`. That carrier does not survive the tree after Phase 157.1: `StoredSettingsSchema` is a `z.strictObject`, so a bare `tag` is an unrecognised top-level member, `parseWithPartialPreserve` refuses it and preserves nothing, and `.tag` comes back `undefined` for **both** requests — a vacuously passing GREEN and an ambiguously failing RED. `survey.linkTemplate` is a real optional string member that reaches `getAppSettings`'s caller unchanged. The apparatus exposes the same identity at three points (the client's `tag`, its `tables` call record, and the resolved payload) so plan 02 can assert on whichever reads most honestly. Recorded in the spec's own docstring.

**2. `obtain` takes a kind discriminator.** The two vectors need two different adapters — the provider for `#supabase`, the writer for `#fetch` through its inherited `clearIdToken`. A single seam covering both keeps the acceptance criterion's "exactly one function constructs or configures the adapter" literally true, with both singleton references confined to its one-expression body.

**3. Zone A's representative is a named file.** `ADAPTER_BOUNDARY_ALLOWLIST` names `src/lib/api/dataProvider.ts` by path rather than by glob, so a sibling virtual name in the same directory resolves to Zone B. Verified read-only against the real config: `dataProvider.ts` → 2, `lib/api/base/*` → 4, `lib/api/adapters/supabase/*` → 7, `adminWriter.ts` → 4. The transcribed counts are correct as written.

**4. Clause 2 is documented as a declaration ban, with research's reason.** The **D2** NOTE asked whether `init` is still a meaningful target after **B3**. The spec's docstring answers it: the bare `.init(` call form was measured firing on `userData.init(...)` and `store.init(d)`, two live in-tree sites unrelated to adapters, so it must not ship; the declaration form catches a reintroduced two-step protocol where it is written rather than where it is called, and that target is live forever. Fixture C7 pins the call form silent so plan 09 cannot reach for it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — missing critical functionality] The zone apparatus probes gained a positive control**

- **Found during:** Task 3.
- **Issue:** The plan's criterion asks each zone probe to resolve the real config and assert `no-restricted-syntax` is defined. That is necessary but not sufficient against the trap the plan itself names: *a fixture whose virtual `filePath` falls outside the base path returns zero messages, indistinguishable from a silent rule.* `calculateConfigForFile` can succeed for a path that no `files` glob actually matches, so the probe as specified would still let an out-of-scope fixture read as silence and would let a fabricated RED into ledger row 4.
- **Fix:** Each zone probe additionally lints an **already-inherited** violation (a TS enum, banned in all three zones) at that zone's virtual path and asserts it fires. Zero hits now means the path is out of scope, not that a rule is silent. The probe also asserts no fatal parse message and checks the zone's inherited-entry table length against its measured count.
- **Files modified:** `apps/frontend/src/lib/_guards/eslint-adapter-singleton-guard.test.ts`.
- **Verification:** All three probes pass; the fixture fires `const assertion` at each of the three zones.
- **Committed in:** `429d018df`.

**Total deviations:** 1 auto-fixed (Rule 2). **Impact:** strengthens the apparatus against the exact failure mode the plan's own objective calls out. No scope creep — still zero application source touched.

## Issues Encountered

**An acceptance criterion was unsatisfiable as literally written, and was resolved rather than worked around silently.**

Task 2's criterion is `grep -nE "setTimeout|setInterval|useFakeTimers|Promise\.race" …concurrency.test.ts` returns nothing. The same task's action mandates a top-of-file docstring recording *"the reason the ordering is deterministic"*, and the prohibition's own `verification` field says the ordering must come only from awaits. The natural way to write that paragraph is to name the constructs being excluded — which trips the grep on **prose**, not on a timing construct. Task 3's criterion has the same shape for both of its files.

**Resolution:** the docstrings state the prohibition without spelling the literal tokens ("no timer of any kind, no fake-timer harness, no promise-race, no zero-delay scheduling") and say explicitly *why* the literals are absent, so a future reader does not "helpfully" reinstate them and redden the check. All three files now satisfy the grep with exit 1 and still carry the required explanation. **The criterion's intent — no timing construct orders the two logical requests — holds; only its literal form needed the accommodation.** Plans 02, 06 and 09 inherit this constraint on these files.

Nothing else was unsatisfiable. Every other acceptance criterion was met as written.
