# Phase 157.2 Plan 06: Job-Owned Admin Writers Summary

Both long-running admin jobs now own one writer for the job's whole run, built from the initiating admin's
source alongside the data-loader that reads on the same credentials — and the cross-admin write that ruling
D11 names as its worst-consequence instance is a transcribed failure before the change and a transcribed pass
after it.

## What was built

**The measurement came first, and it could only be taken once.** Task 1 filled `157.2-01`'s two declared
`it.todo` cases and ran them against the jobs as they stood, with `adminWriter.init({ fetch })` still at
`condenseArguments.ts:44` and `generateQuestionInfo.ts:55`. The drive interleaves two real jobs — not
stand-ins: job A starts, runs synchronously into its own `await loadElectionData(…)` window and parks on the
gate; job B starts and runs its whole job inside that window, configuring the shared writer for its own admin
on the way; the gate opens and A resumes into its error path, where it makes `insertJobResult` — the first
writer call it makes after resuming, read out of the module rather than assumed.

Both cases failed, and failed for the right reason: `AssertionError`, at the isolation assertion's own line,
with the actual value `{ jobId: 'job-A', observedTag: 'B' }` — job A's own post-resume write reporting job B's
admin. The two driver assertions that precede it passed in the same run, which is what makes this a shared
writer observed rebinding rather than an apparatus that never interleaved. Repeated 3×, byte-identical.

**Then the fix.** Each job now takes `source: AdapterSource` instead of `fetch: Fetch`, and constructs
`createAdminWriter(source)` one line below the `PipelineController` — the same position and the same lifetime
as the controller, which was the idiom sitting immediately above the defect all along. Every writer use
through the loop and the error path resolves to that instance. `loadElectionData` takes the same `source` and
obtains its provider from `createDataProvider`, so a job's four parallel reads run on the credentials it will
write with. Both form actions pass `source: { fetch, locals }` in the same commit.

**Then the re-measurement.** Same command, character for character; exit 0; 3 passed; repeated 3×.

## How the job receives its client, and why

**Mechanism: the job receives `source: AdapterSource` and constructs its own writer.** Applied identically to
both jobs; they have been a matched pair since they were written and this plan leaves them that way.

The plan offered two consistent options. The reason for this one is that the job needs a client **twice** —
once for its writer and once for `loadElectionData` — and a constructed writer does not expose the source it
was built from. Handing down a writer would therefore have meant passing a second, independent source for the
reads, with nothing in the type system keeping the two aligned: exactly the divergence threat T-157.2-19
describes. One `source` parameter, two derivations from it, makes "reads under one identity, writes under
another" unexpressible at the call site rather than merely discouraged.

The form action's own writer (`157.2-04`'s, for the job record) is unaffected and still separate — it and the
job's writer are two instances built from the same request's source, which is what per-request instancing
means.
