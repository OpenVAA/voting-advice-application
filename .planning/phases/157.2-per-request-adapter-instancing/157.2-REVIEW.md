# Phase 157.2: Code Review Report

**Reviewed:** 2026-09-01T10:34:40Z
**Depth:** standard
**Files Reviewed:** 84
**Status:** issues_found

## Summary

The phase's core mechanism holds up under scrutiny: the four module-scope Supabase adapters are gone, `supabaseAdapterMixin` now takes its client through a `readonly #supabase` set in the constructor with no post-construction mutator, the four selector factories return a fresh instance per call, and `supabaseAdapter.concurrency.test.ts` is a genuinely deterministic negative control (every ordering constraint is an `await` on an externally-resolved promise; no timers, no races). The ESLint clause set fires on all seven measured evasion shapes and the three zone probes correctly guard against the "out-of-scope path reads as silent rule" failure mode. Svelte 5 context rules are respected in the changed components — `+layout.svelte` reads `appSettings` through a `$derived` alias rather than destructuring it, and `candidateContext` now hands the user-data store a *getter* rather than a captured writer instance.

That said, the phase did not eliminate shared state so much as relocate it, and it opened one authorization path that was previously dead:

1. **The admin API surface now authorizes on an unverified token.** Before this phase `getUserData({ fetch })` built an anonymous client, found no session, and every `/api/admin/jobs/**` request 403'd — the "admin outage" ruling D10 describes. The phase wired the real cookie-bearing client through, which makes the endpoints work *and* makes `_getBasicUserData`'s `getSession()` + `atob(...)` role decode load-bearing for the first time. `getSession()` performs no signature verification (`@supabase/auth-js` 2.99 even proxies `session.user` with an insecure-use warning), so the role claim is attacker-suppliable.
2. **A refresh token is now serialized into every SSR HTML payload** by the new root server load, in a field (`session`) that the root universal load deliberately does not forward and that nothing reads.
3. **Two module-level client memos remain**, and one of them silently discards the `global.fetch` its second caller supplies, so the tab's Supabase client ends up permanently bound to the root universal load's request-scoped `fetch`.

Findings below are ordered by severity. Line numbers are against the reviewed HEAD (`4925f2e81`).

## Critical Issues

### CR-01: Admin API endpoints authorize on an unverified, attacker-suppliable JWT

**File:** `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:155-178`
**Also:** `apps/frontend/src/lib/auth/getUserData.ts:28-33`, and all six endpoints — `routes/api/admin/jobs/start/+server.ts:19`, `.../active/+server.ts:17`, `.../past/+server.ts:19`, `.../abort-all/+server.ts:15`, `.../single/[jobId]/abort/+server.ts:11`, `.../single/[jobId]/progress/+server.ts:13`

**Issue:** `_getBasicUserData` derives the caller's role from `this.supabase.auth.getSession()` and then decodes the JWT body itself:

```ts
const { data: { session }, error } = await this.supabase.auth.getSession();
if (error || !session) throw new Error('No active session');
const payload = JSON.parse(atob(session.access_token.split('.')[1]));
const userRoles = payload.user_roles ?? [];
... role = 'admin';
```

`getSession()` does **not** verify the token. Verified against the installed `@supabase/auth-js@2.99.3`: `getSession → _useSession → __loadSession` reads the session straight out of the configured storage (here, the `sb-*` request cookies via `createServerClient`), checks only the *self-reported* `expires_at`, and wraps `session.user` in `insecureUserWarningProxy` precisely because the value is untrusted. No signature check occurs anywhere on that path.

Every admin endpoint gates purely on this value (`if ((await getUserData({ fetch, locals }))?.role !== 'admin') return 403`). An unauthenticated attacker can set an `sb-<ref>-auth-token` cookie in their own browser containing a base64 session blob whose `access_token` is a self-minted JWT with `{"user_roles":[{"role":"super_admin"}]}` and a future `expires_at`, and pass every one of those six checks. Consequences: start LLM jobs (unbounded OpenAI spend), abort any running job, and read the in-memory job store (`getActiveJobs()` / `getPastJobs()` / `getJob()` return `author` e-mail addresses, job inputs and pipeline messages). The DB writes the job later attempts are re-checked by PostgREST against the real signature and will fail — but only *after* the LLM work and the disclosure have happened.

Note the asymmetry that makes this a defect rather than a house style: the two admin *form actions* do it correctly — `admin/(protected)/argument-condensation/+page.server.ts:24` and `question-info/+page.server.ts:49` both call `locals.safeGetSession()`, which performs the `getUser()` network round-trip. The API endpoints do not.

**Fix:** Authorize on a verified identity in the endpoints, and stop using `getSession()` for any authorization decision:

```ts
// in each /api/admin/jobs/** endpoint
const { session, user } = await locals.safeGetSession();   // getSession() THEN getUser() — verified
if (!user) return json({ error: 'Forbidden' }, { status: 403 });
if (!hasAdminRole(session)) return json({ error: 'Forbidden' }, { status: 403 });
```

and in `_getBasicUserData`, replace the hand-rolled decode with the verifying API:

```ts
const { data: claims, error } = await this.supabase.auth.getClaims(); // asymmetric verification
if (error || !claims) throw new Error('No active session');
const userRoles: Array<{ role: Enums<'user_role_type'> }> = claims.claims.user_roles ?? [];
```

Add a spec that feeds a forged-but-unexpired session cookie to one endpoint and asserts 403.

### CR-02: The full Supabase session (access **and** refresh token) is serialized into every SSR HTML payload, unused

**File:** `apps/frontend/src/routes/+layout.server.ts:22-31`

**Issue:** The new root server load returns `{ session, supabaseCookies }`. `session` is the whole `Session` object from `locals.safeGetSession()` — `access_token`, **`refresh_token`**, `expires_at`, and the full `user` record. Everything a server load returns is serialized into the hydration payload in the HTML body, on every route in the app, for every authenticated user.

The file's long ⚠ comment reasons carefully about `supabaseCookies` and the `httpOnly` cookies it filters out — but it makes no claim at all about `session`, which is sitting next to it in the same return object and carries the same credentials. And `session` is **not consumed anywhere**: `routes/+layout.ts:40-47` explicitly does *not* forward it ("The session and the cookie array are deliberately NOT forwarded"), so a universal load that shadows this server load strips it from `page.data`; `authContext.svelte.ts:23` reads `page.data.session`, which is supplied by `routes/admin/+layout.server.ts:7-9` and `routes/candidate/+layout.server.ts:7-9`. Removing the field from the root load changes no behaviour.

The `refresh_token` is the higher-value credential of the pair: it is long-lived, it is *not* individually present in a JS-readable form otherwise beyond the same cookie, and it is now duplicated into a document body that can be captured by HTML/page caches, `view-source` sharing, DOM-snapshot error reporters (Sentry session replay et al.), and any HTML-level injection. `render.example.yaml` provisions a cache disk for this service, which makes cached authenticated HTML a live deployment shape rather than a hypothetical.

Independently, computing `session` costs a `getUser()` round-trip to Supabase Auth on every authenticated request for a value nobody reads.

**Fix:**

```ts
export async function load({ cookies }) {
  const requestCookies = cookies.getAll();
  const supabaseCookies: Array<UniversalCookie> = requestCookies
    .filter(({ name }) => name.startsWith(SUPABASE_COOKIE_PREFIX))
    .map(({ name, value }) => ({ name, value }));
  return { supabaseCookies };   // `session` removed: nothing reads it, and it carries the refresh token
}
```

If a future consumer needs the session at the root, return a projection (`{ userId, expiresAt }`), never the token-bearing object.

### CR-03: `session` and the cookie array are published app-wide, including on unauthenticated voter routes

**File:** `apps/frontend/src/routes/+layout.server.ts:26-31`, `apps/frontend/src/routes/(voters)/(located)/+layout.server.ts:20-25`

**Issue:** Related to CR-02 but distinct in scope, and it is what makes CR-02 worth fixing rather than accepting. The cookie array is emitted from the *root* server load — i.e. into the payload of every page in the application, including the entirely public voter routes (`/questions`, `/results`, `/nominations`), and again from the located voter subtree's own server load. Prior to this phase no page carried Supabase auth material in its HTML at all.

The justification given ("`@supabase/ssr` sets its own `sb-*` cookies `httpOnly: false`, so passing those through the payload discloses nothing that was not already JS-readable") is factually correct for the installed version — `node_modules/@supabase/ssr/dist/main/utils/constants.js:4-11` has `httpOnly: false` — but it is a *transitive* dependency on a third-party default. `lib/supabase/server.ts:16` spreads the library's options into `event.cookies.set(name, value, { ...options, path: '/' })`, so the day that default changes (or the day someone adds `httpOnly: true` to harden the cookie), the filter keeps forwarding the same names and quietly re-defeats the flag. The guard the file builds against a `cookieOptions.name` rename (`SUPABASE_COOKIE_PREFIX`) has no counterpart for this much more likely change.

Also note the prefix filter is a `startsWith('sb-')` on *all* request cookies, so any future application cookie whose name begins with `sb-` is forwarded to the client with no review.

**Fix:** Two changes, both cheap:

1. Assert the safety property instead of inheriting it. In `lib/supabase/server.ts`, pin the flag explicitly so the payload contract is local and visible:
   ```ts
   event.cookies.set(name, value, { ...options, httpOnly: false, path: '/' });
   ```
   and add a unit assertion that the forwarded set is `httpOnly: false`.
2. Narrow the filter from a prefix to the storage key actually in use (derive it from the project ref, or from `cookieOptions.name` when one is configured), so an unrelated `sb-`-prefixed cookie cannot join the payload by accident.

## Warnings

### WR-01: The browser Supabase client is memoized twice; the first caller's `global.fetch` wins and outlives its load

**File:** `apps/frontend/src/lib/supabase/universal.ts:46-49`, `apps/frontend/src/lib/supabase/browser.ts:5-15`

**Issue:** `createSupabaseUniversalClient`'s browser arm calls `createBrowserClient(url, key, { global: { fetch } })` directly rather than going through `createSupabaseBrowserClient()`. `@supabase/ssr@0.9.0`'s `createBrowserClient` keeps its *own* module-level cache (`let cachedBrowserClient`, `createBrowserClient.js:8-13`) and returns it on any subsequent call in a browser — **discarding the options of every caller after the first**.

The consequence is order-dependent and, after hydration, deterministic in the wrong direction: `routes/+layout.ts:21` runs first in the browser and creates the cached client with the *root universal load's* `fetch` (SvelteKit's load-scoped fetch, valid for that one load pass). Every subsequent `createSupabaseBrowserClient()` — i.e. every `prepareDataWriter()`, `prepareAdminWriter()` and `createFeedbackWriter({ browser: true })` call for the rest of the tab's life — gets that same instance, and therefore issues its network calls through a `fetch` belonging to a load that finished long ago. Meanwhile `browser.ts`'s own `browserClient` memo may never be populated at all, so the two memos disagree about which is authoritative.

This also makes two shipped docstrings wrong: `dataProvider.ts:27` says the browser arm's client "is the module-scope memo in `$lib/supabase/browser`" (it is the `@supabase/ssr` cache, which the browser module happens to also hit), and `universal.ts:35` says "There is no third arm and no fallback" while the browser arm silently inherits an unrelated caller's configuration.

**Fix:** Make the browser path single-sourced and stop passing a per-load `fetch` to a process-lifetime singleton:

```ts
// universal.ts
export function createSupabaseUniversalClient({ fetch, cookies }: { fetch: Fetch; cookies: Array<UniversalCookie> }) {
  // The browser client is a tab-lifetime singleton; it must NOT capture a load-scoped fetch.
  if (isBrowser()) return createSupabaseBrowserClient();
  return createServerClient<Database>(constants.PUBLIC_SUPABASE_URL, constants.PUBLIC_SUPABASE_ANON_KEY, {
    global: { fetch },
    cookies: { getAll: () => cookies }
  });
}
```

and delete the now-redundant `browserClient` memo in `browser.ts`, or keep it and add a comment recording that `@supabase/ssr` memoizes underneath it.

### WR-02: `resolveAdapterConfig`'s third arm is an unguarded `else`, not an exhaustive match

**File:** `apps/frontend/src/lib/api/dataProvider.ts:43-47`

**Issue:**

```ts
export function resolveAdapterConfig(source: AdapterSource): SupabaseAdapterConfig {
  if ('locals' in source) return { fetch: source.fetch, client: source.locals.supabase };
  if ('client' in source) return { fetch: source.fetch, client: source.client };
  return { fetch: source.fetch, client: createSupabaseBrowserClient() };
}
```

The module's own thesis (lines 19-21) is that "a caller that supplies none does not compile" and "a silent fallback ... is something this type cannot express". At runtime it is expressed right here: the `browser: true` discriminant is never tested. Any caller reaching this function without `locals` and without `client` — a `as AdapterSource` cast, a JS consumer, a source object built by spread where `client` came out `undefined` and the key was dropped, a future fourth arm added to the union without a matching branch — silently receives a browser client. On the server that is a *process-lifetime shared* client (`browser.ts`'s memo plus the `@supabase/ssr` cache), carrying whatever session the first caller established: the exact cross-request contamination shape the phase exists to remove, reintroduced one layer up from the code it deleted.

There is no live caller today, so this is defense-in-depth rather than an active bug — but the fix is two lines and the file spends 30 lines arguing that this state cannot exist.

**Fix:**

```ts
if ('browser' in source) return { fetch: source.fetch, client: createSupabaseBrowserClient() };
// Unreachable while `AdapterSource` has three arms; the throw is what keeps a fourth arm from
// silently falling into the browser client.
throw new Error('resolveAdapterConfig: no client source named. Pass { locals }, { client } or { browser: true }.');
```

### WR-03: `SupabaseAdapterConfig.locale` / `defaultLocale` are dead configuration that only tests can populate

**File:** `apps/frontend/src/lib/api/adapters/supabase/supabaseAdapter.type.ts:12-15`, `apps/frontend/src/lib/api/adapters/supabase/supabaseAdapter.ts:21-22,29-30,37-43`, `apps/frontend/src/lib/api/dataProvider.ts:43-47`

**Issue:** The mixin still reads `config.locale` and `config.defaultLocale` and exposes `get locale()` / `get defaultLocale()`, and the provider reads them at eight sites (`supabaseDataProvider.ts:144,183,237,260,296,300,317,503,546`). But `resolveAdapterConfig` — now the *only* construction path in the application — never sets either field. Verified by grep: outside `*.test.ts` there is no `new Supabase*(...)` anywhere and no call site passes `locale`. So in production `this.locale` is permanently `''` and `this.defaultLocale` is permanently `'en'`, on every adapter instance, forever.

Two consequences:

- The mixin's per-instance locale state, the two getters, and the two optional config members are dead surface that reads as live configuration. A future contributor will reasonably assume setting `locale` on the config works.
- `supabaseDataProvider.test.ts:206,313,365,396` construct a `fiProvider` from a `fiConfig` carrying `locale: 'fi'` and assert Finnish extraction — a configuration no production path can produce. The tests are green for a code path that never runs, which is exactly the kind of false confidence the phase's own ledger discipline is meant to prevent.

**Fix:** Pick one. Either wire it — extend `AdapterSource` with an optional `locale`/`defaultLocale` and forward it in `resolveAdapterConfig`, so the per-call `options.locale` becomes an override rather than the sole source — or delete it: drop the two members from `SupabaseAdapterConfig`, drop `#locale`/`#defaultLocale` and their getters from the mixin, make `options.locale` required on the read methods, and hard-code the `'en'` fallback where it is used.

### WR-05: Long-running admin jobs capture the request's `fetch` and cookie-bound client for the whole run

**File:** `apps/frontend/src/lib/server/admin/features/condenseArguments.ts:46,66-70`, `apps/frontend/src/lib/server/admin/features/generateQuestionInfo.ts:57,76-80`, called from `routes/admin/(protected)/argument-condensation/+page.server.ts:39-45` and `question-info/+page.server.ts:64-74`

**Issue:** The fix here is real — each job now builds one `adminWriter` and holds it, so a second admin can no longer rebind the first job's writer. But what the job holds is `source = { fetch, locals }`, i.e. `event.fetch` and `event.locals.supabase`, both of which are bound to a single HTTP request that the action `await`s for the job's entire multi-minute duration.

Two failure modes follow, and neither is guarded:

1. **Token refresh mid-job writes to a response nobody receives.** `locals.supabase` is the `createServerClient` from `lib/supabase/server.ts`, whose `setAll` calls `event.cookies.set`. If the access token expires during a long run, the refreshed session is written as a `Set-Cookie` on a response that is only generated when the job finishes — and if the platform's gateway has already timed out the connection (Render's default is 100s; these jobs are documented as running for minutes), the browser never receives it and the admin's session silently regresses to the pre-refresh tokens.
2. **After the response *is* generated, the same call throws.** `@sveltejs/kit`'s `respond.js:708-716` replaces `event.cookies.set` with a thrower (`Cannot use 'cookies.set(...)' after the response has been generated`) in a `finally` block. Any job path that outlives its response — an aborted job whose `insertJobResult` runs late, or a future move to fire-and-forget — will crash inside the Supabase client's refresh rather than at an obvious call site.

The phase summary records a "mid-job session-refresh deferral", so this is a known gap; it belongs in the review because the code carries no marker at the capture site and the next reader will not know it was deferred.

**Fix:** Decouple the job's credentials from the request lifecycle. At job start, resolve the verified session once and construct the job's client from the tokens (or from a service-role client scoped by the verified admin id), with a plain `fetch`:

```ts
const { session } = await locals.safeGetSession();
const jobClient = createSupabaseJobClient({ accessToken: session.access_token, refreshToken: session.refresh_token });
const adminWriter = createAdminWriter({ fetch: globalThis.fetch, client: jobClient });
```

At minimum, add a `// reason:` at the two capture sites naming the deferral and its symptom.

### WR-06: Storage object path is built from an unsanitized, attacker-supplied filename

**File:** `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:291-296` and `:351-357` (the same block, duplicated)

**Issue:**

```ts
const ext = file.name.split('.').pop() ?? 'jpg';
const storagePath = `${projectId}/candidates/${id}/${crypto.randomUUID()}.${ext}`;
```

`file.name` is fully controlled by the uploading candidate. `split('.').pop()` cannot yield a `..` segment (the result contains no dot by construction), so classic traversal is blocked — but it *can* contain `/`: a file named `a.b/c/d` yields `ext === "/d"` and a path of `…/<uuid>./d`, letting the uploader place objects at chosen sub-paths inside the prefix, and it can be arbitrarily long, contain control characters, `%`, `?`, `#`, or non-ASCII. Any storage RLS policy or later path parser written against the expected `<project>/candidates/<id>/<uuid>.<ext>` shape can be confused by that. The extension is also copied verbatim into the stored `{ path }`, which is later turned into a public URL by `parseImageColumn`/`storageUrl`.

**Fix:** Whitelist the extension rather than deriving it:

```ts
const ALLOWED_EXTENSIONS = new Set(['jpg', 'jpeg', 'png', 'webp', 'gif', 'avif']);
const raw = file.name.split('.').pop()?.toLowerCase() ?? '';
const ext = ALLOWED_EXTENSIONS.has(raw) ? raw : 'jpg';
```

and extract the whole upload block (it is byte-for-byte duplicated between `_setAnswers` and `_updateEntityProperties`) into one `#uploadCandidateFile({ id, file })` helper so the sanitizer cannot be applied to only one of the two copies.

### WR-09: `isEmpty` throws on an unexpected shape from inside a documented type guard

**File:** `apps/frontend/src/lib/api/utils/isValidResult.ts:52-58`

**Issue:** `isValidResult` is contracted as a boolean type guard ("returns `false` if it is invalid", "The boolean contract is unchanged for every input"), and callers use it that way with no `try`: `routes/+layout.svelte:73-79` inside a `$derived.by`, and `lib/admin/utils/loadElectionData.ts:49-52`. But its helper ends in `throw new Error('Unsupported data type')` for any result that is neither an array nor a non-null object. A provider that returns a string, a number, or `NaN`-shaped payload — reachable through the `as` casts at `loadElectionData.ts:46` and `+layout.svelte:79-83`, which assert `DPDataType` over values that came back from `.catch((e) => e)` chains — turns a validation call into an exception, and in `+layout.svelte` that exception is thrown from inside a `$derived` evaluation.

This directly contradicts the posture the phase adopts everywhere else (T-157-06: "one malformed row must not fail the read that contains it").

**Fix:**

```ts
function isEmpty(data: DPDataType[keyof DPDataType]): boolean {
  if (Array.isArray(data)) return data.length === 0;
  if (typeof data === 'object' && data !== null)
    return !Object.values(data).some((value) => value && Array.isArray(value) && value.length);
  return true;   // an unsupported shape is not a usable result; report it as empty rather than throwing
}
```

### WR-10: An unset `PUBLIC_LOG_LEVEL` emits an `error` record on every SSR boot and every browser page load

**File:** `apps/frontend/src/lib/utils/constants.ts:13`, `apps/frontend/src/lib/utils/logLevel.ts:50`, `apps/frontend/src/hooks.client.ts:14-19`, `apps/frontend/src/hooks.server.ts:22-27`

**Issue:** `constants.PUBLIC_LOG_LEVEL` coalesces an unset variable to `''`, and `resolveLogLevel` classifies `''` as `{ reason: 'missing' }`, which both entry points report at `log.error(...)`. The `.env.example`, `docker-compose.dev.yml` and `render.example.yaml` additions in this phase set it — but every existing deployment and every developer with a pre-existing `.env` will now emit an `error`-severity record naming a *default that is working as designed*.

On the server that is one line per process start (tolerable). In `hooks.client.ts` it runs in the **browser module graph**, i.e. once per full page load per visitor, at `error` level, in a codebase whose stated goal for this variable was to make production `error` records collectable and actionable. The first thing an operator will see in their new error stream is a constant, non-actionable "your optional variable is unset" — which is the noise floor that trains people to ignore the channel.

An absent optional variable with a documented default is an `info`-level fact; a *wrong* value is an `error`.

**Fix:** Split the levels by reason:

```ts
if (logLevelProblem) {
  const emit = logLevelProblem.reason === 'invalid' ? log.error : log.info;
  emit('PUBLIC_LOG_LEVEL is unusable; the logger fell back to a default level.', { ...logLevelProblem, level: logLevel });
}
```

(Byte-identical in both entry points, per decision C2.)
