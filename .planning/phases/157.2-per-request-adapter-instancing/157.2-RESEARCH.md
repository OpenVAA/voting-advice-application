## Summary

The phase is smaller than it looks in one dimension and larger in three others.

**Smaller:** the per-site edit is genuinely mechanical. Every one of the 18 production `init()` sites becomes
one line, and the four re-export selector modules are already the documented, ESLint-enforced import seam —
they can absorb the factory without a single import rewrite outside them.

**Larger, first:** the measured surface is **18** production `init()` call sites and **8** module-scope adapter
singletons, not 17 and 4. CONTEXT.md's fact 2 omits `lib/contexts/utils/prepareDataWriter.ts:17`, which is the
single busiest one — it re-`init()`s a shared writer on **every** browser write, from 19 call sites across four
contexts. Fact 1 counts only the Supabase four and misses two dead `apiRoute` singletons and two live-but-stateless
`server/api/adapters/local` ones. Each of those four extra singletons is a target of the D1 guard and needs an
explicit disposition, or `yarn lint:check` fails on files this phase never meant to touch.

**Larger, second:** the hard open question (Q2) resolves **against** the premise fact 5 rests on.
SvelteKit's request-scoped `fetch` forwards cookies **only to the app's own domain and its subdomains**
[CITED: svelte.dev/docs/kit/load], and Supabase is a different origin (`PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`
against a dev server on `:5173`, `*.supabase.co` in production). PostgREST authenticates on the `Authorization`
header supabase-js sets from its own storage, not on a cookie. So `fetch` alone **cannot** carry a session to
Supabase from a universal load's SSR pass, and the current plain-`createClient` branch at `supabaseAdapter.ts:39-44`
— whose in-code comment claims *"The fetch from SvelteKit includes cookies"* — is wrong on both halves. That
comment is the written form of D10's root cause. The working mechanism is the official `@supabase/ssr` SvelteKit
shape: a server load returns the cookie array (serializable), a universal load rebuilds a `createServerClient`
from it on the SSR pass and a `createBrowserClient` in the browser, and child universal loads take the finished
client from `await parent()` — legal because a universal load's return value is **not** serialized and may
carry class instances [CITED: svelte.dev/docs/kit/load].

**Larger, third:** the D1 guard collides with two live constraints that no upstream document names. The
adapter-boundary guard from Phase 157 bans `.supabase` member access outside an allowlist, and the allowlist
**omits `src/lib/api/adminWriter.ts`** — measured firing today where its three siblings are silent. And ESLint
flat config's per-file **REPLACE** semantics, which bit 157.1 hard, mean a naïve new `src/**` block would
silently delete between two and seven inherited `no-restricted-syntax` entries depending on the path, producing
**zero errors** while doing it. The measured per-path inventory is in § "The flat-config REPLACE problem".

**Primary recommendation:** make the factory's client source an **explicit, required argument with no
environment sniffing and no fallback** — that alone discharges A2's binding NOTE by *removing* the third branch
rather than documenting it — supply the three client sources as named helpers (`locals.supabase` for server
loads/actions/endpoints, an isomorphic `createSupabaseUniversalClient({ fetch, cookies })` for universal loads,
and the already-existing but currently **unused** memoized `createSupabaseBrowserClient()` at
`lib/supabase/browser.ts:11-15` for the browser), keep the four `$lib/api/*.ts` selector modules as the factory
locus so the `.supabase` reads stay inside the ESLint allowlist, and add the D1 guard by **spreading a shared
selector array into the three existing config blocks** rather than appending a fourth block.

## The five open questions, answered

### Q1 — The `.init(` clause's fate in the D1 guard **(the D2 NOTE)**

**Recommendation: keep both halves of D2(a) — the operator's tick stands — but re-express the second half as a
DECLARATION ban scoped to `src/lib/api/**`, not a call-site ban.**

This is a refinement of option (a), not an overrule of it, and it is the only form of the clause that is both
*live after B3* and *free of false positives*. Both are measured, not argued.

**Why the clause as literally worded cannot ship.** `no-restricted-syntax` is purely syntactic — there is no
scope analysis, and this repo has **no custom ESLint plugin** (`packages/shared-config/eslint.config.mjs:5-9`
loads only `@typescript-eslint`, `import`, `simple-import-sort` and `unused-imports`), so "on a module-scope
import" cannot be expressed. Executed against fixtures, the bare form
`CallExpression[callee.type='MemberExpression'][callee.property.name='init']` fires on **two live in-tree sites
that survive this phase untouched**:

- `routes/candidate/(protected)/+layout.svelte:120` — `untrack(() => userData.init(snapshot.userData))`, where `userData` is destructured from `getCandidateContext()` at `:32` and its `init` is declared at `lib/contexts/candidate/candidateUserDataState.svelte.ts:168` (`init = (data: CandidateUserData<true>): void => {`). Nothing to do with adapters.
- `lib/contexts/candidate/candidateUserDataState.svelte.test.ts:104` — `store.init(userData)`.

Shipping that clause means shipping two `eslint-disable` comments at sites the rule was never about, which
teaches the next reader that the rule is noise.

**Why "keep only the `new` clause" (the NOTE's second named resolution) is also wrong.** It concedes the exact
thing B3 cannot prevent forever. B3 deletes a *declaration*; nothing then stops a contributor re-adding
`init(config) { … }` to an adapter class next quarter, and the `new`-clause is silent on that.

**The measured alternative.** Ban the declaration where the declaration lived:

```
ClassBody > :matches(MethodDefinition, PropertyDefinition)[key.name='init']
```
scoped to `files: ['src/lib/api/**/*.{ts,js,mjs,cjs,svelte}']`.

Executed, 9 fixtures [VERIFIED: `ESLint.lintText` against an isolated flat config, 2026-08-31]:

| Fixture | Result |
|---|---|
| `abstract class A { init(c){…} }` (the `universalAdapter.ts:22` form) | **fires** |
| `class A { init = (c) => {…} }` (arrow-field form) | **fires** |
| `class A { async init(c){} }` | **fires** |
| `function mix(b){ abstract class W extends b { init(c){ super.init(c); } } return W; }` (the `supabaseAdapter.ts:27` mixin form) | **fires** |
| `class A { #init(c){} }` (private evasion) | **fires** |
| `class A { constructor(c){…} }` (the compliant target shape) | silent |
| `class A { initialise(c){} }` | silent |
| `function f(x){ x.init(1); }` (call site — out of clause scope by design) | silent |
| `export const o = { init(){} };` (object literal) | silent |

Zero false positives, and `candidateUserDataState.svelte.ts` is outside `src/lib/api/**`, so its legitimate
`init` field is untouched **by scope rather than by exemption**.

**What to write in the plan, verbatim as the answer the NOTE demands:** *the `.init(` half is kept, because the
protocol it guards against is exactly what B3 deleted and nothing else prevents its return; it is expressed as a
declaration ban rather than a call ban, because the call form is unexpressible without scope analysis this repo
has no plugin for, and because it was measured firing on two unrelated in-tree sites.*

### Q2 — ⚠ How the 6 universal-load sites reach a cookie-bearing client on the SSR pass

**Answer: `fetch` alone is NOT sufficient, and the tree's comment claiming otherwise is D10's root cause in
prose. The working mechanism is the official `@supabase/ssr` isomorphic-load shape, applied once at the root.**

**Why `fetch` fails — two independent reasons, both authoritative.**

1. **Cookies do not cross origins.** *"It can be used to make credentialed requests on the server, as it inherits the `cookie` and `authorization` headers for the page request"* — but *"if SvelteKit is serving my.domain.com: domain.com WILL NOT receive cookies; my.domain.com WILL receive cookies; sub.my.domain.com WILL receive cookies"* [CITED: svelte.dev/docs/kit/load]. `PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` (`.env:5`) against a dev server on `:5173`, and `*.supabase.co` in production. Neither is the app's domain or a subdomain of it.
2. **Even if they crossed, PostgREST would ignore them.** supabase-js authenticates by setting `Authorization: Bearer <access_token>` from its own storage. `createClient` on the server has no storage populated, so it sends the anon key. Overriding `global.fetch` (`supabaseAdapter.ts:42`) changes the transport, not the credential.

This is precisely `supabaseAdapter.ts:39-44` and its comment at `:40` — *"On the server (universal load
functions without serverClient), use plain createClient. The fetch from SvelteKit includes cookies."* — which
158 criterion 8 blames for the admin outage. **The comment is false on both clauses and must be deleted with the
branch, not carried forward.**

**The mechanism that works.** Two properties of SvelteKit make it possible, both quoted:

- **A universal load's return value is not serialized.** *"A universal `load` function can return an object containing any values, including things like custom classes and component constructors."* [CITED: svelte.dev/docs/kit/load] → **a Supabase client, or a whole adapter, may be returned from `+layout.ts`.**
- **A server load's return value must be.** *"A server `load` function must return data that can be serialized with devalue"* [CITED: svelte.dev/docs/kit/load] → **the client cannot cross the `+layout.server.ts` boundary; the cookie array can.**
- **`await parent()` reaches parent universal data.** *"In `+page.js` or `+layout.js` it will return data from parent `+layout.js` files."* [CITED: svelte.dev/docs/kit/load#Using-parent-data] → **children take the finished client from the root; only one site does the reconstruction.**

The official Supabase SvelteKit shape is exactly this [CITED: supabase.com/docs/guides/auth/server-side/sveltekit]:

```ts
// +layout.server.ts  — serializable
export const load = async ({ locals: { safeGetSession }, cookies }) => {
  const { session, user } = await safeGetSession();
  return { session, user, cookies: cookies.getAll() };
};

// +layout.ts — universal; returns a live client, which is legal here
const supabase = isBrowser()
  ? createBrowserClient(PUBLIC_SUPABASE_URL, PUBLIC_SUPABASE_ANON_KEY, { global: { fetch } })
  : createServerClient(PUBLIC_SUPABASE_URL, PUBLIC_SUPABASE_ANON_KEY, {
      global: { fetch },
      cookies: { getAll() { return data.cookies; } }
    });
```

`isBrowser` is exported by the installed package [VERIFIED: `node_modules/@supabase/ssr/dist/main/utils/helpers.js:29,66`].

**Four things the plan must get right, all measured:**

1. **A root `+layout.server.ts` does not exist and must be created.** `apps/frontend/src/routes/` has `+layout.ts` but no `+layout.server.ts`. `routes/admin/+layout.server.ts:7-9` and `routes/candidate/+layout.server.ts:7-9` exist and return `{ session }` — they are *not* ancestors of `routes/(voters)/**`.
2. **⚠ The shadowing trap.** *"a missing `+layout.js` is treated as a `({ data }) => data` function, meaning that it will also return data from parent `+layout.server.js` files that are **not 'shadowed' by a `+layout.js` file**"* [CITED: svelte.dev/docs/kit/load#Using-parent-data]. The root `+layout.ts` **exists**, so it shadows the new root `+layout.server.ts`: anything the new server load returns must be explicitly forwarded by `routes/+layout.ts`, or it vanishes for every descendant. This is the single most likely silent failure in the whole phase.
3. **⚠ Do not return `cookies.getAll()` verbatim — filter to the Supabase auth cookies.** `@supabase/ssr` sets `httpOnly: false` by default [VERIFIED: `node_modules/@supabase/ssr/dist/main/utils/constants.js:7`], so the `sb-*` cookies are already JS-readable and passing them through the payload discloses nothing new. **But `getAll()` also returns this app's genuinely `httpOnly` cookies** — `id_token` (`api/oidc/token/+server.ts:34,52`, `api/oidc/callback/+server.ts:87`), `oidc_state` / `oidc_nonce` (`api/oidc/authorize/+server.ts:28,37`), and the preregister cookies (`candidate/preregister/+layout.server.ts:45`, `api/candidate/preregister/+server.ts:44`). Serializing those into the HTML defeats their `httpOnly` flag outright. **Filter by name prefix, and say why in the comment.**
4. **Naming, to stay inside the ESLint boundary.** `MemberExpression[property.name='supabase']` fires on `data.supabase` exactly as it does on `locals.supabase` (measured — § "The flat-config REPLACE problem"). Do the read inside the allowlisted `$lib/api/*.ts` factory module (`createDataProvider({ fetch, parentData })`, `createDataProvider({ fetch, locals })`), not at the route. Renaming the key to dodge the selector would be "true by spelling, not by class" — the exact failure the D-rulings call out.

**Rejected alternatives.**
- **Convert the admin universal loads to server loads.** Would work and is smaller, but it is 158 criterion 8's job, it changes client-side navigation semantics for three routes, and A2(a) puts the *mechanism* in 157.2.
- **Return `session.access_token` and set an `Authorization` header.** Same disclosure surface as the cookie, but hand-rolls what `createServerClient` already does and loses refresh handling.
- **`AsyncLocalStorage`.** Explicitly rejected by B1(b); also would not help, since the browser half needs a second path regardless.

## Architecture Patterns

### System architecture — where a client comes from, per runtime

```
                          ┌──────────────────────────────────────────┐
  HTTP request  ─────────►│ hooks.server.ts : supabaseHandle (:36-58) │
                          │  createSupabaseServerClient(event)        │
                          │  → event.locals.supabase   (ONE per req)  │
                          └───────────────┬──────────────────────────┘
                                          │
        ┌─────────────────────────────────┼──────────────────────────────────┐
        │                                 │                                  │
        ▼ server load / action / endpoint ▼ root +layout.server.ts (NEW)      ▼ browser (post-hydration)
  locals.supabase                    returns { session,                  createSupabaseBrowserClient()
        │                              cookies: sb-* only }               (module-scope memo,
        │                                 │                                lib/supabase/browser.ts)
        │                                 ▼                                       │
        │                        routes/+layout.ts  (universal)                   │
        │                        isBrowser()                                      │
        │                          ? createBrowserClient(fetch) ◄─────────────────┘
        │                          : createServerClient(fetch, {cookies:data.cookies})
        │                                 │  returns the client (NOT serialized)
        │                                 ▼
        │                        await parent()  ──►  5 nested universal loads
        │                                 │
        └────────────┬────────────────────┘
                     ▼
     $lib/api/{dataProvider,dataWriter,adminWriter,feedbackWriter}.ts   ← the ONLY place `.supabase` is read
                     │   createDataProvider({ fetch, locals })      (server)
                     │   createDataProvider({ fetch, parentData })  (universal)
                     │   createDataProvider({ fetch })              (browser → memoized client)
                     ▼
       new SupabaseDataProvider(config)   ← fresh instance, no init(), no mutable rebind
                     │
                     ▼
       long-running admin job: receives the instance, OWNS it for the job (B4)
```

### Pattern 1 — Explicit client source, no environment sniffing

**What:** the factory's client is a *required* input; the factory never decides where a client comes from.
**When:** every one of the 18 sites.
**Why it discharges A2's binding NOTE:** the plain-`createClient` branch is **removed**, not documented — there
is no third branch left to be silent, because there is no branch at all. The environment check
(`else if (browser)` / `else`) at `supabaseAdapter.ts:31-44` disappears with it, and so does the
`'Supabase client not initialized. Call init() first.'` throw at `:51`, unreachable by construction.

For the one site that *wants* an anonymous client (`preregister/+layout.server.ts`, D-4), give it a **named**
helper — `createSupabaseAnonClient({ fetch })` in `lib/supabase/` — so the choice is a legible decision at the
call site with a comment, not a fallback. A named anonymous client is not a silent third branch; that
distinction is the whole content of the A2 NOTE, and the plan should say so explicitly.

### Pattern 2 — Type the factory, not the constructor

**Measured trap:** `supabaseAdapterMixin` is annotated `Constructor<SupabaseAdapter> & TBase` where
`Constructor<TClass> = abstract new (...args: Array<any>) => TClass` (`supabaseAdapter.ts:11`). None of the four
concrete classes declares its own constructor (`supabaseDataProvider.ts:106`, `supabaseDataWriter.ts:27`,
`supabaseAdminWriter.ts:41`, `supabaseFeedbackWriter.ts:11`). **So `new SupabaseDataProvider(anythingAtAll)`
will typecheck.** This is the same erasure the tree already documents at
`candidate/(protected)/+layout.server.ts:27-28` for the `init` override.

Two fixes, both cheap, and the plan should take **both**: declare an explicit
`constructor(config: SupabaseAdapterConfig)` on each concrete class (a subclass's own signature wins over the
mixin annotation), **and** put the authoritative typed signature on the factory in `$lib/api/*.ts`.

### Pattern 3 — Job-owned adapter

`condenseArguments` (`:44`) and `generateQuestionInfo` (`:55`) both take `{ fetch }` and `init` the shared
`adminWriter` once, then loop for minutes. Their callers **`await` them inline inside a form action**
(`argument-condensation/+page.server.ts:39`, `question-info/+page.server.ts:65`), so the request *is* the job's
lifetime. Shape: change the parameter from `fetch: Fetch` to the constructed writer (or to
`{ fetch, locals }` and build inside), and let the instance live in the function's closure for the whole loop.

### Anti-patterns to avoid

- **Renaming a key to dodge `MemberExpression[property.name='supabase']`.** Guard-evasion by spelling; the D-rulings name this exact failure ("true *by spelling*, not by class").
- **Appending a new ESLint block that sets `no-restricted-syntax` for `src/**`.** See § "The flat-config REPLACE problem" — it deletes inherited bans while producing zero errors.
- **Widening the change to `#locale` / `#defaultLocale`.** Fact 6, re-confirmed.
- **Touching `hooks.server.ts`.** Not required, and it would move 158's already-four-times-drifted anchors again (D-6).
- **Threading `serverClient` into `preregister/+layout.server.ts`.** Reverses a deliberate 157-16 decision and breaks that path's firing case in `eslint-adapter-boundary-guard.test.ts` (D-4).

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| Cookie-bearing client on a universal load's SSR pass | A bespoke token-forwarding header shim | `createServerClient(..., { cookies: { getAll: () => data.cookies } })` | The official `@supabase/ssr` SvelteKit shape; handles chunked auth cookies and refresh |

### Why this is deterministic, not a race

sequence `configure A → park A → configure B → complete B → resume A` is the program's control flow, not an
observed interleaving. **It fails on the singleton by construction**, which is what makes it a negative control
rather than a race that happened to lose — and it is why C1(b)'s Playwright variant was rejected against the
cardinal rule.

## Common Pitfalls

### P1 — The root `+layout.ts` shadows the new root `+layout.server.ts`
**What goes wrong:** the new server load returns `{ cookies }`, and every descendant sees nothing.
**Why:** *"a missing `+layout.js` is treated as a `({ data }) => data` function"* — the root `+layout.ts` **exists**, so it is not missing, and whatever it does not forward is lost [CITED: svelte.dev/docs/kit/load#Using-parent-data].
**Avoid:** have `routes/+layout.ts` explicitly return what descendants need.
**Warning sign:** the admin app works on client-side navigation and 403s on refresh — the same asymmetry 158 criterion 8 describes.

### P2 — Flat-config REPLACE silently deletes inherited bans
**What goes wrong:** the new guard fires 100 % on its own fixtures while two-to-seven other bans stop existing, with zero errors anywhere.
**Why:** later object wins, totally, per file, per rule. Measured in 157.1 (`157.1-NEGATIVE-CONTROL-LEDGER.md` row 7).
**Avoid:** spread into existing blocks (§ above). If not: re-include byte-identically **and** add one standing regression per entry.
**Warning sign:** `yarn lint:check` is *greener* after the edit than before.

### P3 — `serverClient` excess-property check / `any[]` constructor
**What goes wrong:** either the config object literal is rejected at the call site (today's problem, worked around with typed locals at `+layout.server.ts:29,71`), or — after B3 — **nothing is rejected at all**, because `Constructor<TClass> = abstract new (...args: Array<any>) => TClass` (`supabaseAdapter.ts:11`) erases every parameter type and no concrete class declares its own constructor.
**Avoid:** declare `constructor(config: SupabaseAdapterConfig)` on each concrete class *and* type the factory.
**Warning sign:** `new SupabaseDataProvider('nonsense')` compiles.

### P4 — `yarn test:unit` poisons the database between `db:reset` and `test:e2e`
**What goes wrong:** 4 deterministic E2E failures and 79 did-not-run, none caused by the code under test.
**Why:** `packages/dev-seed/tests/integration/default-template.integration.test.ts` is gated on `describe.skipIf(!process.env.SUPABASE_URL)`, so with Supabase up it seeds the **live** local DB and its teardown leaves 328 candidates, 377 nominations and a second election behind. Fully documented in `157.1/deferred-items.md` § OPEN.
**Avoid:** run **`yarn db:reset` immediately before the E2E half**, not once at the head of the chain (that document's option (c)). E2(a)'s ordering is otherwise unchanged.
**Warning sign:** the voter election combobox reads 2 where the spec expects 1.

### P5 — The adapter-boundary guard fires on new threading sites
**What goes wrong:** `yarn lint:check` fails on files the phase legitimately edited.
**Why:** `MemberExpression[property.name='supabase']` fires on `locals.supabase` **and** `data.supabase`, everywhere outside `ADAPTER_BOUNDARY_ALLOWLIST`. Measured: `src/lib/api/adminWriter.ts` is already outside it.
**Avoid:** do the `.supabase` read inside `$lib/api/*.ts`; add `adminWriter.ts` to the allowlist.
**Warning sign:** the urge to rename the key.

### P6 — Streamed promises outlive the load
**What goes wrong:** a per-request instance looks correct but the returned promise was created against a rebound singleton.
**Why:** `(located)/+layout.ts:102-112` and `nominations/+layout.ts:32-42` return unawaited promises (D-8).
**Avoid:** falls out of the factory; note it in the concurrency test docstring so the shape is on record.

### P7 — Session refresh inside a minutes-long job
**What goes wrong:** the admin's token expires mid-job; `createServerClient` attempts a refresh and calls `event.cookies.set` on a request whose response may already be committed.
**Why:** the job is `await`ed inline in a form action (`argument-condensation/+page.server.ts:39`).
**Avoid:** B4(b) explicitly declined to open this question. **Do not solve it here — log it as a deferred item** so it is not discovered as a surprise in 158.

### P8 — `assert:unit-coverage` and `assert:comment-hygiene`
Both run inside `yarn lint:check` (root `package.json:45`). The former requires any workspace containing test files to declare a `test:unit` script that turbo actually runs (`apps/frontend` already does). The latter is the wrapped-comment rule that cost 157.1 an extra commit (§ breadcrumb inventory).
