## The two declaration forms, and why the asymmetry is a measurement

The plan's text and the measurement agree, and the config now carries the reason:

- The **broad** form fires on the abstract base, on the mixin's inner class (whose name carries no adapter
  suffix), **and on the live `init` member of `candidateUserDataState.svelte.ts`** — a false positive.
- The **scoped** form is silent on the store and on the mixin's inner class.
- The abstract base and the store resolve to the **same** zone (B), so no block placement separates them.

Hence: scoped in all three blocks, broad confined to the adapter tree. The real-file probe over the store returns
**zero** guard messages, which is that false positive not happening.

**One consequence is a hole, and it is named rather than papered over.** Outside the adapter tree, a
configuration member on a class whose name lacks an adapter suffix is not caught. It is written into the config's
blind-spot comment as uncaught form 3 **and asserted** in the self-test — the five generic-named fixtures are
asserted SILENT at zones A and B, so the hole is a measured property that a future edit cannot quietly change.

## The manual observation decision A2(a) assigns here

**Method.** A temporary `super_admin` was created directly against the local stack (auth admin API plus one
`user_roles` row), logged in through the real `/admin/login` form action, and the admin app was then loaded **by
direct entry** and **by refresh**. The account and its role row were deleted afterwards; both leftover counts
verified **0**.

| Observation | Result |
|---|---|
| Unauthenticated direct entry, `GET /admin` | **307** → `/admin/login?errorMessage=loginFailed` — fails closed |
| Login via the admin form action | **200**, `{"type":"redirect","status":303,"location":".../admin"}`, session cookie set |
| **Authenticated direct entry**, `GET /admin` | **200**, 203 522 bytes, zero login-redirect markers in the SSR HTML |
| **Refresh**, the same `GET /admin` again | **200**, byte-identical size |
| **Refresh of a nested protected route**, `GET /admin/jobs` | **200** |
| `GET /api/admin/jobs/active` authenticated | **200**, body `[]` |
| `GET /api/admin/jobs/past` authenticated | **200**, body `[]` |
| The same two routes unauthenticated | **403** `{"error":"Forbidden"}` — still fails closed |

**The admin app is reachable on direct entry and on refresh, and the six `/api/admin/jobs/*` routes serve a
genuine admin.** Under ruling **D10** neither was true.

**The mechanism that explains it.** `admin/(protected)/+layout.ts` is a universal load with no `ssr = false`
anywhere under `routes/admin/`, so it runs on the server on direct entry and on refresh. It reads
`const { supabaseClient } = await parent()` and passes that client to `getUserData`. Before this phase the server
branch of the adapter built a plain `createClient` that never read the forwarded cookies, so `getUserData`
resolved `undefined` and the load redirected an authenticated admin to login. `157.2-03` made the root layout
supply a cookie-bearing client on the SSR pass and `157.2-02`'s factories take that client explicitly, with no
environment sniffing — so the client the load authorizes against now carries the request's own session. Per-request
instancing and the admin restoration are **the same fix**, which is the dependency the roadmap records between
157.2 and 158.

**No admin E2E spec was written.** `git diff --name-only HEAD -- tests` is empty for this phase. Decision **A2(a)**
assigns that proof to Phase 158's criterion 11; claiming it here would duplicate that criterion and assert a proof
this phase does not carry. What is recorded above is one manual observation and the mechanism — exactly what
`157.2-VALIDATION.md` § "Manual-Only Verifications" asks for.
