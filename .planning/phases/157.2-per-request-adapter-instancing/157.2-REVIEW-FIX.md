### CR-01: Admin API endpoints authorize on an unverified, attacker-suppliable JWT

**Files modified:** `apps/frontend/src/lib/server/admin/requireVerifiedAdmin.ts` (new), `apps/frontend/src/routes/api/admin/jobs/{start,active,past,abort-all}/+server.ts`, `apps/frontend/src/routes/api/admin/jobs/single/[jobId]/{abort,progress}/+server.ts`, `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts`, `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.test.ts`, `apps/frontend/src/routes/api/admin/jobs/adminJobsAuthorization.test.ts` (new)
**Commit:** `889b7d6ad`

**Applied fix — the USER-DIRECTED approach, not the report's `getClaims()` suggestion.** The two admin form actions (`argument-condensation/+page.server.ts:24`, `question-info/+page.server.ts:49`) already gate on `locals.safeGetSession()`, which is `hooks.server.ts:40-51` — `getSession()` followed by the verifying `getUser()` round-trip, returning `{ session: null, user: null }` when it errors. That same gate now runs on all six `/api/admin/jobs/**` endpoints, so the asymmetry inside the admin feature is closed and there is exactly ONE verification path in the codebase.

- Factored into `requireVerifiedAdmin({ fetch, locals })` rather than transcribed six times: six copies of a two-step check are six chances to keep only one of the steps. It returns the `Response` to send, or `undefined` for a verified admin.
- **The 403 shape and status for the role failure are unchanged** (`{ error: 'Forbidden' }`, 403). An unverified/absent session is a 401 `{ error: 'Unauthorized' }`.
- `_getBasicUserData` no longer leaves an unverified `getSession()` + `atob()` decode reachable as an authorization input: it now makes the `getUser()` round-trip FIRST, takes the returned (verified) `user` rather than `session.user` (which `@supabase/auth-js` wraps in its insecure-use proxy), and only then decodes `user_roles` from a token whose signature has been checked.
- `getClaims()` was deliberately NOT adopted, per the user's direction.

**Spec added (the review asked for this explicitly):** `adminJobsAuthorization.test.ts` drives the real `active/+server.ts` handler with a `locals` whose `safeGetSession` is transcribed byte-for-byte from `hooks.server.ts`, over a client stub that behaves as the real one does against a forged token — `getSession()` returns a well-formed, unexpired blob claiming `super_admin`, `getUser()` rejects it. Asserts 401 **and** that the job store (author e-mail addresses, inputs, pipeline messages) is never reached. Controls: a verified admin gets 200, a verified non-admin gets the unchanged 403, a request with no session gets 401. A matching adapter-level case asserts the forged token is rejected before `getSession()` is even called.
