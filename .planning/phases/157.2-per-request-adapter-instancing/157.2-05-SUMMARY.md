**Every browser write now runs on a writer that exists for that write and no longer — nineteen consumers plus the feedback sender converted to per-call factories over a Supabase browser client that is still created exactly once per tab.**

## Accomplishments

- **The busiest configuration site in the tree stopped configuring.** `prepareDataWriter` went from "take this shared writer, configure it, hand the same instance back" to "build one for this call". Its nineteen consumers across four context modules each now hold a writer for the duration of one method call.
- **The half-built decision B2(a) is finished.** `src/lib/supabase/browser.ts` — memoized since before this phase, with a docstring promising it was safe to call repeatedly, and imported by nothing — is finally what every browser adapter is built over. The client stays one per tab (one auth listener, one cookie sync) while the adapters around it became per-call, which is precisely the seam B2(a) chose.
- **A type that would have broken the build one wave later was fixed in the plan that owns it.** `adminContext.type.ts` imported the module singleton `adminWriter` AS A TYPE; `157.2-07` deletes that value. It now names `ReturnType<typeof createAdminWriter>`.
- **A bundle regression this plan introduced was caught by measurement and fixed inside the plan.** Sharing one module between both writer kinds put the admin writer on the root layout's graph, and therefore on every voter page. Splitting the admin factory into its own module removed it from node 0.

## Decisions Made

### Task 1's recorded decision, which Task 2 acted on

**The helper survives**, as two thin synchronous factory calls. The plan named the criterion — how many consumers would otherwise repeat the browser guard — and the answer is nineteen. Deleting the helper would have written `if (!browser) throw new Error('Writer methods in contexts can only be called in a browser environment')` into four context modules nineteen times. That guard is load-bearing twice over: it is the invariant that lets the `browser` arm of `AdapterSource` name the memoized client with no environment sniff inside the adapter, and `authContext.svelte.test.ts` mocks this module precisely because the real one throws off the browser.

Two zero-argument entry points rather than one factory-parameterised call, because the admin context uses both kinds and the plan warns that a swap between them would compile. With `prepareDataWriter()` and `prepareAdminWriter()` a swap does NOT compile: `prepareDataWriter().updateQuestion` does not exist.

### The admin context's writer-kind mapping

| Site | Writer kind | Reaches |
|---|---|---|
| `updateQuestion` | admin | `prepareAdminWriter()` |
| `insertJobResult` | admin | `prepareAdminWriter()` |
| `getActiveJobs`, `getPastJobs`, `startJob`, `getJobProgress`, `abortJob`, `abortAllJobs` | data | `prepareDataWriter()` |

### The two excluded `.init(` receivers

The plan's check excludes receivers named `userData` and `store`. Those are the candidate user-data store's OWN `init` method — `init = (data: CandidateUserData<true>) => { this.#savedData = data; }` — which loads the store with the candidate's already-fetched data. It shares nothing with the adapter protocol but the word. After this plan exactly one such call remains in the whole context tree (`candidateUserDataState.svelte.test.ts:102`), and the production call site inside `candidateContext` reaches it through `userData.init(...)`. Both are out of scope and untouched.

### `#dataWriter` became a getter rather than disappearing

The store held a writer INSTANCE in a private field for its whole lifetime — the exact shape the plan's second prohibition forbids ("MUST NOT cache the factory's result in a context field"). Two options existed: drop the parameter and import the factory directly, or narrow the parameter to a getter. The getter was chosen because it discharges the prohibition identically (a function is not an adapter) while keeping the constructor-injection seam that ten `save()` specs use to supply a fake writer, and because it matches the two sibling parameters that are already `() => boolean` and `() => string`. The spec change is one arrow: `dataWriter: fake.writer` became `dataWriter: () => fake.writer`.

The dependency direction costs the admin bundle nothing, because `adminContext` imports both modules anyway.

## Issues Encountered

**The typecheck gate returned in 8 milliseconds for 2711 files, which is not credible on its face.** Rather than accept it, a negative control was run in the same session: a temporary probe file asserting `const probe: AdminContext['updateQuestion'] = 42` made `svelte-check` report `1 ERRORS` with `Type 'number' is not assignable to type '(opts: SetQuestionOptions) => Promise<DataApiActionResult>'`, and the probe was then deleted. This proved two things at once — that the gate can fail, and that Task 3's `ReturnType<typeof createAdminWriter>` resolves to a real signature rather than silently degrading to `any`, which is the failure mode that would have made the whole task a no-op while every check stayed green.

**The `MUST NOT construct a second module-scope browser client` prohibition's verification text is stale, for a reason external to this plan, and it is recorded here rather than papered over.** It reads: *"`src/lib/supabase/browser.ts` still returns a module-scope cached client, and no other module under `apps/frontend/src` calls `createBrowserClient`."* The first clause holds — the file is untouched by this plan and still memoizes. The second clause does not, and did not before this plan started: `createBrowserClient` is also called by `src/lib/supabase/universal.ts:47` (created by `157.2-03`, per-pass by design for the universal load) and by `src/lib/api/adapters/supabase/supabaseAdapter.ts:34` (pre-existing, inside the adapter's own environment branch). **This plan added neither and constructed no client of any kind.** The prohibition's substance is satisfied.

**A related nuance in one of the plan's `truths`.** It states that *"there is no environment branch inside the adapter to decide it any more"*. The branch still EXISTS at `supabaseAdapter.ts:30-43`; what changed is that it is no longer REACHED from any converted site, because every one of them now supplies a `serverClient` through `resolveAdapterConfig`, which takes the first arm. Deleting the dead branch is `157.2-08`'s subject, and this plan's conversions are what make it dead.
