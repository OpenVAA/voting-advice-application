## Phase Boundary

**Retire the shared-mutable-adapter class: no adapter object outlives the request that configured it, and
prove it with a test that fails on the singleton before it passes on the fix.**

Four module-scope adapter singletons are each re-`init()`ed per request with an `await` before use. Two
concurrent requests can therefore be served each other's credentials and each other's data. The ruling is
explicit that **the deliverable is the proof, not the patch** — a concurrency test that FAILS on the
singleton first.

**Five deliverables:**

1. A per-call factory replaces the module singleton for all **4** adapters, at all **17** `init()` call sites
   (A1, B1).
2. `init()` is removed from the adapters, their abstracts and their interfaces; configuration moves to
   construction (B3 + its NOTE).
3. Every server-side site receives the request's **cookie-bearing** client — the one that already exists at
   `lib/supabase/server.ts` and already reaches `event.locals.supabase` — instead of the plain `createClient`
   fallback (A2, facts 9 + 10).
4. The two long-running admin jobs each construct and own an adapter for the job's lifetime (B4).
5. A deterministic concurrency unit test, RED-recorded then GREEN, plus an ESLint guard with a
   `_guards/*.test.ts` lock-in self-test (C1, C2, C3, D1, D2).

**Package reach.** `apps/frontend/src/lib/api/**` (the 4 `adapters/supabase/*/index.ts` singletons, the 4
`lib/api/*.ts` re-exports, `base/universalAdapter.ts`, `adapters/supabase/supabaseAdapter.ts` +
`.type.ts`), the 17 call sites listed in fact 2 (routes, universal loads, server loads, `lib/auth/`,
`lib/admin/`, `lib/server/admin/features/`, `lib/contexts/app/`), `apps/frontend/src/lib/supabase/server.ts`
+ `hooks.server.ts`, and `apps/frontend/src/lib/_guards/**` plus the ESLint config.

**Not in scope:**
- **The admin restoration itself and its E2E.** A2(a): 157.2 supplies the mechanism, **158 consumes it and
  proves it**. This phase does not add admin specs and does not touch the `/admin` route gate.
- **The parse posture.** That is Phase 157.1, which lands first.
- **Routing and auth *surface*.** Phase 158.
- **`AsyncLocalStorage` or any ambient request context.** B1 rejected it explicitly (fact 13).

## Implementation Decisions

All 15 decisions, resolved — every one on the `★ RECOMMENDED` option. `[✓★]` marks the two the operator
ticked to confirm. `[NOTE]` marks binding free text.

### 0.1 — Factual baseline · **(a)** `[★]`
Accept all 15 facts, restated below. Facts 2, 3, 5 and 8 are in neither the ruling nor the review, and each
changes either the size or the mechanism of the work.

### A1 ⚠ — How much of the 17-site surface is in scope · **(a) all 17 sites, all 4 singletons** `[★]`
Retire the class outright. The ruling's own words are that the deliverable is the class, not the patch, and
it names "two inline patches would close the instances and leave the class open" as the mistake to avoid.
The change at each site is mechanical once B1 is fixed.

**Rejected:** (b) server-reachable sites only (12 of 17) — leaves two idioms in the tree with no rule naming
which applies where. (c) the 3 instances the review named — leaves `routes/+layout.ts:18`, the
**every-SSR-request-for-every-page** one, untouched, which is indefensible once fact 3 is on the table.

### A2 ⚠ — Does 157.2 or 158 fix the plain-`createClient` server branch · **(a) 157.2 threads the client; 158 proves the restoration** `[★]`
`supabaseAdapter.ts:39-44` is simultaneously this phase's fallback branch and D10's root cause — the two
phases meet on one line. **157.2 threads the request's cookie-bearing client to every server-side site.
158 proves the admin restoration and adds the E2E.**

This is the split the rulings already assume, it puts the mechanism with the phase whose mechanism it is, and
it keeps 158 about routing and auth *surface* rather than adapter internals.

**[NOTE] — binding, and it is a hard exit condition.** *"whichever wins, the plain-`createClient` branch at
`:39-44` must end this phase either removed or documented as unreachable from a server request — a silent
third branch is what produced D10."* So the phase does not close while that branch still exists silently:
either it is deleted, or there is an explicit, tested statement in the tree that a server request cannot
reach it. "We stopped calling it" is not sufficient.

### B1 ⚠ — What replaces the module singleton · **(a) a per-call factory** `[★]`
`createDataProvider({ fetch, serverClient? })` (and the equivalent for the writer, adminWriter and
feedbackWriter) returning a **fresh instance**.

Fact 13 makes it sufficient: every one of the 17 sites already has a request-scoped `fetch` in hand, and the
2 server sites additionally have `locals.supabase` — so **no ambient context is needed anywhere**. Each site
becomes one line (`const p = createDataProvider({ fetch })`) replacing two (`import` + `.init(…)`), and the
shared mutable object simply stops existing.

**Rejected:** (b) `AsyncLocalStorage` — server-only (the browser needs a second path anyway), invisible
control flow, and SvelteKit universal loads straddle both runtimes. (c) pass the client per call — changes
the signature of every provider and writer method, a far larger diff than 17 sites. (d) keep the singleton
behind a lock — fixes correctness by removing concurrency, and the long-running admin jobs (facts 11, 12)
would hold the lock for minutes.

### B2 — The browser side · **(a) per-request adapters, module-scope memoized browser client** `[★]`
The adapter is cheap and per-call; the Supabase **browser client** is not — it owns auth listeners and cookie
sync, and one per tab is the shape `@supabase/ssr` expects. Memoize the underlying browser client at module
scope and construct adapters freely around it. This splits the two lifetimes at the right seam.

**Rejected:** (b) a fresh browser client per adapter — a new client and its listeners on every navigation that
runs a universal load. (c) a browser-scoped adapter singleton with a server-only factory — reintroduces the
two-idioms problem and forces D1's guard to carry an environment-aware exception.

### B3 — What happens to `init()` · **(a) remove it; the factory takes construction arguments** `[✓★ operator-confirmed]`
An object that cannot be re-configured after construction cannot be re-configured **mid-use**, which is the
defect. It also deletes the `'Supabase client not initialized'` throw at `supabaseAdapter.ts:51` as
unreachable-by-construction.

**[NOTE] — binding, and it widens the diff.** *"Also clean it from the abstacts and interfaces with no
historical mentions."* Removing `init()` from the four concrete adapters is not enough: it must also come out
of `base/universalAdapter.ts`, `adapters/supabase/supabaseAdapter.type.ts`, and any abstract class or
interface that declares it — **and the removal must be clean, leaving no "formerly `init()`" commentary,
deprecation note or historical breadcrumb behind.** The tree should read as though the two-step construction
protocol never existed.

### B4 — The two long-running admin jobs · **(a) each job constructs and owns its adapter for the job's lifetime** `[★]`
`condenseArguments.ts:44` and `generateQuestionInfo.ts:55` init the shared writer once and then run for
minutes across many questions (facts 11, 12), so the rebind window is not microseconds — it is the whole job.
Job-owned instances fall out of B1(a) for free, and it is the only option under which "the first job's writes
execute under the second admin's JWT" becomes **impossible** rather than unlikely.

**Rejected:** (b) re-derive per write — raises what a job should do when the initiating admin's session
expires mid-job, which is a question this phase need not open. (c) out of scope — leaves the
worst-consequence instance in the ruling untouched.

### C1 ⚠ — The shape of the concurrency test · **(a) a deterministic unit test against a fake client** `[★]`
A unit test that **interleaves two logical requests** against a fake client and asserts each sees only its own
credential. It must be written to **fail on the current singleton by construction** — the canonical
interleaving is: init A → yield → init B → resume A → observe B's client.

That determinism is the point: it makes the test a real negative control rather than a race that happens to
lose. Fact 15: nothing of this kind exists today, so the shape is a free choice and there is no precedent to
match.

**Rejected:** (b) a Playwright E2E with two overlapping authenticated sessions — closest to production and it
would have caught the real thing, but it is inherently timing-dependent, which collides head-on with the
cardinal rule's no-flaky-tests stance. (c) both — carries (b)'s flake risk into a suite that must stay green.
(d) a lint/type-level proof — proves the shape changed, never that the contamination stopped.

### C2 — Where the concurrency test lives · **(a) colocated: `adapters/supabase/*.concurrency.test.ts`** `[★]`
It is a **behavioural** test of the adapter, it runs in the existing `test:unit` gate, and colocation is the
repo's convention for adapter specs. `lib/_guards/` is for guard self-tests (does the rule fire) and putting
a behaviour test there would blur that directory's meaning — the guard self-test from D1 *does* belong in
`_guards/`, and keeping the two apart is deliberate.

### C3 — How the RED half is recorded · **(a) run the new test against the pre-change adapter, record the failure verbatim in the SUMMARY, then land the fix** `[★]`
The house RED→GREEN discipline. The recorded failure is what makes the GREEN meaningful.

**Rejected:** (b) a permanently-skipped singleton fixture — the control cannot rot, but it adds a skipped
test future readers must be told how to interpret. (c) GREEN only with the RED in prose — indistinguishable
from a test that never could fail.

### D1 ⚠ — What stops a new server-side singleton being added · **(a) ESLint rule + `_guards/*.test.ts` lock-in self-test** `[★]`
Fact 14: two precedents in this exact repo (`eslint-adapter-boundary-guard.test.ts`,
`eslint-store-guard.test.ts`), each linting virtual fixtures through the **real** config. It fires in the
editor and in `lint:check`, and the self-test proves the rule fires rather than assuming it.

**Rejected:** (b) a vitest source-scan — no editor feedback. (c) a type-level constraint (export only the
factories) — enforceable only if nothing else needs the class, which the tests do. (d) convention plus
review — zero mechanism; it is what was in place while three instances accumulated.

### D2 — What exactly is banned · **(a) module-scope `new` of an adapter class, plus any `.init(` on a module-scope import, in `apps/frontend/src/**`** `[✓★ operator-confirmed]`
Bans both halves of the shape: the shared object, and the re-configure-after-import that makes it dangerous.

**[NOTE] — binding, and it is a live question for the planner, not a rhetorical one.** *"Consider, tho,
whether init is a meaningful target after removing it from the types."*

The tension is real and must be resolved in the plan rather than deferred: B3 removes `init()` from the
adapters **and** their abstracts and interfaces, so after this phase there is no `init` to call on an adapter
and the `.init(` half of the rule has no live target — it would be a rule guarding against a method that no
longer exists. Two defensible resolutions, and research/planning must pick one and say why:

- **Keep both halves.** The `.init(` clause costs nothing, and it catches a future contributor
  *reintroducing* a two-step protocol — which is the failure mode B3 is structurally preventing but cannot
  prevent forever.
- **Keep only the module-scope `new` clause**, on the ground that B3 made the other half dead and a guard
  with a dead clause teaches the next reader that the clause is load-bearing when it is not.

What is **not** acceptable is shipping the `.init(` clause without a decision, or silently dropping it — the
operator asked the question and the plan owes it an answer with a reason. Note also that the ticked box is
option (a), i.e. the default is "keep both"; the NOTE licenses reconsidering it, it does not overrule it.

### E1 — Negative-control discipline · **(a) RED→GREEN per behaviour** `[★]`
The concurrency test, the guard self-test, **and each job-lifetime change** each get a recorded RED before
their GREEN. The milestone's stated non-negotiable, and the ruling names the proof as this phase's central
deliverable.

**Rejected:** (b) RED→GREEN for the concurrency test only — the guard then ships unproven, which is the exact
failure mode `_guards/` exists to prevent.

### E2 — The closing gate · **(a) full gate, single run** `[★]`
`yarn db:reset` first, then: **full E2E** + `build` + `lint` + `format` + `test:unit` + `svelte-check` +
pgTAP.

17 call sites across routes, loads and server features is exactly the diff shape where `svelte-check` earned
its place in Phase 157. The DB prerequisite is **`db:reset`**, *not* `db:reset-with-data`.

Not chosen: (b) a 3× E2E determinism run — the discussion acknowledged this is the highest-blast-radius
change in the milestone so far and that three runs would catch an intermittent a single run cannot, but the
recommendation stands at a single run. **If the single run surfaces any intermittent, escalate to the 3×
determinism run rather than re-running until green** — a retry-until-green is a cardinal-rule violation.

### E3 — Sequencing · **(a) strictly after 157.1, strictly before 158, one phase per wave** `[★]`
157.1 changes what the parse helpers return at the same call sites this phase re-scopes; doing them in one
wave would put two large diffs on the same lines behind one gate. 158's A1 then consumes this phase's
mechanism.

**Rejected:** (b) parallel with 157.1 on separate branches — guarantees a merge conflict on
`supabaseDataProvider.ts` and `parseJsonbColumn.ts`, and neither phase's gate would measure the other's
change. (c) before 157.1 — costs re-touching every call site again, and 157.1's parse outcomes would be
designed against a moving adapter shape.

### OPERATOR RULING 2026-08-31 — `/api/auth/login` is deleted by 157.2, verified by 158

Research question 3 asked which phase removes `apps/frontend/src/routes/api/auth/login/+server.ts`.
Measured: the route has **zero callers**. The only references are two comments — in
`candidate/login/+page.server.ts:4` and `admin/login/+page.server.ts:4` — each explaining that the login
form action deliberately uses `event.locals.supabase` directly *instead of* this route, because a nested

Decision **B3** removes `init()` everywhere, and this route is one of the sites, so "leave it untouched" was
never actually on the table. **The operator ruled: 157.2 DELETES it.** Phase 158's decision **A4** changes
from *perform the deletion* to *verify it is gone* — 158 must not re-plan a removal that has already happened.

The deletion is a phase deliverable and carries the same evidentiary discipline as the rest: record that the
route had no callers before removing it, so the record shows a dead endpoint was retired rather than a live
one broken.

## Open Questions — not settled by the discussion

1. **The `.init(` clause's fate in the D1 guard** (D2 NOTE). Explicitly handed to planning with two named
   defensible answers and a requirement to pick one with a reason. See D2 above.

2. **How the 6 universal-load sites reach a cookie-bearing client on the SSR pass.** Fact 13 says universal
   loads have `fetch` but no `event`; fact 10 says the correct client lives on `event.locals`. On the server
   pass of a universal load, `event.locals.supabase` is not directly in scope — SvelteKit's usual answer is
   for a `+layout.server.ts` to pass it down through `data`. **Whether the 6 universal-load sites need only
   `fetch` (because their requests are cookie-forwarding anyway, per fact 5) or genuinely need the
   `serverClient` threaded through server `load` data is the single largest unknown in this phase** and must
   be settled by research before any plan commits to a call-site shape.

3. **What happens to `api/auth/login/+server.ts:20`.** It is one of the 17 sites, and Phase 158's A4
   (per the 158 addendum) proposes **deleting** that route as a dead credential oracle. Confirm whether this
   phase converts it or whether it is about to be removed — converting a route 158 deletes is wasted work,
   and deleting it here would take scope from 158.

4. **Whether the 4 `lib/api/*.ts` re-export modules survive.** They are one-line re-exports of the four
   singletons (fact 1). Under B1(a) there is no singleton to re-export; the modules either become factory
   re-exports or disappear. Either is fine, but the choice affects roughly 17 import statements and should be
   made once.

5. **`lib/contexts/app/appContext.svelte.ts:297`** is a browser-side context site, not a request. Its
   lifetime under B2(a) (per-request adapters, memoized browser client) needs an explicit answer — an
   "adapter per request" framing does not obviously map onto a long-lived Svelte context.
