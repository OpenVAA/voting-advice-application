# Phase 157.2 Plan 03: The Universal Loads Summary

**Every universal load in the application now holds its own adapter over a client that carries the request's session — and the mechanism the plan specified for getting that client turned out to serialise the voter app's hottest load behind the root's four round-trips, which a single un-retried `requestAnimationFrame` converted into a real WCAG failure; that was bisected to one file, ruled on, and replaced with a per-subtree cookie source.**

## Accomplishments

- **The `httpOnly` prohibition is discharged by OBSERVATION, with a positive control, at BOTH server-load boundaries.** A located voter page rendered with `id_token`, `oidc_state`, `oidc_nonce`, `oidc_code_verifier` and one `sb-`-prefixed sentinel all present yields two payload blocks — `{session:null,supabaseCookies:[{name:"sb-probe-auth-token",value:"SBSENTINELb4d2e1f7"}]}` from the root and `{supabaseCookies:[…same…]}` from the located subtree. The `sb-` sentinel occurs **2×** (once per block, which is what proves the payload genuinely carries the array and that the grep would have found the others); the four `httpOnly` sentinels occur **0×**. This is measured on a rendered page, not read off the filter's source.
- **The filter derives from `SUPABASE_COOKIE_PREFIX` at both sites, and no bare cookie-name literal appears in either server load.** One declaration (`lib/supabase/universal.ts:13`), one seam re-export, two imports, two uses. A `cookieOptions.name` change now moves one name and both arrays follow it, instead of one array emptying silently into an anonymous client that raises no error.
- **The shadowing trap is closed and PROVED closed by type, not by inspection.** A throwaway probe destructuring a non-forwarded key from `await parent()` fails `svelte-check` with *"Property 'supabaseClientNOTFORWARDED' does not exist on type 'LayoutParentData'"* — so `LayoutParentData` really is derived from the root's explicit return, and a forgotten forward surfaces at typecheck rather than as a 403-on-refresh.
- **The six `api/admin/jobs` endpoints were asking an ANONYMOUS client who the user is.** They called `getUserData({ fetch })` with no client at all; `_getBasicUserData` reads `supabase.auth.getSession()`, which on a bare-`fetch` client returns nothing, throws *"No active session"*, and is caught into `undefined` — a 403. They worked only because the module-scope writer singleton had usually been configured with a real client by some earlier request. That is ruling **D10**'s shape exactly, found in the tree rather than in the plan, and now fixed: all six pass `{ fetch, locals }`.
- **`hooks.server.ts` was not touched.** `git diff --name-only HEAD -- apps/frontend/src/hooks.server.ts` is empty; Phase 158's anchors did not move a fifth time. No new `+layout.server.ts` exists beneath `routes/admin/`, and the three admin files remain `+layout.ts`.
- **The full E2E suite is genuinely green: 150 passed, 0 failed, 0 did-not-run, exit 0** (10.6 min), with `db:reset` run immediately before the suite and a fresh dev server, and with `a11y-smoke.spec.ts:300` (NAVA11Y-02) executing as test 22/150 rather than being skipped.

## The regression, the bisect, and the ruling

Task 3 as written took the client from `await parent()` in all five nested loads. That produced a **deterministic** failure of `tests/tests/specs/a11y/a11y-smoke.spec.ts:300 — navigation-a11y — focus lands on heading after Q→Q nav` (NAVA11Y-02): 149 passed / 1 failed on the full suite, and 1 failed / 2 passed in isolation.

**Bisected across this plan's own commits before proposing anything:**

| Tree | Result |
|---|---|
| `1b37af2b0` (plan parent) | 3 passed |
| `7486481bf` (tasks 1+2) | 3 passed |
| `b395c56c7` (task 3) | **1 failed** |
| `b395c56c7`, only `(voters)/(located)/+layout.ts` reverted | 3 passed |

**Mechanism.** `(located)/+layout.ts` previously called `parent()` *only* when election/constituency ids were absent, so on the hot path it awaited nothing and its `getQuestionData` / `getNominationData` ran **in parallel with the root load's four Supabase round-trips**. Taking the client from `parent()` blocks those calls until the root load returns, so they are still in flight when navigation completes. The root layout's focus reset (`routes/+layout.svelte:149-157`) then runs inside a **single** `requestAnimationFrame`, finds neither `[data-focus-on-nav]` nor an `<h1>` — the question heading renders from `voterCtx` once `questionData` resolves — calls `target?.focus()` on `undefined`, and **never retries**. Focus never arrives; the Playwright poll times out because focus is absent, not late. This is a user-facing WCAG regression on every cold entry to a question route, not a test artefact.

**The operator ruled option (a+)** and independently verified the diagnosis. `await parent()` is abandoned wherever it would newly serialise a load: the subtree gets its own `+layout.server.ts` returning the same prefix-filtered array, and the universal load builds its own client from its **own** `data`, which is available with no `parent()` dependency. The accepted cost is that the isomorphic client is reconstructed **once per server-load boundary** rather than once per request. Option (c) — streaming the root load's datasets, which would preserve both single construction and parallelism — is **deferred, not rejected**, and is filed at `.planning/todos/pending/2026-09-01-spike-streamed-root-load-ssr-parallelism.md` for a spike at v2.15 close. `routes/+layout.svelte` was left alone by instruction; the un-retried focus reset is a latent fragility that a different latency shift would expose again, and it is recorded in that todo.

The `must_haves` truth *"The five nested universal loads take the finished client from `await parent()`, so the reconstruction happens once rather than six times"* was **amended in place** in `157.2-03-PLAN.md` to state what is now true. **This was an operator ruling, not executor drift.**

## Derivations recorded because no in-tree analog exists

**The root server-load payload shape: `{ session, supabaseCookies }`.** PATTERNS flagged that no in-tree server load returns a cookie array, so the shape was derived from the mechanism rather than copied. `createServerClient`'s cookie adapter calls `getAll()` and reads only `name` and `value`; the options a cookie was *written* with (`httpOnly`, `secure`, `sameSite`, `maxAge`) are meaningless on the read side, so they are dropped rather than serialised — which also shrinks the payload's disclosure surface to the minimum the mechanism needs. `session` goes through `locals.safeGetSession()` so the existing `getSession()`-then-`getUser()` verification is not bypassed by a cheaper read. The key is `supabaseCookies` rather than `cookies` so it cannot be misread as the request's whole jar. `(voters)/(located)/+layout.server.ts` returns the cookie half only; it has no use for a session.

**No development-mode warning about the returned live client appeared.** Research flagged this as an unverified assumption. `yarn dev` logs across four separate server starts contain nothing about serialisation, devalue, or non-POJO return values — only a pre-existing `Cannot find base config file "./.svelte-kit/tsconfig.json"` and the pre-existing `svelte-visibility-change` exports-condition warning.
