## A. Scope boundary ⚠

### A1 ⚠ DECIDE — How much of the 17-site surface is in scope?

Fact 2: the ruling's "three instances" is an undercount of a 17-site surface across 4 singletons. Fact 3:
the widest site is the root universal load, which nobody named.

- [ ] **(a) All 17 sites, all 4 singletons — retire the shared-mutable-adapter class outright** —
      ★ RECOMMENDED — the ruling's own words are that the deliverable is the class, not the patch, and it
      names "two inline patches would close the instances and leave the class open" as the mistake to avoid.
      The change at each site is mechanical once B1 is fixed.
- [ ] **(b) Server-reachable sites only** (the 6 `*.server.ts` / `+server.ts` / `lib/server/**` sites plus the
      6 universal loads that also run on the server) — 12 of 17, skipping the browser-only ones. Smaller, and
      the browser genuinely has one module graph per user; but it leaves two idioms in the tree with no rule
      naming which applies where.
- [ ] **(c) The 3 instances the review named** — smallest diff, matches the ruling's letter. Leaves
      `routes/+layout.ts:18` — the every-SSR-request one — untouched, which is hard to defend once fact 3 is
      on the table.

### A2 ⚠ DECIDE — Does this phase fix the plain-`createClient` server branch, or does 158?

Facts 9 and 10: `supabaseAdapter.ts:39-44` is simultaneously this phase's fallback branch and D10's
root cause. The two phases meet on one line.

- [ ] **(a) 157.2 threads the request's cookie-bearing client to every server-side site; 158 proves the admin
      restoration and adds the E2E** — ★ RECOMMENDED — it is the split the rulings already assume ("157.2
      supplies the fix and 158 consumes it and proves it"), it puts the mechanism with the phase whose
      mechanism it is, and it keeps 158 about routing and auth *surface* rather than adapter internals.
- [ ] **(b) 157.2 does concurrency only; 158 fixes the client branch** — cleaner one-idea-per-phase framing.
      But 158 then has to re-derive the per-request threading 157.2 just built, on the same lines, one phase
      later — and the admin outage stays live through an extra phase.
- [ ] **(c) 157.2 does both, including the admin restoration and its E2E** — closes the outage soonest;
      absorbs a chunk of 158 and makes this phase two phases wearing one name.

**NOTE:** whichever wins, the plain-`createClient` branch at `:39-44` must end this phase either removed or
documented as unreachable from a server request — a silent third branch is what produced D10.

## B. Mechanism ⚠

### B1 ⚠ DECIDE — What replaces the module singleton?

- [ ] **(a) A per-call factory — `createDataProvider({ fetch, serverClient? })` returning a fresh instance** —
      ★ RECOMMENDED — fact 13 makes it sufficient: every one of the 17 sites already has a request-scoped
      `fetch` in hand, and the 2 server sites additionally have `locals.supabase`, so no ambient context is
      needed anywhere. Each site becomes one line (`const p = createDataProvider({ fetch })`) replacing two
      (`import` + `.init(…)`), and the shared mutable object simply stops existing.
- [ ] **(b) `AsyncLocalStorage` request context on the server** — keeps call sites untouched and is the
      canonical Node answer. It is server-only (the browser needs a second path anyway), it is invisible
      control flow, and SvelteKit universal loads straddle both runtimes — so it buys ambient plumbing this
      codebase does not otherwise need.
- [ ] **(c) Pass the client per call rather than per instance** — `getQuestionData({ supabase, … })`. No
      lifetime questions at all; changes the signature of every provider and writer method, which is a far
      larger diff than 17 sites.
- [ ] **(d) Keep the singleton, serialise access with a lock/queue** — smallest diff. Turns concurrent
      requests into a queue behind one adapter, i.e. it fixes correctness by removing concurrency, and the
      long-running admin jobs (facts 11, 12) would hold the lock for minutes.

### B2 — What happens on the browser side?

Under B1(a), a naive factory calls `createBrowserClient` per load, and the browser client owns auth
listeners and cookie sync.

- [ ] **(a) Per-request adapter instances, but memoize the underlying browser client at module scope** —
      ★ RECOMMENDED — the adapter is cheap and per-call; the Supabase browser client is not, and one per tab
      is the shape `@supabase/ssr` expects. Splits the two lifetimes at the right seam.
- [ ] **(b) Fresh browser client per adapter too** — one rule everywhere, no memoization to reason about;
      costs a new client (and its listeners) on every navigation that runs a universal load.
- [ ] **(c) Keep a browser-scoped adapter singleton, factory on the server only** — least browser churn;
      reintroduces the two-idioms problem A1(b) has, and the guard in D1 then needs an environment-aware
      exception.

### B3 — What happens to `init()`?

- [x] **(a) Remove `init()` from the adapters; the factory takes the config as constructor arguments** —
      ★ RECOMMENDED — an object that cannot be re-configured after construction cannot be re-configured
      *mid-use*, which is the defect. It also deletes the `'Supabase client not initialized'` throw at
      `supabaseAdapter.ts:51` as unreachable-by-construction.
- [ ] **(b) Keep `init()` but make a second call throw** — smaller diff, and it fails loudly on the exact
      misuse. Leaves a two-step construction protocol whose only correct use is "immediately after `new`".
- [ ] **(c) Keep `init()` as-is on the new instances** — no change to any signature; also no structural reason
      the class cannot come back, since a fresh instance can still be re-init'ed by a future caller.

**NOTE**: Also clean it from the abstacts and interfaces with no historical mentions.

### B4 — What about the two long-running admin jobs?

Facts 11 and 12: `condenseArguments` and `generateQuestionInfo` init once and then run for minutes.

- [ ] **(a) Each job constructs and owns its own adapter for the job's lifetime** — ★ RECOMMENDED — falls out
      of B1(a) for free, and it is the only option under which "the first job's writes execute under the
      second admin's JWT" becomes impossible rather than unlikely.
- [ ] **(b) Each job re-derives the adapter per write** — freshest credentials at every write; more churn, and
      it raises the question of what a job should do when the initiating admin's session expires mid-job.
- [ ] **(c) Out of scope; jobs keep the shared writer** — leaves the worst-consequence instance in the ruling
      untouched.

## C. The proof ⚠

The ruling is explicit that the deliverable is the failing-then-passing test, not the patch.

### C1 ⚠ DECIDE — What shape is the concurrency test?

Fact 15: nothing of this kind exists today, so the shape is a free choice.

- [ ] **(a) A unit test that interleaves two logical requests against a fake client, asserting each sees only
      its own credential** — ★ RECOMMENDED — deterministic, fast, and it can be written to **fail on the
      current singleton** by construction (init A → yield → init B → resume A → observe B's client). That
      determinism is what makes it a real negative control rather than a race that happens to lose.
- [ ] **(b) A Playwright E2E issuing two overlapping authenticated requests as different candidates** —
      closest to production, and it would have caught the real thing. Inherently timing-dependent, which
      collides with the cardinal rule's no-flaky-tests stance.
- [ ] **(c) Both — unit for the gate, E2E for the end-to-end claim** — strongest evidence; the E2E half
      carries the flake risk of (b) into a suite that must stay green.
- [ ] **(d) A type-level or lint-level proof only** — cheap; proves the shape changed, never that the
      contamination stopped.

### C2 — Where does the concurrency test live?

- [ ] **(a) Colocated with the adapter, `adapters/supabase/*.concurrency.test.ts`** — ★ RECOMMENDED — it is a
      behavioural test of the adapter, it runs in the existing `test:unit` gate, and colocation is the
      repo's convention for adapter specs.
- [ ] **(b) In `lib/_guards/`** — groups it with the other lock-in specs; `_guards/` is for *guard* self-tests
      (does the rule fire), and this is a behaviour test, so it would blur that directory's meaning.
- [ ] **(c) A new `tests/concurrency/` tree** — visible and self-describing; a new top-level tree for one spec.

### C3 — How is the RED half recorded?

- [ ] **(a) Run the new test against the pre-change adapter, record the failure verbatim in the plan SUMMARY,
      then land the fix** — ★ RECOMMENDED — the house RED→GREEN discipline; the recorded failure is what makes
      the GREEN meaningful.
- [ ] **(b) Keep a permanently-skipped singleton fixture in the spec as a living negative control** — the
      control cannot rot; adds a skipped test that future readers must be told how to interpret.
- [ ] **(c) Assert GREEN only, describe the RED in prose** — cheapest, and indistinguishable from a test that
      never could fail.

## D. Keeping the class closed ⚠

### D1 ⚠ DECIDE — What stops a new server-side singleton being added?

- [ ] **(a) An ESLint rule plus a `_guards/*.test.ts` lock-in self-test** — ★ RECOMMENDED — fact 14: two
      precedents in this exact repo, it fires in the editor and in `lint:check`, and the self-test proves the
      rule fires rather than assuming it.
- [ ] **(b) A vitest source-scan test** — no ESLint surgery; only fails in `test:unit`, no editor feedback.
- [ ] **(c) A type-level constraint** (e.g. the adapter classes are not exported, only the factories are) —
      elegant and cheap; enforceable only if nothing else needs the class, which the tests do.
- [ ] **(d) Convention plus review** — zero mechanism; this is what was in place while three instances
      accumulated.

### D2 — What exactly is banned?

- [x] **(a) A module-scope `new` of an adapter class, plus any `.init(` on a module-scope import, in
      `apps/frontend/src/**`** — ★ RECOMMENDED — bans both halves of the shape: the shared object and the
      re-configure-after-import that makes it dangerous.
- [ ] **(b) Only the module-scope `new`** — catches the origin; a future singleton exported from a factory
      module sails through.
- [ ] **(c) Only `.init(` on an imported adapter** — catches the dangerous operation; leaves the shared object
      in place for someone to mutate another way.


**NOTE**: Consider, tho, wheteher init is a meaningful target after removing it from the types.

## E. Gates, evidence and sequencing

### E1 — Negative-control discipline

- [ ] **(a) RED→GREEN per behaviour: the concurrency test, the guard self-test, and each job-lifetime change**
      — ★ RECOMMENDED — the milestone's stated non-negotiable, and the ruling names the proof as this phase's
      central deliverable.
- [ ] **(b) One RED→GREEN for the concurrency test; assertions only for the rest** — lighter; the guard then
      ships unproven, which is the failure mode `_guards/` exists to prevent.
- [ ] **(c) Assertions only** — contradicts the milestone discipline.

### E2 — The closing gate

- [ ] **(a) Full E2E (`yarn db:reset` first) + `build` + `lint` + `format` + `test:unit` + `svelte-check` +
      pgTAP** — ★ RECOMMENDED — 17 call sites across routes, loads and server features is exactly the diff
      shape where `svelte-check` earned its place in Phase 157; the DB prerequisite is `db:reset`, **not**
      `db:reset-with-data`.
- [ ] **(b) The full gate plus a 3× E2E determinism run** — this phase changes how every server-side request
      obtains its data client, which is the highest-blast-radius change in the milestone so far; three runs
      would catch an intermittent the single run cannot. Costs ~30 minutes of wall clock.
- [ ] **(c) Everything except the full E2E** — not available under the cardinal rule.

### E3 — Sequencing against 157.1 and 158

- [ ] **(a) Strictly after 157.1, strictly before 158, one phase per wave** — ★ RECOMMENDED — 157.1 changes
      what the parse helpers return at the same call sites this phase re-scopes; doing them in one wave puts
      two large diffs on the same lines behind one gate.
- [ ] **(b) In parallel with 157.1 on separate branches** — faster wall clock; guarantees a merge conflict on
      `supabaseDataProvider.ts` and `parseJsonbColumn.ts`, and neither phase's gate would measure the other's
      change.
- [ ] **(c) Before 157.1** — the concurrency defect is the more severe of the two. Costs re-touching every
      call site again when 157.1 lands, and 157.1's parse outcomes would be designed against a moving
      adapter shape.
