# Phase 162.1: Permissions Follow-Up (Read-Cost Investigation and Closed-Project Voter Coverage) - Research

**Researched:** 2026-09-18
**Domain:** PostgreSQL RLS policy ordering, SvelteKit root-layout data flow, dev-seed templates and Playwright scheduling, PostgREST pagination, pg_net and Supabase Storage cleanup
**Confidence:** HIGH for the code paths and the mechanisms (read from the tree and probed live on the local stack). MEDIUM for the design recommendations the operator has not yet ruled on (flagged in the Assumptions Log).

## Summary

Spikes 025-030 already settle Item 1 and the feasibility of pagination and storage cleanup. Their numbers are the evidence base and are not re-derived here. This research covers the parts the spikes did not reach, and it found **three premises in ROADMAP/CONTEXT that the tree contradicts**. The planner must plan against what the tree does, not against the premise.

1. **A closed project does not make `getAppSettings` throw. It breaks the whole application, including the candidate and admin login pages.** `_getAppSettings` already turns PostgREST's zero-row `.single()` error (`PGRST116`) into `{}`, and `_getAppCustomization` does the same. The failure is one layer up. The root `+layout.svelte` validity check calls `isValidResult(data.electionData)` without `allowEmpty`, so the empty elections array a closed project returns to anon becomes `Error loading election data`. Every route then renders `ErrorMessage` ("Something went wrong, sorry!"). A throwaway dev server scoped to a not-open project was measured on `/en`, `/en/elections`, `/en/candidate/login` and `/en/admin/login`: all four returned HTTP 200 with the ErrorMessage, and the server logged only `reason: 'empty'`, with no throw. So before a project opens, which is exactly when candidates need to log in and answer, **nobody can log in**. The fix must make the root layout tolerate a closed project, not only switch to `maybeSingle()`.
2. **pgTAP already pins the anon closed state on the `app_settings`, `elections` and `questions` tables.** `create_test_data()` makes `project_b` closed, and `16-anon-visibility.test.sql` § Section 5 asserts anon sees 0 rows of each table in it. The real gaps are elsewhere: the two RPCs the voter app actually calls (`get_questions`, `get_nominations`) have no closed-state assertion, the grant-holder read on a closed project is not pinned for these tables, and anon's EXECUTE right on `project_open_for_voters` is not pinned.
3. **Fixing `delete_storage_object` as D-11 specifies creates a new, critical injection surface unless paths are validated.** A path is candidate-controlled, because `candidates.image` and `candidates.answers` are writable by the entity's own editor. D-11 moves that path from a JSON body into the request URL, which is sent with the **service-role key**. A live probe showed pg_net/libcurl resolves `..` dot-segments before sending. So a crafted `image.path` could reach any Storage route, and with enough `../` any Kong route, as a service-role `DELETE`: other tenants' objects, or a filtered PostgREST delete. The cleanup functions must whitelist the path shape and confine deletion to the row's own folder. This is a MUST, not a hardening.

**Primary recommendation:** Serialize the three schema-touching plans (`302-rls.sql`, `400-storage.sql`, and `301-auth-functions.sql` if the explicit GRANT is taken), because every schema edit regenerates the single migration file. Run pagination and dev-seed work in parallel with them. Put the closed-project E2E spec on a new **terminal** Playwright node that depends on every other leaf, because closing the suite's single project blanks every concurrent voter spec.

### Pattern 3: Auto-pagination helper (D-07..D-09)

```typescript
// Sketch only. Names are the planner's discretion. Home: apps/frontend/src/lib/api/adapters/supabase/utils/
type PageResult<TRow> = { data: Array<TRow> | null; error: { message: string } | null };
export async function fetchAllRows<TRow>(
  fetchPage: (from: number, to: number) => PromiseLike<PageResult<TRow>>, // builds a FRESH builder per page
  { pageSize, label }: { pageSize: number; label: string }
): Promise<Array<TRow>> {
  const rows: Array<TRow> = [];
  let offset = 0;
  let warned = false;
  for (;;) {
    const { data, error } = await fetchPage(offset, offset + pageSize - 1);
    if (error) throw new Error(`${label}: ${error.message}`);
    const page = data ?? [];
    rows.push(...page);
    offset += page.length;                        // advance by rows RECEIVED, never by pageSize
    if (page.length === pageSize) continue;       // full page: more may follow
    if (page.length > 0 && page.length % 1000 === 0) {   // option (c): looks like a server cap
      if (!warned) { /* log.warn(CONSTANT_MESSAGE, { label, pageLength: page.length, pageSize }) */ warned = true; }
      continue;                                   // one confirming request at the next offset; an empty page ends the loop
    }
    return rows;                                  // short, not a multiple of 1000 (or empty): the end
  }
}
```

### Pattern 4: Storage cleanup that deletes, safely (D-10..D-13)

**Today** [VERIFIED: 400-storage.sql `delete_storage_object`]: `PERFORM net.http_post(url := base_url || '/storage/v1/object/' || p_bucket, body := jsonb_build_object('prefixes', jsonb_build_array(p_file_path)), headers := … 'Bearer ' || service_key …)`. `cleanup_entity_storage_files` passes `path_prefix := OLD.project_id || '/' || TG_TABLE_NAME || '/' || OLD.id || '/'`. `storage_config` holds `('supabase_url', 'http://kong:8000')` [VERIFIED: seed.sql].

**Target:**
1. `delete_storage_object(p_bucket, p_file_path)` builds `base_url || '/storage/v1/object/' || p_bucket || '/' || p_file_path` and calls `net.http_delete(url := …, headers := jsonb_build_object('Authorization', 'Bearer ' || service_key))`. The Authorization header alone was sufficient in the live probe [VERIFIED: probe returned `200 {"message":"Successfully deleted"}`]. **Before building the URL, validate the path.** The whitelist is one or more segments of `[A-Za-z0-9._-]`, no segment equal to `.` or `..`, and no `%`, `?`, `#`, `\` or space. On failure, `RAISE WARNING` and return without a request.
2. `cleanup_entity_storage_files`: enumerate each bucket's objects under the entity's own folder and call the single-object delete per name. Use `WHERE bucket_id = p_bucket AND starts_with(name, prefix)` (or `LIKE` with `_`/`%` escaped: table names such as `constituency_groups` contain `_`, which is a LIKE wildcard). `storage.objects` has `name_prefix_search (name text_pattern_ops)` and `idx_objects_bucket_id_name (bucket_id, name COLLATE "C")` [VERIFIED: pg_indexes]. The postgres role can SELECT `storage.objects` [VERIFIED: has_table_privilege t].
3. **Confinement:** `cleanup_old_image_file` and the new answers cleanup delete a path **only if** it starts with `OLD.project_id || '/' || TG_TABLE_NAME || '/' || OLD.id || '/'`. Paths elsewhere are left alone, which is the safe direction (a leak, not a destroy). Also delete only paths the NEW row no longer references anywhere (`image.path`, `image.pathDark`, and every answer value's `path`/`pathDark`).
4. **Answers (D-13):** a BEFORE UPDATE trigger on `candidates` and `organizations` (the two tables with an `answers` column [VERIFIED: 105-answers.sql header]). For each key of `OLD.answers` whose `value` is a JSON object with `path` (StoredImage shape, from `validate_image` [VERIFIED: 011-validation-functions.sql `validate_image`]), delete the old path(s) that NEW no longer references. **Detect by shape, not by joining `questions.type = 'image'`.** `cascade_question_delete_to_jsonb_answers` strips answer keys by `UPDATE`ing entities when a question is deleted, and at that point the question row may already be gone, so a join would miss exactly the cascade case.
5. **Comments.** Record C1+ (D-10), including the accepted S2 (once-public URL stays valid), in `400-storage.sql`'s comments. Keep one line per paragraph.

**Direct SQL deletion is impossible by design.** `storage.objects` has trigger `protect_objects_delete` → `storage.protect_delete()`, which raises `Direct deletion from storage tables is not allowed. Use the Storage API instead.` unless `storage.allow_delete_query` is `'true'` [VERIFIED: live `pg_get_functiondef`]. So cleanup must go through the API, and tests cannot fake a deletion.

### Anti-Patterns to Avoid

- **Treating "0 `app_settings` rows" as "closed".** An open project may legally have no settings row, because nothing creates one per project. Ask `project_open_for_voters` instead.
- **Only switching `.single()` to `.maybeSingle()`.** This changes nothing visible. The root layout's `isValidResult(electionData)` still wins.
- **Asserting only "main + h1 visible" for the maintenance page.** Assert the title text and assert that `error-message` is hidden.
- **Putting the closed-project spec in the middle of the perm chain.** Base leaves can overlap it and go blank.
- **Advancing the pager's offset by `pageSize`.** Advance by rows received, or a capped server skips rows silently.
- **Building the Storage URL from an unvalidated path, or deleting any path the old row named.** This is service-role request forgery (see Security Domain).
- **Inserting new pgTAP assertions mid-file in `16-anon-visibility` or `25-matrix-conformance`.** This renumbers G8A/G8B's recorded reds.
- **Hand-editing `migrations/00001_initial_schema.sql`, or running two schema plans in the same wave.** Both regenerate the same file.

## Common Pitfalls

### Pitfall 1: The closed-project fix lands in the adapter only
**What goes wrong:** `maybeSingle` + RPC ship, the voter app still shows "Something went wrong", and the E2E stays red.
**Why:** the root layout's `isValidResult(electionData)` rejects `[]`.
**How to avoid:** change the root `validity` in the same plan, and let the red-first E2E drive it.
**Warning signs:** a dev server log carrying `reason: 'empty'`.

### Pitfall 2: Operator's DB settings are invisible to anon while closed
**What goes wrong:** with the project closed, anon cannot read `app_settings`. So `access.candidateApp: false` or `access.underMaintenance: true` stored in the DB are **not honoured** on the anon candidate and admin login pages. Defaults apply (candidateApp true, underMaintenance false).
**Why:** 162-08 Q4 gated `anon_select_app_settings` on `project_open_for_voters`.
**How to avoid:** out of scope to change the policy (it is ratified). Surface it to the operator (Open Question 2).

### Pitfall 3: Service-role request forgery through image paths (introduced by D-11)
**What goes wrong:** a candidate sets `image.path` (or an answer's `value.path`) to a crafted string with `../` or `?…`. The next image change triggers a service-role `DELETE` against any Storage route, or any Kong route.
**Why:** the path moves from a JSON body into the URL. pg_net (libcurl) resolves dot-segments. A live GET probe to `…/object/public/public-assets/x/../../../../rest/v1/elections?select=id&limit=1` arrived at Storage as `Route GET:/rest/v1/elections?select=id&limit=1 not found`, so four `..` segments were consumed and the query string survived [VERIFIED: live probe]. The authenticated role may UPDATE `image` and `answers` on its own row [VERIFIED: 303-column-grants.sql column lists include `image` and `answers`]. Every public photo's path is visible to voters.
**How to avoid:** strict whitelist in `delete_storage_object`, confinement to the row's own folder in every trigger, and pgTAP negative tests that no request is enqueued for crafted paths.
**Warning signs:** any `net.http_request_queue` URL not matching `…/storage/v1/object/(public|private)-assets/<uuid>/<table>/<uuid>/<name>`.

### Pitfall 4: pg_net is asynchronous and transactional
**What goes wrong:** a pgTAP test waits for a file to disappear; it never will.
**Why:** `net.http_*` inserts into `net.http_request_queue` inside the transaction, and the worker sends only after COMMIT. pgTAP files end in `ROLLBACK`.
**How to avoid:** in pgTAP, assert the **enqueued request** (method `DELETE`, exact URL) structurally. It is red today (method POST, bucket-only URL). Observe the **disappearance** (D-14) in a committed-state test (Playwright, see Validation). Poll with a bounded `expect.poll` (the probe saw deletion within 3 s; allow about 30 s). A public GET of a deleted object returns **400**, not 404.
**Warning signs:** a test that "waits N seconds" instead of polling.

### Pitfall 5: `_` in LIKE prefixes, and generic plans
**What goes wrong:** `name LIKE prefix || '%'` over-matches on `_` (a LIKE wildcard, present in `constituency_groups`/`question_categories`). With a PL/pgSQL variable it may not use `name_prefix_search` under a generic plan.
**How to avoid:** use `starts_with()`, or escape the pattern. Scale is small (objects per entity folder), so an index miss is acceptable. [ASSUMED: acceptable at current scale; bulk deletes of thousands of entities would scan `storage.objects` per row.]

### Pitfall 6: Offsets and builders in the pager
**What goes wrong:** rows are skipped under a server cap below the requested size, or duplicated or missing with a non-unique sort.
**How to avoid:** offset += received length; `.order('sort_order').order('id')` everywhere (D-08); a fresh builder per page.

### Pitfall 7: The spike scripts on the committed schema
**What goes wrong:** `run.sh`/`apply-reorder.sql` raise on B quals; `perturb.sh` continues noisily and "passes" for the wrong reason.
**How to avoid:** use the fingerprint gate and phase-local, perturbation-only copies (§ Item 1).

### Pitfall 8: Schema-plan collisions
**What goes wrong:** two plans in one wave both run `yarn schema:regenerate`. The second commit clobbers or conflicts on `00001_initial_schema.sql`, and `assert:schema-migration-parity` fails.
**How to avoid:** serialize every plan touching `schema/*.sql`: Item 1 (`302`, plus the D-04 comment in `400`), Item 2's optional GRANT (`301`) plus the `302` comment fix, and storage (`400`).

### Pitfall 9: E2E after schema changes
**What goes wrong:** `--no-db-reset` keeps the old migration applied, so the suite passes against stale policies.
**How to avoid:** after any schema commit, run `tests/scripts/e2e-run.sh --run-dir tests/e2e-runs/<name>` **without** `--no-db-reset` (or run `yarn db:reset` first). Never reset while a run is in flight. Watch disk space: 58 GiB free at research time, and project memory records ENOSPC voiding full-suite runs.
