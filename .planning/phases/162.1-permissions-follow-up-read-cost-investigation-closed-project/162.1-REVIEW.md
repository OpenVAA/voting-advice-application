The generated migration was spot-checked with `scripts/assert-schema-migration-parity.mjs`, which exits 0 ("generated copy is current").

The storage cleanup SQL is sound on the points the brief asked about:
- `delete_storage_object` checks its input before it reads any config or builds a URL. The bucket must be one of two literals. The path regex is anchored at both ends, allows only lowercase canonical UUIDs, and escapes the extension dot. That leaves no room for `..`, `?`, `#`, `%` or `/` injection into the service-role URL.
- EXECUTE is revoked from PUBLIC, anon and authenticated on both helpers.
- Every SECURITY DEFINER function pins `search_path = ''`.
- `storage_config` is closed to API roles.
- Both BEFORE UPDATE cleanup triggers apply the own-folder check and the still-referenced check symmetrically.
- The entity-delete enumeration uses `starts_with`, not `LIKE`.
- No BEFORE UPDATE trigger on candidates or organizations returns NULL or assigns `answers` or `image`, so an enqueued DELETE cannot outlive a skipped row.

The RLS reorder only moves disjuncts, and the order monitor checks the first occurrence of each call, so it catches both a split order and a swapped order. `fetchAllRows` terminates correctly on an empty page, on an exact multiple of the page size and on a capped page, and it advances the offset by the rows actually received.

## Warnings

### WR-01: The focus wait gives up when the focused element is unmounted, not only when the user moves focus

**File:** `apps/frontend/src/lib/utils/focusNavigationTarget.ts:63-70`
**Issue:** The wait records `doc.activeElement` when it starts. On every mutation, any change to it counts as "the user moved focus", and the wait is cancelled before `focusIfPresent()` runs.

When the focused element is removed from the DOM, the browser silently resets `document.activeElement` to `<body>`. This is exactly what happens in the case the helper was written for. On Q→Q, the async re-render replaces the old question content, including the answer option or button that held focus, and inserts the new heading in the same batch. The observer then sees `activeElement` (now `body`) differ from `focusedWhenWaitBegan` (the detached old control). It calls `cancel()` and returns without looking for the target, which may already be in the DOM. Focus stays on `<body>`, which is the same NAVA11Y-02 failure the helper exists to fix, now on a different ordering.

No unit test covers this. Every test case starts with focus on `<body>`, or moves focus explicitly with `button.focus()`.
**Fix:** Treat a disconnected or body-level previous focus as "not a user move", and look for the target before abandoning:
```ts
observer = new MutationObserver(() => {
  if (cancelled) return;
  const active = doc.activeElement;
  const userMoved =
    active !== focusedWhenWaitBegan &&
    active !== null &&
    active !== doc.body &&
    (focusedWhenWaitBegan === null || focusedWhenWaitBegan.isConnected);
  if (userMoved) {
    cancel();
    return;
  }
  focusIfPresent();
});
```
Add a unit test in which the focused element is removed and the heading is appended in the same tick.

### WR-02: A grant holder is denied the D-17 preview when the closed project has no `app_settings` row

**File:** `apps/frontend/src/lib/api/adapters/supabase/dataProvider/supabaseDataProvider.ts:142-158`
**Issue:** D-17 says preview is "decided on data the caller can actually read". The implementation, however, uses the presence of the settings row as its proxy for readability. When `maybeSingle()` returns no row, it calls `project_open_for_voters`, and `false` returns `voterApp: false` for every caller, grant holders included.

The method's own docblock says "nothing creates a settings row for a project, so an OPEN project may legally have none". Only `seed.sql`, for the default project, and the dev-seed/E2E `ensureProject` insert one. So a project created any other way that is still closed shows its admins and candidates the maintenance page instead of the preview, even though RLS returns them the project's elections and nominations. The 302-rls comment acknowledges this direction as an outage, but only for a row that "disappeared". The row-never-existed case has no test: every E2E and pgTAP closed-project case has a settings row.
**Fix:** Decide preview from data the caller can read even when no row exists. For example, when the RPC returns `false`, probe one readable row the anon policies gate on openness (`this.scopedFrom('elections').select('id').limit(1)`) and return `{}` if it comes back. Alternatively, guarantee that every project has an `app_settings` row: an AFTER INSERT trigger on `projects`, or a NOT-NULL invariant asserted in pgTAP. Add a test for a closed project without a settings row, read by a grant holder.

### WR-03: A wrong or nonexistent `PUBLIC_PROJECT_ID` now shows "voter app not accessible" instead of an error

**File:** `apps/frontend/src/lib/api/adapters/supabase/dataProvider/supabaseDataProvider.ts:146-157` (with `apps/supabase/supabase/schema/301-auth-functions.sql:281-288`)
**Issue:** `project_open_for_voters` deliberately returns `false` for a project that does not exist (COALESCE → false). Before this phase, a canonical UUID that names no project led to `{}` settings, then empty elections, then `ErrorMessage` ("Error loading election data"), which is a visible failure. Now that same misconfiguration looks like a deliberately closed project. The branch returns `voterApp: false`, the root layout accepts the empty data (`allowEmpty: voterAppInaccessible`), and the deployment renders a clean maintenance page with nothing in the logs.

CLAUDE.md's `PUBLIC_PROJECT_ID` policy ("no fallback … rather than letting queries succeed against some other project's rows") exists to make misconfiguration loud. This path makes it silent and indistinguishable from a real state. The E2E preflight catches it in tests, but not in production.
**Fix:** Tell "closed" apart from "does not exist" in the value the adapter reads. For example, add a small SECURITY DEFINER RPC that returns `open_for_voters` or NULL for a missing project, or have the adapter treat a `false` answer as an error unless the project is known to exist. At minimum, log at `error` with the project id on the closed branch, so an operator can see what happened.

### WR-04: `yarn db:seed:teardown` reopens the project whatever it tears down

**File:** `packages/dev-seed/src/cli/teardown.ts:138-140, 206`
**Issue:** D-19 says teardown reopens "a project the closed-project template closed". The CLI instead passes `reopenProject: true` unconditionally. Every teardown, with any prefix (`seed_`, `e2e-perm-foo-`, …) and even one that matched zero rows, writes `open_for_voters = true` to the client's project and prints "Project reopened to voters".

A developer or operator who closed their project deliberately, for example to stage content before release, and then runs an ordinary `seed_` teardown will silently republish that project's data to anon. The write happens after the row and storage cleanup, so it is not rolled back or confirmed.
**Fix:** Reopen only when the teardown targets the closed-project template, or only behind an explicit flag:
```ts
const reopen = values['reopen-project'] === true || prefix === 'e2e-perm-closed-project-';
const { rowsDeleted, storageRemoved } = await runTeardown(prefix, client, { reopenProject: reopen });
```
Print the reopen line only when it happened, and update `TEARDOWN_USAGE` to match.

## Info

### IN-01: A server row cap that is not a multiple of 1,000 still truncates silently

**File:** `apps/frontend/src/lib/api/adapters/supabase/utils/fetchAllRows.ts:14, 59-66`
**Issue:** Option (c) only detects a cap that is a multiple of `ROW_CAP_GRANULARITY`. A hosted project with `max_rows = 500`, `2500`… (still multiples) is fine, but `max_rows = 1500` or `750` returns the first short page as the final page with no warning. This is the D-09 design, not a deviation, but nothing records the limit.
**Fix:** State the assumption in `staticSettings.type.ts`'s `pageSize` docblock, or also run the confirming request whenever `page.length < pageSize` and the previous page was full.

### IN-02: The multi-page and confirming-request paths are never exercised against a real PostgREST

**File:** `apps/frontend/src/lib/api/adapters/supabase/utils/fetchAllRows.test.ts:1-134`
**Issue:** Every paging branch beyond page one is proven only against `fakeTable`. The E2E datasets are far below 50,000 rows and are not multiples of 1,000, so the real-server behaviour is never observed: `range()` on a `.rpc()` builder, and a request with offset equal to the total.
**Fix:** Add one integration check against local PostgREST with a small `pageSize` override, or a pgTAP-free Node test against the local stack.

### IN-03: `setProjectOpenForVoters` silently does nothing for an unknown project id

**File:** `packages/dev-seed/src/supabaseAdminClient.ts:549-555`
**Issue:** An update that matches no row succeeds. Writer Pass 7 can therefore "close" a nonexistent project and report success. The E2E spec would catch it, but a CLI seed would not.
**Fix:** Add `.select('id')` and throw when the returned array is not exactly one row.

### IN-04: A later seed does not reopen a project that `perm-closed-project` closed

**File:** `packages/dev-seed/src/writer.ts:168-170`
**Issue:** Because an absent `openForVoters` leaves the project untouched, running `yarn db:seed --template perm-closed-project` and then `yarn db:seed:default` leaves the default project closed. The developer then sees the maintenance page with no obvious cause. Only the teardown CLI or `db:reset` reopens it.
**Fix:** Have `formatSummary` print the project's current openness when it is `false`, or document the interaction in the template header and the README.

### IN-05: Spec header and assertions drift from the stated contract

**File:** `tests/tests/specs/perm/perm-closed-project.spec.ts:25-33, 88`
**Issue:**
- The docblock for `MAINTENANCE_TITLE` (lines 25-27) sits above `CANDIDATE_EMAIL`, so editor tooling attaches it to the wrong constant.
- Line 88 asserts a hard-coded English accessible name (`'Jobs Monitoring'`), although the file header declares "Testid-only via `testIds`" and the maintenance title is carefully read from the message catalogue for the same reason.

**Fix:** Move the docblock above `MAINTENANCE_TITLE`, and replace the button-name assertion with a `testIds` entry for the admin shell.

### IN-06: One pgTAP assertion counts requests from any session

**File:** `apps/supabase/supabase/tests/database/31-storage-cleanup.test.sql:112`
**Issue:** The "no non-DELETE request" assertion counts every `net.http_request_queue` row above the baseline, with no URL filter. Any concurrent pg_net traffic committed during the file's run would redden it, for example the send-email path or an E2E run against the same database. The sibling DELETE assertion filters on the exact URL.
**Fix:** Also filter on `q.url LIKE (SELECT value FROM public.storage_config WHERE key = 'supabase_url') || '/storage/v1/object/%'`.
