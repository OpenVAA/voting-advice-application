# Phase 162.1 Plan 02: Storage cleanup that deletes, safely — Summary

**`delete_storage_object` now deletes one object via `net.http_delete`, but only for an exact `<uuid>/<table>/<uuid>/<uuid>.<ext>` path in `public-assets`/`private-assets`, API roles can no longer call it, and image cleanup is confined to the row's own folder and to paths the new row no longer references. A committed-state spec watched a replaced photo survive before the fix and disappear after it.**

## Accomplishments

- **D-11:** single-object `DELETE <supabase_url>/storage/v1/object/<bucket>/<path>` with only `Authorization: Bearer <service_role_key>`. The bulk-route POST that had deleted nothing since `11f877913` is gone.
- **D-20(a):** a bucket whitelist plus an exact-shape regex (ten cleanup tables, the `ALLOWED_IMAGE_EXTENSIONS` set, canonical lowercase uuids), checked before any URL is built. Anything else raises `Storage cleanup refused a path outside the upload convention` and enqueues nothing.

- **Security gap closed in-plan:** `delete_storage_object` was EXECUTE-able by anon and authenticated (measured `t` before). It is now revoked from `PUBLIC, anon, authenticated`, together with the new helper. This landed in the same commit as the `http_delete` switch.
