# Phase 162.1 Plan 04: Paged Provider Reads Summary

**All multi-row Supabase provider reads now go through one helper, `fetchAllRows`. It reads in pages of 50,000 rows (a single static setting), orders pages on `sort_order` then `id`, and handles a server row cap using spike 030 option (c): when a short page's length is a multiple of 1,000, it sends one confirming request and logs one constant-message warning. A server cap can no longer silently truncate a collection.**

## Performance

- **Duration:** 3h 8m wall clock (13:52:48Z to 17:00:33Z). About 11 minutes of that was the full E2E suite. A session stall voided one earlier full-suite run.
- **Tasks:** 2 (tracer + expansion, both TDD)
- **Files modified:** 12 (including evidence)

## Accomplishments

- `fetchAllRows.ts` exports `fetchAllRows` and `PROBABLE_ROW_CAP_MESSAGE`:
  - It takes a page factory and builds a fresh query for each page.
  - It advances the offset by the number of rows received.
  - A full page continues the read. A multiple-of-1,000 short page gets one confirming request and one warning per read. Any other short page ends the read.
  - An error throws `<label>: <message>`.
- `staticSettings.dataAdapter.pageSize = 50000` goes through a shared `DataAdapterBase`. Its JSDoc states the coupling to `config.toml` `max_rows`.
- `_getElectionData`, both halves of `_getConstituencyData`, every `get_nominations` fan-out call and `_getEntityData` are paged, with their original error prefixes kept. `_getQuestionData` and the two `app_settings` reads stay unpaged, and a comment says why.
- The provider test mock now supports paging (chain `range`/`maybeSingle`, per-table response queues, a thenable rpc builder with `range`), and there are call-site assertions for ordering, ranges, per-page filters and prefixes.
- Gates: `yarn typecheck`, `yarn lint:check`, `yarn format:check` and `yarn test:unit` all exit 0. The full E2E suite passed 158 with 0 unexpected, flaky or skipped.
