## The four sources, stated once — this is what Task 1 builds

**Canonical keying (D-03a, locked): the resolved snake_case table name.** `resolveCollectionName` is
currently module-private in `supabaseAdminClient.ts` (a plain `function`, around `:81` — re-measure).
Export it from `permittedKeys.ts` and have `bulkImport` import it back, so there is exactly one
implementation. `permittedKeys(collection)` resolves first, then looks up. **A lookup miss throws.**
If it returned an empty set or `undefined`, a keying confusion would make the guard permit everything —
a fake guard of exactly the kind this milestone exists to eliminate.

**Source (1) — DB columns.** `TablesInsert<T>` from `@openvaa/supabase-types`, plus every legal camel
form. The legality rule, measured: for a target column `c` of table `T`, the legal keys are `c` itself
together with every key `k` of `FIELD_MAP` for which `FIELD_MAP[k]` is `c`. **Derive this mechanically
from `FIELD_MAP`; never hand-write a camelCase alias.** Three measured hazards make hand-writing wrong:
`PROPERTY_MAP` is `COLUMN_MAP` reversed and `COLUMN_MAP` maps **two** columns to `organizationId`, so
last-wins gives `organizationId → organization_id_nom` — a column on no table; `sort_order`'s only
legal camel form is `order`, not `sortOrder`; and `published` is an identity entry, so a "keys that
differ" filter would drop it. `FIELD_MAP` also carries the legacy alias `documentId → id`.

**Source (2) — sentinels, from `LINK_SENTINELS`.** ⚠ **A count discrepancy the executor must resolve by
measurement, not by citation.** `144-CONTEXT.md` B-4's headline says **12** pairs; its own enumeration
lists 7 underscore forms plus 3 bare forms, and `144-RESEARCH.md` R2.2's measured table gives the same
**10**. The reconciliation, verified during planning by reading the four resolution sites directly: the
"12" arises from counting camelCase **collection-key** spellings (`constituencyGroups`,
`questionCategories`) as distinct pairs. D-03a locks canonical keying to the resolved snake_case table
name, which collapses those spellings into one entry each. **Under the locked keying the measured set
is 10 `(collection, key)` pairs across 4 rules.** Re-derive it yourself from the four resolution sites
at execution HEAD, record the derived count in the ledger, and if it is not 10 report the disagreement
as a finding rather than reconciling it silently. What both documents agree on, and what is
**non-negotiable**, is that the **three bare non-underscore forms are included** — `elections`'
`constituencyGroups` and `constituency_groups`, and `constituency_groups`' `constituencies` — because
76 rows across `e2e/base` and all 28 `perm-*` templates use the bare form, and because leaving them out
of `LINK_SENTINELS` would move them outside the const's authority and defeat criterion 4.

The four rules, transcribed from the measured code — key order is `??`-precedence order and must be
preserved:
- `elections` → keys `_constituencyGroups`, `_constituency_groups`, `constituencyGroups`,
  `constituency_groups`; ref table `constituency_groups`; target: join table
  `election_constituency_groups`, parent column `election_id`, child column
  `constituency_group_id`, on-conflict `election_id,constituency_group_id`.
- `constituency_groups` → keys `_constituencies`, `constituencies`; ref table `constituencies`;
  target: join table `constituency_group_constituencies`, parent column `constituency_group_id`,
  child column `constituency_id`, on-conflict `constituency_group_id,constituency_id`.
- `question_categories` and `questions` → key `_elections`; ref table `elections`; target: jsonb
  column `election_ids`.
- `question_categories` and `questions` → key `_constituencies`; ref table `constituencies`; target:
  jsonb column `constituency_ids`.

Rule order above reproduces today's dispatch order exactly (elections → constituency groups →
`electionResolve` for categories then questions → `constResolve` for categories then questions).
**Keep it** — `144-03` iterates this array and the order is observable.

**Source (3) — non-column fields, MOVED not re-invented.** `NON_COLUMN_FIELDS` and
`COLLECTION_NON_COLUMNS` already exist inside `bulkImport` (around `:140-146` — re-measure). Move both
to `permittedKeys.ts` and import them back into `bulkImport`. Keep their contents byte-identical and
add the one-line reason D-03 asks for beside each entry. ⚠ `elections`' `constituencyGroups` /
`constituency_groups` and `constituency_groups`' `constituencies` currently live in
`COLLECTION_NON_COLUMNS`; under source (2) they are **sentinel key forms**. Keep them in
`COLLECTION_NON_COLUMNS` for `bulkImport`'s stripping behaviour — that behaviour must not change — but
make `LINK_SENTINELS` the authority for *permission*, and say so in a comment at both sites.

**Source (4) — RPC relationship references.** Transcribe the `_bulk_upsert_record` relationship map
from `apps/supabase/supabase/schema/501-bulk-operations.sql` (the `CASE p_table_name` block, around
`:113-136` — **re-read it at execution time; do not copy line numbers from any document**). Ten
`(collection, key)` pairs: `candidates` → `organization`; `nominations` → `candidate`, `organization`,
`faction`, `alliance`, `election`, `constituency`, `parent_nomination`; `questions` → `category`;
`constituencies` → `parent`. Admit `nominations.faction` even though nothing in-tree emits it — the RPC
declares it and omitting it would break any future factions template. Additionally admit
`candidateExternalId` on `nominations`: `bulkImport` reads it by name when deciding whether a
nomination is a candidate nomination (re-measure the line), even though nothing in-tree authors it.
