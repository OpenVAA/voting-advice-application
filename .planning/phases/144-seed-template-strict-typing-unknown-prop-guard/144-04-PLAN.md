<guard_spec>
## What Pass 0 is, stated once

**Signature and placement.** `assertKnownRowProps(data)` takes the collection→rows map and returns
nothing, throwing on the first offence. It lives at `packages/dev-seed/src/assertKnownRowProps.ts`,
imports only from `./template/permittedKeys`, and **must not import the Supabase client**, so
`yarn test:unit` exercises it with no database. It is called once from `Writer.write()` immediately
above `await this.client.bulkImport(bulkData)`.

**⚠ It takes `data`, not `bulkData`, and that choice is load-bearing.** `Writer.write()` deletes
`accounts`, `projects`, `feedback` and `app_settings` from `bulkData` before Pass 1. A guard reading
`bulkData` at that point **cannot see** any of the four. `app_settings` is a first-class,
template-authorable fragment that **every** built-in emits exactly one row of — so reading `bulkData`
would leave the phase's headline guard blind to a collection every single template uses. `feedback` is
a declared fragment too. `accounts` and `projects` are not in `TemplateSchema` and emit zero rows in
practice, but guarding them costs nothing. Keep D-02's placement — immediately before Pass 1 — and pass
the **pre-deletion `data`**, which is still in scope as the method parameter. Guarding `data` covers all
twelve template-declarable collections and adds two for free; guarding `bulkData` covers ten and
silently exempts `app_settings`. **Record this decision and its measured consequence in the ledger.**

**Rows without an `external_id`.** `feedback`, `accounts` and `projects` have no `external_id` column at
all, and `writer.test.ts` passes rows with none. The guard **does not require** `external_id` — the RPC
already hard-requires it for the ten bulk-import tables and raises by name. When a row lacks one, the
message falls back to the row's **index within its collection**. Do not let the guard throw a
missing-`external_id` error: it would pre-empt the RPC's clearer message and change the failure mode for
every `feedback` row in `writer.test.ts`.

**The message.** House style, measured from the existing dev-seed throws, is
`<function>: <what went wrong>` with the offending identifier interpolated and a remediation sentence.
The CLI wraps everything as `Error: <message>`, so it must read well after that prefix. The unknown-key
message names the offending key, the collection and the row's `external_id` (or its index), states that
the pipeline never reads the key so it would be silently dropped, lists the permitted keys for that
collection, and closes with a remediation sentence naming `LINK_SENTINELS` or `COLLECTION_NON_COLUMNS`
in `packages/dev-seed/src/template/permittedKeys.ts`. The denied-key message shares the shape and
instead states that the key is a real column discarded by the RPC's `skip_columns`, cites
`apps/supabase/supabase/schema/501-bulk-operations.sql`, and says to remove it.

**Throw on the first offence, not an aggregate.** `bulkImport`'s and `linkJoinTables`' existing errors
are all first-failure, and an aggregate over every row in a large dataset would bury the signal. This is
a style judgement rather than a measurement (research assumption A1) and it is **decided here**: first
offence. State the choice in the module's doc comment so a later reader knows it was chosen, not
defaulted into.

**The deny-list (D-09).** The RPC's `skip_columns` array is
`id`, `created_at`, `updated_at`, `project_id`, `entity_type` — re-read it from
`apps/supabase/supabase/schema/501-bulk-operations.sql` at execution time and **do not copy line numbers
from any document**. Seeded literally it rejects every row in the repository, because every generator
emits `project_id` and the RPC drops the payload's copy only to re-supply its own from its
`p_project_id` parameter.

- **`entity_type` — DENY.** The one honest entry. Zero in-tree rows emit it; it is a real column on
  `nominations`, `question_categories` and `questions`; and it is D-09's stated exemplar. Deny it on
  exactly those three tables.
- **`project_id` — EXCLUDE.** Emitted on every generated row. Denying it turns every seed run and every
  E2E setup red.
- **`id` — EXCLUDE.** A `TablesInsert`-legal key that two existing `writer.test.ts` fixtures supply
  (`accounts` and `projects`).
- **`created_at`, `updated_at` — EXCLUDE.** Zero in-tree rows emit them; a template that sets one gets a
  DB-overridden value rather than an error, which is worth a note rather than a throw.

Put the four exclusions in a **documented, non-throwing** `SKIP_COLUMNS_NOT_DENIED` table with a
one-line reason each, and assert in a spec that the denied set and the excluded set **together
reproduce the SQL array exactly**, so a future `skip_columns` addition cannot pass unnoticed.
</guard_spec>
