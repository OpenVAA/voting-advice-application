## Inherited from `144-01-PLAN.md` § `<hygiene_loop>` — read it there; three additions

1. **Measured zod semantics at 4.3.6, this tree's version.** These were probed in the discussion phase
   and reproduced verbatim in research; they are stated so the executor does not guess:
   `.strict()` **before** `.extend()` still rejects an unknown top-level key; `.extend()` then
   `.strict()` also rejects. **Either ordering works — there is no hazard.** A top-level-only
   `.strict()` does **not** reach the fragment: a template carrying an unknown key inside a per-entity
   fragment parses with success and the key is silently stripped. A strict fragment **does** reject a
   nested unknown key, with the issue path naming the fragment. A strict fragment still **accepts** an
   arbitrary key inside a `fixed[]` row — correct per D-04, because that is the runtime guard's job.
   `.strict()`-then-`.extend()` still accepts the extended `latent` field.
2. **Assertion regex shape.** `validateTemplate` formats each issue as `  template.<path>: <message>`,
   so a nested unknown key inside the `candidates` fragment surfaces as a line naming
   `template.candidates` and an unrecognised-key message. The same shape is already in use in
   `latent.schema.test.ts`; reuse it rather than inventing a new matcher.
3. **Row-scoped ledger discipline** — see `<parallel_wave_note>`.
