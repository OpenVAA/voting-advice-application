# Phase 179.1 Plan 76: The Admin App's login page says why Summary

**The Admin App's login page now says why after a sign-out the user did not make on it: a tab that follows a sign-out from another tab arrives with `errorMessage=loggedOutElsewhere`, and after the server's sign-out at a count's end the page's load reads the settled marker and answers `loggedOutAutomatically`, shown before the gate's `loginFailed`. The page's message is an alert, and the heading, which now takes the focus reset, names it as its description.**

## For the operator's reading

An administrator who has the Admin App open in one tab and logs out in another finds the first tab on the login page at once, with "You have been logged out in another tab or window." under the password field (in their locale). An administrator whose browser carried a logout count that ran out, because a Contestant App tab was closed while its logout modal counted, is signed out at the next request the Admin App makes and lands on the login page with "You have been logged out automatically, because a logout you started was not cancelled in time." Before this plan both landed on the login page with no word of why, the second with "Login failed. Please check your username and password." because the gate puts `loginFailed` on the address. The message is an alert. The page's heading now takes the focus the root layout moves after a navigation, and while a message is shown it names the message as its description. A Log out the administrator presses still lands on the login page with no message. No message key changed: the two sentences are plan 74's.

What stays unproven:

- **What a screen reader says.** The alert and the heading's description are asserted as Chromium computes them. VoiceOver, NVDA and TalkBack go on the UAT list.
- **A focus ring on the heading.** The heading is focused on arrival, and a browser may draw its focus ring around it. That is visual and not checked. The Contestant App's login heading and the default heading of every page behave the same way.
- **The real sequence.** The browser test of the count's end writes the run-out count into the browser's cookies (`writeRunOutCount`). It stands for a Contestant App tab closed during its logout modal, and that sequence is driven in `contestant-entity-selection`, not here beside an Admin App tab.
- **Every engine but Chromium**, and real phones.

## Decisions Made

- **The load's reason comes before the address bar's** (deviation 1).
- **The heading is described while any message is shown.** `aria-describedby` follows `status === 'error'`, which is when the one `ErrorMessage` is rendered. A failed sign-in's message is then the heading's description too, and is an alert. That changes nothing visible.
- **The reason is read once.** It is read at init, as `errorMessage` was before. A later navigation to the page keeps the message the page opened with, which `after a sign-out here and a sign-in in another tab, a link stands on the login form …` depends on. `svelte-check` flags the read of `data` without the `svelte-ignore`, measured in `179.1-76-t2-check-probe` (1 warning). The comment above it states why.
- **The link of the new test goes to the question-info page.** Under ruling R1 the protected group has no server load of its own, and question-info's subtree does, so a client-side navigation to it sends a request the hook sees.
