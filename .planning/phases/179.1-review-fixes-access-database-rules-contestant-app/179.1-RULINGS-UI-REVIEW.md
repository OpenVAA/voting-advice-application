## Top 3 Priority Fixes

1. **The dialog's warning may never be announced** ([MARKUP] `ModalContainer.svelte` sets only `aria-label={title}`, with no `aria-describedby`; focus goes to Continue, after every paragraph. [PREDICTED] a screen reader says "Log Out, dialog, Continue entering data, button"; whether it also reads the body depends on the reader). The unsaved-loss sentence and the 30-second count are the point of the modal, and the count ends in a discard. Fix: give `TimedModal` a body id and pass it as `aria-describedby`. Keep focus on Continue.
2. **✕ and Escape look like staying during a sign-out and are not** ([MARKUP] `LogoutButton.svelte:105-108`: only Continue is disabled; a close with `leaving` up calls no `keepGuardedEdits`, and the sign-out runs on). The user chooses to stay and loses the edit. This is on the operator's UAT list and in `deferred-items.md`. My recommendation is to hold both back while `leaving` is up, because staying is what those controls are documented to mean. That needs a prop through `ModalContainer` and `Modal`, as the deferred entry says.
3. **A sign-out in progress says "Loading…", twice, at 20%, and often not at all** ([MARKUP] `LogoutButton.svelte:160-165` passes no `loadingText`; `Button.svelte` swaps the name; no sign-out string exists in `messages/en`). Fix: add a `common.loggingOut` key in seven locales and pass it as `loadingText`; give the `Loading` inside `Button` an `aria-hidden` or an empty label so the name is not doubled; apply `DISABLED_TEXT_CLASS` only when `disabled` is set and `loading` is not (this is `179.1-GAPS-UI-REVIEW.md` priority fix 3, still open); and show the state on the page-level button during `leaving`, for the paths with no modal.

## Detailed Findings

### Pillar 1: Copywriting (2/4)

- **WARNING, "Loading…" is untrue for a sign-out.** [MARKUP] See priority fix 3. The user pressed Log out, and its name becomes "Loading…", "Ladataan…", "Laadimine…", "Chargement…". Nothing says the sign-out is what is running. WCAG 2.5.3 and 4.1.2 are not clearly failed, but voice control by the name "Log out" stops working during this state.
- **WARNING (W4), the hidden-profile sentence ignores its setting.** [MARKUP] `LogoutButton.svelte:132-147`. The `{:else}` branch is entered only when required info is not zero, so at `:145` the first half of the `||` is always true and `hiddenIfMissingAnswers` decides nothing. A user with only opinions left and the setting on sees the count and no consequence, though the component's doc says the setting affects the message. It predates plan 43 in the same logic, so this is not a regression; the plans restructured around it. Fix: move the sentence below both branches, and condition it on required info left, or on `hiddenIfMissingAnswers` with opinions left.
- **WARNING, a zero in a count sentence.** [MARKUP] `itemsLeft` with required info left and no opinions left yields "…items of basic info and 0 opinions to fill". True, and it should read as one item.
- **WARNING, "please try again" with nothing to press.** [MARKUP] The Alert offers only Close and ✕; the user must find Log out. `Alert`'s `actions` snippet could offer retry, but it turns `role` into `dialog`, so this is a trade-off to weigh.
- **WARNING, two controls named Close in one Alert.** [MARKUP] `Alert.svelte`: the text button and the ✕ share `common.close`. The modal's ✕ says "Close dialog", which is better.
- **WARNING, "Continue entering data" in row 4.** See the table.
- **Passes.** [MARKUP] The two new sentences state the consequence and the uncertainty without blame. "may still be logged in" is true of each failure row. "Could not confirm" is not generic. Seven locales hold both keys. Grep for "something went wrong" patterns is not relevant here: none was added.

### Pillar 2: Visuals (2/4)

- **WARNING, no state at all on two of the three sign-out paths.** [MARKUP] Direct path (`triggerLogout` calling `leave` when nothing is left): the button neither disables nor shows loading. Count's end: `TimedModal.svelte:129-132` calls `onTimeout` and closes at once, so the spinner goes with the modal, and the page sits unchanged until the navigation. A further press does nothing, silently (`if (leaving) return`). With a `POST` that never answers, nothing ever changes (`deferred-items.md`).
- **WARNING, absolute parts in a box that can scroll.** [PREDICTED] `<progress class="absolute … bottom-0">` and the ✕ `absolute top-2 right-2` are positioned in `.modal-box`. If it scrolls, both travel with the content, so the bar crosses text or buttons and the ✕ leaves the view.
- **WARNING, long title against the ✕ on a phone.** [PREDICTED] `h2` is centred with the box's padding, and the ✕ reaches further in than that. French at 40 and Swedish at 42 characters wrap, and their first line may touch it.
- **WARNING, the Alert has no visible title.** [MARKUP] `title` only becomes `aria-label`. An Alert appearing after a modal closes has an icon and a sentence, which is enough, so this is minor.
- **Known, not counted:** the header's blue-looking Log out icon, in `179.1-GAPS-UI-REVIEW.md`.
- **Passes.** [MARKUP] One main button, Continue, gives a clear focal action, and Log out is a plain warning-coloured button under it.

### Pillar 3: Color (3/4)

Tokens only. No hardcoded colour was added.

- **WARNING, loading label at 20%.** [MARKUP] `Button.svelte` `DISABLED_TEXT_CLASS` applies while loading. WCAG 1.4.3 exempts inactive controls, yet this label is the only status text on screen. The spinner is `text-secondary`, so it stays visible [PREDICTED].
- **WARNING, Continue and Log out both dim during a failure-free wait.** [MARKUP] Both are disabled at once, so the live-looking element in the modal is the ✕, the one with the misleading effect. This compounds priority fix 2.
- **Unmeasured.** The Alert's foreground on its background, and the hover pair `bg-warning` and `text-warning-content`.
- **Passes.** [MARKUP, computed by estimate] `warning` is `#a82525` on `#ffffff` and `#e16060` on `#000000`, each about 7:1, above AA for the modal's Log out.

### Pillar 4: Typography (3/4)

- **WARNING, the costliest sentence is not distinguished.** [MARKUP] In row 3 four `<p>` have one size and weight, and the loss of edits comes first only by order. Bolding that sentence alone would help a scanning reader, and makes it clear the title says less than it.
- **WARNING, casing.** [MARKUP] English "Log Out" as title and button, "log out" in the body, and a title-case row 1. Noted in the earlier review, and row 2 and 3 now put them one line apart.
- **Passes.** [MARKUP] No new size or weight, and no arbitrary value, was added.

### Pillar 5: Spacing (2/4)

Modal strings, characters. "Row 3 body" is the unsaved sentence, the longest count variant, the hidden sentence and the ingress.

| Locale | Title (row 1) | Unsaved | Longest count | Hidden | Ingress | Row 3 body | Continue | Failed | Longest word |
|---|---|---:|---:|---:|---:|---:|---:|---:|---|
| en | 34 | 59 | 100 | 93 | 96 | 348 | 22 | 95 | automatically |
| et | 32 | 68 | 80 | 81 | 101 | 330 | 25 | 107 | valimisnõustajas (16) |
| fi | 23 | 73 | 93 | 79 | 108 | 353 | 26 | 91 | Uloskirjautumista (17) |
| fr | 40 | 92 | 113 | 105 | 112 | 422 | 19 | 112 | automatiquement (15) |

- **Estonian and Finnish are no longer than English in a way that matters**: 330 and 353 against 348. French is the worst of the three, 21% over English. Luxembourgish has the longest failure message, 128. No word is long enough to overflow at 320 px, so WCAG 1.4.10 has no word-level risk [PREDICTED].
- **WARNING, 200% zoom scrolls the worst row, with focus at the bottom.** [PREDICTED, estimate] 1280 by 720 at 200% is 640 by 360 CSS px, right at the `sm` boundary. A title, four paragraphs with `mb-16` and two buttons at the 44 px minimum come to about 400 px or more, in any of the three locales. Focus on Continue then scrolls the top of the box, which holds the unsaved sentence, out of view. Content stays reachable by scrolling, so 1.4.10 is not failed by this, but the reader lands below the warning. It compounds priority fix 1.
- **WARNING, phone portrait.** [PREDICTED, estimate] At 375 by 812 row 3 in French is about 13 lines and should fit `modal-bottom` without scrolling. At 320 by 568 it probably does not.
- **WARNING, the Alert's ✕ on a phone.** [MARKUP] `sm:!pr-[2rem]` reserves room only from `sm` up. Under `sm` the text is `w-full` and the ✕ is at `top-2 right-2`; the text button has `-mt-16`. [PREDICTED] the ✕ can touch the first line. A 128-character message is a harder test than this Alert has probably had. At 200% zoom landscape the Alert takes much of a 360 px height while it stays until closed, and may cover the page's own action at the bottom.
- **Passes.** [MARKUP] The buttons' `w-full`, `min-h-touch` and `h-auto` allow the label to wrap and keep the 44 px target. The ✕ of both is `btn-sm`, below that, which AA in 2.1 does not require.

### Pillar 6: Experience Design (2/4)

State coverage:

| State | Contestant | Admin |
|---|---|---|
| In flight | Modal only; none on direct path or after the count | **None**, and no guard against a second press |
| Failure | Alert from the layout | Alert from the button, in `Banner` |
| Success | Navigates, with a full load as fallback | Navigates; a rejected `goto` is not handled |
| Never answers | Loading indefinitely, ✕ live | Nothing |

- **WARNING, should be BLOCKER if confirmed (W1): the dialog lacks a description.** See priority fix 1. [PREDICTED for what readers say]
- **WARNING, ✕ and Escape.** See priority fix 2. [MARKUP]
- **WARNING, the pressed button disables under focus.** [MARKUP] Loading sets native `disabled` and `tabindex=-1` on the element that has focus, and Continue is disabled too. [PREDICTED] focus falls to the dialog or the document, and Tab goes to the ✕. Nothing announces the running state, as there is no live region, and the name "Loading… Loading…" (the `sr-only` label of `Loading` plus the button text) is in a disabled button that a reader may not reach.
- **WARNING, the alert's announcement is not safe.** [MARKUP] `Alert` mounts `inert`, since `isOpen` starts false and `onMount` opens it, so the live region comes into the tree with its text already in it. A region's content is announced most reliably when it changes in a region already present. On a failed sign-out from the modal, the flag is set before `leave` closes the dialog, and I did not establish whether `Alert` mounts first; if so it mounts in a page a modal dialog has made inert. [PREDICTED] the message can go unspoken in either case, with the failure otherwise silent for a blind user. Fix: close the modal before raising the flag, and in `Alert`, render the region empty and insert the text after opening. `aria-modal="false"` on `role="alert"` is also not an allowed use, though harmless [MARKUP].
- **WARNING, Alert placement and focus.** [MARKUP] In the contestant app it sits after `Layout`, outside the landmarks, so a user who misses the announcement cannot find it by landmark. Focus is not moved, which is right for an alert. In Admin it renders inside the `Banner`; it is `fixed`, and I found no transform or z-index on the header, but this was not seen on screen.
- **WARNING, how it clears.** [MARKUP] Close, ✕, or a new attempt, which clears it at the start of `#runLogout`. It survives navigation in the contestant app, since the flag is held by a context over the whole app section, and goes on a reload. It lasts, which is right for a message about a session, but after a reload-free recovery its "may still be logged in" lingers until closed. Admin's goes when the button unmounts, so the two apps differ.
- **WARNING, a second press with the message up reopens the modal first.** [MARKUP] With a guard or a task left, retry goes through the modal again. The Alert is behind it until a sign-out starts. Acceptable, though the retry the message asks for costs two presses.
- **WARNING, the `<progress>` has no accessible name.** [MARKUP] `TimedModal.svelte:157`. WCAG 4.1.2 for a native progress bar. Also `id="modal-progress"` is fixed, and the header's and the page's LogoutButton are mounted together on the entity home, `NothingToEdit` and `ReadFailure`, so the id is duplicated (WCAG 4.1.1 in 2.1). No axe scan reaches the modal, by `deferred-items.md`.
- **Accepted by ruling, recorded.** The 30-second count: WCAG 2.2.1 allows a warning with 20 seconds or more and a simple way to extend, and Continue does that, provided the warning is perceived, which W1 puts in doubt. `T-179.1-104`, the message and edits left on a screen when a sign-out fails at the count's end, is the operator's.
- **Passes.**
  - [MARKUP] **Safe default focus.** `focusFirstDescendant` takes the first focusable in DOM order, which is Continue, the safe choice. `showModal` does the same before the timer. Enter on it stays.
  - [MARKUP] Tab order Continue, Log out, ✕ puts the visually top ✕ last, which is minor against 2.4.3.
  - [MARKUP] The backdrop does not close the modal. Navigation closes it without counting as an answer. `leave` runs once, however often asked. A failure logs and shows, and the page stays.
  - [MARKUP] The `Icon` change writes nothing after a superseded import.
