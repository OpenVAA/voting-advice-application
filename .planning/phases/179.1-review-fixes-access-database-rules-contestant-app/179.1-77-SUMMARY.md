# Phase 179.1 Plan 77: The password toggle from the keyboard, and a held Back after a failed sign-out Summary

**The password toggle now keeps the focus when it is pressed from the keyboard (a click whose `detail` is 0), focuses the field only for a pointer press, and exposes its state with `aria-pressed` under the one name "Reveal password". A Back or Forward pressed while a sign-out runs is replayed as the same move in the history (`history.go(delta)`) when the sign-out fails, so Forward returns to the page. Along the way, the Contestant App's Log out buttons each register their own navigation hold, because one shared function in SvelteKit's callback set was removed for every button when the home's own button was destroyed.**

## For the operator's reading

A keyboard user on any password field (the sign-in form, registration, settings, the Admin App's login) can now Tab to the eye button and press Space or Enter as often as they like. The button keeps the focus and toggles each time. Before this plan the first press moved the focus into the field, so a second Space typed a space into the password. A screen reader is now told whether the button is pressed: `aria-pressed` is `false` while the entry is masked and `true` while it is shown. The button keeps one name in both states, "Reveal password" in English (C7 a). The icon still changes, and the "Hide password" string is gone from all seven catalogues. A mouse or touch press behaves as before: it shows or hides the entry and leaves the caret at the end of the field.

A user who presses Log out where it signs out at once, presses Back while the sign-out is still running, and whose sign-out then fails, now ends up one entry back, on the page Back would have shown. Forward returns to the page they were on. Before this plan the Back was replayed as a new link, which added an entry: Forward led nowhere, and a second Back returned to the page they had asked to leave. Measuring this also uncovered a worse defect, which is now fixed. After the user left the candidate's home for another page, a Back or a link pressed during a sign-out started there was not held at all. Each Log out button on a page registered the same function with SvelteKit, which keeps these functions in a set. When the home's own Log out button was destroyed, the header's button lost the hold as well. The navigation then went ahead while the sign-out was still running.

What stays unproven:

- **What VoiceOver, NVDA and TalkBack say at the toggle.** `aria-pressed` and the name are asserted as Chromium computes them.
- **The back gesture on a phone.** Only the page's own `history.back()` and Playwright's Forward are driven.
- **WebKit and Firefox.** The keyboard press's `detail === 0` is the platform convention, observed in Chromium only.
- **A held Back during the logout modal's sign-out** (the modal's Log out or the end of its count). It goes through the same `holdNavigationWhile`, and only the unit cases cover it. The browser test drives the sign-out that runs at once.
