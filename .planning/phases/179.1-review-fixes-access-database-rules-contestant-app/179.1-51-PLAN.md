## The operator's rulings of 2026-11-03, verbatim and locked

1. **WR-10 fix: server loads.** Give the entry routes that lack one a no-data server `load`, so a client-side navigation reaches the gate and a live session is sent home, in dev and production alike. Withdraw the message on every entry route of the app's gate through one shared exported function used by both layouts (the review's `isEntryRoute(routeId)` in `appGates.ts`, IN-20). The alternative of re-reading the session on entering the route is rejected.
2. **The auth-outage row (cookies kept, service down): record as accepted, no code.** Register it as an accepted risk. Correct T-179.1-103's wording (the user is told only while the document stays "and until a link reaches the gate") and the guide. Do not make the session read distinguish "no session" from "could not check".
3. **UI safety gate: waiver extended to this gap plan,** limited to no new component, no new or edited message key, and no visual change. If execution finds it needs one of these, the plan STOPS and returns to the operator instead of proceeding. There is no UI-SPEC and none is to be generated. The behaviour change the operator accepted: when the message appears, and that Back to a login screen with a live session lands on the home.
4. **Take `email-sent` off the list.** Remove `ContestantAppEmailSent` from the Contestant row's `entryRoutes` in `APP_GATES`, with no load on it. A signed-in user who asks for a link on the forgot-password page keeps seeing the truthful "email sent" screen. The operator accepted these consequences when ruling: a live session can stand on that screen, including by address, where the gate redirects it today; and after cleared cookies, Back there could still show the false failed-sign-out message until the next entry route.

2. **The history, measured and read.** In `node_modules/@sveltejs/kit/src/runtime/client/client.js`, `navigate` follows a redirect by calling itself with the same `popped`, and writes history only under `if (!popped)`. So a Back the gate redirects pushes nothing and replaces nothing. Measured in `179.1-planning-probe-4` and `-prod-postfix`:
   - `history.length` is 5 at every step of a walk through five entries.
   - A further Back moves one entry. Forward moves one entry and lands where it should. A Back past the entry screens reaches `about:blank`. **The user is not trapped.**
   - **The address bar keeps the entry route's address.** After Back to the login entry, `location.pathname` is `/contestant/login` while the page is the home, until the next navigation. A reload there sends a document request, which the gate answers with the home, and the message goes with the document. This is the framework's behaviour on a popped navigation. It is not changed here and it goes on the operator's list in plan 53.
   - So `expectOnHome`, which reads the address, cannot be used after such a Back. The tests read what is shown: a new step `expectHomeShownAtAnyAddress`.

3. **A Back that waits.** `page.goBack()` returns when the address has changed, while the old page is still in the DOM, so a step that says the home is shown can pass on the page being left. The new step `goBackAndSettle` takes focus off first, goes back, and waits with `waitForNavigationFocusReset` for the root layout's focus reset, which runs in `afterNavigate`. Measured in both builds: it lands in about 100 to 360 ms on the Contestant App's pages. Focus is taken off first because focus already on the heading would satisfy the wait.

4. **Sign-ins must happen inside the app.** A form posted before the page's script has loaded is a document navigation, and a Back across documents is a different path: the document reloads, and the message goes with it, so a test would pass for the wrong reason. Test 1 and test 3 reach the sign-in screen by `followSignInInsideTheApp`, a new step that waits for the focus reset before it presses. Test 2 opens the sign-in screen by address and calls `signInScriptLoaded` before `login`.
