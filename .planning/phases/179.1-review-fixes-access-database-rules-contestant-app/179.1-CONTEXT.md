### A. Access and security
- **D-05 (A1):** Only `invitations_email_target_key` becomes a partial unique index over open rows
  (`claimed_at IS NULL`). `invitations_code_hash_key` stays over every row, so a used code can never be issued
  again. This reverses D-07/D-08 of Phase 174. pgTAP covers three cases: re-invite after claim, re-invite after the
  claimant is deleted, and promotion from project editor to project admin. The E2E harness's service-role delete
  workaround for this case should become unnecessary. Research confirms whether it can be removed.
- **D-06 (A3a):** All three mailed link types that `GET /api/auth/callback` verifies (`magiclink`, `recovery`,
  `email_change`) pass through one confirm page.
- **D-07 (A3b):** When the browser is already signed in to another account, the confirm page says so and says that
  continuing signs that account out. **Continue** signs out, then verifies. **Cancel** returns to the signed-in
  account's app. The page cannot name the incoming account, because the token is unverified until the POST.
- **D-08 (A3c):** The confirm page belongs to neither app (e.g. `/auth/confirm`), because 179.2 reuses it for the
  Admin App's links. Its `GET` renders a form that holds `token_hash`, `type` and `next`. Its form action `POST`s
  to verify, and SvelteKit's form-action origin check is the CSRF guard. The mails link to the page.
  `GET /api/auth/callback` with a token stops verifying and redirects to the page. After the POST the callback's
  existing order is kept: verify, claim, refresh, land. The link path changes in
  `functions/account-access/signInLink.ts` and in the mails. The E2E specs that open a mailed link press the button.
  — **Reversibility:** costly — the link path is written into the mail templates, the Edge Function and every E2E
  spec that opens a mailed link.
- **D-09 (A3d):** The page's strings are written in all 7 locales now, so the raw-key gate (CSCAN) passes. They are
  flagged for the native-speaker check that the E1 UAT already includes.
- **D-10 (A5):** No code. File a todo on the `deployment` workstream: measure the shared per-IP `sign_in_sign_ups`
  budget on the first hosted project, and if it is confirmed, forward the client IP through a header the auth
  service trusts. Record the issue as a pre-launch risk on the docs' auth / security page (D-24).
- **D-11 (A7a):** `public.user_can` and `public.user_has_account_grant` read `public.grants` for `auth.uid()` instead
  of the JWT `grants` claim. Reads and writes then share one source, and a revoked grant ends both at once. The
  access-token hook keeps writing the claim, and only the frontend's app-entry gates read it. This changes about
  111 call sites in `302-rls.sql`, 13 in `400-storage.sql` and 7 in `503-entity-rpcs.sql` through the function
  alone; the policies are not edited one by one. — **Reversibility:** costly — every RLS decision moves to the new
  source; undoing it is another migration plus a revert of the rewritten pgTAP census.
- **D-12 (A7b):** Cost is proven by measurement:
  - Add an index on `public.grants` that leads with `user_id` if none exists. Research confirms; it is *inferred*
    to be missing.
  - Run `EXPLAIN ANALYZE` on an editor's and an admin's entity, nomination and storage list reads, before and after.
  - Accept only if a 1 000-row read stays within 2× and the E2E wall-clock grows by no more than 10 %.
  - If either bound is broken, read the caller's grants once per statement (an `InitPlan`, as the
    `(SELECT auth.jwt())` pattern does today) and measure again.
- **D-13 (A7c):** The pgTAP rows that pin "revocation takes effect at token refresh" are rewritten, not deleted, to
  assert the new rule: a grant deleted mid-session denies the next read and the next write made with the same token.

### B. Rules the database does not enforce
- **D-14 (B2a):** Add one private helper, `project_answers_locked(project_id)`, the twin of
  `project_nominations_locked`. It is a conjunct on:
  - the entity-scope nomination policies;
  - `set_entity_nominations`;
  - the entity self-update policies of candidates and organizations (answers and profile fields), since F3 found the
    answers lock enforced nowhere in the database;
  - their storage write policies (portraits and logos).

  — **Reversibility:** costly — it touches the entity, nomination and storage policies and the RPC; undoing it is
  another migration.
- **D-15 (B2b):** Only the entity-scope policies get the conjunct. Every project-, account- and global-scope policy
  (`admin_*`, which project editors and admins use through `project.edit_nominations` and the matrix) is untouched,
  so every holder of a project grant passes. This keeps the operator's note that project editors can still edit
  nominations while answers are locked. pgTAP asserts both sides: an entity editor refused, a project editor and a
  project admin admitted.
- **D-16 (B2c):** File the todo "a project editor exempts one entity from the answers lock" in
  `.planning/todos/pending/` (the operator's note on B2). A write refused by the new lock reaches the user as the
  existing "not editable" note (`notEditableNote`), not as a generic save failure.
- **D-17 (B5a):** The Admin App has no settings editor (F2), so there is no save path to validate. Instead:
  - The one writer on the tree, the dev-seed writer's settings write, validates with the shared app-shared schema,
    so a seed template with a typo fails.
  - Add "validate with the shared schema on save" to
    `.planning/todos/pending/2026-10-02-app-settings-shallow-merge-and-no-admin-editor.md`, so the editor does it
    when it is built.
  - The database stays as it is.
- **D-18 (B3):** The constituency rule moves from `set_entity_nominations` into `validate_nomination`, so it covers
  every write, admin writes and `bulk_import` included, because a trigger cannot tell them apart. The dev-seed
  writer and the bulk import link elections to constituency groups before they insert nominations. pgTAP covers the
  direct insert, the admin insert and the bulk path.
- **D-19 (B4):** One service-role RPC takes `pg_advisory_xact_lock` on the identity's key and finds or creates the
  user's entity in the same transaction. `identity-callback` calls it in place of its separate lookup and insert.
  Existing duplicates are not cleaned up, because nothing is deployed.

### C. Contestant App behaviour
- **D-20 (C4):** No entity read failure signs the user out, whether it is a schema mismatch, a network error or a
  server error. Every such failure shows the entity layout's error view, which has a "Try again" action, the support
  block and logout. The failure is logged. This reverses D-11 of Phase 173 for read failures.
- **D-21 (C5):** One settings page at the Contestant App's root, `/contestant/settings`, behind the same gates, for
  every user. The entity menu and the "nothing to edit" view link to it. The entity-scoped URL
  `[entityType]/[entityId]/settings` redirects there.
