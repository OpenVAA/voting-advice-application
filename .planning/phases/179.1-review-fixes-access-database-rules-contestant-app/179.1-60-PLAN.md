## Rulings carried by this plan

1. **The signal exists; nothing listens.** In a browser with `persistSession`, auth-js opens a `BroadcastChannel` named by its storage key, and every local sign-out ends in `_notifyAllSubscribers('SIGNED_OUT')`, which posts to it; a receiving tab re-notifies its own subscribers. Measured in the diagnosis: the event and the `storage` event both reach the second tab, and the app has no subscriber for either.
2. **Through the writer.** Outside the boundary a file may not reach the client's `auth`. `DataWriter` gains `onSignOut(handler)`, typed with `SignOutOrigin = 'here' | 'elsewhere'`, returning the function that unsubscribes; `UniversalDataWriter` forwards it to `_onSignOut`; `SupabaseDataWriter` subscribes `this.supabase.auth.onAuthStateChange` and calls the handler on `SIGNED_OUT` alone. In the browser the writer is built on the tab's one browser client, so every writer of the tab reaches the same subscription list.
3. **This tab's own sign-out.** auth-js emits the event inside `signOut` before it returns. `_logout`'s browser arm counts the sign-outs running in this document, a module counter around the browser client's `signOut`, and `_onSignOut` reports `'here'` while it is above zero and `'elsewhere'` otherwise. A server render never increments it. An auth-js sign-out of its own, after a refresh the service refused, reads `'elsewhere'`, which is right: the session ended outside this tab's flow.
4. **What each app does with `'elsewhere'`.** Each context subscribes in an `onMount` registered from its constructor, which runs during its layout's initialisation, and unsubscribes on destroy. The Contestant App: when no logout of this context is running, it discards the guarded edits, resets its store, and, if the page reads as signed in, goes to its login page the way `#runLogout` does, with the guards stood down and a full load when the address did not move; the shared steps move into one private method both call. The Admin App: if the page reads as signed in, it goes to its login page as its `LogoutButton` does. `'here'` changes nothing in this plan; plan 61 adds the draft removal both origins need.
5. **A stored value follows storage.** `PersistedStateImpl` reads storage once and re-saves on every `set` or `update`. Handles of `localStorage` register in a module-level registry that holds them weakly, so a dropped handle is not kept alive, and one `storage` listener, added in the browser only, updates them: a removed key or a cleared storage returns the handle to its default without saving it, a new value is read as the constructor reads one, and nothing is written back. `sessionStorage` is per tab and is left as it is. `removePersistedByPrefix`'s docstring keeps its warning for the document that removes, where no `storage` event fires.
6. **The residue.** A sign-out made only by a server, in another tab, sends no browser signal; a navigation that makes no request in a tab that stays open then still shows the stale page until it makes one. Plan 59 sends such a tab to the login page on its next protected load in the Admin App and on the gate's next request in either app. It goes on plan 66's list, with no ruling attributed.
