### Critical Issues

#### CR-02: With the logout modal open on a question page, a navigation to a route without `questionId` throws in the header and the next page is not rendered

**File:** `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:66`, `apps/frontend/src/routes/contestant/(protected)/[entityType=servedEntityType]/[entityId=uuid]/(nominated)/questions/[questionId]/+page.svelte:79-81,91,148,150`, `apps/frontend/src/lib/components/preventNavigation/navigationGuards.ts:37-39`

**Issue:** `unsavedOnPage = $derived(modalOpen && hasActiveNavigationGuard())` calls the page's `isActive` in `LogoutButton`'s tracking scope. On the question page that is `!bypassPreventNavigation && hasUnsaved && !answersLocked`. With no store draft, `hasUnsaved` reads `heldInfo`, which reads `question.id`, which reads `questionData`, and `questionData` calls `error(500, 'No questionId provided.')` when the route has no such parameter.

SvelteKit writes the new `constructors` and `page.params` in one batch, and the flush walks the effect tree in order. `Layout.svelte:85-101` puts `<Header>` before `{@render children}`, and the pyramid block that swaps the page sits inside `children`. So the header's `LogoutButton` re-evaluates the page's derived before the page is destroyed. The throw leaves the flush and the page block never runs.

What triggers it:

- Browser Back or Forward from a question page while the modal is open, to the questions list or the home. The modal needs no edit: a counted task opens it. With an unsaved edit it happens after the user agrees at the native question.
- The page's own `goto` at `+page.svelte:269`, when Save was pressed, then Log out, and the save returns while the modal is open, for a target other than another question.

The docblock's sentence "A navigation closes the modal, so it never counts down on a page it was not opened on" is true after this, because `afterNavigate` still fires. The user then has a closed modal over the old question page, with the address of the new one. Anything that reads `question` on that page, Save among them, runs into the same throw until another navigation succeeds.

**Why the suite is green:** the logout's own `goto` also runs with the modal open, but on a successful sign-out `page.data.session` goes in the same batch. `Banner.svelte:49`'s `{#if}` then destroys the button before its effects run. The suite's Back test, at spec line 344, is on the profile, whose guard has no throwing derived. No test presses Back on a question page with the modal open.

**Measured (Svelte harness; `back.svelte.test.ts`, `bannerif.svelte.test.ts`):**

| Scenario, modal open on a question-like page | Uncaught | New page rendered | Old page still there |
|---|---|---|---|
| Nothing unsaved, modal for a count, Back to the list | `{status: 500, body: {message: 'No questionId provided.'}}` | no | yes |
| Unsaved edit agreed, Back to the list | the same | no | yes |
| Control: navigation to another question | none | not applicable, the page stays | yes, on the new question |
| Control: `isActive` chain reading the param instead of the throwing derived, Back to the list | none | yes | no |
| Control: `page.data.session` cleared in the same batch, with the button inside `{#if page.data.session}` | none | yes | no |

A later state change on the block recovered in the harness, so a later working navigation recovers, as a reload would.

**Confirmed by reading:** the chain, the order in `Layout.svelte` and `.svelte-kit/generated/root.svelte`, and which test covers what.

**Not run:** a real browser against a real SvelteKit app. The harness replays `navigate`'s sync writes rather than running SvelteKit, and copies the page's derivations rather than mounting the page. `onNavigate`'s View Transition wrapper was not included. If the throw makes `goto` reject in a real browser (plan 44's ruling 7 says a throw while rendering can), the Back path is an unhandled rejection with the same stale page.

**Fix:** make the guard chain unable to throw, and stop reading it across a route change.

```svelte
// questions/[questionId]/+page.svelte: the guard's chain reads the param, as `answersLocked` beside it already does.
const heldInfo = $derived(heldOpenAnswer?.questionId === parseParams(page).questionId ? (heldOpenAnswer?.info ?? null) : null);
```

```svelte
// LogoutButton.svelte: a second layer that holds for any future guard. onNavigate runs before SvelteKit writes the new page, so the derived short-circuits on modalOpen.
onNavigate(() => {
  if (!modalOpen) return;
  closingForNavigation = true;
  timedModalRef?.closeModal();
  closingForNavigation = false;
});
```

Document on `NavigationGuard.isActive` that it runs in another component's tracking scope and must neither throw nor write state. Add red-first cases: a unit case with a guard whose `isActive` depends on state that a navigation invalidates, and an E2E step on a question page where Log out opens the modal, Back shows the list and the modal is closed.

#### WR-09: A close the platform makes leaves the count running, so 30 seconds later the session ends and the edits are discarded with no modal on screen

**File:** `apps/frontend/src/lib/components/modal/ModalContainer.svelte:91-96,131-139`, `apps/frontend/src/lib/components/modal/timed/TimedModal.svelte:129-130`, `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:105-108`

**Issue:** `ModalContainer` learns of a close only through its own `handleClose`, reached by the ✕, Continue or a `keydown` of Escape. The `<dialog>` has no `oncancel` or `onclose`. A close the platform makes without a `keydown`, such as the back gesture on Chrome for Android through its close watcher, or `requestClose`, removes the dialog and leaves `isOpen` true. `TimedModal`'s timer then checks `isOpen` and calls `onTimeout`. Plan 44 made that count destructive: the user dismissed the modal, sees the page, and is signed out with the edit discarded. `keepGuardedEdits` does not run either. This is a session that ends with neither an agreement nor a count the user can see.

**Measured (`nativeclose.svelte.test.ts`):** with a guard active, firing `cancel` and `close` on the dialog with no `keydown` gave `{closed: true, logoutCalls: 1, keepCalls: 0}` after the clock passed the count.

**Confirmed by reading:** no listener exists. **Not run:** an Android device. That the back gesture closes a modal `<dialog>` this way is platform behaviour known from Chrome's documentation, not observed here. If it is confirmed on a device, treat this as a blocker: it is data loss on the phone the app is used on.

**Fix:** in `ModalContainer`, add `onclose={() => { if (isOpen) handleClose(); }}` on the `<dialog>`. Since `handleClose` calls `close()` and a closed dialog does not fire `close` again, the guard on `isOpen` keeps it idempotent. A `close` that follows Escape or the ✕ finds `isOpen` already false.

#### WR-10: The failure message is not withdrawn when the session ends, and stays on the login screen and into the next sign-in

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:578,584,610-611`, `apps/frontend/src/routes/contestant/+layout.svelte:94-98`

**Issue:** `#logoutFailed` has two writers: the start of a logout and the message's own close. `#reset` does not touch it, and nothing watches the session. In the audit's row 2, the cookies are already cleared on the 502, and `page.data.session` is stale until the next load. If the user follows a link instead of pressing Log out again:

1. The gate redirects to the login page.
2. `routes/contestant/+layout.svelte` stays mounted, so the same context holds the flag.
3. The login screen says "You may still be logged in, so please try again", and offers no Log out, because `Banner.svelte:49` needs a session.
4. The sign-in form uses `use:enhance` and `applyAction` (`login/email/+page.svelte:119,147`), which is a client navigation, so the sentence follows the user into the session they have just started.

The same happens when row 1 or row 3 is followed by a session that expires. The answer to "can it be stale": yes, in this way. Plan 45's ruling 3 chose this shape so that a message could not outlive the failure, and here it does.

**Confirmed by reading:** both writers, the layout's lifetime and the client-side sign-in. **Not run:** no test navigates after a failure, in either direction. So the survival across in-app navigation that the plan intends is itself unpinned: tests 8 to 10 stay on the page or press again.

**Fix:** withdraw it when the session is gone, since then there is nothing left to retry.

```svelte
// routes/contestant/+layout.svelte
$effect(() => {
  if (contestantCtx.logoutFailed && !contestantCtx.isAuthenticated) contestantCtx.clearLogoutFailure();
});
```

Add an E2E step to test 10: follow a link after the failure, end on the login screen, and assert that the message is gone. Add a step to test 8 that navigates to another page and asserts that the message is still there.

#### WR-11: The Admin App's message is painted under any positioned content of the page, its Close included

**File:** `apps/frontend/src/lib/dynamic-components/logoutButton/LogoutButton.svelte:51-55`, `apps/frontend/src/lib/layouts/main/Header.svelte:70,74`, `apps/frontend/src/lib/layouts/main/Banner.svelte:53`

**Issue:** the Admin button renders `Alert` where it stands, inside `<header>`, whose inline `view-transition-name` makes it a stacking context. So `Alert`'s `fixed z-30` counts only inside the header, and the header paints at level 0 of the page. Later positioned content in `<main>` paints over it and takes its clicks. Every `Button` is `relative` (`Button.svelte:105`), and `admin/(protected)/jobs/+page.svelte:94` has a `relative` block too.

The rule `.vaa-basicPage-actions > * > button:not([disabled])` in `Banner.svelte` also recolours the alert's ✕, as the `Alert` root is a direct child of that container. The Contestant App's message is unaffected, as the layout renders it after `<Layout>`.

**Measured (`stack.mjs`, Chromium):** a `position: fixed; z-index: 30` child of a `position: relative` header, over a `position: relative` block in `main`. `elementFromPoint` over the alert returned the positioned block with `view-transition-name: persistent-header` on the header, and the alert with it set to `none` as the control. The `role="alert"` announcement is not affected by paint.

**Confirmed by reading:** the markup above. **Not run:** the Admin App itself. How much of the message a given admin page covers was not established. The deferred entry's "not driven in a browser" is why no run has seen it.

**Fix:** render the Admin message from `routes/admin/+layout.svelte`, outside `Layout`, with the flag on the admin context, as the Contestant App does. This also removes the state from a button that `Banner` unmounts.

#### WR-12: A screen-reader user is not told what the modal says when it opens, and the native question it replaced was read out

**File:** `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:120-127`, `apps/frontend/src/lib/components/modal/ModalContainer.svelte:116-117,131-137`

**Issue:** the dialog has `aria-label={title}` and no `aria-describedby`. `LogoutButton` passes no `autofocusId`, so focus goes to the first focusable descendant, Continue. On opening, the dialog's name and "Continue entering data" are what is announced. "You have unsaved changes. They will be lost if you log out." and "You will be automatically logged out after N seconds" are plain paragraphs behind them, not linked to the dialog. Plan 44 moved a destructive warning from `window.confirm`, whose text assistive technology reads, to this surface, with a count that discards at its end. The checklist asks that the changed parts are fully usable with screen reading, and WCAG 2.2.1 asks that the user is warned of a time limit before it ends.

The deferred entry on axe does not cover this: axe would not flag it, as the markup is valid.

**Confirmed by reading:** the attributes and the focus target. **Not run:** no screen reader. What each one announces on opening varies, and that a linked description would close the gap is the ARIA dialog pattern, not a measurement here.

**Fix:** give the body an id and link it. Pass `aria-describedby` from `LogoutButton` through `restProps`, which `ModalContainer` already spreads onto the `<dialog>`:

```svelte
<TimedModal aria-describedby={bodyId} ...>
  <div id={bodyId}> ...the paragraphs... </div>
```

#### WR-13: The Admin App's handler leaves a rejected `goto` unhandled, and a signed-out page reading as signed in

**File:** `apps/frontend/src/lib/dynamic-components/logoutButton/LogoutButton.svelte:36-46`

**Issue:** plan 45 rewrote this handler so that the sign-out is inside `try`, and left `await goto(...)` after it, outside. A `goto` that rejects after a successful sign-out is an unhandled rejection, with no message and no departure: the state WR-07 fixed for the Contestant App, on the other app. The deferred entry's "the sign-out cannot strand one" holds for a refused navigation, as no Admin page mounts a guard, and not for a rejected one. There is also no check that the page moved and no re-entrance guard, so two presses make two sign-outs and two navigations. The first failing while the second is in flight shows a message beside a sign-out that then succeeds, though `Banner` unmounts it when the session goes.

**Confirmed by reading.** **Not run:** no run makes a `goto` reject, here or in plan 44.

**Fix:**

```ts
try {
  await goto(getRoute.current(redirectTo!), { invalidateAll: true });
} catch (e) {
  log.error(`Error navigating after logout: ${(e as Error)?.message}`);
  location.assign(getRoute.current(redirectTo!));
}
```

Add a `leaving` flag as in the Contestant App's button.
