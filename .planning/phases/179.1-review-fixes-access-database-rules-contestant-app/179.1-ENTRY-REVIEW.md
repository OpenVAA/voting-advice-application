### Warnings

#### WR-16: The redirect loop does not need a failed sign-out: the Admin App's `!userData` arm reaches it with no sign-out at all

**File:** `apps/frontend/src/routes/admin/login/+page.server.ts:21-23`, with `apps/frontend/src/routes/admin/(protected)/+layout.ts:20-32` and `apps/frontend/src/lib/auth/getUserData.ts:46-60` (the last two outside the list)

**Issue:** the new load brings a client navigation to `/admin/login` to the gate. Plan 52's ruling 7, `T-179.1-130` and the UAT list in `179.1-53-SUMMARY.md` all say the resulting loop "needs a sign-out to fail while the session reads as alive". That holds for `handleError` and for the Contestant App's `signOutToLogin`. It does not hold for the first arm of the Admin load:

```ts
const userData = await getUserData({ fetch, client: supabaseClient }, { parent });
if (!userData) {
  // Not authenticated - redirect to login
  return redirect(307, buildRoute({ route: 'AdminAppLogin', locale: lang, errorMessage: 'loginFailed' }));
}
```

`getUserData` answers `undefined` in two cases that do not mean "not authenticated", and this arm signs nobody out in either:

1. **A failed read, with the session alive.** `_getBasicUserData` throws on a failed `terms_of_use_acceptances` read or a failed or malformed `get_user_entities`, and `getUserData` catches that into `undefined`.
   - An administrator signs in through the form. `(protected)/+layout.ts` runs in the browser, the read fails, and the load redirects to `/admin/login?errorMessage=loginFailed`.
   - The data request reaches the gate, which finds the session and answers with `/admin`. The universal load runs again, because the current page is still outside `(protected)`.
   - After twenty hops `navigate` (`client.js:1818-1843`) ends on the root error page with `Redirect loop`.
2. **A stale session in the page data, with no failure anywhere.** `parent()` returns the `session` of `admin/+layout.server.ts`, which does not rerun on a link.
   - A user signs out in tab A, so the data reads `session: null`, and signs in in tab B.
   - In tab A, Back to an `/admin` entry runs the load, which reads `null` and redirects to the login page. The gate finds the cookies and answers with `/admin`.
   - The hop to `/admin` makes no server request, because no server node is invalid, so `session` stays `null` on every hop and the same twenty hops follow.

**What changed:**

| | At `8c1c435a2` in production | Now |
|---|---|---|
| Client navigation | stops on the login form, because that route had no load | twenty hops, then the root error page |
| Document request | browser's "too many redirects", 303 and 307 in turn | the same |
| Dev server | the same hops as now | the same |

So the document path is not new. The client path in production is new, and the sign-in form above is on it. While the read keeps failing, the user cannot reach the login page by any route, and `error.loginFailed` cannot be shown to a live session. No unit test covers `(protected)/+layout.ts`: the `layout.server.test.ts` beside it tests the two feature subtrees' loads.

Ruling 4 does not cover this, and `T-179.1-130` covers it only under a condition the code does not require. The risk is rated low on that condition, so the rating needs a second look.

**Confirmed by reading:** the arm, `getUserData`'s catch, the throws in `_getBasicUserData`, the gate, `load_route`'s invalid-node test and the twenty-hop limit. **Not run:** neither path in a browser, and no run produced a failing read.

**Fix:** tell the two cases apart in the load, so that a failed read does not claim the user is unauthenticated:

```ts
const { session } = await parent();
if (!session) redirect(307, buildRoute({ route: 'AdminAppLogin', locale: lang, errorMessage: 'loginFailed' }));
const userData = await getUserData({ fetch, client: supabaseClient });
if (!userData) error(503, 'The user data could not be read.');
```

The stale case then needs a fresh reading of the session on entering `(protected)`, for example a `routes/admin/(protected)/+layout.server.ts` returning the same `{ userId, expiresAt }` projection, which the universal load reads from `data` in place of `parent()`. This touches the auth path, so it is the operator's choice. If it is not fixed, at least restate `T-179.1-130`, its line in `deferred-items.md` and the UAT line to name both cases.

A related note, also outside the list: `signOutToLogin`'s docstring says a failed sign-out is logged, but `auth.signOut` answers most failures with `{ error }` instead of rejecting (`GoTrueClient.ts:4095-4104`), so its `.catch` never runs. The Contestant App's form of the loop then happens with nothing in the log. Confirmed by reading.

#### WR-17: After cleared cookies the false message also stays on Help, Privacy and the forgot-password page, and the guide names only the "email sent" screen

**File:** `apps/docs/src/routes/(content)/developers-guide/contestant-app/login-and-password-reset/+page.md:69`, `apps/docs/src/routes/(content)/developers-guide/backend/authentication/+page.md:179`, `apps/frontend/src/routes/contestant/+layout.svelte:50-55`

**Issue:** the guide says the message goes on an entry route and gives the "email sent" screen as the one exception, reached "Back". The effect withdraws only on an entry route or when `isAuthenticated` is false, and `isAuthenticated` stays true until the outermost load reruns. So every Contestant App page with no server load keeps the message:

- **`/contestant/help` and `/contestant/privacy`** have a `+page.svelte` alone, are not entry routes, and are not protected. `ContestantNav` offers both to a signed-in user (lines 188-192). After a failure that cleared the cookies, one press in the menu shows Help under "You may still be logged in, so please try again". No Back is needed. No record names these two.
- **`/contestant/forgot-password`** behaves the same. `T-179.1-134` mentions it in passing, as a page reached from the "email sent" screen, but the guide does not, and a user can reach it by a link or by Back without passing that screen.

Ruling 4 accepted this consequence for "there", the "email sent" screen. Truth 16 reads "withdrawn when it is no longer true". The next sign-in is still safe: each of these leads to a sign-in only through an entry route, so WR-15 stays closed. What is wider than recorded is where the false sentence can stand.

The unit cases do not show it either. `leaves the message on the forgot-password page` reads "while the session reads as alive", which covers the true case only.

**Confirmed by reading:** the effect, the route directories and `ContestantNav`. **Measured:** `isEntryRoute` answers false for these routes, in the `answers false for %s` cases that passed. **Not run:** the path in a browser.

**Fix:** no code under ruling 3's limit is needed. Add a sentence to the guide and the auth page: "After a failure that cleared the cookies, the message also stays on the other pages with no server load, Help, Privacy and the forgot-password page, until the next entry route." Then widen `T-179.1-134` and `AR-179.1-10` to name them, and put the wider row on the operator's list, because the ruling as worded does not reach it.

#### IN-21: "Never stands on an entry route" is more than holds

**File:** `apps/docs/src/routes/(content)/developers-guide/contestant-app/login-and-password-reset/+page.md:69`

**Issue:** the gate answers requests. A live session can stand on an entry route where no request is made:

- **A page restored from the back/forward cache.** Across a document boundary, such as a form posted before hydration or a return from the identity provider, Back can restore the old entry screen with its scripts running. No response sets `no-store`, by a search of `hooks.server.ts`, the root layout files and `lib/server`, and the app handles `pageshow` for analytics alone. The Continue on `/contestant/register` posts to `/api/oidc/authorize`, which the gate skips as an API route.
- **A session started in another tab** while this one stands on the screen.

The flag is safe in both, because a restored document holds its own false flag and reads as signed out, so WR-14 stays closed. Only the sentence is too strong. The suite cannot meet the first case: `playwright-core` carries `--disable-back-forward-cache`.

**Confirmed by reading; the switch by a search. Not run** in any browser with the cache on. WebKit is already on the UAT list. **Fix:** "is sent to the app's home on any request it makes, so it does not stand on an entry route after a navigation inside the app".

**File:** `tests/tests/specs/admin/admin-access.spec.ts:285`, `tests/tests/specs/contestant/contestant-entity-selection.spec.ts:1008`

**Issue:** `a sign-out that fails with the session alive: Back to the login page ends on the home` passed before the fix on a dev server, as `179.1-52-SUMMARY.md` records from `179.1-planning-probe-5`, because a dev server treats any `+page.server` as having a load. **Read; the dev-server result is the summary's.** **Fix:** a sentence in the test: "On a dev server this passes with or without the load; C6 is the guard, and this reads what a user meets."

#### IN-23: `expectGateSendsASessionHome` also accepts a redirect to the login page

**File:** `tests/tests/fixtures/admin/adminLoginPage.fixture.ts:138`

**Issue:** `expect(response.headers().location).toContain(adminHome)` with `adminHome` being `/en/admin`, which is a prefix of `/en/admin/login`. The step's own word is "home". The same weak match is at `admin-access.spec.ts:124`, so the new step adds no strength to the check already there.
