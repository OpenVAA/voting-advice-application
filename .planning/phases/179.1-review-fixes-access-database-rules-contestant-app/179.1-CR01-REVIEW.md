### Warnings

#### WR-05: After the full-load fallback the flag clears and the reset runs before the document has left, so WebKit can ask a second time and stay on a reset page

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:571-577`, `apps/frontend/src/lib/components/preventNavigation/navigationGuards.ts:54-61`, `apps/frontend/src/lib/components/preventNavigation/PreventNavigation.svelte:42-49`

**Issue:** `location.assign` only starts the navigation. It returns, the `finally` in `leaveUnasked` clears the flag one microtask later, and `#reset()` follows. Both happen while the document is still there.

Measured order, with a click, a `confirm` answered yes, a `fetch`, then the assign:

| Engine | Order | `beforeunload` saw | Prompts | Answering "stay" |
|---|---|---|---|---|
| Chromium, Firefox | `beforeunload`, assign returned, flag cleared, reset | `flag=true` | `confirm` only | No prompt to answer; ended at the target |
| WebKit | assign returned, flag cleared, reset, `beforeunload` | `flag=false, resetRan=true` | `confirm`, then `beforeunload` | **Stayed on the page, with the reset already run** |

In WebKit the second prompt comes after the user's yes. Answering "stay" gives a page that is signed out and reset but still shown, which is the state CR-01 described and the state ruling 4 says cannot follow a yes.

**Reach (read, not driven in the app):**

- **Which guard:** only one whose `active` survives both the yes and the reset. On the profile and question pages `onConfirm` clears the edits, so they go inactive. The nomination details page has no `onConfirm`, and `somethingToWrite(cards)` reads local state, so it stays active (`details/+page.svelte:594`).
- **How the branch is reached:** `179.1-41-SUMMARY.md` says no known route gets here. There is one. A newer navigation supersedes the `goto`, and `client.js:1809-1812` then returns without moving, so `goto` resolves with `page.url` unchanged. A link clicked during the load or a second press of Log out (WR-06) both do this.
- **Effect on those routes:** the newer navigation is still running, so it should carry the page on to the login screen. The expected effect there is a spurious second prompt, not a stranded page. A stranded page needs a `goto` that fails to move with no other navigation running, and no route to that was found.

In the real app SvelteKit's own `beforeunload` handler also calls the guard's `beforeNavigate` callback, because `is_navigating` is false by then (`client.js:2667-2681`). That callback calls `window.confirm`, which the HTML spec blocks during unload. This part is read, not measured.

The unit test at `contestantContext.svelte.test.ts:2160` pins this order with a synchronous stub of `assign`, so it cannot see the problem.

**Fix:** treat the full load as final, as SvelteKit's `native_navigation` does (`client.js:171-178`). Reset first, assign, then never settle, so the flag stays up for the life of the document:

```ts
await leaveUnasked(async () => {
  await this.#authLogout();
  await goto(loginRoute, { invalidateAll: true });
  if (page.url.href === addressBefore) {
    this.#reset();
    location.assign(loginRoute);
    await new Promise<void>(() => undefined);
  }
});
this.#reset();
```

Change the unit case so the stubbed `assign` asserts the flag is still up and the promise stays pending. A WebKit E2E case would be the only direct check of this branch.

#### WR-06: `#logout` is re-entrant, and one boolean is shared by overlapping calls

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:567-578`, `apps/frontend/src/lib/components/preventNavigation/navigationGuards.ts:43-47,54-61`, `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:67-82,98`

**Issue:** the button stays enabled during a sign-out (`disabled={!timedModalRef}`), nothing shows progress, and `fetch(ROUTE.AuthLogout)` has no timeout. A second press while the first is in flight passes `confirmLeave` unasked because the flag is up, and starts a second sign-out and a second `goto`. From reading:

1. The second `goto` supersedes the first. The first resolves without moving, which falsely triggers the full load of WR-05.
2. The first call's `finally` sets the flag to `false` while the second call is still running. The guards come back mid-logout, and on WebKit that is the second prompt.
3. `#reset` runs once per call.
4. On a profile page with tasks left, the yes has already made the guard inactive, so a second press opens the logout modal and starts its count on a page that is signing out. `afterNavigate` should close it once the page moves.

Double-running the sign-out existed before this change. Items 1, 2 and 4 are new: they come from the flag, the fallback and the new modal condition. A hung POST also leaves the guards down and the page editable for as long as it hangs.

**Fix:** share one run. This also makes the flag safe, since only one `leaveUnasked` can be in flight:

```ts
#loggingOut: Promise<void> | undefined;
#logout = (): Promise<void> =>
  (this.#loggingOut ??= this.#runLogout().finally(() => {
    this.#loggingOut = undefined;
  }));
```

Have `triggerLogout` return early while one is running, so no modal opens. Add a unit case with two overlapping `logout()` calls: one sign-out, one `goto`, no full load.

#### WR-07: A `goto` that rejects after a successful sign-out leaves a signed-out page reading as signed in, and a unit test pins that

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:573-575`, `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.test.ts:2191`, `apps/docs/src/routes/(content)/developers-guide/contestant-app/login-and-password-reset/+page.md:67`

**Issue:** the fallback only runs after `goto` resolves. If `goto` rejects, the session is gone, no full load happens and the page stays. `page.data.session` is still set, so Log out still shows and saves go out with no session. On the profile and question pages `onConfirm` has already discarded the edits.

The docs say "Once the user has agreed the browser always leaves", and threat `T-179.1-88` is mitigated by that promise. A rejected navigation is one that did not move the browser. Ruling 4 says the reset is skipped on a rejection, but it does not say the page should stay.

**Reach:** `_goto` awaits `navigate`, so a throw from an `onNavigate` callback or from rendering the login page should propagate (read in `client.js`, not triggered). The path is rare. Its unit test passes against a fake `goto`, and its title treats "the guard asks again" as the correct outcome, though nothing has been signed in again by then.

**Fix:** log the rejection and fall through to the same check, then invert the test:

```ts
await goto(loginRoute, { invalidateAll: true }).catch((e) => {
  log.error(`Error navigating after logout: ${e?.message}`);
});
if (page.url.href === addressBefore) { /* the full load of WR-05 */ }
```

#### WR-08: The E2E "asks once" stops listening at the first question, so a later dialog on the agreed path cannot fail it

**File:** `tests/tests/fixtures/shared/headerLogout.fixture.ts:121-136`, used at `tests/tests/specs/contestant/contestant-entity-selection.spec.ts:441-442,490,541`

**Issue:** the fixture's doc says it waits "until one native confirm and nothing else has been raised". `expect.poll(...).toEqual(['confirm'])` passes at its first poll after the click returns, and the `finally` removes the listener at once. On a yes, everything that could raise another dialog comes later: the POST, the `goto`, and the unload.

With no listener, Playwright dismisses a dialog by itself (documented behaviour; not run here). So a guard that wrongly asked again during the `goto` would be answered Cancel unseen. The fallback would then still take the page to the login screen, and `expectEndedOnEntry` and `expectSignedOut` would both pass. The nomination details case at line 541 is the exposed one, since that guard stays active after a yes. The step title at line 441 claims "asks once" on the profile, where `onConfirm` makes a second question impossible anyway.

The stand-down is pinned at unit level (`stoodDown` in `contestantContext.svelte.test.ts`), so this is a gap in what the spec claims, not a known product fault. The refused path is sound: its `expectStillSignedIn` is a round trip after the press, and it ends with `expectNoSignOutRequest`.

**Fix:** keep the listener up for the whole test. The existing `nativeDialogs` fixture already does this: call `answerConfirmWith('accept')`, press, and after `expectEndedOnEntry` assert `nativeDialogs.types()` equals `['confirm']`.

#### IN-08: The guard read in `triggerLogout` sits outside the handler that logs failures

**File:** `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:67-72`

**Issue:** `hasActiveNavigationGuard()` runs the page's `active` callback before `logoutLogged` and its `catch`. If it threw, the press would do nothing except raise an unhandled rejection. Inside `#logout`, a throw from `isActive`, `onConfirm` or `onCancel` is safe: it comes before the sign-out and is logged. None of today's three `active` callbacks is known to throw.

**Fix:** move the decision into a `try`, or have the registry treat a guard that throws as active, so a broken guard asks rather than ends the session.

**Fix:** say "when the user refuses" and "when the user agrees", in a navigation or a sign-out.
