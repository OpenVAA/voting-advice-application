# Phase 179.1 Plan 60: A Sign-Out That Reaches Every Tab Summary

**One auth-js `SIGNED_OUT` subscriber per app, reached through `DataWriter.onSignOut`, sends a tab whose session another tab ended to its login page at once; `localStorageState` handles follow another tab's storage events so a removed draft is never stored again.**

## For the operator's reading

What a user with two tabs meets now:

- **Admin App:** the user presses Log out in one tab, and every other open Admin App tab that reads as signed in goes to the login page at once. Before, the other tab stood on the home until it made a request. This was observed on a dev server: the test was red without the change, with the first tab still on `/admin`, and green with it in the full run and in the close.
- **Contestant App:** the user presses Log out in one tab. A second tab holding an unsaved answer then lets go of it, resets the user's data and goes to the login screen at once. Its draft is not in storage afterwards. Before, the second tab stayed on the question with the answer, and its next edit would have stored the removed draft again. That was measured by the diagnosis and is held here by unit cases. Observed on a dev server: red without the change (the second tab stayed on the question) and green with it.
- **Both apps:** a sign-out made by this tab itself is reported as `'here'`, and neither subscriber acts on it. The existing Log out tests pass unchanged in the full run, 686 of 686.
- **Stored drafts:** a `localStorage` handle that another tab removes returns to its default and is not saved again. A later edit stores only what it adds. A cleared storage returns every handle to its default. `sessionStorage` handles are unchanged.

The residue, which no ruling covers (ruling 6, for plan 66's list): a sign-out made **only by a server**, in another tab, sends no browser signal. A tab that stays open then shows its page as it stood after a navigation that makes no request, until it makes one. Its next request to the gate, in either app, and in the Admin App its next protected load, reach the login page (plan 59). The auth page's § *Known residuals* now states this, describing what the user meets and asserting no cause.

What stays unproven:
- WebKit and Firefox were not driven. The cross-tab signal is auth-js's `BroadcastChannel`, plus the `storage` event, and both were observed only in Chromium.
- The tests ran on a dev server only, not in a production build.
- A tab in the background for a long time (throttled or frozen) was not observed. The signal arrives when the tab next runs its tasks, and no run establishes what a frozen tab does with it.
- Plan 61 adds the draft removal both origins need. This plan's `'here'` branch changes nothing.

Observed and inferred:
- Observed: both E2E tests red without their change and green with it, in `179.1-60-green` and `179.1-60-close`. The four unit groups red without their change, or under a mutation (ledger `60-1`, `60-2`).
- Inferred, by reading auth-js 2.117.2: `signOut` awaits `_notifyAllSubscribers('SIGNED_OUT')` before it returns, so the counter is raised while this document's own event is announced. The `'here'` unit case pins the writer's side of that. No run isolated the library's side.
