## Critical Issues

### CR-01: A tab that met the deadline sign-out through a client-side request cannot sign in again until it reloads

**File:** `apps/frontend/src/hooks.server.ts:72-85`, `apps/frontend/src/routes/+layout.svelte:205-224`, `apps/frontend/src/lib/auth/logoutDeadline.ts:23-27`

**Issue:** `logoutDeadlineHandle` signs out every request that carries a `logout-deadline` whose time has passed. Its docblock says it leaves the cookie for "the next document" to remove. The only code that removes it is `settleLogoutDeadline` in the root layout. That runs on `onMount`, and on a `pageshow` whose `persisted` is set. A tab whose root layout is already mounted never runs it again until a full load. Traced sequence, with two tabs of the same browser:

1. Tab A opens the logout modal (`handleOpen` writes the cookie) and is closed during the count.
2. Forty seconds later, tab B makes a client-side navigation that reaches the server (a `__data.json` for a route with a server load). The hook signs the session out, the gate redirects, and SvelteKit's router takes tab B to the login page client-side. The cookie stays.
3. In tab B the user signs in on `/contestant/login/email`. The action (`+page.server.ts:50`) sets the session cookies and answers 303. `applyAction` follows it with a client-side `goto`. Its `__data.json` request reaches `logoutDeadlineHandle` with the passed deadline, and the new session is signed out at once. The gate sends the user back to the login page with no message.
4. This repeats for every sign-in in tab B until the user reloads. An OIDC sign-in started from tab B loses its new session the same way: the callback's redirect reaches the hook before any document has mounted.

The Admin App's login form posts to an action as well, so the same applies there. The E2E test for a closed tab (`contestant-entity-selection.spec.ts:683-728`) opens a new page with a document request, which mounts the root layout, so it cannot see this. Nothing checks a sign-in made after a deadline sign-out.

A related gap: the removal in `setCookie` is host-only (`logoutDeadline.ts:71-74`). A `logout-deadline` set with a `Domain=` attribute is never removed by it, for example by a sibling subdomain tossing a cookie. That cookie forces a sign-out on every request for as long as it lives (see IN-08).

**Fix:** Make the server the party that settles a deadline it has acted on. Remove the cookie in the same response. To let the next document know that drafts must go, hand it a value the hook ignores:

```ts
const logoutDeadlineHandle: Handle = async ({ event, resolve }) => {
  if (hasLogoutDeadlinePassed(event.cookies.get(COOKIE.logoutDeadline), Date.now())) {
    const { error } = await event.locals.supabase.auth.signOut({ scope: 'local' }).catch((e: Error) => ({ error: e }));
    if (error && error.name !== 'AuthSessionMissingError') log.error(`[logout deadline] sign-out failed: ${error.name}`);
    // Not a whole number, so the hook never acts on it again; the next document reads it as "discard the drafts".
    event.cookies.set(COOKIE.logoutDeadline, 'passed', { path: '/', httpOnly: false, sameSite: 'lax', maxAge: 400 * 24 * 60 * 60 });
  }
  return resolve(event);
};
```

`settleLogoutDeadline` would then discard the drafts on `passed` as well as on a passed time. Another option: sign out only a session issued before the deadline, by comparing the access token's `iat` with the cookie's time, so a session created after it is never touched. Add an E2E test in which a second, already-loaded tab meets the deadline sign-out and then signs in.

## Warnings

### WR-01: The deadline is written on the client's clock and enforced on the server's

**File:** `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:125-128`, `apps/frontend/src/lib/auth/logoutDeadline.ts:53-56`, `apps/frontend/src/hooks.server.ts:79`

**Issue:** `handleOpen` writes `Date.now() + logoutModalTimer * 1000`, plus a 10 s grace, from the browser's clock. `logoutDeadlineHandle` compares it with the server's `Date.now()`. The whole margin is 40 s by default. There are two failure modes:

- If the client's clock runs behind the server's by more than 40 s, the deadline has passed for the server the moment the modal opens. Any request made while the modal is open signs the user out, even if they then press Continue. Such a request is, for example, a Back that loads data, or a request from another tab.
- If the client's clock runs ahead by a large amount, the server-side sign-out of a closed tab comes that much later, or in effect never.

Client clocks that are off by minutes are common on unmanaged devices.

**Fix:** Do not compare across clocks. One option is to write the deadline relative to a server-issued time, for example by recording the skew between `Date.now()` and a server `Date` header the page has seen. Another is to have the hook keep the deadline as relative time: the page writes `opened-at` and a duration, and the server stamps its own time on the first request that carries it.

### WR-02: Closing the tab that held the modal signs out, and removes the drafts of, a tab the user is still working in

**File:** `apps/frontend/src/hooks.server.ts:79-83`, `apps/frontend/src/routes/+layout.svelte:210-215`, `apps/frontend/src/lib/contexts/utils/persistedState.svelte.ts:148-161`

**Issue:** The cookie is `Path=/` for the whole browser, and the server cannot tell which tab a request comes from. Suppose a user opens Log out in tab A, closes that tab instead of pressing Continue, and goes on editing in tab B. Forty seconds later, tab B's next request that reaches the SvelteKit server ends the session. The hook's local `signOut` also revokes the refresh token at the auth service. On the next document load, `settleLogoutDeadline` calls `discardContestantDrafts()`. Through the new `storage` following in `persistedState`, tab B's draft handles then reset to their defaults, so its unsaved answers are lost. Closing a tab is a natural way to say "not now", and tab B gave no sign that its user had left.

**Fix:** Scope the deadline to the document that wrote it. Write a per-tab token, kept in `sessionStorage`, into the cookie. Have every document of the app refresh a short-lived "alive" cookie or a heartbeat while it holds a session, and have the hook act only when no other document has shown life since the deadline was written. At the very least, have the hook not act when the request carries the token of a document other than the one that wrote the deadline, and state the browser-wide behaviour in the guide.

### WR-03: Any document that loads removes a deadline that has not passed, including one another tab still needs

**File:** `apps/frontend/src/routes/+layout.svelte:209-224`

**Issue:** `settleLogoutDeadline` removes the cookie "either way". So does every document mount and every `pageshow` from the back-forward cache, in either app or in the Voter App. Opening a link in a new tab while tab A's modal is counting removes tab A's deadline, and so does reloading another tab. If tab A is then closed during the count, the server never signs the session out, and nothing reports it. The same happens when tab A itself is restored from the back-forward cache with its modal still open: the `pageshow` handler removes a deadline the restored, still-counting modal relies on.

**Fix:** Remove only a deadline that has passed, or one this document wrote. For the second, store an id that `handleOpen` keeps in `sessionStorage`, which survives a reload of the same tab and is not shared with new tabs. Leave a future deadline of another document alone. The modal's own close and its sign-out already remove it.

### WR-04: A Back pressed during a sign-out that then fails is replayed as a forward push

**File:** `apps/frontend/src/lib/components/preventNavigation/navigationGuards.ts:100-115`, `:131-135`

**Issue:** `holdNavigation` cancels every navigation, `popstate` included, and keeps only `navigation.to.url.href`. When the run fails, `holdNavigationWhile` follows it with `goto(destination)`, which pushes a new history entry. A Back pressed during a failed sign-out therefore leaves the history as `[…, previous, current, previous]`, not on `previous`. A second Back returns the user to the page they had asked to leave, and Forward is wrong too. For a `popstate`, SvelteKit's cancel has already restored the position, so the replay should be a traversal.

**Fix:** Keep the navigation's type and `delta`, and replay a `popstate` as a traversal:

```ts
let held: { href: string; delta?: number } | undefined;
export function holdNavigation(navigation: Pick<BeforeNavigate, 'type' | 'to' | 'cancel' | 'delta'>): void {
  if (!isNavigationHeld() || leavingUnasked || navigation.type === 'leave') return;
  navigation.cancel();
  if (navigation.to) held = { href: navigation.to.url.href, delta: navigation.type === 'popstate' ? navigation.delta : undefined };
}
// on failure:
if (held?.delta) history.go(held.delta); else if (held) goto(held.href).catch(...);
```

Add a unit case and an E2E step for Back during a failed sign-out.

### WR-05: The compiled-message guard can pass on a stale compiled index

**File:** `apps/frontend/src/lib/i18n/tests/compiledMessages.test.ts:25-35`, `:150-163`

**Issue:** The guard reads the catalogues fresh from `messages/`, but it calls the compiled functions from whatever `src/lib/paraglide/messages/_index.js` is on disk. It refuses only when that index is missing. `apps/frontend/vitest.config.ts` has no compile step. CLAUDE.md's per-package flow, `cd apps/frontend && yarn test:unit`, runs `vitest run` with no build first. A catalogue edit that breaks a variant, such as a dropped `*` or a space-separated selector, is then tested against output compiled before the edit, and the guard stays green. Only the root `yarn test:unit`, through turbo's `dependsOn: ["build"]`, recompiles first.

**Fix:** Compile before the guard reads the index. One way is a `beforeAll` or vitest `globalSetup` that runs `compile-paraglide.ts` into a temporary `outdir` and imports from there. Another is to fail when any catalogue file's `mtime` is newer than the compiled index, naming the compile command.

### WR-06: The password toggle moves keyboard focus off itself, and its new state is not announced

**File:** `apps/frontend/src/lib/components/input/Input.svelte:460-467`, `:752-761`

**Issue:** `togglePasswordRevealed` calls `control.focus()` on every press. For a pointer, `onmousedown` with `preventDefault()` already keeps focus in the field. For a keyboard or screen-reader user, though, activating "Show password" moves focus away from the button. The button's new name, "Hide password", is never announced. A second Space or Enter types into the password instead of toggling it back. The button carries no `aria-pressed`, and the field's change from masked to plain text is not announced either. This degrades WCAG 4.1.2, whose name/role/value includes state, and the keyboard-operability item of the review checklist.

**Fix:** Move focus to the field only for a pointer press, and keep it on the button for a keyboard press, using `event.detail === 0` for a keyboard-activated click. Also expose the state:

```svelte
<Button … aria-pressed={passwordRevealed} onclick={(e) => togglePasswordRevealed({ focusControl: e.detail !== 0 })} />
```

### IN-08: A domain-scoped deadline cookie cannot be removed by the page

**File:** `apps/frontend/src/lib/auth/logoutDeadline.ts:34-43`, `:71-74`

**Issue:** `readLogoutDeadline` returns the first `logout-deadline` in `document.cookie`, and `setCookie` removes only the host-only cookie. A cookie with the same name, set for a parent domain by any sibling subdomain, survives every removal the page makes. The hook acts on it, so the browser is signed out on every request. The fix for CR-01 should remove the cookie from the server, and should also reject or delete a duplicate.
