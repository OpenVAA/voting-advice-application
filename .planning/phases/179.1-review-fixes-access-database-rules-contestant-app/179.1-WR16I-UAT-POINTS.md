## A. This round's code review (`179.1-WR16I-REVIEW.md`, all `open` in its disposition)

### A1 — ⚠ DECIDE — WR-01: 'logged out in another tab or window' shown for a session the auth client dropped by itself

`_onSignOut` (`apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:494`) reports `'elsewhere'` for every `SIGNED_OUT` while `signOutsRunningHere === 0`. Both contexts turn that into `errorMessage=loggedOutElsewhere` (`contestantContext.svelte.ts:617-618`, `adminContext.svelte.ts:183-195`). `GoTrueClient._removeSession` emits `SIGNED_OUT` with no other tab involved: after a rejected refresh, when `getUser()` finds the session gone (which our loads call on client navigation), and for an invalid stored session. On a hosted project with a session time-box, the user is then told something false. The verifier weighs this as the heavier of the two warnings.

- [ ] ★ RECOMMENDED — **Schedule the review's fix.** The tab that logs out announces it first on a `BroadcastChannel`. A follower shows `loggedOutElsewhere` only if it heard an announcement within about 5 s before `SIGNED_OUT`. Any other `SIGNED_OUT` goes to the login page with no reason. Add one unit case per context for a `SIGNED_OUT` with no announcement. No new copy, so no copy checkpoint is needed.
- [ ] Same as ★, but an unannounced sign-out gets a new neutral sentence, `common.loggedOut` ("You have been logged out."). Costs a copy checkpoint and 7 locales, with fr/lb machine-translated.
- [ ] Drop the 'elsewhere' sentence entirely and always show no reason after a follow. Simplest change, but it undoes G-3 for the genuine other-tab case you approved.
- [ ] Accept as a known limit and record it in the auth guide. The false cause stays possible on hosted projects.

### A2 — ⚠ DECIDE — WR-02: two server paths withdraw the count before the outcome is known

`signOutToLogin.ts:27` calls `withdrawLogoutCount(event)` before `signOut` (`:28`). When the sign-out fails and a session is left, the response is the 503 page (`:34`) with the count already expired, so the closed tab's sign-out never happens. This contradicts the hook docblock's "the next request tries again" (`hooks.server.ts:82`). The OIDC callback withdraws on its first line (`oidc/callback/+server.ts:51`), before it checks `error`, `code`, `state` or PKCE. The session is only set at `verifyOtp` (`:202`).

- [ ] ★ RECOMMENDED — **Schedule the review's fix.** In `signOutToLogin`, withdraw after the sign-out has succeeded, or after `isSessionGone` confirms the session is gone, just before the redirect. In the callback, withdraw right after `verifyOtp` succeeds. Add unit cases showing that the 503 path and a callback with `error=access_denied` leave both cookies in place. Leave `/api/auth/logout` as it is: its early withdrawal is deliberate and documented.
- [ ] Fix only `signOutToLogin`, and accept the callback ordering (it needs a live session plus a stale tab or an IdP cancel).
- [ ] Accept both as narrow, and correct the hook docblock so it no longer promises "the next request tries again" on these paths.

### A3 — IN-01: the top bar still switches to `overImgBgColor`

The header image is now painted below the top bar, so the setting's documented meaning ("Background color of the header when it's over an image", `packages/app-shared/src/settings/dynamicSettings.type.ts:78-81`) no longer matches anything. The default `'transparent'` shows no change. A deployment that set a contrast colour would get it over the plain page. Nothing is deployed (ruling of 2026-10-04), so removing the setting needs no back-compatibility.

- [ ] ★ RECOMMENDED — **Correct the docblock and the settings documentation** so they describe what the colour does now (the top bar's background on pages with a header image). No behaviour change.
- [ ] Use `mode.bgColor` for the top bar and remove `overImgBgColor` from the settings type, its defaults and its readers (9 references). Cleaner, but it touches `app-shared` and every reader.
- [ ] Accept as is.

### A4 — IN-02: the untranslated-catalogue guard catches only byte-identical copies

`apps/frontend/src/lib/i18n/tests/translations.test.ts:112-126` compares whole files. A partly translated file, a reformatted copy, or an English string added later to a translated file all pass. The last of these is the most likely regression, given the 121 machine-translated keys.

- [ ] ★ RECOMMENDED — **Schedule it.** Parse the files and compare each string value. Fail a file when every value equals `en`'s, and fail any value that equals `en`'s unless it is on an allowlist of legitimately identical strings (e.g. fr `adminApp.jobs.messages` "Messages", lb `adminApp.login.appSubtitle` "Administration"). This is a unit-test-only change.
- [ ] Schedule only the whole-file rule ("every value equals en"), with no per-value check. Less allowlist upkeep, but it misses a single English string added later.
- [ ] Accept as is.

### A5 — IN-03: `signOutToLogin` takes the same request twice

The signature takes `locals` plus `event: Pick<RequestEvent, 'cookies' | 'request' | 'url'>` (`signOutToLogin.ts:21-26`). The only caller passes a matching pair.

- [ ] ★ RECOMMENDED — **Schedule it with A2**, since it is the same file. Take one `event: Pick<RequestEvent, 'cookies' | 'request' | 'url' | 'locals'>` parameter.
- [ ] Accept as is.
