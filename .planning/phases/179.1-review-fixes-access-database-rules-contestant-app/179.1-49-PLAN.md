## Rulings carried by this plan

1. **`WR-11` is worse than the review measured. Measured at planning, in the real Admin App, in Chromium.** The review measured one static page. `179.1-planning-probe-1` and `-2`, with a temporary project admin and the sign-out made to fail:
   - **On the Admin home at 1280 by 720,** the message is seen, but `elementFromPoint` at the centre of both its Close controls and at four points of its box returns the page's own content block, not the alert. On the jobs page at the same size it returns a `relative` `Button` link and a card. So neither control can be pressed on either page, whatever the page's positioned content.
   - **At 390 by 600,** its box starts at `x = 328` of a 390-wide viewport: below `sm` the `Alert` has no `left`, so it takes its static position from the header's actions, and a sliver shows. On a phone the sentence cannot be read.
   - **`179.1-planning-probe-3`, with the message in the layout:** the same hits land inside the alert, and on a phone its box starts at 0. The Contestant App's message reads the same in the same runs.

2. **The flag goes on the admin context, as the verifier proposes.** `AdminContextProvider.logout` stops being a forward by reference. It is an arrow field that clears `#logoutFailed` as it starts, awaits the auth context's `logout`, and on a rejection sets the flag and rethrows. `logoutFailed` is a prototype getter and `clearLogoutFailure` a stable arrow field. Nothing assigns over them: the constructor forwards the app context alone, which carries no such key. The class JSDoc's sentences on `logout` and its forward are corrected to say this. **The context gains no `$effect`,** as its JSDoc requires.

3. **Moving the flag brings `WR-10` here, so its rule comes too.** While the flag lived in the button, the session's end unmounted the message with the button. In the layout it stays across the admin routes, the login route among them. So `routes/admin/+layout.svelte` has the Contestant layout's effect: `clearLogoutFailure()` while `logoutFailed` and either `!ctx.isAuthenticated` or `page.route.id === ROUTE.AdminAppLogin`. `routes/admin/+layout.server.ts`'s load reads nothing tracked, as the Contestant App's does, so `isAuthenticated` alone goes stale for the reason plan 48 measured. **Measured at planning, `179.1-planning-probe-2` and `-3`:** row 2, then a link to the jobs page, makes no `__data.json` request: the address is `/admin/jobs`, and the header and the message stay, which is right, as a press still works. A second press with the sign-out working ends on the login page with no header button and no message. A full load of a protected page goes to `/admin/login?errorMessage=loginFailed`, with the flag gone with the document. **So no browser test reaches this effect's two arms in the Admin App, and the unit test pins them.** Both layouts repeat these few lines, because a shared component is one the waiver does not cover; the summary's checklist says so.

4. **`WR-13`, one handler.** It keeps the Contestant App's order on every path after a successful sign-out, in a button with no store to reset: a `leaving` flag, so a press while one runs does nothing; the address before; `await logout()` in a `try` whose `catch` logs, clears `leaving` and returns, as the message comes from the layout; `goto` of `getRoute.current(redirectTo)` with `invalidateAll: true` in a `try`, where a resolved navigation counts as moved only when `page.url.href` differs from the address before, and a rejection is logged through `log.error` and counts as not moved; on not moved, `await leaveByFullLoad(route)`; then `leaving` is cleared. The check that the page moved is in the review's finding and not in the verifier's proposal: without it a superseded navigation leaves a signed-out page reading as signed in.
   - **`leaveByFullLoad` from `$lib/components/preventNavigation/navigationGuards`, not a bare `location.assign`,** so that one thing means a full load, and a press during it stays ignored because its promise never settles. A user who aborts that load keeps a page whose Log out does nothing until a reload, with the session already over, as `T-179.1-100` reads for the Contestant App. Plan 50 records that it now reads for both.
   - **`leaving` is a plain `let`:** nothing renders from it. A loading state on the button would be a visual change the waiver does not cover, so the UI review's "no in-flight state" stays as it was, and plan 50 keeps it on the operator's list.
   - **No browser run makes a `goto` reject,** here or in plan 44. It is held by unit cases and said so.

5. **Why one held change.** `LogoutButton.svelte` is the file both gaps change, and the Admin App's Log out is a path a browser observes. A separate commit for the handler would need its own green control, and each takes a full run's time. So the unit cases of both are committed red first, and one held change takes both to green under one control.

6. **`Banner.svelte.test.ts` changes on purpose.** The button now reads the admin context, so the file's fake of `$lib/contexts/auth` becomes one of `$lib/contexts/admin`, and `$app/state`'s fake gains `url`. Ledger rows `45-3` stay as history.
