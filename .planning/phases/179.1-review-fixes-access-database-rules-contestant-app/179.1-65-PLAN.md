## Rulings carried by this plan

1. **The mechanism, confirmed in Chromium and WebKit.** CDP's matched rules on the Admin App's controls: `.btn, .input, .textarea, .select { text-md }` in layer `components`; daisyUI 5's `.input { font-size: max(var(--font-size,0rem), var(--font-size-min,.875rem)) }` in `utilities > daisyui.l1.l2.l3`; `.input-sm` setting `--font-size-min: .75rem`. Computed: the shared `Input` controls 12 px, a bare `.input`, `.btn`, `.select` or `.textarea` 14 px, labels and body 15 px. `app.css` already makes the same move for `.label`, whose comment states the layering.
2. **The rule, revived where it wins.** The reset and the iOS rule leave `@layer components` for an un-sublayered rule in `@layer utilities`, which precedes daisyUI's nested sublayers whatever their specificity: `:where(.btn, .input, .textarea, .select)` with `text-md`, then, inside `@supports (-webkit-touch-callout: none)`, `:where(.input, .textarea, .select)` with the 16 px floor. `:where()` has no specificity, so a Tailwind text utility on an element in the same layer still wins, as it did before the bump. `input-sm` stays in `inputClass`: it sets the row's height and a variable floor, which the rule now overrides. The comment says why the rule lives there, in the form of the `.label` comment.
3. **The blast radius, measured and recorded.** As the rule was written, it reaches sized variants too (`.btn-sm`, `.select-sm`, the shared `Input`'s `.input-sm`), which is how the app read before the Tailwind 4 bump. The executor reads the computed size of a bare `.btn`, a `.btn-sm` such as a modal's ✕, the shared `Input`, the shared `Select` and a `.textarea`, before and after, on the visual recipe's server, with a scratch probe under `$U` that is not committed, and records the table in the summary for the operator's visual review. A text utility named on an element is not overridden; if the probe finds one that is, the plan stops and reports.
4. **The baselines.** `tests/tests/specs/visual/visual-regression.spec.ts` captures four images, the voter results and the contestant preview at two widths, which hold buttons, so their pixels change. By § *The visual recipe*: `yarn build`; `yarn db:reset`, with no E2E run in flight; `yarn db:seed --template e2e/base`; `yarn dev:clean`; the dev server with `PUBLIC_PROJECT_ID` set to `E2E_PROJECT_ID_DEFAULT` from `tests/scripts/e2e-run.sh`, in a process group of its own on port 5173 with `--host 0.0.0.0`. Then three container runs under `tests/e2e-runs/179.1-visual/`: `179.1-65-visual-red` with the change and the old baselines, which must fail on pixels; `179.1-65-rebaseline` with `--update-snapshots-all`; `179.1-65-visual-green` with no update, which must pass. Then the server stopped by its group, the port confirmed free, and `yarn db:seed:default`. Baselines are never regenerated on the Mac.
5. **The test.** `contestantLoginPage.expectTypedTextAtTheBodySize()` reads the computed `font-size` of the email control, the password control and the sign-in button, and expects each to equal the body's. It runs in a new test of `contestant-entry-scan.spec.ts`, the spec of the entry screens a visitor with no session meets, which runs behind `data-setup-base` alone and outside any serial describe. The contestant journey is a serial describe, where a red step would leave its later tests not run and no control could read it. iOS's own size and its zoom on focus are unmeasured: plan 66's list.
