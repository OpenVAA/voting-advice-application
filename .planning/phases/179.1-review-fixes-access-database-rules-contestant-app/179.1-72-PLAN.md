## Rulings carried by this plan

1. **The helper.** `apps/frontend/src/lib/server/auth/logoutCount.ts` exports `withdrawLogoutCount(event: Pick<RequestEvent, 'cookies' | 'request' | 'url'>): void`, TSDoc'd. It reads the two names' values from `event.request.headers.get('cookie')` through `cookieValues`. When the request carries neither name, it does nothing. When `event.cookies.get(COOKIE.logoutPending)` reads `LOGOUT_DEADLINE_SETTLED`, it does nothing: the request carried the marker, or the hook signed this request out and wrote it into this response, and the page's settlement discards the drafts and removes it (`PROH-179.1-40`). Otherwise it deletes both names host-only and for each `removalDomainsOf(event.url.hostname)`, with `path: '/'`, `httpOnly: false`, `sameSite: 'lax'` and `secure: event.url.protocol === 'https:'`, the attributes the page and the hook write them with, so a browser on plain HTTP away from `localhost` accepts the removal. It reaches no Supabase client.
2. **What `cookies.get` sees, read at planning.** `node_modules/@sveltejs/kit/src/runtime/server/cookie.js`, `get`: it looks first in the cookies set during this request that match the URL's host and path, and answers `undefined` for one set with `maxAge: 0`, then reads the request's header. So the hook's `passed`, written with `path: '/'` and no domain, is what `get` answers in a sign-in request the hook signed out. The executor reads the same function again and reports a difference before building on it.
3. **The sign-in sites, derived again at run time** by `git grep -n -E "signInWithPassword|verifyOtp|signInWithInvitationCode" -- apps/frontend/src ':!*.test.ts'` and classified by this rule: a server request that sets a session calls the helper first. Read at planning: the actions of `routes/contestant/login/email`, `routes/admin/login` and `routes/contestant/register/sign-in`, before their `passwordLogin` or `invitationCodeLogin`; the `GET` of `routes/api/oidc/callback`, before its `verifyOtp`; and the action of `routes/auth/confirm`, before `verifyMailedLink`. The data writer's browser `_login` is not a server request and is not called by any sign-in screen of either app; the executor confirms that and records it. A site the run-time list adds or removes is reported with the rule's reading of it. The server's sign-outs are plan 73's.
4. **Each site keeps its contract.** The helper is called once, first, and returns nothing; no refusal, status, redirect or order of claim, refresh and gate changes (`PROH-179.1-48`). A failed sign-in after it leaves no count, which is right: the gate sends a browser with a session away from every sign-in screen, so a request that signs in has no session for a count to end.
5. **The browser test isolates the sign-in.** A Log out would withdraw the count on the page (plan 71) and the logout endpoint would too (plan 73), so the test ends the session by removing the session cookies from the context, as a browser does that no longer holds them, and leaves the two count cookies in place; the sign-in through the email form is then the only request that can withdraw the count. The other sign-ins are pinned by unit cases or by their order in the source.
