## The review's WR-01 and WR-02

The review is `179.1-WR16J-REVIEW.md`, of plans 81 to 85. Its dispositions are all `open`.

**WR-01: not a security threat, and the register misses nothing here.** Read at HEAD:

- `announcement:56-58` stamps the time when the message arrives.
- `auth context:52` posts before `dw.logout()`.
- The other tab's `SIGNED_OUT` arrives only after the writer's requests and auth-js's own message.

So whether the sentence appears depends on request latency. That is T-217's effect, and T-217 accepts it: only the sentence is lost, the drafts are discarded, and the session ends. Losing a reason does not weaken any control. It also points the safer way for T-215, since it names no cause rather than a wrong one. The remaining defect is test determinism. Two pinned E2E titles fail under latency with the code as designed, which is the E2E hard rule's to settle.

If the review's fix is chosen, the security side changes. Today a sign-out reads as another tab's for at most 5 s after a message. With the fix it would read so for up to 60 s after a `'start'` with no `'end'`, and a forged `'start'` is enough (T-216). T-215's residual and T-216's acceptance should then be restated with the cap.

**WR-02: a security threat the register misses. It is open, unregistered, medium and does not block.** Confirmed by reading:

1. `confirm:55` calls `withdrawLogoutCount(event)`.
2. `confirm:57-60` signs out a held session. The code ignores an `{ error }` answer and logs only a rejection.
3. `confirm:61` hands off to `verifyMailedLink`, whose failed `verifyOtp` (`lib/server/auth/mailedLink.ts:108`) ends at the login page (`:141`).

In the installed auth-js, `_signOut` returns a session error without removing the session (`node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:3434-3435`). A failed `verifyOtp` does not remove the held session either. No gate row claims `/auth/confirm`. So a browser that holds a session and a closed tab's count can lose the count while it keeps the session. That is T-218's harm: "a session the user asked to end lives on". T-218's component names only the protected load and the callback.

**This audit's reading, beyond the review:** the same class reaches the sign-in actions the gate protects: `admin/login`, `contestant/login/email` and `contestant/register/sign-in`. During an auth outage, `getUser()` errors and `safeGetSession` answers no session (`lib/supabase/safeGetSession.ts:44-49`). The gate then lets a request with kept cookies through (`hooks.server.ts:155-158`), which is `AR-179.1-09`'s term. Each action withdraws first, for example `routes/contestant/login/email/+page.server.ts:34`. Then `signInWithPassword` or `verifyOtp` fails without removing the held session. The review's sentence, that the gated actions' "withdraw-first order cannot strand a live session", holds only while the session read works. This is read, not run.

The review's fix closes WR-02's path: withdraw once the outcome is known, or after `verifyOtp` sets the session. Applied to every sign-in action, the same fix closes this audit's reading too. Whether to apply it is the operator's call. Either way a register row is needed. The other path of this class, the logout endpoint's withdraw-first, is the operator's ruling A2 ("/api/auth/logout unchanged") and plan 73's `T-179.1-207`.
