# Phase 179.1 Plan 84: where the server withdraws a logout count Summary

**`signOutToLogin` now takes one request `event` and withdraws the logout count only after a sign-out that worked, or after a failed one that left no session. The identity provider's callback withdraws it only right after `verifyOtp` has set the session. A failed sign-out that ends on the 503 page, and a callback that fails before `verifyOtp`, both leave the closed tab's count for the hook. The targeted run passed 707 of 707.**

## For the operator's reading

- **What changes for a user.** Suppose a user presses Log out, the modal starts counting, and they close the tab. The browser's session is now ended at its next request after the count, even in two cases where it was not before:
  - an earlier request's sign-out failed while the auth service was down, and the user saw the error page;
  - the browser came back through the identity provider's callback, and that callback failed before it signed anyone in (a cancel at the provider, a missing code, a bad state, a refused registration, a failed `verifyOtp`).

  Nothing on screen changes, and no copy changed.
- **What stays unproven (rule 17).** Both failure paths are unit-tested only. No browser test drives a protected load's failed sign-out with a session left, or a callback failing early with a live session, followed by the hook's sign-out. The targeted run is Chromium alone.
