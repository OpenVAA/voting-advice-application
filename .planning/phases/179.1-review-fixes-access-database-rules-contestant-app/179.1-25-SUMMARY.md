# Phase 179.1 Plan 25: the nominations view after a save, with Return, card Edit and Delete, and Add Summary

**A stored save in the nomination editor now ends on the nominations view. The view lost its Edit nominations link. It now has Return to the entity's home, Edit and Delete on each card the editor manages, and Add a nomination below the cards whenever another can be added. Delete asks for confirmation inside the card, opens no dialog, and writes the in-reach set without that nomination, checked against the set shown. The close is green: 639 of 639 tests in 128 projects, three more than plan 24, all in `perm-contestant-nominations`.**

## What changed

- **Task 1 (tracer).** The details step's two `goto(nominationsSaveTarget(...))` calls now go to `getRoute.current('ContestantAppNominations')`. This covers both the stored save and the nothing-to-write press. The view's Edit nominations button is gone. Return (`common.return`) takes its place and is shown when `target && target.action !== 'return'`. `nominationsSaveTarget` stays, because `nominationsSaveAction` reads it, and its TSDoc and the module header now say so. Every spec that used to meet the profile or the home after a save now meets the view first (`expectShown`) and moves on through its main button or Return: 15 profile sites and 4 home sites. The journey's step 12 now returns home through the view's Return.
- **Tracer feedback gate.** Interactive, end-of-phase, and the `<verify>` is automated only. As written it exited 1, on the `--dirty-only apps/frontend` slash quirk. Restated, it exited 0, and the plan went on to Task 2.
- **Task 2.** In-reach cards get Edit and Delete under `entryOffered && !contestantCtx.nominationsLocked && !contestantCtx.answersLocked`. Edit links to `ContestantAppNominationDetails` with `selectionSearch` over every in-reach nomination. Delete shows a `Warning` question with Confirm and Cancel, and focus moves to Confirm, which the question describes. Confirm writes `{ id, electionId, constituencyId, electionSymbol, parent: { kind: 'keep' } }` for each other in-reach nomination, with `readFrom` the set shown, and then calls `invalidateAll()`. What came of it shows in two always-rendered regions: an alert carrying `data-outcome` for a refusal, and a status line for a delete that went through.
- **Task 3.** `nominationFactsOf` now returns `canAddAnother`. The page shows Add a nomination below the list when `entryOffered && facts.canAddAnother` holds and neither lock is on. The follow test once again enters the editor through Add, so it stays on one document from start to end.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - correctness] Card Edit names every in-reach contest**
- **Found during:** Task 2, while reading `stepSelection.ts` and the details step.
- **Issue:** The details step builds a card for every in-reach nomination and marks the ones whose election the address does not choose as about to be removed. If Edit addressed only the card's own election and constituency, every other nomination would be staged for deletion.
- **Fix:** Every card's Edit uses one address, built with `selectionSearch` over the elections and constituencies of all in-reach nominations. That address includes the card's own contest. The E2E case presses Edit and finds both cards kept.

**2. [Rule 1 - correctness] `canAddAnother` counts elections, not constituencies**
- **Issue:** Ruling 4 counts "a constituency the entity holds no nomination in". The editor, though, chooses one constituency per election. A party nominated in North of a two-region election can move to South but cannot add South. Under ruling 4 such a party would see an Add that leads nowhere new.
- **Fix:** `canAddAnother = editable && admissibleElectionIds.some(id => no in-reach nomination in id)`. A unit case pins "false once the entity stands in every election that admits it, though a region of one is free". The TSDoc and the docs page give the reason.

**3. [Rule 3 - tests the plan did not list]**
- `details/afterSave.svelte.test.ts` had pinned the profile and home targets. Its two cases now expect the nominations view, committed red alone at `2fb2e85bc`, with the red shown against `details/+page.svelte` at `da095c496`.
- The `cand-nominations` reach in `contestant-a11y.spec.ts` asserted the removed link. That check is dropped; nothing replaces it, and it passed on both trees.
- `layout.tracking.test.ts`'s typed `SERVED` facts gained `canAddAnother`.

**4. [Rule 3 - an interim test shape] The follow test between Task 1 and Task 3**
- **Issue:** Once Edit nominations was gone and before Add existed, a nominated entity had no in-app way into the editor.
- **Fix:** In Task 1, the follow test loaded the editor's entry address and re-marked its document. Task 3 restored both entries through Add and moved the single-document check back to the start. The restored test was shown red in `179.1-25-red-3-follow`.

**5. [Rule 1 - fixture] `pressCardDelete` waited for hydration after focus had moved**
- **Issue:** `179.1-25-green-2` failed on the second Delete. `waitForNavigationFocusReset` cannot land after Cancel has moved focus.
- **Fix:** The step no longer waits for hydration. Its TSDoc requires a hydrated page, and a press made too early fails on the question. The rerun is `-r2`. The tree was changed first; it is not a retry of the same tree.

**6. Unit helper and assertion fixes in the Task 2 feat commit**
- `press` now settles on three macrotasks.
- The refusal cases read the always-rendered status region as empty rather than absent.
- The red failures were on the missing controls, before either change. Ledger row 25-3 records this.
