## Top 3 Priority Fixes

1. **The page does not tell a user that they are still signed in** (F1, F2). On a shared computer, a person whose sign-out failed can walk away from a page that looks finished, with the session alive. Fix, with no `.svelte` or catalogue change: pass the existing sentence as the error's `description`, which `app.d.ts` and `+error.svelte` already support, on the 503s: `error(503, { message: t('error.default'), description: t('contestantApp.error.readFailed.content') })`. It reads "Your data could not be loaded. You are still signed in, so you can try again…". The 403 has no fitting existing message, so it needs new copy, and that needs the operator's waiver widened. This description replaces `error.content`, so on these 503s it also removes the placeholder address in item 2, and the "contact support" it mentions then has no address beside it.
2. **The page offers a placeholder address as its last resort** (F3). [MARKUP] `error.content` hardcodes `first.last@openvaa.org` in all seven catalogues, and it is a literal, not read from `staticSettings.admin.email` (whose value is the same). A deployment that sets its own address still shows this one. Fix: interpolate the address from the settings. This is a catalogue change, so it is outside the waiver, and it is *older, newly reached*.
3. **No control on the page: no retry, no sign-out, no way home** (F4). The Contestant App already has the right view for a failed read, `ReadFailure`: Try again, support and Log out. A user-level read failure gets none of them, though the entity-list read failure one stage later does. Fix: a `.svelte` change, so the operator's to schedule: add `primaryActions` to `+error.svelte` for these statuses, with Try again at the least. A Log out needs care, since the sign-out just failed and the app's context is not mounted there.

## Detailed Findings

### Pillar 1: Copywriting (2/4)

- **F1, WARNING, the state that matters is unsaid.** [MARKUP] The 503 reads "Something went wrong, sorry!" and the 403 reads "You're unfortunately not authorized to access this content." Beneath each is `error.content`. Neither says that a sign-out was tried and failed, or that the session is alive. The load's own comment gives that as the reason for the page; the reader is not told.
- **F2, WARNING, the same failure has two explanations.** [MARKUP] A failed entity-list read says "You are still signed in, so you can try again" (`contestantApp.error.readFailed.content`). A failed user-level read, one stage earlier in `(protected)/+layout.server.ts`, says only the generic text.
- **F3, WARNING, placeholder address.** See priority fix 2. *Older, newly reached.*
- **F5, WARNING, "go back" does not fit every path.** [MARKUP] `error.content` says "You can try to go back and reload the page". [PREDICTED] On a document request from a fresh tab there is nothing to go back to, and after a sign-in Back leads to the stand-off already tracked as `T-179.1-140`. Reload alone is the recovery, and [RECORDED] it reaches home once the read works. The sentence puts the useless step first.
- **F6, WARNING, the 403's two halves differ in kind.** [MARKUP] The title states a permanent refusal, while the text below suggests a transient fault and a reload. [PREDICTED] For this path both are partly right: the user has no admin grant, and a reload retries the sign-out and can reach the login page's `userNotAuthorized`. A reader cannot tell that from the page.
- **Passes.** [RECORDED] The title reads in the reader's language in `en` and `fi`, where it read `Internal Error` before. This is the real copy gain of these plans.

### Pillar 2: Visuals (3/4)

- **Passes.** [MARKUP] Emoji hero, then `h1`, then centred text: one focal point, reused rather than invented.
- **WARNING, F7, no app chrome.** [MARKUP] The root `+error.svelte` sits outside each app's layout, so no `Header` or Banner renders [RECORDED: "no Log out"]. [PREDICTED] A user inside the Admin or Contestant App sees the frame disappear, which reads as having left the application. The page carries no action to anchor the eye below the text (F4).
- **Not judged:** how it looks at all, in any theme, width or direction.

### Pillar 3: Color (3/4)

No class, token or hardcoded colour changed in production code. [MARKUP] **WARNING,** the mailto link in `error.content` has no class of its own, and its contrast and distinction from the surrounding text were not measured on this page. Nothing else could be scored without a render, and that alone holds this at 3.

### Pillar 4: Typography (3/4)

No size or weight changed. [MARKUP] **WARNING,** the title is a whole sentence: `error.403` is about 60 characters in English, and now an `h1` on a real path. [PREDICTED] It wraps to several lines on a phone, more so in Danish, whose string is longer. Not seen.

### Pillar 5: Spacing (3/4)

No class changed, and no arbitrary value was added. [MARKUP] **WARNING, doubled padding,** *older, newly reached*: `+error.svelte`'s `<main>` has `gap-y-lg pb-safelgb pl-safelgl pr-safelgr pt-lg`, and `MainContent`'s own wrapper declares the same classes inside it. [PREDICTED] The side and top padding is twice what other pages have, which narrows the text on a phone. Fix: drop them from the `<main>`.

### Pillar 6: Experience Design (2/4)

- **The gain.** [RECORDED] A loop that ended on an untranslated page, with 44 data requests and 22 reads on one path, now ends at once on a translated page. [MARKUP] Nobody is signed out by a failed read in Admin. A reload retries. The ordering is right: the session check moved ahead of the read, so a load with no session still redirects.
- **F4, WARNING, a dead end.** [MARKUP] `+error.svelte` passes no `primaryActions`. The only exits are browser controls and an email link. Priority fix 3.
- **F8, WARNING, a live session that cannot be ended from here.** [MARKUP] After a failed sign-out, no Log out exists on the page, and the user is not told one is needed (F1). The Contestant App's path is a server load that ran for a user whose data could not be read, so the failure is likely to repeat [PREDICTED]. This is the case with a real cost, on a shared device.
- **F9, WARNING, a reload has a side effect the page does not disclose.** [MARKUP] On the 403 and on `signOutToLogin`'s 503, the reload the page recommends retries the sign-out. [PREDICTED] A contestant who strayed to `/admin` and reloads is signed out of this browser, with any work in other tabs affected. This is by design and recovers correctly, but nothing warns of it.
- **F10, WARNING, the two apps answer a failed sign-out with different statuses and titles.** [MARKUP] Contestant is 503 and `error.default`; Admin is 403 and `error.403`. In Admin this is defensible, since the user is known not to be an admin. In the Contestant App it is a fault with no such fact. No change needed unless the wording is revisited.
- **Passes.** [MARKUP]
  - **Focus.** `focusNavigationTarget` falls back to the first `h1`, and `MainContent`'s has `tabindex="-1"`.
  - **Announcement.** `MainContent` registers its title with the root `#route-announcer`, which stands outside the error branches. Whether a reader says it after an error navigation is [PREDICTED] and unheard.
  - **Document title.** `{title} – {appName}`, translated.
  - **No HTML injection from the title.** It renders as text in the `h1`; only the description goes through `sanitizeHtml`.
  - **Load-tracking rule.** The admin load reads no `url`, `route` or `params` [MARKUP, and the test's throwing getters state it].
