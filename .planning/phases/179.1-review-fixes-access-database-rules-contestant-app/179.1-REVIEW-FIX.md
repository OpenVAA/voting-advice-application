#### DB-WR-01
- **What was wrong:** after the locked `identity_entity_find_or_create`, `identity-callback` sent `updateUserById(app_metadata: …)`. The auth service writes the whole `raw_app_meta_data` column from the copy it loaded. That copy could predate another request's locked write of a different `(project, type)` entry, so the update could drop that entry.
- **Mechanism, observed:** `pg_stat_statements` on the local database holds exactly one auth-service statement shape for the column: `UPDATE "users" AS users SET "raw_app_meta_data" = $1, "updated_at" = $2 WHERE users.id = $3` (151 calls). An update carrying only `email_confirm` writes `confirmation_token`/`email_confirmed_at` and `raw_user_meta_data`, not `raw_app_meta_data`. That is inferred from the same statement shapes. I did not trace which call produced each statement.
- **What changed:**
  - `identity_entity_find_or_create` gains `p_identity_metadata jsonb DEFAULT '{}'`.
    - It must be an object of strings and nulls that does not name `registered_entities`; otherwise 22023, with nothing written.
    - On every answer it is merged into `raw_app_meta_data` under the existing advisory lock: strings are set, nulls removed.
  - The schema change: `schema/506`, new migration `00020_identity_metadata_written_under_lock.sql` (drops the 5-argument function and creates the 6-argument one with an identical body), a manifest line, and regenerated `packages/supabase-types/src/database.ts` (`p_identity_metadata?: Json`).
  - `identity-callback/index.ts` hands `identityAppMetadata(...)` to the RPC. Its one admin update is now `updateUserById(userId, { email_confirm: true })`, inside `if (initialise)`. The error code there is `ERR_ACCOUNT_CONFIRM_FAILED`; no other file referenced the old `ERR_RECORD_WRITE_FAILED`.
  - Comments updated in `index.ts` and `appMetadata.ts`.
- **Tests:**
  - pgTAP 56 asserts that the call writes the identity keys (sets them, removes the nulls, keeps the auth service's members), that a second pair's call keeps the first pair's entry and the keys, that a `found` call writes the metadata too, the refusals, and the new signature.
  - `flowConformance.test.ts` asserts that no `updateUserById` carries `app_metadata`, that the metadata reaches the RPC as `identityAppMetadata(...)`, and that the one admin update is `email_confirm` alone, inside the guard.
- **Residual, not fixed:** any other auth-service write of `app_metadata` made from a stale copy can still race the record in principle. Examples are provider-list updates the auth service makes on its own verification paths. The record still lives in `raw_app_meta_data`. The reviewer's table option (`private.identity_registrations`) would remove that class entirely, but it is a design change that is not this lane's to make.
- **Labelled "requires human verification"** because the finding is a concurrency (logic) defect. The tests pin the contract, not the interleaving.

#### FE-WR-05
- **Behaviour chosen:** a hold on the page, not a filter in `save()`. Plan 26 asked that the open answer can be typed first, and that a draft holding only an open answer is never written on its own.
  - Filtering in `save()` and keeping the entry in the draft would leave `hasUnsaved` true after every later successful save. That would trigger the leave prompt after a stored save, and would enable the profile's Save with nothing to write.
  - So the question page now holds an open answer typed while the question has no answer in page state, keyed by the question id. It stages that answer into the draft only together with a chosen answer.
  - The draft therefore never holds an answer with no value, and no save of any question can write one.
  - Leaving the page while it holds one asks first, as an unsaved draft does (the `PreventNavigation` gate and the Cancel label read it). Cancel and a confirmed leave discard it.
- **Accepted difference from plan 26:** the held text lives in memory. It no longer survives a full reload the way the persisted draft does.
- **Related change:** an answer whose chosen value becomes empty (for example, a multi-choice cleared) now has its open answer moved back to the page, instead of being staged with an empty value.
- **Tests:** three page cases.
  - The written text stages nothing, and the field keeps it.
  - Choosing an answer stages `{ value, info }`.
  - The Cancel label follows the held text.
- **E2E:** the plan-26 E2E case (`an open answer can be written before the question is answered, and is saved with it`) passes.
- **Human verification:** please confirm that losing the held text on a reload is acceptable.
