## WR-01 against the register

The review's reading of `GoTrueClient.js` is correct: `:3447-3449` removes the session and then returns `{ error }`, and `:3435` returns a session-read error with no removal. Measured with `fetch` stubbed:

| Client | State | Auth's answer | `signOut` answers | Cookie afterwards |
|---|---|---|---|---|
| server | token valid | 500 | `{ error }`, `Internal Server Error` | **cleared**, one write with `maxAge` 0 |
| server | token valid | network failure | `{ error }`, `fetch failed` | **cleared**, the same |
| server | token valid | 401 | `{ error: null }` | cleared |
| server | token expired | refresh answers 500 | `{ error }`, 8 attempts, about 25 s | kept, no write |
| universal, no `setAll` | token valid | 500 | `{ error }` | kept, it has no way to write |

Which row each path lands on:

- **`signOutToLogin` is the first or second row.** It runs after the gate and `contestant load:43` have verified a session. By reading, the expired row would need the token to cross the 90 s margin between that read and the sign-out, within one request. So a library failure here means the session has gone from this browser, and the server has not revoked it.
- **The Admin App on a document request is the last row.** The cookies stay and the comment is true.
- **The Admin App in the browser has both.** A 502 from the endpoint after a service failure follows cleared cookies. A gateway failure, a rejected `fetch` or the test's stub keeps them. `routes/api/auth/logout/+server.ts:13` already says "may or may not".

What the register and the records claim, weighed:

| Claim | Where | Weighed |
|---|---|---|
| A failed sign-out ends on the error page, with no redirect | T-179.1-130's mitigation | **Holds in every form.** The row says "or its sign-out worked", and the code does exactly that |
| The loop is reached "by a sign-out that fails in a protected load" | T-179.1-130's component | **True only where the cookies stay.** On the first two rows, by reading, the gate would not have sent the request back |
| `signOutToLogin` looped under an answer of `{ error }` | `179.1-54-PLAN.md:159`, `deferred-items.md`, entry at `:582` | **Measured, but not in the library's form.** Plan 54 says the probes used temporary product edits. The log line reads `Error logging out: probe`, a message the library does not produce, and 22 data requests mean the session survived. The edit itself is gone, so that it kept the cookies is an inference. `signOutToLogin.test.ts` cannot show this either: its fake touches no session. The summaries say "under a temporary fault" and never that the fault kept the cookies |
| "the session is alive", "would send a live session straight back" | `helper:10`, `contestant load:13`, `admin load:45`, `authentication/+page.md:36`, `login-and-password-reset/+page.md:24` | **False on the helper's real failure.** `admin load:37` is about a failed read and is not affected by this |
| "still holds a live session", "the session is what it was before the navigation" | T-179.1-138's boundary and mitigation | **True on a document request and under the stub.** False in the browser when the auth service's answer failed. The mitigation does not depend on it: the load throws either way, so the row stays closed |
| Both forms are logged | T-179.1-139 | **Holds.** Logging does not depend on what happened to the session |
| "redirects to login only if the session has gone, otherwise a translated error page" | R2, `deferred-items.md:639` | **Literally holds, since a redirect implies no session. But** a session gone after a failed sign-out gets the error page, and this is what the review means by R2's first half. T-179.1-130's row is worded on the sign-out, not the session, so the two part here |

What a user meets in that form, read and measured at the library but not driven in a browser:

- Before plan 54 they reached the login page with `loginFailed`, with no loop.
- Now they get a generic 503 with no message, and find themselves signed out on the next reload.
- The cleared cookies do reach the browser, by reading: SvelteKit 2.70.3 adds them to every response `resolve` returns (`respond.js:478`), and a data request's error node passes through the same path (`data/index.js:111`). The orchestrator's note that this was not driven still stands.

Security effect: no elevation, and no new exposure. The unrevoked server session was already there before plan 54, with the token out of this browser. So T-179.1-130, -138 and -139 stay closed.

**Why T-179.1-143 is open and not a note.** The earlier report kept T-179.1-114 and -119 closed because their mitigations held for the sentence they declared. This row is different. It names "a page that says more than was run", plan 55's boundary says such a page "must match what the code does", and the mitigation checks only the summaries and the tree. The behaviour the two pages state is right, and their reason is not. The harm is small and leans the cautious way: a reader assumes a session is still alive when it has gone. Medium stands, as the register rates it, and it does not block.

**How it closes.** Either change the reason in the five places above to "the sign-out failed, and the session may still be alive", which is the first half of the review's fix and changes no behaviour, or have the operator accept it. T-179.1-138's wording should be narrowed at the same time.

**If the operator wants the redirect instead,** T-179.1-130 stays closed by reading, since a redirect then follows only a re-read that finds no session. Plan 54's truth, the row and the unit fake would need to change with it.
