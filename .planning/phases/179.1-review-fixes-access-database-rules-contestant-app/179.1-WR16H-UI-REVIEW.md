## Top 3 Priority Fixes

1. **A fresh sign-in can be ended 40 s later with no message** (WR-01, F6-1). [MARKUP] An explicit Log out in a tab that did not write the count does not withdraw it; a sign-in inside the window is then signed out by the hook when `logout-deadline` drops, and its new drafts are discarded by the `passed` settlement. [PREDICTED] On a shared device the next user is thrown to the login page mid-task, with no message, and loses what they typed. Fix as WR-01 says: withdraw every count on every explicit sign-out and server-side on every sign-in (one shared helper keeps `hooks.server.ts` untouched).
2. **The signed-out tab gets no explanation** (F1-1). [MARKUP] The hook signs out and the gate redirects to the login page; nothing carries a reason. [PREDICTED] A user who walked to another tab sees the login form appear on their next click, hears only the route announcer's page title, and cannot tell a timed sign-out from an error or a lost session. That is a WCAG 3.3 / 2.2.1-in-spirit gap (an unannounced timeout outcome). Fix, needs the operator's leave under PROH-179.1-39: add `reason=loggedOut` to the redirect when the hook's sign-out is what sent the request there, and show the existing login-page notice key if one exists (check `contestantLogin.*` / `common.logout*` before adding a key).
3. **Drafts come back after the session ended** (IN-03, F6-2). [MARKUP] On a `pageshow` restore or a client-only navigation inside the entity layout, `discardContestantDrafts` runs while the draft handles are still mounted, and the next edit writes them back. [PREDICTED] The user believes the drafts are gone (the docs say so); they reappear for the next session on that device. Fix as IN-03 says: reset the mounted contestant context from the `'settled'` branch through a registered callback.

## Detailed Findings

### Pillar 1: Copywriting (2/4)

- **Passes.** [MARKUP] No key added, edited or orphaned. The three docs pages now describe the two-cookie mechanism correctly in the main and are consistent with each other (`login-and-password-reset`, the auth guide, the generated `LogoutButton` page).
- **F1-1, WARNING, silent sign-out.** See priority 2. A deadline sign-out and an explicit Log out from another tab both land on the login page with the same, reason-less screen. The round could not add copy; the gap remains and should be raised, not absorbed.
- **F1-2, WARNING, the auth guide promises what the code does not do** (WR-02). `backend/authentication/+page.md`: a planted `logout-pending` "costs that browser at most one sign-out … every removal … expires the parent domains' copies". On an apex host (`parentDomainsOf('example.org')` is `[]`) a `Domain=<host>` copy is never removed and signs out every other navigation. A deployer reading the guide is told the risk is bounded when it is not. Correct the sentence with the code fix.
- **F1-3, WARNING, the guide's "a sign-in after it keeps its session" is broader than true** (WR-01). It holds only for sign-ins after the hook's own sign-out. State the window, or close it.
- **F1-4, WARNING, docs prose density.** The `login-and-password-reset` § Logout paragraph and the generated `LogoutButton` docblock are now single paragraphs of several hundred words each carrying cookie names, grace, settlement and tab rules. [MARKUP] A reader looking for "what does the user see" has to parse mechanism to get there. Split into a user-facing paragraph and a mechanism list. Minor.
- **Settings redirect after re-sign-in** [RECORDED 67-SUMMARY deviation 1]: the gate's `redirectTo=contestant/settings` is honoured, so a user who clicked Settings, was signed out and signed back in lands on Settings, not on the entity selection. That honours their intent and is the right copy-free behaviour. Note: for a multi-entity user it skips the selection, so which entity Settings opens on is whatever the layout defaults to. Not driven for that case; look at it in UAT.

### Pillar 2: Visuals (3/4)

- **Passes.** [MARKUP] No markup or class changed anywhere in the round (see the grant table). The 699-test run includes the visual-regression project green [RECORDED summary.json], so no baseline moved.
- **F2-1, WARNING [PREDICTED].** The cross-tab sign-out has no visual state at all in the receiving tab: the page stands as it was until the next request, then is replaced by the login page. The docs accept this (server-only sign-out reaches a tab only at its next request). Nothing visual tells a user that an edit they are making in that tab will be lost on submit. Recorded, accepted by ruling `a`.

### Pillar 6: Experience Design (2/4)

- **Gains.** [MARKUP]
  - **CR-01 closed:** a re-sign-in in the tab that met a deadline sign-out keeps its session; the `passed` marker is never acted on again [RECORDED 67-SUMMARY, E2E two-tab test].
  - **No device clock in the decision:** the deadline is the cookie's `Max-Age`, so a wrong clock neither signs out a present user nor keeps a walked-away session (WR-01 of the previous round) [RECORDED 68, clock-behind test].
  - **A page in another tab no longer withdraws the count** (WR-03), and a reload of the counting tab still does.
  - **Drafts are discarded on the server's marker only,** after every navigation too, so a client-side request that met the sign-out still removes them.
  - The modal's focus, hold and announcement behaviour is unchanged by this round.
- **F6-1, WARNING, WR-01** (fresh sign-in ended silently). See priority 1. This is a user-task break on a short window, and it discards the new session's drafts.
- **F6-2, WARNING, IN-03** (drafts written back). See priority 3.
- **F6-3, WARNING, IN-01** (Duplicate Tab / full-load navigation withdraws the count). [PREDICTED] A user who duplicates the tab, or types a URL into the counting tab, then closes it, keeps a session the docs say ends. The visible modal in a restored bfcache page keeps counting with no cookie behind it, so what the user sees (a count) no longer matches what will happen if they leave.
- **F6-4, WARNING, WR-02 on apex hosts.** [PREDICTED] On that deployment shape a planted cookie produces a sign-out loop with drafts discarded every other navigation: from the user's side the app is unusable, with no message. Needs a subdomain attacker, so WARNING.
- **F6-5, WARNING, accessibility of the arrival.** [MARKUP] After the redirect, `afterNavigate` runs `focusNavigationTarget()` and the route announcer speaks the login page, which is the correct WCAG 2.4.3 behaviour. [PREDICTED] What a screen-reader user hears is "Log in" and nothing about being signed out (F1-1). For a sign-out caused by a timer the user may not have seen (another tab), WCAG 2.2.1 asks that the user be warned before and informed after; the warning exists only in the counting tab's modal. Same fix as priority 2.
- **F6-6, WARNING, the receiving tab's in-progress edit.** [PREDICTED] An edit typed in an open tab after another tab's sign-out is lost on submit, through a redirect, with no prompt. Accepted by ruling `a` and stated in the guide; recorded, not disputed.
- **Carried and unchanged:** WR16G F6-1 (loading Log out drops focus to `<body>`, announced "Loading…"), F6-3 / IN-04 (silent held ✕), WR-06 (password toggle on keyboard). This round did not touch them; they keep the pillar at 2 on their own.
