# Phase 179.1 Plan 78: The French password label and the Admin App's illustration Summary

**The input row's control wrapper now takes only what the label leaves (`flex-1`, with a 60 px minimum on the input and the select), so "Mot de passe" stays on one line; and the header paints a page's image in its own element below the top bar, so the Admin App's illustration no longer reaches the logo at 320 px.**

## For the operator's reading

**The two mechanisms, as traced before any fix** (`tests/e2e-runs/179.1-unit/179.1-78-trace.txt`, measured on the visual recipe's server, light and dark the same):

1. **The label.** The input row is a flex row. The label asks for its text's one-line width (96.2 px for "Mot de passe"). The control's wrapper asked for its contents' width, which is the input's default width plus the 44 px toggle and 8 px of padding. Solved from the measured boxes, that comes to about 237 px. Together they ask for more than the row holds: 258 px inside the row at 320 px, 328 px at 390 px. Flexbox takes the excess from both in proportion to what each asked for. The label's share pushed it under its one-line width: 74.4 px at 320 px, and 95.2 px at 390 px, one pixel short. That is enough to put "passe" on a second line. "E-mail" is one word with no break opportunity, so it never wraps. The same numbers were measured on `/fr/contestant/login/email` and on `/fr/admin/login`: both render the shared `Input` row. Ruling 2's hypothesis held, with one refinement. The label does not shrink to its min-content width; it loses a proportional share of the excess.
2. **The illustration.** `<header>` itself painted the image across its whole box, `cover`, centred. That box includes the 40 px top bar, which is transparent over an image. At 320 × 568 the header (320 × 227) is narrower in aspect than `hero-admin.png` (2048 × 1024). `cover` therefore scales the image by the header's height, to 454 px wide from x = −67, and crops its sides. The left edge of the image's opaque area (image x 527, alpha coverage 0.287) lands at page x 49.8, with the logo starting at x 50. The probe counted 10 opaque pixels under the logo at 320 × 568 and 17 at 320 × 844. At 390 and at 1280 it counted 0. The Contestant App's poster is opaque everywhere (alpha coverage 1.0), so the logo lay on it at every width (2400 px, the whole logo box). The voter home's `hero.png` counted 0 at every width. Ruling 2's hypothesis held, with one correction: the pixels lie under the logo's start, not its end.

**What each fix changes for a user** (`179.1-78-trace-after.txt`, `179.1-78-blast-radius-4.txt`):

- **Input rows.** The label is given its one-line width whenever the control keeps 60 px beside it. "Mot de passe" and "E-mail" are on one line on both pages at 320, 390 and 1280 px. On rows built with longer labels, the change shows as follows:
  - In text, password and select rows, "Année de naissance" now stays on one line at 320 and 390 px, where it wrapped before.
  - A label longer than the row allows takes the row down to the control's 60 px floor. At 320 px, with the longest label, a text field goes from 64.5 to 60 px and a password field from 22.9 to 60 px. At 1280 px a text field beside the longest label goes from 107.8 to 60 px.
  - Boolean rows and the selected-option rows of the multiple select are identical before and after.
  - No row overflowed, before or after.
- **Header images.** Every hero image (the voter home, the Contestant App's login, the Admin App's login) now starts below the menu bar instead of behind it. It is drawn in the header's height less the bar's, 40 px less (44 px on the voter home). The header's own height is unchanged. The probe counts 0 opaque pixels under the logo on all three pages, at 320, 390 and 1280 px, in both themes. On the Contestant App's login the poster's top band no longer runs behind the logo and the menu button; the bar there shows the page's background.

**Screenshots**, the same 72 before and after (6 pages × en/fr × 320/390/1280 × light/dark): `tests/e2e-runs/179.1-unit/179.1-78-shots/before/` and `tests/e2e-runs/179.1-unit/179.1-78-shots/after/`. For example:

The settings page was not reached: the base candidate's user exists only after the suite's `auth-setup`.

**The visual project:** green with the change held. `179.1-78-visual-final` exited 0 with 8 expected and 0 unexpected, so no baseline changed. Under C8 there was nothing to regenerate. The four baselines (the voter results and the contestant preview) show no hero image. Their `Input` rows did not move a pixel.

## Decisions Made

- **The label's fix: the wrapper asks for no width, and the control has a 60 px floor.** Three forms were measured with `179.1-78-blast-radius-probe.mjs`, which clones the real rows of `/fr/admin/login` with five labels. Only the third was kept:
  - (a) `basis-1/2` on the wrapper (`179.1-78-blast-radius.txt`). It fixed "Mot de passe", but made boolean labels that fitted wrap, for example "Année de naissance" at 320 px, because the toggle's wrapper asked for half the row.
  - (b) `shrink-0 max-w-2/3` on the label (`179.1-78-blast-radius-2.txt`). It left a password input 7.3 px wide beside a long label at 320 px. "Confirmer le mot de passe", the set-password view's French label, is such a label.
  - (c) `flex-1` on the wrapper, with `min-w-xxl` on the input and the select (`179.1-78-blast-radius-4.txt`). Short labels keep one line. Long labels leave the control 60 px. Boolean and option rows are identical before and after.

  `xxl` (3.75 rem) is the theme's largest word-named spacing value. The rule against arbitrary values and numeric spacing classes is met: `shared.ts` has no new bracketed value.
- **The illustration's fix: an element of its own, below the bar.** Two other fixes would have left the count above 0 on some page. Changing `imgSize` or `imgPosition` cannot stop a `cover` image from reaching the bar on a phone. Giving the bar an opaque colour hides the pixels but still paints them under the logo, and changes a deployment setting. Painting the image below the bar meets the plan's after-criterion on all three pages, the Contestant App's opaque poster included. It does so for any image a deployment sets.
- **The voter home was measured by seeding the suite's project.** On the recipe's server the voter home showed the maintenance page: the CLI seeds `e2e/base` into the default project, and the suite's own project had no elections. A scratch script (`179.1-78-seed-e2e.ts`, never committed) seeded `e2e/base` into the suite's project through `setupFromTemplate`, as `data-setup-base` does. The trace and the screenshots were then taken again with the voter home.
