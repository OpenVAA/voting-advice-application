## Project Constraints (from CLAUDE.md)

- **E2E Hard Rule:** a failing, flaky or "did not run" E2E test blocks everything; no retry-until-green, no skip. A
  void run (exit 8 + `VOID-host-suspend.txt`) is not evidence: re-run under a new `--run-dir`.
- **E2E runs go through** `tests/scripts/e2e-run.sh --run-dir tests/e2e-runs/<name> --no-db-reset`; it owns its dev
  server and the identity-provider environment. The preflight cannot be skipped.
- **Comment hygiene** under `apps/`, `packages/`, `tests/`: no historical narrative, no `.planning/` paths, plan
  numbers or `D-NN` ids (only `see phase N`), nothing addressed to the reviewer, TSDoc on exported symbols.
- **Context Destructuring Rule:** never destructure a reactive accessor of `getContestantContext()` /
  `getAppContext()`; never alias `dataRoot`. Stable refs (`t`, `getRoute`, `setPassword`, …) may be destructured.
- **Svelte warnings:** fix at source; acceptance only with `// svelte-warning: accepted — <reason>`.
- **Localization:** every user-facing string in all 7 locales (`da en et fi fr lb sv` under `apps/frontend/messages/`).
- **WCAG 2.1 AA**; strict TypeScript, no `any`; `MISSING_VALUE` only in matching contexts.
- **Schema change = one commit, three parts** (schema/ edit + numbered migration + manifest line), then
  `yarn db:types`, `yarn db:lint:sql`, `yarn check:schema-equivalence` (needs Docker). A listed migration is never
  edited (`yarn assert:schema-migration-parity` in `lint:check`).
- **Never read `.env`** (memory: a refused read must not be worked around); use `.env.example`.
- Check every change against `.agents/code-review-checklist.md`. Load `Skill("database")` for schema work and
  `Skill("components")` for Svelte work.
- Standing memories that shape execution: the shared local stack is free to use (182 standing authorisation);
  `-infra` and `-gsd` share one stack; background long gates (executor watchdog 600 s); tell executors to ignore the
  orchestrator's "CONTEXT WARNING" hook line; never read a gate's status through a pipe; `yarn test:unit` needs the
  stack up; `[auth]` keys in `config.toml` are served only after `yarn db:stop && yarn db:start`.

## Summary

The phase is about thirty items in four lanes that barely share code: (1) schema/RLS migrations 00011 onwards, (2)
the mailed-link confirm page, (3) Contestant App behaviour and the UAT's UI gaps, (4) small harness/docs items and
records. The tree was read on `feat/entity-signup-multi-grant` at `63166445d`. Several CONTEXT premises are
corrected by the tree:

- **D-12's index already exists.** `public.grants` carries `grants_user_scope_target_role_key UNIQUE NULLS NOT DISTINCT
  (user_id, scope, target_type, target_id, role)`, which leads with `user_id`, and the schema comment says on purpose
  that no second index exists. **Add no index.** A session-local micro-benchmark against the running stack shows a
  table-reading `user_can` **faster** than today's claim-reading one (≈0.7× per call; 11.1 vs 15.0 ms for 987 calls
  as an admin, 14.7 vs 22.2 ms as an editor), because today's function re-parses the whole JWT on every call. The
  InitPlan fallback is very unlikely to be needed. That matters, because it would mean editing all ~131 policy call sites.
- **`bulk_import` cannot write the election↔constituency-group links at all.** Its `processing_order` has no join
  tables, and dev-seed writes them in a separate pass (`linkJoinTables`) after `bulk_import` has already inserted the
  nominations. D-18 therefore needs a link step inside `bulk_import` before `nominations`, and the dev-seed writer
  has to feed it. As things stand, moving the rule into the trigger breaks every seed.
- **The entity layout's "error view" is a bare `<ErrorMessage class="bg-base-300" />`.** D-20 has to build the "Try
  again", support block and logout. The user-level layout also signs out when the entity *list* read fails
  (`(protected)/+layout.server.ts` line 85), and the planner must decide whether D-20 covers that path too.
- **`/contestant/settings` is already taken by the entity resolver.** `[...page=contestantEntityPage]` maps `settings`
  to the entity page, and a user with zero or several entities is bounced to the app root. D-21 has to remove
  `settings` from the matcher and the resolver.
- **Image removal needs no database work.** `cleanup_old_image_file` already deletes the old `path`/`pathDark` when
  `image` changes to null. D3 is adapter + profile page + strings.
- **The not-found `<title>` defect is `handleError` returning `{ message: '500' }` for every error,** a 404 included.

**Primary recommendation:** run the phase as strictly serial waves (as Phase 179 did; `use_worktrees: false`, a
shared stack, shared hot files `migrations.manifest.json`, `packages/supabase-types/src/database.ts`,
`apps/frontend/messages/*`, `src/lib/types/generated/translationKey.ts`). Open with a Wave-0 plan that copies
Phase 179's gate driver and records the D-12 "before" EXPLAIN numbers and a negative-control ledger.

## Architecture Patterns

### System flow of a mailed link after A3

```
mail (account-access) ──link──▶ GET /<locale>/auth/confirm?token_hash&type[&next]
                                   │  (no verification on GET; scanners/prefetchers spend nothing)
                                   ├─ session present? ──yes──▶ render "signed in; continuing signs it out" + Continue/Cancel
                                   └─ no ─────────────────────▶ render Continue
Continue ──POST (form action, origin-checked)──▶ [signOut(local) if session] ▶ verifyOtp ▶ claimAndRefresh ▶ land
                                                     (recovery → reset page; magiclink → next|home;
                                                      email_change → home | login?errorMessage=…)
old link GET /<locale>/api/auth/callback?token_hash… ──303──▶ /<locale>/auth/confirm?same params
```

### System flow of an identity-provider sign-in after B4

```
frontend /api/oidc/callback ─▶ identity-callback (secret, verify token, matrix)
   ─▶ find/create account (unchanged; email_exists-tolerant)
   ─▶ rpc identity_entity_find_or_create(user, project, type, names)   ← ONE transaction
         pg_advisory_xact_lock(key(user_id))
         read raw_app_meta_data.registered_entities[project][type] → grant + row?  found | gone
         else INSERT entity, INSERT grant, UPDATE auth.users raw_app_meta_data record → created
   ─▶ app_metadata rewrite (claims scrubbed) from the RPC's returned record ─▶ magiclink token
```

### Recommended file placement

```
apps/supabase/supabase/migrations/00011_…00016_*.sql   # one per schema item (see grouping)
apps/frontend/src/routes/auth/confirm/+page.server.ts   # load (session probe) + default action (verify)
apps/frontend/src/routes/auth/confirm/+page.svelte
apps/frontend/src/lib/server/auth/mailedLink.ts          # verify→claim→refresh→land, extracted from the callback
apps/frontend/src/routes/contestant/(protected)/settings/+page.svelte   # moved settings page
apps/frontend/src/lib/components/input/Radio.svelte (+ .type.ts)        # G-179-2
```

### Anti-patterns to avoid
- **Editing policies one by one for D-11.** Change the two functions; the policies follow.
- **Putting the D-14 storage conjunct in policy text with a `::uuid` cast of `storage.foldername(name)[1]`.** A caller
  controls the path; a cast in a policy raises and aborts the statement (the `storage_path_can` header says why). Put
  the check inside `storage_path_can`'s entity-scope `write` arm, where the project id is already cast in a guarded block.
- **Validating settings inside `SupabaseAdminClient.updateAppSettings`.** The E2E harness inherits that client and
  sometimes writes settings the frontend refuses on purpose. Validate in the dev-seed **writer** (Pass 5).
- **Using `listUsers` paging again** in new Edge code (todo `2026-10-21-179-identity-lookup-pages-every-auth-user`).

### A1 / D-05 — partial unique index

- Current definition `[VERIFIED: apps/supabase/supabase/schema/305-invitations.sql:151-159]`:
  ```
  CREATE UNIQUE INDEX invitations_email_target_key ON public.invitations (project_id, email, scope, target_type, target_id) NULLS NOT DISTINCT
  WHERE
    email IS NOT NULL;
  ...
  CREATE UNIQUE INDEX invitations_code_hash_key ON public.invitations (project_id, code_hash)
  WHERE
    code_hash IS NOT NULL;
  ```
  The comment above it reads "whether or not the first promise has been claimed" and must be rewritten.
- New: `… WHERE email IS NOT NULL AND claimed_at IS NULL`. Migration: `DROP INDEX public.invitations_email_target_key;
  CREATE UNIQUE INDEX …` (same name, so the error text `duplicate key value violates unique constraint
  "invitations_email_target_key"` stays byte-identical for open duplicates).
- pgTAP rows to rewrite in `39-invitations.test.sql`: the `indexdef` pin (~line 291, which expects
  `… WHERE (email IS NOT NULL)`) and "a claimed row still refuses a second invitation for its address and target"
  (~lines 1083–1112, flagged by 174 WR-04). Then add the three D-05 cases. Re-invite after claim: lives. Re-invite after
  the claimant user is deleted (`claimed_by` → NULL, `claimed_at` kept): lives. A claimed `(project, editor)` row plus a
  new `(project, admin)` row for the same address: lives. Keep a control showing that two OPEN rows still collide.
  Update the `plan(N)` of file 39.
- Claim behaviour after re-invite: `claim_invitations` writes with `ON CONFLICT ON CONSTRAINT
  grants_user_scope_target_role_key DO NOTHING` (migration 00010), so re-inviting a user who still holds the grant
  marks the new row claimed without a second grant. No change is needed there.
- **The harness workaround (D-05 research question).** It is in `tests/tests/utils/supabaseAdminClient.ts`:
  `removeInvitations` (~376–405, deletes by `email`, `pending_email`, `target_id`, `claimed_by`), called from
  `removeUsersByEmailPrefix` (~283, comment "deleting the user alone leaves a claimed row claimed"),
  `unregisterCandidate` (~1369–1370, "so a later run would seed a duplicate of it"), `deleteAllTestUsers` (~1400) and
  `inviteByEmail` (~466–478, deletes the earlier invitation for that address+target before seeding). **Verdict: the

## Common Pitfalls

1. **Constituency rule placed after the early `RETURN NEW`.** Top-level rows skip it. Put it right after the shape rule.
2. **Seeds break the moment the trigger lands.** dev-seed inserts nominations before linking; land the
   `bulk_import`/writer reorder in the **same** plan as the trigger, and run `yarn db:seed:default` plus the e2e
   templates in the plan's verification.
3. **`user_can` garbage-claim tests go red under ROOT.** They now read the table; rewrite them (D-13), don't delete.
4. **The `07-rpc-security` censuses** (private policy helpers `'10/0/10'`; service-role-only definers; `anon` /
   `authenticated` lists) redden on every new function. Each schema plan updates the list it touches. Serialise.
5. **Hot shared files:** `migrations.manifest.json`, `packages/supabase-types/src/database.ts` (`yarn db:types` after
   each migration), `apps/frontend/messages/*/*.json`, `src/lib/types/generated/translationKey.ts`. Two parallel
   plans touching them conflict.
6. **Auth config changes are not served by `db:reset`.** Allowlist edits need `db:stop && db:start` before the
   link-issuing E2E (the wrapper restarts the stack only at its end).
7. **`assertSignInLinkShape` pins the path and exactly two params.** Change it with the link path, or every
   mailed-link spec throws.
8. **Answers-lock refusals are silent for PostgREST UPDATE** (RLS hides the row → 0-row error). Map by refreshing
   settings, not by message, on that path.
9. **Storage conjunct in policy text with a uuid cast** raises on hostile paths. Keep it inside `storage_path_can`.
10. **The E2E 10 % bound is close to run noise** (892–941 s). Compare against a median, and re-run when ambiguous.
11. **`routeConsistency.test.ts` C1/C2** for the moved settings route and the redirect-only directory.
12. **Generated component docs drift** after component edits. Regenerate once, at the end.
13. **Comment hygiene:** new comments must not cite `D-NN`, plan numbers or `.planning/` paths (lint:
    `assert:comment-hygiene`).
