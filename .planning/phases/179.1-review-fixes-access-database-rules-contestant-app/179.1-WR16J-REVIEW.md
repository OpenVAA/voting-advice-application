## Warnings

### WR-01: The 5 s window runs from before the Log out's requests, so the two pinned other-tab E2E titles depend on request latency

**File:** `apps/frontend/src/lib/contexts/auth/authContext.svelte.ts:50-55`, `apps/frontend/src/lib/auth/logoutAnnouncement.ts:9`, `:81-85`, `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:458-484`

**Issue:** The listening tab stamps `lastHeardAt` when the announcement arrives, and that arrival is before the announcing tab sends any request. The listening tab's `SIGNED_OUT` comes only after every one of these has completed, one after the other:

1. `fetch(ROUTE.AuthLogout, { method: 'POST' })`. This is a round trip through the SvelteKit server, whose handler itself calls GoTrue.
2. `supabase.auth.signOut({ scope: 'local' })`. This is a second GoTrue round trip. If the access token has expired, `_useSession` refreshes it first, which adds a third.
3. auth-js's own `BroadcastChannel` message to the other tab.

The reason the other tab shows therefore depends on whether those sequential requests finish within 5 000 ms. As a product behaviour this is accepted (T-179.1-217). But the round also pins two E2E titles on the reason appearing:

- `contestant-entity-selection.spec.ts:938`, `expectNotice('loggedOutElsewhere')`
- `admin-access.spec.ts:551`, `expectSaysWhy('loggedOutElsewhere')`

Both are listed in plan 83's `--expect-title-count` pins. This round's own runs recorded latencies past the window on this host:

- `179.1-81-targeted-r2`: a `GET /contestant` that did not answer within 10 s.
- Plan 84: a load average of about 74 during the targeted run.
- The project memory records the CI runner as about 4.3 times slower.

Under any of these conditions, both titles fail with the code behaving as designed. That is a latent intermittent failure, which the E2E hard rule does not allow.

**Fix:** Make the window follow the Log out rather than a wall-clock time that starts before it. Post `'start'` before the request and `'end'` in a `finally` after it. The follower then counts a sign-out as announced when it heard a `'start'` with no `'end'` yet, bounded by a generous cap so that a tab closed mid-request does not keep it open, or an `'end'` within the 5 s window:

```ts
// authContext.logout
withdrawAnyCount();
announceLogout('start');
try {
  await prepareDataWriter().logout();
} finally {
  announceLogout('end');
}

// logoutAnnouncement.ts
const LOGOUT_IN_FLIGHT_CAP_MS = 60_000;
let startedAt: number | undefined;
let endedAt: number | undefined;
channel.onmessage = ({ data }) => {
  if (data === 'start') {
    startedAt = Date.now();
    endedAt = undefined;
  } else if (data === 'end') {
    endedAt = Date.now();
  }
};
export function heardLogoutAnnouncement(): boolean {
  const now = Date.now();
  if (startedAt === undefined || now < startedAt) return false;
  if (endedAt === undefined) return now - startedAt <= LOGOUT_IN_FLIGHT_CAP_MS;
  return now - endedAt <= LOGOUT_ANNOUNCEMENT_WINDOW_MS;
}
```

Add a unit case: a `'start'` heard, 8 s pass, then the `SIGNED_OUT` still gives `loggedOutElsewhere`.

### WR-02: `/auth/confirm` still withdraws the count before it knows the held session has ended, and this round's guide sentence says no such path remains

**File:** `apps/docs/src/routes/(content)/developers-guide/backend/authentication/+page.md:183`, `apps/frontend/src/lib/server/auth/logoutCount.ts:8`, related `apps/frontend/src/routes/auth/confirm/+page.server.ts:55-61`

**Issue:** The rewritten guide sentence states: "A sign-out the server makes on its own for a request, other than the hook's, expires them only once the sign-out has worked or found the session gone; a failed one with a session left keeps the count for the next request." The confirm action does not do this:

1. It calls `withdrawLogoutCount(event)` first (`:55`).
2. It then signs out the session the request holds (`:57-60`). It ignores an `{ error }` answer and only logs a rejection.
3. It then calls `verifyMailedLink`.

`/auth/confirm` is a page that no gate row claims (`routeConsistency.test.ts:525`), and its load answers `signedIn: true`, so a browser with a live session reaches the action. auth-js's `_signOut` returns its error without removing the session when `_useSession` itself fails (`GoTrueClient.js:3434-3435`), for example when an expired access token cannot be refreshed during an auth-service outage. If `verifyOtp` then fails too, the response keeps the held session and has already expired the count.

This is the sequence WR-02 of 179.1-WR16I traced for `signOutToLogin`: a closed tab's requested sign-out is lost. The precondition is the same failure class. `logoutCount.ts:8` says "The sign-in actions call it before they sign in". That is true of the order, but it does not mention that this sign-in action can run over a live session, unlike the four the gate protects.

**Fix:** Withdraw in the confirm action only when no session is held, or once the held session's sign-out is known to have ended it. Otherwise withdraw after `verifyOtp` has set the new session, inside `verifyMailedLink` before its redirects:

```ts
// routes/auth/confirm/+page.server.ts
const { session } = await readHeldSession(locals);
if (session) {
  const failure = await locals.supabase.auth.signOut({ scope: 'local' }).then(
    (a) => a.error,
    (e: Error) => e
  );
  if (failure) log.error(`Confirm page: signing out before the verification failed: ${failure.name ?? '-'}`);
  if (!failure || (await isSessionGone(locals.supabase))) withdrawLogoutCount(event);
} else {
  withdrawLogoutCount(event);
}
```

Alternatively, pass `event` into `verifyMailedLink` and withdraw right after a `verifyOtp` with no error. Either way, add the confirm action to the guide sentence, or narrow the sentence to the paths it is true of. Add a unit case: a held session whose sign-out answers `{ error }` with a session left, then a failed `verifyOtp`, leaves both count cookies in place.

### IN-01: The Admin App's sign-out of a non-administrator is a browser sign-out in another tab, but it is never announced, so its other tabs now show no reason

**File:** `apps/frontend/src/routes/admin/(protected)/+layout.ts:60-77`, `apps/frontend/src/lib/contexts/auth/authContext.svelte.ts:50-55`

**Issue:** `handleError` calls `dataWriter.logout()` directly, not through `authContext.logout`, so in the browser it signs the tab out without `announceLogout()`. Another open tab of either app receives `'elsewhere'` from its client, does not hear an announcement, and opens its login page with no reason. Before this round that tab said "You have been logged out in another tab or window.", which in this case is true. The guide's new paragraph is consistent with the code ("names another tab as the cause only when that tab announced it"), so the point is the lost sentence, not a wrong one.

**Fix:** Call `announceLogout()` in `handleError` before `dataWriter.logout()` in the browser, or accept the loss and record it beside T-179.1-217.
