# Phase 179.1 Plan 59: A protected load asks whether a session is left after a failure Summary

**One rule, `isSessionGone(client)` in the Supabase adapter, decides in both apps after a failure: no session left goes to the login page, a live session or no answer keeps the error page.**

## For the operator's reading

What a user meets now after a failure in a protected load:

- **Admin App, a session ended elsewhere:** a link from the login form into the app, with the session ended by a request no tab was told of, now reaches the login form with `errorMessage=loginFailed`, and a reload stays there. Before, it ended on the error page (`Something went wrong, sorry!`) at `/admin`. Observed on a dev server, red without the change and green with it. A live session whose read fails still meets the error page, as plan 54 left it: plan 54's failed-read tests pass unchanged in the close.
- **Admin App, a user who is no administrator whose sign-out fails:** when the failed sign-out has cleared the cookies (the auth library removes the session before it answers `{ error }`), the user now ends on the Admin App's login page with `errorMessage=userNotAuthorized`. Before, it was the 403 page. When the cookies stay, the 403 stays (plan 54's test passes unchanged). The server's own pass never asks and keeps the 403, because the client there writes no cookies.
- **Contestant App, a failed sign-out in a protected load:** `signOutToLogin` now redirects to the login page with its code when the request's client answers no session after the failure. It shows the 503 only when a session is left or the client answers an error. **This arm is unit-tested only.** No browser run can fail the server's own call to the auth service.
- **Contestant App, a session ended elsewhere:** a link to a page whose load makes a request reaches the login screen. This was measured before (the diagnosis drove six navigations) and is now held by a committed test. It holds at HEAD by design. Its red comes from a production mutation.

What stays unproven:
- The Contestant App's failed sign-out on the server: unit cases only (ruling 1's library behaviour comes from the diagnosis's probe and was not re-run here).
- A navigation that makes no request and runs no load, after a sign-out made only by a server in another tab, still shows the stale page in both apps (ruling 7). Plan 60's `SIGNED_OUT` listener covers sign-outs the browser makes; the server-only residue is for plan 66's list.
- The Admin App's new paths were driven on a dev server only, not in a production build. The docs page says so.
- Ruling 4's server half (the universal client answering no session after its own failed sign-out) was read, not run. The unit case pins that the server does not ask.

Observed and inferred:
- Observed: every new or rewritten test was red without its change (runs below) and green with it, in `179.1-59-green` and `179.1-59-close`.
- Observed: the plan's two-file mutation (the gate's no-session redirect skipped for the Contestant App and `signOutToLogin` answering the 503 unconditionally) leaves the Contestant App's test green. Adding the protected load's first-stage redirect to the mutation turns it red, on the error page. Inferred, by reading: the first stage's own `!session` redirect is what caught it.
