# Phase 179.1 Plan 73: Every server sign-out withdraws the logout count Summary

**`withdrawLogoutCount` now runs first in the logout endpoint and in `signOutToLogin`, so a sign-out the server makes leaves no logout count behind; with plan 72's sign-ins and plan 71's page, every sign-in and sign-out the application makes withdraws the count, and `hooks.server.ts` is untouched.**

## For the operator's reading

- **What a user now meets:** whatever ends a session, no logout count survives it to end the next one.
  - Before this plan, one sequence still left a count behind. The logout modal opens in one tab, and that tab is closed. The session is then ended by the server with no page told of it, for example a sign-out request made outside any page. The count stayed in the browser until the next sign-in removed it.
  - Now the server's sign-out removes it at once, before it ends the session.
  - The same holds for the Contestant App's protected layout. When it signs a user out because their data cannot be read, the count goes in the same response.
- **Where a count is withdrawn**, as the guides now say:
  - by the page, at any Log out of either app, before its request;
  - by the server, at every sign-in and at every sign-out it makes;
  - the hook's own sign-out settles the count instead of withdrawing it, and the settled marker is left for the page.
- **What stays unproven** (rule 17):
  - **Read, not driven:** the Admin App's protected load's sign-out. In the browser it goes through the data writer's `_logout`, which posts to the logout endpoint before its own sign-out, so it reaches the withdrawal. No browser run signs a non-admin out there with a count present.
  - **Unit-tested, not driven:** `signOutToLogin`. No browser run makes the protected layout's user read fail with a count present.
  - **Not in a browser:** the removal for a host's own domain and its parents on a real apex host. Every E2E origin is `localhost`.

## Decisions Made

- **Both sites pass the event itself**, as the sign-in sites of plan 72 do. Each unit case asserts that the helper's argument is the event.
- **`signOutToLogin`'s new parameter is the fourth.** The first three keep their places and meanings, so its contract is unchanged except for the request fields (`PROH-179.1-54`).
- **The protected layout's load takes `event` and destructures from it.**
  - Destructuring `request` and `url` in the signature would have added two event reads on every request. `layout.tracking.test.ts` pins that the load takes `cookies`, `fetch`, `locals` and `params` and nothing else.
  - With the change, the event is handed on only on the two sign-out paths.
  - The helper then reads `url.hostname` and `url.protocol`. SvelteKit's `make_trackable` does not track either (read in `node_modules/@sveltejs/kit/src/utils/url.js`: only `href`, `pathname`, `search`, `toString`, `toJSON` and `searchParams` are tracked).
  - `layout.tracking.test.ts` passes unchanged.
- **Ruling 1's list, derived at run time** (`tests/e2e-runs/179.1-unit/179.1-73-sites.txt`). Eight `.signOut(` lines are classified as follows; no site was added or removed against the plan's reading:

  - **`sessionAdmission.ts`, `mailedLink.ts` and the confirm action's held-session sign-out:** each runs inside a request that has already called the helper (plan 72).
  - **The endpoint and `signOutToLogin`:** they call it now.
