# Phase 179.1 Plan 26: image removal and the open answer before the answer Summary

**A candidate can now remove their portrait and an organization its logo from the profile, and the stored file is deleted after the save. The writer turns `image: null` into a null image column, and the existing `cleanup_old_image_file` trigger does the rest, so no migration was needed. On the question page the open answer can be written before an answer is chosen. Save stays disabled until then, and the sentence beside it says why. The close is green: 642 of 642 tests in 128 projects, two more than plan 25 in `contestant-journey` and one more in `perm-organization-editing`.**

- **Duration:** about 1h 28m (2026-10-28T22:40Z to 2026-10-29T00:08Z). Part of that was spent waiting while the host was loaded: a FileProvider scan held the 1-minute load at 11–19.
- **Tasks:** 3 of 3.
- **Files:** 26 outside `.planning/`, plus the ledger.

## What changed

- **Task 1 (tracer).** In `_updateEntityProperties`, `image === null` sets the image column to `null` before the upload branch. The read-back gives `null` through `parseImageColumn`'s `absent` outcome. `UniversalDataWriter.updateEntityProperties` no longer refuses `null`. `EditableEntityProps.image` and the store's `setImage` both take `null`. `changedProperties` stages a `null` only over a stored image. The profile page renders Remove under the image `Input` when the descriptor names a label, an image is shown and answers are unlocked. Pressing it calls `userData.setImage(null)`, then moves focus to the image field's button, because Remove leaves the page along with the image.
- **Tracer feedback gate.** Interactive, end-of-phase, and the `<verify>` is automated only. As written it exited 1 on the `--dirty-only apps/frontend` slash quirk and the `yarn -s` quirk. Restated, it exited 0. Tracer verified end to end; the plan went on to Task 2.
- **Task 2.** The organization's descriptor gained `imageRemoveLabel: 'contestantApp.basicInfo.removeLogo'`, and the member became required. The page now reads the label from the descriptor alone.
- **Task 3.** The open-answer `Input` is now `disabled={status === 'loading'}` and `locked={answersLocked}`, with no placeholder. `answerMissing` (no value in the draft or the saved data) feeds `canSubmit`. While it holds, `<p id="contestant-questions-save-reason">` shows `answerQuestionFirst` above Save and is Save's `aria-describedby`. `setAnswer({ info })` already merges into a value-less answer, and nothing autosaves, so a draft that holds only an open answer stays in the draft until Save writes it together with the answer.

## How the deleted object was observed

The new journey test reads the `src` of the profile's thumbnail through `shownImageUrl()`. That is the public `storage/v1/object/public/public-assets/…` address. The address is held in a variable and never logged; the poll's message names no address. Before the removal, an anonymous `fetch` of it returns 200. After the save and a fresh load, the profile shows no image and no Remove. Then `expect.poll` (30 s; 0.5, 1 and 2 s intervals) waits for the same GET to return 400, which is how local Storage answers for a deleted object, as in `storage-cleanup.spec.ts`. Observed in `179.1-26-green` and in the close.

## Issues Encountered

- **An info-only draft and another page's save (inferred, not observed).** The store's `save()` writes every drafted answer. If a draft that holds only an open answer outlives the question page, for example because the tab was reloaded, a later save on the profile page writes `{ info }` with no value. The database admits it (`validate_answer_value` returns early on a null value), and the question still counts as unanswered. The question page itself never saves such a draft. This is recorded here and not changed.
