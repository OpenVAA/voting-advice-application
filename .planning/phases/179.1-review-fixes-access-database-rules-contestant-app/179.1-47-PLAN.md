## Rulings carried by this plan

1. **`CR-02` is measured in a real browser, which no earlier report had.** The review and the verifier replayed SvelteKit's writes in a harness. `179.1-planning-probe-2`, against the unchanged product, sign-in, opinions task, a question, an unsaved answer, Log out, Back with the native question accepted: the address is the list's, the list is not rendered, the question's answer input is, the modal is closed, and the page raised `HttpError`. Past the count the session is alive. `179.1-planning-probe-3`, with the two layers below: the list is rendered, the answer input is gone, nothing is raised. Only the question page's guard chain can throw (read: the profile's and the details' guards read `userData` and local state).

2. **Layer one, the page.** `heldInfo` compares the held answer with `parseParams(page).questionId`, as `answersLocked` beside it already does, in place of the question's own id. **The verifier's wording stops one step short, and the review's code does not:** on a route with no question and no held answer both sides are `undefined`, so they compare equal, and reading `.info` off the undefined holder would throw the same way. The read is `heldOpenAnswer?.info ?? null`. Nothing else in `heldInfo`'s value changes: on a route with a question the comparison gives what it gave.

3. **Layer two, the button.** The close moves from `afterNavigate` to `onNavigate`. SvelteKit runs `onNavigate` after the load and before `root.$set` and `update(page)` (`node_modules/@sveltejs/kit/src/runtime/client/client.js`, in `navigate`), so `modalOpen` is false before the new page is written, and `unsavedOnPage` short-circuits. This holds for any guard a later page mounts. `closingForNavigation` stays, so a navigation's close runs no `keep`. A refused navigation never reaches `onNavigate`, so the modal stays open over the refusal, as it does today. A change of the hash alone keeps the same page under the modal and changes no param, so nothing throws, and the modal staying open there does no harm.
   - **The two invariants of `CLAUDE.md`, checked.** The hooks' order is that of registration. A button mounted in the first hydration registers before the root layout's hook, closes the dialog, and the root's `startViewTransition` finds no `dialog[open]` and keeps its names over a page with no modal open. A button mounted after a client-side sign-in registers after it: the root finds the dialog open and strips the names, and the close follows. Neither order runs a transition with names over an open modal. No `load` is touched, and `onNavigate`'s callback reads no `url`.

4. **Both layers stay.** The page's layer fixes the one chain that throws. The button's layer stops a header component reading a page's state across a route change at all, for every guard. Task 3 shows each alone keeps the next page rendering, so neither is a passenger.

5. **`WR-09`, the event.** The handler is on `close`, not `cancel`. A close request fires `cancel` only when the page has had a user activation since the last one, and fires `close` always; `requestClose()` and a dialog's `close()` also end in `close`. Measured at planning in Chromium 153 on a plain page: `requestClose()` gives `cancel`, then `close`, with no `keydown`.
   - **The verifier's `if (isOpen) handleClose()` is one check short.** Measured at planning on the same page: `close()` then `showModal()` in one task fires the queued `close` with `open` true, and a handler reading only `isOpen` would close the modal just opened. So the handler is `handleNativeClose`, which runs `handleClose()` only while `isOpen` is true and `modalContainer?.open` is false. It also keeps the handler idempotent after Continue, the ✕ and Escape, where `isOpen` is already false.
   - **It reaches every modal,** which is why it is unit-tested on `ModalContainer` itself. Their `onClose` now also runs on a platform close, where before the component believed the modal was still open. Read for each consumer at the task's start, by `git grep -n -E "<(Modal|TimedModal|ConfirmationModal|ModalContainer)( |$)" -- 'apps/frontend/src/**/*.svelte'`; a consumer whose `onClose` would do harm on this path stops the task with a report. `git grep -n onclose -- 'apps/frontend/src/**/*.svelte'` has no hit today, so no consumer passes one through `restProps`.
   - **`179.1-planning-probe-2` reproduced it in the browser:** `requestClose()` on the modal, the clock past the count, and the user is on the login page with the server answering 303. `179.1-planning-probe-3`, with this handler: on the profile, with the server answering 200.

6. **What is not established.** That Android's back gesture reaches this path is from the HTML standard and Chrome's documentation. No run has a device. The handler is right either way, and a device decides how often the path is met. It goes on the operator's list in plan 50.

7. **Tests that change on purpose.** In `LogoutButton.svelte.test.ts` the mock of `$app/navigation` and the three cases that call `afterNavigateCallbacks` (`closes an open modal, and the count no longer logs the user out`, `leaves a closed modal as it was: the dialog keeps its hidden class`, `a navigation closes it, runs no `keep`, and the count no longer logs the user out`) move to a helper that replays SvelteKit's order. They stay green at the old product, as pins, and the ledger says so. The test the helper exists for is new and red.

8. **Sign-ins.** Two more password sign-ins in this spec, below the auth service's thirty in five minutes from one origin. A refusal for that reason is a stop with a report.

9. **Nothing else moves.** No message key, no visual change, no new component: a real close of a dialog looks as a close does. Nothing under `apps/supabase` or `packages/supabase-types`. The ✕ and Escape during a sign-out stay as they are: holding them back is the operator's decision. The visual project is not run, as the rules state.

**Not adopted from the proposals, and why:** the verifier's two proposals above were changed where the code or a measurement said so, in rulings 2 and 5. The review's question whether the throw makes `goto` reject in a browser is no longer open for this path: the probe's Back was a `popstate`, and it raised a page error with no `goto`.
