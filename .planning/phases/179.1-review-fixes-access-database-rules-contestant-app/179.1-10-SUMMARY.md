# Phase 179.1 Plan 10: an invited address is in use on CI1 Summary

**`confirm-address` now asks the service-role function `address_holds_open_invitation` once it has taken both slots. When an open invitation of the project holds the typed address, it answers `in-use` and gives the address's slot back. So an identity-provider account, which can claim no invitation, can no longer take an invited address and lose the invitation.**

## Accomplishments

- **The function** `public.address_holds_open_invitation (p_project_id uuid, p_email text) RETURNS boolean`:
  - `LANGUAGE sql STABLE SECURITY DEFINER`, `search_path = ''`.
  - It answers `EXISTS` over `public.invitations` of the project with `claimed_at IS NULL`, `expires_at` null or in the future, and `email` or `pending_email` equal to `NULLIF(lower(btrim(p_email)), '')`.
  - A null project, a null address and a blank address answer false. It writes nothing.
  - EXECUTE is revoked from `PUBLIC`, `anon` and `authenticated` and granted to `service_role`.
  - It is in `506-invitation-rpcs.sql` after `identity_entity_find_or_create`. The schema's REVOKE / GRANT block names it, and its comment now counts eleven.
- **Migration** `00019_address_holds_open_invitation.sql`, sha256 `37e4c1a6de42527cd4578463d24fbfd1e5dd056b46a827393623b9ce85f38ef1`. It is the manifest's last entry, and parity exits 0. `check:schema-equivalence`: `EQUAL`.
- **pgTAP file 57** (`AOI: `, plan 17):
  - the catalogue and the privileges;
  - true for `email`, for the `pending_email` of a code row, and for a later expiry;
  - true for both addresses asked with spaces and capitals;
  - false for a claimed invitation, an expired one, another project's (true when asked in that project), an address no invitation holds, and null or blank arguments;
  - the calls take no throttle slot and change no invitation.
- **The census:** § 8c of `07-rpc-security` lists thirteen functions, with `address_holds_open_invitation` among them. The database skill names the function in that census, among the invitation helpers, and in `confirm-address`'s order.
- **`confirm-address`:**
  - `AddressConfirmationDeps.addressHoldsOpenInvitation({ projectId, email })` has TSDoc. `confirmAddress` asks it right after `takeSlot` and before the current address's link.
  - It answers `giveBack(deps, slot, 'in-use')` on true. A rejection, or an answer that is neither true nor false, goes to the existing failure path: the slot is given back and the answer is `refused`.
  - `index.ts` calls `admin().rpc('address_holds_open_invitation', { p_project_id, p_email })` and rejects an answer that is not a boolean.
  - `contract.ts`'s in-use paragraph now also covers an address that an open invitation of the project holds, under the same bounds.
- **The E2E case** (`contestant-identity-provider`, describe `an address an open invitation holds`):
  - An open email invitation is seeded for a fresh `identity-provider-` address on the dataset's candidate. Seeding sends no mail.
  - A new identity types that address on CI1 and gets `emailInUse` with `data-reason="in-use"`.
  - The catcher then holds no mail for the address. `confirm-address` answers only after its work, so the answer on screen is the request's completion witness.
  - The address's one invitation still has `claimed_at` null, and the describe's `afterEach` removes it.
  - New fixture steps: `addressAnOpenInvitationHolds`, `expectInvitationOpen`, `removeInvitationsOf` and `expectNoMailFor`.
