# Phase 179.1 Plan 17: support inside the sentence on the identity provider's error screen Summary

**The identity provider's error screen (CI2) offers support once per class. In the retry and cancelled classes, the words "contact support" in the sentence under Try again are the link to the Help page's support section. `ContactSupport` renders that through `sentence`, with the link built in code, escaped, and the whole sentence passed through `sanitizeHtml`. In the noRetry class, the Contact support button has no icon (`icon={null}`). Along the way, the E2E harness was fixed so that each run asks for the mailed links of its three fixed identities under addresses of its own. The suite had been spending each address's 20-a-day mail budget, and that turned `179.1-17-green-2` red.**

## The red green-2, and the harness fix

**What happened (observed).** `179.1-17-green-2` was the one-project control of Task 2's held change.

- It failed in its setup `data-setup-passwordless-session` with `Expected: "sent"`, `Received: "not-sent"`, then 414 did-not-run.
- There was no void marker.

**The cause.** It is diagnosed in full in `tests/e2e-runs/179.1-e2e/179.1-17-green-2.diagnosis.md`.

- **Observed:** `invitation_link_request` takes a `link-address:<hash>` key, 20 per address per day across every project. That key for `TEST_PASSWORDLESS_EMAIL` stood at 21, with its window ending at 2026-10-27 20:58:04 UTC.
- **Observed:** 20 runs across plans 10 to 17 had each spent one take.
- **Re-tested in isolation inside a `ROLLBACK`:** the suite never got its take back. It deletes the invitation first, and that delete's trigger removes the per-minute `link:` key. `invitation_link_release` gives back a day take only when it finds that key.
- It was a harness defect, not a defect of Task 2.

**The fixed addresses.** The suite has three: three identities that ask for a mailed link under one fixed address on every run. They were found by hashing every e-mail literal in `tests/` and `packages/dev-seed`, and every exported address constant of the suite's utilities, the way the function hashes them (`sha256` of the trimmed, lower-cased address), and matching the hashes against the rows. Only these three had a day count above 1. Every other row was at 0 or 1: per-call addresses, or addresses whose slot was given back.

| Identity | Path that asks for the link | Day count before the fix |
|---|---|---|
| `TEST_PASSWORDLESS_EMAIL` | `data-setup-passwordless-session` (`askForLink`) | 21 |
| `UNREGISTERED_CANDIDATE_EMAIL` | `contestant-journey`: the sign-in link, then the forgot-password recovery link, which takes the same budget | 18 |
| perm-localisation-positive `RECIPIENT_EMAIL` | `perm-localisation-positive` (`inviteByEmail`) | 14 (the third address of the diagnosis, which it had not identified) |

**The fix** (test-side only; the database's limit and `invitation_link_release` are unchanged):

- `tests/tests/utils/runAddressTag.ts` holds the run tag in `E2E_RUN_ADDRESS_TAG`: sixteen lower-case hex digits. The first module load writes a fresh tag when the variable is empty, and a malformed value throws.
  - `playwright.config.ts` imports the module. The runner loads the configuration before it starts any worker, so every worker inherits the one tag.
  - Observed: in `179.1-17-harness-green`, the session the setup wrote in one worker was read under the same address by `contestant-a11y-scan` and `contestant-entry-phone` (`expectAddress`), which ran in other workers.
- `runScopedAddress(start, tag, length?)` builds the addresses:
  - `TEST_PASSWORDLESS_EMAIL` is the prefix, the tag, then `x` up to exactly 64 characters. No hyphen or dot follows the prefix, so the screens still meet the longest local part.
  - `UNREGISTERED_CANDIDATE_EMAIL` is `unregistered-aa-<tag>@…`.
  - The new `L10N_POSITIVE_CANDIDATE_EMAIL` in `testCredentials.ts` is `candidate-l10n-pos-aa-<tag>@…`. The localisation spec and its teardown both read it; they had each declared the literal before.
- The teardowns that unregister these users read the derived constants. These are the journey's setup and teardown and the localisation teardown. The passwordless teardown removes everything under the prefix, which the derived address keeps.
- Before the green run there was no user and no invitation under the old fixed addresses, so no grant from an earlier run could block a claim.
