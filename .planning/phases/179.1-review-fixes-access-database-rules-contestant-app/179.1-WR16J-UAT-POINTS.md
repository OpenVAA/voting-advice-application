## A. This round's code review (`179.1-WR16J-REVIEW.md`, all `open` in its disposition)

### A1 — ⚠ DECIDE — WR-01: the 5 s window starts before the Log out's requests

The announcing tab posts before it makes any request. The listening tab's `SIGNED_OUT` only arrives after `POST /api/auth/logout`, then the client's `signOut`, plus a refresh first if the token has expired. If those take more than 5 s, the other tab shows no reason. The product loses only the sentence, which T-179.1-217 accepts. But the two pinned E2E titles (`contestant-entity-selection.spec.ts:938`, `admin-access.spec.ts:551`) then fail, and the E2E hard rule allows no flaky test. They were green under load 38 to 74 in this round.

- [ ] ★ RECOMMENDED — **Schedule the review's fix.** Post `'start'` before the request and `'end'` after it. A sign-out counts as announced while a start is outstanding (capped at 30 s) or within 5 s of an `'end'`. Add unit cases for a slow Log out, a start with no end that runs past the cap, and an end with no start. Restate T-179.1-215/216/217 to match (the audit notes that a forged `'start'` widens what T-216 accepts to the cap). No new copy is needed.
- [ ] Widen the single window to 30 s and change nothing else. It's a one-line change, but a sign-out the client makes by itself within 30 s of another tab's Log out then reads as the other tab's.
- [ ] Accept it as is and record the titles' dependence on latency. This conflicts with the E2E hard rule.

### A2 — ⚠ DECIDE — WR-02 and the audit's unregistered flag: `/auth/confirm` withdraws the count before it knows the held session has ended

`routes/auth/confirm/+page.server.ts:55` withdraws the count, then signs out the held session and ignores an `{ error }` answer (`:57-60`). If that sign-out fails, the session stays, and if `verifyOtp` then fails too, the closed tab's requested sign-out is lost. This is T-179.1-218's harm on a path the register doesn't name, and the auth guide sentence plan 84 wrote (`authentication/+page.md:183`) is false for it. Plan 84 kept this path out of scope (PROH-179.1-60). The audit, reading the code without running it, also says the gated sign-in actions (`admin/login`, `contestant/login/email`, `contestant/register/sign-in`) withdraw first. During an auth outage, a kept session can be read as no session there.

- [ ] ★ RECOMMENDED — **Schedule the fix and register the threat.** In `/auth/confirm`, withdraw only when no session is held, or after the held sign-out has worked or `isSessionGone` confirms the session is gone. On a failed sign-out with a session left, show the failure and keep the count. Diagnose the three gated sign-in actions in the same plan and fix them the same way if the reading holds. Add unit cases that are red first. Register the threat as T-179.1-223, mitigated. The guide sentence then stays true.
- [ ] Fix `/auth/confirm` only, and record the gated actions as an accepted limit (they need an auth outage while a stale tab's count is held).
- [ ] Accept both. Narrow the guide sentence to the paths it is true of, and register T-179.1-223 as accepted.
