# Phase 179.1 Plan 23: a closed menu item's reason opens on click Summary

**The Contestant App's menu now shows its closed items without any reason text. Each closed item that has a known reason (profile, questions, preview) is an operable button announced as unavailable. A click shows the reason under it in a polite live region, and a second click hides it. Nothing navigates and the menu stays open. This is built into `NavItem` as `disabledReason`. The standalone reason line and its `aria-describedby` are gone. The close is green: 635 of 635 tests in 128 projects.**

## What changed

- **Task 1 (tracer).** `NavItem` got two new props: `disabledReason` and `disabledReasonProps`. Its `{#if closedWithReason}` branch renders a button and a `role=status` region (id `${$props.id()}-reason`). The other branch is the earlier `<svelte:element>`, unchanged except that both now share `handleClick`. Pointer events are turned off only for a disabled item that has no reason. `ContestantNav` passed the reason to the preview item. The line stayed only while the profile or the questions item was closed.
- **Task 2.** The profile and the questions items get their reason through `reasonOf(closed)` and `reasonProps`. `closedItemProps` passes the dimming class always, plus the link role only while no reason is known. The line and `CLOSED_REASON_ID` are gone.
- **Tracer feedback gate:** auto mode, `<verify>` automated only. Re-ran restated, exit 0, then expanded.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - test defect] The fixture's click on an `aria-disabled` item never fired**
- **Found during:** Task 1 green control (`179.1-23-green`).
- **Issue:** Playwright's actionability check treats `aria-disabled=true` as not enabled, so `click()` waited until its timeout.
- **Fix:** The fixture asserts the item is visible, then clicks it with `force: true` (inline `// reason:` and `eslint-disable`). It collapses the item with `press('Enter')`, so keyboard operation is covered too.
- **Verification:** `179.1-23-green-r3`.
- **Commit:** `1e2ca99f1`.

**2. [Rule 1 - test defect] The list-item lookup in the fixture matched nothing**
- **Found during:** `179.1-23-green-r2`.
- **Issue:** `filter({ has: menu.getByTestId(…) })` resolves its inner locator from the list item, so an inner locator that starts from the menu never matches. The "no reason before the click" check therefore held trivially.
- **Fix:** Added `rowOf(name)`, which builds the inner locator from `page.getByTestId(…)`.
- **Verification:** `179.1-23-green-r3`, `179.1-23-green-perm`.
- **Commit:** `1e2ca99f1`.

**3. [Rule 2 - controls] perm-no-nomination controls in both tasks**
- **Issue:** The plan named only the journey (Task 1) and the journey plus the scan (Task 2). But perm-no-nomination's menu tests read the rewritten fixture steps, and committing without running them could have turned committed tests red.
- **What was run:** red and green controls for that project in each task. Its chain runs `contestant-journey` first, so the Task 1 red was taken with the journey change left out (`-alone`).
- **Files:** `perm-no-nomination.spec.ts`, which the plan did not list.

**4. [Rule 3 - red for the scan] The scan's red was taken on a revert**
