## Warnings

### WR-01: A failed sign-out is said to leave the session alive, but the commonest `{ error }` form has already removed it

**File:** `apps/frontend/src/lib/server/contestant/signOutToLogin.ts:10`, `:22-29`. The same reason is given in `apps/frontend/src/routes/contestant/(protected)/+layout.server.ts:13`, `apps/docs/src/routes/(content)/developers-guide/contestant-app/login-and-password-reset/+page.md:24` and `apps/docs/src/routes/(content)/developers-guide/backend/authentication/+page.md:36`.

**Issue:** The docstring says of every failed sign-out that "the session is alive, the gate sends a live session straight back from the login page". The installed auth library says otherwise. In `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:3440-3450`, when the auth service's answer to the sign-out fails, `_signOut` calls `_removeSession()` first and then returns `{ error }`. `locals.supabase` is the cookie-writing server client, so that removal clears the cookies. `routes/api/auth/logout/+server.ts` already states this: the client "may or may not have removed the session", and it has "when the auth service's answer is what failed".

So in that form:

- the session is gone from this browser, and the server-side session has not been revoked;
- the gate would not send the request back, so a redirect could not loop;
- the user still gets a generic 503, with no `loginFailed` message, and finds themselves signed out on the next reload.

The plan's truth asks for an error page after any failed sign-out, and the code does that. R2's own wording is "redirects to login only if the session has gone, otherwise a translated error page", and this path does not follow its first half. `signOutToLogin.test.ts` cannot show this, because its fake `signOut` never touches a session. The second comment in `routes/admin/(protected)/+layout.ts:45` has the same weakness on the browser path, where a 502 from the endpoint may also follow cleared cookies. On the SSR path it is true, because the universal client has no cookie writer.

**Fix:** At the least, correct the reason in the four places: the sign-out failed, and the session may still be alive, so a redirect could loop. If the operator wants R2 applied literally, redirect when the failed sign-out left no session:

```ts
if (failure) {
  log.error(`[Contestant App protected layout] Error logging out: ${failure.message}`);
  const { data } = await locals.supabase.auth.getSession();
  if (data.session) error(503, { message: t('error.default') });
}
redirect(307, buildRoute({ route: 'ContestantAppLogin', locale, errorMessage: code }));
```

Add a unit case in which the fake's `getSession` answers no session after `{ error }`. The behaviour change is the operator's call, because plan 54's truth reads the other way.

### WR-02: The test "Back stands on the login form" cannot see where Back ended

**File:** `tests/tests/specs/admin/admin-access.spec.ts:407-420`, with `tests/tests/fixtures/admin/adminLoginPage.fixture.ts:152-168` and `:229-232`

**Issue:** The form is already visible before the Back, and stays visible while the navigation runs. Each step then passes on the page as it stood before the navigation ended:

- `goBackToHomeOrLoginForm` settles on `focusReset || emailInput.isVisible()`, so its first poll is true at once.
- `expectLoginFormStandsWithNoMessage` asserts `toBeVisible` and `not.toContainText`. Both pass on their first check, against the same DOM.
- `reload()` then runs, and from a live session it reaches the home whatever Back did.

If Back ended on the home, on the error page or with the message, the test could still pass, or pass depending on timing. The test also reloads while the navigation may be running, so which address it reloads from is not fixed. The fixture's TSDoc admits the step "reads what stands, not that a navigation has ended", and the sibling link test settles on the address, but the Back test has no settle of its own. Ledger row 54-4 confirms that no control reaches this half: the only mutation that turns this title red, `mut-cookies`, fails at `expectAdminHome` after the reload. CLAUDE.md treats a timing-dependent test as a defect, and the title claims more than the test holds.

**Fix:** Give the Back a signal that its navigation has ended before reading the page. The address cannot serve as one, because a Back keeps its address. One option is to wait for the redirect the load makes, with a `framenavigated` or URL wait the step registers before `goBack`, if the redirect does change the address on this path. Then prove the assertions can fail with a mutation that makes Back end elsewhere, and add a ledger row. If no signal exists, retitle the test to what it holds, such as "after Back, a reload reaches the home", and drop `expectLoginFormStandsWithNoMessage` from it, so that no one reads it as holding R1's "no message" term for Back.

### WR-03: With a stale session in the page data, a gone session is still reported as a failed read

**File:** `apps/frontend/src/routes/admin/(protected)/+layout.ts:22`, `:35-38`, with `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:574-580`

**Issue:** This is T-179.1-137, undecided on the operator's list and pinned by a committed test at `admin-access.spec.ts:438-463`. It is raised because WR-16's stated aim is that the load tells no session from a failed read, and it does so in one direction only. `session` comes from the outer server load, whose data is not refreshed on a client navigation. `_getBasicUserData` throws `No active session` when the session is gone, `getUserData` turns that into `undefined`, and the load answers 503 with "Something went wrong, sorry!" to someone who is simply signed out, and logs it at error level. Before this change the same path showed the login form, so this is a regression, and a reload clears it. The title of the guide's bullet, at `backend/authentication/+page.md:180`, covers only the stale tab.

**Fix:** Do not change this without a ruling. If the operator schedules it, it needs no new load: have the writer raise a distinct error for the two `No active session` lines, or have the load ask its client whether a session exists once the read has failed, and redirect to login when none does. `getUserData.ts` is protected by `PROH-179.1-22`, so a fix there needs the ruling to cover it. Otherwise the load would call the writer itself.

### WR-04: The Admin App's page states the role rule the opposite of the code's

**File:** `apps/docs/src/routes/(content)/developers-guide/admin-app/+page.md:12`

**Issue:** The line says "A user who also holds an `editor` grant on a candidate is given the role `candidate`, not `admin`." Both halves are wrong:

- `UserRole` is `'contestant' | 'admin'` (`lib/api/base/dataWriter.type.ts:286`), so there is no role `candidate`.
- `_getBasicUserData` tests the admin arm first, and its comment says that "an identity holding both an admin grant and an entity editor grant is an administrator".

A reader of this page would conclude that an entity grant takes away admin access, when such a user is admitted to the Admin App. The line is not in the diff, but it sits directly below the bullet this change rewrites, which says "Any other user is signed out". The checklist asks for the docs to match what the change touches.

**Fix:** "The role is worked out from the access token's grants, and the admin grants are tested first: a user who holds both an admin grant and an entity's `editor` grant has the role `admin`. A user with only entity grants has the role `contestant`, and a user with neither has no role."
