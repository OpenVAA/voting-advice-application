# Phase 179.1 Plan 19: one bordered Radio for registration, the party option's wording and the hero Summary

**Registration's radios now come from one new component, `Radio` in `lib/components/input`: a native radio with `radio radio-primary border` inside a label that covers its row, bound with `bind:group`. The identity provider's entity-type radios use it, and they now draw a border, which they did not before because the theme sets DaisyUI's `--border` to 0. The mode selector uses it too. The party option reads "A party or constituency association" ("Puolue tai valitsijayhdistys" in Finnish, and its equivalent in five other locales). The registration page has a hero, the old pre-registration route's 🖋️, through the new key `contestantApp.register.heroEmoji`.**

## Deviations from Plan

1. **[Rule 3 - Blocking] The E2E assertion is in `perm-closed-project`, not `contestant-code-registration`.**
   - **Found during:** Task 1's red step.
   - **Issue:** the plan named `contestant-code-registration`, with setup `data-setup-base`. That spec lists the email and code modes only, so the identity provider's entity-type group never renders there. The group renders in E2E only in `perm-closed-project`, under settings that let the provider register both types.
   - **Fix:** a new test is the last of that spec's serial group: "the registration page's radios draw their border, and the provider's panel names each entity type from the catalogue". It opens the panel through the spec's existing `openProviderAskingTheType` and calls the new fixture step `expectRadiosBordered`.
   - **Cost:** `perm-closed-project` depends on every leaf, so its red and green controls each ran the whole suite. The project's count goes from 22 to 23, so the close is judged `--except perm-closed-project=1`.
2. **[Rule 1 - Test design] The red is the border, not the label's text.**
   - The plan's behaviour reads "the party option's label equals the catalogue's new `types.organization`".
   - The rules have every message read from its catalogue, and `expectIdentityProviderPanel` already names each radio by the catalogue's text. Such an assertion passes before and after the reword, so it cannot be shown red.
   - The observable change the new component makes is the border, so the red is `border-top-width` other than `0px` on every radio of the screen. The label stays asserted through `expectIdentityProviderPanel` in the same test.
3. **Restated checks.** Each check was run as written first. Neither the checks nor the verdict script were edited.
   - Task 1's verify: the control stage was restated with the project actually used and the slash, and `yarn -s` as `yarn`.
   - Task 2's verify: the two held controls with the slash, and the close with `--except perm-closed-project=1`.
   - Both logs are kept in `tests/e2e-runs/179.1-unit/` as `179.1-19-t{1,2}-verify.log` and `-verify-restated.log`. The verdicts are in `tests/e2e-runs/179.1-e2e/` as `.verdict-as-written.txt` and `.verdict-restated.txt`.
4. **The Radio file's red took four logs.**
   - A missing component fails at mount with a `TypeError`, so the file was also run against a stub that renders nothing, as plan 18 did.
   - The first stub run showed one case passing vacuously. Every case now asserts how many radios it found before it reads them, and the red was taken again (red-1c with the stub, red-1d without).
5. **The selector's Radio case uses a module mock.** The selector's raw radios already carried `border`, so no DOM difference shows which component drew them. The case wraps the library's `Radio` in a mock that records each render and renders the real one.
6. **`Radio` gained `containerProps`.** The selector's option needs `p-lg` on its label. It is named as `Input`'s outermost-container prop is.
7. **A docs page was updated:** the bank-authentication page of the developers' guide quoted the old option text. It was committed before the held controls and the close.
