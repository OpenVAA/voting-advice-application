## Top 3 Priority Fixes

1. **`WR-12` is present and unproven, and its key sentence arrives after focus moves** ([MARKUP] `ModalContainer.svelte:112-115` calls `showModal()`, which focuses Continue, and only then `onOpen`; `unsavedOnPage` depends on `modalOpen`, so the unsaved sentence and the corrected title are written afterwards, in a later microtask). [PREDICTED] Browsers usually report to assistive technology after that flush, so this probably works, but it is the case to test. Fix: run the reader test in UAT item 1 before calling `WR-12` closed. If the sentence is missed, set `modalOpen` before `showModal`, for example with a callback that runs first.
2. **✕ and Escape still look like staying during a sign-out and are not** (open from the last report; `LogoutButton.svelte:113-116`). The user chooses to stay and loses the edit. Fix: hold both back while `leaving` is up, through a prop on `ModalContainer` and `Modal`.
3. **A keyboard user must cross the whole Admin page to close the message** (N1, new). Focus stays on Log out in the header, and the Alert's buttons are now the last in the document, after the page and the drawer. The Contestant App has had the same order. Fix: after a failure, offer a skip, or move focus to the Alert only if testing with a reader shows the announcement is missed; focus was rightly not moved so far, so this needs a decision.

## Detailed Findings

### New in this diff

- **N1, WARNING, the Admin Alert's Close is last in the document.** [MARKUP] See B3 and priority fix 3. `expectFailureMessagePressable` proves the pointer case with `elementFromPoint`, and no keyboard path is tested. WCAG 2.1.1 is met, since it can be reached, and 2.4.3 is arguable. It is a real cost that the move added for Admin.
- **N2, WARNING, the description is completed after focus.** [MARKUP, with the effect PREDICTED] Priority fix 1.
- **N3, WARNING, a press that does nothing, on a button that looks live.** [MARKUP] `dynamic-components/logoutButton/LogoutButton.svelte:33,36`: `leaving` is a plain `let`, by design, so nothing renders from it. On a slow sign-out a second press is ignored with no sign. On a sign-out that never answers, the button stays dead until reload, where before a press would try again. Once `leaveByFullLoad` runs, its promise never settles, and an aborted load leaves a dead button, as `T-179.1-100` now records for both apps. The in-flight state itself is open, but this consequence is new.
- **N4, WARNING, a failure on the login route shows nothing.** [MARKUP] Both layouts' effects clear the flag whenever the route is the login route, so a failed sign-out pressed from the stale Log out on the login screen is logged only. `179.1-50-SUMMARY.md` calls that button harmless "as no run pressed it", and this is a case where it is not harmless, because a failure goes unreported. It should be rare. Fix: remove the stale button, which also resolves the open item.
- **N5, WARNING, not established: the button now throws outside Admin's context.** [MARKUP] `getAdminContext()` raises a 500 with no context, where the two contexts it replaced exist everywhere. `Banner.svelte:52` mounts it on `appType.current === 'admin'`, and `Banner.svelte:50` has the same shape for the contestant button. [PREDICTED] A client navigation from the Contestant App to the Admin App sets `appType` during the admin layout's init, while the old `Banner` may still exist. It is probably destroyed in the same flush, so I expect no error, but no record covers it. Test: with a contestant session, follow a client link into `/admin`.
