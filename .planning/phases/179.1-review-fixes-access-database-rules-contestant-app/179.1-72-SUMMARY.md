# Phase 179.1 Plan 72: Every server sign-in withdraws the logout count, through one helper Summary

**One server helper, `withdrawLogoutCount`, now expires both cookies of the logout count at every sign-in the server makes, before the session is set. A count left by a closed tab can no longer end a session that was signed in after the old one ended with no Log out. `hooks.server.ts` is untouched.**

## For the operator's reading

- **What a user now meets:**
  - **Whatever ended their session, a sign-in keeps it.** Before this plan the sequence was: the logout modal opens in one tab, and that tab is closed. The session then ends without a Log out: it expires, the browser drops it, or the server ends it elsewhere. The user signs in again. About 40 seconds after the modal opened, the new session was ended with no message and its drafts discarded. Now the sign-in request removes the orphaned count, so the new session stays.
  - This holds for every way to sign in: the Contestant App's email form, the Admin App's form, the registration code, the identity provider's return, and a mailed link confirmed on the confirm page.
- **The server's settled marker is left alone.** If the hook signs a sign-in request out because its count had run out, the helper sees the marker the hook wrote into the same response and leaves it. The page then discards that ended session's drafts as before.
- **What stays unproven** (rule 17):
  - **Unit-tested, not driven:** the identity provider's callback and the confirm page's mailed-link sign-in. No browser run drives them with a count present.
  - **Read only:** the Admin App's sign-in. Its order is read from the source; it has no unit case and no browser run.
  - **Not in a browser:** the removal for a host's own domain and its parents on a real apex host. Every E2E origin is `localhost`.
  - **Not yet built:** the server's sign-outs. Plan 73 adds the same helper there.

## Decisions Made

- **The helper takes the event itself.** Each site calls `withdrawLogoutCount(event)` and then destructures, so no site picks the fields by hand. The email action's committed red case asserts the call's argument is the event.
- **The confirm action withdraws after its field check.** A refused post leads to the login page and "leaves a held session signed in", by its own docblock. Withdrawing there would end the held session's count, which no sign-in replaces. This mirrors the registration-code action, whose offer check comes first. Each of the two has a pinning case, shown red by a placement mutation.
- **The identity provider's callback withdraws first, before any check.** Ruling 4 says "first", and its reasoning holds: the gate sends a browser with a session away from every sign-in screen, so a failed callback has no session for the count to end.
- **The helper also reads the settled marker from the header,** besides `cookies.get`. SvelteKit's `get` returns one value of a duplicated name, while `logoutDeadlineState` sees every value. Both say `'settled'` in every case the plan names, and the header read adds the case of the marker beside an id (a unit case).
- **Ruling 2, read again:** `node_modules/@sveltejs/kit/src/runtime/server/cookie.js` at 2.70.3. `get` looks first among the cookies set in this request that match the URL's host and path, answers `undefined` for one set with `maxAge: 0`, and then reads the header. `delete` is `set` with `maxAge: 0`. There is no difference from the plan.
- **Ruling 3's list, derived at run time:** five sites, no site added or removed (`tests/e2e-runs/179.1-unit/179.1-72-sites.txt`). The data writer's browser `_login` has no caller: `git grep -n -E "\.login\(" -- apps/frontend/src ':!*.test.ts'` has no hit, and `UniversalDataWriter.login` is never called. It is not a server request and no sign-in screen of either app calls it.
- **The browser test's sign-in lands on the settings page.** The gate carries `redirectTo` to the email form, so the sign-in returns to the page the link asked for. The proving link therefore goes to the app's root, whose `(protected)/+page.server.ts` makes the request, and `expectStillSignedIn` follows.
- **Baseline:** the plan names `179.1-71-close` for both the full control and the close, and that is the latest green close (700/700 on `12257e980`), so one baseline serves.
