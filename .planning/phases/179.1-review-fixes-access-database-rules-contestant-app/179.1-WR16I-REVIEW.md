## Warnings

### WR-01: Every sign-out the document did not start is reported as "logged out in another tab or window", including a session the auth client dropped by itself

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:617-618`, `apps/frontend/src/lib/contexts/admin/adminContext.svelte.ts:183-195`, `apps/frontend/src/lib/api/adapters/supabase/dataWriter/supabaseDataWriter.ts:494`

**Issue:** `_onSignOut` reports `'elsewhere'` for every `SIGNED_OUT` event while `signOutsRunningHere === 0`. This round makes both contexts turn `'elsewhere'` into `errorMessage=loggedOutElsewhere`, and the login screen then says "You have been logged out in another tab or window."

But `@supabase/auth-js` also emits `SIGNED_OUT` from `_removeSession` (`GoTrueClient.js:4418-4435`) when no other tab is involved:

- After a proactive refresh is rejected with an expired access token (`:4300-4314`).
- When `getUser()` finds the session gone (`:2714-2727`). The browser calls `getUser()` in `_getBasicUserData` (`supabaseDataWriter.ts:616`), which the contestant and admin loads run on client navigations.
- When the stored session is invalid (`:2526`, `:4119`).

Causes that reach these paths include:

- an auth-service session time-box or inactivity timeout on a hosted project, which the auth guide names as the outer bound;
- a revoked refresh token, a deleted user, or reuse detection after concurrent refreshes;
- a local sign-out by a server request whose `Set-Cookie` never reached this browser.

In each case the user, who did nothing in any other tab, reads a cause that is false. They may even look for another device or window holding their account. This round's tests (`contestantContext.svelte.test.ts`, `adminContext.svelte.test.ts`) drive only the `'elsewhere'` origin, so they cannot see the conflation.

**Fix:** Name the reason only when the cause is known. The tab that logs out announces it before its request, and the other tabs give `loggedOutElsewhere` only when they heard that announcement shortly before `SIGNED_OUT`. Any other `SIGNED_OUT` goes to the login page with a neutral reason, for example a new `loggedOut` sentence ("You have been logged out.") or no `errorMessage`:

```ts
// authContext.logout
const LOGOUT_CHANNEL = 'openvaa-logout';
withdrawAnyCount();
new BroadcastChannel(LOGOUT_CHANNEL).postMessage('logout');
await prepareDataWriter().logout();

// the follower: remember the time of the last announcement
channel.onmessage = () => (lastAnnouncedLogout = Date.now());
const reason = Date.now() - lastAnnouncedLogout < 5_000 ? 'loggedOutElsewhere' : undefined;
```

Add a unit case for each context: a `SIGNED_OUT` with no announcement leaves to the login route without `loggedOutElsewhere`.

### WR-02: Two server paths withdraw the count before they know the session has ended, so a failure keeps a session the user asked to end

**File:** `apps/frontend/src/lib/server/contestant/signOutToLogin.ts:27-34`, `apps/frontend/src/routes/api/oidc/callback/+server.ts:50-51`, `apps/frontend/src/hooks.server.ts:82`

**Issue:** The previous round's fix was to end a count when the session it was meant to end is gone. Two of the new call sites withdraw unconditionally and first:

- **`signOutToLogin`** calls `withdrawLogoutCount(event)` before `signOut`. On the path where the sign-out fails and `isSessionGone` answers that a session is left, it ends in `error(503)`. The count's cookies are still expired in that response.

  Traced sequence: a user presses Log out on an entity page, the modal opens and writes `pending=X` and `deadline=X`, and the tab is closed. Within the window, another tab's `(protected)` load fails to read the user data while the auth service is failing, and calls `signOutToLogin`. The sign-out fails, the session is live, and the response is a 503 that removes both cookies. When the deadline passes, nothing is left to sign out, so the closed-tab sign-out the user asked for never happens.

  The hook's docblock promises the opposite for a failed sign-out: "the request goes through with its session, and the next request tries again" (`hooks.server.ts:82`). That promise no longer holds once any request in the window reaches `signOutToLogin`.
- **The OIDC callback** withdraws on its first line, before it checks `error`, `code`, `state` or the PKCE verifier (`:51`, then `:62-70` and onward). `/api/oidc/callback` is not one of the gate's entry routes, so a browser with a live session reaches it, from a stale tab, an IdP cancel or a link. Each early failure redirects to the error screen with the count withdrawn and the session untouched. `logoutCount.ts`'s own docblock says the withdrawal is made "as every sign-in the server makes does before it sets the session". These paths set no session.

`/api/auth/logout` also withdraws before its sign-out. That one is deliberate and documented: a failed Log out is shown to the user, and the server must not repeat it later. It is not part of this finding.

**Fix:** Withdraw once the outcome is known, in the same response:

```ts
// signOutToLogin
const failure = await locals.supabase.auth.signOut({ scope: 'local' }).then(...);
if (failure) {
  log.error(...);
  if (!(await isSessionGone(locals.supabase))) error(503, { message: t('error.default') });
}
withdrawLogoutCount(event);
redirect(307, buildRoute({ route: 'ContestantAppLogin', locale, errorMessage: code }));
```

In the callback, move `withdrawLogoutCount(event)` to right after `verifyOtp` succeeds (`:202`), where the session is set. Add a unit case to each: the 503 path, and a callback with `error=access_denied`, both leave the count's cookies in place.

### IN-01: The top bar still uses `overImgBgColor` though it is no longer drawn over the image

**File:** `apps/frontend/src/lib/layouts/main/Header.svelte:45-48`, `:103-107`, `packages/app-shared/src/settings/dynamicSettings.type.ts:78-81`, `:91-94`

**Issue:** The header image is now painted in its own element below the top bar. The top bar still switches to `headerStyle.*.overImgBgColor` whenever `imageSrc` is set. That setting's documented meaning, "Background color of the header when it's over an image", no longer matches anything. With the default `'transparent'`, nothing visible changes. A deployment that set it for contrast over the image, such as a translucent white or black, now gets that color over the plain page on the voter home and both login pages.

**Fix:** There are two options:

- Use `mode.bgColor` for the top bar, and deprecate `overImgBgColor`.
- Keep the switch, and change the type's docblock and the settings documentation to say what the colour now does.

### IN-02: The guard against untranslated catalogues catches only byte-identical files

**File:** `apps/frontend/src/lib/i18n/tests/translations.test.ts:112-126`

**Issue:** The guard compares whole files byte for byte. It still passes in these cases:

- the copy differs from `en` by a reformat or a trailing newline;
- one key of the copy is translated and the rest stay English;
- a later edit adds an English string to a translated file.

That last case is the most likely regression. The guard cannot see any of them.

**Fix:** Parse both files and compare each string value. Fail a file when every value, or more than a set share of them, equals `en`'s. Keep an allowlist of strings that are legitimately the same, such as fr `adminApp.jobs.messages` "Messages" and lb `adminApp.login.appSubtitle` "Administration".

### IN-03: `signOutToLogin` takes the same request twice, as `locals` and as a slice of the event

**File:** `apps/frontend/src/lib/server/contestant/signOutToLogin.ts:21-26`

**Issue:** The function takes `locals` and, as its new fourth parameter, `event: Pick<RequestEvent, 'cookies' | 'request' | 'url'>`. Both have to come from one request: the sign-out runs on `locals.supabase`, and the withdrawal writes to `event.cookies`. Nothing stops a caller from passing a mismatched pair. The only caller passes `locals` and `event` from the same `load(event)`.

**Fix:** Take one parameter, `event: Pick<RequestEvent, 'cookies' | 'request' | 'url' | 'locals'>`, and read `event.locals.supabase` from it.
