## Notes for the operator

- **Does a sign-out that fails after a yes leave the user believing they are signed out? In one case, yes.** The edit is
  gone in all three cases and no message is shown: `AuthContextProvider.logout` logs the failure and resolves, so
  `#logout` goes on to the navigation and `#reset`. T-179.1-92 and its deferred entry describe only the first case.

  | What failed | Cookies | Where the user ends | Actually signed out? | Screen tells the truth? |
  |---|---|---|---|---|
  | The endpoint's answer, with the auth service up | kept | the home, with Log out in the header | no | yes, though nothing says the sign-out failed |
  | The auth service, with the access token valid | cleared, despite the 502 | the login screen | in this browser yes; the session is not revoked on the auth service | yes |
  | The auth service, with the access token expired | kept | the login screen, with no Log out | **no: the same cookies read as signed in once the service is back** | **no** |

  - **The third case contradicts the acceptance's reason**, "no screen claims a sign-out". `safeGetSession` answers null
    during the outage, so `appGateHandle` does not redirect and `routes/contestant/+layout.server.ts` publishes no
    session. On a shared computer, the next person to open the app after the service recovers is signed in as this user.
  - **The window is narrow.** It needs an auth outage while the access token is expired or within auth-js's 90-second
    margin. Only the expired state was measured (60 seconds past expiry). The behaviour predates plan 41, whose addition
    is that the user had just agreed.
  - **How far this is established.** The cookie and gate results of the last two rows were measured, for both a refused
    connection and a 503, with `/private/tmp/claude-501/-Users-kallejarvenpaa-Desktop-OpenVAA-voting-advice-application-gsd/6e102dd6-bb1a-4928-a2ff-4d0b4786b4bc/scratchpad/failed-signout.mjs`
    against `@supabase/ssr` 0.12.7, auth-js 2.117.2 and the real `safeGetSession`. The first row, and the screens in all
    three, come from reading the hook and SvelteKit 2.70.3. No browser run makes the sign-out fail.
  - **Two comments are wrong for the second row:** `routes/api/auth/logout/+server.ts:13` ("removes no session") and
    `supabaseDataWriter.ts:457` ("stays signed in on both sides"). `_signOut` in auth-js removes the session before it
    returns the error from the auth service. The test at `server.test.ts:35` stubs `signOut`, so it cannot see this.
  - **For the operator to decide:** accept T-179.1-92 again on these facts, or schedule the deferred entry's fix, where
    `logout` reports the failure to `#logout`, which then skips the reset and says so. Telling the user covers all three
    cases; it does not by itself clear the cookies of the third.
- **Module-level guard state cannot leak across requests on the server.** `contestantContext.svelte.ts` imports the
  module, so the server has a copy, but nothing on the server writes to it.
  - `guards` is written only by `registerNavigationGuard`, whose one non-test caller is `onMount`, which the server never
    runs.
  - `leavingUnasked` is written only by `leaveUnasked`, whose one non-test caller is `#logout`. That is reached only from
    browser events: `LogoutButton.svelte:99,111,141`, and `onclick` at `IdentityProviderGate.svelte:394`,
    `TermsOfUseGate.svelte:105` and `SetPasswordGate.svelte:148`.
  - A guard holds two closures and no user data. This is established by reading; no test renders the module on the
    server.
- **T-179.1-88:** the declared mitigation holds, with three limits, all read and not run.
  - The full load is proven only by a unit case with a stubbed `location`.
  - Plan 41's summary flags a second native prompt as possible on that path, because the flag clears as soon as
    `location.assign` returns. Only the nomination details page can still have an active guard then: its guard reads
    `cards`, which `#reset` does not touch.
  - That summary says no known route reaches this path, but one can, depending on timing. A second press of Log out during
    the first press's sign-out can supersede the first `goto`, which then resolves without moving. The later `goto` still completes, so the user
    ends on the login page. By the same reading, `goto` rejects only for another origin, so the path where a signed-out
    page stays after a rejection is not reachable with this same-origin route.
