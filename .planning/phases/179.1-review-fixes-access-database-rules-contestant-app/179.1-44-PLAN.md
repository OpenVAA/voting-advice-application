## Rulings carried by this plan

1. **The operator's ruling 1, in their words first:** "let's fix this". On Log out with unsaved edits, the app's `TimedModal` opens instead of the native prompt, says the edits are unsaved and will be lost, and counts down from `logoutModalTimer`, with a way to stay and a way to log out. Stay ends nothing and keeps the edits. Log out or the count's end signs out and discards the edits, including the persisted drafts, so nothing is left on a shared computer.
   - **This overturns plan 41's rulings 2 and 3, and its truth "ends the session and discards the edits only if the user agrees".** The truth now reads: when the sign-out succeeds, the session ends and the edits are discarded after the user presses the modal's Log out, or after its count ends with no answer; a Stay ends nothing. Truth 6 of `179.1-VERIFICATION.md` is to be read in this form when the phase is verified again.
   - **`T-179.1-89` is retired.** It accepted that a user who walked away stayed signed in, and that state is gone when the sign-out succeeds. The opposite cost is registered as `T-179.1-98`.
   - **The limit of this ruling, which the operator reads first.** "Nothing is left on a shared computer" holds when the sign-out succeeds. If it fails at the count's end, the operator's ruling 2 keeps the edits, so a user who walked away stays signed in, with their draft in storage and the message on the screen. It is registered as `T-179.1-104` in plan 45, opens the operator's reading in the summaries of plans 45 and 46, and is on the UAT list. In this plan `#authLogout` still resolves on a failure, so plan 45 is where this state begins.
   - Plans 41 and 42 and their summaries are not edited. A verifier reads their overturned statements through this ruling, including plan 41's artifact that `#logout` calls the question function, and its truth that no count runs over an unsaved edit.

2. **`logout()` no longer asks at all, and the question function of plan 41 retires.** With the modal in the button, a native question in `#logout` would have no reachable caller: `LogoutButton` is the only caller that can be under a guard, and the three gates render in place of the page, as plan 41's ruling 7 read. Keeping it behind an option would leave a code path no browser reaches and a second way to be asked. So `logout()` means that the caller has what it needs from the user. The registry keeps `hasActiveNavigationGuard`, `leaveUnasked` and `isLeavingUnasked`, and gains `keepGuardedEdits` and `discardGuardedEdits`. A guard offers `isActive`, `keep` and `discard`. `PreventNavigation`'s native question stays local to its `beforeNavigate`, which is ruling 6.

3. **The sign-out comes before `onConfirm`.** The target says `onConfirm` must still run on the discard path, and ruling 2 of the operator says that on a failed sign-out the edits stay. `handleNavigationConfirm` on the question page clears `heldOpenAnswer` and calls `userData.resetUnsaved()`, and the profile's does the second, so running it before the sign-out would lose the edits on a failure. The order is therefore: sign out, `discardGuardedEdits`, leave, reset. In this plan `#authLogout` still resolves on a failure, because that changes in plan 45; the order is set here so that plan 45 changes one thing. `onConfirm` running after the sign-out is new; it does not change what a yes on an ordinary link does.

4. **What the modal says.** Read from the catalogue and the code:
   - The existing title, `contestantApp.logoutModal.title`, is "Some of Your Data Is Still Missing", which is false when nothing is missing. So that title appears only over a counted task with no unsaved edit, and every other state uses `common.logout`.
   - The existing body falls to `itemsLeft` when the lists are empty, which would read "0 items of basic info and 0 opinions". So the count's sentences render only while a counted task is incomplete, the condition `triggerLogout` already held, now a `$derived` named `countedTaskLeft`.
   - The counts read saved answers (`savedEntityData`), not the draft, so an unsaved answer does not change a count, and "there is still one opinion to fill" stays true beside "your changes will be lost".
   - So every combination is stated. The ingress, "Are you sure you want to log out? You will be automatically logged out after N seconds", is true in all four, and Continue's label, "Continue entering data", serves as Stay in all four:

     | Guard active | Counted task left | Title | Body |
     |---|---|---|---|
     | yes | no | `common.logout` | `common.logoutUnsavedChanges`, the ingress |
     | yes | yes | `common.logout` | `common.logoutUnsavedChanges`, the count's sentences, the ingress |
     | no | yes | `contestantApp.logoutModal.title` | the count's sentences, the ingress: as it is today |
     | no | no | `common.logout` | the ingress alone |

     The last row is reached only when the modal is open and what opened it has gone: a guard going inactive during the count, or a counted task settling. The modal stays open, because the user pressed Log out and the count still runs, and what it says stays true.
   - The unsaved sentence is read live: `$derived(modalOpen && hasActiveNavigationGuard())`, which needs `modalOpen` as `$state`. A guard's own state reaches the derived through the reactive reads inside its `isActive()`. **A guard that registers after the modal opened must reach it too, and a plain `Set` would not tell it, so the registry's `guards` becomes a `SvelteSet` from `svelte/reactivity`.** That works in a plain `.ts` file and needs no rune. Its server export is the plain `Set` (read in `svelte/src/reactivity/index-server.js`), and registration stays in `onMount`, so the server's copy still holds no guard. A guard that becomes active behind the modal, by another tab's storage or a late-settling field, therefore shows its sentence before the count ends. The count's end then discards, as ruling 1 says, and raises nothing.

5. **Stay is every close that is not a logout's or a navigation's.** `ModalContainer` closes by the ✕ and by Escape through the same `onClose` as Continue, so all three run `keepGuardedEdits`, and `onCancel` runs once. The modal's Log out, the count's end and `afterNavigate`'s close do not run it. `TimedModal` calls `onTimeout` and then closes by itself, so the flag the handler sets is already up when that close arrives.
   - **Stay is not offered while it cannot keep anything.** Once the modal's Log out is pressed, a sign-out is in flight, and on a hung `POST` the modal stays open until the count's end. So `leaving` is `$state`, Continue is `disabled={leaving}`, and the modal's Log out takes `loading={leaving}`, whose text is `Button`'s existing `common.loading`, so that the disabled Continue has a visible reason.
   - **The ✕ and Escape stay live in that window, and the plan says so.** They close the dialog and do not stop the sign-out already running, so a user who pressed one may believe they stayed, yet on a successful sign-out they are signed out and the edit is gone. Neither says it keeps anything: the ✕ is named `common.closeDialog`. Holding them back needs a prop through `ModalContainer` and `Modal`, which are outside this plan's file line, for a window that lasts a round trip unless the `POST` hangs. Plan 46 records it in `deferred-items.md` and on the UAT list.

6. **Ordinary link navigation keeps the native prompt.** `beforeNavigate` behaves as it does today: asks, runs `onConfirm` or `onCancel`, cancels on a refusal. `the prompt: switching from the editor with an unsaved edit raises one native confirm, and Cancel keeps the edit` is unchanged and pins it.

7. **WR-05 to WR-08 are included on the orchestrator's proposal.** The operator has not objected and has not expressly approved. They may overrule this before execution. The property: after the modal's Log out or the count's end, on a successful sign-out, the browser leaves and the store is reset only then, with no second prompt, on every path.
   - **WR-06.** `#logout` holds one running promise in `#loggingOut`, and overlapping calls return it. The button also ignores a press while it is leaving, so no modal opens over a sign-out.
   - **The stand-down is narrower than the review's sketch.** `leaveUnasked` now starts after the sign-out has succeeded, not before it. A hung `POST` then leaves the guards up instead of down, and a failure in plan 45 never has to take a flag back down. This answers the last sentence of WR-06.
   - **WR-07.** A `goto` that rejects is logged and treated as not having moved, whatever `page.url` then reads, because a rejection can come after the address changed (`goto` rejects on a throw while rendering).    - **WR-05.** The full load is `leaveByFullLoad(address)` in the registry: it calls `location.assign` and returns a promise that never settles, so `leaveUnasked`'s `finally` never runs and the flag stays up until the document has gone. `#reset` runs before it, as the drafts must go before the document does.
