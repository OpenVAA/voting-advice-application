**2. Harness fix: the JWKS server speaks HTTP/1.1 keep-alive (operator decision 2)**
- **Found during:** Task 1 step 4. The baseline E2E `179.1-01-baseline-r2` (head `8eb139b6b`) was red: 1 failed and 23 did not run, because `identity-callback` hit `ERR_JWKS_TIMEOUT` in the contestant-identity-provider organization flow.
- **Diagnosis (measured):**
  - The wrapper served the JWKS document with `python3 -m http.server`. That server speaks HTTP/1.0 and closes each connection itself.
  - Docker Desktop's network stack (gvisor) keeps a TIME_WAIT of about 60 s for a container-to-`host.docker.internal` connection that the host side closed first. A new SYN that reuses that 4-tuple within the window stalls until the TIME_WAIT expires.
  - The container kernel re-randomises its port base about every 10 s, so it sometimes revisits such a port. jose then makes one 5 s fetch, and it fails.
  - A/B, 5 000 connections each: the HTTP/1.0 server had 26 failures, all of them port reuses within 60 s; a keep-alive HTTP/1.1 server had 0.
  - A real edge-runtime fetch: 12 failures in 4 000 against the HTTP/1.0 server, each a 5.00 s TimeoutError, the same signature as r2. Against the keep-alive server, 0 in 4 000, all over one pooled connection.
  - DNS stalls were ruled out (0 slow lookups in 35 000 Deno-faithful lookups), as were host sleep (no `pmset` entry) and event-loop starvation (the timer fired on time).
  - The r2 run itself is attributed to this cause by signature and rate only. That attribution is unconfirmed: no per-connection port record exists for the run.
- **Fix:** in `prepare_identity_provider`, `python3 -m http.server …` is replaced by an inline Python 3.9 `ThreadingHTTPServer` with a `SimpleHTTPRequestHandler` subclass whose `protocol_version` is `HTTP/1.1`.
  - It keeps the dual-stack all-interfaces bind, request logging into `idp-jwks-server.log`, the readiness curl on `127.0.0.1` and the process-group stop.
  - The comment describes the current behaviour only.
- **Verification:**
  - `bash -n` passes and `yarn assert:comment-hygiene` reports 0 violations.
  - The server was started on spare port 8793 and checked: `lsof` showed `*:8793` IPv6 LISTEN. Two curl requests over one connection gave `HTTP/1.1 200`, `Content-Length` and "Re-using existing connection". `[::1]` and the readiness-style probe both answered 200, every request left a log line, and after the stop nothing was listening.
  - In the run, 58 `GET /jwks HTTP/1.1 200` lines and no other lines.
  - The baseline `179.1-01-baseline-r3` on this commit is green.
- **Scope:** `tests/scripts/` is not on the verdict's `scope` refusal list, so no driver or check was bent.
