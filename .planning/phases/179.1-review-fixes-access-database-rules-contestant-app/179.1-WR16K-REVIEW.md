### WR-02: An `end` from any tab closes any other tab's outstanding `start`, so overlapping Log outs bring back the slow-Log-out defect the pair was built to fix

**File:** `apps/frontend/src/lib/auth/logoutAnnouncement.ts:62-69` (and `92-97`)
**Issue:** `outstandingStartAt` is a single slot, and the messages carry no sender. Trace with three tabs on one session:
1. Tab A presses Log out and posts `start` at t=0. Its requests are slow.
2. Tab B presses Log out at t≈0.2 s. B's logout endpoint answers non-ok quickly, so `_logout` throws before the client's `signOut`, and B's `finally` posts `end` at t≈1 s.
3. Tab C's `onmessage` sets `lastEndAt = 1 s` and clears `outstandingStartAt`, although A's `start` is still in flight.
4. A's sign-out completes at t≈8 s, and C's client reports `SIGNED_OUT`. `heardLogoutAnnouncement()` finds no outstanding start and an `end` 7 s old, more than `LOGOUT_ANNOUNCEMENT_WINDOW_MS`, and returns `false`.

So C goes to the login page with no reason. That is exactly G-179.1-WR16J-1's slow-Log-out case, which ruling A1 and the "still counts a start 8 000 ms later" unit case were meant to close. The reverse also holds: a second tab's `start` overwrites the first one's time. Two overlapping Log outs are not common, but they are reachable, for example a user pressing Log out in two tabs during a flaky backend. The unit suite has no multi-sender case, and the module's docblock ("a sign-out counts as another tab's while a `start` is outstanding") states a guarantee the single slot does not keep.
**Fix:** Key the pair by an id per document, kept in a closed message format so the strict validation stays, and count the window while any start is outstanding:
```ts
const DOCUMENT_ID = crypto.randomUUID();
// post: channel.postMessage(`${kind}:${DOCUMENT_ID}`)
const outstanding = new Map<string, number>(); // sender id -> start time
channel.onmessage = ({ data }: MessageEvent) => {
  if (typeof data !== 'string') return;
  const match = /^(start|end):([0-9a-f-]{36})$/.exec(data);
  if (!match) return;
  const [, kind, sender] = match;
  if (kind === 'start') outstanding.set(sender, now());
  else { outstanding.delete(sender); lastEndAt = now(); }
};
// heard: [...outstanding.values()].some((at) => within(at, t, LOGOUT_IN_FLIGHT_CAP_MS)) || within(lastEndAt, t, LOGOUT_ANNOUNCEMENT_WINDOW_MS)
```
Add a unit case: two announcing documents, the second posting `start` then `end` while the first's `start` is outstanding, with the listener still counting at 8 000 ms. If the single slot is kept on purpose, restate the docblock and `AR-179.1-19` to say that an `end` from any tab closes the window.

## Info

### IN-01: The window is measured on the wall clock, so a clock correction during a Log out silently drops the other-tab sentence

**File:** `apps/frontend/src/lib/auth/logoutAnnouncement.ts:64,66,93,105-109`
**Issue:** `Date.now()` moves when the OS corrects the clock. A backward NTP step during an in-flight Log out makes `elapsed < 0`, which `within` deliberately counts as neither. A forward jump of more than 30 s expires the start early. Both times are recorded and compared inside one document, which is the case a monotonic clock is for. The clock-set-back branch and its unit case then guard a state that a monotonic clock cannot reach.
**Fix:** Use `performance.now()` for `outstandingStartAt`, `lastEndAt` and `now`. The `elapsed >= 0` check can then go, and the "clock set back" unit case becomes moot. Tests can fake `performance` with `vi.useFakeTimers({ toFake: ['performance'] })`.

### IN-02: The Admin App's announcement is tested only for a sign-out that works in the browser

**File:** `apps/frontend/src/routes/admin/(protected)/layout.test.ts:326-343`; `apps/frontend/src/routes/admin/(protected)/+layout.ts:65-73`
**Issue:** The docblock (`+layout.ts:5,60`) promises `end` "once it has settled, worked or failed" and "on the server nothing is announced". The one new case covers neither. `end` sits after a `.then(ok, fail)`, not in a `finally`, so two mutations would go unnoticed: moving `announceLogout('end')` into the success handler, or dropping either `browser` guard. The file's header item 7 claims less than the code does, so the gap is not visible from the header either.

### IN-03: The i18n tests now hold three variant-message detectors that disagree

**File:** `apps/frontend/src/lib/i18n/tests/translations.test.ts:30-35` vs `:665-673`; `apps/frontend/src/lib/i18n/tests/compiledMessages.test.ts:50`
**Issue:** Plan 86 made `isVariantMessage` require `match` together with `declarations` or `selectors`. In the same file, `flattenMessageKeys` still treats any object holding `declarations`, `selectors` **or** `match` as a leaf, "as in the `TranslationKey` generator", and so does `compiledMessages.test.ts:50`. A namespace with a key named `match` would therefore be a branch for the per-value comparison and a single leaf for the key-parity tests. A key missing under such a namespace in one locale would then pass the parity test that exists to catch it. No such namespace exists today: the WR16J review counted 154 variant messages and none of that shape. So this is latent, but the fix for IN-04 of WR16J is only half done.
**Fix:** Move one `isVariantMessage` predicate into a small shared test helper, and use it in `flattenMessageKeys` and `compiledMessages.test.ts`. If the generator really keeps the loose rule, the test should mirror the generator, and the stricter predicate's unit case should also assert the key-parity walk.

### IN-04: `describeRemovalAt` says its copies were "planted for each" domain, but jsdom keeps fewer, and the check only asks for more than zero

**File:** `apps/frontend/src/lib/auth/logoutDeadline.testUtils.ts:124-129` (also `:56-62`)
**Issue:** jsdom's cookie jar keys a host-only cookie and a `Domain=<host>` cookie by the same (name, domain, path). Planting both keeps one. I measured this with jsdom: at `https://example.org/`, 2 planted copies leave 1 in the jar; at `https://app.example.org/`, 3 leave 2. The precondition `toBeGreaterThan(0)` hides this. As a result, the jar half of `expectEveryCopyExpired` ("leaves no copy") cannot tell a missing `Domain=<host>` expiry from a present one. Only the write-list assertion does. Real browsers store the two as distinct cookies (the domain cookie is stored with a leading dot). The carried-over test titles therefore claim more than the jar half proves. The plan's recorded negative control turned the test red through the write list, so the gate still works. This weakness was moved from the two host files, not introduced by the move. Separately, `forEachDomain` with an empty `domains` array renders `", and for undefined"`. The docblock says a domain-name host always has at least one domain, but nothing enforces it.
**Fix:** Assert the jar count jsdom actually yields, so the precondition is explicit: `expect(cookieValues(document.cookie, name)).toHaveLength(domains.length)`. Note in the docblock that the jar merges the host-only and `Domain=<host>` copies, so the write list is the evidence for that expiry. Throw early on an empty `domains`.

### IN-05: The three sign-in docblocks say "a refused sign-in leaves a session the request already held as it was", which is false for the 403 and 500 refusals

**File:** `apps/frontend/src/routes/admin/login/+page.server.ts:8`; `apps/frontend/src/routes/contestant/login/email/+page.server.ts:10`; `apps/frontend/src/routes/contestant/register/sign-in/+page.server.ts:14`
**Issue:** `grantNotAllowed` (403) and `noSession` (500) are both answered after the sign-in has succeeded on the request's client (`sessionAdmission.ts:41-52`). By then any session the request held has been replaced. On 403 the new session is signed out locally. On 500 the new session is left in the response's cookies with the kept count beside it, and the hook ends it at the next request once the count has run out. The behaviour is fail-closed and acceptable. The sentence holds only for the `invalidCredentials` refusal and for a refusal during an outage, which is the diagnosed case. A reader who relies on it would misjudge the 500 path.
**Fix:** Restate the sentence: "A refusal keeps the count. Wrong credentials leave any held session as it was. A refusal after the sign-in (no session read back, or no allowed grant) leaves either no session or the new one, and the request hook ends a session left with a run-out count at the browser's next request."

### IN-06: The confirm action repeats `signOutToLogin`'s failure-reading block and imports the adapter module, though `DataWriter.isSessionGone` exists

**File:** `apps/frontend/src/routes/auth/confirm/+page.server.ts:21,56-66`; `apps/frontend/src/lib/server/contestant/signOutToLogin.ts:29-35`
**Issue:** The sequence `signOut({ scope: 'local' }).then(a => a.error, e => e)`, then log, then `isSessionGone(locals.supabase)`, then `error(503, t('error.default'))` is now written twice. The checklist forbids repeated code; plan 89 records this as a residue held by `PROH-179.1-67`. The action also imports `$lib/api/adapters/supabase/sessionGone`, a path the lint rule `^\$lib/(supabase|api/adapters)` bans. Only the file-wide allowlist entry silences it, and that entry's annotation justifies the `signOut` call alone. `createDataWriter({ fetch, locals }).isSessionGone()` reaches the same function through the interface, and the admin layout already uses that form.
**Fix:** When `PROH-179.1-67` lifts, extract a `signOutOrFail503(locals)` server helper that both sites call. Meanwhile, use `createDataWriter({ fetch, locals }).isSessionGone()` here, or extend the allowlist annotation to name the adapter import as well.
