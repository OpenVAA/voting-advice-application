## Rulings carried by this plan

1. **The host.** Each new file sets its jsdom address by vitest's per-file `@vitest-environment-options` with a `url`: `logoutDeadline.apexHost.test.ts` at `https://example.org/`, `logoutDeadline.subdomainHost.test.ts` at `https://app.example.org/`. A per-file option is the mechanism the ruling names first, and it moves the document itself, so jsdom's cookie jar applies a browser's domain rules. A stubbed `location` would leave the jar on `localhost`, where it refuses a `Domain=example.org` cookie. Each file's first case asserts `location.origin`, so a file whose option is not honoured fails instead of passing on `localhost`. Measured at planning with a probe file that is gone: vitest 5.0.2 honours the option (`location.origin` read `https://app.example.org`). At that address jsdom accepted a cookie planted with `Domain=example.org`, and expiries with the same attributes removed it. If this vitest does not honour the option when the plan runs, the executor stops and reports, with the first case's output. It does not fall back to a stub on its own.
2. **What is run.** The page's removal through its two exported callers that expire every copy:
   - the modal's Continue, `writeLogoutDeadline(30)` then `clearLogoutDeadline()` in the same document;
   - a Log out's `withdrawAnyCount()`, after copies of both names are planted, host-only and with `Domain=` each domain of `removalDomainsOf(location.hostname)`, as another host of the site would write them.

   For each, the cases assert the written strings: per name, one host-only expiry and one `Domain=<d>` expiry for each `d` that `removalDomainsOf` names (`example.org`; then `app.example.org` and `example.org`). Every expiry has `Max-Age=0`, `Path=/`, `SameSite=Lax` and `Secure`. After each removal, `document.cookie` holds no copy of either name. jsdom's jar keys a cookie by name, domain and path, as RFC 6265 does. A copy planted with `Domain=` the host itself therefore replaces the host-only copy there, where a browser that marks domain cookies apart keeps both. Measured at planning: at `app.example.org`, three plants of one name left two values. So the jar is read only for "no copy left". The written strings are what show one expiry per domain. The settled marker's branch is not this gap's and is not driven here.
3. **The helpers.** `parseWritten` and `recordCookieWrites` move from `logoutDeadline.test.ts` into `apps/frontend/src/lib/auth/logoutDeadline.testUtils.ts`, exported and TSDoc'd, after the precedent of `routes/contestant/(protected)/loadTracking.testUtils.ts`; the three files import them. `logoutDeadline.test.ts` changes in its imports and in nothing else, and its cases are unchanged.
4. **The red.** The cases test what the tree already does, so their red is a mutation (execution rules § *The unit cycle*): with the line `for (const domain of removalDomainsOf(hostname)) setCookie(name, '', 0, domain);` removed from `expireEveryCopy`, both new files are red. `logoutDeadline.test.ts` run alone under the same mutation stays green, which records the blind spot the gap names.

The publishers' guide's line on `overImgBgColor` in § `headerStyle` says the same. `bgColor`, `imgSize` and `imgPosition` and the developers' guide's settings table (which states a type, not a meaning) stay as they are. No behaviour changes (`PROH-179.1-58`).
