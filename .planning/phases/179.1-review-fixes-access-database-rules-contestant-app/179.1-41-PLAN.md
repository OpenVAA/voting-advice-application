## Rulings carried by this plan

1. **The question moves in front of the sign-out, through a registry of guards.** Navigating first is impossible: `appGateHandle` in `hooks.server.ts` redirects a signed-in caller away from the login page, so the sign-out has to come before that navigation. A new logout route would be a GET that signs out, or a page that flashes. So `PreventNavigation` registers its question with `navigationGuards.ts`, `#logout` asks through it, and the navigation that follows runs with the guards stood down. Every caller of `logout()` is covered at one place. Only `PreventNavigation` cancels a navigation (`git grep -n 'beforeNavigate(' -- apps/frontend/src ':!*.test.ts'` at planning: the guard, `Video`, the layout context and the root layout, and the other three cancel nothing). A module rather than a context member: a base component reads no context but the component's, and `getComponentContext` fakes across the suite would each need the member. Registration is in `onMount`, which the server never runs, so the server's copy of the module holds no guard and nothing of one visitor reaches another.

2. **The count, when the user has walked away (orchestrator's requirement to decide).** With an unsaved edit on the page the modal does not open and no count starts: the press raises the native question and waits. A user who presses Log out and walks away stays signed in, with the edit, behind that question, until someone answers it. The gap's truth decides this: the session ends and the edit is discarded only if the user agrees, and a count nobody is watching is not agreement. The cost is real and is accepted as `T-179.1-89`: on a shared computer the session stays open. It is bounded by what the user was told: the modal's sentence that they will be logged out automatically is never shown in this state, and the prompt that is shown says the page still holds their changes. If a guard becomes active while a count is running, which only a change from another tab's storage or a late-settling field could do behind a modal dialog, the count's end goes through the same `#logout` and asks; it never discards. **This plan's summary opens `## For the operator's reading` with this ruling (Task 3), plan 42's does the same, and plan 42's verify reads it there.**

3. **For a user who is present, the native question takes the modal's place.** They are asked once, not twice, and with an edit at stake a single question is the right one. They do not see how many questions are left. Showing the modal after a yes would be a second "are you sure", and its Continue would then have to undo an agreement. Stated in the summary as a visible change.

4. **Once the user has agreed, the browser always leaves.** `#logout` compares `page.url.href` before and after its navigation; if the navigation did not move the browser it replaces the page with a full load of the login page. That is the only state in which a signed-out page could go on reading as signed in, and with the guards stood down nothing known reaches it, but CR-01 is exactly that state and the requirement is that a reset follows only a browser that left. `#reset` runs after this, and not at all if the navigation rejects.

5. **`onConfirm` and `onCancel` keep their meaning.** One `ask` function in `PreventNavigation` serves the navigation path and the registry, so agreeing runs `onConfirm` and refusing runs `onCancel` on either path. A navigation made under `leaveUnasked` asks nothing and runs neither, as the question has been answered. `#reset` does more than `resetUnsaved`, and the question page's held open answer goes with its unmount.

6. **`AdminLogoutButton` does not have this defect.** It has the same order (`logout()`, then `goto`) and no reset, but no page of the Admin App mounts `PreventNavigation` (`git grep -q -F PreventNavigation -- apps/frontend/src/routes/admin`, exit 1 at planning), so its navigation cannot be refused. It is not changed. Task 3's verify pins the fact, and plan 42 records in `deferred-items.md` that phase 179.2's account flows must use the registry if they mount a guard.

7. **The three gates' calls of `logout()` are covered and unchanged.** `SetPasswordGate`, `TermsOfUseGate` and `IdentityProviderGate` render in place of the page (`(protected)/+layout.svelte`), so no guard is mounted under them and `confirmLeave` asks nothing.
