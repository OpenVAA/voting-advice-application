# Phase 179.1 Plan 61: Drafts Removed by Every Browser Sign-Out Summary

**One remover, `discardContestantDrafts` in `contestantDrafts.ts`, which the Contestant App's reset also calls. The Admin App's Log out, its subscriber to a sign-out made in another tab and its protected load's browser sign-out of a non-administrator now call it too, so no browser sign-out leaves a Contestant App draft behind. A session that lapses keeps its draft.**

## For the operator's reading

Where the Contestant App's drafts are removed now, per the ruling of 2026-11-06 (browser sign-outs only):

- **Contestant App's Log out:** removed, as before, through the store's reset, which now calls the shared remover.
- **Admin App's Log out:** removed once the sign-out has worked. A sign-out that fails keeps them, so `T-179.1-104` stands as the operator kept it. Before this change the Admin App's Log out left the draft. A dev-server run with only the tests changed showed that: the seeded key was still in storage on the login page.
- **The Admin App's protected load, in the browser, for a user who is no administrator:** the drafts are removed before the redirect to the login page. This happens after a sign-out that worked, and after one that failed with no session left. In the Contestant App's tab, the subscriber also resets the user's data on that sign-out, so the page holds no draft handle that could store it again.
- **A sign-out in another tab:** the Admin App's tab removes the drafts whether it reads as signed in or not. The Contestant App's tab resets, as plan 60 made it.

Where they stay, by the same ruling:

- **A lapsed session.** A load that merely finds no session removes nothing, in either app.
- **A sign-out made by the server alone.** `signOutToLogin`, and `handleError` during a server render, cannot reach `localStorage`. This includes a full load of `/admin` by a non-administrator, which the diagnosis measured as the SSR arm. That user is signed out on the server, and their draft stays in the browser until their next sign-in, when `init` removes another user's drafts. It does not remove the same user's.
- **A sign-out that fails with the session left.** The draft and the session both stay.

What stays unproven:
- WebKit and Firefox were not driven, and no production build was run. Every browser observation is Chromium on a dev server.
- No browser run covers an Admin App tab removing drafts when **another** tab signs out (D4). Unit cases hold it. Plan 60's two-tab Admin test stores no draft.
- The Contestant App's new `'here'` reset is not isolated by a browser run. The link-into-the-Admin-App tests pass through both it and `handleError`'s own removal. Unit cases hold each one apart, including the mutation that makes the reset run during the context's own logout.

Observed and inferred:
- Observed: the three E2E tests red without their change, at `expectNoContestantDraft` and nowhere else, and green in `179.1-61-green` and in `179.1-61-close` (688 of 688). The unit cases red without their change, or under a mutation (ledger `61-1`, `61-2`).
- Inferred, by reading `supabaseDataWriter._logout`: in the browser the writer awaits the logout endpoint before the client signs out. So a `'here'` announcement never arrives before the Contestant App's `#loggingOut` is set. The contestant pin's fake writer now models that await. No run isolated the order.
