## Rulings carried by this plan

1. **`WR-10`'s proposal does not fire on the path it was written for, and the plan does not adopt it alone. Measured at planning.** The verifier and the review propose an effect on `logoutFailed && !isAuthenticated`. `isAuthenticated` is `!!page.data.session`, and `routes/contestant/+layout.server.ts`'s `load` reads nothing SvelteKit tracks, so a link does not run it again: SvelteKit marks that node unchanged (`has_changed` in `client.js`) and keeps the last value. `179.1-planning-probe-2`, row 2, then a link that reaches the gate: the address is `/contestant/login?redirectTo=…`, the header still has Log out and the message is still there. So `isAuthenticated` stays true on the login screen, and the review's sentence that the login screen offers no Log out does not hold on this path. **The rule built is: the message is withdrawn while `contestantCtx.logoutFailed` and either `!contestantCtx.isAuthenticated` or `page.route.id === ROUTE.ContestantAppLogin`.** The login route is what the gate redirects a sessionless request to, so standing on it after a failure says the session is gone. `179.1-planning-probe-3`, with this rule: the login screen has no message. `179.1-48-mut-session` shows the proposal alone red in a browser.
   - **What is kept from the proposal:** the `!isAuthenticated` arm, for a load that does run again, as an `invalidateAll` does. The unit test pins it.
   - **A page with no server read stays as it was.** Row 2, then Back from the profile to the home: `179.1-planning-probe-1` read no `__data.json` request, and the page, the header's Log out and the message stay, while the link to the profile after it made the one request that reached the gate. That is right: the page still reads as signed in, the message is what tells the user otherwise, and a press works. The tests assert it.
   - **Reported and not changed:** on the login screen after this path the header still shows Log out until something runs the session's load again. Pressing it is harmless by reading: the sign-out finds no session and answers 200, and the logout's `goto` to the same address falls through to the full load. Plan 50 records it. 3. **`WR-12`: how the sentence with the count relates to the description.** Plain `aria-describedby` over the modal's body, as the review proposes, would point the dialog's description at a sentence whose number changes every second. A description is normally read when focus enters the dialog; what a reader does when the description of an open dialog changes is the reader's to decide, and re-reading it each second is the failure to avoid. It is not knowable from markup and no run can establish it. So the description never holds the ticking number:
   - `aria-describedby` names one element inside the dialog: a `<div id={descriptionId} hidden>` that holds what the modal says is at stake and the ingress sentence, with `logoutModalTimer` as its `timeLeft`. Referenced content counts for the description though it is hidden.
   - The visible ingress keeps its ticking number, outside that element. A user moving through the dialog by virtual cursor reads what is left there.
   - **So a reader is told what will be lost, that a count ends in a sign-out, and the count's full length, once.** The same sentence read again mid-count still says the full length. That is the cost, and it is less than a description that changes every second.
   - **Measured at planning, in Chromium's accessibility tree through CDP, `179.1-planning-probe-3`:** the dialog's description is "You have unsaved changes. They will be lost if you log out. Are you sure you want to log out? You will be automatically logged out after 30 seconds."; five seconds later on the page's clock the visible sentence says 25 and the description is unchanged.
   - **No wrapper around the visible paragraphs, because of `p:last-child` in `apps/frontend/src/app.css`:** wrapping them would take the margin off the last one, a visual change the waiver does not cover. So the sentences at stake live in a snippet `whatIsAtStake`, declared at the top level of the file, outside `TimedModal`, and rendered in both places. A snippet declared inside `TimedModal` would become a prop of it.
   - **The id is `getUUID()` from `$lib/utils/components`, the repository's convention, as `Alert` and `Input` have it, not a fixed id:** the header's button and the page's are mounted together on the entity home, `NothingToEdit` and `ReadFailure`, and a repeated id would point one dialog at the other's text.
   - **It passes through `restProps`,** which `TimedModal`, `Modal` and `ModalContainer` already spread onto the `<dialog>`. Neither those files nor their types change: `ModalContainerProps` is `SvelteHTMLElements['dialog']`.
   - **Focus stays on Continue,** as the UI review asks.
   - **This is a human item, and the plan does not claim it.** What VoiceOver, NVDA and TalkBack say is on the operator's list in plan 50. The tests show that the attribute is there and what the browser computes from it, and nothing more.
