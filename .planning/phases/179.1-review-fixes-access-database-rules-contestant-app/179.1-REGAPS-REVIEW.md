### Warnings

#### WR-14: The message is withdrawn on the login route while the session is alive, and a sign-out that fails there shows nothing

**File:** `apps/frontend/src/routes/admin/+layout.svelte:32-37`, `apps/frontend/src/routes/contestant/+layout.svelte:50-55`, `apps/docs/src/routes/(content)/developers-guide/contestant-app/login-and-password-reset/+page.md:69`

**Issue:** both effects clear the flag when `page.route.id` is the login route, and both comments give the reason: "the login route, where the gate sends a request with no session, is what says the session has gone". The guide says the same: "the login screen, which says the session has gone". The gate does send sessionless requests there, but nothing keeps a live session away. `appGates.ts:17` states it: a client-side navigation to an entry route whose page and layouts load nothing from the server "sends no request the request hook sees, so it is not redirected".

The two login routes are such routes in a production build:

- `routes/contestant/login/` has no server file.
- `routes/admin/login/+page.server.ts` exports `actions` and no `load`. `write_client_manifest.js:70-77` takes `has_server_load` from the build's metadata, so a production client sends no data request. A dev server treats any `+page.server` as having one, so there the gate redirects the Admin case to its home. **The E2E suite runs on a dev server, so it cannot meet the Admin case.**
- The outermost `+layout.server.ts` files read nothing tracked, as plans 48 and 49 measured.

The path, with the sign-out failing and the session alive (the audit's row 1):

1. An administrator signs in through the form. `applyAction` pushes the home (`client.js:2601`), so `/admin/login` stays behind it in history.
2. Log out fails. The message says "You may still be logged in, so please try again".
3. Browser Back shows the sign-in form. No request is made, the route id is the login route, and the effect withdraws the message.

The session is alive, the screen is a sign-in form, and the sentence that said otherwise is gone. In the Contestant App the same happens at `/contestant/login` with no server file, in both dev and production, by going further back in history.

**The second half.** On that screen the header still offers Log out, because `isAuthenticated` is true. A press that fails sets the flag, and the effect clears it in the same flush, so no message is ever shown. The button's `catch` only logs. The user has no feedback on a failure that leaves them signed in.

Plan 48's ruling 1 and the deferred entry cover the stale header after a session has gone, and call a press there harmless because it "finds no session". Neither covers a live session.

**Pinned the wrong way:** `admin/layout.svelte.test.ts:137` and `contestant/layout.svelte.test.ts:130`, `withdraws the message on the login route, although the session still reads as alive`, assert this as intended. They model the stale case, which the fake context cannot tell apart from a live one.

**Measured (`login.svelte.test.ts`, the real admin layout):** `{"A_shownOnProtected":true,"A_shownOnLoginWithSessionAlive":false,"A_clearCalls":1,"A_stillAuthenticated":true,"B_shownAfterFailedPressOnLogin":false,"B_flagAfter":false,"B_clearCalls":1}`. A is the message reaching the login route. B is a failed press on it. The contestant effect has the same condition; it was read and not measured.

**Confirmed by reading:** the effects, the gate's own statement, the server files, the manifest code and `applyAction`'s push. **Not run:** the path in a real app. That Back makes no request in a production build rests on the two sources cited and on the plans' measurement of the outermost load, and was not observed on this path.

**Fix:** make the premise true, so the route arm means what the comments say. Give the entry routes a server `load`, so that a client-side navigation reaches the gate and a live session is sent home, in dev and in production alike:

```ts
// routes/admin/login/+page.server.ts, routes/contestant/login/email/+page.server.ts, and a new routes/contestant/login/+page.server.ts
export const load = () => ({});
```

Correct the paragraph of `appGates.ts:17`, which then says less than holds. Rewrite the two unit cases to name the sessionless case. Add an E2E step to `the message stays across links`: with the session alive, Back through history to the login route ends on the home with the message still there. If adding the loads is unwelcome on the auth path, the alternative is to drop the route arm and re-read the session on entering the route; that is the operator's choice, as plan 48's ruling 1 says of a dependency on the outermost load.

#### WR-15: WR-10's defect remains on the sign-in screen: after a failure that cleared the cookies, Back reaches it with the message, and the message follows into the next sign-in

**File:** `apps/frontend/src/routes/contestant/+layout.svelte:50-55`, `apps/frontend/src/lib/routes/route.ts:147`, `apps/frontend/src/lib/routes/appGates.ts:108-116`

**Issue:** the effect names one route, `/contestant/login`. The gate lists seven entry routes for the Contestant App, and the sign-in screen is `/contestant/login/email`. Plan 48's truth, "so it stays off the login screen and out of the next sign-in", holds only for a path that passes through `/contestant/login`.

The path, for a single-entity user in the audit's row 2 (the answer cleared the cookies):

1. History is login, sign-in, entity home, profile. Log out fails on the profile, with the message shown.
2. Back to the home. No server read, as plan 48's own test `a link finds the session gone` asserts.
3. Back to `/contestant/login/email`. Going from a protected page to it runs no `(protected)` load. Its server file has `actions` alone, so production makes no request. A dev server makes one, but with no session the gate lets it through, and the outermost load does not rerun. `isAuthenticated` stays true and the route id is not the login route, so the flag stays.
4. The sign-in form now says "You may still be logged in, so please try again".
5. The user signs in, possibly another person on a shared computer. `use:enhance` and `applyAction` (`login/email/+page.svelte:119`) make a client navigation with `invalidateAll`, so `contestant/+layout.svelte` stays mounted and `isAuthenticated` is true afterwards. Nothing clears the flag, and the sentence stands in the new session until it is closed.

This is the harm of `T-179.1-114`. `179.1-48-mut-any-link` and the two tests of plan 48 go through a link that reaches the gate, or stay signed in, so no test presses Back this far. A user with several entities crosses a change of entity on the way back, which reruns `(protected)/+layout.server.ts` and reaches the gate, so they are not on this path.

The Admin App has one entry route and is not affected.

**Confirmed by reading:** the effect's condition, the route constants, the gate's list, the sign-in screen's server file and handler, and that no other writer of the flag exists (`contestantContext.svelte.ts:578,584,611`). **Not run:** this path in a real app.

**Fix:** withdraw on every entry route of the app's gate, which also holds for any entry route added later, with WR-14's loads so that the premise holds on each of them. `resolveAppGate` is already exported from `$lib/routes`:

```svelte
// routes/contestant/+layout.svelte; the Admin layout takes the same line.
$effect(() => {
  if (!contestantCtx.logoutFailed) return;
  const routeId = page.route.id;
  const onEntryRoute = !!routeId && !!resolveAppGate(routeId)?.entryRoutes.some((key) => ROUTE[key] === routeId);
  if (!contestantCtx.isAuthenticated || onEntryRoute) contestantCtx.clearLogoutFailure();
});
```

Add an E2E test: row 2, Back to the sign-in screen, no message; sign in, no message.
