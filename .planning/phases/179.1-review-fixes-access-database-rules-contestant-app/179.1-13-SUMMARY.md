# Phase 179.1 Plan 13: the mails link to the confirm page Summary

**`account-access` now mails `<site>/<locale>/auth/confirm?token_hash=…&type=…` for the sign-in, recovery and address-change mails. A mailed token no longer passes through a GET that could verify it.**
- The auth service admits that page and no longer admits the callback. This holds locally (`config.toml`) and for a hosted project (`infra/modules/supabase/hosted-settings.json`), and the parity guard holds the two equal.
- The E2E shape check and the contract pin the new path. The suite is green this way: 625/625, held and at the close.

**Note for the deployment workstream:** `infra/modules/supabase/hosted-settings.json` changed (D-27). `redirect_callback_paths` now holds `["/auth/confirm", "/*/auth/confirm"]`. The key name is unchanged, so `settings.tf` builds `uri_allow_list` from it as before. A hosted project applied from this tree admits the confirm page and refuses `/api/auth/callback`.

## Why the first held run was red

- **Observed:** the four confirm-page scans failed their reach proof: `Expected: "/auth/confirm"`, `Received: "/en/auth/confirm"`. These were `auth-confirm-signed-out` and `auth-confirm-signed-in`, each with its dark twin.

- **Fix:** the scan entries now state the segment (`addressLocale: 'en'`). The mail is not special-cased for the base locale. The run was repeated on that changed tree as `179.1-13-held-2`, which was green. Nothing was re-run on an unchanged tree.
