# Phase 179.1 Plan 64: The Admin App's login form and the password field Summary

**The Admin App's login form now posts to `getRoute.current('AdminAppLogin')`, so a sign-in after Back reaches the home instead of the error page. Its email field is the shared, labelled `Input`. The password control carries `autocapitalize="none"`, `autocorrect="off"` and `spellcheck="false"` in both states. Its show/hide toggle keeps focus on the control and puts the caret at the end.**

## For the operator's reading

**What a user now meets on the Admin App's login screen.** The email field has a visible label, "Email" in English, with no placeholder in its place. It is the same kind of field as the password beside it. The sign-in button turns on as the address and the password are typed. Now take a user who signed out in one tab and signed in in another, then pressed Back in the first tab. A sign-in on the form there reaches the Admin App's home. Before, it ended on the root error page, titled with the message of a JSON parser. The form posts to the login route in the reader's locale, whatever address the page stands at.

**What a user now meets in the password field, in both apps.** This covers the Admin App's login, the Contestant App's sign-in and both fields of the password setter. The field asks the platform not to capitalise, autocorrect or spell-check, whether the text is hidden or shown. Pressing the show/hide toggle leaves the cursor in the field, at the end, with nothing selected. That holds for a mouse or touch press (the press no longer takes focus from the field) and for a keyboard press (focus returns to the field). A keyboard user who wants to press the toggle again uses Shift+Tab. That is what ruling 6 asks for.

**The register page (ruling 4).** Its Dismiss posts to `?/dismissRegistered`, which resolves against the address the page stands at. No redirect draws that page at another address, so nothing was changed. These are the paths read:
- Every `redirect(` under `apps/frontend/src` outside tests. None targets `ContestantAppRegister`.
- The Contestant App's gate row in `appGates.ts`. It redirects only to `ContestantAppLogin` (no session in the protected group) and to `ContestantAppHome` (a session on an entry route).
- The OIDC callback. It redirects to the home or to the identity provider's error screen.
- The two `goto(getRoute.current('ContestantAppRegister'), { replaceState: true })` calls in `register/email` and `register/sign-in`. They are client navigations whose address is the register page itself.

The page's only form action is that query-only one: `git grep 'action=("|\{)'` lists `routes/admin/login` and `routes/contestant/register` alone. No test was written for a path that was not driven.

**What stays unproven.** These go on plan 66's UAT list:
- iOS Safari does not capitalise the password's first letter, masked or revealed.
- iOS does not select the contents when the toggle focuses the field from code. Chromium and desktop WebKit were measured in the diagnosis; iOS was not.
- Whether the iOS keyboard stays up through a tap on the toggle.
- What VoiceOver, NVDA and TalkBack say when a keyboard press of the toggle moves focus to the field.
- How the newly visible email label looks on the Admin App's login screen (7C's visual change). No visual baseline covers that page.

- **Issue:** The test failed at `fillAwaitingScript` (`toBeEnabled`, `Received: disabled`). The trace shows the problem. The settle step `goBackToHomeOrLoginForm` passed 3 ms after `goBack`, because the login form was already standing before Back. Both fills then landed while the router was still completing the popped navigation, and the password read empty once the page was drawn. In `179.1-64-green` the timing had happened to fall the other way.

The steps that follow up to the DOM update are microtasks. The test uses this step in place of `goBackToHomeOrLoginForm`. Only test code changed.
