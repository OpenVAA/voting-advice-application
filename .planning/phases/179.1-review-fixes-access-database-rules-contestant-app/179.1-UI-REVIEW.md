## Top 3 Priority Fixes

1. **A closed menu item gives sighted users no sign that it is closed or expandable** — in `NavItem.svelte` the closed-with-reason branch is a `<button aria-disabled="true" aria-expanded>` that carries the same classes as an open item (`hover:bg-base-200`, `!text-neutral`); only the `pointer-events-none hover:bg-transparent` branch is dimmed, and that branch does not apply when a reason exists. A user cannot tell the item is unavailable until they press it, and the reason then appears in a region below it. Fix: give the closed state a visible treatment (reduced opacity or the lock icon the home page uses for closed entries, plus a disclosure chevron or the reason beneath), and confirm contrast of the reason text, then capture it at 375 px.
2. **PasswordSignIn renders two adjacent links to the same page** — `forgotPasswordHref` is passed to both "Forgot password" and "I have not set a password" (`PasswordSignIn.svelte`), each as a full-width Button. Two stacked buttons with different words and one destination read as a choice that is not one, and double the tab stops. Fix: render one link with wording that covers both, or, when `noPasswordYetOffered`, show only the second sentence as a line of text with a single link.
3. **Settings page carries a no-op class and an overlong action stack** — `flex-nowarp` (typo for `flex-nowrap`) at `routes/contestant/(protected)/settings/+page.svelte:225` has no effect, and the same container holds password setter, error, Update, and Contact support, with the Contact support button disabled after a successful change for no stated reason. Fix: delete or correct the class, and drop the disabled state of Contact support (support is not something a success should lock).

## Detailed Findings

### Pillar 1: Copywriting (3/4)
- Key parity: `authConfirm` (9 keys), `contestantApp.emailSent` (25), `contestantApp.home` (38), `contestantApp.register` (48), `contestantApp.nominations` (93), `contestantApp.settings` (20), `contestantApp.error` (8), `contestantApp.common` (19) hold the same count in da, en, et, fi, fr, lb and sv.
- Contract strings read well: the confirm page names what Continue does per link type (`authConfirm.intro.*`) and what a signed-in browser loses (`authConfirm.signedIn`); the read failure says the user is still signed in (`contestantApp.error.readFailed.content`); the sentence-with-link pattern ("If you have problems receiving the email, {contactSupportLink}.") keeps the link words inside the sentence; the home task names the address ("Confirm your email address {email}").
- The Swedish `common.login` is now "Logga in", so the earlier mislabel noted in phase 179 is gone from the already-registered notice's Log in button.
- Defect (WARNING): `contestantApp.register.registeredNotice.content` reads "Please login with your email and password…". "login" is the noun; the verb is "log in". Fix in the en file and re-check the six translations.
- Gap (WARNING): the settings submit button takes `validationError || t('contestantApp.settings.password.update')` as its label (`settings/+page.svelte`), so the button text changes into an error sentence while the password is invalid. A label that turns into an error is a copy and a11y smell (the name of the control changes as the user types).
- Locale quality for the new keys is not evidenced as reviewed by a native speaker.

### Pillar 2: Visuals (3/4)
- Confirm page: `MainContent` with title, intro, optional bold signed-in notice, Continue as `variant="main"`, Cancel a plain button only when signed in. One focal action. Hidden fields live in a form that the button reaches by `form={formId}`.
- ReadFailure: ErrorMessage hero, one sentence, Try again (`variant="main"`, no icon), support block, logout. Clear order; matches the intent.
- Identity-provider error page: three classes, one main action each; `noRetry` leads with support and demotes Try again. Matches the plan.
- Registration modes: native fieldset and legend, each option a `bg-base-100 rounded-lg` card with a bordered Radio (`radio radio-primary border`), the chosen mode's panel opens inside the same card. Good grouping. Not seen rendered.
- Defect (WARNING): two same-destination links on PasswordSignIn (fix 2).
- Defect (WARNING): closed menu item has no visual disabled/expandable treatment (fix 1).
- Home: the email task is the list's first `<li>` with the `mail` icon and `wrap-anywhere hyphens-none`; it carries no status or badge by design. It sits inside the same `<ol>` as tasks that do show a status, so the first row reads differently from the rest; intentional per the plan, but unverified at 375 px with a long address.

### Pillar 3: Color (4/4)
- No hex or `rgb(` literal in any audited component or page.
- Accent: `variant="main"` for the single main action, `color="warning"` for destructive or leave-actions (Delete nomination, Remove portrait), `radio-primary` on Radio. No `text-primary`/`bg-primary` written in the audited files.
- One use of `text-secondary` in `routes/contestant/help/+page.svelte:41`, outside this phase's surfaces.
- Surfaces: `bg-base-300` on the confirm and error pages, `bg-base-100 rounded-lg` for cards; the 60/30/10 split follows the existing shell. Contrast of `onShadedBg` inputs on `bg-base-300` was not measured.

### Pillar 4: Typography (3/4)
- Sizes written: only `text-lg`. Weights: only `font-bold`.
- `font-bold` on the registration legend (`RegistrationModeSelector.svelte:98`), the signed-in notice (`auth/confirm/+page.svelte:58`), and the address in the password-reset page.
- `text-lg` hand-written on the nomination card h2 (`nominations/+page.svelte:350`, `details/+page.svelte:631`), the entity-selection group heading (`(protected)/+page.svelte:144`) and as the `subheadingClass = 'text-lg mt-lg mb-md mx-md'` string, duplicated in `settings/+page.svelte:150` and `profile/+page.svelte:338`. The registered-notice h2 on the register page carries no size class at all, so card headings differ across the app. Fix: one shared subheading class or an h2 style in `app.css`.

### Pillar 5: Spacing (3/4)
- Tokens used: `gap-md`, `gap-sm`, `gap-xs`, `gap-lg`, `mt-lg`, `mt-md`, `p-lg`, `px-lg`, `pb-lg`, `mb-md`, `min-h-touch`, `pb-safelgb`. No numeric class in the new components.
- Defect (WARNING): `flex-nowarp` at `settings/+page.svelte:225` is not a Tailwind class (typo for `flex-nowrap`); it has no effect. It dates from the original app shell rewrite, but this phase moved and edited the page and left it.
- Defect (WARNING): `NavItem.svelte`, edited by plan 23, still uses `px-10` (numeric) and `pl-[2.75rem]` (arbitrary) beside the token scale; the reason line uses `ps-touch pe-md`, so the reason's indent depends on `touch` equalling the icon column (`2.75rem`), which is two sources for one number.
- `app.css` gives every `p` a global `mb-16` and `p:last-child` zero. The stacked sentences of EmailSentPanel therefore have space between them; but the sr-only status paragraph is the last child, so the visible last paragraph keeps its margin (a small trailing gap before the Send again block, on top of the block's `mt-lg`). Unverified rendered.

### Pillar 6: Experience Design (3/4)
- Covered well: Continue on the confirm page is single-flight (`submitting` flag, `cancel()` on a second submit, `loading` on the button); Try again on ReadFailure is single-flight, logs a failed rerun, and returns focus to the button when focus fell to `body`; Send again keeps `aria-disabled` rather than native `disabled` so focus is not lost, and the count is `aria-describedby` rather than a live region; the closed menu item is a real button with `aria-expanded`/`aria-controls` and a `role="status"` region that exists before the reason is put in; the nomination delete asks for confirmation in place with a `Warning` and `aria-describedby`; image removal stages the change, hides itself while answers are locked and moves focus to the upload control; the settings pending-address block has resend, change address, save with `loading`, in-use and failed messages, and a polite status region.
- Gap (WARNING): the settings address form has no way back once "Use another email address" is pressed (`changingEmail` is only reset by a successful save), so a mis-press leaves a form the user must fill or leave the page to escape. The same one-way pattern was flagged in phase 179 for the gate.
- Gap (WARNING): `settings/+page.svelte` `Contact support` is disabled after a success, and the update button's label turns into the validation error.
- Gap (WARNING): reason of a closed menu item is toggled by click alone; keyboard users get it (button), but there is no dismissal on Escape or on navigating away other than the item becoming open.
- Gap: the confirm page's `Cancel` is rendered only for a signed-in browser; an unsigned visitor who does not want to continue has no explicit exit (the page is also reachable only from a mailed link, so this is low risk).
- Not verified: rendered states, contrast, 375 px wrapping of long addresses, behaviour in dark mode; no axe scan run in this audit.
