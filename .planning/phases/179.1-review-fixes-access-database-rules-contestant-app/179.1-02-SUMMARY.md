# Phase 179.1 Plan 02: Re-invitable Claimed Addresses Summary

**`invitations_email_target_key` is now a partial unique index over open rows (`email IS NOT NULL AND claimed_at IS NULL`). It keeps its name, so an address whose invitation was claimed, or whose claimant was deleted, can be invited to the same target again, and a project editor can be promoted by a project-admin invitation. Two open rows still collide with the same error, and the code index is unchanged. pgTAP and the server contract both showed this red on the old index and green on the new one.**

## Decisions Made

- **The test's place in the walk.** The plan put the new test after the claim test. Under `mode: 'serial'`, a failing test skips every test after it, so the red control's rule "every other test passed" could not hold with the new test in the middle. It is therefore the last test of the walk, which is still after the claim. It reads the claimant's session that the claim test now keeps in `invitedSession`.
- **No `inviteAgain` fixture step.** `seedEmailInvitation` seeds through the inherited `createInvitations` with no delete before it. The duplicate test already relies on that. The fixture is unchanged.
- **The second claim answers `claimed: [candidateGrant]`.** `claim_invitations` lists a row whose grant already exists as claimed and writes no second grant. The test asserts that answer, one grant row for the address, and both candidate invitations claimed.
- **The pgTAP cases clean up after themselves.** Each one deletes, as postgres, the rows it seeded. This keeps the later sections' counts unchanged, for example "every project-scope promise is still there" and "deleting a candidate removes the invitation that targets it".
