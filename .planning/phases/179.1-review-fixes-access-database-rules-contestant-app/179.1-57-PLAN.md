## Rulings carried by this plan

1. **The mechanism, confirmed.** Measured in the diagnosis in both apps with the sign-out held 6 s: the button stays enabled, its icon drawn, its name `Log Out`. The Admin App's `LogoutButton.svelte` keeps `leaving` as a plain `let` and passes no `loading`; the Contestant App's trigger passes no `loading` though its `leaving` is `$state`. `Button` ignores a Promise its `onclick` returns (`Button.type.ts` types it as returning nothing): its `loading` prop is the one way, which draws `Loading` in place of the icon and disables the button. So the operator's guess, a returned Promise, is not how `Button` works, and the plan uses `loading`.
2. **The name while loading.** For `variant="icon"` the loading text replaces the `aria-label` and the `title`, so the header button is named `Loading…` once while it loads; a test that finds the button by its test id is not affected, and the fixture finds it so. For the other variants the visible label is the loading text and `Loading`'s own `sr-only` label repeats it: `Loading… Loading…`, measured on the modal's Log Out in the diagnosis. Inside `Button` the spinner is hidden from assistive technology with `aria-hidden="true"`, so the name is the label once. `Loading` stands alone elsewhere and keeps its label there.
3. **Focus.** A pressed button that becomes disabled loses focus to the body, as the modal's Log Out already does. On success the page leaves; on failure the button is enabled again with the message shown. Recorded for the operator's screen-reader check; no focus is moved here.
4. **No copy.** `common.loading` exists in all seven catalogues. The spinner is the visual change G-15 grants.
