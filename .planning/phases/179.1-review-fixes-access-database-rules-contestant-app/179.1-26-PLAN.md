## Rulings and deviations carried by this plan

1. **No database change for D3** (research): `cleanup_old_image_file` acts when `OLD.image IS DISTINCT FROM NEW.image` and deletes the old `path`/`pathDark` in the row's own folder that the new row does not name; the object's deletion is observable only after commit, as `storage-cleanup.spec.ts` observes it (a public GET of the deleted object answers 400).
2. **The name of the store's setter** (`userData.setImage` or the context's equivalent) is read from the tree; clearing passes `null` through the same path a new image takes, and the save writes it.
3. **The Remove action is hidden while answers are locked**, as the image input is locked then; the database refuses it then anyway (plan 05's storage arm and self-update conjunct).
