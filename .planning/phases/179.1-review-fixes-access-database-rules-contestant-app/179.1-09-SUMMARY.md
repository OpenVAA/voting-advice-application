# Phase 179.1 Plan 09: identity-callback through the locked find-or-create, and smart name casing Summary

**identity-callback finds or creates the entity with one call of `identity_entity_find_or_create`, so five racing first sign-ins of one identity end with one account, one candidate and one editor grant. A name the provider sends in capitals is stored smart-cased by a frontend util and its Edge copy, which a parity test keeps equal.**

## Accomplishments

- **Step 6 is one locked call.** `identity-callback` calls `supabaseAdmin.rpc('identity_entity_find_or_create', …)` in place of the record read, the own-entity lookup, the insert, the grant write and the compensating delete. `findOrCreateOutcome` maps `created`, `found` and `gone` to `created`, `found` and `no_entity`, and refuses any other shape without putting an id in its message.
- **The concurrency case.** The `bank-auth` case `five concurrent first sign-ins of one identity create one candidate and one editor grant` sends five calls with `Promise.all`. It asserts five 200 answers, exactly one `created`, one account, one candidate with the identity's names, and one candidate editor grant.
  - It was red on the function as it was (`179.1-09-red`).
  - It was green with the change (`179.1-09-green`, 14 of 14) and in the close.
- **The dead helpers are gone.** `resolveOwnEntity`, `createCandidate`, `deleteCandidate`, `createOrganization`, `deleteOrganization`, `writeEntityGrant`, `readRegisteredEntity` and `withRegisteredEntity` are removed with their tests, and so are three modules that were left empty (`candidateRecord.ts`, `organizationRecord.ts`, `entityGrant.ts`).
  - `flowConformance.test.ts` pins the call order: the account, then the find-or-create, then the `app_metadata` write, then the link.
  - It also pins that no separate lookup, insert, grant write or delete is called, and that every exported value is used.
- **Smart casing.** `smartNameCase(text, locale?)` returns `toNameCase(text)` when the text holds a letter (`/\p{L}/u`) and equals its own `toLocaleUpperCase(locale)`, and returns the text unchanged otherwise. `toNameCase` splits on white space and dashes, so `ÖSTERBERG` becomes `Österberg`, where the old pattern gave `ÖSterberg`. `extractIdentityClaims` returns both names smart-cased and leaves the match value as sent.
- **The parity table** (`nameCase.test.ts`). Each name is checked both ways: the Edge copy against the frontend module, and the result against the expected column.

  | Name sent | Stored as |
  |---|---|
  | `MATTI-PEKKA VIRTANEN` | `Matti-Pekka Virtanen` |

  | `ÖSTERBERG` | `Österberg` |
  | `ANNA  MARIA` | `Anna  Maria` |
  | `JEAN-LUC 2` | `Jean-Luc 2` |
  | `McDonald`, `van der Berg`, `matti`, `Matti-Pekka`, `ÄIJÄLÄ-österberg` | unchanged |
  | `''`, `123`, `-` | unchanged |

- **The close.** `179.1-09-close` passed 616 of 616 tests (`179.1-08-close`'s 615 plus the one `bank-auth` case) across 128 projects, with no flaky, skipped or did-not-run tests. ## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Racing first sign-ins failed at the account step**
- **Found during:** Task 1, red run `179.1-09-red`
- **Issue:** Four of five concurrent first sign-ins answered 503 (`Failed to create auth user: Database error saving new user`). The invites raced for one placeholder address, and the account step's `email_exists` tolerance did not cover that error. The research had assumed the opposite (ruling 2).
- **Fix:** After any failed invite, the function looks the account up on its placeholder address and goes on with the account it finds. It throws only when there is none.
- **Files modified:** `apps/supabase/supabase/functions/identity-callback/index.ts`, `flowConformance.test.ts`
- **Verification:** `179.1-09-green` 14 of 14; ledger row 09-4
- **Committed in:** `60529ad55`

**2. [Rule 1 - Bug] An `app_metadata` write could put back an older registered-entities record**
- **Found during:** Task 1
- **Issue:** The auth service writes the whole `app_metadata` column from the copy the caller read. A write that held `registered_entities`, or that ran before the find-or-create, could overwrite the record the locked transaction had just written.
- **Fix:** Every `app_metadata` write comes after the find-or-create, and none carries `registered_entities`.
- **Files modified:** `appMetadata.ts`, `appMetadata.test.ts`, `index.ts`
- **Verification:** `appMetadata.test.ts` and `flowConformance.test.ts` (`never carries the registered-entities record`); ledger row 09-4
- **Committed in:** `60529ad55`
