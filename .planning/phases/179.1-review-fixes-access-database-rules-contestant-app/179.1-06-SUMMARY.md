# Phase 179.1 Plan 06: The Answers Lock in the Contestant App Summary

**A save refused by the answers lock is now reported as the lock. The question page and the profile page show the not-editable note, and the nomination editor shows its `nominationsAnswersLocked` note, in place of the generic save failure.**
- **How the refusal is recognised:** the writer turns the database's `42501` "answers are locked in this project" into `AnswersLockedError` or into the `answersLocked` refusal.
- **When the database cannot name it:** the pages read their data again after any failed save and decide from the lock.

## Accomplishments

### The writer (Task 1)

- **The recogniser.** `ANSWERS_LOCKED_REFUSAL = 'answers are locked in this project'`, `INSUFFICIENT_PRIVILEGE_CODE = '42501'`, and `isAnswersLockedRefusal(error)`. It answers true when the code is `42501` and the message ends with the text. Its TSDoc follows `isNameRefusal`.
- **The answer setters.** `_setAnswers` throws `new AnswersLockedError()` on the lock's refusal and `setAnswers: …` on anything else. The raised text is not passed on.
- **The nomination setter.** `_setEntityNominations` returns `{ type: 'refused', reason: 'answersLocked' }`, checked before the other three refusals.
- **The types.** `SetEntityNominationsResult`'s reason union gains `answersLocked`, with its TSDoc line. The `@throws` lines of `updateAnswers`, `overwriteAnswers` and `setEntityNominations` and the section note now name four refusals.
- **The error.** `AnswersLockedError` (`name = 'AnswersLockedError'`), in `apps/frontend/src/lib/api/base/answersLockedError.ts`.

### The question page (Task 1)

- **After a failed save:** `await invalidateAll()`, then `await tick()`.
- **When the lock explains it:** if the error was an `AnswersLockedError`, or `contestantCtx.answersLocked` is true after the re-read, the page sets no failure message.
  - `saveRefusedByLock` is ORed into the page's `answersLocked` alias, so the existing note renders, the answer input switches to display, and Save is replaced by Return.
  - Otherwise the failure is shown as before.
- **Reactivity.** No reactive accessor is destructured; every read is `contestantCtx.answersLocked`.

### The profile page and the nomination editor (Task 2)

- **The profile page.**
  - Its failure branch does `invalidateAll()` and then a tick.
  - While `contestantCtx.answersLocked` is true afterwards, no failure message is set. The note above the title says why.
  - Focus goes to `profile-submit` or, when that has been replaced, to `profile-return`.
- **The nomination editor.**
  - `StayedOutcome` and `NOT_STORED_MESSAGE` gain `answersLocked`.
  - `notStoredOutcome` returns it first.
  - The message region renders `<NotEditableNote reason="nominationsAnswersLocked">` for it, in place of the `ErrorMessage`.
  - The editor already reads its data again after every save. When that re-read leads to the nominations view, as it does in the E2E suite, the page shows nothing itself.
  - The `@component` list of save outcomes gains case 2, "Answers are locked".

## Deviations from Plan

### Restated or adjusted

**1. The plan's `--dirty-only apps/frontend/src` names a file, not a directory**
- **Found during:** Task 1, the green control's verdict.
- **The rule.** `179.1-verdict.mjs` treats a `--dirty-only` path as a directory only when it ends with `/`: `allowed.endsWith('/') ? p.startsWith(allowed) : p === allowed`. Its header says so.
- **The effect.** The green and held verdicts as the plan writes them fail with "outside the --dirty-only paths (apps/frontend/src, …)" for files under `apps/frontend/src/`.
- **What I kept.** Both runs' as-written verdicts (`179.1-06-green.verdict.log`, `179.1-06-held.verdict.log`), and the same verdicts with only the slash added (`…verdict-restated.log`: PASS).
- **What I did not change.** The verdict script and the plan's checks.

**2. `AnswersLockedError` was committed alone before the red cases**
- **Planned:** the error class held with the writer until the implementation commit.
- **Why it changed.** The red cases construct and check the real class. Without the module, both test files fail to load. That is an invalid red, and it would have turned every existing case in the two files red too.
- **What I did.** The execution rules let "a module that decides nothing yet" be committed first. I committed the class at `d2963d84a`. Nothing threw it until `5cc3e472e`.

**3. [Rule 1 - Bug] Two committed profile page cases pinned "no re-read after a failed save"**
- `stays and says that the save failed when the store reports a failure` and `… when the save rejects …` each asserted `invalidateAll` not called. That contradicts the plan's behaviour.
- I rewrote both to expect one re-read and no note, and retitled them `stays, reads the data again and says …`.
- They were committed red with the new cases (`a142edec2`) and are in ledger row 06-3.

**4. [Rule 2 - a11y] Focus after a refusal the lock explains (profile page)**
- Save is replaced by Return when the lock comes on, so focusing `profile-submit` would leave focus on nothing.
- The focus line now also matches `profile-return`. The new profile cases assert it.

**5. The E2E case restores the lock in the step that sets it**
- The plan says the test's last step sets the lock on again.
- The lock-on write that precedes the save already leaves the setting as the dataset has it, and nothing after it changes the setting. So that write is the restoring one, and no second, identical write was added.

**6. Docs left for later**
- The developers' guide does not yet describe how a page reports a save the lock refused. No sentence is false.
- A docs commit after the close had started would have made the close stale. I recorded it in `deferred-items.md` (`status: open`).

**7. `yarn -s`:** see Verify blocks.
