# Phase 179.1 Plan 89: Where a sign-in withdraws a closed tab's logout count Summary

**The confirm page withdraws a closed tab's logout count only once the link's `verifyOtp` has set a session, and ends on the 503 error page when it cannot sign out the session the browser holds. The three gated sign-ins withdraw only once their helper has admitted the session. The plan halted once at its targeted run, which was red in the manner of the slow first route load. The operator ruled one rerun with the host's contention removed, and that run is 707 of 707.**

**The first attempt stopped the plan at its last step.** The targeted run `tests/e2e-runs/179.1-e2e/179.1-89-targeted` ended with 682 passed, 1 failed and 24 did not run, on the committed tree `ea39e4f3b`.
- **The red test:** `admin-access` › `the Admin App's protected load` › `a session ended elsewhere with no signal to this tab: a link from the login form into the app reaches the login form, and so does a reload`.
- **First failing line:** `Error: Back settled neither on the home nor on the login form`, after `Timeout 10000ms exceeded while waiting on the predicate`.
- **The 24 that did not run:** the 23 of `perm-closed-project` and its setup, which run behind `admin-access`.
- **The run's records:** wrapper status 1, no void marker, and no Sleep entry in the window. Load was near 10 and about 35 GB of swap was in use. Another project's Supabase stack was up on the host.

What the trace shows (observed):
- The sign-in `POST /admin/login` answered 200 in 172 ms, and the home loaded.
- The test ended the session (`POST /api/auth/logout`).
- Back loaded `/admin/login` as a document in 59 ms.
- From 19:00:21.043Z, 76 of the page's client-module requests to the dev server got no answer before the wait ran out. Among them were `Alert.svelte` and `adminContext.svelte.ts`.
- Over the same seconds the dev server kept logging other workers' page views.
- The watcher's `file watching backend requires a full rescan` burst is logged at about 19:00:30Z.

That is the shape `.planning/todos/pending/2026-11-01-e2e-intermittent-slow-first-route-load.md` records for `179.1-39-green`, where a client module was never answered. So rule 16 makes it a stop, and the run was not made again.

Why this plan's change is not the cause (inferred, not re-tested in isolation):
- The request that failed carries no logout count.
- So `withdrawLogoutCount(event)` returns at once in the old position and in the new one.
- None of the stalled modules is a file this plan touched: its changes are server-only.

**What the code now does for a user.** The case is a closed tab whose Log out left a count. That browser's session now ends at its next request even when, in between:
- a sign-in failed, in either app;
- a mailed link was opened while the auth service was failing.

When the confirm page cannot sign out the account the browser holds, it shows the error page instead of going on.

**A deliberate narrowing of A2's ★ text.** The confirm page withdraws only after a `verifyOtp` that set a session. So a verification that fails with no session held now keeps the count, where the ★ sketch withdrew before verifying. The reason is the audit's outage reading: during an auth outage a session that cannot be read reads as none. Withdrawing first would then lose a closed tab's count while the browser keeps the session. The gated sign-ins are fixed for the same reason. A kept count with no session costs at most one sign-out by the hook, once the count runs out.

**What stays unproven (rule 17).** No browser drives these; they are unit-tested only:
- the confirm page's 503;
- the four sign-ins during an auth outage.
