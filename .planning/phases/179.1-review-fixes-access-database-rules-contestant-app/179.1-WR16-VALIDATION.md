## How to read this

The definitions are those of `179.1-REGAPS-VALIDATION.md`:

- **COVERED:** a standing automated test asserts the truth and was seen red at that assertion. For a run-count truth, the run's own files show it.
- **PARTIAL:** a test asserts part of the truth, and the rest rests on a step never seen red, a stub where a browser path exists, or a path no browser run drove.
- **MISSING:** no standing test asserts the truth. A one-off check may exist, and the row says so.
- **Limit:** something the plan says no run shows. It is never counted as coverage.

## WR-02, tested

**The claim:** `after a sign-out here and a sign-in in another tab, Back stands on the login form, and a reload reaches the home` cannot see where Back ended.

**Verdict: confirmed, and the Back half has no control.** It was tested by reading the fixture and the runs. Nothing was driven, so how the steps behave under a change is inferred.

**The fixture.**
- Before Back the form is on screen: `signOutHereAndSignInInAnotherTab` ends by `expectOnLoginPage`, and that tab has stood there since.
- `goBackToHomeOrLoginForm` polls `focusReset || emailInput.isVisible()`. The form is still there at the first read, so the poll can pass at once. Its failure message, `settled neither`, cannot be reached while the old form stands.
- `expectLoginFormStandsWithNoMessage` asserts `toBeVisible` and `not.toContainText` on a page whose form was already there. Its TSDoc says so: "reads what stands, not that a navigation has ended".
- The message has one more reason not to appear: `errorParam` is read once, when the page is created. So the line can only go red if the page is created again or a later change adds a message.
- The spec's next step is `reload`, with no wait between.

**The runs.**

| Run | Back title | Line it stopped at |
|---|---|---|
| `179.1-54-prod-red`, `179.1-54-dev-red-admin` | passed | none |
| `179.1-54-prod-mut-no-gate` | passed | none |
| `179.1-54-prod-mut-cookies` | failed | `adminLoginPage.fixture.ts:129`, in `expectAdminHome` after the reload |

So the ledger's reading is right: no run has failed this title before its reload. `expectLoginFormStandsWithNoMessage` has never been red in either test that uses it.

**Three refinements to the review.**

1. **"Which address it reloads from is not fixed" is overstated for that mutation's run.** Under `-mut-no-gate`, a reload at the login address stays there: the link's title went red at `fixture.ts:127` with exactly that address. The Back title passed in the same run, so its reload was not at the login address. That is one production run's indirect evidence that Back had moved the address. It is the only such evidence: **the test never reads the address, and truth 54-2's "at the address `/admin`" has no standing assertion.**
2. **"Could still pass" depends on when the wrong ending lands.** A Back that had finished on the home or the error page before the first read would fail at `toBeVisible`. A later one would pass, and then the reload reaches the home from a live session anyway. So the test does not reliably catch it. The review's wording, "depending on timing", is the right one.
3. **The review's first fix may not be available.** It offers a wait on the redirect's address "if the redirect does change the address". The plan's table measured the address staying `/admin`, so that signal is unlikely on this path.

**What stands behind R1's term for Back.** The planning probes `179.1-planning-probe-wr16-r1-prod` and `-r1-head` passed `P3`, in a temporary spec that is gone. Their `results.json` holds no stdout for it, so what `P3` read cannot be re-read from there. The operator's term rests on that measurement, and no standing test holds it.

**Beyond the review.** The same step gives `a session ended in another tab` its two Backs, and its later error-page line was seen red, so that test is not affected in the same way. No such control exists for the "no loop" of either stale-tab test.
