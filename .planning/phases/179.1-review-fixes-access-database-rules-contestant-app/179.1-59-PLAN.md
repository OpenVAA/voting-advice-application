## Rulings carried by this plan

1. **G-1, confirmed by running the installed libraries.** auth-js 2.117.2 `_signOut` removes the session before it returns `{ error }` when the logout call itself fails (5xx, network), and `@supabase/ssr` writes the cookie removal through `server.ts`'s `setAll`; `getSession()` on the same client then answers no session. Only an expired token whose refresh fails retryably leaves the session, and `getSession()` then answers an error. So the rule is: **a client holds no session when `getSession()` answers no session and no error**; an error, a rejection or a session means the error page. Not driven end to end in a browser: the server's own call to the auth service cannot be failed from one, so this arm stays unit-tested, as plan 54 left it.
2. **G-3, confirmed.** In the Admin App the protected load runs in the browser on entering the group, reads a stale live `session` from `parent()`, and the writer's `No active session` folds into the same `undefined` as a failed read in `getUserData.ts`. The fix asks after the failure and leaves `getUserData.ts` as it is (`PROH-179.1-15`): the review's other form, a distinct error in the writer, would change that file. In the browser the client is the tab's browser client, which reads `document.cookie`, so it answers no session in the stale tab (read in `universal.ts`, measured in the diagnosis).
3. **Through the adapter.** Outside `ADAPTER_BOUNDARY_ALLOWLIST` a file may not import Supabase or reach `.supabase`. The rule lives in `lib/api/adapters/supabase/sessionGone.ts`, inside the boundary. `signOutToLogin.ts` is on the allowlist and calls it on `locals.supabase`. The Admin App's load calls it through a new data-writer method, `isSessionGone()`, declared on the `DataWriter` interface, forwarded by `UniversalDataWriter` to an abstract `_isSessionGone`, and implemented by `SupabaseDataWriter`, the codebase's form for an auth method.
4. **`handleError` asks only in the browser.** There the writer's sign-out first calls the logout endpoint, whose server client clears the cookies on the failure ruling 1 names, and throws before the browser client's own sign-out; the browser client then reads the cleared `document.cookie`. On the server the universal client has no `setAll`, so after its own failed sign-out its `getSession()` answers no session though the browser keeps the cookies, and a redirect there would loop. So on the server `handleError` keeps the 403. `browser` from `$app/environment` tells the two apart.
5. **The tests the fix changes.** Plan 54's test `a session ended in another tab: a link from the login form into the app ends on the error page, and a reload reaches the login form` pins the 503 and ends the session by the other tab's header Log out. Plan 60's listener will act on that sign-out's broadcast, so the rewritten test ends the session by a request the browser sends no tab a signal for: `headerLogout.endSessionWithNoSignal()` posts to the logout endpoint through `page.request`, which shares the context's cookies and takes the cleared ones from the answer, as a sign-out made by a server load in another tab does.
6. **The Contestant App's half, measured, not assumed.** The diagnosis drove six client navigations after a session ended elsewhere: those that make a request are redirected to the login page by the gate, and none reaches the 503. A committed test now holds one such navigation. It holds at HEAD by design, so its red is a production mutation in Task 3, with the gate's no-session redirect skipped and `signOutToLogin` answering 503 unconditionally.
7. **What no request reaches.** A navigation that makes no request and runs no load still shows the stale page, in both apps. Plan 60's `SIGNED_OUT` listener covers it for every sign-out the browser makes. A sign-out made only by a server, in another tab, sends no browser signal; that residue goes on plan 66's list.
