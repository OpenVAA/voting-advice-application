## Warnings

### WR-01: A count orphaned by a closed tab signs out a session signed in after an explicit sign-out elsewhere

**File:** `apps/frontend/src/lib/auth/logoutDeadline.ts:115-122`, `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:113-122`, `apps/frontend/src/hooks.server.ts:94-106`

**Issue:** `logoutDeadlineHandle` signs out whatever session a `'runOut'` request carries. It has no tie to the session that was live when the count opened. Only the document that wrote a count can withdraw it (`clearLogoutDeadline` returns early when `ownCountId` is unset). No other sign-out touches the cookies. That covers the immediate Log out in another tab, the Admin App's Log out, `ROUTE.AuthLogout` and `signOutToLogin`. Traced sequence:

1. Tab A opens the modal at time T and writes `pending=X` and a `deadline=X` that expires at T+40 s. Tab A is then closed.
2. In tab B, which has nothing left to do, the user presses Log out. `leave()` runs, and its `clearLogoutDeadline()` does nothing, because tab B has no `ownCountId`. The `__data.json` of the login page carries `'counting'`, so the hook does nothing.
3. Before T+40 s the user, or the next user of a shared device, signs in. The request carries `'counting'`, so the session is created normally.
4. At T+40 s the browser drops `logout-deadline`. The next request is `'runOut'`, and the hook signs out the **new** session. The user is sent to the login page with no message. The `passed` settlement then discards the drafts made in that new session.

The window is short, from the explicit sign-out to T+40 s. Still, this is a sign-in that does not keep its session, which is the property the gap was opened for. The guide's "a sign-in after it keeps its session" covers only sign-ins after the hook's own sign-out.

**Fix:** End a count when the session it was meant to end is gone. Any sign-out or sign-in the application makes should withdraw every count, whoever wrote it. Export a `withdrawAnyCount()`, the current private `withdrawEveryCount()`. Call it from the contestant and admin `logout` flows before their sign-out request. Expire both names on the server in the sign-in actions and the OIDC callback before the session is set. Doing the last in one helper the actions share would leave `hooks.server.ts` untouched, as PROH-179.1-38 requires. Add a unit case: a document that did not write the count signs out and then finds no count. Add an E2E step: close the count's tab, Log out at once in a second tab, sign in again, let the deadline drop, and the session stays.

### WR-02: A copy planted for the host's own domain is never removed, so on an apex deployment a planted cookie signs the browser out over and over and discards the drafts at every navigation

**File:** `apps/frontend/src/lib/auth/logoutDeadline.ts:88-94`, `:196-202`, `apps/frontend/src/hooks.server.ts:107-113`, `apps/docs/src/routes/(content)/developers-guide/backend/authentication/+page.md:183`

**Issue:** Removals cover the host-only copy and `parentDomainsOf(hostname)`, which lists only the host's **proper** parents. A cookie set with `Domain=<the host itself>` is a domain cookie, stored apart from the host-only copy of the same name, and nothing removes it. Any subdomain of the host can set one: for an application served at the apex `example.org`, that is every `*.example.org`. `parentDomainsOf('example.org')` returns `[]`. Consequences:

- **A planted `logout-pending=<32 hex>` with `Domain=example.org`:** the browser's next request is `'runOut'`. The hook signs out and writes a host-only `passed`. The page's settlement discards the drafts and expires the host-only copy, but not the planted one. The request after that is `'runOut'` again. The browser is signed out at every other navigation that reaches the server, and its drafts are discarded each time, as long as the planted cookie lives. That is CR-01's lockout back again, on that deployment shape.
- **A planted `passed`:** the page discards the drafts at every navigation, and every real count is ignored as `'settled'`.
- **A planted second id:** the hook logs a `warn` on every request (`hooks.server.ts:108`) and never clears it.

The auth page states that such a cookie "costs that browser at most one sign-out … every removal … expires the parent domains' copies". That statement is false for an apex host and for any host with child subdomains. The unit test `parentDomainsOf … names none for example.org` (`logoutDeadline.test.ts:127`) pins exactly the gap.

**Fix:** Include the host itself, when it is a domain name, in every removal, on the page and on the server:

```ts
export function removalDomainsOf(hostname: string): Array<string> {
  if (hostname.includes(':') || IPV4_ADDRESS.test(hostname) || !hostname.includes('.')) return [];
  return [hostname, ...parentDomainsOf(hostname)];
}
```

Use it in `expireEveryCopy` and in the hook's `duplicated` loop. Correct the auth page's sentence, and add unit cases for `example.org` and for a server request to an apex host.

### IN-01: The tab record names a tab's `sessionStorage`, not the document that holds the modal

**File:** `apps/frontend/src/lib/auth/logoutDeadline.ts:144-147`, `:17-19`

**Issue:** A `'document'` settlement removes a running count when `id === readTabRecord()` and `id !== ownCountId`. That treats every new document of the tab as "the reload that closed the modal". Two cases break this:

- **Duplicate Tab.** It copies `sessionStorage`, and so does a `window.open` with an opener. The copy withdraws the count that the original tab's modal is still running.
- **A full-load navigation of the same tab while the modal is open,** for example a typed URL or a bookmark into the app. It withdraws the count, but the old document stays in the back-forward cache with its modal counting. Its `ownCountId` still holds X, so after Back the restored page keeps counting with no cookie.

In both cases, closing the counting tab afterwards ends nothing on the server. These are narrow, but they reopen the WR-03 hole for those paths, and neither is in the UAT list.

**Fix:** On `pagehide`, write a "this document left with its modal open" flag into the record, together with the id. On `pageshow` with `persisted`, clear it. Let a fresh document withdraw the count only when that flag is set and the document's navigation type is `reload`, using `performance.getEntriesByType('navigation')[0].type`. At least, state the duplicate-tab case in the guide.

### IN-02: Any `logout-deadline` value keeps every count running, whatever id it holds

**File:** `apps/frontend/src/lib/auth/logoutDeadline.ts:76-79`

**Issue:** `logoutDeadlineState` answers `'counting'` when `deadlineValues.length > 0`. It never checks that a deadline value equals the pending id, and it never counts deadline copies. A `logout-deadline` planted for a parent domain with a long `Max-Age` turns off the closed-tab sign-out for that browser, silently and for every later count. It is not a "duplicate" either, so nothing ever removes it. The cookie module's docblock says the deadline is "the same id".

**Fix:** Answer `'counting'` only when `deadlineValues.includes(id)`. Treat a deadline value that names another id, or more than one distinct deadline value, as `'duplicated'`.

### IN-03: The drafts are discarded under live draft handles when the settled marker is met by a restored page or by a navigation that does not reach the server

**File:** `apps/frontend/src/routes/+layout.svelte:172`, `:210-214`, `apps/frontend/src/lib/contexts/contestant/contestantDrafts.ts:11`

**Issue:** The layout comment says "the navigation that follows a sign-out unmounts the entity layout, which drops its draft handles first". `discardContestantDrafts` depends on that: a handle in the same document "stores it again on its next edit". There are two cases where the handles are still live:

- A `'settled'` met on a `pageshow` restore of an entity page.
- A client-side navigation inside the entity layout that makes no server request. Here the marker came from an earlier non-navigation request, for example a preload or an API fetch.

In both cases the drafts are removed while the handles live, and the next edit writes them back after the session has ended.

**Fix:** In the `'settled'` branch, also call the contestant context's reset when it is mounted, through a registered callback. Or make `discardContestantDrafts` notify the handles in the same document, for example with a `BroadcastChannel` or an in-process event that `persistedState` follows.

### IN-04: The page's removal of parent-domain copies is untested, and the server's removal differs from its write

**File:** `apps/frontend/src/lib/auth/logoutDeadline.test.ts:170-186`, `:208-222`, `apps/frontend/src/hooks.server.ts:110-111`

**Issue:**

- Every page-side test runs on jsdom's `localhost`, where `parentDomainsOf` returns `[]`. Removing the inner `Domain=` loop of `expireEveryCopy` would pass the whole suite. Only the server's loop is pinned (`hooks.server.test.ts`, the four `delete` calls).
- The server's `event.cookies.delete(name, { path: '/' … })` takes SvelteKit's defaults, `httpOnly: true` and `secure: true` everywhere except on `http://localhost`. The `passed` write passes `secure: event.url.protocol === 'https:'` instead. On an `http:` host other than `localhost`, the browser refuses the `Secure` removal and the duplicate is never cleared.

**Fix:** Run one `describe` under `// @vitest-environment-options {"url":"https://app.example.org/"}`, or stub `location`, and assert the `Domain=example.org` writes. Pass `secure: event.url.protocol === 'https:'` and `httpOnly: false` to the deletes, as the set does.

### IN-05: The hook test drives `handle` through SvelteKit's private request store

**File:** `apps/frontend/src/hooks.server.test.ts:46-52`

**Issue:** The test imports `with_request_store` from `@sveltejs/kit/internal/server` and fakes the store's private `state.tracing.record_span` shape. Neither is public API. A SvelteKit patch release that renames either one fails the file for a reason unrelated to the hook. The rest of the tree's `yarn up` flow would see that as a red unit gate.

**Fix:** Export `logoutDeadlineHandle` (for example as `export const __test = { logoutDeadlineHandle }`, or from a small `$lib/server/logoutDeadlineHandle.ts` that `hooks.server.ts` imports). Test it directly, with a `resolve` stub. Keep one ordering assertion on the `sequence` line by source match, as PROH-179.1-38 is already checked.

### IN-06: The E2E fixture copies the grace and the id shape from the module

**File:** `tests/tests/fixtures/shared/headerLogout.fixture.ts:79`, `:82`

**Issue:** `LOGOUT_DEADLINE_GRACE_SECONDS = 10` and `COUNT_ID` repeat `logoutDeadline.ts:6` and `:33`. A shorter grace in the module would still pass `expectLogoutDeadlineSet`'s upper bound, so the copy can drift silently.
