## Rulings carried by this plan

1. **The operator's ruling 2, in their words first:** "let's add the error msg". `AuthContext.logout` stops swallowing the failure and reports it to `#logout`. On a failure, including at the end of a count: an error message is shown to the user, no reset, no navigation, and the edits stay.
   - **Where this limits ruling 1, which the operator reads first (`T-179.1-104`).** Ruling 1's purpose is that nothing is left on a shared computer. If the sign-out fails at the count's end, this ruling keeps the edits: a user who walked away stays signed in, their draft stays in storage, and the message is on the screen for whoever comes next. Nothing retries by itself. Both rulings are honoured as written, and this is what they leave together, so the summaries of this plan and plan 46 open with it and the UAT list holds it.

2. **The three rows of `179.1-CR01-SECURITY.md`'s table, read against the code at `98e212aee`.** The reading is of `_signOut` in `@supabase/auth-js` 2.117.2, `createSupabaseCookieAdapter` in `$lib/supabase/server.ts`, `routes/api/auth/logout/+server.ts`, `_logout` in `supabaseDataWriter.ts` and `appGateHandle` in `hooks.server.ts`. The cookie results of the last two rows are the audit's measurement; what the screen shows after this plan is read from the code, and tests 8 and 10 drive the browser's half.

   | What failed | Cookies after the `POST` | Before this plan | After this plan, on screen | Is the message true? |
   |---|---|---|---|---|
   | **Row 1:** the endpoint's answer, with the auth service up | kept | the home, Log out in the header, the edit gone, nothing said | the same page, Log out in the header, the edit there, the message | **Yes.** The user is still logged in, and "may still be logged in" says no more than that. A second press signs out once the endpoint answers. |
   | **Row 2:** the auth service, with the access token valid | **cleared**: `_signOut` calls `removeCurrentSession()` before it returns the error, `setAll` writes the removal to `event.cookies`, and SvelteKit sends those on the 502 too | the login screen; signed out here, not revoked on the service | the same page. **`page.data.session` still holds the last load's value, so the header still shows Log out and the page still reads as signed in**, with the edit and the message | **Yes, and this is the row the wording was written for.** This browser no longer holds the session, and the sentence does not say it does: it says the logout could not be confirmed and that the user may still be logged in. If it ever threw, the message would appear for a user who is in fact signed out, and "may still be" stays true. A `POST` that never answers shows neither the message nor a departure; it stays in `deferred-items.md`, through plan 46.

3. **One message for the Contestant App, shown from one place.** `#logout` holds a reactive `#logoutFailed`, and `routes/contestant/+layout.svelte` renders `Alert` while it is true. The alternative was a message in `LogoutButton` and in each of the three gates, which would repeat the markup and its state four times. `popupQueue` was rejected because it has no way to withdraw an item, so a popup could outlive the failure and say "could not confirm" over a logout that has since succeeded. Here the next attempt clears it. `Alert` is `fixed` and has `role="alert"` when it has no `actions`, and it closes by its own button. Its `title` is `common.logout`.

6. **The two comments the audit calls wrong.** In `routes/api/auth/logout/+server.ts`, the sentence that says the auth client "removes no session" becomes: on a failed sign-out the auth client may or may not have removed the session (it does when the auth service's answer is what failed, and not when the session could not be read to begin with), so a caller must not take the user for signed out. In `supabaseDataWriter.ts`, the sentence that says the user "stays signed in on both sides" becomes: whether the cookies still hold the session depends on what failed, so the failure is thrown for the caller to report. **Reported, not changed:** the sentences beside them say the cookies are httpOnly, which `createSupabaseCookieAdapter`'s `httpOnly: false` contradicts. Plan 46 records this in `deferred-items.md`.

7. **Tests that pinned the old behaviour.** `AuthContextProvider`'s suite has no case pinning the swallow. None of the gates' cases changes. Test 5 of plan 44 and the others do not touch a failure. So this plan adds, and rewrites nothing.

8. **How the failure is driven.** `page.route` on the endpoint, in the fixture. Row 1 fulfils 502 without reaching the server, so the cookies are kept. Row 2 uses `route.fetch()` and then fulfils with that response at status 502. The real sign-out runs, so its `Set-Cookie` clears the cookies, and the page sees the failure. That the fetch applies the cookies to the context is **inferred** from Playwright's docs on the context's request; `expectSignedOut` in test 10 reads it, and a red there stops the task with a report. Row 3 cannot be driven in a browser without an auth outage. **Its browser half is row 1's**, and what differs is the server's answer to a later load, which the audit measured.

9. **Sign-ins.** Three more password sign-ins in this spec, thirteen in all, below the auth service's thirty in five minutes from one origin. A refusal for that reason is a stop with a report.

10. **The visual project is not run.** Checked as the rules state: the message renders only after a failed sign-out, and no baseline fails one. The layout's closed branch paints nothing. Task 3's verify pins that the spec does not name it.

11. **The UI safety gate.** No UI-SPEC, by the orchestrator's decision, because this reuses `Alert`. **The message is new visible copy, and it goes to the operator's UAT list in plan 46's summary, with its place on the page, which covers the bottom of the screen until closed.**
