## Rulings carried by this plan

1. **The helper (A5, then A2).** The signature is `signOutToLogin(event: Pick<RequestEvent, 'cookies' | 'request' | 'url' | 'locals'>, locale: string, code: ContestantLoginError): Promise<never>`. The order inside:
   - the sign-out on `event.locals.supabase` with scope `local`, its two failure forms caught as now;
   - on a failure, the log line, then `isSessionGone(event.locals.supabase)`: a session left, or no answer, throws the 503 with `error.default`, and nothing has been withdrawn;
   - only then `withdrawLogoutCount(event)`;
   - then the 307 to the login page with `errorMessage` set to the code.

   So a sign-out that worked, and a failed one that left no session, withdraw in the same response that redirects. The TSDoc says when the count is withdrawn and why: the 503 path keeps it, so the hook's next request tries again. It also says why one parameter: the sign-out and the withdrawal must act on one request.
2. **The caller.** The protected layout load's two sign-outs become `return await signOutToLogin(event, lang, 'loginFailed');`. Its docblock's sentence on the helper says the count is withdrawn after the sign-out has worked or found the session gone, reading of the URL only its host and protocol, which SvelteKit does not track. The load reads no other `url` property (CLAUDE.md § Results Navigation Invariants). The ESLint allowlist's comment for the helper's file stays true and is not edited (rule 8).
3. **The callback.** `withdrawLogoutCount(event)` leaves `GET`'s first line. `register` calls `withdrawLogoutCount` right after the `try` block whose `verifyOtp` set the session, and before the arrival marker is set. It is given what the helper reads, `request` and `url` beside the `cookies` it already has. Every return before that point leaves both cookies: the provider's error or cancel, a missing code, a refused state or verifier, a rejected token, a refused or failed registration, and a failed `verifyOtp`. The route's docblock loses its sentence beginning `Before anything else the callback withdraws`, and its step 7 gains the withdrawal. The test file's header sentence says the same.
4. **`logoutCount.ts`.** Its docblock's clause beginning `as every sign-in the server makes does` becomes true of every call site the executor lists with `git grep -n -E "^[[:space:]]+withdrawLogoutCount\(" -- apps/frontend/src`. At planning there are seven: four sign-in actions withdraw before they sign in; the logout endpoint withdraws before its sign-out, deliberately; and after this plan the helper and the callback withdraw once the outcome is known. Its code does not change.
5. **The tracer's end-to-end check is the load.** No E2E test drives a failed sign-out of the protected load: `git grep -n -E "loginFailed|failUserDataRead" -- tests/tests/specs` names only the Admin App's spec. `layout.server.test.ts` drives the real load through the real helper and the real `withdrawLogoutCount`, with only the writer and the request's client faked, so it is the slice from the load to the response's cookies. Its fake event gains `cookies.delete` and a `Cookie` header that carries one count, and its fake client gains `getSession`; the existing cases keep their behaviour.
6. **The browser proof** (rule 10). The change serves every protected page of the Contestant App and the identity provider's flow, whose project runs behind the whole perm chain. So the targeted run is `perm-closed-project`, with `contestant-identity-provider` named by `--expect-project`. The plan adds and rewrites no E2E test, and its deltas are none.
