### Critical Issues

#### CR-01: Log out on a page with unsaved edits signs out first, so Cancel at the prompt loses the edits and strands the page

**File:** `apps/frontend/src/lib/contexts/contestant/contestantContext.svelte.ts:566-569`, reached from `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:78,83` and exposed by `apps/frontend/src/lib/layouts/main/Banner.svelte:49-51`

**Issue:** `#logout` ends the session, then navigates, then resets:

```ts
await this.#authLogout();
return goto(this.#getRoute.current('ContestantAppLogin'), { invalidateAll: true }).then(this.#reset);
```

The profile page (`profile/+page.svelte:346`), the question page (`questions/[questionId]/+page.svelte:304`) and the nominations details page (`nominations/(edit)/details/+page.svelte:594`) each mount `PreventNavigation`. Its `beforeNavigate` runs inside that `goto`, after the sign-out, and asks the user with `window.confirm` (`PreventNavigation.svelte:31-40`).

If the user presses Cancel to keep their edits:

1. The session is already gone: `_logout` has POSTed to the logout endpoint and cleared the cookies (`supabaseDataWriter.ts:451-462`).
2. A cancelled `goto` resolves rather than rejects. `navigate` returns at `node_modules/@sveltejs/kit/src/runtime/client/client.js:1743-1747`, and `_goto` awaits it at line 548. So `.then(this.#reset)` runs anyway.
3. `#reset` calls `userData.reset()`, which clears the saved data, the staged edits and the draft, and deletes the persisted drafts from `localStorage` (`contestantUserDataState.svelte.ts:335-344`). The edits the user just chose to keep are gone.
4. `force_invalidation` is set only in `accept` (`client.js:557-559`), which does not run for a blocked navigation. `page.data.session` therefore stays set, and the page goes on looking signed in, with Log out still in the header.
5. The next edit throws, because `#savedData` and `#draft` are now undefined: `Cannot set a property before user data is loaded` (`contestantUserDataState.svelte.ts:239`) or `Cannot set an answer before user data is loaded` (`:353`). A save would go out with no session.

**Reach:** the direct path is `LogoutButton.svelte:78`, when no counted task is incomplete. The modal's Log out and its countdown both go through `:83`. On the countdown path a user who has walked away has been signed out before the prompt appears.

**Why it is new here:** at the base commit the header tested `page.data.token`, which nothing in `apps/frontend/src` provides any more, so the button never rendered. `9db8b555d` fixed that correctly. The other `LogoutButton` sites (the entity root page, `NothingToEdit`, `ReadFailure`) mount no `PreventNavigation`. No spec or unit test presses Log out with an unsaved edit.

**Confirmed by:** reading every step above, including the SvelteKit source. Not run in a browser.

**Fix:** ask before anything is ended, and reset only if the browser actually left. One shape:

```ts
#logout = async (): Promise<void> => {
  // Ask every active PreventNavigation first; a refusal leaves the session and the edits as they are.
  if (!this.#navigationGuards.confirmLeave()) return;
  await this.#authLogout();
  this.#navigationGuards.bypassOnce();
  await goto(this.#getRoute.current('ContestantAppLogin'), { invalidateAll: true });
  this.#reset();
};
```

`PreventNavigation` would register its `active` and `onConfirm` with that registry, so the user is asked once. Add a red-first spec on the profile page: stage an edit, press Log out, dismiss the prompt, then assert the user is still signed in and the edit is still there.

### Warnings

#### WR-01: The password kind, once revealed, is an ordinary text field for spellcheck and mobile keyboards

**File:** `apps/frontend/src/lib/components/input/Input.svelte:727-736`

**Issue:** the toggle turns the control into `type="text"`, and it carries no `spellcheck`, `autocapitalize` or `autocorrect`. No password caller passes them either (`PasswordSignIn.svelte:111-123`, `PasswordSetter.svelte:167-196`, `admin/login/+page.svelte:121-130`). The file's own colour kind sets the first two (`Input.svelte:683-684`), and `RegistrationCodeField.svelte:91` sets `autocorrect="off"`.

While revealed, a browser's cloud spellcheck can receive the password, and a phone keyboard can capitalise or correct what is being typed, so the stored password differs from the one the user meant. `PasswordField` had the same gap, but this is now the one shared control and the right place to close it. The markup is confirmed; the browser effects are known platform behaviour and were not exercised.

**Fix:**

```svelte
<input
  ...
  spellcheck="false"
  autocapitalize="off"
  autocorrect="off"
  {...concatClass(restProps, inputClass)} />
```

Add a case to `Input.password.svelte.test.ts`.

#### WR-02: After the Trash, choosing the same file again does nothing

**File:** `apps/frontend/src/lib/components/input/parts/ImagePart.svelte:99-109`, with `Input.svelte:370-390` and `profile/+page.svelte:227-233`

**Issue:** the hidden file input keeps its selection, because nothing clears its value after a file is read or after the image is removed. A user who picks a file, presses Trash and picks the same file again gets no `change` event, so nothing happens and no message appears. This affects a file chosen during the same mount. An image that was already stored can be replaced by any file. The missing reset is confirmed by reading; the missing event is the platform's rule and was not run. The old Remove button had the same gap.

**Fix:** clear the input before opening the dialog, so that the choice always registers:

```ts
function openFileDialog(): void {
  if (fileInput) fileInput.value = '';
  fileInput?.click();
}
```

Use it for both `onclick` and `handleFileInputLabelKeydown`.

#### WR-03: A revealed password is never masked again, even after `reset()` or when the control is disabled

**File:** `apps/frontend/src/lib/components/input/Input.svelte:447,730,744`, `apps/frontend/src/lib/contestant/components/passwordSetter/PasswordSetter.svelte:97-102`, `apps/frontend/src/routes/contestant/(protected)/settings/+page.svelte:80`

**Issue:** `passwordRevealed` has one writer, the toggle.

- **`reset()`:** on the settings page a saved password calls `reset()`, which empties the fields but leaves them revealed, so the next password typed there shows in clear. `PasswordField` behaved the same way.
- **`disabled`:** this is new. The toggle is disabled along with the control, so an input that is disabled or locked while revealed shows the password with no way to hide it. No current caller disables a password field, so this one is latent. The unit test at `Input.password.svelte.test.ts:147` checks the disabled state only while masked.

**Fix:** mask whenever the control is disabled, for example `type={passwordRevealed && !isDisabled ? 'text' : 'password'}`. Also export a `conceal()` function on `Input` for `PasswordSetter.reset()` to call on both fields.

#### WR-04: The E2E step "past the count, the user is still signed in" cannot fail

**File:** `tests/tests/specs/contestant/contestant-entity-selection.spec.ts:329-333`

**Issue:** `advancePastModalCount` fires the timer, and the two assertions then read a page that has not yet changed. A logout started by that timer has to POST to the logout endpoint and then navigate, while `expectOnHome` and `expectShown` pass on their first poll. So a live countdown would pass this step (inferred from the ordering, not run).

Ledger row 33-5 shows that the red control stopped earlier, at `expectDialogClosed`, so this step has never been seen red. The behaviour itself is pinned correctly by the unit test at `LogoutButton.svelte.test.ts:265-277`, so what is wrong here is the spec's claim, not the product.

**Fix:** record requests to the logout route from before the fast-forward, and assert that there were none after a round trip the page must finish, such as a navigation inside the app. Otherwise delete the step and let the unit test carry it.

### Info

#### IN-01: `handleLogout` still closes the modal twice, the fault the new comment warns about

**File:** `apps/frontend/src/lib/contestant/components/logoutButton/LogoutButton.svelte:61-64,82-85`, `apps/frontend/src/lib/components/modal/timed/TimedModal.svelte:130-131`, `apps/frontend/src/lib/components/modal/ModalContainer.svelte:98-103`

**Issue:** `ModalContainer.handleClose` is not idempotent, and `modalOpen` works around that at one call site. On the countdown path `TimedModal` closes the modal, then `handleLogout` closes it again. With a successful logout the button is unmounted and this does not matter. If the sign-out fails and the button stays mounted, a second close after the transition has ended loses the `hidden` class. The visible effect is UNCONFIRMED, since a closed `<dialog>` may show nothing anyway.

**Fix:** add `if (!isOpen) return;` to `handleClose`, then remove `modalOpen` and its comment.
