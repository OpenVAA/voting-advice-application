# Phase 179.1 — Execution Rules

> Read once by every executor of a Phase 179.1 plan, before its first task. Each plan names this file in its
> `<context>`. A plan's own blocks add to these rules and never relax them. Where a plan and this file
> disagree, stop and report.

**A hook line of the form `CONTEXT WARNING NN%` in a tool's output belongs to the orchestrator. Ignore it and
keep working; it is never a reason to stop, to shorten a task or to hand a plan back unstarted.**

## When this phase runs

Phase 179.1 executes after Phase 179 and after its UAT (`/gsd-verify-work 179`, CONTEXT D-03): `179-UAT.md` is
tracked with `status: diagnosed` and fourteen gaps marked `folds_into: 179.1`. Plan 179.1-01 checks that and stops
with a report when it is not so.

**The frozen baseline holds.** `apps/supabase/supabase/migrations.manifest.json` lists `00001_initial_schema.sql`
first, and nine appended migrations (`00002_…` to `00010_…`) after it. **No plan regenerates, edits or re-hashes a
listed migration.** Every schema change of this phase is an appended migration (`00011_…` onward, CONTEXT D-02).

The plans were written on 2026-10-25 against the tree at `ac717ac40` (outside `.planning/`: `63166445d`). Every
path and symbol in a plan is a hint, resolved by the symbol or the quoted content given and **never by a line
number**; every population (the docs stubs, the specs that open a mailed link, the `max-w-md` sites, the policy
call sites) is derived again by the command the plan gives when it runs.

**No SPEC.md exists for this phase** (the spec-less probe fallback was skipped: the phase has no requirement ids
to probe). The must-haves are derived from the CONTEXT decisions D-01..D-30 and from the `missing` lists of the
UAT gaps G-179-1, -2, -5 … -16.

### The order of the plans (item PL-01)

Thirty-two plans in thirty-two serial waves. No two plans run at once: the stack is shared, and
`migrations.manifest.json`, `packages/supabase-types/src/database.ts`, `apps/frontend/messages/*/*.json`,
`apps/frontend/src/lib/types/generated/translationKey.ts`, the `07-rpc-security` census and the negative-control
ledger are written by many plans.

1. **The instruments (01).** The drivers, the baseline, the ledger and the RLS cost baseline of D-12.
2. **The schema block (02–10)**, one appended migration per item (two for B2), in this order: A1, B3's bulk link
   step, B3's trigger rule with D5, B2's database half, B2's frontend half, A7, B4's function, B4's Edge half with
   G-179-5, G-179-12. B2 precedes G-179-10's card actions; A7's "before" is measured on the tree it changes.
3. **The confirm page (11–14).** The page first, reached by nothing; then the callback hands every token link to it
   and every spec presses its button; then the mails link to it; then G-179-6's banner, set by the page's action.
   At no commit is a mailed link unverifiable.
4. **Contestant App behaviour (15–16)**: C4 with D-25, then C5.
5. **The UAT's interface gaps (17–26)**, after C5 because the settings page is a consumer of the email-sent
   components and the home's email task links to it.
6. **The identity provider's round trip and the harness (27)**: G-179-15, E4 and E5's void-run stop.
7. **Small items and records (28–30).**
8. **E4's CI observation (31)**, the one plan with a human action, placed last but one so the phase runs alone as
   long as it can.
9. **The close (32)**: the generated component docs, every gate, one full run, the ledger closed.

## The standard cycles

Plans name these cycles instead of restating them.

### The schema cycle (every schema item, D-02)

1. `Skill("database")` is loaded first.
2. **Red.** The new pgTAP assertions, with their file's `plan(N)` raised, are committed alone, before the schema that
   turns them green: `yarn workspace @openvaa/supabase test:db` in the background, its log, status and head kept as
   `$U/<plan>-pgtap-red-<n>.{log,exit,head}`, red in the named files only.
3. **The change.** The edit of the `$S/schema/` file that owns the concern; the same change as a new migration
   `$S/migrations/<next>_<name>.sql`, where `<next>` is the five-digit number after the highest in the manifest; a
   function re-created by a migration has the same body text, comments included, as in `schema/`; that migration's
   line, with its `shasum -a 256`, appended to the manifest's `migrations` list. `yarn assert:schema-migration-parity`
   exits 0.
4. **Applied** (the [BLOCKING] schema push: nothing is deployed, so the push is local): in the background,
   `yarn check:schema-equivalence` (exit 0, `EQUAL`); then `yarn db:reset`; then `yarn db:types` on the freshly reset
   database; then `yarn db:lint:sql`; then `yarn workspace @openvaa/supabase test:db`, green in every file. Build and
   type checks are not evidence that the schema was applied.
5. **One commit** of the schema file, the migration, the manifest, the regenerated types and any census or skill
   line, subject `feat[db](179.1-NN): …`.
6. The ledger row of each new assertion names the red log and its first failing line.

### The unit cycle

A new or rewritten vitest case is committed red and alone (`test(179.1-NN): …, as failing cases`), its run's log,
status and head kept as `$U/<plan>-unit-red-<n>.{log,exit,head}`; then the change turns it green in the next
commit. A case whose red cannot be shown by a revert (a pin of an order, say) is shown red with its expectation
inverted, and the ledger says so.

### The browser cycle

- **No red E2E test is ever committed, and no commit turns a committed test red.** A change a browser can observe —
  a page, a layout, a load, a component a page renders, the callback, a function the suite calls, the wrapper — stays
  in the working tree until a run of that uncommitted tree has passed, and is committed together with the spec and
  fixture changes that depend on it, in one commit. What may be committed before it: a unit or component test, red
  and alone; a module that decides nothing yet; a component nothing renders; a route nothing links to; catalogue keys
  no screen reads; a SQL function nothing calls.
- **A new E2E test is shown red first** (D-04): the spec and fixture change alone, uncommitted, run with
  `tests/scripts/e2e-run.sh --run-dir $R/<plan>-red[-n] --no-db-reset --project <project>`, then
  `node tests/scripts/e2e-evidence.mjs $R/<plan>-red`, judged with
  `node $P/179.1-verdict.mjs control <plan>-red --project <project> --setup <its setup project> --dirty-only <path>… --red "<title substring>"`.
  It counts only when exactly the named tests are red, each ended `failed` on an expectation — not on a timeout,
  not on a compile error — and every other test of the run passed.
- **The held change is then proven** with the product change added: a one-project control `--green --were-red-in <plan>-red`
  or, where the change reaches every stored session (the callback, the mails, the wrapper), a full control
  `--full --same-projects-as <predecessor> --except … --green`. Then the one commit.
- Each plan says, under *What this plan's commits do to committed specs*, which commit is the one.
- **The `--setup` project a plan names for a one-project control is the planner's reading** of
  `tests/playwright.config.ts`. The executor reads the project's `dependencies` there and uses the setup project it
  names; a difference is recorded in the summary, never a reason to change the project's wiring.

### The close of a plan

Every plan that changes a surface a browser can observe, a dataset, the schema, a function or the harness closes on
a full default run of its own committed tree: `bash $P/179.1-e2e.sh <plan>-close`, judged with
`node $P/179.1-verdict.mjs e2e <plan>-close --same-projects-as <its predecessor's close label, or $(cat $P/179.1-BASELINE) for 179.1-02> [--except <project>=<delta>]…`,
the deltas being the tests the plan adds, stated in the plan. A schema plan first runs the database rows on the
committed tree: `bash $P/179.1-gates.sh <plan>-db --rows db-reset,types-regen,types-clean,pgtap,sql-lint,integration`,
judged with `node $P/179.1-verdict.mjs gates <plan>-db --rows …`. After a reset: `yarn db:seed:default` at the end.
A plan whose predecessor did not close on a run (a records-only plan) names the last plan that did.

## The shell

- Begin every shell call that runs `yarn`, `npx` or `node` with
  `export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"`.
- A status is read from the command itself, **never through a pipe**. A commit follows a gate with `&&`, never `;`.
- No gate-set run, E2E run, schema-equivalence run or pgTAP run is made in the foreground: launch it in the shell
  tool's background mode as `( caffeinate -dimsu <command>; echo $? > <marker>.exit ) > <marker>.log 2>&1` and poll
  with one short foreground command per poll (a bounded loop of at most 45 one-second waits that ends when the
  `.exit` marker exists). Ceilings: 25 minutes for one full run (it restores the stack at its end), 20 for one gate
  set. A foreground long gate trips the executor's 600-second watchdog.
- Before a long run: `pmset -g batt`. No run is started on battery below 30 %.
- An `<automated>` block is run from a script file taken byte for byte from the plan (`$U/<plan>-t<N>-verify.sh`)
  with `bash`, never pasted into the login shell; its log, exit status and head are kept beside it. A block that
  holds a long gate is launched in the background and polled.
- `.env` is never read, listed or tested for (memory: a refused read is never worked around); the template is
  `.env.example`.

- The edge runtime runs `policy = "per_worker"`: a function edit is judged by the default runtime only after a
  restart; the wrapper's own function server serves the tree during a run.
- `yarn test:unit` needs the stack up (the dev-seed integration reads `SUPABASE_URL`).
- Nothing is deployed: PostgreSQL 17, no compatibility shim, no migration of stored data, no clean-up of duplicates.
- The local database is reached for measurement as `docker exec -i supabase_db_openvaa-local psql -U postgres -d postgres -v ON_ERROR_STOP=1`,
  the script on standard input; no connection string with a password is written anywhere.

## E2E

- Runs go through `tests/scripts/e2e-run.sh` only (directly for a control, through `179.1-e2e.sh` for a committed
  tree). A dev server is started by the wrapper and by nothing else.
- **Void** is decided by the wrapper's marker alone: status 8 with `VOID-host-suspend.txt`. A void run is kept and
  made again under the next `-rN` suffix. A red run without the marker is a failure; with no other cause,
  `pmset -g log` is read before the tree is blamed. A did-not-run is a failure. Nothing is retried until green on an
  unchanged tree; no test is skipped or annotated to pass. Nothing under `tests/e2e-runs/` is deleted.
- **No spec waits a fixed time** (the CI runner is about four times slower). A count is never waited out: the page's
  clock is advanced, and a mail slot is given back through the existing release step before a press that must send.
- A spec holds hard assertions only and no locator in a test body: every locator is in a fixture and every id comes
  from `$T/utils/testIds.ts`. A message is read from its catalogue file, never copied. A mailed link is opened **as
  received**: only its scheme, host and port are replaced by the run's origin (`$T/utils/mailedLink.ts`); from plan 12
  on it is opened through `openMailedLink`.
- No expectation takes an address's existence, a link, a token, a `sub` or a claim value as its subject, and a "no
  mail" assertion is made only after the request's completion witness has finished.
- The auth service admits thirty sign-ins and thirty link verifications in five minutes from one origin; a spec that
  would pass that number says so and paces itself.

## An interrupted cycle

From the step that writes uncommitted changes until the step that commits them, the working tree holds exactly the
files that plan's `<uncommitted_changes>` block names, and a copy of each as the pre-commit run ran it is kept beside
the run (`$R/<label>.<file name>.kept`). The next executor either goes on from the working tree (or from the kept
copies) or discards the change with `git checkout -- <the named files>`, deletes the new ones and starts that task
again. The gate driver and the E2E driver refuse a tree with uncommitted changes outside `.planning/`.

## Code rules that bind every edit

- `CLAUDE.md` § *Context Destructuring Rule*: `appSettings`, `answersLocked`, `user`, `entities`, `selectedEntity`,
  `locale` and `dataRoot` are reactive accessors — read `contestantCtx.X` inside the tracking scope, never
  destructure; `dataRoot` is never bound to a read alias. `t`, `getRoute`, `logout`, `setPassword`, `setDataRoot` and
  the writer-backed functions are stable.
- `CLAUDE.md` § *Results Navigation Invariants*: no element added by this phase carries a `view-transition-name`, no
  `<dialog>` is added, and no layout load reads a `url` or `route` property; the tracked-read tests pass unchanged.
- Svelte warnings are fixed at their source; an accepted one carries `// svelte-warning: accepted — <reason>`.
- A string a user reads has a message key in all seven locales. A typed address is rendered as text, or HTML-escaped
  by `escapeHtml` before it reaches `sanitizeHtml`.
- New markup writes no numeric spacing class and no arbitrary value: `xs`, `sm`, `md`, `lg`, `xl`, `xxl` and `touch`
  only.
- WCAG 2.1 AA: every new interactive control has a name, a role and a visible focus; a disclosure carries
  `aria-expanded` and `aria-controls`.
- Strict TypeScript, no `any`; exported symbols carry TSDoc.
- `.agents/code-review-checklist.md` is walked in every plan that adds application code; each item's outcome is
  recorded in the summary.
