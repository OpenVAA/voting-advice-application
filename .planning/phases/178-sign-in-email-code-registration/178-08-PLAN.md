## Rulings and deviations carried by this plan

1. **The new keys are owned by one task; rewordings and removals are not** (item PL-17). The UI contract asks that one task own every new, reworded and removed key, because plans that edit one catalogue collide in a shared working tree. The waves here are serial, so nothing collides; a reworded sentence changes what an existing screen shows and lands with the plan that rebuilds that screen, and a removed key lands with its last reader (plan 178-23).
2. **The route key of the sign-in screen is `ContestantAppSignIn`** (the UI contract's, over the research's `ContestantAppLoginEmail`; item U-28). No route key is added here: a key and its directory land together.
3. **The sign-off's three rulings are built as written**: the count from settlement, the ten-second bound, the function that takes the settings, and one 65-second constant for the count and for "asked again too soon".
4. **`listedRegistrationModes` is not `isAnyRegistrationAllowed`** (item U-29, a departure from D-19 and REG-01 for one kind of matrix). The option that keeps the letter is located: this function's first condition.
5. **The recovery method replaces no method yet.** `requestForgotPasswordEmail` and `resetPassword` leave the writer and both contexts in plan 178-19, with the pages that call them.
6. **Plans 177 and 178 share no catalogue file but the generated key type**, which is regenerated here on the catalogues as Phase 177 left them.
7. **The catalogue edits and the logic edits are separate commits, and every task ends on a clean boundary** — a note on the plan's size: it lists some fifty files, thirty-five of them seven-locale catalogue files changed by one mechanical pass. That pass is Task 1's commit, with the regenerated key type; the logic is Tasks 2 and 3, each its own commit. The seven catalogues go in one commit, not locale by locale: the namespace gate and the translations test need one key set in all seven. Nothing is held across a task, no page renders a new key and no spec reads one, so the plan can be handed back after Task 1 or after Task 2 with the tree clean and the remaining tasks named.
