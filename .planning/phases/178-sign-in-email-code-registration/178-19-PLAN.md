## Rulings and deviations carried by this plan

1. **`requestForgotPasswordEmail` does not survive as a name** (item PL-13): the forgot-password page calls the context's `sendEntryLink` with the origin that selects the recovery method, and the auth context's wrapper is removed with `resetPassword`.
2. **The reset page gets a server load** (item PL-06, the research's question 12): the page is always reached by a full load — the callback's redirect — so the server can decide it, and a signed-out visitor sees no flash of the form.
3. **Probe row P1 decides one line of the callback.** With `P1: held` the callback is not edited: it verifies a link as its own type, and the recovery arm already claims before it lands. With `P1: not held` it verifies every link as `magiclink` and reads `type` for the landing alone; the callback and its test are edited only then.
4. **Probe row P4 decides how the reset page leaves after a save**, as it decided the gate's: with `P4: held`, a client-side navigation to the app root that reruns the loads; with the full-load fallback, the full page load the page makes today.
5. **FIX-01's case is a spec of its own, with a user of its own** (item PL-15), on the reserved candidate `test-e2e-base-ca-recovery`.
6. **A mail scanner that opens the link first is not built against** (item U-30 ★): the link is verified when opened, and a user whose link was spent lands on the login screen with its sentence. The confirmation page is filed by plan 178-23.
7. **The message keys this plan's pages stop reading stay in the catalogues until plan 178-23** (item PL-17).
8. **The recovery spec seeds its user and cleans up in its own hooks, not in a setup project with a teardown project** — the same departure from D-21's letter as the email spec's, named under item PL-14 and not an amendment of D-21: its user and everything under its prefix are removed before all, after each and after all, so a failed test leaves nothing for the next.
