## Rulings and deviations carried by this plan

1. **`EmailSentPanel` is two components and one rune class in one directory** (the context leaves the split to the planner). The page frame puts a screen's actions in a region of their own, so the body — the sentences, the address, the status region — is `EmailSentPanel`, the control — "Send again" and its line — is `EmailSentResend`, and the count both read is `ResendCountdown`, which the page creates once.
2. **The count runs from the settlement of the request** (sign-off ruling 1, over S7's "from arrival and from every press"): the state holds the time the request settled, and the count is computed from it, so it is right after the tab was in the background.
3. **The flow state is kept while E is shown** (item U-03 ★, a declared departure from D-02's letter; the research clears on leaving E and the UI contract, the later reading, does not). `clearEntryFlow` exists for the screens that end the flow by signing the user in.
4. **`sendEntryLink` is the only caller of the two link-request methods from a screen.** A page awaits it and navigates; it has no result to read. Which writer method it calls is decided by the request's origin.
5. **`newUserEmail` stays** until its last reader goes (plan 178-23). The flow state is added beside it in the same four places.
6. **Assumption carried, unresolved** (UI contract, *research · The count against the server's minute*): that 65 seconds from the request's settlement outlasts the server's 60-second slot, and that a page's clock can drive the count in a browser test. Neither was run. The first is harmless if wrong in one direction and is what plan 178-17's resend case shows in the other; the second is probed by plan 178-12.
