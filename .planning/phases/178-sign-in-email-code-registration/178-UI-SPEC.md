# Phase 178 — UI Design Contract

> Visual and interaction contract for the surfaces Phase 178 adds or reshapes in the Contestant app: the
> entry flow — the login screen (A), sign in with email (B), the registration-mode selector (C), entering
> and confirming an email (D1), the code-reuse sign-in (D2), "email sent" (E) — the set-password gate (F),
> forgot-password and password-reset on the same pieces, the shared components they are built from, and
> the copy that comes with them. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker. It is
> the sequel of `177-UI-SPEC.md` and `176-UI-SPEC.md` and follows their conventions; the same executors
> and verifier read all three.
>
> **This phase adds no design language.** SvelteKit 2 + Svelte 5 runes, Tailwind 4 + DaisyUI 5, Inter,
> theme colours in `packages/app-shared/src/settings/staticSettings.ts`. The token sections below
> **document the established contract** the surfaces obey; they introduce **no new token, font, spacing
> step, colour, icon or component library**. The load-bearing content is in *Surface Contracts*,
> *Copywriting Contract*, *Locator Contract*, *Axe Scan Entries*, *UI Considerations* and the closing
> *PROPOSED — Operator to Confirm*.
>
> **How to read the evidence marks.** `[tree]` = read on this worktree at HEAD `b8fc8ac12` on 2026-10-11.
> Phases 170–176 and 174.1 are executed on that tree; Phase 177 is planned and **not executed**, so
> nothing of it is on the tree; Phase 177.1, which `[CONTEXT D-21]` expects to run before this phase, has
> an empty directory and no `p_confirm_entity` in the schema. `[run]` = the output of a command run for
> this document — the component count, the four resolved versions, the key count of the seven catalogues,
> and the searches that derive a population or read a stylesheet — each quoted where it is used. **Nothing
> was rendered**: no dev server, no browser, no unit test and no E2E run stands behind any sentence here.
> `[CONTEXT D-nn]` = a locked decision of `178-CONTEXT.md`; `[CONTEXT J-n]` = one of its six items marked
> for operator review, **written here at the option the context proposes**; `[174-MAP]` =
> `174-NAME-MAP.md` § *The server contract for Phase 178* and § *Measurements*. `[RESEARCH …]` =
> `178-RESEARCH.md` (2026-10-11), named by its own section, pitfall or item; **none of its behavioural
> claims about the auth service was run on this tree** — it marks them UNCONFIRMED and leaves them to a
> first probe — and this document carries that status with each. `[computed]` = calculated from the theme
> tokens for this document. `[not read]` and `[not run]` = a fact this document could not establish; each
> is listed under *What reading could not establish*. `[U-nn]` = a rule proposed in this document —
> **PROPOSED — operator to confirm** — all listed together at the end. Code is cited by path and a
> content anchor (a symbol or a quoted line), never by line number. Names of symbols, routes, message
> keys and test ids this phase introduces are suggestions unless a `[CONTEXT]` mark fixes them; what they
> must do is the contract. Frontend paths are relative to `apps/frontend/src/` unless they start with
> `apps/`; `ENTRY/` abbreviates `routes/contestant/`. The letters A to F are the screens of
> `CAND-APP-PLAN.md`; G is the terms-of-use gate, H the profile selection, I the entity's home.
>
> **This run was non-interactive.** The first draft was written before `178-RESEARCH.md` existed; this is
> its revision, made after the checker read the draft against the context and the research, and after the
> research was read in full. Nothing the context records as settled is reopened. Every place where the
> context leaves a UI question open carries a `[U-nn]` mark and is written at that item's ★ option. **The
> items `[U-01]` to `[U-07]` and `[U-29]` decide the shape of the shared components, of every form and of
> what the entry screens offer**; the screens are not planned until they are read. **Six proposals depart
> from the text of a locked decision or requirement**, and each says so where it is made: `[U-03]`, from
> "cleared when the flow ends (the link is requested, …)" of `[CONTEXT D-02]`, because E's Resend has to
> repeat the request; `[U-05]`, from "always enabled" of `[CONTEXT D-09]` and "Continue stays enabled" of

> countdown" of `[CONTEXT D-11]`, by a margin of five seconds; `[U-20]`, from "not 'too soon'" of

`max-w-md` and `max-w-xl` are container widths (`--max-width-*`), not spacing, and `min-w-0` on C's
`fieldset` is a width too: a browser gives a `fieldset` the minimum width of its content, which would
widen the page at 320 px, and `177-UI-SPEC.md` writes the same class on its selector for the same

is written for them. The paragraph's 16px bottom margin is the base stylesheet's. Spacing inside a reused
component (`Button`, `PasswordValidator`, `ContactSupport`) is that component's and is not restyled.

### Shared premises

- **One route per screen, and nothing of the flow in the URL** `[CONTEXT D-02]`:

  | Screen | Directory | Route key | Title — `<h1>`, document title and route announcement |

  | B | `ENTRY/login/email/` | `ContestantAppSignIn` | "Sign in" |
  | C | `ENTRY/register/` | `ContestantAppRegister` (existing) | "Registration" |
  | D1 | `ENTRY/register/email/` | `ContestantAppRegisterEmail` | "Enter your email address" |
  | D2 | `ENTRY/register/sign-in/` | `ContestantAppRegisterSignIn` | "Sign in with your password" |
  | E | `ENTRY/email-sent/` | `ContestantAppEmailSent` | "Check your email" |
  | F | none — a gate view of `ENTRY/(protected)/` `[CONTEXT D-03]` | none | "Choose a password" |
  | — | `ENTRY/forgot-password/`, `ENTRY/password-reset/` | existing | "Forgot Password?", "Set a new password" |

  The new keys are suggestions `[U-28]` — the research proposes `ContestantAppLoginEmail` for B, and
  either name does — `ContestantAppSetPassword` leaves the map `[CONTEXT D-08]`, and no route takes or
  shadows `register/identity-provider` `[CONTEXT D-19]`. **No two screens share a title**: the route
  announcer is a live region, and a region whose text does not change announces nothing — which is why
  A's title is the app's name and not "Sign in", as it is today `[tree]`.
- **What is offered is one list, asked once** `[U-29]`. The modes C lists, in order: `identity_provider`
  where the matrix allows it **for candidates** `[CONTEXT D-20]`, `email` and `code` where it allows them
  for any served type `[CONTEXT D-10]`. One function over `contestantCtx.appSettings` returns that list;
  A's "Register", C, the menu and the server guard of `register/` read the same one, so they cannot
  disagree. While answers are locked the list is empty for all four `[CONTEXT J-5]`. **This is not
  `isAnyRegistrationAllowed`**, which `[CONTEXT D-19]` names for the guard and REG-01 for A: the two
  differ for exactly one kind of matrix — the only allowed mode is `identity_provider`, and it is allowed
  for organizations alone — where the letter offers Register and admits C, and C, by `[CONTEXT D-20]`,
  has nothing to list until Phase 179. `[U-29]` is that departure and names the option that keeps the
  letter.
- **Server-rendered where a full load can reach it.** A, B, C, forgot-password, password-reset and F are
  complete in the server-rendered markup; `export const ssr = false` leaves the register tree with its
  legacy page. **Password-reset is always reached by a full load** — the callback's redirect — and a
  server load decides it, in place of the browser's `goto` it has today `[RESEARCH, question 12]`. D1, D2
  and E are reached only from inside the app with something held in memory: a document request for one of
  them, and a visit with nothing held, renders no frame of the screen and ends on the step that owns the
  value `[CONTEXT D-02]` `[U-21]`.
- **Every form is one `<form method="POST" novalidate>`, and one form is one process** `[U-01]` `[U-05]`
  `[U-16]`. Its fields are inside it; its main button is a `type="submit"` button in `primaryActions`,
  tied to it by the `form` attribute, so Enter in a field submits it. `method="POST"` is on every form
  whether or not a server action answers it: a form that fell back to `GET` would write an address, a
  code or a password into the URL `[RESEARCH Pitfall 8]`.
- **A main button is never unavailable because a form is unfinished** `[CONTEXT D-10, D-12]` `[U-06]`. A
  press with something missing or malformed sends nothing, shows the reason at the field and moves focus
  to the first field in error. It is unavailable in two cases only: while its own request runs (`loading`),
  and — where it needs the page's script — until that script has loaded, when it carries the native
  `disabled` attribute `[U-05]`. Native, because only a disabled default button stops Enter in a field
  from posting a `method="POST"` form that no action answers; `aria-disabled` would not.
- **The field pattern** `[U-02]`, written once and used by every field of this phase:

  ```
  <div class="flex w-full flex-col gap-xs">
    <label for={id} class="text-start">{label}</label>              Body, neutral — not the `label` class
    <input {id} class="input w-full" {type} {name} {autocomplete}
           aria-describedby="{id}-info {id}-error" aria-invalid=…  required />
    <p id="{id}-info" class="small-info text-start">…</p>            where the field has a hint
    <ErrorMessage inline id="{id}-error" role="alert" />            while the field is in error
  </div>
  ```

  A form is `flex w-full max-w-md flex-col gap-md`. A field's error is the pattern `Input` already has —
  "The inline error has `role="alert"`, and the control is `aria-invalid` while it is shown" `[tree]` — and
  it goes when the user edits the field.
- **No oracle** `[CONTEXT D-09, D-10, D-11, D-13]`. A screen never differs by whether an address, an
  invitation or an account exists. The three places that are allowed to differ are named where they occur:
  a refused sign-in against a successful one, the three answers of the code check, and F against no F.
- **Reactive accessors are read, never captured.** `appSettings`, `answersLocked`, `isAuthenticated`,
  `user`, `locale` and the new flow state are reactive accessors: read `contestantCtx.X` inside the
  tracking scope, never destructured (`CLAUDE.md` § Context Destructuring Rule;
  `.claude/skills/components/context-reactivity.md`). The flow state is a private `$state` field of the
  context instance, as `newUserEmail` — which it replaces — is today `[RESEARCH Pattern 3]`; never a
  module's `[CONTEXT D-02]`.
- **Vocabulary.** On these screens the UI says "sign in", never "log in": `common.login` reads "Sign in"
  `[tree]`, and the two sentences of the flow that say "log in" — B's and the locked one — are reworded
  in place (*Copywriting Contract*). It says "registration code", never "key". It never names the
  invitation: a user is not told that they were or were not invited.
- **RTL is out of scope on this branch.** New markup uses logical utilities where it sets a side
  (`text-start`, never `text-left`).

Every rendered input has a visible label tied to it by `for`, and every input a `name` and a unique `id`.
No field blocks paste. The password field's show / hide toggle is `type="button"` and changes the
control's `type` only, as today `[tree]`.

**The address field of the setter is not rendered** `[U-07]`. It is in the form's markup with
`display: none`: it takes no space, **is not a tab stop**, is not in the accessibility tree and is not
seen by axe, so it has and needs no label. It is not `type="hidden"`, which a manager does not read as a
user name, and it is not "visually hidden", which would leave an invisible tab stop and an unlabelled
input. This is the form the Chromium guidance gives a change-password form — "Use hidden fields for
implicit information" `[RESEARCH RQ-7]`; which managers honour it is a person's check (N-6).

**`EmailField`.** The field pattern with `type="email"`. Props: `value` (bindable), `label` (default
`common.email`), `name`, `autocomplete`, `info`, `error`, an `id`; a `focus()` export, as `PasswordField`
has, and a `checkValidity()` export that answers for its control. It holds no rule of its own: the caller
says when it is in error.

**The one rule for an address** is the control's own: an address is usable when the `type="email"`,
`required` control reports itself valid `[RESEARCH, Don't Hand-Roll]`. `novalidate` on the form stops the
browser's bubbles, not the control's verdict. **No pattern is written and none is lifted out of
`Input.svelte`**: the server's own test is only "3 to 320 characters holding `@`" (`contract.ts`), the
browser's is the stricter of the two and needs no code, and the server answers every address alike
whatever the browser let through. What is sent is the control's value, which a browser has already
trimmed.

**`EmailEntry`** `[CONTEXT D-12]`. Two `EmailField`s, "Email" and "Confirm email", both
`autocomplete="email"`. The two are compared trimmed and without regard to case. "The email addresses
don’t match." is shown under the second field when it loses focus while both hold text, and on a press; it
goes when either field is edited. A `validate()` export shows the errors, moves focus to the first field
in error and returns the verdict; `email` is bindable and is the first field's value. It takes no code.

**`PasswordSignIn`.** The field pattern around `PasswordField` (`autocomplete="current-password"`,
`externalLabel`, label `common.password`), then the message of a refused sign-in as
`ErrorMessage inline role="alert"`, then "Forgot Password?" as a text `Button` linking to
`ContestantAppForgotPassword`. Props: `password` (bindable), `error` (the field's own, "Enter your
password."), `failure` (the refusal's sentence), and three test ids — the field's error, the refusal and
the link — which B and D2 each pass their own of (*Locator Contract*).

**`RegistrationCodeField`.** The field pattern with the attributes of the table. Its hint shows the
format: "The code looks like this: ABCD-EFGH-JKMN. Capital and small letters are treated the same." The
field takes a code typed or pasted with or without separators and **never rewrites it under the caret**
`[CONTEXT D-15]`; what is sent is the trimmed text. It has no `maxlength`.

**`PasswordSetter`, as changed.** Its `<form>` is one `flex w-full flex-col gap-md` stack holding, in this
order: the address field that is not rendered, the existing sentence, `PasswordValidator` — now given the
address — and the two labelled fields, "Password" and "Confirm password". `validate()` judges the
password **as typed**, not on the validator's debounced display, so a press straight after the last
keystroke is judged right; it shows "The password does not meet the requirements above." at the first
field or "Passwords don’t match" at the second, moves focus there and returns the verdict.
`onValidityChange` stays, for the settings page.

## View Transitions

`CLAUDE.md` § Results Navigation Invariants: *a document View Transition must never run with names while a
modal is open*, and *the `(located)` load must not read the URL tracked*.

- **This phase adds no `view-transition-name`.** Not on a field, an option block, the address or a
  message. The surfaces inherit the standing names: `main-content` (`MainContent`) and `persistent-header`
  (`Header`).
- **No modal is introduced.** No screen of the flow opens a `<dialog>`; F's Log Out calls the context's
  `logout` as G's does and asks nothing. `[U-22]` (b) is the option that brings `LogoutButton`, which
  mounts a `TimedModal` it would never open under a gate (T-8).
- **Each step is a page**, so going from step to step takes the standing document transition. **Passing F
  is not a navigation** `[CONTEXT D-03]`: the loads are rerun, the view is replaced, and no document
  transition starts. Choosing a mode, a press of "Send again" and a field's error navigate nowhere.
- **A redirect is one navigation**, decided on the server or before the screen renders, so no screen that
  is passed over is mounted.
- **No layout load this phase adds or changes reads a `url` or `route` property tracked.** The user-level
  load still reads the two params it reads for the dependency and nothing else, and
  `ENTRY/(protected)/layout.tracking.test.ts` still passes `[CONTEXT D-03]`. The register tree's legacy
  load reads `url.searchParams.get('registrationKey')` `[tree]`; its replacement reads no search
  parameter, because there is none left to read. B reads `redirectTo` in its page, as the login page does
  today, not in a load.

## Focus and Announcements

The root layout's post-navigation reset focuses `[data-focus-on-nav]`, else the first `<h1>`
(`focusNavigationTarget` `[tree]`), and `#route-announcer` speaks the page's title. **Every screen of this
contract renders an `<h1>` that can take focus** (T-9): `MainContent`'s default on F, and
`<h1 tabindex="-1">` inside the `heading` snippet everywhere else. A unit case of each page holds it.

| Event | Focus | Announcement |
|-------|-------|--------------|
| A screen opens by a navigation inside the app | its `<h1>` | its title — never the same as the screen before (*Shared premises*) |
| A full page load of A, B, C, forgot-password, **password-reset** — which is never reached any other way — or of any page that shows F | the browser's own for a new document | the document `<title>` |
| A redirect away from D1, D2 or E, or from a registration route that is off | the `<h1>` of the screen shown | that screen's title, once |
| A notice on A | the `<h1>` | the title; the notice follows in reading order as a `role="alert"` |
| A press with a field in error — every form | the first field in error | that field's error (`role="alert"`), and again as the field's description |
| C: a mode is chosen | stays on the radio | nothing; the panel's field is the next tab stop |
| C: Continue with no mode chosen | the first radio | the group's error |
| C: a code is not confirmed | the code field | the sentence |
| D1: the confirmation loses focus and differs | where the user moved it | the mismatch (`role="alert"`) |
| B, D2: a refused sign-in | stays on the main button | the sentence (`role="alert"`) |
| E: "Send again" is pressed | stays on the button | "A new email has been requested." (polite) |
| E: the count ends | unchanged | "You can now ask for a new email." (polite) |
| F, password-reset: a failed save | stays on the main button | the sentence (`role="alert"`) |
| F is passed | the `<h1>` of the view that replaces it, by the layout (T-2) | that view's title |

Focus is never left on `<body>` and never placed on a screen that was not rendered. A button that becomes
unavailable while it has focus — "Send again" — stays a tab stop, so focus is not dropped. A button that
is natively `disabled` before the script has loaded `[U-05]` is so before anyone can have focused it.

### The eight the components, the forms and the entries cannot be planned without

**U-01 — Where a screen's main button sits.**

directly under the password; the terms gate, the home and the profile have theirs in the page's actions.
A `<form>` cannot span the page frame's body and its actions.

- [ ] (b) Inside the form, directly under the fields, on B, D1, D2, F, forgot-password and password-reset; C alone has it in the actions. Today's sign-in layout is kept; two layouts in one flow, and F differs from G.
- [ ] (c) As (a), by wrapping each page's frame in the `<form>`. `Button` is not changed; a form element around the whole frame, and a layout that rests on `display: contents`.

**U-02 — Whether a field's label is visible.**
`[CONTEXT D-15]` asks for "a visible or programmatic label". Today every field of these pages is named by a
hidden label and shows a placeholder.
- [ ] ★ RECOMMENDED (a) A visible label above every field and no placeholder. It changes the look of today's sign-in form and of the password setter wherever it is used, the settings page included.
- [ ] (b) As today: a label for assistive technology and a placeholder. No visual change; on D1 and on F two filled fields look alike, and a browser that fills a field hides the only text that said what it is.
- [ ] (c) The profile's field rows, with the label inside the row. One field look across the app; that component commits on change only and keeps its error to itself, and the password field would be rebuilt as a row.

**U-03 — What stays in memory while E is shown.** **Departs from `[CONTEXT D-02]`**: "It is cleared when the flow ends (the link is requested, the sign-in succeeds) and on logout."
"Send again" must repeat the request; on the code path that request holds the code. The research reaches the same conclusion — "the only [reading] under which D-11's resend works for D1 and D2" — and draws the line one step earlier, at leaving E.
- [ ] ★ RECOMMENDED (a) E keeps the one request it can repeat — its wording, the typed address, the code on the code path — where it came from and when, in the context instance alone, until the tab reloads, the user signs in or out, or another request replaces it. Everything else of the flow is cleared at the request.
- [ ] (b) **`D-02` to the letter**: everything is cleared when the link is requested. E then cannot repeat a request made with a code, cannot show the address the user typed and has no way back to where it came from; "Send again" exists for nobody.
- [ ] (c) E keeps the wording and the address and never the code: on the code path "Send again" leads back to C. A user who registered with a code types it a second time to get a second mail, and a used code's holder goes through C and D2 again for each one.

- [ ] ★ RECOMMENDED (a) When the request has settled, whatever it settled as — sent, refused or thrown — with the control that sent it in its loading form meanwhile. - [ ] (b) **"Always enabled" and "Continue stays enabled" to the letter**: nothing is unavailable. A press or an Enter in the first moment posts a form that nothing answers — an error page — or does nothing, and every test step that presses must retry.
- [ ] (c) Every step is a server action and works with no script at all. The typed address then reaches E by a cookie or the URL — **against `[CONTEXT D-02]`'s "in-memory only"**.
