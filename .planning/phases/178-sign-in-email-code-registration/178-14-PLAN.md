## Rulings and deviations carried by this plan

1. **The tracer comes after the dataset and the fixtures, and after the plans of parts** (execution rules, order 3). It pulls D-23's fourth stage ahead of its second; item PL-01.
2. **Probe row P4 decides how F is passed.** With `P4: held`, the handler saves the password and reruns the loads, as the terms gate does. With `P4-FALLBACK: refresh`, `_setPassword` in the adapter refreshes the session — the remedy its own comment names — before the rerun; `supabaseDataWriter.ts` is edited only in that case. With `P4-FALLBACK: full-load`, the handler leaves by a full page load to the app root. One branch is built, the one the findings name; what the user meets is the same.
3. **F reads the address from the contestant context** (item PL-09): the context derives `user` from the page data, and a gated load returns the user with the gate. A unit case holds it.
4. **F's way out is G's plain button, not the `LogoutButton` component** (item U-22 ★, the UI contract over the research and the context's table): that component mounts a timed dialog it would never open under a gate.
5. **The callback also refuses `signup` and `email`** (item J2 (a)); the pending todo `2026-10-07-174-callback-keeps-signup-and-email-arms.md` is this phase's, and plan 178-23 closes it.
6. **The legacy set-password page is not deleted here.** Nothing leads to it after this commit; it goes with the tree it belongs to, in plan 178-16 — a removal after its replacement works.
7. **The witness on a page's request is used here for the first time** (item PL-10). When the control of Task 1 is red in step 3 of the path and not in step 5, the interception could not carry the member: the fixture's fallback step is taken, that fixture change is committed alone, and the control is made again.
8. **`P3-IDP: empty` in the findings stops this plan before Task 2**: such an account would meet F during its first registration, which REG-11 excludes. It is reported to the orchestrator; nothing is built around it here.
9. **The gate is the Contestant App's and no other's** (item PL-29, added by the revision and put to the operator). The roadmap's criterion says a user who arrives by a mailed link without a password must set one "before any other page"; D-03 makes F a view of the Contestant App's protected layout and accepts that the data API stays reachable. Neither names the Admin App, whose protected layout, two form actions and six job endpoints decide by a verified identity and the admin role, and ask nothing about a password. A project-scope invitation claimed through a mailed link produces exactly such a session. **No Admin gate is built here**: the reach is stated in this plan's threat register and in the authentication page (plan 178-23), on D-03's own reasoning — the session was obtained by proving the address, and no authority depends on having a password. The other options are the operator's, who accepted this one on 2026-10-11 (decision H38 (a)): the same gate in the Admin layout and its eight server entry points, a plan of its own after this one; or the question handed to Phase 179.
10. **The spec seeds its invitation and removes its user in its own hooks, not in a setup project with a teardown project** — a departure from D-21's letter ("each seeding its own invitation in a setup project … Each has a teardown"), named under item PL-14 and not an amendment of D-21. The model the research names, the invitation landing spec, does the same. What D-21's two clauses are for is kept: the invitation is seeded through the fixture's seeding step before the test that needs it, and the user and its invitations, claimed ones included, are removed before all, after each and after all, so a failed test leaves nothing for the next — which a teardown project that runs once, at the end, does not give.
11. **The fact is on every read of the user-level data** (item J1 (b), the operator's ruling of 2026-10-11, decision H1). The load calls `getBasicUserData()` as it does today, with no argument, and the gate list and `firstNeededGate` take `BasicUserData`, which holds `passwordSet` as a boolean from plan 178-04's Task 3 on. The load still hands the user to the gate list only when the member is a boolean, and signs the user out with `loginFailed` otherwise. `178-RESEARCH.md` § *J1* and the pattern map's section on the gate files prescribe a narrowed parameter type and a setting on the call; neither file is edited, and on this point the ruling is the later reading and this plan stands.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a mailed link → a session | whoever opens the link is signed in; the callback verifies it on the server |
| a signed-in session → the protected pages | the user-level load decides, on the server, what a signed-in user may be shown |
| the browser → the gate | everything the browser holds — a flag, a cookie it can write, the page's state — is the user's to change |
| a signed-in session → the account's password | the gate sets a password with no proof of an old one, because there is none |
| a passwordless link session → everything outside the Contestant App's protected layout | the gate is a view of one layout; the data API, the Admin App's pages, its form actions and its job endpoints decide on their own rules |
