## Rulings and deviations carried by this plan

1. **D-17 and J6 share one plan and one restart; J6 is Task 2 alone** (item PL-18). The operator has not ruled on J6: with option (b) or (c), Task 2 is dropped whole — the function, its census entry, the configuration table, the gate's requirement and row P6 — and nothing else of the plan changes.
2. **The hook is a function of the database**, configured as the access-token hook already is: no secret, no network hop, executable by the auth service's role alone.
3. **The hook has a consequence for Phase 179**: under it the auth service sends no mail for a change of address either, so Phase 179's confirmation of a pending address must be sent by a function. A mail is a user-facing string and must ship in seven locales, which the service's own mail cannot — so that phase has to send its own in any case. It is written into this plan's summary for Phase 179 and is not this plan's to build.
4. **Row P5 needs an account whose seven-character password predates the change**, so the probe has a step that runs before the restart (`p5pre`) and leaves that account for `p5`, which removes it. **`p5pre` runs in Task 3, after the last reset of the database and immediately before the stop**: a reset empties the auth service's users, and Task 2 ends on one, so an account made earlier would be gone when `p5` looks for it. The running service keeps the configuration it read at its last start, so it still admits seven characters then; should it not, `p5pre` stores the seven-character password's hash for its account directly in the database and says so, and the step is measured all the same.
7. **The lifetime of a mailed link is pinned here, not changed** (item PL-27, added by the revision). `otp_expiry` keeps the value the tree holds; the gate now requires it and the stack probe compares the running service with it. D-18 asks that single use and the lifetime both be asserted: plan 178-02 observes the first and records the second, and this plan makes the second a gate. Whether a link is in fact refused after that time is not observed anywhere in the phase.
5. **This plan is committed after a full run of the uncommitted tree** (item PL-20): the configuration reaches every sign-in of the suite.
6. **The schema file is regenerated into the one migration once more** (item PL-02): this is the fourth and last schema commit of the phase.
