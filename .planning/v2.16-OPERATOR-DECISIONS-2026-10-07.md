## A. Phase 174 — auth configuration

### A1 — Public sign-up off and email confirmations on

`apps/supabase/supabase/config.toml` now has `[auth] enable_signup = false` and
`[auth.email] enable_confirmations = true` (commit `592547b68`). It is applied on the local stack.

Why it was changed, as measured:

- With the old configuration, a public sign-up with any email address returned a signed-in user whose
  address was marked confirmed, with no mail sent. On the live local stack both `POST /signup` and a
  one-time-code user creation answered 200.
- Phase 174's claim trusts a confirmed address. So a stranger could have claimed someone else's
  invitation by typing their address.
- Confirmations alone do not close it: an attacker pre-registers with the victim's address and their own
  password, and the victim's later click confirms that same account.
- Turning public sign-up off does close it. After the change both requests answer
  `422 signup_disabled`.
- No product or test code calls public sign-up, and every admin-created user already passes the
  confirmed flag. Both bank-auth projects were green just before the change.

Not yet tested: a full E2E run with sign-up closed. That is the last task of 174-03.

A hosted Supabase project's dashboard settings must be set to match. The repository cannot enforce
that, and `claim_invitations` has no in-database guard for it.

- [ ] **(a) Confirm both switches as committed** — ★ RECOMMENDED — it is the only measured
      configuration under which an invitation cannot be claimed by typing someone else's address.
- [ ] **(b) Sign-up off only; leave confirmations off** — closes the measured hole. An admin-created
      user with an unconfirmed address would then be treated as confirmed, which the claim also trusts.
- [ ] **(c) Revert both, and change the claim so it does not rely on a confirmed address** — keeps open
      sign-up. Phase 174's plans 03–10 are built on (a) and would need re-planning.

## B. Phase 175 — confirmed entities and the name lock

Your note on 175-B2/B3 said to discuss this when the phase is reached, and gave this direction:

- identity provider → candidate confirmed, organization **not** confirmed (its name is user-defined);
- code or email → candidate confirmed, organization confirmed;
- changing a name (first, last, name, short name) is gated on `!entity.confirmed`, for all types;
- the nominations lock affects nominations only.

Phases 174 (INV-05) and 179 (179-C1) are already planned to agree with it.

### B1 — Is that the final rule?

- [ ] **(a) Yes, as written above** — ★ RECOMMENDED — it is your stated direction, and 174 and 179
      already match it. GEN-03 is reworded from "editable while nominations are unlocked" to "editable
      while the entity is unconfirmed".
- [ ] **(b) Name fields are editable until the nominations lock, whatever `confirmed` says** — the
      original 175-B2 ★. An organization seeded by code or email could then rename itself after an
      admin confirmed it.
- [ ] **(c) Read-only when the entity is confirmed OR nominations are locked** — the strictest
      reading. Adds a second condition for no requirement that asks for it.

### B2 — An organization seeded by code or email can never edit its own name

Under B1 (a) such an organization is confirmed from seeding, so its user sees `name` and `short_name`
as locked fields from the first sign-in. Only an admin can change them.

- [ ] **(a) Intended: the admin who seeds the organization sets its name** — ★ RECOMMENDED — it is
      what "code or email → confirmed" means, and matches how candidate names already work.
- [ ] **(b) A seeded organization stays unconfirmed until an admin confirms it** — its user can set
      the name first. This contradicts INV-05 as planned in 174 (one type test and its pgTAP rows
      change), and the organization is invisible to voters until confirmed.
- [ ] **(c) Confirmed, but the name fields stay editable for organizations until the nominations
      lock** — an exception to the one rule in B1, for one entity type.

### B3 — `short_name` freezes on confirmation too

Today the database freezes an organization's `name` when the row is confirmed and never freezes
`short_name`. Under B1 (a) both freeze.

- [ ] **(a) Yes, freeze `short_name` with `name`** — ★ RECOMMENDED — one rule for every name field,
      enforced in the trigger, and `entity.edit_immutable` still lets an admin correct either.
- [ ] **(b) Keep `short_name` always editable** — today's behaviour. A confirmed party could change
      the abbreviation voters see without an admin knowing.
