## Problem

Under D-16, `private.email_holds_grant_in_project` (through `private.grant_reaches_project`, migration 00022) makes an address that holds ANY grant at global or account scope eligible for a recovery or sign-in mail, whatever the grant's role. A global or account **editor** therefore gets the mail, but no app admits them today:

- `ADMIN_GRANTS` lists only `admin` at global, account and project scope, so the Admin App's protected load answers such a user `{ admitted: false }` and signs them out to its login with `userNotAuthorized`.
- `CONTESTANT_GRANTS` lists only the two entity-editor shapes, so the Contestant App shows "nothing to edit".
- A link the Admin App asked for keeps its Admin App landing for them (`isContestantOnly` is false for a user with no Contestant App grant), so they land in the Admin App and are signed out there.

The operator kept D-16 on review: "They'll be lead to the admin app but when it's fully implemented they'll only see parts of the functions there." No admission change was made in phase 179.2.

## Solution

In the Admin App phase that builds the editors' screens:

- Add `{ scope: 'global', role: 'editor' }` and `{ scope: 'account', role: 'editor' }` (and decide on `{ scope: 'project', role: 'editor' }`, see `2026-10-07-174-admin-grants-admit-no-project-editor.md`) to the Admin App's admission.
- Have each Admin App page ask the database (`user_can`) what it may show, so an editor sees only the functions their role carries.
- Re-check the app-entry gates that read `ADMIN_GRANTS`: the Contestant App's `isAdminOnlyInProject` fallback, the confirm page's Cancel and the mailed-link landing's `isContestantOnly` all change with the set.
