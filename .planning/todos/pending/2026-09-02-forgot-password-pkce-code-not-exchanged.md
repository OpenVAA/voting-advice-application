---
title: The in-app forgot-password link cannot complete — PKCE code is never exchanged
priority: high
source: Phase 158 plan 06 manual verification, 2026-09-02
---

## What was measured

A real password-recovery mail was triggered from the app at `/fi/candidate/forgot-password`
against a live local stack, and its link followed hop by hop:

```
mail link  http://127.0.0.1:54321/auth/v1/verify?token=pkce_f86adb…&type=recovery
           &redirect_to=http://localhost:5173/fi/api/candidate/auth/callback

hop 1      303 -> http://localhost:5173/fi/api/candidate/auth/callback?code=6f5ee11d-…
hop 2      303 -> http://localhost:5173/fi/candidate/login?errorMessage=authError
```

The auth service's PKCE verify endpoint hands the callback a **`code`** query parameter.
`apps/frontend/src/routes/api/candidate/auth/callback/+server.ts` reads only `token_hash`
and `type`, so `token_hash` is null, the `if` guard fails, and the handler falls straight
through to its error redirect. **A user who asks for a password reset from inside the app
lands on the login page with an auth error, every time.**

## Why nothing catches it

The E2E suite never exercises this path. `tests/tests/fixtures/shared/emailBucket.fixture.ts`
`toCallbackUrl` pulls the raw token out of the verify link and hand-builds
`?token_hash=…&type=…` against the callback directly, bypassing the verify redirect
entirely — its own docblock says so. The callback is therefore only ever reached in the
shape it can handle.

The admin-triggered path works and is what the suite covers: an `admin.generateLink`
`hashed_token` passed as `?token_hash=` was measured redirecting correctly to
`/fi/candidate/password-reset` with the session cookie set.

## Why it was not fixed in place

The obvious fix, calling `exchangeCodeForSession(code)` in the handler, does not work as
written. The PKCE `code_challenge` is generated by the BROWSER Supabase client and the
matching `code_verifier` lives in browser storage; the per-request server client the
handler holds has no access to it. Deciding which client performs the exchange, and where
the verifier crosses to it, is an architectural choice rather than a local repair, so it
was recorded rather than guessed at.

## Related, already fixed

Two other links in the same chain were repaired in phase 158 plan 06 and are not part of
this item:

- The `redirectTo` the writer emitted named an origin the auth service's allowlist rejected
  (`localhost` vs the `127.0.0.1` hostname `site_url` names), so the link used to fall back
  to `site_url` and never reached the callback at all.
- The `redirectTo` carried no locale, so a non-base-locale reader was sent to a base-locale
  page. It now carries the reader's locale, measured end to end.

## Suggested shape of a fix

1. Decide whether the exchange happens in the browser (page-side) or on the server with the
   verifier handed across, and record the decision.
2. Handle `?code=` in the callback, or move the exchange to the page the callback redirects
   to.
3. Add an E2E case that follows the verify redirect rather than bypassing it, so the shape
   the user actually receives is the shape under test.
