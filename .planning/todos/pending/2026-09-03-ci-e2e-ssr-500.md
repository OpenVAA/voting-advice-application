# CI's e2e jobs have never passed: the dev server answers HTTP 500

**Filed:** 2026-09-03 (Phase 163, from the first observed CI runs of this branch)

**Status:** `e2e-tests` and `e2e-visual` failed on all four evidence runs
(33751423659, 33760872637, 33773591570, 33774590234). The same suite passes LOCALLY at
155 passed / 0 failed / 0 skipped / 0 did-not-run.

## Measured, from the Phase-137 preflight's own diagnostic

    reason:            nothing answered 2xx on port 5173 within 120s - last response was HTTP 500
    expected checkout: /home/runner/work/voting-advice-application/voting-advice-application
    observed:          HTTP 500 -> http://localhost:5173; <title>(none)</title>; served module root: (not found)
    listening process: node 12693 runner 49u IPv6 TCP [::1]:5173 (LISTEN)

## What this rules OUT

**It is not the backgrounded-process hypothesis.** `- run: yarn workspace @openvaa/frontend dev &`
looks like it should die with its step's shell, but the diagnostic shows a node process
STILL LISTENING on 5173 during the next step, and the preflight waited its full 120s. The
server is alive and serving 500s. Do not re-open this as a process-lifecycle bug without
new evidence.

## The likely area, NOT yet confirmed

The dev server SSRs an error. `.env` is `cp .env.example .env`, and Supabase is started by
the job, so the leading candidates are an env/Supabase mismatch or an SSR-time throw. This
is a hypothesis; nothing here has measured it.

## The blocker on diagnosing it

The job captures NO dev-server output - it backgrounds with a bare `&` and no redirect - so
the 500's cause is invisible in the run. **First step of any investigation: redirect the
dev server's stdout/stderr to a file and upload it as an artifact**, the way
`tests/scripts/e2e-run.sh` owns the dev-server log locally. Without that, every attempt is
a guess costing a full CI round-trip.

## Why it matters more than a normal red

CLAUDE.md makes a failing or did-not-run E2E test a CARDINAL FAILURE. That rule has been
enforced entirely on local runs; in CI the suite has never passed even once. So the
project's strongest quality gate has never actually run in CI, on any branch - `main.yaml`
only triggers on `main`, and nobody had observed these jobs before this phase added the
`ci-evidence/**` channel.

## Not in scope for Phase 163

163's criteria concern `db:lint:sql`, secret scanning and dependency audit. None depends on
e2e. Deliberately deferred rather than judged unimportant.
