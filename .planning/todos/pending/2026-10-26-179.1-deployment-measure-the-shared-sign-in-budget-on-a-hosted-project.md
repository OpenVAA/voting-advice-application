## Problem

Both password sign-ins are made server-side. The code sign-in calls `signInWithPassword` from the `account-access` Edge Function, so it reaches the auth service from the Edge runtime's address; the email sign-in calls it from the frontend server. The auth service limits sign-ins per address of origin: `[auth.rate_limit] sign_in_sign_ups` is 30 in five minutes in `config.toml` locally.

If a hosted project's auth service counts these requests under the server's address and not the person's, every user of the deployment shares one budget per server. A few people holding used codes (each code allows ten password look-ups per quarter hour), or anyone sending wrong passwords for any addresses through the email sign-in, could use it up and refuse every user's sign-in until the window ends. The per-code budget does not prevent that.

Not measured anywhere: which address a hosted project's auth service counts a server-side sign-in under. On the local stack every caller reaches the function with the same forwarded address, the container network's gateway, so the local stack cannot answer it. The docs page records it as a pre-launch risk.

## What to measure, on the first hosted project, before it goes live

Use a test project or test accounts only, never a real user's address.

1. From one client, make more than the limit of failing sign-ins inside five minutes: wrong passwords on the email sign-in for a test account, and, for the code path, wrong passwords on `code-sign-in` with test codes (several codes, since one code allows ten).
2. Then, from a second client on a different network, sign in with correct credentials, once by email and once by code.
3. If the second client's sign-in is refused with the rate-limit answer (`429`, `over_request_rate_limit`), the budget is shared. If it succeeds while the first client is refused, the auth service counts the person's address.
4. Read the hosted project's auth logs (Logs Explorer) for the sign-in requests and note which address each was recorded under, for each of the two paths.
5. Repeat for each path separately: the Edge runtime and the frontend server reach the auth service from different addresses, so one result does not settle the other.

## The fix, if the budget is shared

- Forward the client's address from the frontend server and from `account-access` to the auth service through a header the auth service trusts for its rate limit, so each person is counted under their own address.
- Not checked: which header a hosted project's auth service trusts for that, and whether a request from the Edge runtime or from the frontend server may set it. A header the auth service trusts from any caller would let a caller choose the address it is counted under, so the header must be one only the deployment's servers can set.
- Until it is fixed, raising `sign_in_sign_ups` on the hosted project narrows the risk without closing it.
- When it is settled either way, update the pre-launch risk on the docs page (`developers-guide/backend/authentication`, § Known residuals) and close this todo.
