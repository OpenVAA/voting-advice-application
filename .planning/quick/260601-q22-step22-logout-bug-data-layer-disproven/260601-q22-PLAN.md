# Quick Task 260601-q22 — Dig into step-22 (candidate logout) data bug

**Type:** investigation (no production code change)
**Date:** 2026-06-01

## Task

Dig into the candidate-mega-journey step-22 failure documented in
`.planning/todos/pending/2026-06-01-candidate-home-savedanswers-empty-logout-modal.md`.
The standing hypothesis was a backend "auth-linkage mismatch" — that the
freshly-registered candidate's answers were persisted to a different
`candidates` row than `auth.uid()` resolves to, so the auth.uid()-scoped RPC
`get_candidate_user_data` returns empty answers on the home reload, driving
`LogoutButton.triggerLogout` into the confirm-modal branch instead of logging
out.

Approach (as proposed pre-clear): add temporary server-side logging to the
`get_candidate_user_data` caller (`(protected)/+layout.server.ts`) and compare
the auth.uid()-scoped RPC row vs. the actual `candidates` rows for that auth
user, on a live candidate session.

## Method

1. Instrument `(protected)/+layout.server.ts` load with fire-and-forget logging
   of: request path, `session.user.id`, the RPC candidate id + answer-key count,
   and a direct `select id, auth_user_id, external_id, answers from candidates
   where auth_user_id = session.user.id`.
2. Restart the dev server under controlled stdout; run `candidate-mega-journey`.
3. Read the per-load diagnostic to settle the row-mismatch question.
4. Revert instrumentation; record findings in the todo.

## Acceptance

- Determine whether the answers live in a row distinct from the auth.uid() row.
- Leave the tree clean (instrumentation reverted).
- Update the todo with verified findings.
