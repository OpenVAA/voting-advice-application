<objective>
Revalidate the finding at the base commit, and fix it if it still holds. The finding: the dev-seed seed and teardown CLIs, and every library caller of the dev-seed `SupabaseAdminClient`, build a service-role client (the key bypasses row-level security) against whatever `SUPABASE_URL` resolves to, and nothing checks that the host is local. The fix adds one locality guard in the client constructor. It allows only local hosts, and the operator can opt out explicitly: `--allow-remote` on both CLIs, or `DEV_SEED_ALLOW_REMOTE=1` for library and harness callers. Unit, subprocess and drift-gate tests cover it, and the local/E2E/CI invocations are proven to still pass.

Purpose: `db:seed:teardown` deletes every prefixed row across ten content tables. A mis-set `.env` or an exported shell variable pointing at a hosted Supabase would today run that with a service-role key and no warning. The same holds for about 50 E2E setup/teardown clients.

Guard placement: in the constructor, not the CLIs. Every construction path goes through the base constructor: the Writer composes it and the tests/ harness subclass extends it. The constructor is also the only place that sees the URL actually handed to `createClient`. That matters because, as measured, the teardown CLI's client reads the module default captured at import, before the CLI loads the repo-root `.env`.

Output: a new `packages/dev-seed/src/localSupabaseUrl.ts`, the constructor enforcement, the `--allow-remote` flag on both CLIs, a `WriterOptions.allowRemote` pass-through, help-text and README updates, and two new test files. If Task 1 finds that the finding does not hold anymore, the outcome is "dropped — reason" and no code changes.
</objective>
