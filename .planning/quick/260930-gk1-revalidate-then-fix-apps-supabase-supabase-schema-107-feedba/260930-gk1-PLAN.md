<key_design>
Precedence of the rate-limit key, with the reason for each step. Tasks 2 and 3 implement it exactly.

1. **`cf-connecting-ip`, when it parses as `inet`.** On hosted Supabase, Cloudflare fronts every request and sets this header to the connecting client. It is the only value that was the client in both hosted captures.
2. **Otherwise the LAST `x-forwarded-for` entry, when it parses as `inet`.** The gateway appends this entry from the TCP peer. Every earlier entry is client-written and is never consulted, not even when the last entry is malformed.
3. **Otherwise `unknown`.** This is unchanged: direct database inserts and pgTAP without headers land here.

The value is normalised with `host(<value>::inet)`. The helper returns `text` because `private.feedback_rate_limits.ip_address` and the advisory-lock key are both text.

Why not the other candidates:
- **The last entry alone** would put every hosted voter behind one Supabase-internal hop into a single bucket. That would switch off feedback for a real election.
- **`x-real-ip`** has the same problem on hosted, and adds nothing locally, where it equals the last hop.
- **`cf-connecting-ip` alone** is absent on the local stack.

The accepted residual is recorded in the threat model: where no Cloudflare sits in front (the local CLI stack, a self-hosted Kong), a client can send its own `cf-connecting-ip` and the gateway forwards it. Those deployments must strip or overwrite that header at their edge. The schema comment says this, so a self-hoster reading the function learns it.
</key_design>
