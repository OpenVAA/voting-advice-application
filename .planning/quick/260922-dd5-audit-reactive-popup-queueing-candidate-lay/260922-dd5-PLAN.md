<objective>
Audit every popup-enqueue site in the frontend against the one-shot rule that `candidate/+layout.svelte` states in prose, and close the one path the audit finds that can re-queue a popup the user already dismissed.

Purpose: `candidate/+layout.svelte` carries a comment saying its queue push is a one-shot `onMount` *because* a reactive `$effect` re-queues popups. The candidate preregister page had exactly the shape that comment describes and was fixed in `303c52fbf`. This item checks whether any other site has it.

Output: a classification of the whole enqueue population recorded in the SUMMARY, plus the one production fix and the unit test that locks it.
</objective>

Sibling queue API, indirect path (`grep -rn "startSurveyPopupCountdown(\|startFeedbackPopupCountdown(" apps/frontend/src/routes`): `routes/(voters)/(located)/results/[[electionTab]]/+layout.svelte` arms both countdowns from two `$effect`s. Those effects **re-arm** on every app-settings change, which the file's own comment says is deliberate (settings arrive after mount, via async data load, and the countdown functions clear the prior timeout). The push itself happens in the timer callback, outside the effect's tracking scope, so the write-after-read self-retrigger that bit the preregister page does not apply here. **This is intended repetition and must be left alone** — but it is only *safe* because the timeout's status guard refuses to push a popup the user already dismissed, which is true of the feedback path today and becomes true of the survey path in Task 1.

Why the preregister page cannot become a bare `onMount`: its condition reads `isPreregistered` and `idTokenClaims`, both live context accessors that are not yet resolved at mount. A mount-time read would be false and the notification would never show. The `$effect` is required; `untrack` plus the one-shot flag is what makes it safe.

Blast-radius check already done at plan time: `SurveyBanner.svelte` hides only on a *received* status, so persisting *dismissed* does not remove the banner surface — the change is confined to the popup countdown, exactly mirroring how a dismissed feedback status gates only the feedback popup and not the header button.
</prior_findings>

  <behavior>
    - Arming the survey countdown and letting the timer fire enqueues exactly one survey item.
    - Invoking that item's close handler writes a dismissed survey status through user preferences.
    - Arming the survey countdown again after that dismissal and letting the timer fire enqueues nothing.
    - When the survey status is already received, the item's close handler leaves it received — it does not downgrade.
    - Arming the survey countdown twice before the first timer fires still enqueues only one item (the prior timeout is cleared).
    - A zero or negative delay arms nothing.
    - Regression on the untouched path: the feedback countdown still enqueues one item per armed countdown, and a dismissed feedback status still blocks a later push.
  </behavior>
  <action>
Make the survey countdown match the feedback countdown, which already has the complete shape. Two edits inside `startSurveyPopupCountdown`, both in `apps/frontend/src/lib/contexts/app/appContext.svelte.ts`:

1. Widen the timeout's status guard so it declines to push when the persisted survey status is either received or dismissed — today it only checks received, which is why a dismissed survey popup comes back the next time the countdown is armed.

2. Give the pushed queue item an `onClose` that calls `setSurveyStatus` with the dismissed status. Guard that write the same way the feedback item's handler guards its own: if the persisted status is already received, do not overwrite it. This guard is load-bearing, not symmetry for its own sake — `SurveyButton` sets received, and `SurveyPopup` then closes itself on a timeout, so the close handler always runs after a successful click-through and would otherwise downgrade received to dismissed.

Reach for the private queue field the way the surrounding methods already do; do not route through the public handle.

Add a short comment above the survey countdown recording why repeated arming is safe: the arming call sites in the results layout re-arm deliberately on every settings change, and it is this status guard — not the arming site — that stops a re-arm from re-queueing something the user closed. Keep it to the reasoning; the mechanism is readable from the code beneath it.

Then add `apps/frontend/src/lib/contexts/app/appContext.popupCountdown.svelte.test.ts` covering the behaviours above. The `.svelte.test.ts` suffix is required for rune compilation. Two deviations from the spread test's stubs are needed and both matter:

- The user-preferences stub must be live, not inert: its update method has to apply the updater to a mutable holder that its `current` getter reads back, otherwise the status the countdown guard reads can never reflect what the close handler wrote and every assertion passes vacuously.
- The popup-queue stub must record the items pushed to it, so the test can both count pushes and reach into a recorded item to invoke its close handler.

Drive the timers with vitest's fake timers and advance past the configured delay rather than waiting on wall-clock time. Restore real timers in teardown.
