<decisions>

## D-01 (OPERATOR RULING, supersedes the planner's original recommendation) — `cn` is `twMerge(clsx(...inputs))`

`clsx` and `tailwind-merge` are added as **declared** dependencies of `apps/frontend` (versions and evidence in `<versions_and_compatibility>`). `cn` is the conventional composition: `clsx` flattens strings, arrays, objects and conditionals into one string; `twMerge` then resolves Tailwind conflicts, last-wins.

The JSDoc states the semantics **positively**: `cn` resolves conflicting Tailwind utilities, and the LAST conflicting class wins — so `cn('h-16', 'h-32')` is `'h-32'`. It must also point at `<configuration_verdict>`'s subject: the merge is configured for this project's theme, and that configuration must be revisited whenever `app.css`'s `@theme` scales change.

## D-02 (WITHDRAWN) — the mutually-exclusive-branch design is dropped

The original plan partitioned the class sets so that `h-16`/`h-32`, `w-16`/`w-32` and `outline-2`/`outline-4` never coexisted, because a non-merging `cn` left the winner to Tailwind's generated source order. With `twMerge` that hazard is gone: base + override is safe and is the simpler expression of the same intent. **Use base + override.** The conflict table and its invariant test are removed.

## D-03 (UNCHANGED) — the predicate is computed from the PROPS, not the live checked state

`:disabled:not(:checked):not(.entitySelected)` translates to:
