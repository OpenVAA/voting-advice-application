<objective>
Make the Results filter set relevant per entity type: offer a filter only when that entity type's
own nominations produce more than one distinct value for it, counting "missing" as one such value
shared by all non-answerers (operator ruling — see `<design_decision>`, which is settled).

Purpose: today every filter built for an election is offered on every entity tab. The cause is in
the data model, not in a missing scope: `Question.appliesTo()` uses `match()`
(`packages/data/src/utils/filter.ts`), and `match()` returns `true` when the filter value is unset —
so a question that declares no `entityType` restriction applies to candidates, organizations,
factions and alliances alike. `election.getQuestions({ constituency, entityType, type })` in
`nominationAndQuestionState.svelte.ts` therefore hands the SAME filterable questions to every leaf,
and `filterState.svelte.ts` builds a filter for each of them regardless of whether the entities of
that type ever answered it. A cardinality rule at the construction site fixes this without
demanding that every dataset annotate `entityType` on every question.

Terminology, made precise because the item says "entity category": `@openvaa/data` has no "entity
category". Its discriminant is `EntityType` (`candidate | organization | alliance | faction`) — that
is what the results tabs are, what `FilterTree` is keyed on (`electionId -> entityType ->
FilterGroup`), and what this plan scopes filters by. "Category" in this codebase means
`QuestionCategory` (info vs opinion), a different axis entirely, and it is NOT what changes here.

Output: one new pure helper module plus its unit tests, and a three-line wiring change in
`filterState.svelte.ts`.

Deliberately out of scope: `/nominations` (`apps/frontend/src/routes/(voters)/nominations/+page.svelte`)
builds its own `FilterGroup` from `buildParentFilters` over every candidate nomination in the app.
The item names the Results view, that page is not entity-type-scoped, and leaving it untouched keeps
this plan to one construction site. Record it as a follow-up rather than widening the change.
</objective>

<design_decision>
## How missing answers count toward "distinct" — OPERATOR RULING, settled

This is the load-bearing choice; it changes which filters survive. It was put to the operator with
the counter-argument stated in full, and the operator ruled. **Do not relitigate it.** Implement it
as written.

**RULING: a missing answer COUNTS AS A DISTINCT VALUE.** It is ONE value shared by every
non-answering target of that entity type — not one per non-answerer. A filter is offered when the
entity type's targets yield two or more distinct values, where "missing" sits alongside each
canonicalised answer set as an ordinary candidate value.

The trade the operator accepted, recorded so nobody re-opens it on discovering the downside: a
question where the answerers all agree but a minority skipped KEEPS its filter, because "answered"
and "did not answer" are two values. In exchange the voter keeps the ability to narrow to
"answered / did not answer" on a unanimous question. The counter-argument put to them — that a
single non-answerer anywhere resurrects a filter, and that in real data somebody always skips — was
stated and chosen against.

**An entity's answer is its whole answer, not each of its values.** (Unchanged from the original
plan; the operator agreed with this half and it matters more than the missing-value half.) For a
multi-value filter (`options.multipleValues`, e.g. `MultipleChoiceCategorical`) the entity's answer
is the SET of values it selected, canonicalised by de-duplicating, sorting and `JSON.stringify`-ing.
Without this, a population where every candidate answered the same two choices counts as two
distinct values and the filter survives, even though selecting either choice returns everybody — the
exact false positive this change exists to remove. For single-value filters the canonical key
degenerates to the value itself, so one code path covers both.

### Keeping "did not answer" apart from "answered with nothing"

Both are now COUNTABLE values, so they must be distinguishable, and the collision is real: an
all-missing value array and a genuinely empty stored array both reduce to zero surviving members. The
discriminator is available upstream of that reduction, in `Filter.getValue()`'s own contract:

- `getValue()` returns `[MISSING_VALUE]` for a multi-value filter **exactly when** the stored value
  was null or undefined — that is "did not answer".
- It returns `[]` — passed through `castValue` — when the entity genuinely stored an empty array.
  That is "answered with nothing", a different fact.

So classify BEFORE reducing. A target's key is:

- the `MISSING_VALUE` object itself when the target has no value at all: the scalar is missing, or
  its value array is non-empty and every member is missing;
- otherwise the JSON canonicalisation of its de-duplicated, sorted non-missing members — which for a
  genuinely empty stored array is the two-character string for an empty JSON array.

**Why the collision is impossible rather than merely unlikely:** the missing key is the
`MISSING_VALUE` singleton OBJECT exported by `@openvaa/filters`, and every answered key is a STRING
produced by `JSON.stringify`. A `Set` keys on identity, and an object is never identical to a string,
so no canonicalisation of any answer — including the empty array — can ever land on the missing
sentinel. Using the package's own sentinel rather than inventing a magic string is what makes this
structural instead of a naming convention someone can break later.

**Threshold constant:** `MIN_DISTINCT_ANSWERS = 2`, exported from the helper so the decision is
greppable and flipping it is a one-line change.
</design_decision>

<rederivation>
## Re-derived under the ruling — the two verdicts the operator asked for

Both predictions in the original plan were made under the overruled rule and have been re-derived
from `packages/dev-seed/src/templates/e2e/base.ts` and the frontend source.

### Verdict 1 — `voter-journey.spec.ts`'s `toHaveCount(3)` is SAFE. The assertion does not break.

The framing in the ruling ("3 is a FLOOR not a ceiling") needs one correction, and the correction is
what makes the verdict clean: **the relevance pass is purely SUBTRACTIVE over a filter universe that
is fixed upstream of it.** That universe is decided by `buildParentFilters` plus the
`getCustomData(q).filterable` test in `filterState.svelte.ts` — neither of which this change touches.
The new rule can let MORE of the existing filters survive; it can never bring into being a filter
that was not built in the first place. So the count has a hard ceiling at the universe size.

That universe on the candidate tab in `e2e/base` is exactly 3, derived two independent ways:
`grep -n filterable` over the whole template returns four hits and only TWO of them are
`filterable: true` — `test-e2e-base-qu-info-multipleChoiceCategorical` and
`test-e2e-base-qu-info-number` (`singleChoiceCategorical` sets no custom data at all, and
`qu-info-boolean` sets `filterable: false`) — plus one parent-organization filter from
`buildParentFilters`; and the spec's own derived comment states the same three by name.

3 is therefore simultaneously the floor and the ceiling. `toHaveCount(3)` holds under the ruling, and
holds strictly more comfortably than it did under the original rule.

### Verdict 2 — the reported symptom IS still fixed. The operator's read is correct, and verified.

This one had to be checked rather than assumed, because the ruling turns "some answered, some did
not" from a drop into a keep. The question is whether the organizations and alliances tabs are that
mixed case. They are not:

- **No organization or alliance row in `e2e/base` carries answers at all.** The `organizations` and
  `alliances` blocks hold only `external_id`, `name`, `short_name`, `color`, `sort_order` and
  `is_generated`. `answersByExternalId` appears on candidate rows only, always via `withInfoAnswers`.
  Both filterable questions therefore yield `MISSING_VALUE` for EVERY target on those tabs: one
  distinct value, below the threshold, dropped. The symptom is fixed.
- **Imputation does not leak into the filter targets, so this is not an illusion.** `matchState`
  builds `MatchingProxy` objects carrying imputed parent answers for organization and alliance
  matching, but `unwrapProxiedMatch` (`apps/frontend/src/lib/utils/matching/imputeParentAnswers.ts`)
  returns `new Match({ target: proxy.target })` — the real nomination. The proxy never reaches the
  rendered list, so it never reaches `EntityFilters`' `targets` either. Independently,
  `imputeParentAnswers` only ever imputes OPINION questions and only for SingleChoiceOrdinal,
  SingleChoiceCategorical and Number types; both filterable questions here are INFO questions, which
  it does not touch at all.
- **The parent filter on those tabs is a separate, legitimate survivor.** On the organizations tab
  `buildParentFilters` builds an alliance filter from the organization nominations' parents, which in
  `e2e/base` yields alliance A, alliance B and the unaffiliated Party C — three distinct values,
  retained under either rule. That is a working filter, not the reported bug.

**The caveat this creates, stated rather than hidden.** `e2e/base` fixes the symptom because those
entities answer NOTHING. A dataset where organizations answer a candidate-facing question
*partially* keeps that filter on the organizations tab under the ruling, showing one answer row plus
"No answer". That is the accepted cost of the ruling, and — because `e2e/base` has no such data —
**no E2E spec can catch it**. Task 2 records the observed per-tab sets so the behaviour is measured
against the real dataset rather than inferred from this note.
</rederivation>
