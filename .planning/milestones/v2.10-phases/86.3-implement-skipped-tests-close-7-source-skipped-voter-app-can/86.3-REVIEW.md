### WR-02: `topBarSettings` $effect can clobber child-layout / child-page pushes — design assumption unverified

**File:** `apps/frontend/src/routes/(voters)/+layout.svelte:52-62`
**Issue:**
The reactive `$effect` block uses a fixed `topBarBaseIdx` captured at component
init (line 52) and does `topBarSettings.revert(topBarBaseIdx); push(next);` on
every re-run. If a downstream consumer (child layout, +page.svelte) has pushed
its own overlay onto `topBarSettings` between two $effect runs of the parent
(voters)/+layout, the parent's next re-run will `revert(topBarBaseIdx)` —
dropping BOTH the parent's previous push AND the child's intermediate push —
then re-push only its own value. The child's overlay is silently erased.

The trigger for parent $effect re-runs is a write to `$appSettings`, which the
appContext does only on navigation (`page.data.appSettingsData` change at
`appContext.svelte.ts:94-100`). In normal SvelteKit lifecycle, child consumers
register their own `onDestroy(() => topBarSettings.revert(indexTopBar))` via
`getLayoutContext`, so their overlays are torn down BEFORE navigation triggers
the parent re-run. This makes the bug very narrow but not impossible — there's
a window during navigation where the new child layout could mount and push
BEFORE the parent's $effect re-runs in response to the appSettings change.

The canonical pattern referenced in the comment (`appContext.svelte.ts:93-100`)
does NOT have this concern because it manages a raw `$state` value, not a
`StackedState` with child-layer interleaving.

**Fix:**
Either:

1. Document the assumption explicitly in the inline comment — note that the
   pattern relies on Svelte's mount-order guarantee that this $effect re-runs
   before any child layout's mount-time push, and that any future child
   consumer pushing inside an effect that responds to the same `$appSettings`
   change must order itself AFTER this $effect.

2. Capture `topBarBaseIdx` reactively inside the $effect rather than at
   component init:
   ```svelte
   $effect(() => {
     const baseIdx = topBarSettings.getLength() - 1;
     const next = { actions: { ... } };
     // revert is now unconditional based on current length; we capture the
     // baseline AT effect run time, not at component init. This still drops
     // the current top push (which is THIS effect's previous push) but does
     // not drop earlier child-pushed overlays IF they sit ABOVE topBarBaseIdx.
     // ...
   });
   ```
   Note: option 2 still doesn't fully solve the race if child pushes land
   ABOVE the parent's previous push within a single effect run cycle. The
   underlying API (StackedState push/revert by absolute index) is ill-suited
   to multi-consumer reactive composition.

Option 1 (documentation) is the lower-risk, in-scope fix.

### WR-03: `notificationQueued` fire-once flag never resets — stale or empty notifications cannot re-queue

**File:** `apps/frontend/src/routes/(voters)/+layout.svelte:77-87`
**Issue:**
The `notificationQueued = $state(false)` flag is set to `true` after the first
successful push and is never reset. If the operator changes the notification
content via `dynamicSettings` (e.g., flips `show=false` then `show=true` again,
or updates the `title`/`content` body), the $effect re-runs, sees
`notificationQueued === true`, short-circuits, and never re-queues the (new)
notification. The new notification is silently dropped.

This is a behavioural divergence from the original `onMount` semantic — the
old code also fired once, but at MOUNT time. After a hot-reload or live
settings update, the new $effect-based code is still stuck on the first push.

The Phase 86.3-01 comment frames this as "Pitfall 2 guard" but does not
acknowledge the trade-off. The current behavior is acceptable IF the contract
is "notification is queued ONCE per voter session, never refreshed". If the
contract is "newest notification wins", the flag needs a reset trigger.

**Fix:**
If the "fire-once per session" semantic is intentional, add a comment noting
that operator-side notification changes within a live session are NOT
propagated to the queued popup:

```svelte
// notificationQueued: fire-once per page load. Operator-side changes to
// $appSettings.notifications.voterApp content/title (or show=false→true
// cycles) within a live voter session are NOT re-queued. To re-queue, the
// voter must reload the page. Matches the pre-86.3 onMount semantic.
```

If "newest notification wins" is intended, gate the flag on the notification
identity (title + content) instead of a boolean:

```svelte
let queuedNotificationKey = $state<string | undefined>();
$effect(() => {
  if (!$appSettings.access.voterApp) return;
  const n = $appSettings.notifications.voterApp;
  if (!n?.show) return;
  const key = JSON.stringify({ title: n.title, content: n.content });
  if (queuedNotificationKey === key) return;
  popupQueue.push({ component: Notification, props: { data: n } });
  queuedNotificationKey = key;
});
```

### WR-04: `popupQueue` is destructured from `initVoterContext()` — verify reactive-accessor contract

**File:** `apps/frontend/src/routes/(voters)/+layout.svelte:36`
**Issue:**
Per CLAUDE.md "Context Destructuring Rule (Svelte 5)" (lines 218-251), reactive
`$state`/`$derived`-backed accessors must NOT be destructured — they must be
read via `ctx.X` to keep the dependency edge live inside the tracking scope.

The destructure at line 36 pulls `popupQueue` (along with `appSettings`,
`appType`, `userPreferences`, `t`) out of `initVoterContext()`. `popupQueue` is
mutated by `popupQueue.push(...)` at lines 81 and 97; the write target must be
the live context reference, not a captured snapshot.

This is most likely safe: `popupQueue` is a CLASS instance (push/pop API), not
a getter-returning-`$state`-array. Destructuring captures the class reference
once and uses its API methods — exactly the "stable reference" pattern in
CLAUDE.md's section (1). However, this is not explicitly documented in the
context source, and a future refactor that swaps `popupQueue` for a `$state`-
based collection would silently break.

Cross-check `apps/frontend/src/lib/contexts/voter/voterContext.svelte.ts` (and
appContext) to confirm `popupQueue` is a stable instance, NOT a `$derived`
getter, and add an inline comment to line 36 documenting the assumption.

**Fix:**
Audit `initVoterContext()` to confirm `popupQueue` is a stable instance
property (class field, NOT a `$state`/`$derived` getter). If confirmed, add an
inline comment to line 36 documenting the assumption:

```svelte
// popupQueue is a class-instance reference (stable per CLAUDE.md Context
// Destructuring Rule §1). DO NOT switch to a $derived/$state getter without
// updating consumers to use ctx.popupQueue per the destructuring rule.
const { appSettings, appType, popupQueue, userPreferences, t } = initVoterContext();
```

If `popupQueue` is in fact a reactive accessor, change to:
```svelte
const voterCtx = initVoterContext();
const { appSettings, appType, userPreferences, t } = voterCtx;
$voterCtx.appType = 'voter';   // or however appType is set
// Then use voterCtx.popupQueue.push(...) in $effect and onMount.
```

### IN-02: `voter-popup-hydration.spec.ts` beforeAll/afterAll still run for the SKIPPED test — settings churn

**File:** `tests/tests/specs/voter/voter-popup-hydration.spec.ts:80-120`
**Issue:**
`test.skip(true, …)` inside the test body short-circuits the test execution but
does NOT skip the surrounding `beforeAll` / `afterAll` hooks. The beforeAll
(lines 80-116) still:
- Issues `client.updateAppSettings({ results: { showFeedbackPopup: 2, … } })`
- Queries the elections, constituencies, and questions tables via Supabase
- Populates module-scoped `electionId` / `constituencyId` / `questionIds`

And the afterAll (lines 118-120) issues another `updateAppSettings` to restore
defaults. This churn is wasted work because the test never runs the assertion,
but it also means the spec mutates the global `app_settings` row even for a
skipped test — potentially racing with other settings-mutating specs in the
same run.

This is currently neutral because:
- The describe is configured `serial`, so no in-spec races.
- Other specs that share `app_settings` use their own beforeAll/afterAll
  restore cycles.

But the wasted Supabase round-trips on every run for a permanently-skipped test
are a minor maintainability smell.

**Fix:**
Add an early-exit guard in beforeAll:

```typescript
test.beforeAll(async () => {
  // Phase 86.3-04 SKIP-FALLBACK guard: the body test is permanently skipped.
  // Skip the settings churn until the upstream cold-deeplink race is fixed
  // (v2.11+ Recommendation #3).
  // eslint-disable-next-line no-console
  if (true) return; // Remove the guard when the spec is re-activated.
  ...
});
```

Or restructure to move discovery into the test body (inside a `test.step`) so
the skip short-circuits before any Supabase round-trip.
