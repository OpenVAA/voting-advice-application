## Objective

Land the parallel scaffolding for Phase 88's catalog refactor: a generic `setupFromTemplate(template)` helper, a new BUILT_IN `baseV1` dataset (the spec at TEST-INVENTORY-REFACTOR-1.md:13-108), and a single voter mega-journey spec consuming both. All new artifacts run as NEW playwright project entries appended to `playwright.config.ts`; the existing setup files, templates, specs, and project entries remain untouched and continue to gate against the Phase 87 anchor (`b2ad76e5…`). The rationale, scope discipline, and gating constraints are in `88-CONTEXT.md` — this plan delivers the parallel landing only; later 88-NN plans absorb the remaining specs (refactor-doc lines 379+) and eventually retire the old surfaces once the new mega-journey is proven stable.

## Approach

The build sequence is foundation-first, consumer-second, integration-last, so each task can verify in isolation against a small surface:

1. The new BUILT_IN template (`baseV1`) lands first (Task 1) — registered in `BUILT_IN_TEMPLATES` so the CLI can seed it via `--template baseV1` for ad-hoc verification BEFORE any playwright wiring exists.
2. The generic setup helper (Task 2) lands second; it composes `runTeardown` + `runPipeline` + `fanOutLocales` + `Writer` + post-seed subset-match into a single callable that mirrors the existing `data.setup.ts` body. The helper is a pure module export and is unit-testable via direct invocation from a one-off playwright spec entry.
3. The voter-mega fixture (Task 3) lands as a sibling to the existing `voter.fixture.ts`; the existing fixture is preserved (Phase 86+ specs depend on it).
4. The mega-journey spec (Task 4) lands consuming both the new template (via baseV1's seeded dataset) and the new fixture (via `voterTest.use({ answerMode: 'max' })` etc.). The spec uses `test.describe.configure({ mode: 'serial' })` so the assertions chain in execution order per the refactor doc.
5. Playwright project entries (Task 5) land last because they only make sense once the spec compiles and the helper + template are stable. The new project chain runs ALONGSIDE the existing suite, gated by its own `data-setup-baseV1` setup and `data-teardown-baseV1` teardown — zero overlap with existing project dependencies.
6. Full-suite regression (Task 6) confirms the existing test surface remains green with the parallel projects appended; the mega-journey project is also green.
7. Optional developer-facing README (Task 7) documents which existing tests the mega-journey absorbs (cross-referenced to `tests/TEST-INVENTORY.md` numbering), so 88-02+ migrations can pick up cleanly.

Parallel-running verification: after Task 5 lands the new playwright projects, Task 6's full-suite run is the definitive proof. Between Task 1 and Task 5 the executor verifies in isolation with focused commands (`yarn db:seed --template baseV1`, then `yarn test:e2e --project=voter-mega-journey`) — see per-task Verify blocks.

## Risks & Mitigations

- **Risk #1: baseV1 dataset shape breaks pipeline invariants.** The dataset is the largest single new asset (~30 candidates, 14 questions, hierarchical CG, alliance↔organization wiring) and the pipeline's row-fanout + sort_order + nomination-graph code has historical landmines (Phase 85+ DETERM-11/12/14 lineage). **Mitigation:** Task 1's Verify includes per-table row-count probes BEFORE Task 2 begins. If a probe fails, Task 1 stops and discovers the pipeline gap; no downstream work is blocked since Tasks 2-7 only execute after Task 1's Done criterion holds.

- **Risk #2: Chained-assertion shape interacts badly with cold-start race conditions.** The v2.10 lineage (DETERM-04 / DETERM-12 / DETERM-14) documents repeated cold-start race lessons where the first navigation in a serial spec landed at a partially-hydrated page and a follow-on assertion failed non-deterministically. **Mitigation:** Task 4 uses the established `walkVoterIteration` helper (which encodes the maxSteps=6 + category-intro + Skip-Next + terminal-URL pattern that v2.10 settled on) rather than raw `page.goto()` chains; the fixture's `answeredVoterPage` is used ONLY from the "Results landing" step onward. Any step that cannot be made deterministic on first author is marked `test.fixme(true, ...)` with an explicit follow-up note rather than a flaky pass.

- **Risk #3: Parallel playwright project entries inflate full-suite duration.** The new chain adds ~3 minutes of wall-clock (1 setup + 1 mega-journey + 1 teardown, single-worker) on top of the existing suite. **Mitigation:** The plan documents this expected delta; the operator can disable the chain during incremental development via `--project=` filters (omit `voter-mega-journey`, `data-setup-baseV1`, `data-teardown-baseV1`). Long-term, once 88-02+ retires the parallel specs and the mega-journey absorbs their coverage, the net duration delta is expected to be < 0 (consolidation reduces total work).

- **Risk #4: PREFIX='test-' collision between baseV1 and the existing e2e dataset.** Both templates use `externalIdPrefix: 'test-'` and `runTeardown('test-', ...)` clears ALL rows under that prefix. If both `data-setup` (existing) and `data-setup-baseV1` (new) run in parallel against the same Supabase, the second to start would clear the first's seed mid-test. **Mitigation A (chosen):** the new chain does NOT depend on `data-setup` and runs in its own worker group; playwright's project ordering ensures `data-setup-baseV1`'s teardown→seed happens BEFORE `voter-mega-journey` begins, AND the existing chain's `data-setup` completes before `voter-app` begins. The collision window is therefore between projects belonging to DIFFERENT chains — and since the new `data-teardown-baseV1` is invoked via the `teardown:` key on `data-setup-baseV1`, it runs ONLY after `voter-mega-journey` completes (Playwright project-graph semantics). If the operator runs both chains concurrently (e.g. via `--workers=12`), Playwright's setup-project semantics serialise `data-setup-*` projects within their respective dependency subgraphs but DO NOT serialise across subgraphs. **Mitigation B (forward-looking):** A later 88-NN plan can introduce a per-template prefix (`'test-baseV1-'` for baseV1, `'test-e2e-'` for the existing dataset) to fully decouple. For 88-01 the operator accepts the shared-prefix sequencing risk; the full-suite runs in Task 6's Verify ARE the empirical proof that the sequencing holds.

- **Risk #5: CG hierarchy (`CG-Mun → CG-Reg parent`) may not be expressible in today's template schema.** The refactor doc (line 21) says "Fully hierarchical with CG-Reg as parent" — but the dev-seed pipeline's `constituency_groups` schema may not currently support a parent-CG reference. **Mitigation:** Task 1 attempts the most natural shape first (e.g. `parent_constituency_group: { external_id: 'test-cg-reg' }`); if the pipeline rejects the field at write-time, Task 1 captures the gap as a discovery-blocker and posts to operator for resolution: the operator may either (a) accept a flat CG-Mun and adjust the mega-journey's hierarchy assertions OR (b) approve a small pipeline extension as a sibling 88-01 task. The default fallback is (a) — flat CG with the hierarchy assertions marked `test.fixme` per Risk #2.

- **Risk #6: Surgical testIgnore extension is the only modification to existing playwright project entries.** Task 5 extends the `voter-app` project's `testIgnore` regex by one alternation (`mega-journey`) to prevent the existing project from double-picking up the new spec under the wrong dataset. This is the ONLY breach of the "no existing entry modified" constraint and is structurally required for parallel landing. **Mitigation:** documented inline in Task 5's Action; Task 6's Verify confirms the existing voter-app project still runs green; the change is mechanically additive (regex grows by 13 characters, no semantic change to existing matched specs).

- **Risk #7: The new mega-journey's hierarchical CG-Mun spec step may fail if the constituency dropdown does NOT only show municipalities.** Refactor-doc:226 explicitly says "only show municipalities" — this is a UI contract the planner cannot verify from the doc alone; the frontend may show CG-Reg + CG-Mun in the dropdown depending on the `startFromConstituencyGroup` setting. **Mitigation:** the baseV1 settings block explicitly sets `elections.startFromConstituencyGroup: undefined` (per refactor-doc:181) — if the resulting UI does not match the spec, Task 4 marks the step `test.fixme` with a follow-up note for the frontend behaviour to be confirmed in 88-02 OR for a settings adjustment.

- **Risk #8: `--likert-only` deprecation triggers regressions elsewhere.** Refactor-doc:3 calls for deprecation of the flag, but 88-01 does NOT remove it — it only stops the new template from needing it. **Mitigation:** the helper's optional `likertOnly: boolean` parameter preserves backward compatibility; existing variant setups continue to call `applyLikertOnlyFilter(template)` directly (no behavior change). Flag removal is explicitly OUT OF SCOPE for 88-01 (see "Deferred" section).
