## Approach

The build sequence is foundation-first, consumer-second, integration-last, fanning into two parallel waves:

**Wave A (parallel — foundation):**

- Task 1 lands the shared helper module (`voterIntro.ts`). It is a pure helper module — depends only on `@playwright/test` + `testIds` — and can be authored independently of any template work.
- Task 2 lands all 8 minimal templates + the BUILT_IN registration. Templates depend only on `Template` type from `@openvaa/dev-seed`; no Playwright code touched. The new directory `packages/dev-seed/src/templates/permutations/` is created here. Tasks 1 and 2 can run in parallel because they touch disjoint file sets (`tests/tests/utils/*` vs `packages/dev-seed/src/templates/permutations/* + index.ts`).

**Wave B (parallel — consumers):**

- Task 3 lands all 16 setup+teardown files. Depends on Task 2 (templates must exist in `BUILT_IN_TEMPLATES` for `setupFromTemplate('perm-<NAME>')` to resolve). Each setup/teardown is a tiny wrapper — no per-file complexity beyond the wrapping pattern from `baseV1.setup.ts` / `baseV1.teardown.ts`.
- Task 4 lands all 8 spec files under the NEW directory `tests/tests/specs/perm/`. Depends on Task 1 (helpers must exist) and Task 2 (so the executor can run a smoke seed and verify the spec's locators match real DOM). Specs use only the helper module + raw `@playwright/test` primitives — no other shared infra needed. Tasks 3 and 4 can run in parallel because they touch disjoint file sets (`tests/tests/setup/perm-*.*.ts` vs `tests/tests/specs/perm/perm-*.spec.ts`).

**Sequential close:**

- Task 5 lands the 24 playwright config entries (including the per-HIGH-2 sequential chain wiring within the perm-* family) and runs the full verification matrix (isolated-per-project + full-suite parallel + mega-journey regression). Depends on Tasks 3 and 4 (the project entries must reference existing setup + spec files). This is the only task that modifies `tests/playwright.config.ts` and the only task that runs full e2e suites.

The two-wave shape minimizes serial dependencies while preserving the "templates before consumers" + "files before config" build order.

- **Risk #2: ~~per-template `app_settings` external_id collisions~~ — STRUCTURALLY RESOLVED by HIGH-2.** The original concern (cross-prefix app_settings singleton clobbering under parallel-setup execution) is resolved by chaining the perm-* setups sequentially within the family per HIGH-2 (88-03-SCOPE.md line 13). - **Risk #3: helper module's `expect.toBeHidden` on selectors may be over-eager.** Some selector lists may remain in DOM during transition animations. `toBeHidden`'s default polling should handle the transition, but if a spec fails on the post-advance hidden-check, the executor either bumps the helper's timeout OR rephrases to `await page.waitForURL(/expected-path/)` followed by the locator-visible assertion. **Mitigation:** Task 1's helpers use `TIMEOUT.page (4_000ms)` for the hidden-check, which matches the same bucket as the mega-journey's URL-transition waits. If a spec needs the slower bucket, the executor adjusts the spec-level wait without touching the helper.

- **Risk #4: rigidity vs flakiness tradeoff.** The SCOPE memo bans `expect.soft`, try/catch around expect, and best-effort `.catch()` on assertion-bearing locators. This is operator-mandated for the minimal-dataset specs (the whole point is that minimal data makes every contract enforceable). If a spec proves flaky under cold-start full-suite race conditions, the FIX is to harden the dataset / fix the frontend race / wait for a deterministic settle signal — NOT to soften the assertion. **Mitigation:** Task 5's Gate B catches flakes; the executor surfaces them in the SUMMARY for operator decision (do not silently soften).

- **Risk #5: ~~voter-app may pick up perm-*.spec.ts~~ — STRUCTURALLY RESOLVED by HIGH-1.** The new perm-* specs live in `tests/tests/specs/perm/` (NEW directory) — the `voter-app` project's `testDir` is `./tests/specs/voter`, so files under `./tests/specs/perm/` are categorically outside the `voter-app` discovery surface. NO modification to the `voter-app` `testIgnore` regex is needed (or permitted, per the APPEND-ONLY constraint). This risk is closed; the executor MUST NOT add a `|perm-` alternation to `voter-app`'s testIgnore — doing so would be a SCOPE violation per the HIGH-1 resolution at 88-03-SCOPE.md line 12.

- **Risk #6: per-template prefix-set externalIdPrefix vs pre-prefixed external_ids.** baseV1 uses `externalIdPrefix: ''` + pre-prefixed external_ids (`'test-el-reg'`); the new perm-* templates use `externalIdPrefix: 'test-perm-<short>-'` + bare external_ids (`'el-1'`).
