### 4.1 🔴 WCAG 2.1 AA contrast violation (cross-cutting, HIGH)

> **⚠ CORRECTED 2026-08-10 (Phase 134, D-01c).** This section is retained as written, with the stale
> and incorrect claims annotated inline rather than deleted — the fact that a stale measurement
> produced a wrong conclusion (and a wrong "do not change this component" instruction) is itself part
> of the record. In summary: the elections-selector contrast defect had **already been closed** by
> commit `0eb27c677` (2026-06-22 19:59) before this audit was written; the filter line numbers are off
> by one and that class was **dead**, not a live violation; and the constituency-selector exemption
> below is **materially incomplete** — that component carried a separate, measured AA failure through a
> different mechanism. What the section got right is the **gate** gap: the suite genuinely could not
> have caught the original defect.

CLAUDE.md states the app must be WCAG 2.1 AA compliant. It currently is not, on a primary voter-facing surface. _(Corrected: as of `0eb27c677`, and re-measured in Phase 134, it is — on this surface. See §4.1's annotations and the newly-found `ConstituencySelector` failure below.)_

**Origin:** `apps/frontend/src/lib/components/electionSelector/ElectionSelector.svelte:56` — `class="label gap-sm cursor-pointer justify-start !p-0"`. The `.label` class is applied as a *layout* primitive (gap / cursor / justify / padding), but DaisyUI also attaches:

```css
.label { color: color-mix(in oklab, currentcolor 60%, transparent); }
```

The inner `<span>{name}</span>` (lines 69-71) inherits it, compositing to **#858585 on #ffffff = 3.69:1** against the required 4.5:1.

> **⚠ STALE.** That figure describes the state **before** commit `0eb27c677` (2026-06-22 19:59), which
> closed the app-side defect. Phase 134 re-measured `/elections` with an axe scan gated on the
> data-driven `election-selector-option-label` anchor before `awaitAnimationsSettled`: **0
> color-contrast violations, light and dark.** The same settled re-scan of `/`, the `/questions`
> intro, `/results` with entity cards, and the results filter drawer also returns 0/0.

**Why the suite did not catch it:** `.planning/debug/a11y-entrance-fade-opacity-scan-timing.md` records settled axe scans failing **12/12**. a11y-smoke passes only because the data-driven labels intermittently render outside the scan window. The 3× green E2E gate does **not** clear this defect.

> **⚠ STALE FIGURE, VALID DIAGNOSIS.** The 12/12-FAIL count is from the same pre-`0eb27c677` debug
> session and no longer reproduces. The *mechanism* the sentence identifies is real and was never
> fixed: a11y-smoke settled on a heading rather than on the data-driven content, so it scanned before
> the labels rendered. That gap — not the contrast value — is what Phase 134's FIX-01 actually closes,
> via a **required** `contentTestId` on every axe scan route.

**Further surfaces found during this audit** (same pattern, no REQ-ID, out of v2.14 scope but same defect class):
- `NumericEntityFilter.svelte:85, 98, 113` — child spans use `text-label`, which has **no definition anywhere in `app.css`**, so there is no color override at all. _(Line numbers corrected 2026-08-10 from the 84/97/112 originally recorded here, which point at the enclosing `<label>` elements.)_
- `EnumeratedEntityFilter.svelte:198` — per-option filter label. (The `:224` select-all variant escapes via an explicit `text-primary`.)

> **⚠ CORRECTED — wrong lines, and not a violation.** The `text-label` spans are at
> `NumericEntityFilter.svelte:85, 98, 113`; the numbers above point at the enclosing `<label>`
> elements. And the second half of the observation inverts its own conclusion: because `text-label`
> matched **no** CSS rule at all, nothing dimmed those spans — they measured `rgb(51, 51, 51)` at
> `opacity: 1` (12.6:1), i.e. a **dead class**, unrealised intent rather than a live contrast failure.
> `EnumeratedEntityFilter.svelte:198` likewise measures AA-clean. Phase 134 swaps the dead class for
> the project's own opaque `small-label` token so the intent is expressed by something real.

**Correction to the debug doc's guidance:** it recommends auditing the constituencies selector too. `ConstituencySelector.svelte` is unaffected by *this particular* mechanism — it uses the project's own `.small-label` (`app.css:384` → `@apply text-secondary text-xs font-normal uppercase`), an opaque token with no alpha reduction. **That does not make the component clean, and this paragraph must not be read as an exemption** — see the correction immediately below.

> **⚠ MATERIALLY INCOMPLETE — do not read this as an exemption.** The mechanism claim is true:
> `ConstituencySelector` is not affected by the DaisyUI `.label` alpha. The *conclusion* drawn from it
> — that the component needed no attention, which propagated into ROADMAP criterion 1 as an explicit
> "do not change it" — was wrong. The debug doc's instinct to audit the constituencies selector was
> right, for a reason neither document identified. Phase 134 found that the
> `constituencies-selector` axe route had **never once reached a constituency selector** (a bare
> `/constituencies` visit 307-redirects to `/elections`, and the scan settled on a heading that
> resolves on the election page, so it silently duplicated the elections scan). Once the route was
> made to actually arrive, it failed AA: **`color-contrast` × 2 nodes, 1.52:1 light / 1.46:1 dark**,
> caused by `class:faded` (`@apply opacity-30`) compositing `text-secondary` `#666666` to `#d1d1d1`.
> This is steady state, not an in-flight animation, so no settle wait can clear it. Fixed in Phase 134
> under D-17 Option A: the implied-constituency readout is gated on selection instead of dimmed, and
> the now-dead `.faded` rule was removed from `app.css`.

**Fix direction:** stop using `.label` as a layout primitive on primary content, or give the inner span an explicit full-opacity color.

> **RESOLVED.** Taken by `0eb27c677` before this audit was written, via the global `.label { color: inherit }`
> override, which Phase 134 verified AA-clean in both themes and deliberately left in place (D-03).

### 4.2 🔴 D1 — raw i18n key shown to users in all 7 locales (Phase 130, HIGH)

`QuestionChoices.svelte:421-422`:

```ts
? t('questions.multiChoice.selectExact', { count: multiConstraints.effectiveMax })
: t('questions.multiChoice.selectRange', { ... })
```

Those keys exist in `src/lib/i18n/translations/{locale}/questions.json` (the **type-generation** source, which is why they type-check via `translationKey.ts`) but are **absent from the runtime Paraglide catalog** `apps/frontend/messages/{locale}/questions.json` — the path registered at `project.inlang/settings.json:53`. Confirmed: 0 occurrences across all 7 locale catalogs and **0 hits in the generated `src/lib/paraglide/` output**. `t()` imports from `$lib/paraglide/messages` (`i18n/wrapper.ts:1`) and returns the raw key on miss (`wrapper.ts:34,39`).

**Result:** every multi-choice question with authored min/max shows the literal text `questions.multiChoice.selectRange` as its helper.

> **Audit note.** The integration checker classified this as a *stale/incorrect diagnosis, not a live defect*. That conclusion was **wrong** — it inspected `src/lib/i18n/translations/` (type-gen source) rather than `messages/` (runtime catalog). The original Phase 130-05 diagnosis was correct. Verified independently before recording.

**Coverage consequence:** Phase 130 step 18.5 deliberately asserts only helper *visibility*, withholding the content assertion so the phase would not lock in the bug. So the helper text content is asserted nowhere — a small residual coverage gap under EQTYP-01, to be closed together with the fix.

> **⚠ SCOPE CORRECTED 2026-08-10 (Phase 134, D-01c/D-08) — the diagnosis is right, the scope was too
> narrow.** A full key-set diff of both catalogs across all 7 locales found **7** keys in this state,
> not 2, and they span **two** catalog files, not one:
>
> | Key | Catalog file | Call site | User impact |
> | --- | --- | --- | --- |
> | `questions.multiChoice.selectExact` | `messages/{locale}/questions.json` | `QuestionChoices.svelte:421` | visible helper text |
> | `questions.multiChoice.selectRange` | `messages/{locale}/questions.json` | `QuestionChoices.svelte:422` | visible helper text |
> | `components.accordionSelect.listboxAriaLabel` | `messages/{locale}/components.json` | `AccordionSelect.svelte:84` | **`aria-label`** — a screen reader announced the literal dotted key. A WCAG defect, not a cosmetic one, and the most serious of the seven. |
> | `components.multipleTextInput.add` | `messages/{locale}/components.json` | `MultipleTextInput.svelte:206` | visible button text |
> | `components.multipleTextInput.moveUp` | `messages/{locale}/components.json` | `MultipleTextInput.svelte:176` | visible button text |
> | `components.multipleTextInput.moveDown` | `messages/{locale}/components.json` | `MultipleTextInput.svelte:183` | visible button text |
> | `components.multipleTextInput.remove` | `messages/{locale}/components.json` | `MultipleTextInput.svelte:191` | visible button text |
>
> All 7 × 7 landed in Phase 134, with `selectExact` authored as an MF2 plural declaration so a 1-of-1
> constraint reads `Select 1 option.` rather than `Select 1 options.`. The structural follow-on is a
> cross-catalog **key-set parity check** in the unit suite — the reason this class of defect went
> unnoticed is that nothing compared the two catalogs.

### 4.3 🟡 D2 — saved boolean `false` renders as unanswered (Phase 130, MEDIUM)

`apps/frontend/src/routes/candidate/(protected)/questions/+page.svelte:58`:

```ts
if (!localizedAnswer?.value) return undefined;
```

A truthiness guard discards a legitimately saved `false`. Candidates who answer a boolean opinion question "No" see it as still unanswered on the overview.

> **⚠ CORRECTED 2026-08-10 (Phase 134, D-12/D-13) — one site, and a different fix.** Two claims in
> the original wording do not hold:
>
> 1. **The struck clause asserting the completion gating reads this same helper** — the gating does not
>    read this helper and was never defective. `candidateContext.svelte.ts:233` already used
>    `isEmptyValue()`, which returns `false` for a saved `false`. A repo-wide falsy-guard sweep across
>    `apps/` **and** `packages/` (4 grep patterns, 11 distinct hits, each inspected in source) returned
>    exactly **one** genuine defect: this one. The other 10 hits are benign.
> 2. **The prescribed fix** — an explicit null check would have traded one inconsistency for another.
>    A saved empty string or empty array is null-ish only under `isEmptyValue()`; under a bare null
>    check such an answer would start rendering as **answered** on the overview card while
>    `candidateContext`'s `unansweredOpinionQuestions` still counted it unanswered, so the card and
>    the completion counter would disagree in the opposite direction. Phase 134 therefore guards with
>    the canonical predicate — `isEmptyValue(localizedAnswer?.value)`, imported from `@openvaa/data`
>    to match the sibling — so both paths apply one predicate to one value shape. This is a
>    deliberate, operator-approved deviation from the fix as prescribed here and in ROADMAP criterion 3.

### 4.4 🟡 Context Destructuring Rule violation (pre-existing, LOW)

`apps/frontend/src/routes/candidate/(protected)/preview/+page.svelte:32` — `const dataRoot = $derived(ctx.dataRoot);` is verbatim the Phase-117 alias-indirection anti-pattern documented in CLAUDE.md. It does not currently manifest: the `$effect` fires once per page lifecycle and the provide/get calls happen synchronously on the same stable reference. It is fragile to any future out-of-band `#version` bump. Not caused by Phases 123/124.
