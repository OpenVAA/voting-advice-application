<objective>
Close the single verified Phase-129 gap (129-VERIFICATION.md, UNBLK-02 voter-side persistence; corroborated by 129-REVIEW.md WR-01): the voter questions layout persists ANY non-empty multi-choice selection unconditionally, so an out-of-range selection (e.g. 1 of minSelections 2, or 4 of maxSelections 3) silently enters the answers store and pollutes matching while the UI signals "Skip"/unanswered — violating the D-07 contract ("voter app: keep the action button as Skip while outside min/max"; invalid = not a matchable answer). Also AND `opinionInputValid` into the `nextLabel` override so a last-position invalid selection never shows a "Results" CTA.

The fix is NOT the literal WR-01 diff: two hazards found by direct source reading must be handled. (1) `valid` is pushed by an `$effect` in `OpinionQuestionInput` that flushes AFTER the synchronous `onChange` dispatch, so `handleAnswer` would read one-toggle-stale validity — the assignment must move into (be duplicated synchronously in) the multi-choice `onChange` wrapper. (2) `QuestionChoices.selectedMulti` live-tracks the `selectedIds` prop, so deleting the answer on an invalid toggle would wipe the voter's in-progress checkboxes (checkboxes render `checked={selectedMulti.includes(id)}`) — the seed must become question-keyed, with explicit deletes handled via a remount epoch.

Purpose: matching-data integrity for the new multi-choice categorical variant (the substance of UNBLK-02) per D-07.
Output: gated voter persistence path + synchronous validity propagation + a unit-tested shared validity helper; existing 129-01..129-08 work untouched otherwise.
</objective>
