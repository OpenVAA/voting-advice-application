Run the full suite three consecutive times. Per run: kill any process on :5173, run `yarn db:reset`
so the database is clean (never `db:reset-with-data` — the default template pollutes the E2E
dataset), start exactly one fresh dev server, wait for it to serve, then run `yarn test:e2e`.

Restart the dev server for every run without exception. This phase edited Paraglide message JSON
(compiled by a Vite plugin) and a global stylesheet — both are documented HMR-staleness traps in
this repo, and a run against a stale compiled module verifies nothing.

Run the whole suite, not a project subset. Do not set the a11y or performance opt-out env vars; the
new scan entries are exactly what needs proving under parallel pressure. Research's 0-violation
measurements were taken single-worker against a warm server, so this gate is where a timing flake
would surface if one exists.

Record for each run: run number, timestamp, passed / failed / did-not-run counts, and duration.
A "did not run" test counts as a failure, including a cascade from an upstream dependency.

If any run fails: root-cause it, fix it in place — a new flake surfacing mid-gate is in-scope fix
work, never an exemption — and then restart the count at zero. No `.skip`, no `.fixme`, no
retry-until-green, no "known-flaky" annotation. If the failure is a known infrastructure wedge
(repeated `db:reset` returning a storage 502, or an imgproxy 502), recover with a full Supabase
stop/start followed by `db:reset`, assert the `public-assets` bucket exists, then discard that run
and re-run it — and log the discard rather than quietly absorbing it. Never run a bare Supabase
start from the repository root; it steals the Postgres port.

If the count cannot reach 3 within a reasonable budget, stop and escalate honestly with the gate
left red. Do not annotate around it.
