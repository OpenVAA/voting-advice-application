# Plan 135-03 — dev-seed NF-01: remove the load-dependent wall-clock assertion

## Context

`packages/dev-seed/tests/integration/default-template.integration.test.ts:144` asserts
`expect(elapsedMs).toBeLessThan(10_000)` where `elapsedMs` wraps `runPipeline` +
`fanOutLocales` + `writer.write` — i.e. it includes network I/O to a local Supabase.

Measured 2026-08-10 (Phase 134):

| Condition | Result |
|---|---|
| Under turbo's 19-task parallelism + a Vite dev server + Playwright | **FAILS** — 23630ms, and separately 11592ms |
| `cd packages/dev-seed && yarn test:unit` in isolation | **PASSES** — 444/444, ~10143ms whole-test |

The margin is thin even when the machine is quiet. This sits inside the **blocking**
`yarn test:unit` CI step, so it is masked today only because CI runs on a quiet runner —
any future CI parallelism or a slower box turns it into an intermittent red build that
gets blamed on whatever change is in flight. It also silently forbids running the unit
suite alongside a dev server locally.

Note what the test ALREADY asserts deterministically, immediately below the budget line:
`rows.candidates.length === 327`, `rows.questions.length === 26`, `nominations === 377`,
`portraits === 327`, and more. **Correctness is already covered by work-done assertions.**
The wall-clock line is a performance guard riding along inside a correctness test.

## Tasks

<task number="1" name="Make NF-01 load-independent">
<action>
Replace the load-dependent hard gate. Choose ONE of these principled resolutions and
state in the SUMMARY which you chose and why:

(a) **Separate the concerns (preferred).** Remove the wall-clock assertion from this
correctness test, and re-home NF-01 as an explicit performance check that is measured
fairly — e.g. a dedicated test that runs serially / is opted out of parallel execution, or
a benchmark script invoked deliberately rather than on every `test:unit`. The 10s budget
stays meaningful where it can be measured under controlled conditions.

(b) **Assert work, not time.** Replace elapsed-time with a deterministic operation budget
the pipeline can be instrumented for (e.g. number of write round-trips / batched calls),
so a genuine performance regression — an N+1 write, a lost batch — still fails, but
scheduling noise cannot.

(c) **Demote to a pathology signal.** Keep a wall-clock guard but log the duration and
assert only against a threshold that indicates real pathology rather than contention,
with an in-file comment stating plainly that this is no longer a fine-grained budget.

**EXPLICITLY FORBIDDEN:** changing `10_000` to a larger number and leaving everything else
as-is. That preserves the flaky shape and only moves the goalposts — it is the resolution
the todo names as unacceptable. If you choose (c), the comment must make clear the
assertion changed KIND, not just magnitude.

Whichever you choose, do NOT weaken or remove any of the deterministic row-count /
portrait-count assertions. Those are the test's actual correctness value.

Update the file's header docblock (lines ~15 and ~29 reference NF-01 and the 60s timeout)
so it describes what the test now guarantees. Do not leave a docblock asserting a budget
the test no longer enforces.
</action>
