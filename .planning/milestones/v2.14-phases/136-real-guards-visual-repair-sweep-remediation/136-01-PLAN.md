# Plan 136-01 — F1 performance budget + F7 dead wait

## Context (from the sweep, measured — do not re-derive)

**F1** (`tests/tests/specs/perf/performance-budget.spec.ts:65-66`): budgets are 8000ms / 15000ms;
measured actual from the 2026-08-11 full-suite trace is **domContentLoaded 1055ms, loadComplete
1056ms** — 7.6× and 14.2× headroom. Worse, it is structurally blind: `ttfb` is 1045 of that 1055ms
and `loadEventEnd` lands 1ms after DCL, so the measured window **closes at the SSR response** —
before hydration, the Supabase round-trips, match computation, or the results list renders. The spec
then calls `settleNetworkIdle()`, explicitly waiting for work it stopped measuring. **A 10×
matching-algorithm regression moves neither number.** It runs by default in the blocking CI job and
consumes a ~27s `answeredVoterPage` walk per run to assert nothing.

**F7** (`tests/tests/fixtures/voter/voter-journey.fixture.ts:384-387`): a measured **10.0s dead
wait** on every `answeredVoterPage` invocation — 38% of that fixture's 26.4s. Every consumer pays it
(a11y scans, visual, perf, voter journeys).

<task number="1" name="Make the performance budget measure the page">
<action>
Re-point the assertion at a metric that moves when the results page gets slower. Candidates: time to
the results list being visible (the thing a user waits for), Largest Contentful Paint, or a
hydration-complete signal — choose based on what is measurable deterministically here and say why.
Set the threshold from MEASURED actual with a defensible multiplier, and record the measurement.

If no metric can be measured deterministically enough to gate on, the honest outcome is to DELETE
the spec and say so — a ~27s CI cost for zero signal is worse than no test. Deleting is an
acceptable resolution for this task; pretending is not.

**Forbidden:** keeping `domContentLoaded`/`loadComplete` with smaller numbers. The metric is the
defect, not the threshold.
</action>
