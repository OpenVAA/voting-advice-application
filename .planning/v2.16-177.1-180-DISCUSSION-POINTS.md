### 177.1-A. `p_confirm_entity`

#### 177.1-A1 — What `true` does for an entity that has no name

Today a nameless entity is silently left unconfirmed (fact 1), and INV-05 speaks only of an entity "seeded
with a name". The typical nameless case is a code for a party that will name itself after signing in.

- [ ] **(a) Keep the name condition, and say so in the answer** — ★ RECOMMENDED — `true` confirms every
      named entity of the batch; a nameless one stays unconfirmed, and each returned item carries whether its
      entity is now confirmed. A batch may mix named and nameless entities, and the admin reads the outcome
      instead of assuming it.
- [ ] **(b) Refuse the batch** — `22023` naming the item. Nothing the caller asked for is quietly dropped.
      A batch that mixes named and nameless entities then needs two calls, one with `true` and one with
      `false`.
- [ ] **(c) Confirm whatever the name** — the parameter means exactly what it says. An entity with an empty
      name can then be confirmed, which locks the name fields for the user who was meant to fill them in
      (the name freezes on confirmation).

#### 177.1-A2 — What `false` does for an entity that is already confirmed

- [ ] **(a) Nothing: `false` means "this call confirms no one", never "unconfirm"** — ★ RECOMMENDED —
      inviting a second user to a party voters already see cannot hide it. An admin unconfirms an entity by
      editing the entity.
- [ ] **(b) `false` sets the entity unconfirmed** — the parameter states the resulting state. An invitation
      for a public entity sent with `false` would then take it out of the voter app by side effect, the
      mirror image of the defect this phase removes.

#### 177.1-A3 — One value for the call, or a value per invitation

Criterion 1 names a parameter, so one value per call is the ruled form. The question is whether an item may
override it.

- [ ] **(a) One value per call; no item key** — ★ RECOMMENDED — one place to look. A batch that wants both
      is two calls.
- [ ] **(b) An optional `confirm_entity` key on an item overrides the parameter** — one call for a mixed
      batch. Two places decide the same thing, and each needs its pgTAP rows and its paragraph in the docs.

### 177.1-B. The nominations

#### 177.1-B1 ⚠ DECIDE — A separate parameter, or a key on each invitation

Left open by F3 (a). `set_entity_nominations` takes its entity as two arguments, so its nomination objects
do not say whose they are (fact 12). `create_invitations` takes a batch of invitations for different
entities.

- [ ] **(a) A `nominations` key on each entity-scope invitation, holding the array** — ★ RECOMMENDED — the
      objects keep exactly 177's keys, because the invitation already names the entity, and an invitation
      reads as one complete statement. Criterion 2's "takes an optional `p_nominations`" is reworded.
      Stating nominations for one entity on two items of a batch is refused, as is the key on a
      project-scope item.
- [ ] **(b) A separate `p_nominations` array, each object also naming its entity** — criterion 2 to the
      letter. Every object gains `target_type` and `target_id` or `external_id`, so the shape is no longer
      177's; the entity is stated twice; and a rule is needed for a nomination that names an entity the
      batch does not invite.
- [ ] **(c) A separate `p_nominations` array aligned with `p_invitations` by position** — 177's keys and a
      parameter both. One inserted or removed invitation silently shifts every nomination after it to
      another entity.

#### 177.1-B2 ⚠ DECIDE — What the call does to nominations the entity already has

`set_entity_nominations` is planned as the entity's whole set: a row the set leaves out is deleted
(fact 12). An invited entity often has nominations already, from an import.

- [ ] **(a) Create or update, never delete** — ★ RECOMMENDED — an object with an `id` describes that row
      and changes it where it differs; an object without one is a new row; a new row at a contest where the
      entity already stands under the same parent is refused by the existing uniqueness key. A missing key
      and an empty array both write nothing. Inviting someone can never remove a nomination.
- [ ] **(b) The whole set, as in 177** — one meaning for both writes. An invitation sent with an empty
      array, or with only the new nomination, deletes the entity's other nominations in its reach.
- [ ] **(c) Insert only** — the simplest function: every object is a new row, and `id` is not read. An
      admin cannot correct a nomination through an invitation, and a dataset that already seeds the
      nomination must stop seeding it (177.1-D2 does that for the journey either way).

#### 177.1-B3 — A nomination's `confirmed` when the object does not state it

`confirmed` is an admin-only key (criterion 2). The entity's confirmation is required to be stated
(criterion 1), and criterion 4 asks for the nomination "stated outright".

- [ ] **(a) Required on every nomination object; a missing key is refused with `22023`** — ★ RECOMMENDED —
      no default can surprise in either direction: nothing is published by omission, and an admin who
      confirms the entity does not find it invisible because its nomination silently stayed unconfirmed.
      One more key on every object.
- [ ] **(b) Defaults to `false`, the column's default** — nothing becomes public by omission. A confirmed
      entity whose nomination was left out stays hidden from voters with no message saying why.
- [ ] **(c) Follows `p_confirm_entity`** — one switch for both. The journey's hidden candidate needs the
      two to differ (177.1-D1), and one call could then not state that.

A project editor is refused for `confirmed: true` (fact 10) under every option; that rule is not this
phase's to change.

#### 177.1-B4 — The election round

177's shape carries no round: a new nomination is written at its election's `current_round` (fact 12).
Criterion 2 lists "the election round" among the keys.

- [ ] **(a) An optional `election_round` key; absent means the election's `current_round`** —
      ★ RECOMMENDED — the common case needs nothing, and an admin can still seed a nomination for another
      round. Criterion 2 is reworded from a key the object has to a key it may have.
- [ ] **(b) Required** — the round is always stated. Every caller must first read the election's current
      round to write the ordinary case.
- [ ] **(c) No round key; always the current round, as in 177** — the same shape to the last key. A
      nomination for another round still needs `bulk_import`.

The nomination's other writable columns (`name`, `short_name`, `info`, `color`, `image`, `sort_order`,
`subtype`, `external_id`) are accepted under their column names, as criterion 2 says. `custom_data` is
merged, so the typed-party key that `parent.kind = other` sets is not overwritten.

#### 177.1-B5 — How a nomination names its election, constituency and parent

`create_invitations` already accepts an `external_id` for the invited entity and looks it up in the project
(fact 2). 177's shape names everything by uuid.

- [ ] **(a) Uuids only, as in 177** — ★ RECOMMENDED — the same keys with the same meaning. A caller that
      works from external ids, as the E2E admin client does, resolves them before the call; it already does
      so for the entity.
- [ ] **(b) Each of the three may instead be named by an external id** (`election_external_id` and so on) —
      a seed file can be written without a lookup. Three more keys, a lookup branch for each, and the shape
      departs from 177's.

#### 177.1-B6 — Which entity types and which parents an admin may state

`set_entity_nominations` serves candidates and organizations, and pairs the parent's type with the
caller's (fact 12). The hierarchy also allows a faction as a candidate's parent, and an invitation can name
a faction or an alliance.

- [ ] **(a) As in 177: candidate and organization only, a candidate's parent an organization, an
      organization's an alliance; `none`, `entity` and `other` as there, `keep` only with an `id`** —
      ★ RECOMMENDED — one rule for both nomination writes, and the shared parent function (177.1-C1) has one
      pairing. `nominations` on an invitation for a faction or an alliance is refused with `22023`; those
      rows stay with `bulk_import`.
- [ ] **(b) Everything the hierarchy allows** — an admin can seed a faction's or an alliance's nominations,
      and a candidate under a faction, in the invitation call. The parent function then serves pairings the
      self-nomination path must still refuse, and the pgTAP grid grows by each of them.

#### 177.1-B7 — What the call answers

- [ ] **(a) Each returned item gains `entity_confirmed` (the entity's state after the call, null on a
      project-scope item) and, when it stated nominations, `nominations` with 177's counts** —
      ★ RECOMMENDED — `inserted`, `updated`, `unchanged`, `parents_created`. The caller sees what happened
      without a second read, and the nameless-entity case of 177.1-A1 is visible.
- [ ] **(b) The answer stays as it is** — nothing to document. A caller that needs the outcome reads the
      rows back, and a silently unconfirmed nameless entity is found only by looking.

#### 177.1-C2 — Whether a parent nomination the call creates is confirmed
