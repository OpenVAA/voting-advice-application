# Phase 189.1.1: Code Review Report (gap plans 21 and 22)

**Reviewed:** 2026-11-26T18:27:58Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

I reviewed the 13 files changed against `81b80140f` (commits 408158c7e, 5b924d557 and 43d988840). The change gives E2E waits on the address budgets of N times `TIMEOUTS.slowPage`, where N is the number of server answers that the triggering action returns before. I checked every new budget against the frontend code that the action really runs: `passwordLoginAction.ts`, `(protected)/+page.server.ts`, the profile page's `handleSubmit`, `entityUserDataState.save`, `rereadPageData` and `supabaseDataWriter._updateEntityProperties`.

The rule itself is sound, but the change does not apply it consistently:

- **Sign-in to an entity's home.** `expectOnHome` was given the budget of one server answer. Eleven call sites in `contestant-entity-selection.spec.ts` use it straight after a sign-in, which is the three-answer chain that `SIGN_IN_REDIRECT_TIMEOUT` documents (CR-01).
- **Profile save.** `PROFILE_SAVE_TIMEOUT` undercounts the save. It leaves out the `invalidateAll` re-read and the storage upload. One save a spec runs makes four answers in a row against a budget of three (CR-02).
- **Settings after sign-in.** One budget comment describes a redirect through the app root that the code does not make (WR-01).
- **Unchanged waits.** Several waits that hold the same chains were left at the old budgets, both in the reviewed spec and in sibling fixtures (WR-02, WR-03).
- **Structure.** A page-object fixture now imports from a setup module (WR-04). The new N-times-`slowPage` constants are duplicated across eight files instead of living in `timeouts.ts` (WR-05).

The deployed-smoke closure files changed only in budgets and their comments:

- `contestantLoginPage.fixture.ts`: four timeout values and four explanatory comments.
- `contestantLogoutButton.fixture.ts`: one timeout value, one comment, and an import of `TIMEOUTS` from `../../helpers`. That barrel is already in the smoke's closure through `contestant.smoke.ts`.

`tests/tests/utils/deployedSmokeGuards.test.ts` passes (20/20), and ESLint passes on all 13 files. TypeScript is strict throughout: no `any`, and the `expectAddress` parameter type `RegExp | ((url: URL) => boolean)` matches `toHaveURL`'s overloads.

Comment hygiene: I found no historical narrative and no planning references. The one redundant comment is IN-02.

## Critical Issues

### CR-01: `expectOnHome` has a one-answer budget but is called right after sign-ins, which are three-answer chains

**File:** `tests/tests/fixtures/contestant/contestant-entity-selection.ts:263-268, 292-293`

**Issue:** The new `expectPath` documents its budget as "the budget of a server round trip" (`TIMEOUTS.slowPage`), and `expectOnHome` uses it. In `tests/tests/specs/contestant/contestant-entity-selection.spec.ts`, `expectOnHome` runs directly after `contestantLoginPage.login(TEST_LOGOUT_ENTITY_EMAIL, …)` at lines 344→345, 368→369, 396→397, 432→433, 468→469, 1065→1066, 1626→1627, 1680→1681, 1707→1708, 1762→1763 and 1791→1792.

That user edits exactly one organization (`testCredentials.ts:29`), so each of these sign-ins makes three server answers before the address changes:

1. The form action answers with a 303 to `ContestantAppHome` (`passwordLoginAction.ts:65`).
2. The root's `__data.json` answers with the 307 of `(protected)/+page.server.ts` (the `entities.length === 1` branch).
3. The entity home's `__data.json` answers.

This is exactly the chain whose TSDoc in `registerAndStoreSession.ts:21-26` sets `SIGN_IN_REDIRECT_TIMEOUT = 3 * TIMEOUTS.slowPage`. The same diff gives `contestantEntitySelectionPage.expectShown` that budget because the screen "may be reached by a sign-in". `expectOnHome` is reached by a sign-in far more often and still waits one answer.

By the diff's own rule, these eleven waits have one third of their budget. Under load they are a timing failure that runs green on an idle host. Under the project's E2E hard rule, that is a defect, not an acceptable flake.

**Fix:** Let the path wait take the budget of the action that led to it, and give the sign-in callers the sign-in's budget:
```ts
async function expectPath(pathname: string, timeout: number = TIMEOUTS.slowPage): Promise<void> {
  await expect(page).toHaveURL(exactPathRe(pathname), { timeout });
}
// …
/** Assert the page is that entity's home … The home may be reached by a sign-in, so the address has the sign-in's budget. */
async expectOnHome(entity: SelectionEntity): Promise<void> {
  await expectPath(homePath(entity), SIGN_IN_REDIRECT_TIMEOUT); // constant moved to helpers/timeouts.ts, see WR-04/WR-05
  …
}
```

### CR-02: `PROFILE_SAVE_TIMEOUT` leaves out the re-read and the upload, so a save that specs run makes four answers against a budget of three

**File:** `tests/tests/fixtures/contestant/contestantProfilePage.fixture.ts:88-93`

**Issue:** The TSDoc says the save "writes the answers, the other properties and the names, three server answers in a row … The destination inside the entity adds no answer." The profile page's `handleSubmit` does more than that before it navigates:

- **The re-read.** After any stored property, `+page.svelte:304` runs `if (result.listedPropertySaved) await rereadPageData(LOG_LABEL)`. That is `invalidateAll()` (`rereadPageData.ts:16-17`): a fourth, awaited server answer, and `goto` runs only after it.
- **The image upload.** A new image is uploaded to Storage inside the "other properties" write, before that write's own request (`supabaseDataWriter.ts:702-717`, `#uploadEntityFile`). A `File` answer is uploaded the same way inside `_setAnswers` (`supabaseDataWriter.ts:627-651`).

`perm-organization-editing.spec.ts:252-258` fills the names, uploads a logo and calls `save({ expect: 'navigation' })`. That save makes four answers in a row: the logo upload, the property write, the names write, and the re-read. `expectLeftAfterSave` gives it 3 × `slowPage`. A save with an answer, a new logo and names would make five.

The diff's rule, one slow page per answer, is therefore broken at a site the specs run. The TSDoc's own count is also wrong.

**Fix:** Count the longest chain the page can run, and document it accurately:
```ts
/**
 * How long a profile save may take to leave the profile page: the answers' write, the image's upload, the other properties' write,
 * the names' write and, after any stored property, the re-read of the page's data, five server answers in a row,
 * each given a slow page's time, before the application navigates.
 */
export const PROFILE_SAVE_TIMEOUT = 5 * TIMEOUTS.slowPage;
```

## Warnings

### WR-01: `expectLedToSettings`'s budget comment describes a redirect through the app root that does not happen

**File:** `tests/tests/fixtures/contestant/contestantLoginPage.fixture.ts:349-352`

**Issue:** The comment says "A sign-in reaches the settings after the form's post, the app's root and the settings' data: three answers". Both callers sign in from a sign-in screen that carries the settings page as its `redirectTo`:

- `contestant-email-registration.spec.ts:454-459`
- `contestant-entity-selection.spec.ts:820-829`

For a valid `redirectTo`, the action answers `redirect(303, `/${locals.currentLocale}/${redirectTo}`)` (`passwordLoginAction.ts:65`), which goes straight to the settings page. The app root is never visited, so the chain is two answers.

The 3× budget is larger than needed, so this is not a timing failure. The problem is the comment: it states a mechanism the code does not have, and it would mislead anyone who later reasons from it.

**Fix:** `// A sign-in that carries the settings as its redirect target reaches them after the form's post and the settings' data: two answers, each given a slow page's time.` with `timeout: 2 * TIMEOUTS.slowPage`. Or keep 3× and give the real reason.

### WR-02: Waits in the reviewed journey spec that hold the same sign-in or save chains keep the old budgets

**File:** `tests/tests/specs/contestant/contestant-journey.spec.ts:553-556, 675-678, 986-987, 1019-1020`

**Issue:** The diff budgets the URL waits after the password reset (line 530) and after the profile saves (lines 716 and 731). The same file still has waits that hold equivalent or longer chains:

- **553-556 (step 9).** `submit()` signs in, which is three answers, then a status-message wait of `TIMEOUTS.slowPage`.
- **675-678 (step 13).** A profile save with a portrait upload, then the home's status message at `TIMEOUTS.slowPage`. Step 13.5 runs the same save kind and got `PROFILE_SAVE_TIMEOUT`.
- **986-987 and 1019-1020.** `login()` (three answers), then `contestantHomePage.expectStatusMessage()`. That method is `expect.soft(status).toBeVisible()` with the default 5 s expect timeout (`contestantHomePage.fixture.ts:163-165`). That is half of one `slowPage` for a three-answer chain. Because the assertion is soft, a timeout lets the test go on and fail later at an unrelated step.

These are element waits rather than URL waits. They are still the first wait after an action that returns before its answers, so the gap's own rule covers them.

**Fix:** Before each element wait, add a URL settle with the chain's budget, as step 13.5 does:
```ts
await page.waitForURL(contestantHomeUrlRe(), { timeout: SIGN_IN_REDIRECT_TIMEOUT });
```
Or give the element wait that budget. Replace the soft `expectStatusMessage()` after a sign-in with a hard wait that has the sign-in budget.

### WR-03: Sibling fixtures outside the diff keep one-answer budgets for sign-in and save chains

**File:** `tests/tests/fixtures/contestant/contestantEntityPages.fixture.ts:56-57`; `tests/tests/fixtures/contestant/contestantEntityHomePage.fixture.ts:113-117`

**Issue:** Commit 43d988840 is titled "budget every URL wait that holds server answers its action does not wait for", but these two fixtures were not changed:

- **`contestantEntityPages.fixture.ts`.** `expectUrlOfEntity` waits `TIMEOUTS.slowPage`. `perm-unnominated-entities.spec.ts:1115-1116` reaches it straight after a sign-in, which is three answers. `:747-748` reaches it straight after a profile save (see CR-02).
- **`contestantEntityHomePage.fixture.ts`.** `expectLanded` waits `TIMEOUTS.slowPage` for the status message, then `toHaveURL` at the default timeout. `contestant-password-recovery.spec.ts:201-202, 250-251, 290-291` reach it straight after `login()`.

`contestantEntityPages.fixture.ts` is also a near-duplicate of the `createContestantEntityPages` this diff edits. That duplication is why one copy got budgets and the other did not.

**Fix:** Give these waits the same budgets: a `timeout` parameter on `expectUrlOfEntity`, and the sign-in budget in `expectLanded`. Follow up by merging the two entity-pages fixtures.

### WR-04: A page-object fixture now imports from a setup module that loads the service-role client

**File:** `tests/tests/fixtures/contestant/contestantEntitySelectionPage.fixture.ts:24`

**Issue:** `import { SIGN_IN_REDIRECT_TIMEOUT } from '../../setup/shared/registerAndStoreSession'` is the only import from a fixture into `setup/` in the tree (`grep -rn "from '../../setup" tests/tests/fixtures`). `registerAndStoreSession.ts` imports `fs`, `SupabaseAdminClient` and `createContestantLoginPage` by value, and `SupabaseAdminClient` in turn imports `@openvaa/supabase-types` by value.

So loading the selection-screen page object now also loads the service-role client and a workspace package. `supabaseAdminClient.ts` is in `FORBIDDEN_FILE_NAMES` of `deployedSmokeGuards.test.ts`, so any future smoke that uses this page object fails that guard for a reason unrelated to its own code. The import also makes a fixture depend on setup, and setup already depends on fixtures. No cycle exists yet, but the next edge in that direction would make one.

**Fix:** Move the budget constants into `tests/tests/helpers/timeouts.ts`, which is a leaf module with no workspace imports and is already in the smoke's closure. Import them from there in both `registerAndStoreSession.ts` and the fixture.

### WR-05: Each N-times-`slowPage` budget is defined again in each file that uses it, outside the declared single source of truth

**File:** `tests/tests/fixtures/contestant/contestantIdentityProviderGate.fixture.ts:48`, `contestantNothingToEditPage.fixture.ts:31`, `contestantLoginPage.fixture.ts:258, 313, 329, 351`, `contestantLogoutButton.fixture.ts:50`, `contestantRegisterPage.fixture.ts:105`, `adminLoginPage.fixture.ts:69`, `setup/shared/registerAndStoreSession.ts:26`, `specs/contestant/contestant-journey.spec.ts:211`

**Issue:** The same budgets are written out again and again:

- **The sign-out budget, 2 × `slowPage`.** Defined twice as `SIGN_OUT_TIMEOUT` with word-for-word identical TSDoc. Written inline three more times in the login and logout-button fixtures. Defined once more as `ADMIN_LOGIN_REDIRECT_TIMEOUT`.
- **The identity-provider round trip, 5 × `slowPage`.** `IDENTITY_PROVIDER_ROUND_TRIP_TIMEOUT` in the register fixture, and again inline in `continueWithIdentityProvider`.
- **3 × `slowPage`.** Defined three more times, as `SIGN_IN_REDIRECT_TIMEOUT`, `PROFILE_SAVE_TIMEOUT` and `PASSWORD_RESET_REDIRECT_TIMEOUT`, and once more inline in `expectLedToSettings`.

`timeouts.ts` opens with "Single source of truth for spec timeouts". The code-review checklist rules out code repeated within a PR. The inline copies in the two smoke-closure fixtures look like a workaround for the closure, but `helpers/timeouts.ts` is already reachable from the smoke and would have served them. The cost of the repetition is that the copies drift, which is how CR-01 came about.

**Fix:** In `timeouts.ts`, add one documented helper and the named chain budgets:
```ts
/** The budget of a wait that holds `answers` server answers in a row, each given a slow page's time. */
export function serverAnswersTimeout(answers: number): number {
  return answers * TIMEOUTS.slowPage;
}
export const SIGN_OUT_TIMEOUT = serverAnswersTimeout(2);
export const SIGN_IN_REDIRECT_TIMEOUT = serverAnswersTimeout(3);
export const IDENTITY_PROVIDER_ROUND_TRIP_TIMEOUT = serverAnswersTimeout(5);
```
Import them everywhere, the two smoke-closure fixtures included.
