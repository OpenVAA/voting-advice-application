### What the reset removes and what it leaves

The pinned CLI (`supabase` 2.118.0, `node_modules/.bin/supabase`) carries the remote reset's SQL in its binary; it was read there (`strings`, session scratch directory) and is what the following says. For a linked target the CLI asks "Do you want to reset the remote database?" (answered by `--yes`), prints `Resetting remote database...`, and then, on one connection:

1. In **one transaction**: drops every schema not owned by `supabase_admin` and not a platform schema (so `public` and `private` with every table, row, function, trigger and type), every extension but `pg_graphql`, `pg_net`, `pg_stat_statements`, `pgcrypto`, `pgjwt`, `pgsodium`, `plpgsql`, `supabase_vault` and `uuid-ossp`, every policy of `pg_policies` (those on `storage.objects` included), every publication but the realtime ones, and **truncates every table of `auth`** (but its `schema_migrations`), of `supabase_functions` and of `supabase_migrations`. A failure in this part rolls back and nothing is lost.
2. Applies each file of the work directory's `supabase/migrations`, printing `Applying migration <file>...` (here four). A failure here leaves the database without what part 1 dropped; the sitting stops there.
3. With `--no-seed`, runs no seed (`seed.sql` holds the local demo key and users).

**Lost:** every row of staging's database: the 1001 smoke candidates and nominations, the election, the questions, the account, the project and its settings row (`analytics.trackEvents` true included), both `storage_config` rows, `private.deployment_settings` (`behind_cloudflare` true), `private.access_throttle`, feedback, grants and terms acceptances; **every auth user**, the smoke contestant, **Step 21's first administrator (the user and its project-scope `admin` grant)** and any user a test or a person created; and the 24-version migration history, replaced by four. **Step 21 is not redone** (D-16 does not order it): after the sitting staging has no administrator, until Step 21 is run again.

**Rebuilt by the sitting:** the bootstrap rows with `behind_cloudflare` true and the project open for voters, the `smoke` dataset (1001 candidates and nominations, and its settings row), the smoke contestant, and `analytics.trackEvents` true.

**Left as it is:** the storage buckets and their objects (the storage schema is not truncated, so the old candidates' portraits stay in `public-assets` as files no row names), Vault, the hosted auth and API settings and the function secrets (the Terraform root's), the three deployed functions (the 189.1-07 code, whose `account-access` calls `invitation_caller_take`, which `00003` and `00004` define), the served frontend `2ddc331d1`, the GitHub environment's secrets and variables, and the keychain item `openvaa-staging-smoke-contestant`.

**While the sitting runs** staging serves no election and refuses every sign-in from the drop until the migrations have recreated the access-token hook's function, and voters see no candidates until the seed has finished (about 5 to 15 minutes).
