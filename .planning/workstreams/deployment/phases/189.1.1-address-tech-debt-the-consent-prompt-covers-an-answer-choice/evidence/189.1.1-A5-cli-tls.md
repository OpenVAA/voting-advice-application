# 189.1.1 A5: the Supabase CLI's own connection under verify-full

Measured 2026-11-27 on the developer host, after the security audit of 189.1.1 raised residual R-1: no run had shown whether `supabase db push` honours `PGSSLMODE` and `PGSSLROOTCERT`. The CLI is the pinned 2.118.0 (`node_modules/.bin/supabase --version`), whose platform binary is a Bun-compiled bundle. Nothing reached a hosted service: the measurement runs against a local Postgres 17 serving TLS, with a profile whose API URL is a closed loopback port and a dummy access token. Every IPv4 address reads `ADDRESS`, and no pooler host of staging appears.

The script is `evidence/189.1.1-A5-cli-tls.sh`. It creates two throwaway CAs and a server certificate that CA A signs for `aws-0-a5.pooler.localtest.me`. `localtest.me` names resolve to the loopback, so the CLI's real linked code runs against the local server. It turns on `log_connections`, so each session's TLS state is read from the server's own log. It then runs five cases: the right root, a wrong root, the pipeline's committed Supabase root (which did not sign this server), a host the certificate does not name, and a control with no `PGSSLMODE`.

## What the binary does (static reading of the bundle)

- `supabase db push --linked` resolves its connection in `Rje`. It first opens a TCP connection to the direct host `db.<ref>.<project_host>:5432` (`m_r`, 5 s timeout). If that connects, the CLI uses `{host, port, user: "postgres", password, database}`, an object that never passes the libpq-style parser, so `PGSSLMODE` and `PGSSLROOTCERT` are not read. Only when the direct host does not connect does it read `supabase/.temp/pooler-url` (`LPt` → `$oe` → `Cc`).
- `Cc` parses a connection URL as libpq does: `sslmode` from the URL, then a service file, then `PGSSLMODE`; `sslrootcert` likewise with `PGSSLROOTCERT`; the password from the URL or a password source, `PGPASSWORD` included. `qCe` maps `verify-full` to `rejectUnauthorized: true` with the CA and the server name.
- `--db-url <url>` goes to `Cc` directly, with no direct-host probe.
- The 2.118.0 debug output prints neither `Using connection pooler` nor `Resolved DNS`, which is why `push-migrations.sh` printed `push_connection=unknown` in every run.

## Which path the pipeline took

The staging project's direct host `db.cofbsatfrdysyphajsky.supabase.co` has an AAAA record and no A record (DNS read 2026-11-27), and GitHub-hosted runners have no IPv6 route, so on the runner `m_r` fails and the CLI took the pooler path of Result 1. The pushes recorded in this phase were therefore verified. The direct path stays reachable if the project gains an IPv4 address (the IPv4 add-on) or the runner gains IPv6, and then the push would verify nothing.

## The fix: `push-migrations.sh` gives the CLI `--db-url`, never `--linked`

The script now builds `postgresql://$PGUSER@$PGHOST:$PGPORT/$PGDATABASE` from the variables it already gave the drift check, refusing unless they name the project: the direct host with `postgres`, or one session pooler host with `postgres.<ref>`, not port 6543, no `PGHOSTADDR` or `PGSERVICE`, and `PGPASSWORD` set. The URL holds no password, `sslmode` or `sslrootcert`, so the CLI reads `PGPASSWORD`, `PGSSLMODE` and `PGSSLROOTCERT` as psql does. `push_connection=` now prints the path the address takes. The unit tests: `infra/scripts/push-migrations.test.ts` 39/39 green; against the previous script, 19 failed and 20 passed; `yarn test:unit:infra` 557/557.
