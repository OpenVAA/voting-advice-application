## Warnings

### WR-01: `saveThroughReread` waits one slow page for a re-read that comes third in a chain of three answers

**File:** `tests/tests/fixtures/contestant/contestantProfilePage.fixture.ts:496-502` (the `reread = page.waitForResponse(… LOAD_DATA_REQUEST …, { timeout: TIMEOUTS.slowPage })` in `saveThroughReread`), caller `tests/tests/specs/perm/perm-organization-editing.spec.ts:615` ("profile: a name edited before a confirmation is refused by name")

**Issue:** The test edits the name and the colour. The administrator then confirms the organization, and the test calls `saveThroughReread()`. The page's `handleSubmit` runs `userData.save()`, and `entityUserDataState.save` writes the other properties first: the colour, as answer 1. It then writes the names, which are refused, as answer 2. Only then does the `nameRefused` branch in the profile page's `+page.svelte` run `await rereadPageData(LOG_LABEL)`, which is `invalidateAll()`, and that makes the `__data.json` the fixture waits for: answer 3.

The `waitForResponse` is armed before the click with `TIMEOUTS.slowPage`. So it holds three serial answers on the budget of one. That is the same undercount as CR-02, at a third of the budget instead of three quarters. It sits a few lines below `expectLeftAfterSave`, which the fix gave `PROFILE_SAVE_TIMEOUT`. On an idle host it passes, and under load it times out. Under the E2E hard rule that is a defect.

`save({ expect: 'message' })` at line 479 is safe for its one caller, the `NAME_REFUSED_SCAN` reach at `perm-organization-editing.spec.ts:738`. That reach writes only the names, and the page sets `saveMessage` before it re-reads, so one answer comes before the message. The branch has no budget for a save that writes more than that, though.

**Fix:** Budget the re-read by the chain it closes, and say so:
```ts
// The re-read follows the save's writes: the other properties', the names', then the loads' data.
const reread = page.waitForResponse((response) => new URL(response.url()).pathname.endsWith(LOAD_DATA_REQUEST), {
  timeout: PROFILE_SAVE_TIMEOUT
});
```
In `save`, give the `message` branch the same budget, because any write of the save can come before the message:
```ts
await expect(saveMessage).toHaveAttribute('data-outcome', /.+/, { timeout: PROFILE_SAVE_TIMEOUT });
```

### WR-02: A contestant sign-in in `admin-account-flows.spec.ts` is followed by a wait with the default 5 s expect timeout

**File:** `tests/tests/specs/admin/admin-account-flows.spec.ts:320-322` (`contestantLoginPage.login(email, CHOSEN_PASSWORD)` → `contestantLoginPage.expectSignInNotShown()`); `tests/tests/fixtures/contestant/contestantLoginPage.fixture.ts:399-401` (`expectSignInNotShown`)

**Issue:** `expectSignInNotShown` is `expect(page.getByTestId(ids.signInPage)).toHaveCount(0)`, and it passes no timeout. `playwright.config.ts` sets no `expect.timeout`, so the wait gets Playwright's default of 5 s.

After `login()`, SvelteKit keeps the sign-in screen mounted until the whole navigation has loaded. That is the post's 303, the root's `__data.json`, and then either the 307 to the home of the one candidate the user edits (`editorGrantOn(ADMIN_FLOWS_CANDIDATE)`) or a gate. So the wait holds two or three server answers on half of one `slowPage`.

This is the same class as the old CR-01 and WR-02, in a spec the gap's commits did not touch. It is the only wait I found straight after a contestant sign-in that still has a budget below the sign-in's. Every other one goes through `expectOnHome`, `expectLanded`, `expectShown`, `expectLedToSettings`, `expectErrorMessage` (no navigation) or `expectHomeAfterSignIn`.

**Fix:** Let the step take the budget of the action that led to it, as `expectPath` does now:
```ts
/** Assert that the sign-in screen is not rendered. The screen may be left by a sign-in, so the wait has the sign-in's budget. */
async expectSignInNotShown(): Promise<void> {
  await expect(page.getByTestId(ids.signInPage)).toHaveCount(0, { timeout: SIGN_IN_REDIRECT_TIMEOUT });
},
```

### IN-02: `PROFILE_SAVE_TIMEOUT`'s TSDoc presents five answers as the save's chain, but a save with file answers makes more

**File:** `tests/tests/helpers/timeouts.ts:74-77`

**Issue:** The TSDoc lists "the answers' write, the new image's upload, the other properties' write, the names' write and … the re-read", five in a row. `_setAnswers` (`supabaseDataWriter.ts`, the `for (const [questionId, answer] of Object.entries(answers))` loop) awaits one `#uploadEntityFile` for each `File` answer before `upsert_answers`, so the chain is 5 + the number of file answers. The fix report says the TSDoc "counts the longest chain the page runs", which is not quite true.

No spec saves a `File` answer, so five covers every save the suite runs. The only uploads in specs are `uploadPortrait` and `uploadLogo`, which are image properties. That is why this is Info.

**Fix:** Qualify the count, for example "…five server answers in a row for a save with no file answer; each file answer adds its upload before the answers' write", or count one file answer and use `serverAnswersTimeout(6)`.

### IN-03: `expectHomeAfterSignIn` repeats a step three fixtures already provide

**File:** `tests/tests/specs/contestant/contestant-journey.spec.ts:212-219`

**Issue:** The helper waits for `contestantHomeUrlRe()` within `SIGN_IN_REDIRECT_TIMEOUT` and then for the home's status message within `slowPage`. Three fixtures already do the same:

- `expectOnHome` in `contestant-entity-selection.ts`: path, then status message
- `expectOnHome` in `contestantEntityPages.fixture.ts`
- `expectLanded` in `contestantEntityHomePage.fixture.ts`: status message within the sign-in budget, then URL

Keeping a step that one spec uses inside that spec follows the checklist, but the checklist also asks for "no code that is repeated … elsewhere in the repo". Meanwhile the journey's own `contestantHomePage.expectStatusMessage()` is still the soft check with a 5 s timeout. It is now safe only because each of its remaining callers (`contestant-journey.spec.ts:910`) settles the URL first.

**Fix:** Give `contestantHomePage` a hard landing step, for example `expectLandedAfter(timeout)`, and use it in place of the spec-local helper. Or document on `expectStatusMessage` that it must follow a URL settle.
