## Summary

**One finding blocks every staging deploy in this phase, and no CONTEXT decision covers it (Blocker B-1).** Hosted staging (`deploy/staging` = `2ddc331d1`, deployed 2026-11-21) was built from a tree that holds **24 migrations, `00001`–`00024`**, and its `account-access` function calls `invitation_caller_take`. Since then, commit `bba309b72` ("regenerate the baseline from schema/ and drop migrations 00002-00024") has restacked this branch. HEAD now holds **4 migrations**: `00001_initial_schema`, `00002_refusal_codes`, `00003_invitation_caller_limit` and `00004_access_caller_limit`. The pinned Supabase CLI 2.118.0 refuses that history ("Remote migration versions not found in local migrations directory.", found in its binary). The next pipeline run from HEAD will therefore fail in the `migrations` step. The run cannot reach `verify-full` green (D-12), the staging re-measure (D-07) or the wrapper drop (D-14c) until the operator rules how staging's history is reconciled. Hosted staging also does **not** run the renamed functions yet, which contradicts D-14c's premise. The planner must put an operator checkpoint first in the pipeline track.

**D-09 is satisfied, and was measured this session without credentials.** `aws-0-eu-north-1.pooler.supabase.com:5432` is the value of `vars.SUPABASE_POOLER_HOST` (read with `gh variable list --env staging`). It serves `CN=*.pooler.supabase.com` (SAN `*.pooler.supabase.com`, `*.pooler.supabase.co`), signed by Supabase Intermediate 2021 CA, which is signed by **Supabase Root 2021 CA** (valid to 2031-04-26). libpq 17.6 with `sslmode=verify-full` and that root got past TLS to Supavisor's own `tenant/user ... not found` reply. It was refused with `certificate verify failed` for the system bundle and for a wrong CA. It was refused with `server certificate for "*.pooler.supabase.com" ... does not match host name` for a wrong host name. Supavisor's source advertises only `SCRAM-SHA-256`, with no `-PLUS` variant, so `PGCHANNELBINDING: require` should be recorded as not supported (D-10). The hosted confirmation is designed below.

**The consent prompt becomes a modal with a small change, and the change has three real traps.** The change is to swap `Alert` for `Modal` (which renders `ModalContainer`) in `DataConsentPopup`, open it on mount, and route every close through one `onClose` that records `denied` when no choice was made. The traps:

1. The prompt nests the info button's own `Modal`. ModalContainer's Escape handler is a separate document listener in each instance, so one Escape would close both and decline (Pitfall 1).
2. `voter-prefs-tracking.spec.ts` relies on a close that records no choice, and on opening the menu while the prompt is up. Both become impossible with an inert modal (Pitfall 2).
3. The View Transition strip already keys on `dialog[open]`. D-03 then holds by construction, and only needs pinning (Pattern 3).

**Primary recommendation:** Split the phase into two independent tracks. **Track A** (frontend and tests, local only) can run at once: the consent modal, D-14a, b, f and h, and the D-14j reconciliation. **Track B** (pipeline and database) opens with the B-1 operator checkpoint, then commits the Supabase root CA with a fingerprint-pinning test and sets `verify-full` on both steps. It continues with D-14d, e and g, and with the D-14c migration on a staging deploy *after* the renamed functions are live. It closes with one observed deploy and one observed `ci-evidence/**` CI run. The phase ends with one full local E2E run, judged against 729 passed.

### Pattern 1: The consent prompt through `Modal` → `ModalContainer`
**What:** Keep the popup service contract (it passes `onClose`). Open on mount. Treat every close without a choice as a decline.
**Today** [VERIFIED: `DataConsentPopup.svelte:29-37`]:
```svelte
<Alert bind:this={alertRef} title={t('common.privacy.dataCollection.title')} icon="privacy" {...restProps}>
  ...
    <DataConsent onChange={() => alertRef?.closeAlert()} description="none" />
```
`Alert` renders `role={actions ? 'dialog' : 'alert'}` with `aria-modal="false"` [VERIFIED: `Alert.svelte:91-92`]. ModalContainer renders `<dialog ... aria-modal="true" aria-label={title}>` and opens with `modalContainer?.showModal();` [VERIFIED: `ModalContainer.svelte:131,156-164`]. ModalContainer has **no `autoOpen`**, so the popup must call `openModal()` in `onMount`.
**Sketch** [ASSUMED shape. Names like `chosen` are illustrative, and the executor reads the components first]:
```svelte
<script lang="ts">
  import { onMount } from 'svelte';
  import { Modal } from '$lib/components/modal';
  import { getAppContext } from '$lib/contexts/app';
  import { DataConsent, DataConsentInfoButton } from '../';
  import type { DataConsentPopupProps } from './DataConsentPopup.type';

  let { onClose, ...restProps }: DataConsentPopupProps = $props();
  const { t, setDataConsent } = getAppContext();
  let modalRef: Modal | undefined = $state();
  let chosen = false;

  onMount(() => modalRef?.openModal());

  /** Any close without a choice is a refusal, recorded as the decline button records it. */
  function handleClose() {
    if (!chosen) setDataConsent('denied');
    onClose?.();
  }
</script>

<Modal bind:this={modalRef} title={t('common.privacy.dataCollection.title')} onClose={handleClose} {...restProps}>
  <p>{t('dynamic.privacy.dataConsentIntro.popup')}</p>
  <DataConsentInfoButton class="!inline" />
  {#snippet actions()}
    <DataConsent onChange={() => { chosen = true; modalRef?.closeModal(); }} description="none" />
  {/snippet}
</Modal>
```
- `setDataConsent` (in `appContext.svelte.ts:352-364`) writes `{ consent, date }` under `consentPreferenceKey(page.route.id)`, calls `this.#tracking.resetAllEvents()`, and only for `'granted'` tracks `dataConsent_granted` [VERIFIED: file read]. A decline therefore emits no event, which is D-05's observable.
- `shouldShowVoterPrompt` returns false for `denied`, since it requires `input.consent === undefined || input.consent === 'indetermined'` [VERIFIED: `sendPolicy.ts:60-68`]. "Does not reappear" holds through the existing code path.
- The popup renders at the root layout tail, inside `appCtx` but outside the voter context [VERIFIED: `routes/+layout.svelte:266-275`]. `getAppContext()` is available there (`DataConsent` already uses it), but `getVoterContext()` is not.
- The context-destructuring rule: `t` and `setDataConsent` are stable references and safe to destructure. Do not destructure `userPreferences.current` or `analyticsPolicy`.

**Backdrop click:** ModalContainer defaults to `closeOnBackdropClick = true` [VERIFIED: `ModalContainer.svelte:57`]. Under the sketch, a backdrop tap is a decline. Recommend keeping it, so that **every dismissal is a refusal**. That is simple to state in the legal brief and privacy-safe, and the choice stays changeable on `/privacy`. The alternative, `closeOnBackdropClick={false}`, is an open question for the operator (Q-3).

### Pattern 2: Escape closes the topmost modal only
`<svelte:document onkeydown={handleEscape} />` [VERIFIED: `ModalContainer.svelte:153`] compiles, per instance, to `$.event('keydown', $.document, h);` [VERIFIED: Svelte 5.57.1 compile output this session]. That is one `addEventListener` on `document` per ModalContainer. `handleEscape` calls `e.stopPropagation()` [VERIFIED: :95-100], which does not stop other listeners on the same target.     e.stopPropagation();

## Common Pitfalls

### Pitfall 1: Nested info modal Escape declines consent
**What goes wrong:** Escape inside "Read more" closes both dialogs and records `denied`.
**Why:** Each ModalContainer has its own document keydown listener, and `stopPropagation` does not stop listeners on the same node (Pattern 2).
**How to avoid:** The topmost-only guard in `handleEscape`, with a red-first unit test.
**Warning signs:** After closing the info dialog with Escape, the consent prompt is gone and `dataCollection.consent` is `denied`.

### Pitfall 2: `voter-prefs-tracking.spec.ts` assumes a non-modal prompt
**What goes wrong:**
- (a) `dismissConsentPrompt` clicks `prompt.getByRole('button', { name: /^close$/i })` and then asserts no choice is stored [VERIFIED: spec :141-158]. ### Channel binding (D-10)
- Supavisor's `lib/supavisor/protocol/server.ex` defines `@scram_request <<?R, 23::32, 10::32, "SCRAM-SHA-256", 0, 0>>`. The AuthenticationSASL message lists one mechanism, `SCRAM-SHA-256`, with no `-PLUS`. ### Non-text contrast assertion (Playwright, sketch)
```ts
// Source: WCAG 2.1 relative luminance formula. The sketch is [ASSUMED], to be written by the executor.
async function borderContrast(locator: Locator): Promise<number> {
  return locator.evaluate((el) => {
    const parse = (c: string) => (c.match(/[\d.]+/g) ?? []).map(Number);
    const lum = ([r, g, b]: Array<number>) => {
      const f = (v: number) => ((v /= 255) <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4);
      return 0.2126 * f(r) + 0.7152 * f(g) + 0.0722 * f(b);
    };
    const style = getComputedStyle(el);
    if (parseFloat(style.borderTopWidth) === 0) return 1;
    let bgEl: Element | null = el.parentElement;
    let bg = 'rgb(255, 255, 255)';
    while (bgEl) {
      const c = getComputedStyle(bgEl).backgroundColor;
      if (!c.startsWith('rgba(0, 0, 0, 0)') && c !== 'transparent') { bg = c; break; }
      bgEl = bgEl.parentElement;
    }
    const [a, b] = [lum(parse(style.borderTopColor)), lum(parse(bg))].sort((x, y) => y - x);
    return (a + 0.05) / (b + 0.05);
  });
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no change | SCRAM-SHA-256 to Supavisor (no channel binding offered) |
| V3 Session Management | no | — |
| V4 Access Control | yes (D-14c) | `REVOKE … FROM PUBLIC, anon, authenticated` / `GRANT … TO service_role` patterns. Dropping the function removes a privileged entry point. pgTAP 07 and 39c pin the remaining set. |
| V5 Input Validation | no change | — |
| V6 Cryptography | yes | A pinned root CA, verified by libpq (`verify-full`). No hand-rolled verification. |
| V9 Communications | yes (core) | TLS with server identity verification for every pipeline DB connection (`verify-full` + `PGSSLROOTCERT`) |
| V14 Configuration | yes | The guard tests fail on a fallback to `require`, a dropped root path, or an expiring CA |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Pooler impersonation (MITM between runner and `*.pooler.supabase.com`) answering the settings check itself | Spoofing / Tampering | `verify-full` against the private root. The red probes show refusal. |
| SCRAM relay without channel binding | Spoofing | Not available on Supavisor (source). Server identity via `verify-full` bounds it, since the attacker cannot present a valid cert. Record the residual risk. |
| A rotated or wrong root silently weakening verification | Tampering | The fingerprint pin and expiry-margin test, and a loud deploy failure |
| Consent bypass via a dismissal path that records nothing (prompt reappears, or events flow) | Repudiation / Info disclosure | Every close records `denied`; `maySendEvents` requires `granted`; E2E D-05 |
| A stale privileged RPC (`invitation_caller_take`) left callable | Elevation | Drop it by migration; the pgTAP privilege lists updated |
