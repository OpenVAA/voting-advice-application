## Critical Issues

### CR-01: Escape in the consent prompt's information dialog closes the prompt too and records a decline

**File:** `apps/frontend/src/lib/components/modal/ModalContainer.svelte:96-103` (consequence at `apps/frontend/src/lib/dynamic-components/dataConsent/popup/DataConsentPopup.svelte:46-49`; the false claim at `ModalContainer.svelte:25`)
**Issue:** `handleEscape` closes the dialog in a `keydown` listener and calls `e.stopPropagation()`, but never `e.preventDefault()`. The browser's own Escape handling is the default action of that same `keydown`, so it still runs afterwards, against whichever dialog is topmost by then.

With the information dialog open inside the prompt, one Escape does this (event order recorded in all three engines: `keydown`, `cancel@Outer`, `close@Inner`, `close@Outer`):
1. The outer modal's handler sees `dialog[open]` inside it and returns (line 98).
2. The inner modal's handler closes the inner dialog from script.
3. The platform then sends `cancel` to the dialog that is now topmost, the prompt. `handleCancel` prevents it only under `holdOpen`, so the prompt closes natively.
4. The prompt's `close` reaches `handleNativeClose`, which calls `handleClose()`, which runs `onClose`.
5. `DataConsentPopup.handleClose` sees `chosen === false` and calls `setDataConsent('denied')`.

So a voter who opens "more information" and presses Escape to return to the choice has a decline stored, and the stored decline keeps the prompt from opening again. Measured on the real components: `{"open":0,"consent":["denied"],"log":["popup onClose"]}` after one Escape, in Chromium 153, Firefox 155 and WebKit 26.6.

Why Critical: it is deterministic in every engine, it records a consent choice the voter did not make, and this phase introduced it. Before the phase the prompt was a non-modal `Alert` with no Escape handling, so Escape in the information dialog closed that dialog alone. The error is in the privacy-safe direction (nothing more is sent), which is the argument for ranking it lower; the voter can still grant on the privacy page.

The component doc at line 25 ("Escape closes only the topmost open modal") and the comment at line 97 therefore describe behaviour no browser shows. The same holds for any other modal nested in a `ModalContainer`: the outer's `onClose` runs on the first Escape.
**Fix:** Cancel the key's default action when a modal handles it, so the platform does not act on the same key press:
```ts
function handleEscape(e: KeyboardEvent) {
  // A modal opened inside this one takes the Escape; this one closes on the next.
  if (modalContainer?.querySelector('dialog[open]')) return;
  if (isOpen && !holdOpen && e.key == 'Escape') {
    handleClose();
    e.stopPropagation();
    // The platform's own Escape handling runs after this listener and would close the dialog that is topmost by then.
    e.preventDefault();
  }
}
```
Verified on a scratch copy with only the `preventDefault` line added: one Escape closes the inner dialog alone (`open: ["Outer"]`, `log: ["inner onClose"]`, no `cancel` event) in all three engines. Not verified: the `holdOpen` paths and the single-modal specs under this change, so run the modal unit file and the E2E projects that press Escape (`voter-prefs-tracking`, the drawer specs) after it. Land it together with WR-01's browser-level test, red first.

## Warnings

### WR-01: The nested-Escape tests are green while the behaviour is broken in every browser

**File:** `apps/frontend/src/lib/components/modal/ModalContainer.svelte.test.ts:199-229`, `apps/frontend/src/lib/dynamic-components/dataConsent/popup/DataConsentPopup.svelte.test.ts:184-200`, and the missing case in `tests/tests/specs/voter/voter-prefs-tracking.spec.ts:384`
**Issue:** Both unit cases press Escape by dispatching a synthetic `keydown` on `document` in jsdom, where `showModal` and `close` are polyfilled as attribute writes (`DataConsentPopup.svelte.test.ts:42-50`). jsdom has no dialog top layer and no Escape default action, so the step that breaks the behaviour in a browser (the platform's `cancel` and `close` on the outer dialog, CR-01) never happens in the test. The cases assert "the prompt should stay open" and "`setDataConsent` not called", and pass, while a browser does the opposite.

The E2E test added for the modal prompt (`the consent prompt over a question`) presses Escape only with the prompt alone. No spec opens the information dialog inside the prompt and presses Escape, so the full suite's 745 green tests do not cover the case either. The phase's own research named this trap ("Nested info modal Escape declines consent") and settled it with the unit test alone.
**Fix:** Pin the property in a browser, where it lives. In `voter-prefs-tracking.spec.ts`, with the prompt open: click the information button, wait for two `dialog:modal`, press Escape, then assert that the prompt is still visible, that exactly one `dialog:modal` remains and that `expectNoConsentChoiceStored(page)` holds; a second Escape then gives `expectStoredConsent(page, 'denied')`. Run it red against the current tree before applying CR-01. For the two unit cases, either make the polyfilled press model the platform (after the dispatch, if the event was not default-prevented, fire `cancel` and then `close` on the last dialog opened that is still open) or say in each file's header that the cases hold the handlers' logic only and name the spec that holds the browser behaviour.

### IN-01: The drawer's Escape handler has the same gap, and the prompt can now share the top layer with the drawer

**File:** `apps/frontend/src/lib/components/modal/drawerHost/DrawerHost.svelte:110-115`
**Issue:** `DrawerHost.handleEscape` dismisses on any Escape while a drawer is shown, with `stopPropagation()` and no `preventDefault()`, and it has no check for a dialog above it. Its own `cancel` is always prevented, so it was safe while it was the only modal. The consent prompt is now a modal dialog that opens when the voter layout mounts, so on a cold entry to a drawer URL in gated mode both can be open. If the prompt is the topmost of the two, one Escape dismisses the drawer through its handler and then closes the prompt through the platform's default action, which records a decline. Not measured: whether the prompt or the drawer is opened last on that entry. If the drawer is last, the platform's `cancel` lands on the drawer and is prevented, and nothing is wrong.
**Fix:** When fixing CR-01, give `DrawerHost.handleEscape` the same `e.preventDefault()`, and decide the stacking question by a measurement (a cold load of a results drawer URL with no stored choice, reading which dialog is last in `document.querySelectorAll('dialog:modal')` and what one Escape does).
