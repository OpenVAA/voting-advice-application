<decisions>
## Implementation Decisions

### Consent prompt (operator ruling 189.1-08 `answer_wcag_fix=modal`, confirmed 2026-11-24)
- **D-01:** The voter consent prompt (`DataConsentPopup`, accessible name `Collecting Usage Data`) renders as a modal dialog through `apps/frontend/src/lib/components/modal/ModalContainer.svelte` (`showModal()`), so the page under it is inert and the dialog is in the top layer.
- **D-02:** Escape is a **decline**: it is recorded and persisted exactly as pressing the decline button is today. Nothing beyond the pageview is sent, and the prompt does not reappear afterwards (same as after a decline).
- **D-03:** The View Transition gate covers a prompt that is open at load: a navigation started while it is open runs without names or not at all (`apps/frontend/src/lib/utils/viewTransition.ts`, CLAUDE.md § Results Navigation Invariants). Pinned by a test.
- **D-04:** A new E2E assertion with the prompt shown: `dialog:modal` matches, the answer choices under it cannot be focused or clicked, and Escape closes it. axe is not evidence for this defect class, because it checks the DOM and not what an overlay paints over.
- **D-05:** An E2E assertion that after Escape no event beyond the pageview is sent (same observable as a decline).
- **D-06:** The local specs that drive the prompt by role and name, and the deployed `tests/tests/deployed/voter.smoke.ts`, stay green. Targeted runs per affected project within the phase, and one full-suite run at the phase's end judged against the last full run (729 passed) with summed deltas.
- **D-07:** After deploy, the 189.1-08 measurement is rerun on staging (Desktop Chrome 1280x720) with `A11Y_FINDING=none` and `A11Y_ESCAPE_CLOSES=yes`, plus a narrow viewport and dark mode. Evidence is recorded in the phase's `evidence/`.

### Database connections in the deploy pipeline (WR-02 residue, operator ruling 2026-11-24: option A)
- **D-08:** The `migrations` and `settings` steps of `.github/workflows/deploy.yml` use `PGSSLMODE: verify-full` and `PGSSLROOTCERT` pointing at the Supabase root CA. The CA is either committed to the repository or downloaded with a pinned checksum (researcher recommends; planner chooses on evidence).
- **D-09:** Research must first confirm that the CA Supabase publishes validates the **session pooler's** certificate and host name (`vars.SUPABASE_POOLER_HOST`, port 5432), not just the direct database host's. If it does not, stop with a checkpoint for the operator. Do not silently fall back to `require`.
- **D-10:** `PGCHANNELBINDING: require` is added too **only if** a measurement shows the pooler supports SCRAM channel binding. Otherwise it is recorded as not supported, with the evidence.
- **D-11:** `infra/scripts/deploy-workflow.test.ts` env pins (`SETTINGS_ENV` and the migrations step's pin) gain the new keys, and a mutation that drops `verify-full` back to `require` fails the guard.
- **D-12:** Proof: red then green against staging. A connection with a wrong root cert (or wrong host) is refused, and the observed pipeline run with `verify-full` is green.

### Relay legal review (operator ruling 2026-11-24: option B)

The legal review itself stays an external blocker in STATE.md, gating the production launch. Staging keeps `trackEvents` on (ruling `keep-on` stands).
