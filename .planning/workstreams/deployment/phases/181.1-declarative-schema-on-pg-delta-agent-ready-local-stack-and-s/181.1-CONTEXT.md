**Gathered:** 2026-10-18
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase decides, before the 181-17 baseline freeze, whether three things from Supabase Select 2026 enter v2.17: Declarative Schemas 2.0 on pg-delta, the agent-ready local stack, and config as code. It writes those decisions into 181-17 and into phase 183. It also makes the Supabase agent skills discoverable to agents without committing them.

The decisions all point the same way. Nothing from the three features is adopted in v2.17. The phase therefore delivers:
1. text amendments to 181-17, 183-CONTEXT and STATE.md;
2. a per-user install of the Supabase skills, plus a `recommended-skills` project skill that points to them;
3. deferred todos with the rationale written down.

No schema, migration, guard, check, CI pin or `config.toml` change is in scope.

</domain>

<decisions>
## Implementation Decisions

### pg-delta declarative schema (§A)
- **D-01:** Do not adopt pg-delta before the freeze. 181-17 freezes on the project's own model (181 D-01 to D-05 unchanged). Record pg-delta as a post-freeze option for *authoring* `000NN` migrations, to be reconsidered when pg-delta leaves alpha. This becomes a deferred todo. Reasons:
  - pg-delta is alpha and may break between releases;
  - DML in schema files is an error under it;
  - buckets are not diffed;
  - it has no drift check against a live database;
  - the freeze is one-way.
- **D-02:** The two top-level DML statements stay in `schema/`. They are the `storage.buckets` insert in `400-storage.sql` and the `private.deployment_settings` insert in `107-feedback.sql`. SUPA-04 requires the buckets in the migration. If pg-delta is adopted later, they move then. The roadmap also named `506-invitation-rpcs.sql`, but its DML is entirely inside function bodies, so it needs nothing.
- **D-03:** Keep five-digit migration versions (181 D-05). 181-17 adds a comment to the guard header in `scripts/assert-schema-migration-parity.mjs`: a later switch to CLI timestamp versions (`YYYYMMDDHHMMSS`) would mean relaxing only the no-gap rule, because timestamps sort after `00001`.
  - **Correction (2026-10-18, research):** The decision stands; only its rationale is corrected. In the guard a timestamp-named migration is refused first by the name pattern (`BAD NAME`, from `MIGRATION_NAME_RE`). Only once that pattern is widened does the no-gap rule fire (`VERSION GAP`). The order rule holds, because every timestamp sorts after `00001`. A later switch therefore means widening the name pattern and relaxing the no-gap rule. 181-17's `<context>` carries the corrected comment text. The same correction applies to the Deferred Ideas item that says the guard's no-gap rule is relaxed: the name pattern is widened too.
- **D-04:** pg-delta replaces none of the existing checks. These all stay:
  - the 181-10 equivalence check, `apps/supabase/scripts/check-schema-equivalence.sh`;
  - the 181-12 drift check, `infra/scripts/check-drift.sh`;
  - the freeze guard.

  pg-delta never reads a live database and does not compare rows or role settings.

### Agent-ready local stack (§B)
- **D-05:** The native per-worktree stack is not adopted in this phase. File a spike todo for after the freeze. The spike covers:
  - bump the CLI to at least 2.121, once the age gate allows it;
  - make the 15 literal ports in `config.toml` `env()`-driven, or remove them;
  - make `tests/scripts/e2e-run.sh` read the API URL from `supabase status` instead of hard-coding `54321`;
  - run the full E2E suite once with `--runtime native` in a worktree;
  - link the todos `2026-08-29-config-toml-hard-coded-ports-phase-156.md` and `2026-10-03-supabase-config-inbucket-section-deprecated.md`.
- **D-06:** E2E evidence from the native stack does not count toward any gate. Gates (181-19 and later) run on the Docker stack, as CI does. A native run is supporting evidence only.

### Config as code (§C)
- **D-07:** Phase 183's D-15 stays: Terraform `supabase_settings` is the only writer of hosted settings, and `supabase config push`, `config pull` and `supabase pull` are used nowhere. Amend `183-CONTEXT.md` D-15 with a dated note (2026-10-18, phase 181.1) recording that these commands were considered and rejected:
  - `config pull` writes `config.toml`, which holds local-development values;
  - `supabase pull` writes migration history on the remote and needs Docker;
  - `config push` would be a second writer.

  `config diff --exit-code` is the only read-only option (exit 2 on drift). It was also rejected: compared with the hosted project, the local-values `config.toml` would always differ, and the SUPA-11 guard (183-10) already covers parity. The 183 plans are unchanged.

### Supabase CLI (§D)
- **D-08:** The freeze and phase 181 stay on CLI 2.118.0: the catalog `^2.118.0` and the six `setup-cli` pins in `main.yaml`. The 181-12 ruling and every isolated observation were measured on 2.118. The bump goes to the D-05 spike todo. Note that 2.121.0 fails `npmMinimalAgeGate: 7d` until 2026-10-21.

### Supabase agent skills (§E), as ruled by the operator
- **D-09 (operator ruling):** Nothing from `supabase/agent-skills` is committed to the repo. The skills are installed for the operator's user only, and the repo gets a discoverable "recommended skills" pointer that agents extend as new needs appear.
- **D-10:** Create a new project skill at `.claude/skills/recommended-skills/SKILL.md`.
  - Its description triggers on installing or setting up skills, and on missing Supabase or Postgres guidance.
  - It lists each external skill set with its source repository, pinned SHA, review date, exact install procedure and scope (user, never project).
  - It has a "Conflicts with this repo" section that defers to `database`.
  - Register it in the same commit, as `.claude/skills/README.md` requires: a row in `CLAUDE.md` § Skill Routing, an entry in `.claude/skills/README.md`, and a row in `BOUNDARIES.md`.
  - Give it no `targets:`, so the drift audit reports SKIP.
  - It must pass `.claude/scripts/audit-skill-links.sh` (repo-relative paths) and `audit-skill-routing.sh` (one-hop depth; a description opening not shared by 3 or more skills).
- **D-11:** The install procedure:
  1. Clone `github.com/supabase/agent-skills` and check out `544bfc56c89afe2b87b20017a59b2c6e9502a1fb` (tag v0.1.9; the skill content is identical at main `c9be0e9`).
  2. Read both skill directories in full.
  3. Copy `skills/supabase` and `skills/supabase-postgres-best-practices` into `~/.claude/skills/`.

  Do not use the plugin route. Because of `source: "./"`, it probably also registers the remote `mcp.supabase.com` MCP server. Do not use `npx skills add` either: it is a third-party installer outside the age gate. Doing this install for the operator's user is a task in this phase. It writes outside the repo, so it needs the operator's confirmation when it runs.
- **D-12:** Recommend both skills. Warn that `supabase` fetches `supabase.com/changelog.md` before every task, may create `.mcp.json`, and picks a migration workflow that is wrong for this repo (it would produce a second migration file). The conflicts section names the four known conflicts, and `database` wins on each:
  1. the imperative workflow, then `db pull` or `migration new`;
  2. revoking EXECUTE on the `private.*` helpers, which breaks policies;
  3. requiring an `auth.uid()` check in every definer body, where the service_role-only helpers rely on EXECUTE revocation;
  4. preferring bigint or UUIDv7 primary keys, where the project uses `uuid gen_random_uuid()`.

  It also notes the per-table `user_id` ownership policies against `grants`/`user_can`, and the advisors/MCP tooling against `yarn db:lint:sql` and pgTAP.
- **D-13:** Updates are manual. The skill records the pinned SHA and the review date. To bump, read the upstream diff in full, then update the SHA and the conflicts list in the same commit. There is no update script.
