## § A — Declarative schema on pg-delta

### A-1 ⚠ DECIDE — Does the schema workflow move to pg-delta before the 181-17 freeze?

- [ ] **★ RECOMMENDED — No. Freeze as planned on the project's own model (D-01 to D-05 unchanged). Record pg-delta as a post-freeze option for *authoring* `000NN` migrations, to be looked at again when pg-delta leaves alpha (deferred todo).** The freeze stays one-way and is never built on an alpha engine. Row 8 keeps the later path open. Cost: after the freeze, each schema change is still a hand-written numbered migration, kept honest by the 181-10 equivalence check.
- [ ] Adopt pg-delta **only as a draft generator** after the freeze: `db schema declarative sync --no-apply` against `schema/`, then the output renamed to `000NN_<name>.sql` and reviewed, with the equivalence check as the authority. The decision is made now; the build waits until after the freeze. Cost: `[experimental.pgdelta]` in `config.toml`, the two DML statements moved out of `schema/`, the `NOTIFY` question (row 6), and a rename step that splits one sync into several files (row 7). Its behaviour on alpha can change between CLI bumps.
- [ ] Adopt fully **before** the freeze: `declarative_schema_path = "./schema"`, the baseline generated by pg-delta, timestamped migrations from then on. Cost: the guard, the manifest, `schema:regenerate`, the 181-12 history half and the 181-18 rewrites of four documents all change. The freeze waits for that work, and it lands one-way on an alpha engine.

### A-2 — What happens to the two DML statements in `schema/`?

The answer only matters if `A-1` is not the ★ option. SUPA-04 requires the buckets **in the migration**. D-07 put them there, and 181-08 observed it working.

- [ ] **★ RECOMMENDED — Leave them where they are.** Under the ★ in `A-1` nothing reads `schema/` except the concatenation, so they cause no problem. Cost: none now. If pg-delta is adopted later, they move then.
- [ ] Move them now into a dedicated file, still in the migration (for example `schema/_data/` concatenated last), so that a later pg-delta switch is a path change only. Cost: the baseline changes before the freeze, which means another regeneration and another isolated observation, for a switch that may never happen.
- [ ] Move the bucket rows to `seed.sql` and the `[storage.buckets.*]` config. Cost: breaks SUPA-04 (`seed.sql` is out of scope on hosted), so the hosted project would get no buckets.

### A-3 — Migration version format after the freeze

- [ ] **★ RECOMMENDED — Keep five-digit versions (D-05). Note in 181-17's guard header that a later move to CLI timestamps would mean relaxing only the no-gap rule, because timestamps sort after `00001`.** Cost: one comment.
- [ ] Switch the guard to accept timestamp versions now, so that it is ready for pg-delta. Cost: reopens the 16 fixtures and the guard tests before the freeze, for a hypothetical need.

### A-4 — Which existing checks does pg-delta replace?

- [ ] **★ RECOMMENDED — None. All three stay: the 181-10 equivalence check, the 181-12 drift check and the freeze guard (rows 9 and 10). Record the reason in CONTEXT so that the question is not raised again.** Cost: none.
- [ ] Retire the 181-12 schema half in favour of `db pull --declarative` plus `git diff`. Cost: it needs pg-delta adopted, it writes files, and it inherits pg-delta's blind spots (buckets, rows).

## § B — Agent-ready local stack

### B-1 ⚠ DECIDE — Does local development move to the native, per-worktree stack?

It would fix a real, repeated problem (row 13: the shared stack wiping across worktrees). It does not affect the freeze.

- [ ] **★ RECOMMENDED — Not in this phase. File a spike todo for after the freeze: bump the CLI, make the ports in `config.toml` `env()`-driven or remove them, make `e2e-run.sh` read the URL from `supabase status`, and run the full E2E suite once on `--runtime native` in a worktree.** Cost: the shared-stack problem stays through the end of v2.17. The spike already has its outline.
- [ ] Do that spike **inside** 181.1, without gating anything, in parallel with the freeze preparation. Cost: it needs the CLI bump (`D-1`) and port rewiring on the same tree the freeze commits. That tree is the one most at risk of collision, and the work adds to the phase the freeze waits on.
- [ ] Adopt it as the default local stack in v2.17. Cost: it is alpha, CI stays on Docker, so local and CI diverge, and all 15 pinned ports plus the harness change.

- [ ] **★ RECOMMENDED — No. Gates (181-19 and later) run on the Docker stack, as CI does. A native run is supporting evidence only.** Cost: none while `B-1` follows the ★.
- [ ] Yes, if the same commit is also green on Docker at least once. Cost: two runs per gate.

## § E — Supabase agent skills (operator ruling: install per user, not in the repo)

Settled: nothing from `supabase/agent-skills` is committed. The operator's user gets the skills, and the repo gets a place where agents can find which skills are recommended.

### E-1 — Where do agents find the recommended skills?

- [ ] **★ RECOMMENDED — A short project skill `.claude/skills/recommended-skills/SKILL.md`. Its description triggers on "set up / install skills / missing Supabase or Postgres guidance". It lists each external skill set (Supabase first) with the source repository, the pinned SHA, the install command, the scope (user, not project), and a "where it conflicts with this repo" section that defers to `database`. Add one row to CLAUDE.md § Skill Routing, one to `.claude/skills/README.md`, and one to `BOUNDARIES.md`.** Cost: one more skill, which must pass the routing and link audits (no `targets:`, so drift is SKIP).
- [ ] A section in `.claude/skills/README.md` only, with no skill. Cost: agents do not load that README by routing, so it is less discoverable. A human reads it; an agent mostly does not.
- [ ] A section in `CLAUDE.md`. Cost: it is always in context and costs tokens in every session for something needed rarely.

### E-2 — How is it installed for the operator's user?

- [ ] **★ RECOMMENDED — Copy only the two skill directories, `skills/supabase` and `skills/supabase-postgres-best-practices` at `544bfc56c89afe2b87b20017a59b2c6e9502a1fb` (tag v0.1.9; the skill content is identical at main HEAD `c9be0e9`), into `~/.claude/skills/`, read in full beforehand. The recommended-skills skill gives this exact procedure.** Pinned, with no MCP server and no automatic updates. Cost: updating is manual.
- [ ] As a Claude Code plugin (`claude plugin marketplace add supabase/agent-skills`, then `claude plugin install …`). Cost: because of `source: "./"`, the root `.mcp.json` probably comes along and registers the remote `mcp.supabase.com` MCP server (not tested). Updates are not pinned.
- [ ] `npx skills add supabase/agent-skills` at user scope. Cost: it runs a third-party installer from npm, and the 7-day age gate does not apply to `npx`. Whether it pins anything is unverified.

### E-3 — Which skills does it recommend?

- [ ] **★ RECOMMENDED — Both, with a warning on `supabase` that it fetches the changelog before every task, may create `.mcp.json`, and recommends a migration workflow that is wrong for this repo. Repo agents follow `database` on every conflict listed in row 18.** Cost: the broad `supabase` description ("Use when doing ANY task involving Supabase") will still load in this repo. The precedence note is the only defence.
- [ ] Only `supabase-postgres-best-practices`. Cost: loses the Supabase-platform guidance (auth, storage, CLI), which the project skill covers only partly.
- [ ] Both, unqualified. Cost: an agent that loads `supabase` here will try `migration new` or `db pull`, which creates a second migration file. The parity guard catches it, but only after the fact.

### E-4 — How are the recommended versions kept current?

- [ ] **★ RECOMMENDED — Manually. The recommended-skills skill records the pinned SHA and the date it was reviewed. A bump means reading the upstream diff in full, then updating the SHA and the conflicts list in the same commit.** Cost: nobody is told when upstream changes.
- [ ] Add a script that compares the pinned SHA with upstream HEAD and prints the skill-file diff. Cost: one more script for a two-skill list.
