This research found one factual error in a locked decision, and it has to be fixed in the wording, not in the decision itself. D-03 says the guard-header comment should state that a later switch to CLI timestamp versions "would mean relaxing only the no-gap rule". In the guard's code, that is false. A timestamp-named migration is first rejected by the **name-pattern** rule (`BAD NAME`, from the five-digit regex). Only once that regex is widened does the **no-gap** rule (`VERSION GAP`) fire. Both probes were run this session and their output is pasted below. The order rule does hold, because a 14-digit timestamp sorts after `00001`. So the comment the 181-17 executor writes must name **two** relaxations. 181-17 Task 3 also forbids phase and requirement ids in the header, so the comment cannot say "D-03" or "181.1".

The other findings that matter for planning. The whole-corpus link and routing audits already **exit 1 by design** (223 dangling citations and 5 routing violations on today's tree), so acceptance has to use per-skill runs, which exit 0, plus a no-regression comparison of the whole-corpus figures. The link audit flags several obvious ways of writing the new skill as dangling citations: `~/.claude/skills/`, `skills/supabase`, `.mcp.json`, `mcp.supabase.com`, and URLs written without a scheme. A draft skeleton that passes all three audits is given below, with its measured output. Hooks are disabled in this worktree (`core.hooksPath=/dev/null`, worktree-local), so commits go through cleanly. They also do not auto-format, and `CLAUDE.md` (unlike `.claude/` and `.planning/`) is in Prettier's scope.

**Primary recommendation:** plan three autonomous text plans (amendments; the skill and its registration; todos) and one `autonomous: false` plan for the per-user install. ## Common Pitfalls

### Pitfall 1: Writing D-03's comment as decided
**What goes wrong:** the guard header claims that only the no-gap rule would need relaxing. A future pg-delta adopter relaxes the gap rule, gets `BAD NAME`, and loses trust in the header.
**How to avoid:** use the corrected text (two relaxations) and record the correction in the summary or CONTEXT.
**Warning signs:** the 181-17 `<context>` note says "only".

### Pitfall 2: Phase ids in the guard comment
**What goes wrong:** the 181-17 Task 3 acceptance check "no phase or requirement id" in the header fails.
**How to avoid:** the comment text carries no `181.1`, `D-0x` or `SUPA-` token. Only the `<context>` paragraph names 181.1.

### Pitfall 3: 181.1 editing the guard itself
**What goes wrong:** a 181.1 commit touches `scripts/assert-schema-migration-parity.mjs`, the freeze commit's "exactly three files" check is no longer clean in context, and the tree moves under 181-17's readiness checks.
**How to avoid:** 181.1 changes only `181-17-PLAN.md`. The comment is written by the 181-17 executor (D-14).

### Pitfall 4: Whole-corpus audit exit codes used as gates
**What goes wrong:** the plan requires `audit-skill-links.sh` and `audit-skill-routing.sh` to exit 0, but both exit 1 on the unchanged tree.
**How to avoid:** use per-skill runs for exit 0, and no-regression comparisons (token sets and violation counts) for the whole corpus.

### Pitfall 5: Natural citations that dangle
**What goes wrong:** `~/.claude/skills/`, `skills/supabase`, `.mcp.json`, `mcp.supabase.com` and scheme-less URLs fail the link audit.
**How to avoid:** use `$HOME/…`, `https://…`, fenced code, or unbackticked prose (see the trap list above).

### Pitfall 6: README rule contradiction left unexplained
**What goes wrong:** a reviewer reads README § Adding a skill ("`targets:` must be populated") and flags the new skill.
**How to avoid:** the README entry states that a pointer skill to external content owns no directory, so it has no targets and SKIP is intended.

### Pitfall 7: Committing during another phase's operator checkpoint
**What goes wrong:** the STATE execution rule voids a pending E2E or freeze answer.
**How to avoid:** before each commit, check for a pending attempt (a `*.current` pointer under `tmp/18x-evidence/` whose attempt has a `CHECKPOINT_PRESENTED` line and no decision). Today, none exists for 181-17.

### Pitfall 8: Range-diff validation polluted by other phases
**What goes wrong:** `git diff f6c9c5107..HEAD -- apps/` shows changes because 182 or 183 executors commit in the same checkout.
**How to avoid:** validate per 181.1 commit (`git show --stat --format= <sha>` for each commit whose subject starts `docs(181.1`), not over a range.

### Pitfall 9: Subagent refused writing `~/.claude/skills/`
**How to avoid:** use an operator checkpoint with a fallback in which the operator runs the block (see Install).
