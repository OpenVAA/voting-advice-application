Run the full local E2E suite on the tree as this phase has changed it, in a window the operator confirms.

Purpose: the phase changes the application (the hooks, two routes, the build configuration, the image, the schema and the function configuration), so it closes on a green local suite, and a test that did not run counts as failed. The run uses a stack started from this worktree, with a database reset. The reset discards the other session's local database state, which is why the operator's confirmation comes first.

This gate verifies the pre-freeze work. Plan 181-19 runs the suite again after the freeze, because the tree changes in between.

<attempt_protocol>
The three tasks of this plan share one attempt file across the operator's wait. Its record name is `181-16-e2e-gate`.

- What starts it. Task 1 starts the attempt by the attempt rule: a new attempt id, a new attempt file `181-16-e2e-gate.<attempt id>.txt`, and the pointer `181-16-e2e-gate.current` set to it. Every run of Task 1 is a new attempt.
- What continues it. Task 2 and Task 3 append to the attempt file the pointer names, and to no other file. They never start an attempt and never move the pointer.
- What resets it. Only a new attempt of Task 1. After that, nothing the earlier attempt holds is read: not its readiness lines, not its confirmation, not its run.
- The question. When Task 2 presents the checkpoint it appends the line `CHECKPOINT_PRESENTED attempt=<attempt id> head=<sha>`, with the sha from `git rev-parse HEAD` at that moment, and shows both values in the checkpoint message. The attempt id is the nonce of the question.
- The answer. When the reply arrives, Task 2 appends the reply, quoted and indented, and then one answer line that carries the two values of the last `CHECKPOINT_PRESENTED` line: `OPERATOR_CONFIRMED_STACK_FREE=yes attempt=<attempt id> head=<sha>` when the reply holds the words "stack is free" and that attempt id, and the same line with `no` in place of `yes` for any other reply. The answer key may occur more than once in an attempt; the last answer line is the one in force.
- The answer check. Task 3 runs the command below before anything else and reads its status directly. It exits 0 only when the pointer names an attempt file that carries its own id, the last `CHECKPOINT_PRESENTED` line and the last answer line both carry that id and the sha `git rev-parse HEAD` prints now, the answer is `yes`, it was written after that question, and the attempt file has no `TASK3_STARTED=` line.
- A refused answer is never used. When the check exits non-zero, Task 3 touches no stack and writes no tracked file. If `git rev-parse HEAD` still equals the sha on the last `CHECKPOINT_PRESENTED` line of the pointer-named file and that file has no `TASK3_STARTED=` line, Task 2 presents the checkpoint again in the same attempt. In every other case (the pointer or the attempt file is missing, `HEAD` has moved since the question, the answer was already used) the attempt is over: Task 1 runs again as a new attempt, and then Task 2 asks again.
- An answer is used once. Directly after a passing check Task 3 appends `TASK3_STARTED=<UTC time>`. From that line on the check refuses this attempt.
- One attempt makes one wrapper run. When the run is void, red or not evidence, or a deferred observation fails, Task 3 still stops the stack and writes and commits the record, which then shows the failure, and the attempt is over. The next try is a new attempt of Task 1 and a new confirmation. No second run is made on a confirmation that was already used.
- A bound on asking again. A confirmation is voided when the operator confirmed and no wrapper run was started on it: the answer check refused it, or step 0 of Task 3 ended the attempt. Whoever finds that appends `ANSWER_VOIDED=` followed by the reason in one line (the check's last output line, or what stopped step 0) to the attempt file the pointer names, when there is one. Task 1 of the next attempt reads that line before it moves the pointer and writes the same reason as `PREVIOUS_ANSWER_VOIDED=` into the new attempt file. It is the only line taken over from an attempt that is ending, and it can only stop the plan: no check passes because of it. When a confirmation is voided and the pointer-named attempt file already holds `PREVIOUS_ANSWER_VOIDED=` with the same reason, two in a row were voided for one reason: start no new attempt and do not ask a third time. Stop, and return a blocking checkpoint that quotes the reason and this attempt's id, so the cause (for example a commit made in this checkout by another executor or by the orchestrator) is removed first.
