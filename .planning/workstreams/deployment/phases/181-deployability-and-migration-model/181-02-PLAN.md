<objective>
Build the isolated-instance harness and prove it with a recorded spike, before any plan depends on it.

Purpose: this worktree and the v2.16 worktree share one local Supabase instance (A-03, follow-up X-2). Every database observation of this phase therefore runs on an instance of its own. The research rates that harness as untested (assumption A1, Open Question 5), so proving it is the first database task.
Output: `apps/supabase/scripts/isolated-instance.sh` and the spike record.

If the spike fails: the record carries `HARNESS_DB_MODE=failed`. Plans 181-08, 181-10, 181-11, 181-12 and 181-17 name `HARNESS_DB_MODE=ok` as a precondition and halt at a blocking checkpoint. The operator then chooses between the other options of follow-up X-2 (an untracked project id and ports for this worktree, or an exclusive window on the shared stack), and the database plans are revised for that choice. No plan falls back to the shared stack by itself.

`requirements` lists SUPA-10 as the phase's only closing requirement; this plan builds toward SUPA-04 and SUPA-06 and closes nothing.

    Subcommands and flags:
    - `start --name <id> --mode db|full --migrations <dir> [--seed <file>] [--port-base <n>] [--tests <dir>]`
    - `env --name <id>` prints `KEY=value` lines for `ISO_WORKDIR`, `ISO_PROJECT_ID`, `ISO_DB_CONTAINER`, `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD` and, in `full` mode, `ISO_API_URL`. It never prints the anon or service-role key.

    - `list` prints the names that have a state directory.

    Behaviour of `start`:
    - State directory `${TMPDIR:-/tmp}/openvaa-isolated/<id>/`, holding `supabase/config.toml`, `supabase/migrations/` (a copy of the directory given), and `supabase/seed.sql` only when `--seed` is given.
    - The copied `config.toml` gets `project_id = "openvaa-iso-<id>"`, every port key moved to a value derived from `--port-base` (default 55400), and `[db.seed] enabled = false` unless `--seed` is given. `--tests <dir>` copies a pgTAP directory to `supabase/tests`.
    - Before any CLI call it asserts: the name matches `[a-z0-9-]+`; the project id is not `openvaa-local`; the work directory is not under the repository; no port value in the copy equals a port value of the source config; each chosen port has no listener.
    - `--mode db` runs `supabase db start --workdir <dir>`. `--mode full` runs `supabase start --workdir <dir>` with the services this phase does not need excluded through `-x`; take the service names from `supabase start --help` at run time. Keep the database, the API gateway, auth, PostgREST and storage.
    - The CLI binary is `node_modules/.bin/supabase` of the repository root.

    Exit codes: 0 done; 2 usage; 3 Docker or the CLI is unavailable; 4 a refused precondition (name, project id, work directory, a port in use); 5 the CLI failed to start or stop the instance; 130 interrupted. Every non-zero exit goes through `fatal` with a message.

    The script holds no connection URL constant for a hosted database and adds no `set -x`. Do not start an instance in this task.
