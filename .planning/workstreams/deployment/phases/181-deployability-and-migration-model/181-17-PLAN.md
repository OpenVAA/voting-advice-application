<objective>
Freeze the baseline: one commit that adds the manifest of the real baseline and switches the guard to frozen mode (D-01, D-02, D-04, A-02).

Purpose: `db push` skips a version it has recorded, so an edit to the single migration after the first hosted push never lands. From this commit on, a schema change in either stream is an appended, numbered migration. This is the phase's one-way door.
Output: the manifest, the switched guard, the updated gate spec, and two records.

This plan cannot run until three things are true, and Task 1 re-checks each by command:
(a) the v2.16 stream's phase 177.1 has landed;
(b) the two branches' `schema/` have been merged one way, so both hold the same bytes (A-01);
(c) phase 182's schema change of its decision D-13 is in `schema/` and the baseline (D-06).
The guard's logic, its fixtures and its red controls already exist (plan 181-06). Only the manifest of the real baseline waited.

The freeze commit leaves the baseline's bytes unchanged, and the manifest names the freeze commit's parent as the commit the baseline came from, because a commit cannot hold its own hash (follow-up 181-R1, planned on its recommended option).

The first proof that the baseline applies on a hosted project comes after the freeze, in phase 184. A failed push records nothing, so the baseline can still be corrected then by an edit to the file and its manifest line in one commit, which D-01 accepts as visible in review. It becomes one-way only after the first successful push.

After this plan the v2.16 branch must merge this branch through the freeze commit before its next schema change. Until it has the new guard, its `yarn schema:regenerate` still rewrites `00001`. The operator carries that to the v2.16 session (follow-up X-1).
</objective>

<attempt_protocol>

- What starts it. Task 1 starts the attempt by the attempt rule: a new attempt id, a new attempt file `181-17-freeze-readiness.<attempt id>.txt`, and the pointer `181-17-freeze-readiness.current` set to it. Every run of Task 1 is a new attempt.
- What continues it. Task 2 and Task 3 append to the attempt file the pointer names, and to no other file. They never start an attempt and never move the pointer.
- What resets it. Only a new attempt of Task 1. After that, nothing the earlier attempt holds is read: not its readiness verdicts, not its decision.
- The question. When Task 2 presents the decision it appends the line `CHECKPOINT_PRESENTED attempt=<attempt id> head=<sha>`, with the sha from `git rev-parse HEAD` at that moment, and shows both values in the checkpoint message. The attempt id is the nonce of the question.
- The answer. When the reply arrives, Task 2 appends the reply, quoted and indented, and then one answer line that carries the two values of the last `CHECKPOINT_PRESENTED` line: `OPERATOR_DECISION=` followed by `freeze`, `freeze-without-commit` or `not-yet`, then ` attempt=<attempt id> head=<sha>` (for example `OPERATOR_DECISION=freeze attempt=20261012T101500Z.0123456789ab head=` and the 40-character sha). `freeze` and `freeze-without-commit` are written only when the reply holds that option and that attempt id; every other reply, a reply that names another attempt id included, is written as `not-yet`. The answer key may occur more than once in an attempt; the last answer line is the one in force, so a `freeze` that is followed by `not-yet` freezes nothing.
- The answer check. Task 3 runs the command below before anything else and reads its status directly. It exits 0 only when the pointer names an attempt file that carries its own id, the last `CHECKPOINT_PRESENTED` line and the last answer line both carry that id and the sha `git rev-parse HEAD` prints now, the answer is `freeze`, it was written after that question, the attempt file has no `TASK3_STARTED=` line, its one `READY_TO_FREEZE=` line reads `yes`, and `HEAD` differs from the sha on its `HEAD_AT_READINESS=` line in no path outside `.planning/`.
- A refused answer is never used. When the check exits non-zero, Task 3 changes no file and makes no commit. If the last answer line carries this attempt's id and the current `HEAD` and reads `not-yet` or `freeze-without-commit`, that is the operator's decision: Task 3 returns it to the orchestrator and the plan stays open. Otherwise the decision in force does not answer the current question: if `git rev-parse HEAD` still equals the sha on the last `CHECKPOINT_PRESENTED` line and the file has no `TASK3_STARTED=` line, Task 2 presents the decision again in the same attempt; in every other case (the pointer or the attempt file is missing, `HEAD` has moved since the question, the answer was already used, the attempt is not ready) the attempt is over, Task 1 runs again as a new attempt, and then Task 2 asks again.
- A decision is used once. Directly after a passing check Task 3 appends `TASK3_STARTED=<UTC time>`. From that line on the check refuses this attempt.
- A Task 3 that is started again. When the pointer-named attempt file already holds `TASK3_STARTED=`, Task 3 does not run the answer check and asks nobody. It decides by git whether this attempt's freeze commit exists: `git log --diff-filter=A --format=%H -- apps/supabase/supabase/migrations.manifest.json` names a commit, and that commit's parent equals the `FREEZE_PARENT=` line of the attempt file. If so, the freeze was made in this attempt: Task 3 continues after the freeze commit and finishes the two records from this attempt file. If not, nothing was frozen and this attempt is over: restore the guard and the spec with `git checkout --` if this task left them modified (they are this plan's own files; an untracked manifest left behind is overwritten by the next attempt), then Task 1 runs again as a new attempt and Task 2 asks again. A second freeze commit is never made.
- A bound on asking again. A selection of `freeze` is voided when nothing was frozen on it: the answer check refused it, or Task 3 ended the attempt before the freeze commit. Whoever finds that appends `ANSWER_VOIDED=` followed by the reason in one line (the check's last output line, or the step that ended the attempt) to the attempt file the pointer names, when there is one. Task 1 of the next attempt reads that line before it moves the pointer and writes the same reason as `PREVIOUS_ANSWER_VOIDED=` into the new attempt file. It is the only line taken over from an attempt that is ending, and it can only stop the plan: no check passes because of it. When a selection is voided and the pointer-named attempt file already holds `PREVIOUS_ANSWER_VOIDED=` with the same reason, two in a row were voided for one reason: start no new attempt and do not ask a third time. Stop, and return a blocking checkpoint that quotes the reason and this attempt's id, so the cause (for example a commit made in this checkout by another executor or by the orchestrator) is removed first.
