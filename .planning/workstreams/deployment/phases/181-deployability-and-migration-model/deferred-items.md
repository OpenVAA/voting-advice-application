Each item was outside the scope of the plan that found it. None was fixed.

## From plan 181-02

Please use [local_smtp] instead.` The section is `[inbucket]` in `apps/supabase/supabase/config.toml`, with the keys `port`, `smtp_port` and `pop3_port`. The stack starts and the keys are honoured. Renaming the section changes a file both worktrees share and the port table in `apps/supabase/README.md`, so it was not done here. Seen on 2026-10-12 in the output of `supabase db start` and `supabase start` on an isolated instance.

## From plan 181-06

- **A guard started through a symbolic link exits 0 and checks nothing.** `scripts/assert-env-pair-registry.mjs` ends with `if (process.argv[1] && path.resolve(process.argv[1]) === fileURLToPath(import.meta.url)) main();`. Node resolves symbolic links for the module's own URL and not for `process.argv[1]`, so when the script's path holds a link the two strings differ and `main()` is never called. Measured on 2026-10-12 under Node v24.21.0: `node <link to the repository>/scripts/assert-env-pair-registry.mjs` printed nothing and exited 0, where the same script by its real path printed its summary line. `scripts/assert-edge-function-env.mjs` and `scripts/assert-env-pairs-agree.mjs` end with the same line; neither was run through a link, so for them this is inferred. `yarn lint:check` starts the guards by a relative path from the repository root. Node resolves a relative script path against the working directory, so that case is expected to be unaffected; it was not measured with a linked working directory. The case measured is a script path that itself holds a link. Not fixed: the three files are outside plan 181-06. `scripts/assert-schema-migration-parity.mjs` got the entry-point test in that plan with both sides passed through `realpathSync`, and it was seen running through a link.

## From plan 181-09

- **A page takes about 14.5 seconds and answers 200 when Supabase cannot be reached.** Measured on 2026-10-12 on the built server with `PUBLIC_SUPABASE_URL` naming a port that refuses connections: `GET /` answered 200 after 14.48 s with the application's error message as its body. The root load (`apps/frontend/src/routes/+layout.ts`) makes the customization read first and the other three together, and `@supabase/postgrest-js` 2.117.2 retries a `GET` whose fetch rejected three times, waiting 1, 2 and 4 seconds. So every page request holds a connection for two retry chains while the upstream is down, and a status check of a page cannot tell that it is down. Not changed: the reads and the client are outside the plan's files. It bears on the request and idle timeouts of phase 185. Recorded in `evidence/181-09-production-start.md`.
- **Row 1a of the research table names a red control that does not hold.** `181-RESEARCH.md`, "Success Criteria → Green Observation and Red Control", says of the health criterion: "A page route (`/`) on the same server does not answer 200." It answers 200 (the entry above). Plan 181-09 already uses a discriminator instead (the upstream answers inlined into the page: 6 with a valid upstream, 0 with it refusing). A later plan that wants this control must not read the page's status.
- **A stand-in for the Supabase API must send `access-control-allow-origin`.** For a universal load running on the server, kit 2.70.3 rejects a cross-origin answer without that header (`src/runtime/server/page/load_data.js`), and the PostgREST client then retries the read. A stub without it makes every read of the root load fail, which looks the same as an unreachable upstream. Plan 181-09's stub was given the header as its one allowed adaptation; a later plan that stubs the upstream needs it from the start.
