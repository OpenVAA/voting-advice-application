<objective>
Build the drift check (D-11, A-05) and show it locally: green after a push to a local database, red on planted DDL, red on a history mismatch.

Purpose: SUPA-10 asks for a drift check after deploy that reads its exit status directly. `supabase db diff` exits 0 with or without a difference, so the script sets the status itself from the diff's output and from a migration-history query.
Output: `infra/scripts/check-drift.sh` and its record.

Two assumptions are measured first (Task 1), and the plan says what changes if either goes the other way:
- A2: the diff is empty on a clean database built from this baseline. If it is not, the schema half of the check uses the dump comparison of plan 181-10 between the target and an isolated build from the migrations, limited to the schemas this project owns, and the header says so.
- A10: the CLI accepts and orders a migration named by a five-digit version and a name, such as `00002_probe.sql`, after the baseline. If it does not, stop and return a blocking checkpoint: the naming ruled in D-05 would need another look, and that is the operator's to decide.

The real manifest does not exist until the freeze (plan 181-17). The observations here use a manifest written into a temporary directory in the contract's shape; plan 181-18 runs the check once more against the real one. No CI job is added.

SUPA-10 is closed by the phase as a whole; this plan builds its drift-check clause.
</objective>

    Per D-11 and A-05. Create `infra/scripts/check-drift.sh`, executable, in the house shape: header with purpose, usage, prerequisites, the blind spots, and an exit-code table; `set -euo pipefail`; paths from the script's location; `usage` and `fatal`; an interrupt trap that exits 130; no `set -x`.

    Flags: `--manifest <path>` (default `apps/supabase/supabase/migrations.manifest.json`), `--workdir <dir>` (the Supabase work directory whose `supabase/migrations` the diff uses; default `apps/supabase`), `--target local|linked` (default `local`; passed to the CLI as `--local` or `--linked`), `--out <dir>` for the files it writes. There is no flag that takes a database URL, because a URL on a command line holds the password. The history query's connection comes from the `PG*` variables.

    Two parts, one status:
    1. History. Read the versions from the manifest (the five-digit prefix of each `migrations[].file`, in order) and the versions recorded in `supabase_migrations.schema_migrations` (the column the spike recorded, ordered) through `psql -X -At`. They must be equal as ordered lists. A version in the manifest and not in the database, or the reverse, is drift, named in the output.
    2. Schema. When Task 1 recorded `A2=held`: run `supabase db diff` for the target with the schema set Task 1 found empty on a clean build, standard output to a file; a file larger than zero bytes is drift, and the file is printed. When `A2=failed`: use the snapshot comparison of `check-schema-equivalence.sh` between the target and an isolated build from the migrations, limited to the schemas `public`, `private` and `storage`.

    Statuses: 0 when both parts hold; 1 on drift; 2 when the check could not run (the manifest is missing or unreadable, psql or the CLI failed); 130 interrupted. Both parts always run, so one report shows both.

    The header's blind-spot paragraph says what the schema half does not see with the diff engine in use: rows, column privileges, comments, role settings and `alter policy` statements. It says that the equivalence check and the conformance probe of a later phase cover those.
  </action>
