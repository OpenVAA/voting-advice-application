<objective>
Build the check that will replace byte parity: an equivalence check between a database built from `schema/` and one built from the migrations (D-03, A-04), and see it fail on each kind of difference it must catch.

Purpose: after the freeze, a schema change is a `schema/` edit plus a numbered migration. Nothing in the Node-only `lint:check` chain can tell whether the two agree, because grants and policies exist only in a built database. `supabase db diff` is not used for this: it does not capture column privileges, rows, comments or role settings, and this schema has a whole file of column grants.
Output: `apps/supabase/scripts/check-schema-equivalence.sh` and its record.

The check runs on demand and needs Docker. It is not a link of `lint:check`, and no CI job is added (D-11).

SUPA-10 is closed by the phase as a whole; this plan builds the check that keeps `schema/` and the migrations in agreement after the freeze.
</objective>

  <action>
    Per D-03 and A-04. Create `apps/supabase/scripts/check-schema-equivalence.sh`, executable, in the house shape: header with purpose, usage, prerequisites, what the check cannot see, and an exit-code table; `set -euo pipefail`; paths from the script's location; `usage` and `fatal`; an interrupt trap that exits 130.

    Flags: `--schema-dir <dir>` (default `apps/supabase/supabase/schema`), `--migrations-dir <dir>` (default `apps/supabase/supabase/migrations`), `--out <dir>` (where the two snapshot files and the diff are kept; default a temporary directory), `--reuse-m <file>` (use an existing snapshot of the migrations side instead of building it again).

    Steps:
    1. Side M: an isolated database-only instance `eq-m` built from the migrations directory. Side S: an instance `eq-s` on port base 55500 built from a temporary directory holding one migration file, the concatenation of every `.sql` file of the schema directory in filename order with each file ending in a newline, which is what `concatenateSchema` produces. Seeding is off on both. The two are built one after the other; each is stopped before the script exits, on every path.
    2. For each side, write a snapshot file made of: a schema-only `pg_dump` run inside that instance's database container with `docker exec`, as the role and with the scope the spike recorded, excluding the schema `supabase_migrations`, and with a fixed `--restrict-key` when the spike recorded it as supported (otherwise strip the two restrict lines); then three query results in a stable order: role settings from `pg_db_role_setting` joined to role names, installed extensions from `pg_extension`, and the rows of `storage.buckets` (`id, name, public, file_size_limit, allowed_mime_types`) and of `private.deployment_settings`.
    3. Print a census for each side: the number of `CREATE TABLE`, `CREATE POLICY`, `CREATE FUNCTION` or `CREATE OR REPLACE FUNCTION`, `GRANT` and `CREATE TRIGGER` lines in its snapshot. Refuse to pass, with status 2, when either side has no `CREATE TABLE public.` line or fewer than 20 tables, 50 policies or 50 functions: an empty dump compared with an empty dump is equal and proves nothing.
    4. Compare the two snapshot files with `diff -u` into a file. Exit 0 when the diff file is empty, 1 when it is not (print the diff), 2 when a build, a dump or a query failed.

    The header's "cannot see" paragraph lists: `--` comments outside function bodies, sequence positions, and anything in a schema the dump could not read. It also states the two properties developers meet: a column added by a migration lands last, so `schema/` must put it last too; and a function re-created by a migration must have the same body text as `schema/`, comments inside the body included.

    If the spike recorded `DUMP_SCOPE=named-schemas`, dump the schemas `public`, `private` and `storage`, and say so in the header.
  </action>
