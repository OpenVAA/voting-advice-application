**The diff is empty in all three, and standard output is not.** Standard error of each run ends with `No schema changes found`. Standard output of each holds one line of JSON whose `diff` member is a single newline. The command as the plan writes it therefore never gives zero bytes here.

The reason is the CLI's caller detection. It has a global flag `--agent` ("Override agent detection: yes, no, or auto (default auto)") and a global flag `--output-format` (`text`, `json`, `stream-json`). This session's shell carries the variables `AI_AGENT`, `CLAUDECODE` and several `CLAUDE_CODE_*`; with detection on `auto` the CLI answered in JSON. The same command with `--agent no`, and again with `--output-format text`, writes nothing to standard output on the clean build and the same lines to standard error. Which of the session's variables the detection reads was not looked into.

So the rule "a file larger than zero bytes is drift" is true of the text output only. A check that does not select the output format would be red for an agent on a clean database and green for a person at a terminal. The check passes `--agent no --output-format text`; both flags together were run (rows marked "both" above).

### An interrupt, and the fault it found

The first version of the script passed `SIGTERM` to the CLI process it had started and waited for it. Run once that way, before the commit: the check exited 130 and the shadow database was still running, published on port 55902. The next run of the check then exited 2, because the CLI could not publish that port again, and that failed diff left a second container of its own in the state `Created`. Both carried the label of the instance's project id, neither was in the container list of before the plan, and both were removed by id.

What the CLI does with a signal was then measured on the CLI alone (`supabase db diff --local --workdir <ISO_WORKDIR> --agent no --output-format text`, signalled once its shadow database was listed). `node_modules/.bin/supabase` is a Node wrapper that starts a binary (`node_modules/@supabase/cli-darwin-arm64/bin/supabase`), which starts `docker` processes:

| Signal | Sent to | Status of the wrapper | Shadow database afterwards |
|--------|---------|------|------|
| `SIGTERM` | the wrapper alone | 130 | left running |
| `SIGINT` | the wrapper alone | 130 | left running |
| `SIGTERM` | the wrapper and every process below it | 130 | removed (run twice) |
| `SIGINT` | the wrapper and every process below it | 130 | removed |
| `SIGHUP` | the wrapper and every process below it | 129 | a container left, in the state `Created` |

The statuses of this table were read from the session's output, not from saved files. Every container these probes left was removed by id before the next probe.

So the committed script sends `SIGTERM` to every process below the CLI wrapper and to the wrapper, whatever signal it received, and then waits. On the committed script:

| Key | Signal | Status | Seconds | Shadow database seen before the signal | Containers at the signal | Containers when the check returned |
|-----|--------|--------|---------|------|------|------|
| `DRIFT_SIGTERM_EARLY_EXIT` | `SIGTERM` to the script, when the shadow database is first listed | 130 | 2 | yes | 1 | none |
| `DRIFT_SIGTERM_LATE_EXIT` | `SIGTERM` to the script, two seconds later | 130 | 5 | yes | 2 | none |
| `DRIFT_SIGINT_GROUP_EXIT` | `SIGINT` to the script's process group | 130 | 1 | yes | 1 | none |

Standard error of the first of them:

```
check-drift.sh: history: reading supabase_migrations.schema_migrations
check-drift.sh: schema: running supabase db diff --local; this starts a shadow database and can take a minute
check-drift.sh: FATAL -- interrupted
```

"Containers when the check returned" lists every container that is not one of the 24 of before the plan or the instance's own database. In the late run the diff engine's container was running beside the shadow database when the signal came; both were gone when the check returned. The `SIGINT` run was started from a Node process as the leader of a process group of its own and signalled as a group, the way a terminal does it: a background job of a non-interactive shell has `SIGINT` ignored and could not show it. After the three runs the check exited 0 again.

### What part 2 did not measure

- **`--target linked`.** The flag is passed to the CLI as `--linked`. It was never run: nothing is linked and no hosted project was touched. That the diff is empty against a clean hosted database, that the history table reads the same there, and how the script's connection and the CLI's are known to be the same database, are all unobserved.
- **The default `--manifest` and the default `--workdir`.** The first does not exist yet. The second names the shared stack, where the diff would publish its shadow database on port 54320.

- **Two runs at the same moment.** They would want the same shadow port.

- **Drift that the JSON output carries.** The script refuses JSON; it was not shown a JSON answer holding a real difference.
- **A changed migration file.** The history part compares versions and not hashes, so a file edited after it was applied was not planted here. The frozen-mode checker of the parity guard is what compares hashes.
