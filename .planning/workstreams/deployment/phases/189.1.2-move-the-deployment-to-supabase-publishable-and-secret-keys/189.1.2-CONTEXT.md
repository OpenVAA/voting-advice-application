# Phase 189.1.2: Move the deployment to Supabase publishable and secret keys - Context

**Gathered:** 2026-11-25 (UTC), from `189.1.2-DISCUSSION-POINTS.md`. Operator reply, verbatim: "1 Rename all now / 2-6 recommended".
**Research:** `189.1.2-RESEARCH.md` (6a4f1646b) and its rename addendum.

## Phase boundary

The deployment runs on Supabase publishable (`sb_publishable_…`) and secret (`sb_secret_…`) keys, every name that says `anon` key or `service_role` key is renamed for them, and staging works with its legacy `anon` and `service_role` keys disabled, before Supabase retires them (docs: "by the end of 2026"). Requirement FUT-02, promoted into this milestone.

## Decisions

- **D-01 (operator overruled the recommendation): rename everything in this phase.** Every environment variable, SSM parameter, `storage_config` row key, Terraform variable or output, GitHub variable, registry entry, fixture, test helper, doc and runbook that names the legacy keys is renamed for the publishable and secret keys. The names follow Supabase's own (`SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY`, with `PUBLIC_` for the frontend's), unless the rename addendum shows a reason to do otherwise. Platform-injected names the project does not own (`SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` inside Edge Functions) are read only as a fallback and are not ours to rename. The rename and the value switch reach staging without a window where a running consumer reads a name nothing sets. The local `.env` rename is a breaking change for every developer checkout: the `.env.example` files, an assertion that names the old variable and its replacement, and the docs must make it impossible to miss (compare the `PUBLIC_PROJECT_ID` precedent).
- **D-02: the legacy keys are disabled inside this phase**, as the last operator script (B). It proves the old anon key gets 401 and the publishable key still works, and it prints a rollback.
- **D-03: Terraform disables them**, through provider 1.11.0's `supabase_project.legacy_api_keys_enabled`. The default is null, so nothing is written. The plan gate allows exactly one in-place change. Never use the dashboard toggle. Never use the `supabase_apikeys` data source or the `supabase_apikey` resource, because they would put key values in state.
- **D-04: the `send-email` dry run in script A** runs only if the smoke admin already holds `project.edit_entities` on the smoke project. The script checks this first. Otherwise the step is skipped and the reason recorded.
- **D-05: `identity-callback`'s admin client on hosted** is covered by the shared helper (exercised by `account-access`'s smoke) and the local `bank-auth` E2E. No hosted bank sign-in is added.
- **D-06: plan now, execute after 189.1.1 closes.** Staging and the local Supabase stack are shared, and 189.1.1's final plan judges a full E2E run on this tree.

## Carried constraints

- **Hosted settings:** Terraform under `infra/modules/supabase` is their only writer.
- **Committed literals:** never commit an `sb_secret_` literal. Tests build fake keys by concatenation.
- **Local stack and CI** stay on the legacy keys, and every consumer accepts both shapes. The local values may be the CLI's `sb_` keys under the new names if the addendum shows that works.
- **Operator sittings:** each is one bash script with self-checking steps. It advances on a match, asks y/n on a mismatch, confirms any destructive step explicitly, prints the error line of a failed command, resumes with `--from N` and cleans up on any exit. The reference is `189.1.1-12-rebuild-sitting.sh`.
- **Operator approval:** executors never push and never write to hosted staging. Approvals are bound at top level.
- **E2E:** targeted per-project runs inside the phase, each new or rewritten test red first. One full run at the phase end, judged against the last full run with the summed deltas.
- **Comment hygiene.**

## Deferred

None. The rename is in scope.
