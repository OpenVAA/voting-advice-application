## Summary

The move is smaller in code than it looks, because the platform does most of the work. On a hosted project, the gateway takes `sb_publishable_`/`sb_secret_` in the `apikey` header and maps each to the `anon`/`service_role` role. supabase-js 2.117.2, the version pinned in the frontend and in all three Edge Functions, already treats new-format keys specially: it never sends them as the Bearer of a Functions call, though it still sends the key as the Bearer of REST, Storage and Auth calls when no session exists. The Edge Function runtime injects `SUPABASE_PUBLISHABLE_KEYS` and `SUPABASE_SECRET_KEYS` as JSON dictionaries keyed by key name (`default`). This was verified both in the docs and in the local CLI's edge-runtime source.

That leaves three things that genuinely break once a `sb_` value replaces a legacy JWT.

1. **The storage cleanup trigger** sends `Authorization: Bearer <storage_config.service_role_key>` and nothing else. Measured locally this session, Storage refuses a `sb_secret_` key sent that way (`403 Invalid Compact JWS`) and accepts it in `apikey` (`404 NoSuchKey` for an absent object, `200` for a bucket list returning service-role rows). The fix is a new migration that sends `apikey`, and adds the Bearer only for JWT-shaped values. pg_net 0.20.4's `http_delete` takes a `headers jsonb` argument, so this needs no new pg_net feature.
2. **The Edge Functions** read `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` directly, and `admitWitness` compares the `Authorization` header with `Bearer <SUPABASE_SERVICE_ROLE_KEY>`. Once legacy keys are disabled, the legacy values are refused by the gateway: the docs still list them as injected, but they carry the disabled legacy keys. The functions need a `_shared` helper that reads the new dictionaries first and falls back to the legacy names.
3. **The operator tooling** decodes a key's JWT `role` claim (`role_of` in the sitting script, gate `s2_anon_role=anon`/`s2_service_role=service_role`), which returns nothing for an `sb_` key. The probe already handles `sb_` keys.

The frontend needs **no code change**. Its five client factories pass `PUBLIC_SUPABASE_ANON_KEY` to supabase-js/`@supabase/ssr`, and the publishable key has been observed on staging working for REST, auth, password sign-in and `account-access` in that same call shape. The value lives in the SSM parameter `/openvaa/staging/frontend/PUBLIC_SUPABASE_ANON_KEY` and is read at runtime through `$env/dynamic/public`. Switching it is an operator `ssm put` followed by new tasks. No GitHub secret holds a Supabase API key, and Terraform holds none either. Terraform provider 1.11.0 exposes `supabase_project.legacy_api_keys_enabled` (optional, computed, deprecated). The disable step can therefore be a Terraform apply and does not need a dashboard click, so the single-writer rule holds. The provider also has a `supabase_apikeys` data source and a `supabase_apikey` resource. Neither is needed, because adopting them would put key values in Terraform state.

**Primary recommendation:** Ship dual-shape code first (functions helper, trigger migration, tooling prefix checks, a Terraform variable defaulting to "unmanaged"), deploy it while staging is still on legacy values, and watch the functions move to the secret key by themselves under the deploy smoke. Then switch the two stored values (SSM parameter, `storage_config` row) in one operator sitting script. Disable the legacy keys by a Terraform apply in a second script, which first proves the old anon key is refused. Keep variable names unchanged in this phase. The local stack and CI keep the legacy keys.

## Q2: Storage API and the cleanup trigger

**Measured locally this session (CLI 2.118.0, storage-api v1.77.0, Kong 2.8.1)** against `DELETE /storage/v1/object/public-assets/<convention-shaped path that does not exist>` and `GET /storage/v1/bucket` [VERIFIED-local]:

| Headers sent | DELETE result | Bucket list |
|---|---|---|
| `Authorization: Bearer <sb_secret>` only (the trigger's current shape with a new key) | `403 Invalid Compact JWS` | `403 Invalid Compact JWS` |
| `apikey: <sb_secret>` only | `404 NoSuchKey` (accepted) | `200`, both buckets (service role) |
| `apikey` and `Bearer`, both `<sb_secret>` | `404 NoSuchKey` (accepted) | — |
| `Authorization: Bearer <legacy service_role JWT>` only (today's shape) | `404 NoSuchKey` (accepted) | — |
| `apikey: <legacy JWT>` only | `404 NoSuchKey` (accepted) | — |
| `apikey: <sb_publishable>` | — | `200 []` (anon sees no bucket) |

Why it behaves this way locally: the CLI's Kong `request-transformer` on `/storage/v1/`, `/rest/v1/`, `/auth/v1/` and `/graphql/v1` rewrites `Authorization` when it is absent or begins `Bearer sb_`. It substitutes the legacy JWT of the role that the `apikey` value maps to (the secret key maps to the service_role JWT, the publishable key to the anon JWT), and otherwise keeps the header. On `/functions/v1/` it does **not** rewrite `Authorization`. It adds an `sb-api-key` header instead [VERIFIED-local: `/home/kong/kong.yml` in `supabase_kong_openvaa-local`, lines 44-51, 62-69, 160-167, 181-188; values not reproduced].

Hosted, per the docs:
- "The new secret keys aren't JWTs, so they're rejected there. Send the secret key on the `apikey` header instead." This is about `pg_net` calls that put the key in `Authorization: Bearer` [CITED: https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys].
- Migration checklist item: "Cron jobs, workers, and `pg_net` calls or Database Webhooks" [CITED: same].
- **Docs conflict:** the migration guide says "If you also pass the key on the `Authorization: Bearer` header, which many Supabase clients do by default, the platform tries to parse it as a JWT and rejects the request with `Invalid JWT`." Discussion 29260 says a publishable or secret key in that header is allowed for backward compatibility if it "exactly matches the value in the `apikey` header" [CITED: discussion 29260]. The phase-184 record sides with the discussion: the publishable key in **both** headers got 200 on hosted REST, auth and `account-access` [VERIFIED-record: 184-12]. supabase-js 2.117.2 itself sends `Bearer <key>` equal to `apikey` on REST, Storage and Auth (above). **Resolution for the trigger:** send `apikey` always, and add `Authorization: Bearer` **only for a JWT-shaped key**. That shape is correct under both readings, and it is the one the docs prescribe for pg_net.

**Recommended function body** (only the header expression changes):

```sql
-- in delete_storage_object, replacing headers := jsonb_build_object('Authorization', 'Bearer ' || service_key)
PERFORM net.http_delete(
  url := base_url || '/storage/v1/object/' || p_bucket || '/' || p_file_path,
  headers := CASE
    WHEN service_key LIKE 'sb\_%' THEN jsonb_build_object('apikey', service_key)
    ELSE jsonb_build_object('apikey', service_key, 'Authorization', 'Bearer ' || service_key)
  END
);
```

The `ELSE` branch adds `apikey` to the legacy shape, which local Storage accepted (row 5, and `apikey`+`Bearer` with the legacy JWT also 404-accepted). This is [VERIFIED-local] for the stack and [ASSUMED] for the hosted gateway with a legacy key, where today's shape is Bearer-only. To minimise hosted risk, the `ELSE` branch may instead keep today's exact Bearer-only header. **Recommend keeping today's exact `ELSE` shape** (`jsonb_build_object('Authorization', 'Bearer ' || service_key)`), so the legacy path is byte-identical and only the `sb_` path is new. The pgTAP file then pins both branches precisely.

## Architecture Patterns

### System flow after the move

```
Browser / SvelteKit SSR ── apikey: sb_publishable (+ Bearer = user JWT, or = key when no session) ──▶ Supabase gateway ──▶ REST / Auth / Storage (role anon or authenticated)
        │                                                                                              │
        └── functions.invoke (no Bearer without session) ──▶ gateway ──▶ account-access / identity-callback (verify_jwt=false)
                                                                     └─▶ send-email (verify_jwt=true, admin JWT)
Edge Function admin clients ── apikey: SUPABASE_SECRET_KEYS.default (+ matching Bearer, from supabase-js) ──▶ gateway ──▶ REST / Auth admin (service_role)
Row change ─▶ cleanup trigger ─▶ delete_storage_object ─▶ pg_net DELETE, apikey: storage_config.service_role_key (sb_secret) ──▶ gateway ──▶ Storage (service_role)
Terraform (supabase root) ── legacy_api_keys_enabled=false ──▶ Management API ──▶ gateway refuses legacy JWT apikeys
```

### Pattern 1: one `_shared` key helper for the three functions

**What:** `apps/supabase/supabase/functions/_shared/apiKeys.ts` (name [ASSUMED]) exports `publishableKey()` and `secretKey()`. Each reads the new dictionary first and falls back to the legacy name. **When:** every read of `SUPABASE_ANON_KEY` or `SUPABASE_SERVICE_ROLE_KEY` in function code.

```typescript
// Shape follows the docs' JSON.parse(...)['default'] example (supabase.com/docs/guides/functions/secrets)
function fromDictionary(name: 'SUPABASE_PUBLISHABLE_KEYS' | 'SUPABASE_SECRET_KEYS'): string | undefined {
  const raw = Deno.env.get(name);
  if (!raw) return undefined;
  try {
    const value = (JSON.parse(raw) as Record<string, unknown>)['default'];
    return typeof value === 'string' && value !== '' ? value : undefined;
  } catch {
    return undefined;
  }
}

/** The project's secret key, else the legacy service-role key; throws naming both when neither is set. */
export function secretKey(): string {
  const key = fromDictionary('SUPABASE_SECRET_KEYS') ?? Deno.env.get('SUPABASE_SERVICE_ROLE_KEY');
  if (!key) throw new Error('Neither SUPABASE_SECRET_KEYS nor SUPABASE_SERVICE_ROLE_KEY is set');
  return key;
}
// publishableKey(): the same, with SUPABASE_PUBLISHABLE_KEYS and SUPABASE_ANON_KEY.
// Also export the set of all secret-key values, for admitWitness.
```

The order is new first, legacy second. The platform injects the new dictionaries on hosted projects and in CLI 2.118.0, so both hosted and local use the new keys once this ships, and the fallback serves only a runtime that lacks them, such as an older CLI or a self-hosted runtime [ASSUMED for self-hosted]. **The moment this deploys to staging, the functions run on the secret and publishable keys**, with no operator step. That is the first observable switch (Q8, wave 2).

### Pattern 2: `admitWitness` accepts either key shape

Admit the witness when the request's `apikey` header equals **any** value of `SUPABASE_SECRET_KEYS` (constant-time), **or** `Authorization` equals `Bearer <SUPABASE_SERVICE_ROLE_KEY>` (today's rule, kept so the local E2E helper `supabaseServiceRoleKey.ts`, which sends the legacy key as the Bearer, keeps working). The local Kong forwards `apikey` and `Authorization` to functions unchanged (it only adds `sb-api-key`) [VERIFIED-local]. Hosted forwarding of `apikey` to a `verify_jwt=false` function is [ASSUMED]. The witness is a test instrument, and the deployed smoke never sends one (`service-role-key-absent` gate), so a hosted mismatch cannot break production. Signature: `admitWitness(request, headers: { authorization: string | null; apikey: string | null }, keys: { legacyServiceRole?: string; secretKeys: readonly string[] })`. The planner chooses the exact shape.

### Pattern 3: pgTAP for both trigger branches

Inside the test's transaction, which ends in ROLLBACK: (a) with the seed's JWT row, assert `headers` keys = `ARRAY['Authorization']` and the value `'Bearer ' || key` (unchanged). (b) `UPDATE public.storage_config SET value = 'sb_' || 'secret_' || 'pgtapnotarealkey' WHERE key = 'service_role_key'`, trigger a replace, and assert keys = `ARRAY['apikey']` and value = that string. The concatenation keeps a literal `sb_secret_…` out of the tracked file (Pitfall 5). The committed-state Playwright spec `tests/tests/specs/storage/storage-cleanup.spec.ts` keeps proving the legacy branch end to end locally.

### Pattern 4: Terraform owns the legacy switch

```hcl
# infra/modules/supabase/variables.tf
variable "legacy_api_keys_enabled" {
  description = "Whether the legacy anon and service_role JWT keys are enabled; null leaves the project's state unmanaged."
  type        = bool
  default     = null
}
# infra/modules/supabase/main.tf, in resource "supabase_project" "this"
  legacy_api_keys_enabled = var.legacy_api_keys_enabled
```

Pass it through the staging, example and scratch roots. Staging `terraform.tfvars` gets `legacy_api_keys_enabled = false` only in the disable wave. A `tftest.hcl` case asserts null when unset and false when set. The `plan` run in the disable sitting must show exactly one in-place update, `legacy_api_keys_enabled: true -> false`. Any other diff stops the sitting. Whether an optional+computed attribute set to null plans no diff on an imported project is [ASSUMED-high] (it is the provider's `!plan.IsNull()` guard). The first `plan` in script B proves it.

### Pattern 5: key-shape checks in operator scripts

Replace JWT `role` decoding with prefix gates: `case "$K" in sb_publishable_*) ok;; *) fail;; esac`, the same for `sb_secret_`, and never print a value or a length. Reuse the gate/`rl` helpers of `189.1.1-12-rebuild-sitting.sh` by copy. Do not edit that file.

### Anti-patterns

- **Renaming variables in the same phase** (`PUBLIC_SUPABASE_ANON_KEY` → `…_PUBLISHABLE_KEY`, the `service_role_key` row, `SUPABASE_SERVICE_ROLE_KEY` in bootstrap). This touches the SSM parameter path, the task environment, two registries, about 40 files and the page-scraping tests, for no functional gain. Defer it (Open Question 1).
- **Reading keys via the `supabase_apikeys` data source.** That puts secrets in state.
- **Disabling legacy keys in the dashboard.** It breaks single-writer, and the probe would not know which state is declared.
- **Sending `Bearer sb_secret_…` from pg_net.** Measured refused locally, and the docs say refused on hosted.
- **Making local/CI switch to `sb_` keys in this phase.** Local cannot disable legacy, and the CLI's Kong maps each `sb_` key back to the legacy JWT, so a local switch tests less than it seems while touching the whole E2E key path. Unit and pgTAP tests cover the `sb_` branches, and staging covers the platform.

## Common Pitfalls

### Pitfall 1: the trigger fails quietly
**What goes wrong:** with `sb_secret` stored and the old trigger, every cleanup DELETE gets 403, the trigger only raises a WARNING ("Degrades to a WARNING", `400-storage.sql:641`), and replaced photos stay public. **Avoid:** migration 00006 ships and deploys **before** `bootstrap.sql` is re-run with the secret key. Script A checks `net._http_response` for the probe DELETE. **Warning sign:** `status_code` 400 with `Invalid Compact JWS` in `net._http_response.content` [table name ASSUMED for pg_net 0.20.4; check `\d net.*` first].

### Pitfall 2: the ECS tasks keep the old SSM value
**What goes wrong:** `ssm put-parameter` changes nothing until new tasks start, because ECS resolves `secrets` at task launch [ASSUMED: standard ECS behaviour; the operations page § "The two parameters" already says "start new tasks"]. **Avoid:** put the value, then force a new deployment or let the next pipeline deploy (a new image digest means a new task definition) roll the tasks. Verify that the served page's inlined env carries the `sb_publishable_` prefix (the Step 13 scrape plus a prefix check).

### Pitfall 3: disabling before every consumer has moved
**What goes wrong:** anything still holding a legacy JWT fails at once: an old task, the `storage_config` row, an operator `.env`, or a k6 run. **Avoid:** script B first proves the move (served page prefix, `storage_config` row prefix read in SQL without printing the value, probe green, smoke green). It then applies the disable and finally runs the positive falsification: a request with the **legacy anon key** must now be refused (401), and the same request with the publishable key must succeed. The disable is reversible (`true` plus apply).

### Pitfall 4: an env guard turns injected names into required ones
**What goes wrong:** wrapping `SUPABASE_SECRET_KEYS` in `requireEnv(...)` makes `assert-edge-function-env.mjs` demand it in `functions/.env.example`, which must not hold it. **Avoid:** the helper reads with `Deno.env.get` and throws its own error. Run `yarn lint:check` (it includes `assert:env-pair-registry` and the edge-env guard), and read the status directly, never through a pipe.

### Pitfall 5: committing an `sb_secret_` literal
**What goes wrong:** GitHub push protection's partner pattern `supabase_secret_key` is on by default for public repos [CITED: https://github.blog/changelog/2026-03-10-secret-scanning-pattern-updates-march-2026/]. The mapping to the `sb_secret_` format is [ASSUMED]. Committing the CLI's fixed local secret in `seed.sql` or a test would be blocked or alerted. **Avoid:** `seed.sql` keeps the legacy demo JWT, and tests build fakes by concatenation. The local CLI keys appear to be fixed constants across installs [ASSUMED], but that does not make them committable.

### Pitfall 6: the two docs statements on `Bearer` disagree
See Q2. Code written by us sends a new key in `apikey` only (trigger, sitting curls). supabase-js's own Bearer=apikey behaviour is left alone, since the record observed it working.

### Pitfall 7: the deprecated Terraform field
`legacy_api_keys_enabled` will be removed in a later provider version. The provider pin `= 1.11.0` is exact, and the README says to raise it only with a new reading of the source, so this is a known item for the next provider bump. Record it in the module comment.

### Pitfall 8: the "service-role-key-absent" smoke gate and the new name
`deployedTarget.ts:28` lists `'SUPABASE_SERVICE_ROLE_KEY'` as a variable that must be absent from the smoke environment. If an operator puts the secret key under a new name (for example `SUPABASE_SECRET_KEY`), the gate would not see it. Keeping the names unchanged avoids this. If names change later, extend the gate.

|---|---|---|
