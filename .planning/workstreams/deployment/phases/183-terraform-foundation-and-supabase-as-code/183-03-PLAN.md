    It declares two `data "aws_iam_policy_document"` trust documents, `plan_trust` and `deploy_trust`. Each also has two `dynamic "condition"` blocks, emitted only when the matching variable is not null, with test `StringEquals` on `token.actions.githubusercontent.com:repository_id` and on `token.actions.githubusercontent.com:repository_owner_id`. No condition in this file uses any other test: the ruling is exact matches only.

    It declares `aws_iam_role` named `plan` with name `"${var.name_prefix}-plan"` and `aws_iam_role` named `deploy` with name `"${var.name_prefix}-${var.environment}-deploy"`, both with `path = var.iam_path` and `assume_role_policy` taken from the matching trust document. Neither role sets any argument that carries an inline policy or a list of managed policy ARNs; attachments are separate resources in Task 2.

    It declares `aws_iam_role_policies_exclusive` for each role, named `plan` and `deploy`, with `role_name` set to the role's name and `policy_names = []`. With an empty list Terraform removes any inline policy that someone adds to the role by hand, on the next apply.

    One comment above the trust documents states the two facts a reader needs: a trust policy is outside the repository's rule against inline policies, and the subject strings are name-based, so a rename or transfer of the repository, or an opt-in to id-bearing subjects, stops the roles being assumable until the subjects are changed and the root is applied again.

    `policies.tf` declares four customer-managed policies, each an `aws_iam_policy` with `path = var.iam_path` whose document is a `data "aws_iam_policy_document"`, one per concern (per D-07). Use a local for the pipeline state object ARN, `"${var.state_bucket_arn}/${var.pipeline_state_key}"`, and one for its lock object, the same string followed by `.tflock`.

    1. `tfstate_pipeline`, name `"${var.name_prefix}-tfstate-${var.environment}-aws"`. Allow `s3:ListBucket` on the bucket ARN with a `StringEquals` condition on `s3:prefix` whose value is `var.pipeline_state_key`. Allow `s3:GetObject` and `s3:PutObject` on the state object. Allow `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on the lock object. This is an allow-list of one key, so the deploy role cannot read or write any hand-applied root's state.
    2. `ecr_push`, name `"${var.name_prefix}-ecr-push"`. Allow `ecr:CompleteLayerUpload`, `ecr:UploadLayerPart`, `ecr:InitiateLayerUpload`, `ecr:BatchCheckLayerAvailability`, `ecr:PutImage` and `ecr:BatchGetImage` on `var.registry_arn`. Allow `ecr:GetAuthorizationToken` on `*`.
    3. `plan_deny`, name `"${var.name_prefix}-plan-deny"`. Deny `s3:GetObject` and `s3:GetObjectVersion` on `"${var.state_bucket_arn}/${var.hand_state_prefix}*"`. Deny `secretsmanager:GetSecretValue`, `secretsmanager:BatchGetSecretValue` and `kms:Decrypt` on `*`. Because every hand-applied root keeps its state under one prefix, a root added later is covered without an edit (per A-08).
    4. `plan_lock`, name `"${var.name_prefix}-plan-lock"`. Allow `s3:PutObject` and `s3:DeleteObject` on the lock object only. A plan takes the state lock, and the AWS-managed read-only policy grants neither action (per A-08).

    It declares five `aws_iam_role_policy_attachment` resources. On the plan role: the AWS-managed policy `arn:aws:iam::aws:policy/ReadOnlyAccess`, `plan_deny` and `plan_lock`. On the deploy role: `tfstate_pipeline` and `ecr_push`. Do not use the account-wide exclusive attachment resource (the one whose type name has no `role`, `user` or `group` in it): it detaches the policy from every other identity in the account.

    One comment in the file records two consequences for later roots without citing a phase: the root that the plan role plans must hold no secret value it has to refresh, because secret reads are denied; and the deploy role gains further policies only through this hand-applied module.

    `outputs.tf` exports `oidc_provider_arn`, `plan_role_arn`, `plan_role_name`, `deploy_role_arn` and `deploy_role_name`.

    What the S3 backend lists was read from its documentation and its source, not recalled. The documentation for Terraform 1.16 (`language/backend/s3`) asks for `s3:ListBucket` on the bucket, which "at a minimum … must be able to list the path where the state is stored", and its example policy conditions that permission with `StringEquals` on `s3:prefix` set to the state key, as `tfstate_pipeline` does. The source at tag `v1.16.5` (`internal/backend/remote-state/s3/backend_state.go`, function `Workspaces`) makes the backend's one list call: `ListObjectsV2` with the prefix `env:/`, the default workspace key prefix and a slash. When that call is refused with `AccessDenied` and the prefix is the default one, the function logs "Unable to list non-default workspaces" and carries on with the default workspace. The state object and the lock object are reached by head, get, put and delete calls on their exact keys. So this policy does not admit the backend's list call, and Terraform 1.16.5 tolerates the refusal. Say exactly that in one comment above `tfstate_pipeline`, naming the source file by its path, `internal/backend/remote-state/s3/backend_state.go`, the Terraform version it was read at, and the prefix `env:/`; the third check of this task looks for both in a comment line. Do not write that the condition admits every list call.

    Three things stay unobserved and are written nowhere as fact: whether S3 reports a missing state or lock object as not found or as forbidden under a list permission that carries this condition; whether a later Terraform version keeps tolerating the refused workspace listing; and whether `ReadOnlyAccess` lets a plan read everything a root's resources need. Plan 183-16 runs the policy simulator over the calls named above for both roles. The fallback, if a call the backend needs is refused when a workflow first uses a role, is a one-line change in this file and a hand apply of the bootstrap root: add `env:/` to the `s3:prefix` values for the workspace listing, or replace the equality by a `StringLike` match on the state key and on the key followed by `.tflock` for the missing-object case. Record all three in the SUMMARY as open until phase 187 first assumes a role.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions token → AWS STS | A workflow presents an OIDC token; the trust policy decides which workflow becomes which role |
| plan role → state bucket and secret stores | A pull request's plan runs code from the pull request under the plan role |
| deploy role → state bucket | The pipeline holds write access to one state key |
