<objective>
Fix the status-reading steps of the three pipeline workflows for the shell GitHub actually runs them in, prove the fix locally under that shell, rebuild the evidence commits, and observe the red run again on a new branch, per the operator's ruling `RULING_BASH_E=fix-now-and-re-observe` (evidence/187-18-red-run.md § Operator ruling (2026-11-17)), and per D-03, D-02, G-01, G-04, G-05, B-01 and C-02.

GitHub runs a `run:` step that names no `shell:` as `bash -e {0}`. The steps of `deploy.yml`, `destroy.yml` and `infra-plan.yml` open with `set -uo pipefail` and read each command's status with `$?` on the next line, so under `-e` a failing command ends the step before its status is read and before its diagnosis is printed. Run 44042442257 showed it twice: the build step printed no `failed=build`, and the `wrong-subject` job ended at `IFS=. read -r _ payload _ < "$token_file"` (status 1 at the end of a token file with no trailing newline) before either STS call. The same shape would fail a pull-request plan with changes (status 2), a re-deploy of a pushed image (status 3) and the destroy job's expected Supabase-root refusal.

The fix (Claude's discretion, recorded here): every status read is captured on its command's own line, as `name=0` on the line before the command and `cmd || name=$?` on its last line, the form `main.yaml` already uses.
- A command in an `||` list does not trigger errexit, so the step reaches its status check and its diagnosis.
- Every other command keeps the runner's `-e` and ends the step when it fails, so no failure passes on silently.
- The one tolerated non-zero status that is not a `$?` read, the token's `read` at the end of a file with no trailing newline, gets the guard `|| [ -n "$payload" ]`. A token file with no trailing newline then passes, and an empty or unreadable one still ends the step.

Turning errexit off per step, with `set +e`, was not chosen. It would let a failing command whose status the step does not read pass on silently: an unreadable `config.toml` in the functions step would make every expected `verify_jwt` default to true. Turning it off for a workflow or a job was not chosen for the same reason, and because it would take `-e` from the steps that set it on purpose. The cost of the chosen form, accepted: a failing command whose status the step does not read ends the step with the runner's own `Process completed with exit code <n>` and the command's own error output, with no diagnosis line of the step's. No such command has one now either.
