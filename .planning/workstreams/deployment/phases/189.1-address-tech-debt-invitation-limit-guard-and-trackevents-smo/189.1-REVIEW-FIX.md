### WR-02: The settings check sends the database password over a connection that does not verify the server

**Files modified:** `.github/workflows/deploy.yml`, `infra/scripts/deploy-workflow.test.ts`, `infra/README.md`
**Commit:** e8bc67b58
**Applied fix (partial by design, `require` only):**
- `PGSSLMODE: require` is now in the env of both the `migrations` step and the `settings` step. This removes libpq's fallback to plaintext.
- Each step's comment says that psql refuses a connection without TLS and that the server's certificate is not verified.
- Test pins:
  - `SETTINGS_ENV` and the exact env pin of the migrations step carry `PGSSLMODE: 'require'`.
  - The two test titles say "with TLS".
  - A new mutation test drops `PGSSLMODE: require` from the settings step and is red.
- `infra/README.md` stage 4 now says the check runs "over TLS (`PGSSLMODE=require`, which does not verify the server's certificate)". The rest of that paragraph, including "the database password in `PGPASSWORD` alone", still holds. The README's stage 3 text and the deployment guide say nothing about sslmode, so they needed no change.

**Why `require` is safe against the hosted pooler (checked, not assumed):**
- **The pooler speaks TLS.** `openssl s_client -starttls postgres -connect aws-0-eu-north-1.pooler.supabase.com:5432` completed a TLS handshake. That is the repo's own pooler region, and no credentials were sent. The certificate is `CN=*.pooler.supabase.com`, issued by Supabase Intermediate 2021 CA under Supabase Root 2021 CA.
- **The migrations step also drives the Supabase CLI, and the CLI still works.** The drift check's `supabase db diff --linked` starts a local shadow database in Docker, and the local `supabase/postgres` image runs with `ssl = off`. A direct `psql` with `PGSSLMODE=require` to the local stack fails with "server does not support SSL". The CLI itself was checked at the repo-pinned version (`node_modules/.bin/supabase` 2.118.0), with `PGSSLMODE=require` exported:
  - `supabase migration list --local` connected and listed 24 migrations;
  - `supabase db diff --local --workdir apps/supabase` started its shadow database, applied every migration and finished "No schema changes found", exit 0.
  - So the CLI's local and shadow connections ignore `PGSSLMODE`. In that step, the setting governs only one libpq client: the drift check's psql to the pooler, which works over TLS.

**Left open, and why:**
- **`verify-full` + `PGSSLROOTCERT`.** The pooler's chain ends at a root private to Supabase (Supabase Root 2021 CA), not at a public CA. Verifying it needs that root committed, or downloaded with a pinned checksum. The repo has no such file, and no authoritative, stable source and checksum could be confirmed from here. A wrong or rotated root would fail every deploy. This needs an operator decision.
- **`PGCHANNELBINDING: require`.** Nothing in the repo or elsewhere that could be checked confirms that Supavisor offers SCRAM-SHA-256-PLUS. If it does not, `require` would refuse every connection, so it was not added.
- **Status of the gap.** With `require`, the link is encrypted, but an active attacker who can present a certificate can still impersonate the pooler. That part of WR-02 remains open.
