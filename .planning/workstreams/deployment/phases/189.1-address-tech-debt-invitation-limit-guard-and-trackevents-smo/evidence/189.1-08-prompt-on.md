- **The same numbers in all three runs.** The viewport, the five choices, the focused input, the three boxes, `scrollY` 0, `label_inside_dialog=full` and `escape_closes=no` were printed identically each time.
- **`A11Y_LABEL_INSIDE_DIALOG=full`.** The last choice's label spans x 812.8 to 928.0 and y 566.2 to 636.0. The dialog spans x 304.0 to 976.0 and y 526.0 to 700.0, so the label lies inside it entirely, and so does the radio input itself (x 854.4 to 886.4, y 566.2 to 598.2), which carries the focus ring. The focus did not scroll the page (`scrollY` 0): the choice was already inside the viewport, so focusing it moved nothing clear of the fixed Alert. The dialog's computed style read `opacity` 1, `transform` none, `pointer-events` auto and `z-index` 30, without the closed state's `translate-y-full` class.
- **`A11Y_CENTER_HITS_DIALOG=yes`, the settled reading.** One second after the focus, `document.elementFromPoint` at the label's centre and at the input's centre both returned an element inside the dialog, in the second and the third run (`settled_label_center_in_dialog=yes`, `settled_input_center_in_dialog=yes`, the input still focused, the dialog box unchanged). In the second run the instant reading already hit the dialog, at the dialog's `span.uc-first.relative`, the element the red run of Task 1 names as intercepting the click. The reading taken at the instant of the focus differed between runs (`A11Y_CENTER_HITS_DIALOG_AT_FOCUS=` above): in the third run it returned the `html` element at both points, which is what Chrome's hit test answers while a document View Transition covers the page. The app runs one on navigation into the question, so the instant reading most likely fell inside that transition; this cause is **unconfirmed** (not measured). The boxes are the same in every reading, so the classification does not depend on it.
- **`A11Y_ESCAPE_CLOSES=no`.** After `Escape` and half a second, the dialog was still present, not `inert` (`dialogs_after=1 inert_after=0`), and `getByRole('dialog', …)` still counted 1, which agrees with `components/alert/` having no Escape handler.
- **`A11Y_FINDING=focus-entirely-obscured`.** With the prompt open on Desktop Chrome at 1280×720, keyboard focus on the fifth (last) Likert choice of the first question sits entirely behind the non-modal consent dialog, and Escape does not reveal it. WCAG 2.2 SC 2.4.11 Focus Not Obscured (Minimum) (AA) fails a component that is entirely hidden by author-created content when it receives focus. W3C's understanding text says an entirely obscured focus indicator would likely fail 2.4.7 Focus Visible, which is AA in WCAG 2.1, the project's standard.
- **`MEASURE_SPEC_REMOVED=yes`.** `test ! -e tests/tests/deployed/consent-overlap-measure.smoke.ts` holds and `git status --porcelain -- tests` prints nothing. `git log --all --format=%H -- tests/tests/deployed/consent-overlap-measure.smoke.ts` prints nothing: the file was never committed. Its text was kept in the session scratch directory only.

### For the operator: the two app fixes, and what no gate catches

- **`scroll-padding`.** Bottom `scroll-padding` on the scrolling root, plus bottom padding on the main layout, equal to the open Alert's height (174 px at this viewport, the box above, and more on a narrow screen, where the Alert spans the full width), applied only while the Alert is open. Focus then scrolls a covered choice clear of the prompt, and the page has room to scroll. It addresses 2.4.11 and 2.4.7 for every focusable element under the prompt, for keyboard and pointer users alike.
- **`escape-closes`.** Escape closes the Alert. This brings in only the exemption of 2.4.11's second note (the user can reveal the focused component without moving focus), and that note's text speaks of content the user opened, while this prompt opens by itself. Read that way, Escape alone may not meet the criterion. That reading is the executor's, not a measurement. It also adds a keyboard dismissal the Alert lacks today.
- **No gate catches it.** No axe scan runs with the voter prompt open: the local scans run on datasets where the voter prompt does not show, or for the contestant opt-out. And axe would not detect obscured focus in any case, since it checks the DOM and not what a fixed overlay paints over. A fix would need its own E2E assertion, a box check like the one above.
