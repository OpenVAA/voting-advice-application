## Warnings

### WR-01: The probe can report "limit not in force" on a healthy deployment when the window resets partway through a run

**File:** `tests/tests/utils/callerLimitProbe.ts:101-132`
**Issue:** `invitation_caller_take` uses a fixed window (`private.invitation_throttle_take`, schema/506-invitation-rpcs.sql:659-664). The first take after `window_start + 10 min` resets the count to 1 and starts a new window. The probe allows at most `limit + 1` = 31 calls. Take a caller whose current window already holds `k` takes, with 1 ≤ k ≤ 29, and suppose that window ends after `j ≥ 1` of the probe's calls. The new window then admits 30 more calls, so the first refusal can come no earlier than call `j + 31` > 31. The probe returns `ok: false` with "no 429 within 31 calls: the per-caller limit is not in force; check … behind_cloudflare", but the limit is working correctly.

How the window gets partly used:
- an earlier smoke run that was aborted, or that failed partway through the probe on a transient non-200/429 answer;
- the operator's own `check-code`, `request-link` or `request-recovery` traffic from the same address in the last 10 minutes.

Each of these is likely when an operator re-runs `yarn test:e2e:deployed` from the same machine. This is an intermittent false red, which the project's E2E Hard Rule treats as a defect. The probe's own docstring already says the admitted count "is reported, not judged", so a higher ceiling costs nothing in detection: a deployment with no limit in force still never answers 429.
**Fix:** Allow one window reset within the call budget:
```ts
// A window that was partly used when the probe started can end partway through, and the new window admits `limit` more calls.
const calls = 2 * limit + 1;
```
Then update the unit tests: "no 429 within 61 calls", the `codes` lengths, and the `limit = 3` case → 7. Also update the "31 calls" wording in `caller-limit.smoke.ts:4`.

### WR-02: The settings check sends the database password over a connection that does not verify the server

**File:** `.github/workflows/deploy.yml:345-368` (env pinned exactly by `infra/scripts/deploy-workflow.test.ts:38-45`)
**Issue:** The step sets `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD` but no `PGSSLMODE`, so libpq falls back to its default, `sslmode=prefer`. That means TLS without certificate or host verification, and a silent fall back to plaintext if TLS negotiation fails. An active network attacker between the runner and `*.pooler.supabase.com` can then:
- impersonate the pooler. With no `PGCHANNELBINDING=require`, a SCRAM exchange can be relayed;
- answer the `SELECT` itself, which turns this security gate into a pass.

The migrations step at :311-336 already has the same gap. This phase copies it into a new step whose whole purpose is a security assertion. `SETTINGS_ENV` then pins the gap in place: it requires the environment to hold exactly these six keys, so adding the fix fails the guard test.
**Fix:** Add `PGSSLMODE: verify-full` and `PGSSLROOTCERT` pointing at the Supabase CA, which is committed or downloaded with a pinned checksum. At minimum use `PGSSLMODE: require` with `PGCHANNELBINDING: require`. Add the same keys to `SETTINGS_ENV` and to the migrations env pin.

### WR-03: The guard tests pass when the settings step can no longer fail the run

**File:** `infra/scripts/deploy-workflow.test.ts:436-452`
**Issue:** The new guard pins these and nothing more:
- the step's position;
- its exact environment;
- five lines of its script: `export PGUSER…`, `unset …`, `settings_exit=0`, `psql … || settings_exit=$?` and `echo "settings_exit=…"`.

So each of these mutations leaves every test green:
- deleting the `if [ "$settings_exit" -ne 0 ]; then … exit 1; fi` block;
- changing `exit 1` to `exit 0`;
- adding `continue-on-error: true` to the step;
- adding an `if:` that skips the step.

The `|| settings_exit=$?` capture, under `set -uo pipefail` without `-e`, means that without that block a finding is logged and the run carries on to the functions and the rollout. The mutation tests ("removed", "moved after the apply") cover order only. Nothing in `infra/scripts/` checks `continue-on-error` anywhere.
**Fix:** Extend the guard:
```ts
expect(script).toContain('if [ "$settings_exit" -ne 0 ]; then');
expect(script).toMatch(/if \[ "\$settings_exit" -ne 0 \]; then\n\s+echo "::error::[^\n]*"\n\s+exit 1\n\s+fi/);
expect('continue-on-error' in settings).toBe(false);
expect('if' in settings).toBe(false);
```
Add a mutation test that drops the `exit 1` and is red.

## Info

### IN-01: A type assertion stands in for type narrowing in the caller-limit spec

**File:** `tests/tests/deployed/caller-limit.smoke.ts:37-39`
**Issue:** `result as Extract<ProbeResult, { ok: true }>` relies on a comment ("the hard assertion above has proved `ok: true`") instead of the type system. If someone later loosens the `toMatchObject` (for example to `expect.soft`), the cast still compiles and the spec logs `undefined`.
**Fix:** Narrow instead. A thrown error is a hard failure, so the rigidity contract still holds:
```ts
if (!result.ok) throw new Error(result.reason);
const { admitted, retryAfterSeconds } = result;
```

### IN-02: Phantom requirement — tracing is turned off to protect a public key

**File:** `tests/tests/deployed/caller-limit.smoke.ts:10,20`
**Category:** necessity
**Issue:** The stated reason for `trace: 'off'` is that "the calls' headers carry the anon key". But the spec reads that key from the inline `env` block the application serves to every visitor (`extractServedEnv(html).PUBLIC_SUPABASE_ANON_KEY`, line 26). The key is public by design, so the trace would expose nothing that `GET /` does not. This is a judgment call: a policy of keeping traces free of any key would justify the setting, but the comment states a rationale that does not hold. Turning tracing off costs the trace on a red probe, which is when it is most useful.
**Fix:** Either keep tracing at the config default, `retain-on-failure`, or give the actual policy reason in the comment. The guard at `deployedSmokeGuards.test.ts:258-263` pins the line, so update it to match.

### IN-03: The probe's failure message names one cause when there are several

**File:** `tests/tests/utils/callerLimitProbe.ts:129-132`
**Issue:** In the deploy pipeline, the `settings` stage has already proved `behind_cloudflare` true before the smoke runs. A "no 429" there must have another cause:
- the window reset in WR-01;
- `cf-connecting-ip` missing at the function;
- the deployed function predating the take;
- the egress address changing between calls.

The message points the operator only at `behind_cloudflare` and the SQL check, which already passed in the same run.
**Fix:** Word the message as possible causes, for example "…not seen to be in force: check behind_cloudflare (check-deployment-settings.sql), that the function receives cf-connecting-ip, and that no earlier traffic from this address shares the window".

### IN-04: The consent-handler guard checks only one file, not the files it imports

**File:** `tests/tests/utils/deployedSmokeGuards.test.ts:265-274`
**Issue:** The test asserts "the shared navigation installs none" by searching the text of `voterNavigation.ts` for `addLocatorHandler`. `navigateToFirstQuestion` reaches other modules (it imports `voterHomePage.fixture` among others), and the repo already has a shared helper that installs a consent-granting handler (`fixtures/voter/voter-journey.fixture.ts:92-94`). If a granting handler reached the deployed voter spec through an import, this guard would stay green. The deployed run would then grant consent and send identified usage events to the hosted project, which is the exact outcome the spec's header rules out.
**Fix:** Run the existing value-import walk (the `describe('the value-import walk')` machinery in the same file) from `voter.smoke.ts`, and assert that no reached file other than `voter.smoke.ts` contains `addLocatorHandler`.

### IN-05: The SQL header's exit-status list leaves out status 1, and the step has no time limit of its own

**File:** `infra/scripts/check-deployment-settings.sql:12-15`; `.github/workflows/deploy.yml:345-368`
**Issue:**
- **Exit status.** The header lists the statuses 0, 2 and 3. psql also exits 1 on a fatal error of its own, such as the script file not being found or running out of memory, and the step reports that as a settings failure too. The `infra/README.md` "Reading a red run" row likewise lists only 2 and 3.
- **Time limit.** `PGCONNECT_TIMEOUT` bounds only the connection. With no `statement_timeout` (`PGOPTIONS=-c statement_timeout=…`) and no step `timeout-minutes`, a session holding `ACCESS EXCLUSIVE` on `private.deployment_settings` would leave the step hanging until the 60-minute job timeout.
**Fix:** Add a line for status 1 to the header and the README row. Add `PGOPTIONS: "-c statement_timeout=15s"` (and to `SETTINGS_ENV`) or `timeout-minutes: 2` on the step.
