# Phase 189.1: Address tech debt: invitation-limit guard and trackEvents smoke - Research

**Researched:** 2026-11-21
**Domain:** Deploy pipeline guard (GitHub Actions + psql against hosted Supabase), deployed Playwright smoke entry, voter consent prompt
**Confidence:** HIGH for the mechanisms (every one read in the tree this session, two probed); MEDIUM for the operator-facing choices, which no CONTEXT.md has locked

## Summary

There are two debts, and each comes down to a small, well-bounded change. **(1) The limit is silently inert.** `public.invitation_caller_take` returns `0` (admit) whenever `private.deployment_settings.behind_cloudflare` is not true. The migration ships the row with `false`. The only writer for a deployment is the hand-run `infra/scripts/bootstrap.sql`, and nothing in `.github/workflows/deploy.yml` reads the value. A rebuilt or restored hosted project, or a bootstrap run with `BOOTSTRAP_BEHIND_CLOUDFLARE=false` by mistake, therefore deploys green with no per-caller limit. It also leaves the feedback limit (OBS-10) keyed on a shared platform hop. The deploy job already holds a `postgres` connection to the hosted database in its `migrations` step (session pooler, `PGPASSWORD` from the `staging` environment secret, psql installed). A read-only assertion fits there as a new step right after the migration push and before the AWS apply. A misconfigured project then stops the rollout and the alert names the cause.

**(2) The voter smoke is red with `trackEvents` on.** `voter.smoke.ts` reaches the first question through `navigateToFirstQuestion`, which, unlike `walkUntilQuestionsIntro`, installs no consent-prompt handler. With `trackEvents` on and the consent mode gated, the voter layout queues `DataConsentPopup`. It is a non-modal `Alert` (`role="dialog"`, `aria-modal="false"`), fixed to the bottom of the viewport, and it covers the fifth `question-choice` that answer mode `max` clicks. That was observed in 188-12. The local suite never caught this because every local spec that runs with `trackEvents` on handles the prompt explicitly, and every spec that uses `navigateToFirstQuestion` runs with it off or handles it itself. The fix the smoke needs is a spec-local `page.addLocatorHandler` that declines through the prompt's real control. Playwright built that API for exactly this kind of overlay: it may or may not show, and at unpredictable times. Do not put it into the shared `navigateToFirstQuestion`, which two local specs rely on to see the prompt raw.

A third deliverable is a deployed smoke `caller-limit.smoke.ts`. It sends up to 31 `check-code` calls with fresh unknown codes from the runner's own address and asserts a 429 with `{ "error": "too-many-requests" }` and an integer `Retry-After` from 1 to 600. Its only write is the caller's own `private.invitation_throttle` row, which expires with the 10-minute window. Its side effect is that the calling address is refused by the three limited operations of the staging project for up to 10 minutes. It must not send `cf-connecting-ip`, because Cloudflare refuses a client-sent copy with 403.

**Primary recommendation:**
- **Assert** `behind_cloudflare = true` in a new read-only deploy step that runs a new `infra/scripts/check-deployment-settings.sql` (modelled on `check-seed.sql`), placed between `migrations` and `functions`. Do not let the pipeline *establish* the value.
- Add `caller-limit.smoke.ts`, built on a pure, unit-tested probe helper.
- Make `voter.smoke.ts` decline the consent prompt through a spec-local `addLocatorHandler`.
- Leave the app unchanged in this phase, but record the measured WCAG finding (see Open Question 1).

### Pattern 1: A read-only SQL check run by psql, whose exit status is the verdict
**What:** A `\set ON_ERROR_STOP on` script with one `DO` block that raises `check-<name>: …` on a finding, so that psql exits 3. This is the existing convention of `check-seed.sql` and `bootstrap.sql`.
**When to use:** The settings assertion.
**Evidence:** `infra/scripts/check-seed.sql` header: "Exit status, which is psql's own and is the verdict: 0 nothing of the seed was found / 2 the connection was refused or lost / 3 a finding" [VERIFIED: Read infra/scripts/check-seed.sql, header]. The mechanism was probed this session on the local stack with a scratch copy of the check:
```
psql -X -q -c "BEGIN" -c "UPDATE private.deployment_settings SET behind_cloudflare = false" -f check.sql  → red_exit=3
psql -X -q -f check.sql                                                                                 → green_exit=0
select behind_cloudflare … → t   (the uncommitted UPDATE was discarded with the session)
```
[VERIFIED: local probe, psql 17.6 against 127.0.0.1:54322]. The same `BEGIN` + `UPDATE` prefix is the red-first recipe for the real file on the shared local stack, and it leaves the stack unchanged.

Skeleton (values quoted below):
```sql
-- Deployment settings check: does this hosted database trust cf-connecting-ip?
-- Run: psql -X -f infra/scripts/check-deployment-settings.sql   (PG* variables, as postgres)
-- Exit: 0 behind_cloudflare is true / 2 connection refused or lost / 3 a finding, message begins `check-deployment-settings:`
\set ON_ERROR_STOP on
DO $check$
DECLARE
  rows_found bigint;
  trusted boolean;
BEGIN
  SELECT count(*), bool_and(behind_cloudflare) INTO rows_found, trusted FROM private.deployment_settings;
  IF rows_found = 0 THEN
    RAISE EXCEPTION 'check-deployment-settings: private.deployment_settings holds no row; run infra/scripts/bootstrap.sql with BOOTSTRAP_BEHIND_CLOUDFLARE=true';
  ELSIF trusted IS NOT TRUE THEN
    RAISE EXCEPTION 'check-deployment-settings: behind_cloudflare is false, so the per-caller limit of account-access admits every call and the feedback limit keys on the gateway hop; run infra/scripts/bootstrap.sql with BOOTSTRAP_BEHIND_CLOUDFLARE=true';
  END IF;
END
$check$;
```
The table shape is `singleton boolean PRIMARY KEY DEFAULT true CHECK (singleton)` and `behind_cloudflare boolean NOT NULL DEFAULT false`, followed by `INSERT INTO private.deployment_settings DEFAULT VALUES ON CONFLICT DO NOTHING;` [VERIFIED: Read apps/supabase/supabase/schema/107-feedback.sql, the "Per-deployment settings that migrations cannot know" block]. Because of that `INSERT`, a migrated-but-not-bootstrapped project has the row with `false`, which is the common red case. The row-missing branch is defensive.

### Pattern 2: A deploy step that reads its status with `|| name=$?` and gets secrets through `env` only
**What:** Every `run:` step uses `name=0; cmd || name=$?; echo "name=$name"`, because a step that names no shell runs under `bash -e`. Secrets reach scripts only through `env:`, and no `run:` script holds a `${{ }}` expression [VERIFIED: Read .github/workflows/deploy.yml header comment and infra/scripts/workflowGuards.ts `sharedViolations` doc].
**New step (prescriptive):** id `settings` (stage `settings`), placed directly after `migrations`. Its env is a copy of the `migrations` step's PG block (`PGHOST: ${{ vars.SUPABASE_POOLER_HOST }}`, `PGPORT: "5432"`, `PGDATABASE: postgres`, `PGCONNECT_TIMEOUT: "10"`, `PGPASSWORD: ${{ secrets.SUPABASE_DB_PASSWORD }}`, `REF: ${{ steps.link.outputs.ref }}`). The script sets `export PGUSER="postgres.$REF"` and `unset PGHOSTADDR PGSERVICE`, exactly as the migrations step does [VERIFIED: Read deploy.yml "Push the migrations" step]. It prints `settings_exit=<n>`, and on a non-zero status prints `::error::check-deployment-settings.sql exited <n>.` and exits 1. It needs neither `SUPABASE_ACCESS_TOKEN` nor `SUPABASE_DB_PASSWORD` under that name: only `PGPASSWORD`.
**Guard tests that must change** [VERIFIED: Read infra/scripts/deploy-workflow.test.ts]:
- `STAGE_ORDER = ['build', 'plan', 'migrations', 'functions', 'apply', 'stable', 'smoke', 'served-build', 'alert']`. Insert `'settings'` after `'migrations'`.
- "gives the Supabase and database secrets to the link, migrations and functions steps only": `expect(holders).toEqual(['link', 'migrations', 'functions'])` becomes `['link', 'migrations', 'settings', 'functions']`, and `expect(mentions).toHaveLength(6)` becomes `7`.
- The alert: add `SETTINGS_OUTCOME: ${{ steps.settings.outcome }}` and the pair `"settings:$SETTINGS_OUTCOME"` between `migrations:$MIGRATIONS_OUTCOME` and `functions:$FUNCTIONS_OUTCOME`. "names a stage for every step before it" enforces both.
- Add one case under "the deploy-specific guards are red on a faulty copy": the settings step removed, or moved after `apply`.
- "removes … in the cleanup step": the new step writes no file, so nothing changes there unless a log file is added.

### Pattern 3: A deployed smoke that calls the function the way the browser does, without a Supabase client
**What:** The ESLint deployed block forbids value imports matching `(^|/)(supabaseAdminClient|authApi|accountAccessClient|localSupabaseUrl)(\.ts)?$`, `^@openvaa/dev-seed$`, `^@supabase/(supabase-js|ssr)$` and `^dotenv(/.*)?$` [VERIFIED: Read tests/eslint.config.mjs, last block]. The existing `tests/tests/utils/accountAccessClient.ts` is therefore off limits, because it imports `supabaseServiceRoleKey`. The smoke uses the Playwright `request` fixture. It reads the anon key and `PUBLIC_SUPABASE_URL` from the served page with the existing `extractServedEnv`, and the project id with `extractServedProjectId` (both exported by `tests/tests/utils/deployedTarget.ts`) [VERIFIED: Read deployedTarget.ts export list]. The gate has already proved that the served ref and project id are the dedicated ones.
**Request shape** (matches 188-16's hosted proof and `parseAccountAccessRequest`): `POST ${PUBLIC_SUPABASE_URL}/functions/v1/account-access` with headers `apikey: <anon>`, `Authorization: Bearer <anon>`, `Content-Type: application/json`, and body `{ "operation": "check-code", "project_id": "<id>", "code": "<fresh random>" }`. A code is any string of length 1..64 (`const CODE_MAX_LENGTH = 64;`, `isStringOfLength(value, 1, CODE_MAX_LENGTH)`) [VERIFIED: Read contract.ts]. A body that does not parse is answered 400 before the take, so it would never reach 429 (`if (parsed === null) return answer(BAD_REQUEST_BODY, 400);` precedes `if (takesCallerSlot(request.operation))`) [VERIFIED: Read account-access/index.ts, Deno.serve handler].
**Values to assert, quoted:**
- `v_max constant integer := 30;` and `v_window constant interval := interval '10 minutes';`, inside `public.invitation_caller_take` [VERIFIED: Read apps/supabase/supabase/schema/506-invitation-rpcs.sql, the invitation_caller_take block].
- `export const TOO_MANY_REQUESTS_BODY = Object.freeze({ error: 'too-many-requests' } as const);` and `'Access-Control-Expose-Headers': 'Retry-After'` [VERIFIED: Read contract.ts, CORS_HEADERS block].
- `return answer(TOO_MANY_REQUESTS_BODY, 429, { 'Retry-After': String(seconds) });` [VERIFIED: Read index.ts `tooManyRequests`].
- The DB returns `GREATEST(1, ceil(extract(epoch FROM (v_start + v_window - now())))::integer)` [VERIFIED: same block], so `Retry-After` is an integer from 1 to 600.

**Probe algorithm (pure helper, injected `post`):**
1. For `i` from 1 to 31 (= `v_max + 1`), send one `check-code` with a fresh code. Stop at the first answer that is not 200.
2. Every answer before the stop must be 200 with a body `{ status }` whose status is one of the three words. A fresh random code answers `unknown`.
3. The stop answer must be 429, with body exactly `{ "error": "too-many-requests" }` and a `retry-after` header matching `^[1-9][0-9]*$` with a value ≤ 600.
4. If 31 answers of 200 arrive with no 429, fail with a named message: "no 429 within 31 calls: the per-caller limit is not in force; check private.deployment_settings.behind_cloudflare (infra/scripts/check-deployment-settings.sql)".
5. Never assert exactly 30 admitted. The caller's window may already be partly or fully used, for instance by a re-run within 10 minutes from the same runner or workstation, and then the first 429 comes earlier, possibly at call 1. Every such outcome still proves that the limit is in force.

Pin the two constants (30, 10 minutes / 600 s) with a unit test that reads `506-invitation-rpcs.sql` for the quoted lines, so the smoke cannot drift from the function.

### Pattern 4: Answering an overlay that may or may not appear (`page.addLocatorHandler`)
**What:** Playwright "checks for the overlay every time before executing or retrying an action that requires an actionability check". After the handler runs, it "will ensure that overlay that triggered the handler is not visible anymore". The handler's time counts toward the triggering action's timeout, and the handler moves focus and the mouse [CITED: playwright.dev/docs/api/class-page#page-add-locator-handler].
**The in-tree precedent** is `walkUntilQuestionsIntro`: `const consentGrant = page.getByRole('dialog').getByRole('button', { name: /agree to share my data/i }); await page.addLocatorHandler(consentGrant, async () => { await consentGrant.click(); });` [VERIFIED: Read tests/tests/fixtures/voter/voter-journey.fixture.ts].
**Prescription for the smoke:** decline rather than grant, so the smoke sends nothing beyond the identifier-free pageview that is sent anyway (`maySendPageview` = `relayUsable(input)`) [VERIFIED: Read apps/frontend/src/lib/contexts/app/tracking/gates.ts]. Scope the locator to the named dialog, so another popup, such as a voter notification queued ahead of it, cannot match:
```ts
const prompt = page.getByRole('dialog', { name: /collecting usage data/i });
const decline = prompt.getByRole('button', { name: /don.t want to share my data/i });
await page.addLocatorHandler(decline, async () => {
  await decline.click();
});
```
The names are quoted: `"title": "Collecting Usage Data"` (`common.privacy.dataCollection.title`, the `aria-label` of the Alert); `"denied": "I don’t want to share my data"` and `"granted": "Yes, I agree to share my data"` [VERIFIED: Read apps/frontend/messages/en/common.json and privacy.json]. The `.` in the regex covers the typographic apostrophe, as in `contestantPrivacyPage.fixture.ts`'s `DENIED_BUTTON = /don.t want to share my data/i`.
**Why "hidden afterwards" holds:** `DataConsent`'s `onChange` calls `alertRef?.closeAlert()`. `closeAlert` calls `onClose`, and the root layout's popup renderer passes `onClose={() => { item.onClose?.(); popupQueue.shift(); }}`, which unmounts the Alert [VERIFIED: Read DataConsentPopup.svelte, Alert.svelte, apps/frontend/src/routes/+layout.svelte popup block]. The prompt is queued once, in the voter layout's `onMount` [VERIFIED: Read (voters)/+layout.svelte], so it does not come back during the walk.
**Install it before `navigateToFirstQuestion(page)`, in the spec itself.** Do not add it to `navigateToFirstQuestion`. `voter-pageview-only.spec.ts` asserts that no prompt is shown, and `analytics-privacy.spec.ts` drives the prompt itself, and both call `navigateToFirstQuestion` [VERIFIED: `git grep -ln navigateToFirstQuestion -- tests`]. A handler there would hide a regression in the first and change the second.

### Anti-Patterns to Avoid
- **The pipeline writing the flag.** It creates two writers and masks a skipped bootstrap (see Alternatives).
- **Sending `cf-connecting-ip` from the smoke.** On hosted Supabase, Cloudflare refuses a request that carries its own `cf-connecting-ip` with 403 before the project ("Observed on staging, 2026-11-10 … refused by Cloudflare with status 403") [CITED: apps/docs deployment guide § Feedback rate limit and Cloudflare, read this session]. Locally the header is required to get a bucket, because without it the take is admitted with no row (188-05 `LOCAL_NO_HEADER_STATUS=200`). The helper therefore takes optional extra headers, and the smoke passes none.
- **A `try/catch` or `isVisible({timeout})` probe for the prompt.** The rigidity contract forbids both. `addLocatorHandler` is the conditional mechanism.
- **Editing the schema comment in `schema/107-feedback.sql`** to mention the pipeline. Schema files feed the declarative-schema/migration parity machinery. Keep the statement in the docs and in the new script's header.
- **Asserting an exact admitted count of 30** in the smoke (see Pattern 3, step 5).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| An overlay that may or may not appear | A polling `isVisible` loop or a `try/catch` around a click | `page.addLocatorHandler` | Built-in retry-with-handler semantics, and the rigidity contract allows it |
| Reading the anon key, URL and project id from staging | A new HTML parser | `extractServedEnv`, `extractServedProjectId` in `deployedTarget.ts` | Already used and unit-tested by the gate |
| A DB check with a verdict status | A Node script with a pg client | A psql script with `ON_ERROR_STOP` and `RAISE EXCEPTION` (exit 3) | The repository convention (`check-seed.sql`), no new dependency, password via `PGPASSWORD` only |
| Calling `account-access` in the smoke | `accountAccessClient.ts` or supabase-js | Playwright `request.post` | ESLint forbids both in the deployed entry |
| Binding operator approval | Relayed "approved" text | `phases/183-*/tools/attempt.sh new/put/bound/has` | Executors refuse relayed approval. The orchestrator binds the reply (memory: operator approval bound at top level) |

## Common Pitfalls

### Pitfall 1: The smoke limits whoever runs it
**What goes wrong:** After `caller-limit.smoke.ts`, the calling address gets 429 from `check-code`, `request-link` and `request-recovery` on the staging project for up to 10 minutes. An operator who runs the smoke from a workstation and then tries a sign-in-link mail on staging is refused.
**Why:** The caller is keyed per project per address, across the three operations together.
**How to avoid:** Document it in tests/README.md § Deployed smoke run and in the spec header. Order is not a problem: `contestant.smoke.ts` signs in with a password and takes no caller slot, and `code-sign-in` takes none either (`CALLER_LIMITED_OPERATIONS` = `'check-code', 'request-link', 'request-recovery'`) [VERIFIED: Read callerLimit.ts].
**Warning signs:** A 429 in a later manual staging check within 10 minutes of a smoke run.

### Pitfall 2: The README's "read-mostly" statement and the guard tests
**What goes wrong:** tests/README.md says the run "seeds nothing, clears nothing and holds no service-role client". The new spec writes one throttle row. `deployedSmokeGuards.test.ts` pins the entry list with `arrayContaining([...])` and walks the value-import closure.
**How to avoid:** Update the README wording: one `caller:` row per run, expiring with its window, which a later take deletes. Add the new util to the ESLint deployed block's `files`. Extend the guard test's expected entry list. Name the new spec so that no local project's `testMatch` collects it. The guard "collects no file under tests/tests/deployed/ that a local project would also collect" checks this; `*.smoke.ts` is safe.

### Pitfall 3: The workstation smoke procedure requires `apps/` and `packages/` unchanged against the deployed SHA
**What goes wrong:** tests/README.md step 1 requires `git diff --quiet "$DEPLOYED_SHA" -- apps packages` to exit 0. The docs edits in `apps/docs` break that precondition for a workstation run against the currently served build.
**How to avoid:** Either run the workstation smoke before the docs commit, or make the observed run a pipeline run of a commit that already holds every change, docs included, so that `SMOKE_EXPECTED_SHA` is that commit. Recommended: the pipeline run is the phase's proof, and workstation runs are only for iterating.

### Pitfall 4: A red-first run for the deployed specs needs the hosted state
**What goes wrong:** CLAUDE.md requires each new or rewritten test to be seen red first, then green. The voter smoke is red only with `trackEvents` true on staging, and the limit smoke only with `behind_cloudflare` false on staging. Both are hosted writes, so both need the operator.
**How to avoid:**
- Voter smoke: 188-12 recorded the red (`Test timeout of 90000ms exceeded` at `locator.click` of the fifth `question-choice`, with the dialog intercepting pointer events). In the operator sitting, with `trackEvents` true, run the unchanged spec once (red) and the changed one (green).
- Limit smoke: red-first with the pure helper's unit test (a stand-in that answers 31 × 200 must fail with the named message). Optionally, also record a local run of the helper against the local function with a TEST-NET `cf-connecting-ip` (e.g. `198.51.100.7`, as in 188-05). The function's take runs in its own database session, so the transaction trick cannot make it red. - Settings check: red/green on the local stack with the transaction recipe of Pattern 1, which leaves the stack untouched.

### Pitfall 5: The pipeline order on a brand-new project
**What goes wrong:** On a fresh project, the first pipeline run before bootstrap would go red at `settings`.
**Why it is fine:** The deployment guide orders a fresh project as migrations by hand → bootstrap → … → § The deploy pipeline [VERIFIED: Read the guide's headings and "Migrations and functions" / "The bootstrap" paragraphs]. The settings check runs after the push in the pipeline, so the table always exists. State the ordering in the guide's pipeline section: "the pipeline fails at `settings` until the bootstrap has run".

### Pitfall 6: The handler declines, but a notification is queued first
**What goes wrong:** If `notifications.voterApp.show` is on for staging, the popup queue shows the Notification first and the consent prompt only after it is closed. The Notification is `role="alert"` without actions.
**How to avoid:** The consent locator is scoped to the dialog by name, so it never matches the notification. If staging ever turns a voter notification on, the smoke needs a second handler. Today it is out of scope, so note it in the spec header only.

### Pitfall 7: Host sleep voids runs, and long gates trip watchdogs
The full local E2E run (~18 min) and the deploy run (~10 min) must run in the background, and the executor polls them (memory: executor watchdog on long gates). Exit 8 with `VOID-host-suspend.txt` is void, never a red, and the run is made again under a new `--run-dir`.

## Code Examples

### The probe helper (shape only; the planner fixes names)
```ts
// tests/tests/utils/callerLimitProbe.ts — pure; no Supabase client, no env reads.
export type ProbeAnswer = { status: number; body: unknown; retryAfter: string | null };
export type ProbeResult =
  | { ok: true; admitted: number; retryAfter: number }
  | { ok: false; reason: string };

/** Calls `post` up to `limit + 1` times with fresh codes and stops at the first answer that is not 200. */
export async function probeCallerLimit(
  post: (code: string) => Promise<ProbeAnswer>,
  freshCode: () => string,
  limit: number, // 30, pinned to `v_max constant integer := 30;`
  windowSeconds: number // 600, pinned to `interval '10 minutes'`
): Promise<ProbeResult> {
  for (let call = 1; call <= limit + 1; call++) {
    const answer = await post(freshCode());
    if (answer.status === 200) continue;
    if (answer.status !== 429) return { ok: false, reason: `call ${call} answered ${answer.status}` };
    // body must deep-equal { error: 'too-many-requests' }; retryAfter must be /^[1-9][0-9]*$/ and <= windowSeconds
    // ...
    return { ok: true, admitted: call - 1, retryAfter: Number(answer.retryAfter) };
  }
  return { ok: false, reason: `no 429 within ${limit + 1} calls: the per-caller limit is not in force` };
}
```
The spec then does `expect(result, result.ok ? '' : result.reason).toMatchObject({ ok: true })`, which is a hard assertion. `freshCode` uses `crypto.randomUUID()` sliced to 12 characters or similar (any 1..64-character string parses).
