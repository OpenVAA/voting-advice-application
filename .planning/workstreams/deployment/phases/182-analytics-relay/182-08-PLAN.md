  <behavior>
    - `enqueue` of three events on an empty queue returns 3 and `size()` is 3.
    - With `maxSize` 5, enqueueing 4 and then 4 returns 4 and then 1, and `size()` is 5.
    - `flush()` passes the queued events to `provider.capture` in calls of at most `batchSize` events, in order, and leaves `size()` at 0.
    - A provider whose `capture` rejects leaves `flush()` resolved and the queue empty.
    - With fake timers, events enqueued and left alone are passed to the provider after `flushIntervalMs` without a call to `flush()`.
    - `registerShutdownFlush(queue, emitter)` makes one emission of `sveltekit:shutdown` on the stand-in emitter call the provider once with the queued events; a second emission does nothing.
    - `enqueue` returns before `capture` is called.
  </behavior>
  <action>
    Write `queue.test.ts` first with the docblock `@vitest-environment node`, a recording stand-in provider and Vitest's fake timers.

    `queue.ts` exports a factory, so that tests share no state. The queue is an array with a cap: when an `enqueue` would exceed `maxSize`, it keeps what fits, drops the rest and adds the number dropped to a counter; at the next flush, if the counter is above zero, it logs one `warn` record with a constant message and the count, and resets the counter. It logs no event. The flush timer is created with the interval given, is `unref`'d so that it never keeps the process alive, and is cleared by `stop()`. `flush()` takes the whole queue, sends it in slices of `batchSize`, awaits each `capture`, catches a rejection and continues; it never rejects. `enqueue` is synchronous and never awaits.

    `registerShutdownFlush` attaches one `once` listener for the event name `sveltekit:shutdown` on the target, by default `process`, and the listener calls `flush()` and `stop()`. The module comment says that adapter-node emits this event before the process exits and that the Vite dev server does not emit it.

    `relay.ts` is one exported async function that takes the request and the origin as input and the configuration, an `enqueue` function and an optional clock as dependencies. It imports no `$env` module, no SvelteKit module and no logger call that takes a value from the request. The steps run in this order and each returns as soon as it decides:
    1. provider `none`: return 204 before any header or body is read;
    2. the `Sec-GPC` header is present: return 204;
    3. same origin: when `Sec-Fetch-Site` is present it must be `same-origin`; when it is absent, `Origin` must equal the input origin; otherwise 403;
    4. the media type of `Content-Type` must be `application/json`, otherwise 415; a declared length above `MAX_BODY_BYTES` is 413; read the body as text and answer 413 when its byte length is above the cap;
    5. parse the text as JSON and pass it to `parseBatch`; a parse error or a result that is not ok is 400;
    6. build one `AnalyticsEvent` per kept wire event: the time is the clock minus `ago`; the app is `appOfRoute` of the envelope's route id, and an undefined app is 400; the pageview's attributes are the route id, the locale, the duration clamped to `MAX_PAGEVIEW_DURATION_MS` and rounded down to a multiple of `PAGEVIEW_DURATION_ROUNDING_MS`, and `allowedPageviewParams` of its params, and it is never given an id; every other event keeps its parsed attributes, and keeps its id only when the visit-id mode is `memory`, the event is not sensitive under consent mode `free`, and the id's UUIDv7 timestamp is within `MAX_VISIT_ID_SKEW_MS` of the clock;
