Every command runs under Node 24.21.0 (`export PATH="$HOME/.nvm/versions/node/v24.21.0/bin:$PATH"`). Database tests run on the isolated instance `p182` (project id `openvaa-iso-p182`), never on the shared instance `openvaa-local`.

Rules every plan's `<environment>` block states and every record's verify enforces:

- **A gate describes a commit.** Before and after every whole-workspace gate, build, E2E run and recorded run, `git status --porcelain --untracked-files=no` over the whole tree prints nothing and `git rev-parse HEAD` is the same. Otherwise the output is kept verbatim and the task stops at a blocking checkpoint naming the paths; no file of another phase is stashed, reverted or committed. Plan 182-02, which must be one commit, has the one stated exception: its runs before the commit are made on a tree whose only uncommitted tracked changes are its own, compared with an exact list.
- **Scratch state belongs to one attempt.** Each attempt of a task that runs a gate writes a new file `tmp/182-evidence/<slot>.<UTC timestamp>.<short HEAD>.txt` (the directory is ignored; `git check-ignore` proves it, with a fallback outside the repository) and a pointer `tmp/182-evidence/<slot>.current`. A verify or a precondition reads only the file a pointer names. A status or verdict key is written once in an attempt file, and quoted output is indented so that it cannot read as a key. Every verify begins with a guard that fails on a missing pointer, a pointer that names no attempt file, a key written twice, or a tracked record that is not a byte-identical copy of the current attempt file. Gates that are run again are a new attempt that runs all of them. Earlier attempt files are kept and never read.
- **A gate record is bound to the plan's final code.** Every commit of a plan carries the scope `(182-NN):`. A gate verify finds the plan's last commit that changes a file outside `.planning/` with `git log -F --grep` and requires it to be an ancestor of, or equal to, the commit the gates ran on, so a fix committed after a green attempt fails the verify until the gates are run again. Statements about what a plan's commits contain are checked per commit of that scope with `git show --stat`, never over a range that includes other phases' commits.
- **An operator's answer is bound to what it answers and is used once.** The protocol is phase 181's (181-16, `<attempt_protocol>`): the checkpoint writes `CHECKPOINT_PRESENTED attempt=<id> head=<sha>` and shows both; the reply "stack is free <id>" is recorded as `OPERATOR_CONFIRMED_STACK_FREE=yes attempt=<id> head=<sha>`, any other reply as `no`; the last answer line is the one in force; the run task's first step is the answer check, which requires the question and the answer in force to carry this attempt's id and `git rev-parse HEAD`, the answer to follow the question, and no `TASK3_STARTED=` line; on a pass `TASK3_STARTED=` is written at once. One answer authorises one window, the stated runs each made once; a failed run ends the window, the stack is handed back and the records are committed, and the next try is a new attempt with a new confirmation. Two confirmations voided in a row for the same reason stop the plan (`ANSWER_VOIDED=` / `PREVIOUS_ANSWER_VOIDED=`). During a window nobody commits in the checkout, the orchestrator included. The decision of plan 182-02 (`OPERATOR_D13_DECISION`, `D13_STARTED=`) and the span acknowledgement of plan 182-15 (`OPERATOR_SPAN_ACKNOWLEDGED`, `SPAN_STARTED=`) follow the same protocol, the bound on asking again and the rule that nobody commits between the question and the step it authorises included. The decision's reply carries the attempt id too (`land-in-baseline <id>` or `append-after-freeze <id>`); a reply without it selects nothing and is recorded as `none`; the checkpoint has no default, so no option is selected without a person; a valid `append-after-freeze` ends the question, and the plan stops and returns it for a replan. In all seven answer checks and in every `att()` guard the pointer file must hold exactly one line that names a file in the scratch directory.
- **Long gates run in the background** with the exit status in a file; a status is never read through a pipe. Scoped unit runs, `--list` commands and source greps stay in the foreground.
- **E2E verdicts are exit statuses computed over the report**, again inside the verify, and are bound to the run directory's own `head`, `worktree-status.txt`, `exit` and `provenance.txt`. Wrapper status 8 is a void run, not evidence. A red control's reason is read from the report as well: the verdict script's `--failure-contains` requires a text in the error text of the named failed test (the stored key and the third-party host in plan 182-11; the non-pageview sentence with the event name, and the variable's name, in plan 182-31), so a line the executor typed decides nothing.

## Sampling Rate

- **After every task commit:** the scoped command of the task (a unit run of the touched directory, a `--list`, or a source grep)
- **At the end of every plan that changes source:** its closing gates on the commit that holds its work, recorded under `evidence/NN-gates.txt` (frontend typecheck and lint; the whole frontend unit run from plan 182-14 on; `yarn build` in plans 182-01, 182-09, 182-16, 182-17, 182-18, 182-19, 182-22 and 182-26; the tests' typecheck, lint and a11y wiring guard in plans 182-10, 182-16, 182-20, 182-21, 182-27 and 182-30). Plan 182-15 is the one exception: it records no gate, because the tree does not typecheck until plan 182-26 ends
- **Before `/gsd-verify-work`:** `yarn build`, `yarn lint:check`, `yarn test:unit`, `yarn format:check` and the pgTAP directory green on one commit (plan 182-22); one complete green full-suite E2E run in default mode and one complete green run of the consent-free project on the same commit (plan 182-28); the closing record (plan 182-29)
- **Max feedback latency:** 60 seconds for a scoped unit run. E2E feedback comes in five operator-confirmed windows: wave 16 (red run and whole-suite baseline before the cutover), wave 21 (green after the cutover), wave 28 (new specs alone, green), wave 29 (the two red controls by consent mode), wave 30 (full suite and consent-free project)
