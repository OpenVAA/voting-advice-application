<attempt_protocol>
The three tasks of this plan share one attempt file across the operator's wait: the window's, slot `23-window`. The runs of Task 3 have slots of their own, `23-green` and `23-control`.

- What starts it. Task 1 starts the window's attempt by the attempt rule. Every run of Task 1 is a new attempt.
- What continues it. Task 2 and Task 3 append to the file the pointer `23-window.current` names, and to no other window file. They never start a window attempt and never move that pointer. Each run of Task 3 begins one attempt of its slot and writes `WINDOW_ATTEMPT=` with the window's attempt id into it.
- What resets it. Only a new attempt of Task 1. After that, nothing the earlier attempt holds is read: not its readiness lines, not its confirmation, not its runs.
- The question. When Task 2 presents the checkpoint it appends the line `CHECKPOINT_PRESENTED attempt=<attempt id> head=<sha>`, with the sha from `git rev-parse HEAD` at that moment, and shows both values at the top of the checkpoint message. The attempt id is the nonce of the question.
- The answer. When the reply arrives, Task 2 appends the reply, quoted and indented, and then one answer line that carries the two values of the last `CHECKPOINT_PRESENTED` line: `OPERATOR_CONFIRMED_STACK_FREE=yes attempt=<attempt id> head=<sha>` when the reply holds the words "stack is free" and that attempt id, and the same line with `no` in place of `yes` for any other reply. The answer key may occur more than once in an attempt; the last answer line is the one in force, so a later `no` overrides an earlier `yes`.
- The answer check. Task 3 runs the command below before anything else and reads its status directly. It exits 0 only when the pointer names an attempt file that carries its own id, the last `CHECKPOINT_PRESENTED` line and the last answer line both carry that id and the sha `git rev-parse HEAD` prints now, the answer is `yes`, it was written after that question, and the attempt file has no `TASK3_STARTED=` line.
- A refused answer is never used. When the check exits non-zero, Task 3 touches no stack and writes no tracked file. If `git rev-parse HEAD` still equals the sha on the last `CHECKPOINT_PRESENTED` line and the file has no `TASK3_STARTED=` line, Task 2 presents the checkpoint again in the same attempt. In every other case (the pointer or the attempt file is missing, `HEAD` has moved since the question, the answer was already used) the attempt is over: Task 1 runs again as a new attempt, and then Task 2 asks again.
- An answer is used once. Directly after a passing check Task 3 appends `TASK3_STARTED=<UTC time>`. From that line on the check refuses this attempt. A second entry into Task 3 on the same answer, after a restart or after a stop at a checkpoint, is refused in the same way.
- One answer, one window. The window is the set of runs Task 3 names: the green run in the direct form; the same run in the route form, made only in the one case Task 3 states; and the control, made only when the direct form was green. When a run is void, not evidence or not as expected in any other way, Task 3 makes no further run, still hands the stack back, and still writes and commits the records, which then show the failure; the task is not done, its verify fails, and the attempt is over. The next try is a new attempt of Task 1 and a new confirmation, and it makes the window's runs again.
- A bound on asking again. A confirmation is voided when the operator confirmed and no wrapper run was started on it: the answer check refused it, or step 0 of Task 3 ended the attempt. Whoever finds that appends `ANSWER_VOIDED=` followed by the reason in one line (the check's last output line, or what stopped step 0) to the attempt file the pointer names, when there is one. Task 1 of the next attempt reads that line before it moves the pointer and writes the same reason as `PREVIOUS_ANSWER_VOIDED=` into the new attempt file. It is the only line taken over from an attempt that is ending, and it can only stop the plan: no check passes because of it. When a confirmation is voided and the pointer-named attempt file already holds `PREVIOUS_ANSWER_VOIDED=` with the same reason, two in a row were voided for one reason: start no new attempt and do not ask a third time. Stop, and return a blocking checkpoint that quotes the reason and this attempt's id, so that the cause (for example a commit made in this checkout by another executor or by the orchestrator) is removed first.
