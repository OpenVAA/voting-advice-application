## Phase 181 — Deployability and Migration Model

### 181-1 — How the baseline freeze is represented and enforced ⚠ DECIDE

- [ ] ★ RECOMMENDED — A committed hash manifest: each frozen migration with its sha256, the baseline's name and
      the commit it came from. The guard recomputes hashes and accepts added entries only. Survives squash and
      rebase. An edit to a file and its manifest line in one commit passes, but shows in review.
- [ ] Git comparison against a tag or base ref. Truly enforces append-only; needs history where `lint:check`
      runs (`main.yaml` has `fetch-depth: 0` only in `secret-scan`) and a ref that survives squashing.
- [ ] A copied baseline, byte-compared. Same bypass as the manifest, plus a second 377 KB file.

Goes with any option: `yarn schema:regenerate` is removed or made to refuse; frozen files leave prettier and
`assert:comment-hygiene`, so a later rule change cannot redden a file nobody may edit; the guard gains injectable
paths and a fixture so it can be seen failing without editing the real file.

### 181-2 — What `schema/` is after the freeze ⚠ DECIDE

the RPCs return"; `assert-grant-permission-enum.mjs` reads `schema/000-enums.sql`).

- [ ] ★ RECOMMENDED — `schema/` stays the hand-edited current view. Each change is a `schema/` edit plus a
      numbered migration in one commit. Byte parity is replaced by an equivalence check between two built
      databases. That check needs a running stack, so it sits outside the Node-only `lint:check` chain, and the
      method that covers grants and policies needs research.
- [ ] `schema/` is frozen with the baseline; changes exist only as migrations. Smallest guard change. The two
      guards above go stale on the first appended migration (inferred: the enum guard goes red on the first
      appended permission).
- [ ] `schema/` is deleted; the guards are re-pointed at the migrations or the database.
- [ ] `schema/` is regenerated from the applied database. Concern ordering and comments are lost.

Fields (★ unless edited): the SvelteKit route id (not the path, because Contestant paths hold the entity's UUID),

### Six readings I made of the notes

Each is written into the context files as a decision. Say so if one is wrong; the cost of a reversal is given.

1. **182-1, "include duration".** A pageview's duration is known only when the page is left, and the record has
   no identifier, so two sends could not be joined. Read as: the one beacon is sent when the page is left (on the
   next navigation, and on `pagehide` for the last page), carrying the route id, the allowed parameters, the app,
   the locale and the duration. The consented `page_leave` event of 182-4 is then not built, because the pageview
   holds what it would have held. A tab that is killed without `pagehide` loses its last pageview. Cheap to
   reverse before the vocabulary plan is executed.
2. **182-1, "all other route params".** Read as an allowlist of parameter names per route in the closed schema.
   Entity and nomination identifiers are never on it, and a parameter not on the list is dropped, so a route
   added later sends nothing until it is listed. Query strings stay dropped (RELAY-08).
3. **182-1b, the pageview with `trackEvents` off.** RELAY-10, RELAY-15 and criterion 3 of phase 182 said nothing
   is sent with `trackEvents` off. They are reworded: `trackEvents` gates every event except the pageview, and
   provider `none` is the only setting that stops the pageview. `Sec-GPC` still drops it (182-11 ★).
4. **182-12, terms acceptance as consent.** Read as: the voter app keeps its popup, in the voter layout as today.
   In the Contestant app there is no popup; accepting the terms grants consent unless the user opts out with the
   second checkbox, and the choice is written to the same origin-wide store the popup writes. The checkbox is on
   a page the v2.16 stream is changing, so the two streams meet there at merge. Its exact form (ticked means
   "allow", or ticked means "do not track") is left to planning.
5. **182-12, the Admin app.** It has no terms page (182-13), so nothing there can grant consent. Read as: Admin
   sends the pageview, and other events only if the same browser already holds a grant from another app. No
   prompt is added to Admin.
6. **182-12 gap, "fix it in the baseline".** The schema change belongs to phase 182 and must land before the
   freeze of phase 181. It is added to 181's list of changes that go in before the freeze. The freeze waits for
   v2.16's 177.1 in any case (181-3 ★).
