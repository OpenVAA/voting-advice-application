## B. Analytics relay

Today, per FEATURES and PITFALLS, `trackingService.svelte.ts` keeps a session id in `sessionStorage`
(`appContext-sessionId`), stamps it on every event including `answer` events carrying `{ questionId, value }`, gates
on consent, and passes the id to `surveyLink`. The legal reading that storage-free tracking needs no consent is rated
LOW to MEDIUM by the researchers and is a reading, not a conclusion (EDPB Guidelines 2/2023 v2.0, Traficom 2022).

### B1 — Consent mode ⚠ DECIDE

- [ ] ★ RECOMMENDED — Consent-free is the default, and a consent-gated mode stays as a deployment setting for
      deployers whose jurisdiction requires it. The consent components are kept but rendered only in that mode.
- [ ] Remove the consent interface outright. Less code; a deployer who needs a prompt must rebuild it.
- [ ] Consent-gated stays the default, consent-free is opt-in. Contradicts the direction you gave.

### B2 — Answer values in consent-free mode ⚠ DECIDE

Answers to statements are political-opinion data.

- [x] ★ RECOMMENDED — Answer events are sent, each with a fresh random id, so no two answers and no answer and
      pageview can be linked. Aggregate distributions per question remain available.
- [ ] Answer events are sent without their value (only that a question was answered).
- [ ] Answer events are sent with the visit id like any other event. A visit's full answer set is then one linked
      record at the provider.
- [ ] Answer events are not sent at all in consent-free mode.

NOTE: Add a todo for investigating a differential privacy version of this, or some timestamp + insert order masking to prevent matching with access logs.

### B3 — Visit identifier ⚠ DECIDE

- [ ] ★ RECOMMENDED — Two modes as a setting: `memory` (default; a UUIDv7 in a JS module variable, gone on reload,
      nothing written to the device) and `none` (random id per event). No hash of address and user agent is built.
- [ ] `none` only. Simplest claim to defend; no funnels.
- [ ] Add a daily server-side hash of address and user agent as a visitor id (ARCHITECTURE's proposal). FEATURES
      and PITFALLS both call this the highest-exposure option, and it is a fingerprint.

NOTE: Add a todo for adding a setting for both event white and blacklisting.

### B4 — The survey link's `{sessionId}` ⚠ DECIDE

- [ ] ★ RECOMMENDED — `{sessionId}` is filled from the in-memory visit id in `memory` mode and is empty in `none`
      mode; the docs say survey responses cannot be joined to analytics in `none` mode.
- [ ] Remove the `{sessionId}` template variable. Survey responses are never joinable.
- [ ] The survey link gets its own random id, unrelated to analytics.

### B5 — Contestant and Admin apps

- [ ] ★ RECOMMENDED — Excluded from tracking in this milestone; their users are signed in, which changes the
      privacy analysis.
- [x] Tracked the same way as the voter app.

NOTE: Add a paragraph in the ToU about tracking. Their most sensitive data (answers) will anyway be public.

### B6 — Event shape

STACK notes the current code folds a page's events into one compound `pageview` (ARCHITECTURE: because of Umami's
50-property limit); unfolding multiplies volume.

- [x] ★ RECOMMENDED — Discrete events through a closed server-side schema, with a PostHog billing limit and a
      bounded drop-when-full forwarder. NOTE: Let's make all events compatible with OTEL and the current logging format.
- [ ] Keep the compound `pageview`. Lower volume; funnels are harder to build at the provider.

### B7 — Who owns the "no consent needed" statement

- [x] ★ RECOMMENDED — The docs describe the mechanism (what is and is not stored or sent) and state that whether a
      prompt is needed is the deployer's determination. No sentence says "no consent is required".
- [ ] The docs state it as OpenVAA's position, after a named reviewer signs off. Name the reviewer in a NOTE.

NOTE: Make asking for consent the default. And still respect the trackEvents setting for tracking anything. Simple pageviews should be tracked, tho, in any case, from the server.

### B8 — Abuse limiting on the relay endpoint

- [ ] ★ RECOMMENDED — Mandatory: closed schema, body-size cap, same-origin check, bounded queue. A WAF rate rule is
      an opt-in Terraform variable, off by default.
- [ ] WAF rate rule on by default. Cost scales with traffic.

## C. Supabase

**C-note (re-verified by me, `471f01e8e`):** the frontend server does not need the service-role key. `.env.example`
says "Nothing under `apps/frontend/src` reads it; only local tooling and the test harness do", and the only
`SERVICE_ROLE` match under `apps/frontend/src` is `supabaseDataWriter.integration.test.ts`. The key stays off the
frontend task.

### C1 — Migration model after the first push ⚠ DECIDE

PITFALLS: the repo keeps one migration regenerated in place, enforced by
`scripts/assert-schema-migration-parity.mjs`; `supabase db push` skips a version it has already recorded, so later
edits would never reach the hosted database and nothing would go red. This ends the "nothing deployed, no
back-compat" ruling of 2026-10-04 for the schema.

- [ ] ★ RECOMMENDED — Baseline and append-only: land the pre-deployment schema changes (including the storage
      buckets) in the single migration, freeze it at a named cutover commit, and change the parity guard to
      "byte-equal to the baseline, then append-only numbered migrations". Coordinate the cutover with the v2.16
      session, which is still editing the schema.
- [ ] Disposable target: the hosted test project is reset from the single migration on every deploy. The
      single-file model survives, but nothing persistent can ever be deployed this way.
- [ ] Baseline now, cutover deferred: build and test the append-only mechanism against a throwaway project, but do
      not freeze the real baseline until v2.16 merges.

**NOTE for C1:** the third option may suit the parallel run best; I recommend the first only if you are content to
have v2.16's remaining schema work land as appended migrations.

### C2 — The hosted project ⚠ DECIDE

- [ ] ★ RECOMMENDED — You create one persistent project on the Pro plan (about 25 USD a month) in a dedicated
      organisation; Terraform imports it and owns its settings, with `prevent_destroy`. A second, throwaway project

- [ ] Free plan, with a scheduled smoke run to keep it awake. Reported to pause after about a week idle

- [ ] Terraform creates the project. A destroy then deletes the database, and a recreated project changes ref,

      that reads its outputs. CI teardown targets the AWS root only.
- [ ] One root per environment (ARCHITECTURE's layout). Simpler; a teardown reaches the database.

### C4 — Owner of hosted auth settings

- [ ] ★ RECOMMENDED — Terraform's `supabase_settings` is the only writer; `supabase config push` is never used

      importing from the throwaway project first.
- [ ] The CLI's `[remotes.<name>]` blocks and `config push`. One file for local and hosted; a third-party report
      says omitted keys reset to template defaults (unverified).

### C5 — API keys

Supabase's legacy `anon` / `service_role` keys are reported as deprecated by the end of 2026.

- [x] ★ RECOMMENDED — Measure what a new project issues; stay on legacy keys if they work and file a dated

- [ ] Adopt publishable keys now. Touches the frontend, the Edge Functions and the storage cleanup trigger, in

### C6 — Mail

PITFALLS: hosted Edge Functions block outbound ports 25 and 587 and both functions hard-code `secure: false`; SES

- [ ] ★ RECOMMENDED — SES, the sandbox accepted for staging with verified addresses, production access requested

- [ ] Another SMTP provider. Name it in a NOTE.

### C7 — Edge Function secrets in Terraform state

- [ ] ★ RECOMMENDED — Accepted in state (provider design), behind a state bucket with encryption, versioning and

- [ ] Kept out of Terraform and set by the CLI in the deploy script. A second owner for function configuration.

### D1 — Admin jobs with more than one task ⚠ DECIDE

`apps/frontend/src/lib/server/admin/jobs/jobStore.ts` keeps jobs in process memory, so job-progress polling breaks
when a second task serves the request.

- [ ] ★ RECOMMENDED — A documented limit: staging runs one task; the production-shaped variables allow more, and
      the docs say Admin job progress is unreliable above one task. Moving the store is recorded as a future
      requirement.
- [ ] Move the job store to the database in this milestone. Correct fix; it is Admin App work outside deployment.
- [ ] Load-balancer stickiness. Sets a cookie on every visitor, which undercuts the storage-free claim.

### D2 — Network

- [ ] ★ RECOMMENDED — Public subnets, no NAT gateway; tasks have public addresses and a security group that admits
      only the load balancer.
- [ ] Private subnets with a NAT gateway. A fixed egress address (useful if per-IP auth limits bite); adds a
      standing monthly cost.

### Four readings I made, each cheap to reverse

1. **B7 note, "pageviews in any case".** Read as: a server-recorded pageview with no identifier is sent whether or
   not the visitor has consented, and every other event waits for consent in the default mode. `trackEvents` off
   is read as turning off everything, the server pageview included, because the note says the setting is respected
   "for tracking anything". If you meant pageviews even with `trackEvents` off, RELAY-15 changes by one clause.
2. **B2 after B1 was overruled.** The fresh id per answer event is ruled for consent-free mode. For a visitor who
   has consented in the default mode, answer events carry the visit id, as they do today. Raised again in the
   phase 182 discussion.
3. **F1, "a code pipeline for deploying by push to named branch".** Read as a GitHub Actions deploy triggered by
   a push to a per-environment branch (`deploy/staging`), since GitHub Actions is already settled. Not read as
   AWS CodePipeline.
4. **F1, "let's move" the DNS.** Read as: a Route 53 hosted zone serves `staging.openvaa.org`. Whether that is a
   delegated subzone or the whole `openvaa.org` zone is settled in phase 183; a subzone is the smaller change,
   because the parent zone carries records this milestone does not own.
