# Continue Here — Spike 012 (getRoute rune-native)

## What this spike is

Convert `apps/frontend/src/lib/contexts/app/getRoute.svelte.ts` from its
current `writable<RouteBuilder>` + `afterNavigate(() => store.set(...))`
shape to a pure rune-native handle exposing `get current()`. The file
header explicitly documents a Svelte 5 trap that broke the previous
shape (`derived(toStore(() => page), …)`):

> `$app/state.page` is a long-lived `$state` proxy — its OBJECT
> REFERENCE never changes across navigations, only its internal state
> mutates. Svelte 5's `toStore` wraps the getter in an internal
> `render_effect` whose `set(value)` short-circuits when the getter
> returns the same reference, so the wrapping `derived` never re-fires
> and consumers... keep holding a stale closure.

The previous Wave-1 → Wave-3 inventory (Spike 010) flagged this file
as **Wave 3 — careful** specifically because of this trap.

## Briefing as it stands (for reference if the user wants me to restate)

### Research — 4 approaches considered

| Approach | Shape | Verdict |
|---|---|---|
| A. `$derived` over `page` object reference | `const b = $derived(() => makeBuilder(page))` | **REJECTED** — same trap as production's rejected shape; stable object reference won't re-fire |
| B. Getter reads `page.X` per call | `get current() { return (opts) => buildRoute(opts, { params: page.params, ... }) }` | Control variant — works but allocates a fresh closure on every consumer read (134 sites compound) |
| **C. `$derived.by` over per-field `page` reads** | `const b = $derived.by(() => { const { params, route, url } = page; return (opts) => buildRoute(opts, { params, route, url }); })` | **PRIMARY** — fine-grained per-field tracking bypasses the page-object-reference trap; memoized — one closure per nav |
| D. C + `afterNavigate` belt-and-suspenders | C above + defensive republish | Open question — include or skip? |

### Proposed build shape

`apps/frontend/src/routes/runes-test/getroute-rune/`:
- `getRouteRuneStore.svelte.ts` — exports three (or four) variants
- `+page.svelte` — renders all variants with the same input;
  internal navigation links drive `page.route` / `page.url` changes
- `nested/+page.svelte` — sub-route to navigate to
- Optional `+layout.svelte` to initialize the rune context

Visible state to show side-by-side after each navigation:
- Approach C output URL
- Approach B output URL (control)
- Snapshot output URL (deliberate negative control — should go stale)
- Live `page.url.pathname` and `page.route.id` for ground truth

### Verification gate

VALIDATED iff:
- Approach C URL output matches Approach B (proves C tracks correctly)
- AND Approach C URL output reflects the CURRENT page after navigation
- AND Snapshot URL output stays stale (locked at init values)
- AND zero `effect_update_depth_exceeded` warnings in console
- AND no hydration mismatches

## Critical Anti-Patterns (do NOT repeat these)

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| `toStore` short-circuit on stable object reference | `derived(toStore(() => page), …)` doesn't re-fire because page's object reference is stable across nav | advisory | Use Approach C: pure `$derived.by` reads `page.params`/`page.route`/`page.url` as separate fields. Never read `page` as a value. |
| Premature VALIDATED verdict | spike workflow explicit: "Never declare VALIDATED after a single happy-path test" | advisory | Test multi-step navigation including back/forward; test locale-param transitions if applicable; check console for effect-loop warnings |
