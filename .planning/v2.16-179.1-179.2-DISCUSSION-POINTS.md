## Phase 179.1 — Review Fixes: Access, Database Rules & Contestant App Behaviour

### A. Access and security

#### 179.1-A1 — Re-inviting a claimed address: the index change

A1's ★ is decided: a partial unique index on open rows (`claimed_at IS NULL`). The index's columns hold no role
(`project_id, email, scope, target_type, target_id`), so with the claimed row left out, promoting a claimed
project editor to project admin works too. `invitations_code_hash_key` is a different matter: a code must stay
unique whether or not it was claimed, or a used code could be issued again.

- [ ] ★ RECOMMENDED: make only `invitations_email_target_key` partial; keep `invitations_code_hash_key` over every row; pgTAP covers re-invite after claim, after the claimant is deleted, and promotion editor → admin
- [ ] Make both partial. Costs: a used code could be reissued, and `invitation_code_status` would then read `used` and `valid` for one code.

#### 179.1-A3a — Which mailed links pass through the confirm page

A3's ★ is decided (add the confirm page). All three types the callback verifies (F12) can be consumed early by a
mail scanner.

- [ ] ★ RECOMMENDED: all three (`magiclink`, `recovery`, `email_change`), through one confirm page
- [ ] `magiclink` and `recovery` only; `email_change` keeps the one-click link. Costs: a scanner can still spend the address-confirmation link, which an identity-provider user has no other way to resend except from settings.

#### 179.1-A3b — ⚠ DECIDE — A link opened in a browser already signed in to another account

The token does not say which account it belongs to until it is verified, so the page cannot name the
incoming account.

- [ ] ★ RECOMMENDED: the confirm page says the browser is signed in to another account and that continuing signs it out; Continue signs out and then verifies, Cancel returns to that account's app
- [ ] Refuse: ask the user to sign out first, then open the link again. Costs: one more round trip, and the single-use link has to survive it (it does: nothing has verified it yet).
- [ ] No rule: Continue replaces the session silently, as today's GET does. Costs: the login-CSRF half of A3 stays open for a browser that is already signed in.

#### 179.1-A3c — The confirm page's mechanics and route

179.2 needs the same page for the Admin App's links, so its route should belong to neither app.

- [ ] ★ RECOMMENDED: an app-neutral page (e.g. `/auth/confirm`) whose `GET` renders a form holding `token_hash`, `type` and `next`, and whose form action `POST`s to verify (SvelteKit's form-action origin check is the CSRF guard); the mails link to the page; `GET /api/auth/callback` with a token stops verifying and redirects to the page
- [ ] A Contestant App page (`/contestant/confirm`), with 179.2 adding an Admin App copy. Costs: two pages for one rule.

#### 179.1-A3d — The page's texts in 7 languages

- [ ] ★ RECOMMENDED: write all 7 now, flagged for the native-speaker check that E1's UAT already includes
- [ ] English only, with the other locales falling back. Costs: the raw-key gate (CSCAN) would fail, or need an exemption.

#### 179.1-A5 — The shared per-IP sign-in budget, with nothing deployed (F5)

#### 179.1-A7a — ⚠ DECIDE — Revocation at once: where the table is read (F4)

You overruled A7 to "make the write policies read the `grants` table". Every policy, read or write, goes
through `user_can`.

- [ ] ★ RECOMMENDED: change `user_can` and `user_has_account_grant` to read `public.grants` for `auth.uid()` instead of the claim, so reads and writes share one source and a revoked grant ends both at once; the token hook keeps writing the claim, which only the frontend's app-entry gates read
- [ ] A second predicate for writes only (the INSERT, UPDATE and DELETE policies and the definer RPCs that authorise writes); reads stay on the claim. Costs: two predicates that can disagree for up to an hour — a revoked user still reads what they can no longer write — and about 70 policy sites to sort into two kinds.

#### 179.1-A7b — How the cost of the table read is proven

`user_can` runs per row in list reads. `public.grants` has an index on `(scope, target_type, target_id)`; an index
that leads with `user_id` is *inferred* to be missing and is for research to confirm.

- [ ] ★ RECOMMENDED: add an index leading with `user_id` if none exists; measure `EXPLAIN ANALYZE` on an editor's and an admin's entity, nomination and storage list reads before and after; accept the change only if it stays within 2× on a 1 000-row read and the E2E wall-clock does not grow by more than 10 %; otherwise read the caller's grants once per statement (an `InitPlan`, as the `(SELECT auth.jwt())` pattern does today)
- [ ] No measurement; the E2E run is the check. Costs: a slow path shows only on large projects, which the suite does not seed.

#### 179.1-A7c — What happens to the pgTAP that pins the claim behaviour

- [ ] ★ RECOMMENDED: rewrite those rows to assert the new rule: a grant deleted mid-session denies the next read and write with the same token
- [ ] Delete them and add the new rows separately. Costs: the census loses its trace of what changed.
