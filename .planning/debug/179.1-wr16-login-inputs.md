## Per-gap diagnoses

### G-179.1-WR16-7C - the Admin App's email is a raw input (CONFIRMED)

- Cause: routes/admin/login/+page.svelte (the `<div class="flex w-full flex-col items-center">` block) renders `<label for="email" class="hidden">` and a raw `<input type="email" name="email" id="email" bind:value={email} class="input mb-md w-full max-w-md" placeholder=... autocomplete="email" required />`. 387c09148 (179.1-37) moved only the password onto Input; no plan moved the email.
- Measured: the raw field computes 14px beside the Input password's 12px; it has a placeholder in place of a visible label, and native `required`.
- Fix direction (non-binding): render EmailField (it uses only ComponentContext, which the admin page already provides to Input) or Input type="email" with validate={false} plus an oninput that writes the live value. Keep id="email" (fixture `#email`), name="email" (the action) and per-keystroke `email` (canSubmit; the fixture's fillAwaitingScript). A bare `<Input type="email" bind:value>` commits only on `change` and would keep the submit disabled.

### G-179.1-WR16-8A - typed text is small (CONFIRMED in Chromium and WebKit; iOS UNCONFIRMED)

- Causes (both contribute): (a) `inputClass` in components/input/shared.ts includes `input-sm` (daisyUI 5: `--font-size-min: .75rem`), so all single-line Input kinds compute 12px; (b) the app.css reset `.btn, .input, .textarea, .select { @apply text-md }` and the `@supports (-webkit-touch-callout: none)` 16px rule are inside `@layer components` and lose to daisyUI 5's `.input { font-size: max(var(--font-size,0rem), var(--font-size-min,.875rem)) }` in `@layer utilities > daisyui.l1.l2.l3`. The reset has been dead since the Tailwind 4 / daisyUI 5 upgrade (3d75e3e27); it was written for daisyUI 4 / Tailwind 3 (fe69ae611).
- Measured: Input email/password 12px, raw .input 14px, labels/body 15px, --text-md 15px; bare .btn/.select/.textarea also 14px.
- Side effect, UNCONFIRMED: on iOS the controls are presumably also 12px, under the 16px threshold at which iOS Safari zooms on focus, which is what the dead rule was meant to stop.
- Fix direction (non-binding): either drop `input-sm` for these kinds (gives 14px, still not default) or set the control's font size where it wins: move the reset (and the iOS rule) out of `@layer components` into an un-sublayered `@layer utilities` rule as app.css already does for `.label`, or give the control a text-md class. Reviving the reset changes every .btn/.select/.textarea/.input in the app (14px to 15px), so the scope is the operator's call.

### G-179.1-WR16-8B - the password field autocapitalises on iOS (mechanism CONFIRMED up to the platform; iOS UNCONFIRMED)

- Cause: Input.svelte branch 6.5 renders `type={passwordRevealed ? 'text' : 'password'}` and gives the control no `autocapitalize`, `autocorrect` or `spellcheck`. Revealed, it is an ordinary text field, which iOS autocapitalises (sentences) by default; masked, iOS's keyboard is documented to leave type=password alone. The deleted PasswordField had the same gap (not a regression of 179.1-37).
- Measured: no such attributes in either state (Chromium, WebKit); type="text" when revealed. EmailField sets autocapitalize="none" spellcheck="false" for its own control.
- UNCONFIRMED: the iOS behaviour itself and which state the operator typed in. If the masked field also capitalised, the cause would lie elsewhere.
- Fix direction (non-binding): put `autocapitalize="none"` (or "off"), `autocorrect="off"` and `spellcheck="false"` on the password kind's control itself in Input.svelte, so PasswordSignIn, PasswordSetter's two fields and the admin login all get it; confirm on an iOS device in both states.

### G-179.1-WR16-8C - the toggle does not focus the input (CONFIRMED in Chromium and desktop WebKit)

- Cause: the toggle is `<Button type="button" ... onclick={() => (passwordRevealed = !passwordRevealed)} />`; nothing returns focus to `control`, and Button has no focus handling of its own. The old PasswordField did the same.
- Measured: after a press, activeElement is the toggle button in both engines. A bare control.focus() afterwards leaves caret 6/6 (nothing selected) in both; iOS's selection on programmatic focus is UNCONFIRMED.
- Fix direction (non-binding): after the flip, focus the control and set the caret explicitly with setSelectionRange(len, len) so no engine selects the contents; or keep focus on the input throughout by preventing the toggle's pointerdown default (which also keeps the iOS keyboard up). Weigh keyboard and screen-reader users, who would no longer stay on the toggle. Update the unit test's "changes the control's type alone" wording and add an activeElement and selection assertion.
