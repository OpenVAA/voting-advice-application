## Resolution

root_cause: |
  G-1 (CONFIRMED at library level): signOutToLogin.ts:26-29 answers every failure with error(503), on the stated ground that the session is alive. auth-js 2.117.2 GoTrueClient._signOut (dist/main/GoTrueClient.js:3439-3450) removes the session before it returns { error } whenever the logout call itself fails (5xx, network), and @supabase/ssr then writes the cookie removal through server.ts's setAll into event.cookies, which SvelteKit adds to the 503 response. Only a failure to load the session (a refresh failing retryably) leaves it. So the commonest failure form ends on a 503 with no session left.
  G-3 (CONFIRMED, Admin App; Contestant App measured, not affected): routes/admin/(protected)/+layout.ts runs in the browser on entering the protected group, reads `session` from parent(), i.e. admin/+layout.server.ts data that no request refreshed and that still reads it alive, and calls getUserData(); SupabaseDataWriter._getBasicUserData (supabaseDataWriter.ts:574, :580) throws a plain Error('No active session'), which getUserData.ts:54-57 folds into the same undefined as a failed read; the load's line 38 answers 503. The Contestant App's user-data reads are server loads behind hooks.server.ts's request gate, which redirects a request with no session before a load runs, so no Contestant navigation reaches the 503. In both apps a navigation that sends no request and reruns no load shows the stale page, neither the login form nor the 503.
  G-4 (CONFIRMED by differential): routes/admin/login/+page.svelte:88 `action="login"` is relative; at /admin, where the form stands after Back (a popped navigation keeps its address through redirects), it resolves to /login, which answers 404 HTML; use:enhance's JSON parse fails and the SyntaxError is rendered as the root error page's title.
  G-10 (CONFIRMED): Modal.svelte:99 (X) and ModalContainer.svelte:92-109 (Escape keydown, native close) close unconditionally, with no veto for a consumer; TimedModal.svelte:127-135 closes itself right after an unawaited onTimeout, so the count's end closes the modal as the sign-out starts; contestantContext #runLogout calls discardGuardedEdits()/leaveUnasked() only after the sign-out answers, so PreventNavigation's beforeNavigate (PreventNavigation.svelte:36-44) still asks window.confirm for a link during it.
  G-15 (CONFIRMED in both apps): lib/dynamic-components/logoutButton/LogoutButton.svelte:33 keeps `leaving` as a plain let and :62 passes no `loading`; lib/contestant/components/logoutButton/LogoutButton.svelte:119-125 passes no `loading` either, though its `leaving` is $state.
