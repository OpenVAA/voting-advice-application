## Resolution

### 11A — second tab keeps and re-stores the draft

root_cause: "PersistedStateImpl (persistedState.svelte.ts) holds its value in a private $state read from storage only in its constructor, and its set/update write #value back unconditionally; the second tab's contestantUserDataState keeps its #draft handle and #savedData, and nothing in the frontend observes another tab's sign-out: no `storage` listener on the handle and no onAuthStateChange subscriber on the browser client, although the browser delivers the storage event and auth-js broadcasts SIGNED_OUT to the tab. So the tab goes on showing the data and its next setAnswer re-creates the removed key with the removed answers in it."
confirmed: MEASURED (wr16-11a-run1.txt) for the in-memory keep, the re-store and the arrival of both signals. The page.data half (user, entities, contestantUserData standing in tab B until it navigates) is READ, not driven.
and_gate: two contributing conditions: (a) the handle does not observe storage changes -> re-store; (b) no cross-tab sign-out subscriber -> the data stays on screen. (a) alone gives the re-store; (b) alone gives the stale screen.

### 11B — the Admin App's Log out leaves Contestant App drafts

root_cause: "Draft removal is not part of the sign-out: it is ContestantContextProvider's private #reset (userData.reset() -> removePersistedByPrefix(stem-)), run only from that context's #runLogout. The Admin App builds no contestant context; its Log out (AdminLogoutButton -> adminContext.logout -> authContext.logout -> dataWriter.logout) and handleError (createDataWriter(...).logout()) end the same shared Supabase session (one sb-<ref>-auth-token cookie for both apps) and never touch localStorage. Of the six sign-out sites, only #runLogout removes drafts; two (SSR handleError, signOutToLogin) run on the server, where localStorage cannot be reached at all."
confirmed: MEASURED for the Admin Log out (wr16-11b-run1.txt) and the SSR arm of handleError (wr16-11b-run2.txt). The client-navigation arm of handleError is READ.

### 11C — a timer that does not run signs nobody out

root_cause: "The count's sign-out exists only as one relative setTimeout pending in the live document (TimedModal.svelte 127-135, onTimeout={leave} in the contestant LogoutButton). No deadline is recorded anywhere outside the document (no timestamp, no storage, no cookie), nothing re-checks on visibilitychange/pageshow/resume/freeze, and no unload handler signs out. Nothing server-side bounds the session either: [auth.sessions] timebox and inactivity_timeout are commented out in config.toml and absent from the running auth service, and @supabase/ssr writes the cookie with maxAge 400 days. So when the document's tasks do not run (closed, discarded, reloaded, and by the lifecycle model frozen or suspended) the session and the draft stay."
confirmed: MEASURED for the closed tab (wr16-11c-run2.txt: cookie 400 d, user validated in the next tab) and for the absent server bound (docker inspect). READ for the timer having no deadline or resume handling. UNCONFIRMED for frozen/suspended tab, locked phone, closed lid: the CDP freeze did not take hold in headless Chromium (no freeze event; timer fired on time), so what Chromium/Safari do with the pending timer on resume was not observed.
and_gate: yes: (a) the only enforcement is in-document and relative, and (b) there is no out-of-document bound (persisted deadline or server session bound). Either one alone would sign the walked-away user out, at a different resolution.
hosted: per the Supabase docs, the time-box and inactivity timeout are Pro-plan-and-up only, enforced at the next refresh, effective bound = setting + JWT expiry (3600 s here). Not a 30-second bound.
