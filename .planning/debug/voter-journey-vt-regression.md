## Resolution

root_cause: The voter-journey helper `expectQuestionAndAdvance` (tests/tests/specs/voter/voter-journey.spec.ts) read `answerOptions.count()` synchronously at helper entry, BEFORE the Q→Q navigation triggered by the previous step's click (which fires `goto` after a `DELAY.md`=350ms debounce) had resolved. Because the Phase 95 rune migration made `questions/[questionId]/+page.svelte` derive its `question` via `$derived` and SvelteKit reuses the component on param-only navs (no remount), the OUTGOING question's `[data-testid=question-choice]` radios stayed mounted at entry. So `count()` captured the previous question's option count — entering base-4 (Categorical, 3 options) it read base-3's count (Likert7 = 7) → `optionIndex(7)=6` → `.nth(6)` never resolved on the 3-option question → element-not-found/timeout. The View Transition (Phase 99) was NOT the cause: applying `reducedMotion:'reduce'` provably suppressed the VT (shouldAnimate honors it) yet the failure was identical, and the failure-time DOM showed only the 3 settled options with no coexisting outgoing DOM.

fix: Made the helper deterministically SETTLE on the new question before counting (candidate fix #2). It now captures the entry URL and waits for navigation to land on a NEW `/questions/<id>` route (questionId path segment changed) before reading options, then polls until the option count is stable across two consecutive reads before computing the index. No fixed waits, no reliance on View Transitions. File: tests/tests/specs/voter/voter-journey.spec.ts (helper `expectQuestionAndAdvance`, +45/-4). The exploratory `reducedMotion:'reduce'` change to tests/playwright.config.ts was reverted (disproven as the fix).

verification: `playwright test --project=voter-journey` (data-setup-base → voter-journey → data-teardown-base) green twice consecutively (1.2m each, under the 120s JOURNEY_TEST_MAX). ESLint clean on the edited spec + config. Helper is spec-local (not imported elsewhere) so no other spec regresses; setup/teardown projects passed.

## Eliminated

- timestamp: 2026-06-04T16:05:00Z — Phase 95 rune migration of answer stores ruled out as the PRIMARY trigger. The failure is a DOM timing race, not a stale `$state`/`$derived` answer read: the page snapshot at failure shows the CORRECT new question heading ("Base opinion 4 — Categorical", 3 options), and the spec only mis-resolves `.nth(6)` because `answerOptions.count()` read the OUTGOING question's options. The answer-store state is correct. Rune migration IS a contributing precondition (param-only nav reuses `[questionId]/+page.svelte`, so options swap in-place after a render tick rather than via full remount), but the defect is in the test helper.
- timestamp: 2026-06-04T16:18:00Z — **PRIMARY HYPOTHESIS (VT DOM-coexistence) DISPROVEN.** Applied candidate fix #1 (Playwright `reducedMotion: 'reduce'` in tests/playwright.config.ts use-block) and re-ran `--project=voter-journey`. `shouldAnimate()` line 40 provably suppresses the VT under reduced-motion, yet the spec failed IDENTICALLY: same `.nth(6)` / `not.toBeChecked` / element-not-found, same step (spec:548 `for` loop), and FASTER (11.9s). Therefore the stale `count()=7` is NOT caused by old+new option DOM coexisting during a VT; the VT is irrelevant to this failure. Fix #1 reverted.
