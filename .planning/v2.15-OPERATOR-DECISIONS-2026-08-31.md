## D8 — The degrade-to-empty posture

**RULED: FAIL LOUDLY, in its own phase, before 158. → new Phase 157.1.**

A parse failure must become distinguishable from absence at the adapter boundary. The caller
decides what to do about a malformed column; the adapter does not decide for it by returning an
empty value that is indistinguishable from "there was nothing there".

**What this retires.** The class, not its instances: a `z.strictObject` schema describes a JSONB
column more narrowly than the database actually permits, the consuming `safeParse` degrades a
failed parse to an empty value, and so one unacceptable field silently discards every other value
in the column. Widening the schemas (fixes A-CR-01 / A-CR-02, landed) removed the **known
triggers**. It did not retire the class: an unknown key inside an answer object still wipes the
blob, and the next schema drift re-opens it.

**Blast radius:** five schemas and their call sites — `_getAppSettings`, `parseAnswersColumn`,
`sendEmail`, and the two write-path instances below.

**The two instances that make this severe, both on the write path:**

- `_setAnswers` returns `{}` after a **successful** RPC write. `{}` passes the
  `if (!updatedAnswers) throw` guard, `resetAnswers()` clears the edit buffer, and the candidate's
  just-entered answers vanish while the UI reports `{ type: 'success' }`.
- One unrecognised key in `app_settings.settings` discards every dynamic setting, including
  `access.underMaintenance` and `access.answersLocked`.

**A test currently locks the wrong behaviour in.** `supabaseDataProvider.test.ts:248-270` puts a
valid `access: { candidateApp: true }` in the fixture and asserts `expect(result).toEqual({})`.
That assertion is a specification of the defect and must be inverted by this phase, not deleted.

**Why its own phase and not a fix pass on 157:** the change is a posture change across five
schemas and every consumer of their results, and it needs its own negative controls. Closing 157
with the class open would carry a false premise into 158.

**Ordering constraint:** 157.1 lands before 158. It also lands before 157.2 (D11), because the
per-request adapter work touches the same call sites and should arrive after the parse contract
is settled.

## D9 — The production logger

**RULED: ENABLE warn/error in production NOW. Land it inside Phase 157.1.**

`hooks.server.ts:15` / `hooks.client.ts:7` set the logger level to `'silent'` unless
`DEV || PUBLIC_DEBUG`, and `logger.ts` early-returns on silent. Every "degrades with one warning"
comment in the adapter layer is therefore **false in production** — zero signal, zero sinks. This
is what turns each silent degradation from untidy into severe, and it is the highest-leverage
single change on the list.

**Scope of the ruling:** stop silencing `warn` and `error` in production. That is the whole
change. Wiring a durable structured sink (Sentry or equivalent) is explicitly **not** in scope
here — it is a larger piece of work and is queued to the backlog rather than smuggled in.

`log.*` is already total as of fix A-CR-03 (it can no longer throw out of a catch block), so
enabling output cannot itself introduce a throw. What it emits was deliberately left alone by
that fix and is settled here.

**Placement:** inside 157.1, as its first plan. D8's fail-loudly posture is only observable in
production if this lands with it; shipping the posture change on a silent logger would produce a
phase whose central claim is untestable in the field.

## D10 — The admin-app outage

**RULED: FOLD INTO PHASE 158. Not a new phase, and not counted against Phase 157.**

Phase 158 is *Routing & Auth Surface Harmonisation* — one login path, one route locus, one cookie
locus. The admin outage is the same surface, so it is scope, not a neighbour.

**The defect.** `_getBasicUserData` authorizes off `supabase.auth.getSession()`, while
`supabaseAdapter.ts:41-44` builds a **plain `createClient`** on the server branch whose
`getSession()` reads its own storage and never the forwarded cookies. Every server-side
`getUserData` therefore resolves `undefined`:

- all six `/api/admin/jobs/*` routes return **403 to genuine admins**;
- `admin/(protected)/+layout.ts` is a **universal** load with no `ssr = false` anywhere under
  `routes/admin/`, so an authenticated admin is bounced to login on every direct entry or refresh,
  and SvelteKit does not re-run the load client-side to recover.

It fails **closed** — an outage, not an authorization hole.

**Attribution, corrected and final.** Review lot C blamed 157-11's `unknown` C4 coverage item.
That is wrong and is already corrected in `157-REVIEW.md`. The pairing dates to `c3e948a84`; at
the 157 base, `getUserData` already passed `{ authToken: '' }` under a comment reading *"authToken
is ignored by Supabase adapter — session is cookie-based"*, so 157-11 removed an argument already
documented as inert and changed no authorization semantics. **This does not count against Phase
157.**

**Also folded into 158, same area, all open:**

- the admin **form actions** carry only a session check and no role check;
- `hooks.server.ts` gates only `/candidate`, never `/admin`;
- `/api/auth/login` is a dead, unauthenticated credential endpoint with zero callers whose
  403-vs-400 split confirms valid passwords. **Ruled: delete it.** 158 criterion 1 already says an
  unused generic `/api` login route is deleted rather than kept; this is that route, and the
  oracle is the reason the disposition is not optional.

**Why no gate caught it:** zero E2E specs touch the admin app. 158 must close that too — the
restoration is not provable without at least one spec that enters an admin route as an
authenticated admin and survives a refresh.

**Dependency:** 158's admin restoration comes **after** 157.2 (D11). Per-request adapter
instancing that carries the request's own cookie-bearing client is the same mechanism that makes
the admin server branch see the forwarded session, so 157.2 supplies the fix and 158 consumes it
and proves it.

## D11 — Adapter singleton concurrency

**RULED: ITS OWN PHASE. → new Phase 157.2, after 157.1, before 158.**

Server-side adapter selectors are module singletons re-`init()`ed per request with an `await`
before use. Three instances:

- `candidate/(protected)/+layout.server.ts:30→33→44` — concurrent candidates can be served each
  other's data;
- `condenseArguments.ts:44` — rebinds the shared `#supabase` mid-job, so a concurrent admin
  request can make the first job's writes execute under the second admin's JWT;
- a third instance added by Phase 157.

**Why its own phase rather than a fold-in or two inline patches.** Per-request adapter instancing
is an architectural change touching every server-side selector, and the deliverable that matters
is not the patch but the proof: a concurrency test that **fails on the singleton** before it
passes on the fix. Two inline patches would close the instances and leave the class open — the
same mistake the `157-18` gate made with D8's schema class, and the one lesson this phase most
clearly earned. Folding it into 157.1 would bundle two architectural changes behind one gate.

**Pre-existing:** two of the three instances predate v2.15. Phase 157 added the third. This is not
charged to Phase 157 either.

**Ordering:** 157.1 → 157.2 → 158. 157.2 is placed before 158 because D10's admin restoration
depends on it (above).

## Carried forward from the 157 handoff

- **`svelte-check` is load-bearing; `build` + `test:unit` is NOT a sufficient backstop.** Three
  times in Phase 157 a green build and a green unit suite sat on top of a real defect that only
  the frontend typecheck caught. Put it in every gate.
- **The E2E database prerequisite is `yarn db:reset`, NOT `yarn db:reset-with-data`.** The latter
  seeds the `seed_`-prefixed `default` template into a suite asserting against `e2e/base`, and
  `setupFromTemplate` whitelists `seed_` in its freshness probe — so the wrong one fails
  *quietly*. CI's own e2e job seeds nothing.
- **Trust your own measurement over a review's.** Two of the three review lots needed a
  correction: lot C's attribution (D10 above), and lot A's own note that the cast guard's zero is
  true *by spelling*, not by class.
