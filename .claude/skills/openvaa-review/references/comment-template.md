# PR comment template

`.claude/skills/openvaa-review/scripts/compose_comment.py` renders this layout. Change the script, not this file, when the layout changes. This file documents what the reader sees and why.

The first line is the marker that the re-run and the learning loop search for. Keep it exact, including the trailing space after `v1`.

## The option list is a contract

`/openvaa-review fix` reads these ticks back with `.claude/skills/openvaa-review/scripts/parse_decisions.py`, so the shape matters as much as the prose:

- The heading line carries the id, the block (`decision`, `critical` or `fix`) and the criterion. The parser anchors on it, and options belong to the heading above them, up to the closing `---`.
- `Discuss` and `Don't fix` are exact labels, always last, always in that order. Every other option is a fix the agent can apply as written, so an option has to name the change, not a direction.
- Ticking nothing means the recommended option. That makes the common case — the reviewer agrees — zero work, and it is why the recommended option must be the one you would apply unattended. The exception is a `decision` finding: ticking nothing there leaves it undecided, and fix mode asks.
- Ticking two options is a conflict the fix mode refuses rather than resolves.
- One route per checkbox. Two acceptable fixes are two options — the recommended one first, carrying *(Recommended)*, the other as an alternative — never one option reading "(a) … (b) …". A bundled option cannot be chosen between, and it hands the fix agent both routes at once.
- A multi-line option indents its continuation lines by two spaces so they nest under its checkbox; the parser reads every line up to the next option as part of it, so the choice reaches the fix agent whole.
- Reviewers may write anywhere around the options: edit an option, add one, type after a label ("Don't fix: intentional") or add notes after the last option. The parser keeps all of it. The data block's `opts` holds a fingerprint of each generated fix option, which is how it tells an edited or added option from a generated one; `option_fingerprint` in `compose_comment.py` and `parse_decisions.py` must stay identical.

The reviewer-feedback block at the end is separate: it says a finding was **wrong**, which tunes future reviews, whereas `Don't fix` declines a fix for a finding that is real. A finding can be both.

## Blocks and continuations

The three blocks are separate comments: each non-empty block after the first starts a comment of its own, so a reviewer sees the decisions on their own first, the critical findings next, and the rest last. Empty blocks are left out, so a review whose only findings are fixed by default is one comment. The first comment carries the header, the first non-empty block, the feedback checklist and, when there is room, the data block. The lens sections follow the last block.

A part that would exceed about 20,000 characters (a third of GitHub's 65,536-character limit, because checkboxes toggle unreliably in long comments) overflows into a further comment. The data block counts towards the first comment's size; when it does not fit, it gets a last comment of its own with no checkboxes. Every continuation opens:

```markdown
<!-- openvaa-review:v1-cont pr={N} head={HEAD_SHA} part={i}/{total} -->
## Review brief, part {i} of {total}

### 2. Critical
…
```

A committed review file (`--local`, or a plan review without a PR) is never split: the blocks follow one another.

## Plan reviews

`compose_comment.py --plan` renders the same findings contract around a different header:

```markdown
<!-- openvaa-plan-review:v1 pr={N or none} branch={BRANCH} head={HEAD_SHA} -->
## Plan review brief

> Thematic review of the plans listed below, generated by `/openvaa-review --plan` before they are executed. …

**Branch:** `{BRANCH}` @ `{HEAD_SHA:0:10}` · **Plans reviewed:** {n} · **Context read:** {m} files

### Plans under review

- `{plan path}`: {title}

### What the plans set out to do
…
### Reading guide
…
### Findings
…
```

- The marker differs on purpose. A branch can carry a plan review and, later, a code review on the same PR, and a shared marker would have each re-run overwrite the other.
- Every fix option leads with the end result and only then gives the document change: an `Outcome:` line saying what gets built if the option is chosen, then a `Plan edit:` continuation line naming the plan, task and replacement. The reviewer decides on the outcome, so the options must be distinguishable by those lines alone.
- Finding headings, the option list and the data block are identical, so `parse_decisions.py --plan` reads either home of the review. The data block adds `"mode":"plan"`, `"branch"` and `"plans"`, and `"pr"` is `null` when there is no PR.
- With no PR the review is one file, `OPENVAA-PLAN-REVIEW.md`, committed to the branch. A file has no size limit, so it is never split into continuations.
- On an unpushed branch evidence is `path#Lx-Ly` text rather than a link.
- There is no reviewer-feedback block: the learning loop harvests code reviews only, and a box that tunes nothing should not be offered.

## Local reviews

`--local`, and a plan review of a branch with no PR, write the review to a file committed on the branch instead of a comment: `OPENVAA-PLAN-REVIEW.md` beside the plans, or `.planning/reviews/<branch-slug>-OPENVAA-REVIEW.md` for a code review. The layout is the same with three differences: it is never split into continuations, it has no reviewer-feedback block (the learning loop reads PR comments only), and the marker reads `pr=none` when the branch has no PR.

## Notes
- `refuted` is kept in the data block, not the visible body. The learning loop uses it to see which criteria generate noise.
- The data block must be a single valid JSON object. `harvest.py` parses it with `json.loads`.
