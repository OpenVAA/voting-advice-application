# `tests/` — End-to-end test suite

Playwright-driven cross-monorepo E2E tests covering the voter app, contestant app, and the configuration-permutation matrix. Configuration: [`tests/playwright.config.ts`](./playwright.config.ts). Seed data is produced by [`@openvaa/dev-seed`](../packages/dev-seed/) via the project's `data-setup-base` + `data-setup-perm-*` setup projects.

## Run

```bash
# Prereqs: yarn install. The wrapper starts Supabase and the dev server itself.
tests/scripts/e2e-run.sh --run-dir tests/e2e-runs/<name> --no-db-reset
tests/scripts/e2e-run.sh --run-dir tests/e2e-runs/<name> --no-db-reset --project voter-journey
```

The wrapper starts the dev server it owns with `PUBLIC_PROJECT_ID` set to [the project the suite seeds](#the-project-the-suite-owns), and every artifact of the run — exit status, Playwright's JSON and HTML reports, the dev server's log, the observed worker and retry posture — lands in `--run-dir`. The output of starting Supabase lands there too, as `db-start.log` or `db-reset.log`, without the stack's status: `supabase start` ends by printing the local keys, and [`scripts/withhold-stack-keys.mjs`](./scripts/withhold-stack-keys.mjs) replaces that part with a marker line before anything is written. A script that writes the output of starting the stack, or of `supabase status`, to a file pipes it through the same filter; `tests/utils/withholdStackKeys.test.ts` fails on a harness script that does not. Omitting `--no-db-reset` additionally clears and re-seeds the database, which no run needs (the suite owns its own project) and which is only worth doing after a schema change. `--no-watch` starts only the frontend dev server, without the shared-package watcher that root `yarn dev` adds; it needs the packages already built, and CI passes it after its `yarn build` step.

Driving your own server — for `--grep`, a different reporter, or a debugging session — means starting it on that same project, because a plain `yarn dev` serves the **default** one and the specs would then drive an application with no elections, no questions and no nominations:

```bash
# In another shell. Without the prefix the served-project preflight aborts the run, naming both ids.
PUBLIC_PROJECT_ID=00000000-0000-0000-0000-0000000000e2 yarn dev

yarn test:e2e                              # the gate suite — 6 workers (1 on CI); EXCLUDES the @probe specs
yarn test:e2e:probes                       # the isolation probe, run on its own
yarn test:e2e --project=voter-journey      # one project (still pulls in its dependency chain)
yarn test:e2e --grep "result card"         # filter by title substring
yarn test:e2e --reporter=line              # less noisy output
```

### Void runs — a suspended host ends the run, by name

A host that is suspended in the middle of a run — a laptop that goes to sleep, a virtual machine that is paused — leaves behind a wall of timeouts and did-not-run tests that says nothing about the tree. Playwright measures its deadlines on the wall clock, which keeps counting while nothing runs, and the wake that follows drops the browser's in-flight requests. The wrapper detects this itself: from before database preparation until teardown, a heartbeat loop sleeps 2 s at a time and compares the wall-clock time that passed with those 2 s. A beat that arrives 3 s or more late means the wrapper was not scheduled for that long.

When that happens the run is **void**:

- The wrapper stops Playwright, tears down the dev server it owns as it does after any run, and exits with status **8** — never 0 and never 1, whatever Playwright had reported by then.
- The run directory holds **`VOID-host-suspend.txt`**, which records the gap in milliseconds and the UTC time of the last beat before it and of the first beat after it. Status 8 and the marker always go together: neither occurs without the other.
- `tests/scripts/e2e-evidence.mjs` carries the marker into `summary.json` (the `void` field) and `provenance.txt`, and `tests/scripts/determinism-batch.sh` records the run as `VOID`, stops, and exits 6.

A void run is evidence in neither direction: it is not a pass, and it is not a failing tree. **Do not diagnose it** — its failures belong to the suspend, not to the code. Keep the directory and make the run again under a new `--run-dir`. On GitHub Actions the failed step carries an error annotation titled `E2E run VOID (host suspended)`, and the remedy is to re-run the job.

A busy host does not trip the heartbeat. Under a CPU load several times the core count a beat arrives less than 0.2 s late, and every run records its own figures: the lateness of each beat in `heartbeat.log`, and the largest of them as `heartbeat_max_late_ms` in `env-posture.txt`. The threshold is not configurable, and a suspend shorter than it goes undetected. `tests/scripts/e2e-run.sh --self-test` exercises the detector without a run: it has to stay silent under CPU load and under a hold shorter than the threshold, and it has to fire when its loop is held with `SIGSTOP` for longer.

The wrapper also keeps an idle host awake, because the heartbeat cannot see every sleep. A sleep transition that leaves the CPU running — a dark wake — makes no beat late, yet when it starts the page's socket to the dev server closes, and the dev server's client answers a closed socket by reloading the page. The page comes back without whatever the application keeps in memory only (the voter's category selection, for one), so the failure reads as wrong content several steps later; the line that names it is `[vite] server connection lost` in the page console, which every spec built on the voter fixture root attaches to its test result as `console.log`. Where `caffeinate` exists (macOS) the wrapper holds the display, idle, disk and system sleep assertions from before database preparation until the end of teardown, and `env-posture.txt` records that as `sleep_assertion`. An assertion prevents an idle sleep. It does not prevent the sleep that closing the lid forces, so `pmset -g log` is still the check when a red run has no marker and no other cause.

### Preflight — every run proves it is driving this checkout

Before any spec body executes, Playwright's global setup runs a preflight against the base URL the specs are about to drive. It asserts that the served application's own HTTP response proves the page under test came from **this** checkout — the server must serve, and echo back, this working tree's absolute path via Vite's `/@fs` endpoint — rather than trusting that something merely answered on the port. If that does not hold, the run aborts with exit 1 before the first spec. Nothing skips it: there is no bypass flag and no bypass environment variable, and `FRONTEND_PORT` moves the target rather than disabling the check. The gate polls for liveness first (30s locally, 120s on CI — a budget ceiling that absorbs a just-started dev server, not a figure derived from observed CI timings), then asserts identity once.

**The second clause — the served project.** Immediately after the checkout is established, global setup reads the project id the served application publishes on its HTML root and compares it with the project this suite creates and seeds. A mismatch aborts the run naming both ids and the remedy; so does an absent attribute, and so does an unsubstituted placeholder — a substitution that stopped happening must never read as agreement. The clause is separate from, and runs after, the checkout clause, because a run against the wrong checkout should be diagnosed as that first. The published value is the `PUBLIC_` project id, which the browser bundle already carries, so nothing is disclosed by putting it on the document.

**Reading a success.** On the happy path the gate prints exactly one line, `E2E PREFLIGHT OK <served module root> (verified against <repo root>)`, once per Playwright invocation. It exists so that "the preflight passed" is a POSITIVE fact rather than the absence of a failure: `tests/scripts/e2e-run.sh` and `tests/scripts/determinism-batch.sh` derive their "preflight-confirmed" verdict from it, and require at least one success line **and** zero failure lines. Without it, a run in which the gate never executed and a run in which it passed produce identical evidence. Both literals are exported constants in `tests/tests/support/preflight.ts`, and `e2e-run.sh` refuses to start (exit 7) if the strings it greps for are not present there.

**Reading a failure.** The block prints these fields, in this order:

- **`reason`** — which clause failed. For the load-bearing `/@fs` clause it names the exact URL probed and the status that came back.
- **`expected port`** — the port, and the base URL, the suite was targeting.
- **`expected checkout`** — the absolute path of the working tree this run should have been driving.
- **`observed`** — what actually answered: HTTP status, the final URL _after redirects_, the `<title>`, and the **served module root**, i.e. the checkout the responding application is rooted at. The served module root is usually the single most diagnostic line, because it names the wrong checkout outright.
- **`listening process`** — `lsof` output for whatever holds the port. Best-effort: on a platform without `lsof`, or when the lookup fails or times out, the section is omitted rather than reported as an error, so it may be absent from an otherwise complete failure.

Then the two remedies, exactly as the message prints them:

- stop the other server occupying the port, then start this repo's `yarn dev`; or
- re-run with `FRONTEND_PORT=<port your server is actually on>`

**The alternate-port hatch.** `FRONTEND_PORT` works in two forms. A `FRONTEND_PORT` line in the root `.env` sets the port for the frontend dev server **and** for Playwright, and persists across sessions (the frontend's Vite config reads that file through `loadEnv`). Prefixing a single command — `FRONTEND_PORT=5273 yarn dev`, `FRONTEND_PORT=5273 yarn test:e2e` — overrides the file for that one run, because a shell value wins over `.env`. Whichever form you use, the dev server and the suite have to end up on the same port; otherwise the preflight aborts and names the mismatch.

Related: `yarn dev` now refuses to start when its port is already taken (`Error: Port <port> is already in use`) instead of quietly moving to the next one. That closes the same-address collision at source. It does not close the case where another process holds the wildcard address and both servers coexist on the same port number — that one is what the preflight catches.

Reseeding the base dataset is not a manual step and does not involve clearing the database. `data-setup-base` is a declared dependency of the voter projects, so invoking a voter spec reseeds `e2e/base` into the E2E project the suite owns, and `data-teardown-base` clears that project's rows when the family finishes. The chain is therefore just the stack plus the spec:

```bash
# Terminal 1 — the stack (Supabase + package watcher + Vite), on the project the suite seeds:
PUBLIC_PROJECT_ID=00000000-0000-0000-0000-0000000000e2 yarn dev
# Terminal 2 — the spec; its dependency chain reseeds e2e/base into the E2E project:
npx playwright test -c tests/playwright.config.ts --project=voter-journey
```

Wiping the database is no part of this: the suite's rows live in a project nothing else writes to, so there is nothing outside that project to clear. (`yarn db:seed --template e2e/base` seeds the **default** project, which the suite does not read — it is a local-development command, not a harness one. `yarn dev:clean` remains available for a stale Vite cache, which is a frontend concern rather than a data one.)

> The base dataset (`e2e/base`) is authored so the voter fixtures answer every opinion type natively; no question-set filtering is required.

### Unit tests of the harness

The harness's own utilities have Vitest unit tests beside them, as `tests/tests/utils/*.test.ts`, selected by [`vitest.config.ts`](./vitest.config.ts). `tests/` is not a workspace, so turbo does not run them; the root `test:unit` script does, as its last link, and CI runs that script.

```bash
yarn test:unit:tests              # these tests alone
yarn test:unit:tests mailedLink   # one file of them
yarn test:unit                    # every workspace's unit tests, then these
```

`scripts/assert-unit-test-coverage.mjs`, the first link of `yarn test:unit`, fails when the root script no longer chains `yarn test:unit:tests`.

## Concurrency model

- `workers: 6` (non-CI default; `1` on CI). The 6-worker pool is **global** across all projects.
- `fullyParallel: true` is the global default — files within a project run concurrently unless the project overrides `fullyParallel: false`. The journey + perm spec projects set `fullyParallel: false` (single serial test each).
- Project-level `dependencies: [...]` enforces "runs after". A project becomes eligible the moment all its dependencies finish; multiple eligible projects then share the worker pool.
- `teardown: '<project>'` runs the named teardown project after this project and all its transitive dependents complete.

### Project families (default suite, no opt-in env vars)

                                     ┌───────────────────┐

  data-setup-base ──► data-setup-entity-selection ──┐

                      (teardown: data-teardown-entity-selection)

> The `perm-per-app-notifications` projects and spec are **live** in the default `yarn test:e2e` run — not quarantined and not excluded. The spec declares an ordinary `test.describe('perm-per-app-notifications', …)` block carrying 2 tests (`tests/tests/specs/perm/perm-per-app-notifications.spec.ts`), and `playwright.config.ts` wires `data-setup-perm-per-app-notifications` → `perm-per-app-notifications` inside the perm chain, with `data-setup-perm-missing-nominations` chaining off it in turn.

- The base / journey family and the voter permutation family run **in parallel** — the permutation chain's first setup has no cross-chain dependency.
- Within the permutation family, setups chain **sequentially** because each mutates the singleton `app_settings` row; serial chaining prevents cross-permutation clobbering.
- `contestant-entity-selection` runs beside `contestant-journey`, after `data-setup-entity-selection` and `auth-setup`, and is named in the dependencies of the first permutation setup (`data-setup-perm-1e1cg1co`): it asserts UI that depends on the served entity types, and every permutation setup replaces the settings row.
- `contestant-terms-gate-phone` runs after `data-setup-base` and `auth-setup` and is named in the dependencies of the first permutation setup too: the view it opens is served only while the Contestant App is on and the row its user edits exists, every permutation setup replaces the settings row, and the first one's pre-clear deletes that row.
- The candidate settings-perm chain (`perm-disable-voter-app` → `perm-disable-contestant-app` → `perm-per-app-notifications`) is sequenced AFTER `contestant-journey` and uses distinct `e2e-perm-*` external-id prefixes for parallel-safety.

#### The invitation contract

`invitation-contract` runs [`invitation-contract.spec.ts`](./tests/specs/contestant/invitation-contract.spec.ts): one serial walk that stands where an anonymous visitor and then a signed-in user stand. It calls the `account-access` Edge Function, reads the sign-in mail from the local mail catcher, exchanges the mailed token for a session, calls `claim_invitations`, refreshes, and reads back exactly which grants exist. It drives no page; the path of a mailed link through the browser belongs to the specs that drive the application.

- **Steps, not requests.** The spec is written in the steps of [`fixtures/shared/invitationFlow.fixture.ts`](./tests/fixtures/shared/invitationFlow.fixture.ts) (seed an invitation, ask for a link, receive the sign-in link, sign in with it, claim, refresh, read the grant rows). The fixture is worker-scoped, so `beforeAll` and `afterAll` use it too.
- **A token comes out of a mail.** No test or fixture reads a sign-in token from the database, from the admin API or from a function's answer.
- **A received link is opened through `mailedLink`.** [`tests/utils/mailedLink.ts`](./tests/utils/mailedLink.ts) asserts that the link has the callback's shape for the requested locale (`assertSignInLinkShape`) and, for a spec that opens it in a browser, moves it to the run's origin (`toRunOrigin`, `runOriginFromEnv`): scheme, host and port are replaced and nothing else. A spec never builds the callback URL.
- **"Nothing was sent" waits on a witness, never on time.** A link request is answered before its work is done, and two requests' background work does not finish in request order. `askForLink` opens a completion witness with the service role, sends its id with the request and returns once that witness reads `sent` or `not-sent`; `expectNothingSent` asserts the outcome first and only then looks at the mail catcher and the accounts.
- **Fresh addresses.** Every address begins with `invitation-contract-` and is unique per run, so no test meets the one-mail-per-address-per-minute interval of an earlier run. The two tests that need a taken slot take it themselves.
- **What it writes.** Invitations and grants on the two rows the base dataset reserves for it, and users under its address prefix. `beforeAll` and `afterAll` remove all of it and put the two rows back as seeded.
- **A changed function needs a restart.** The local edge runtime does not serve an edited function until `yarn db:stop` and `yarn db:start`; until then the spec observes the old code.

#### Where a claim lands

`invitation-landing` runs [`invitation-landing.spec.ts`](./tests/specs/contestant/invitation-landing.spec.ts): three serial tests that follow a project-scope invitation through the browser. A user who has a password and is promised the project's editor role opens the mailed link and lands in the Contestant App, signed in, with the grant claimed and nothing to edit. A user promised the project's admin role signs in at the Admin App's login and is let in, although they held no grant when they submitted the form. A user nobody invited signs in at the Contestant App's login while an invitation is open for another address, is refused, and holds no grant afterwards.

- **Its own address prefix.** Every address begins with `invitation-landing-` (`INVITATION_LANDING_ADDRESS_PREFIX`). `invitation-contract` runs beside it and removes every user under `invitation-contract-`, so the two specs never share a prefix. The flow fixture takes the prefix as an option: `createInvitationFlow(admin, { addressPrefix })`.
- **No grant is written by a fixture.** Each test asserts that its user holds no grant before the application's own request claims one, and reads the grant rows with the service role afterwards.

#### Registering a user by mail

A spec that needs a user who registered by mail registers one through the invitation model. Two specs do: `contestant-journey` and `perm-localisation-positive`. The steps:

1. **Clear what an interrupted run left.** `client.unregisterCandidate(email)` removes the address's user, the user's grants and every invitation addressed to it, claimed ones included. A leftover user with a password would make the registration a returning user's sign-in, which does not meet the set-password view.
2. **Invite.** `client.inviteByEmail({ entityType, externalId, email, locale, confirmEntity })` seeds one email invitation through `create_invitations` and asks the `account-access` Edge Function for a sign-in link. `confirmEntity` is required, as it is by every seeding step of `invitationFlow`: the call states whether the invited entity is confirmed. An optional `nominations` list, each built with `client.invitationNomination`, creates or updates the entity's nominations in the same call. Seeding creates no user and writes no grant; `afterSeeding` is the hook for asserting that. The request carries a completion witness, and the call returns once the mail was handed over, so the newest mail with the sign-in subject is this request's, also for an address an earlier run mailed.
3. **Read the mail.** `emailBucket.getLinksInEmail(SIGN_IN_LINK_EMAIL_SUBJECT)`. A string subject is the whole subject of the mail; the mail holds exactly one link.
4. **Open the link as received.** `assertSignInLinkShape(link, { locale })`, then `page.goto(toRunOrigin(link, runOriginFromEnv()))`, all from [`tests/utils/mailedLink.ts`](./tests/utils/mailedLink.ts). The mailed link names the function's `SITE_URL`, which is not the port the wrapper serves the application on, so the origin is replaced and nothing else is.
5. **The callback does the rest.** It verifies the token, claims the invitation, refreshes the session and lands the user in the Contestant App, where the protected layout shows a user who has no password the set-password view in place of every page: `contestantSetPasswordGate.expectShown()`, `.setPassword(password)`, then `.expectGone()` or the next view's own step. The grant the user holds afterwards is the one the claim wrote: no fixture writes a grant for a user registered this way, and the journey asserts the user's grant rows with `invitationFlow.grantRowsOf`.

**The seeding call states whether the invited entity is confirmed.** `confirmEntity: true` confirms an entity that has a name; `false` confirms nothing and never unconfirms. A confirmed entity with a confirmed nomination is public, and voter specs read the base dataset's public rows in parallel, so a spec that invites an entity voters must not see states that entity's nominations unconfirmed in the same call. The journey does so: it confirms its candidate and states the candidate's one nomination with `client.invitationNomination({ …, confirmed: false })`. No spec hides an entity by toggling rows around a seeding.

**A password-recovery link is opened the same way.** The forgot-password page asks the `account-access` function for it, so the mail is that function's and its one link is already the application's callback URL, with the type `recovery`. `invitationFlow.recoveryLinkToOpen(address)` reads the newest mail with the recovery subject, asserts the link's shape and returns it on the run's origin; the journey's password-reset step and [`contestant-password-recovery.spec.ts`](./tests/specs/contestant/contestant-password-recovery.spec.ts) open it as received. Both give the page's request a completion witness (`invitationFlow.witnessPageRequest`) and read the link only once the witness reads `sent`: the request is answered before its mail is sent, and for an address an earlier run mailed, as the journey's is, the newest mail before that moment is the earlier run's, whose link is spent. An address that has an invitation and no account is mailed the sign-in link instead, which `signInLinkToOpen` reads. The server sends one mail per address a minute, for both kinds together: a step that asks for a second mail for an address inside that minute gives the slot back first, with `invitationFlow.releaseLinkSlot`.

## Datasets reference

### `e2e/base` — the canonical base seed

Lives in [`packages/dev-seed/src/templates/e2e/base.ts`](../packages/dev-seed/src/templates/e2e/base.ts) (the canonical base dataset). Resolve it with `--template e2e/base`. Defines:

- 2 elections + multi-constituency hierarchy (region / municipality)
- The candidate rows consumed by the journey + permutation specs
- Mixed opinion question types (Likert-5 + categorical + boolean + number) and info questions
- An `app_settings.fixed[0].settings` block that suppresses intermediate pages (questions intro, category intros, popups) by default — settings-mutating specs re-enable them transiently
- A `contestantApp` settings root that serves **both** entity types: `entityTypes: ['candidate', 'organization']` with `registrationModes: { candidate: ['email', 'code'], organization: ['email', 'code'] }`. The contestant app therefore names itself with `dynamic.contestantAppName.candidateAndOrganization` under this dataset, and the login page offers the same registration entries as a candidates-only project, because organizations are allowed the two modes candidates are
- Three rows reserved for entity-selection tests: the candidates `test-e2e-base-ca-sel-a` and `test-e2e-base-ca-sel-b` and the organization `test-e2e-base-or-sel`. Each is seeded `confirmed: false` with one nomination in the regional election (constituency `test-e2e-base-co-reg-n`) and no editor grant. Unconfirmed rows and their nominations are invisible to voters, so a test may write to these three without moving a voter assertion; a test that edits one grants its own editor and removes it again. The two candidates carry the answers of `test-e2e-base-ca-aa-1` and differ from each other on `test-e2e-base-qu-opin-base-1-likert5` alone
- Two rows reserved for invitation tests: the candidate `test-e2e-base-ca-invitation` and the organization `test-e2e-base-or-invitation`. Each is seeded `confirmed: false` with a name and with no nomination, answer or editor grant, so neither can ever be public. An invitation confirms one only when its call says so; `invitation-contract.spec.ts` sets both back to unconfirmed before and after its walk. The candidate admits one editor, so only one invitation for it can be claimed at a time
- Five rows reserved for the registration, password-recovery and signed-out scan tests: the organization `test-e2e-base-or-registration` and the candidates `test-e2e-base-ca-registration`, `test-e2e-base-ca-recovery`, `test-e2e-base-ca-scan-open` and `test-e2e-base-ca-scan-used`. Each is seeded `confirmed: false` with a name and with no nomination, answer or editor grant, so none can ever be public. A candidate admits one editor, so each test file that claims an invitation for a candidate has a candidate of its own. `tests/tests/utils/invitationConstants.ts` names the five rows and one address prefix per spec or setup; no prefix is the beginning of another, so a cleanup by prefix removes one spec's users and invitations only

### `e2e/perm/*` — permutation overlays

Lives under [`packages/dev-seed/src/templates/e2e/perm/`](../packages/dev-seed/src/templates/e2e/perm/). Each permutation template overlays the base shape for a specific settings/data configuration. A perm template serves candidates only unless it says otherwise, as `MINIMAL_BASE_APP_SETTINGS` declares: the perm family keeps the single-type app (`dynamic.contestantAppName.candidate`) on purpose, so the two dataset families differ in the served entity types. The exceptions restate the `contestantApp` root to serve both types, because an organization's editor signs in on them: `perm-organization-editing`, `perm-no-nomination` and `perm-contestant-nominations`. Every opinion question of `perm-organization-editing` is addressed to organizations alone through `entity_type`, which leaves its candidate with no opinion question to answer. An election of a template states a type that admits the template's own nominations; `perm-contestant-nominations` holds three elections of three types. Their setup projects use `test-perm-<short>-` (voter perms) or `e2e-perm-*` (candidate settings perms) external-id prefixes for parallel-safe row scoping.

### Modifiers — `--external-id-prefix`, `--seed`

Available on `yarn db:seed` invocations. `--external-id-prefix` / `--seed` control namespace + deterministic randomisation. See [`packages/dev-seed/README.md`](../packages/dev-seed/README.md).

## State assumptions per spec

Most specs assume the following baseline established by `data-setup-base`:

- An E2E project containing only this run's `test-` prefixed rows. The rest of the database is not "clean" and does not need to be: anything a local development session or a `yarn db:seed` left in the default project sits in a different project and is invisible to every query the suite issues.
- App settings suppress all intermediate pages by default (questions intro hidden, category intros hidden, popups null)
- Storage buckets `private-assets` + `public-assets` exist

State that specs **must not assume** (because the chain re-seeds):

- Stable Postgres UUIDs — specs use `findData({ externalId: { $eq: 'test-...' } })` to look up rows
- Specific filter counts (depends on seed evolution)
- Browser storage isolation between specs in the same serial describe — settings specs use `storageState: { cookies: [], origins: [] }` to start clean

### The project the suite owns

Every row the suite writes and every row it reads belongs to one project, `00000000-0000-0000-0000-0000000000e2` — deliberately **not** the project the Supabase seed creates, which is where `yarn db:seed` and an ordinary `yarn dev` session put their data. That id is a committed default, so a plain checkout needs no configuration to run the suite; `E2E_PROJECT_ID` overrides it, and because the default is spelled out independently in the harness's TypeScript resolver **and** in `tests/scripts/e2e-run.sh`, an override belongs in the environment, where both of them read it. Neither is authoritative over the other.

Playwright's global setup creates the project idempotently, immediately after the served-application preflight — in that order, because creating rows against a server that turned out to be the wrong checkout would be writing into a database the run has no business touching.

Teardown clears the project's **contents** and deliberately leaves the **project row** in place. Content teardown is prefix-scoped, so it never needed the row gone; keeping the row means run _N+1_ finds it already present and takes the same idempotent code path run _N_ took, instead of the create-path being exercised only on the first run after a wipe. A project row with nothing in it is inert.

This is what makes a run independent of the database's prior state, and it is why `tests/scripts/e2e-run.sh` accepts `--no-db-reset`: the flag skips the reset while still starting Supabase (the readiness poll needs something to poll), and records `db_reset=false` plus the resolved project id in the run's `env-posture.txt`. Use it for back-to-back evidence runs, and whenever you want a run to prove it can start from whatever the last one left behind. Omit it when you have changed the schema and want migrations reapplied.

## Common pitfalls

- **`yarn db:reset` in another terminal will wipe the suite mid-run** — the teardown projects are the only legitimate path to clear test data. Don't reset while the suite is running. This warning carries _more_ weight now that no run asks for a reset: reaching for that command by hand is the one remaining way to destroy a run's data underneath it.
- **A stored session is read-only.** `STORAGE_STATE`, `TERMS_PENDING_STORAGE_STATE`, `MULTI_ENTITY_STORAGE_STATE`, `NO_ENTITY_STORAGE_STATE` and `PASSWORDLESS_STORAGE_STATE` are each one file loaded by every test that names it, so a spec that signs one out ends it for all of them and the rest of the run cascades. A case that must sign out registers an identity of its own and signs it in on the sign-in screen, as the "nothing to edit" case of `contestant-entity-selection.spec.ts` does. The three sessions `data-setup-perm-organization-editing` stores differ in one respect: they belong to `perm-organization-editing.spec.ts` alone, so that spec edits and saves under them. Signing one out would still end it for every later test of the file. `TERMS_PENDING_STORAGE_STATE` has two readers, the axe scans of the terms-of-use view and `contestant-terms-gate-phone`, and for it accepting the terms is as final as signing out: neither reader presses the view's Continue. `PASSWORDLESS_STORAGE_STATE` is read by the set-password view's scans and phone checks, and saving a password under it is as final: no reader saves one.
- **A used invitation survives its user.** Deleting a user leaves the invitations that user claimed in place and still claimed, so a later run that seeds the same invitation meets a duplicate. `unregisterCandidate` and `deleteAllTestUsers` remove a user's invitations first; a spec that deletes a user any other way calls `removeInvitations` itself.
- **"No such user" is always a complete read.** Every `SupabaseAdminClient` lookup of an auth user by address pages through all the users and throws when the listing fails. `getAuthUserByEmail` returning `undefined`, and `unregisterCandidate` or `revokeEntityGrant` returning at all, each mean that every user was read. A setup or teardown therefore fails, naming the method, when the auth users cannot be listed; it never reports a cleanup it did not make.
- **A candidate admits one editor.** `SupabaseAdminClient.grantEntity` refuses, by name, a candidate that already has one. Give a new identity a row no other identity of the run edits; an organization admits several editors.
- **`STORAGE_STATE` (the visual-regression candidate session) is shared** within the opt-in visual chain. If you add a candidate spec that revokes a token, sequence it appropriately.
- **Fixture timeouts vs locator timeouts.** Per-test `test.setTimeout(N)` and the global timeout are wall budgets — keep them large enough for fixture warm-up (cold dev-server hydration can run 5-8s). Per-locator `{ timeout: N }` options should be smaller (≤ 10s) so individual element waits fail fast; the test-level budget contains them. Timeout constants live in [`tests/tests/helpers/timeouts.ts`](./tests/helpers/timeouts.ts).
- **Trace files.** Locally, traces are recorded for every test but kept only for **failures** (`trace: 'retain-on-failure'`), so a green run leaves no trace zips behind. In CI (`CI` set, which also turns on retries) a trace is recorded only for a test's first retry (`trace: 'on-first-retry'`), so first attempts run without the recorder's overhead. The `performance` project records no trace at all, because trace recording runs inside its measured window (see its comment in `tests/playwright.config.ts`) — that is expected, not a misconfiguration. A failing test's trace lands in `tests/playwright-results/<spec>/trace.zip`; open with `npx playwright show-trace <path>`. If you need the traces of _passing_ tests for an investigation (grepping console output across a green run, say), temporarily set `trace: 'on'` in `tests/playwright.config.ts` and revert it afterwards — it costs 260-340 MB per full-suite run.
- **Missing-nominations modal.** The voter app's `(located)/+layout.svelte` renders a `<Modal>` (`data-testid="voter-missing-nominations-modal"`) only when the selected election and constituency leave some election without nominations, and removes it from the DOM otherwise. A spec on a fully nominated path asserts it absent with `toBeHidden`, as `selectConstituencyAndAdvance` in [`tests/tests/utils/voterIntro.ts`](./tests/utils/voterIntro.ts) does after Continue; `perm-missing-nominations.spec.ts` asserts the modal's contents. The modal is a DaisyUI `.modal` `<dialog>`, which keeps `display: grid` when closed, so a rendered modal's open state is its native `open` attribute, not its visibility.
